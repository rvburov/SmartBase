## Многопользовательские проверки

[Матрица покрытия](../docs/developer/testing/concurrency-coverage.md) связывает каждый раздел
с тестами и оставшимися границами. [Нагрузочный стенд](../docs/developer/testing/concurrency.md)
описывает параметры, отчеты и фактические результаты; наличие сценария не означает успешный
прогон. Все сборки и проверки одной копии выполняются последовательно.

Готовая последовательная матрица — [run-concurrency.sh](run-concurrency.sh):

```bash
./Tests/run-concurrency.sh --out /tmp/sb-concurrency-small
./Tests/run-concurrency.sh --clients 1000 --out /tmp/sb-concurrency-thousand
```

По умолчанию — 8 клиентов, все восемь сценариев и три профиля. Есть фильтры `--provider`
и `--scenario`; скрипт собирает стенд один раз, сохраняет `matrix.tsv`, журналы и отчеты
каждой попытки, продолжает матрицу после падения и завершает ее ненулевым кодом.

`Integration` включает `ConcurrentLifecycleTests` и модульные `ConcurrentFieldTypes/StaleRecovery/Structure/Planning/Library/Access/Integration/Backup/ConnectionRecovery/PersonalFilesTests`.
Они используют собственные временные БД/файлы; PG требует локального сервера на 5455,
нативные копии — `pg_dump`/`pg_restore`, отрицательные проверки пароля — password-auth.

`multiuser` поддерживает `lifecycle`, `hotcell`, `rollback`, `planning`, `library`,
`integrations`, `access` и `structure`. Сначала малый запуск, затем каждый выбранный
сценарий с нужным числом сессий на трех профилях:

```bash
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile wal --scenario planning --clients 8
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile wal --scenario planning --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile shared --scenario planning --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider postgres --profile server --scenario planning --clients 1000
dotnet run -c Release --project Tests/ConcurrentUi -- --mode all --out /tmp/sb-concurrent-ui-new
```

`access` при 1000 клиентах моделирует 500 авторов и 500 читателей, а не 1000 успешных
писателей. Личный реестр/заметки проверяются в отдельных хранилищах; расширения — восемью
настоящими обработчиками независимых файлов и отдельными конфликтами общих журналов.
`ConcurrentUi` — один UI-наблюдатель, а не 1000 окон; нативные баннеры, SMB/NFS и разные
ОС требуют своего окружения. Без заданного `--p95-ms` функциональный `Passed` не является
гарантией приемлемой задержки.

## Стенды интерфейса

`WindowPlacement` — отдельный стенд размещения окон без экрана. Команда:

```bash
dotnet run --project Tests/WindowPlacement -f net10.0
```

Запускать после правок `WindowPlacement`, `DialogFit`, `WindowZoom` и общего стиля `Window`.
Правило размещения и взаимодействие с модальными владельцами описаны в
[dialogs.md](../docs/developer/ui/dialogs.md#положение-дополнительных-окон).
Геометрия безголовой среды не заменяет проверку нативных рамок и нескольких мониторов на
Windows, macOS и Linux.

`MarkupLayout` стоит отдельно от `Unit`, потому что ему нужен `Avalonia.Headless`, а `Unit`
объявлен без внешних зависимостей. Проверяет то, чего не видно без раскладки: что абзац не теряет
перенесенные строки и что просвет между блоками равен пустым строкам исходника. Обе эти ошибки уже
были — прогонять после любой правки `Controls/Markup`.

`EditGeometry` — по той же причине отдельно. Держит правило «текст не двигается при смене
состояния» (docs/developer/ui/theming.md). Проверяет четыре вещи: бокс даты/времени компенсирует
отступом прирост рамки в фокусе; надпись заголовка и поле его правки стоят в одной точке и одной
высоты; ячейка таблицы (настоящая база, настоящие клики — первый выделяет, второй открывает
правку) не двигает ни текст, ни рамку выделения и не заводит второй рамки от темы; плоский режим
редакторов не держит своей высоты. Стенд сам следит, что состояние действительно сменилось, —
иначе проверки проходили бы вхолостую.

Расположение текста (меню «Форматирование текста») стенд проверяет в высокой строке при всех
девяти сочетаниях горизонтали и вертикали: у полей ввода («Название», текст, число) показ и правка
совпадают до физического пикселя всегда, у списка и даты — по вертикали всегда, по горизонтали
слева и по центру (справа их значение встает левее кнопки редактора). По центру глифы стоят на
дробных позициях, а поле ввода красит текст чернее показа, поэтому там допускается пиксель по
одному краю «чернил», но не общий сдвиг обоих краев. Кадры снимаются с указателем вне таблицы:
подсветка наведения совпадает по цвету с серым фокуса списка и прятала его. Отдельно сверяется
фон рядом с текстом (внутри полосы редактора) и заливка окрашенной ячейки у края, куда редактор
в полосе не дотягивается. `EDITGEOM_ALIGN=center/top` — только одно сочетание (разбор одного
расхождения); с `EDITGEOM_DUMP` стенд печатает, где на самом деле стоят надписи и презентеры
редактора.

Рисованную сетку таблицы (переключатель разработчика, план drawn-grid.md) стенд проверяет
дочерним процессом с ключом `--drawn`: переключатель читается раз на процесс. Ее показ рисует
сама сетка, контрола с точкой начала текста у него нет, поэтому ячейка («Название», текст,
число, список, дата) сверяется по пикселям кадра: «чернила» текста в показе и в правке обязаны
совпасть до физического пикселя; заодно — нет своей рамки у редактора, рамка выделения видна в
обоих состояниях, фон с подсветкой тот же. Переменная `EDITGEOM_DUMP=<папка>` сохраняет кадры
обоих состояний в PNG для разбора.

Стенд намеренно ЧЕСТНЫЙ: настоящий шрифт (Skia, `UseHeadlessDrawing=false`) и RenderScaling=2,
выставленный рефлексией у headless-окна. На подставном шрифте и масштабе 1 главный дефект —
вертикальный сдвиг пары показ/правка на полпикселя из-за разных сеток округления — математически
невозможен, и стенд был бы слеп (проверено: без LineHeight-токенов он ловит ровно +0.50px, с
ними зеленый). Прогонять после правок `Border.timeField`, шаблонов ячейки, навбаров с названием,
плоского режима редакторов и `FontScale`.

`PopupGeometry` — отдельно по той же причине. Мерит, где ОКАЗЫВАЕТСЯ раскрытая панель
относительно своего якоря: зазор сверху и сдвиг левого/правого краев. Прогоняет один и тот же
набор при масштабе окна 1 и 2, при зуме приложения 100 и 110 %, и по очереди снимает у плашки
`Margin`, рамку, скругление и зум-обертку — видно, какое число чем создано. Эталон в выводе —
выпадашка `ComboBox`: с ней сверяются панели, собранные `Flyout`.

Ограничение платформы честно оговорено в шапке стенда: headless не умеет отдельных попап-окон
(`HeadlessWindowImpl.CreatePopup()` возвращает `null`), попап живет в `OverlayLayer` того же
окна. Позиционер при этом ТОТ ЖЕ (`ManagedPopupPositioner`, его же создает macOS), поэтому
размеры и выравнивание краев честные, а вот огрубление позиции настоящего попап-окна до целого
физического пикселя, ограничения у края монитора и тень окна macOS стенд не воспроизводит.

`DocReader` — стенд панели чтения документа, отдельно по той же причине (нужна живая Avalonia).
Ловит то, чего не видят ни сборка, ни модульные тесты: ссылка на ресурс в разметке
(`StaticResource`) разрешается при ЗАГРУЗКЕ, и опечатка в ключе иконки роняет панель ровно в тот
момент, когда человек нажал «Прочитать». Плюс проверяет то, что видно только на живом контроле:
переводы строк документа дожили до экрана отдельными строками, подсветка собралась из `Inlines`,
текущее совпадение покрашено иначе прочих, счетчик «2 из 5» шагает по кнопке, а скан без
текстового слоя объясняется словами. Прогонять после правок `DocReaderView`, `DocReadText` и
`DocHighlight`; кроме того, его гоняют `./Tests/run-all.sh` и CI (job `tools`). Разделы стенда
независимы: провал одного не уносит из отчета остальные, а в конце печатается сводка по разделам.

Сценарий позднего текста управляет порядком завершения разборов: текст разрешается только после
перехода по страницам PDF. Большая книга проверяет, что скрытый текст не пересчитывается при
смене запроса, а при возврате в «Текст» получает нужную подсветку. Отдельно проверяются снятие
панелей, остановка таймеров, отмена чтения, отсутствие удерживающих подписок и повторное
присоединение без дублирования обработчиков.

Для изменений связей дополнительно обязательны четыре самостоятельных режима `RecordPage`:

```sh
dotnet run -c Release --project Tests/RecordPage -- --only relations --out /tmp/relations-ui
dotnet run -c Release --project Tests/RecordPage -- --only relationcomputed --out /tmp/relationcomputed-ui
dotnet run -c Release --project Tests/RecordPage -- --only relationintegrity --out /tmp/relationintegrity-ui
dotnet run -c Release --project Tests/RecordPage -- --only backlinks --out /tmp/backlinks-ui
```

Все четыре создают свою малую базу и не требуют `--db`. Режим `relations` проверяет сохранение
и отмену настроек, выбор и поиск по свойствам, автосвязь (в том числе по нескольким парам:
строки пар, флажок свертки, итог подбора, повтор пары, правило более новой версии, строка
«Подбирается автоматически» в списке), условие выбора записей (строки окна, переспрос пустого
условия, подсказка и пометка прежней связи в списке выбора), права и защиту от устаревшего
результата поиска; сохраняет кадры `relations-auto-dialog.png`, `relations-auto-pairs.png` и
`relations-condition-dialog.png`. Режим `relationcomputed`
проверяет показ, запрет ручной правки и обновление lookup/rollup после изменения данных.
Режим `relationintegrity` открывает настоящее окно из настроек и проверяет чтение без записи,
выбор и отмену исправления, отказ копирования, проверенную копию перед исправлением,
повторную проверку и скрытие старого отчета после отзыва прав. Режим `backlinks` проверяет
блок «Ссылаются на эту запись»: место после «Добавить свойство», пустые карточки, список
источников (страницы, точное число, поиск, переход по строке и Enter), Delete и правый клик по
карточке ссылок и ответ, пришедший во время ввода.
Любой провал дает ненулевой код выхода без флага `--gate`; этот флаг нужен для порогов
режима `perf`. Эти проверки дополняют `Unit` и `Integration` и не входят в `run-all.sh`.

Прогнать автотесты ядра, стенд панели чтения и BackupUi: `./Tests/run-all.sh`; вместе с расширениями — `./Tests/run-all.sh --with-extensions`.

`RecordPage` перед проверками измеряет текст системным шрифтом. Если высота равна нулю,
стенд останавливается с сообщением о шрифте: результаты кликов и геометрии в такой среде
недостоверны. Нужен рабочий шрифт TrueType/OpenType; на Linux выбор проверяется через
fontconfig, в том числе с отдельной конфигурацией `FONTCONFIG_FILE`.

Тесты расширений живут отдельно намеренно: расширение удаляется вместе со своей папкой тестов, и
тесты ядра о расширениях не знают — см.
[docs/developer/testing/extension-tests.md](../docs/developer/testing/extension-tests.md).


### Полный путь чтения библиотеки

`dotnet run --project Tests/Benchmarks -f net10.0 -- docread --count 20 --pages 10 --csv /tmp/docread.csv`
создает повторимый набор PDF/DOCX/XLSX/MD и отдельно меряет разбор, запись в настоящий FTS
и открытие XLSX в модель таблицы. `--dir /папка` использует готовые файлы без изменения;
несуществующая или пустая папка возвращает ошибку. Два прохода CSV различают первый и прогретый
процесс; кеш ОС не сбрасывается. Бенчмарк запускать без параллельной сборки и тестов.


Для изменений файлового свойства есть три самостоятельных режима `RecordPage`:

```sh
dotnet run -c Release --project Tests/RecordPage -- --only fileauto --out /tmp/file-ui --ref /tmp/file-ui-reference
dotnet run -c Release --project Tests/RecordPage -- --only fileprobe --out /tmp/file-ui --ref /tmp/file-ui-reference
dotnet run -c Release --project Tests/RecordPage -- --only fileload --files 100000 --out /tmp/file-ui --ref /tmp/file-ui-reference
```

Они не требуют `--db`. `fileload` использует общий `FileAutoBench`: во время построения и
запросов каталога настоящий headless dispatcher принимает ввод, работает UI-таймер.
В full CI после трех проверок связей последовательно идут `fileauto`, `fileprobe` и
`fileload --files 100000`. Каталог содержит синтетические метаданные путей, не физические файлы;
это smoke-проверка, а не доказательство скорости реального диска.

Масштаб 10 млн проверяется отдельным ручным запуском `--only fileload --files 10000000`;
автоматический CI его не запускает. Замер 21.10.2026 на синтетических метаданных с настоящим
SQLite-индексом и приемом ввода приведен в [описании файлового свойства](../docs/developer/architecture/data-types/file.md#проверка-масштаба-21102026).
