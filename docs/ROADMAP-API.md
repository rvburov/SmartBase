# ROADMAP-API — Интеграции: обмен с другими программами и автоматизация

Отдельная дорожная карта подсистемы **«Интеграции»**: работа со сторонними программами по API,
прием данных извне и сценарии автоматизации над разделами приложения. Выделена из пункта
«API / автоматизации» раздела «Долгосрочно» основного [ROADMAP.md](ROADMAP.md).

> **Состояние на 13.09.2026: план выполнен целиком, шаги 0–16 закрыты.** Работают контур
> безопасности, соединения и запросы, обмен «ответ → коллекция», папка-приемник, сценарии с

>

> интерфейс под объемы, 15 — администрирование безопасности в панели администратора, 16 —
> менеджер паролей.
>
> **Документ описывает замысел, а не код.** Отметка `[x]` означает «шаг закрыт», а не «сделано
> все, что обещано его разделами»: часть обещаний осталась долгом, и весь он перечислен в
> разделе «Долг по закрытым шагам» ниже. Сверяться с кодом надо по нему, а не по отметкам.

> **Определяющее требование.** В базах хранится секретная информация, программу проверяет
> служба безопасности. Сама по себе программа не отправляет наружу ничего, и пользователь не
> может завести выгрузку куда захочет. При этом ни одна функция не убирается: интеграции и
> автоматизация работают в полном объеме — внутри рамок, которые задает не тот, кто их
> настраивает (раздел 10).

> **Имена сторонних программ — только в этом файле.** Здесь конкретные названия оставлены
> намеренно: файл рабочий, по нему проектируют, и «как это сделано у них» — половина его пользы.
> **Дальше их быть не должно** — ни в документации `docs/developer/` и `docs/user/`, ни в
> комментариях кода, ни в подписях интерфейса, ни в инструкции пользователя. Там пишем родовым
> именем: «программа-мессенджер», «программа-бухгалтерия», «учетная система», «внешний сервис»,
> «табличный редактор». Причин три: документ читают проверяющие, и названный мессенджер как
> канал обмена сам по себе повод к вопросам; названия меняются, а тексты живут годами;
> в интерфейсе и инструкции конкретное имя читается как обещание поддержки, которого никто не
> давал. Это относится и к макетам экранов ниже: при переносе в инструкцию пользователя примеры
> соединений переименовываются.

## 1. Три разных «API» — их надо развести

Под «работать с другими программами через API» прячутся три задачи с разной ценой и разными
местами в интерфейсе.

| Направление                                                         | Пример                                                                             | Нужен ли слушающий порт | Цена       |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------- | -------------- |
| **Наружу, тянем** (pull)                                      | раз в час забрать заказы из чужого API в коллекцию | нет                                      | низкая   |
| **Наружу, толкаем** (push, исходящий вебхук) | запись создана → POST в Bitrix24 / Telegram / 1С                         | нет                                      | низкая   |
| **Внутрь** (входящий)                                      | 1С или скрипт сам кладет запись в базу                     | да, либо суррогаты           | высокая |

Четвертое, названное отдельно, — **автоматизация**. Это не API, это клей: событие → условие →
действия, где одним из действий может быть HTTP-запрос, другим — создание записи, третьим —
запуск расширения. Именно она должна пронизывать все разделы.

## 2. Модель: четыре объекта, которые настраивает пользователь

Разделение принципиальное и повторяет n8n, Home Assistant и Grafana: **учетные данные отдельно
от запросов, запросы отдельно от сценариев.**

1. **Соединение** — «куда и под кем ходим»: базовый адрес, способ авторизации (нет / ключ в
   заголовке / Bearer / Basic / ключ в query), сам секрет, таймаут, дополнительные заголовки.
   Настраивается один раз, переиспользуется всеми запросами.
2. **Запрос** — «что дергаем»: метод, путь `/orders?since={{последний_запуск}}`, заголовки, тело,
   пагинация (страница / курсор / offset), путь к массиву в ответе (`data.items`). Обязательна
   кнопка **«Проверить»** с показом сырого ответа — без нее пользователь чужой API не настроит
   никогда.
3. **Привязка** — «как ответ ложится в коллекцию»: колонка ответа → поле коллекции, ключ
   сопоставления (по какому полю обновлять существующую запись), что делать с новыми и
   пропавшими. Это существующий `ImportPlanner`, только источник не файл.
4. **Сценарий** — «когда и что»: триггер + условия + шаги.

Плюс **журнал запусков**: когда, что, сколько записей, код ответа, тела запроса и ответа с
вырезанными секретами. Без журнала интеграция неотлаживаема — именно журнал делает пригодными
к жизни n8n и Airtable Automations.

### Триггеры сценариев

Все источники уже есть в приложении:

- **по расписанию** — каждые N минут / в HH:MM (`NotificationScheduler`, `Utils/BackgroundWorker`);
- **изменение данных** — создана/изменена/удалена запись, поле стало равно значению. Свои правки
  дает шина [ChangeBus.cs](../Database/ChangeBus.cs), чужие — [ChangePoller.cs](../Database/ChangePoller.cs)
  поверх `change_log`. Готовая шина событий, писать нечего;
- **календарное событие** — за N минут до срока (`TaskEventScheduler`);
- **вручную** — кнопка в навбаре коллекции и пункт контекстного меню таблицы;
- **при старте и остановке приложения**.

### Шаги (действия)

HTTP-запрос · импорт ответа в коллекцию · создать/обновить запись · экспорт выборки в файл или
на адрес · показать уведомление · запустить расширение.

### Как данные попадают в коллекцию

Руками пользователь не пишет ничего: это тот же экран сопоставления, что уже работает при импорте
Excel.

```
пробный запрос или файл из папки
   → показ первых 20 строк таблицей
   → сопоставление мышью:  колонка источника → поле коллекции
   → ключ сопоставления:   «Номер заказа»
   → режим: добавлять · обновлять по ключу · и то и другое
   → запись через ConstructorRepository
```

Строка источника = запись, колонка = поле. Вложенный JSON приводится к таблице заранее: путь к
массиву (`data.items`) и точка для вложенных полей (`client.name`). Неизвестная колонка либо
игнорируется, либо создает поле — галочкой, с угадыванием типа, как при импорте. Плохие строки
уходят в отчет, остальные принимаются: механизм `ImportErrors` уже есть. Пропавшие на той стороне
записи по умолчанию не трогаются — удаление по чужому молчанию слишком дорого стоит.

Наружу — зеркально: коллекция и фильтр (какие записи), затем таблица «поле коллекции → имя в
JSON». Помеченные поля в этом списке не появляются (раздел 10.6).

## 3. Где хранить и кто выполняет — главная ловушка

Базы лежат в общей папке и открыты на нескольких машинах одновременно. Если сценарий положить
**в файл базы**, событие «создана запись» выстрелит столько раз, сколько запущенных копий
программы его увидело: пять коллег — пять POST-ов в стороннюю систему. Это не риск, а гарантированное
поведение поллера.

- **Соединения и секреты — только локально**, в `app.db`, секрет через
  [SecretProtector.cs](../Utils/SecretProtector.cs) (DPAPI / Связка ключей — механизм уже написан
  для паролей PostgreSQL). Секрет **никогда** не попадает в файл базы: файл не шифруется и ездит
  по сети.
- **Сценарии — тоже локально**, с явной надписью «работает на этом компьютере». Побочный эффект
  полезный: в боевой среде естественно назначить одну машину оператором обмена.
- **Обмен настройками между людьми — экспортом сценария в JSON** без секретов. Ложится в
  «Этап 8 — Шаблоны систем» основного ROADMAP.
- Позже, если понадобится общий сценарий в базе, — поле «исполнитель: имя машины» плюс захват
  блокировки строкой в базе. Надстройка, а не фундамент.

**Права:** завести действие в `PermAction` («управление интеграциями») и требовать локального
подтверждения при первой отправке данных наружу. Иначе коллега с доступом к общей базе сможет
настроить выгрузку чужих данных куда угодно — см.
[users-permissions.md](developer/architecture/users-permissions.md).

## 4. Место в интерфейсе

Разбор трех вариантов, зафиксированный, чтобы не возвращаться:

- **Расширение** — отпадает по собственному контракту. [IExtension](../Extensions/IExtension.cs)
  намеренно ни от чего не зависит и живет в своем окне, а автоматизация обязана дотягиваться до
  базы, календаря, задач, уведомлений и до других расширений. Сделать ее расширением — сломать
  единственное правило, ради которого раздел расширений существует.
- **Раздел настроек** — выбран. «Настройки» здесь не диалог с галочками, а полноценный модуль с
  сайдбаром, где уже живут тяжелые панели: управление базами, резервное копирование, таблица
  журнала в «Диагностике». Так же устроен Home Assistant.
- **Раздел Activity bar** — правилен в конечной точке, но восьмая иконка ради функции для единиц
  пользователей не окупается на старте.

**Итог — три уровня, и это не компромисс, а разные вещи:**

1. **Настройки → «Интеграции»** — соединения, запросы, сценарии, доступ извне, журнал.
2. **Вынос в раздел Activity bar**, когда сценарии станут рабочим инструментом (ориентир: у людей
   появляется 5+ сценариев). Скрыт по умолчанию через
   [ViewCatalog.Navigation](../Settings/ViewCatalog.cs) и включается галочкой в «Оформлении».
   Переезд дешевый: панели переносятся целиком, ключи в `app_settings` не меняются.
3. **Точки вызова — внутри существующих разделов.** Пользователь не должен ходить в раздел, чтобы
   выгрузить заказ: пункт «Действия» в контекстном меню таблицы, кнопка в навбаре коллекции, пункт
   в панели записи. Это те же точки встраивания, что запланированы для расширений
   ([extensions/overview.md](developer/features/extensions/overview.md), «режим 2») — въезжать туда
   автоматизация и расширения должны **одним механизмом**.

### Как выглядит экран

Сайдбар настроек плоский, и шесть строк интеграций задавят остальные разделы. Поэтому одна строка,
а вкладки внутри — **выпадающим списком в навбаре раздела**, ровно как виды у календаря.

```
 Настройки     │ Интеграции                              [Соединения  ▾]   ← навбар
 …             │───────────────────────────────────────────────────────────
 Расширения    │ Соединения                                   [+ Добавить]
▶Интеграции    │
 Инструкция    │ Поставщик АО «Ромб»    https://api.romb.local/v2   ● ok
 Диагностика   │ Telegram-бот           https://api.telegram…       ● ok
 О программе   │ 1С Обмен               http://srv-1c:8080          ! 401
               │───────────────────────────────────────────────────────────
               │ Карточка соединения
               │ Название · Адрес · Авторизация [Bearer ▾]
               │ Токен  ••••••••••••          [Проверить связь]
               │ Заголовки  + · Таймаут 30 с

 список навбара:  Соединения · Запросы · Сценарии · Доступ извне ·
                  Безопасность · Журнал
```

Контрол уже есть — тот же `ComboBox` `ViewSelector`, которым навбар календаря переключает виды
([NavbarCalendar.axaml](../Controls/Components/Navbar/NavbarCalendar.axaml)). Живет он в
`HeaderBar` раздела настроек, который и сейчас показывает заголовок по ключу категории и
контекстные кнопки (`ShowDatabaseActions`, `ShowLogsActions` в
[SettingsView.axaml.cs](../Views/Settings/SettingsView.axaml.cs)): добавляется еще одно
контекстное состояние — в «Интеграциях» переключатель виден, в остальных разделах скрыт.

**Список вкладок берется из своего маленького реестра, а не из [ViewCatalog](../Settings/ViewCatalog.cs).**
Там позиция пункта — глобальный номер вида, на который завязаны сохраненные у людей значения, и
оттуда же растут обе настройки «Оформления» — вид по умолчанию и галочки видимости. Прятать
«Безопасность» или «Журнал» галочкой нельзя по той же причине, по которой в каталоге намеренно
нельзя скрыть «Настройки»: спрятав, человек лишится способа вернуть их обратно. Реестр вкладок —
три строки по образцу [SettingsRegistry](../Settings/SettingsRegistry.cs).

**Последняя открытая вкладка запоминается** в `app_settings`, как `calendarView` у календаря.
Настройку «вкладка по умолчанию» в «Оформлении» при этом не заводить: это не режим просмотра
данных, а место внутри раздела.

**Смена вкладки закрывает панель деталей.** У «Журнала» и «Безопасности» таблицы во всю высоту, и
панель деталей строки лежит в корне, а не внутри панели раздела — как уже сделано в
«Диагностике» (`CloseLogsDetail`). Иначе детали переживут переключение и повиснут поверх чужой
вкладки.

Вкладка **«Безопасность»** (раздел 10.16) стоит предпоследней и только показывает: политику,
режим контура, белый список, действующие направления и расход квот. Менять там нечего — в этом
и смысл.

Плюс к раскладке: когда «Интеграции» переедут в Activity bar своим разделом, переключатель уже

## 5. Два режима конструктора запроса

Ключевое правило: **простой режим не создает «другой» запрос.** Пресет — это мастер, заполняющий
тот же самый объект «Запрос»; после него можно нажать «Показать подробно» и увидеть метод, адрес,
заголовки и тело. Обратный путь (эксперт → пресет) не нужен.

- **Простой** — карточки готовых систем (вебхук Bitrix24, бот Telegram, «просто JSON по ссылке»,
  «файл по ссылке») и **вставка cURL из буфера**. Последнее сильнее всех пресетов вместе взятых:
  человек копирует строку из документации сторонней программы, программа ее разбирает — запрос настроен. Это и
  есть «пользователь настраивает API сам».
- **Экспертный** — метод, адрес, заголовки, тело, пагинация, путь к массиву в ответе, переменные.

Переменных нужен минимум, иначе получится язык: `{{поле.Название}}`, `{{запись.id}}`,
`{{сегодня}}`, `{{последний_запуск}}`, `{{соединение.адрес}}`. Последняя важнее, чем кажется: она
дает инкрементальную выгрузку «отдай изменения с прошлого раза» вместо перекачки всего каждый час,
что на медленной сети критично.

## 6. Входящий доступ: кто кому звонит

Суть: у программы на рабочем столе нет постоянного адреса, как у сайта. Дотянуться до нее можно
тремя способами, и выбор — не про код, а про то, **где физически стоит отправитель**.

### 6.1. Только этот компьютер — `127.0.0.1`

Постучаться могут лишь программы, запущенные на той же машине; с соседнего ПК невозможно
физически, даже зная токен.

- Кому годится: 1С, скрипт, макрос Excel, Power Automate Desktop — все, что стоит рядом.
- Что нужно от админов: **ничего**.
- Безопасность: максимальная, снаружи не видно вообще.

### 6.2. По локальной сети — адрес компьютера

Постучаться может любой ПК сети: сервер, машина коллеги, служебная задача.

- Что нужно от админов: **права администратора один раз** — разрешение занять адрес
  (`netsh http add urlacl`) плюс правило брандмауэра. Делается инсталлятором из [Setup/](../Setup/).
- Безопасность: запрос может послать любой в сети, защита только токеном, и по обычному HTTP он
  идет открытым текстом. Для заводской сети приемлемо, но сказать об этом надо прямо.
- Подвох: работает, только пока программа запущена на машине-приемнике. Выключили ПК — обмен встал
  молча.

### 6.3. Папка-приемник

Двери нет: сторонняя программа кладет файл в общую папку (`P:\Обмен\Входящие`), а программа раз в
полминуты туда заглядывает.

- Кому годится: всем. Файл умеет положить что угодно — 1С, скрипт, планировщик, человек руками.
- Что нужно от админов: **ничего**, общий диск уже есть.
- Безопасность: правами на папку, тем же механизмом, что и базы.
- Уникальное свойство: **работает асинхронно** — файл дождется, пока приемник включат. При
  выключаемом сервере это не мелочь, а главное.
- Минус: не мгновенно и нет мгновенного ответа отправителю — только квитанцией.

### 6.4. Чего не дает ни один вариант

**Достучаться из интернета.** Программа внутри локальной сети снаружи не видна: нужен белый IP,
проброс портов и согласование с ИТ — отдельный проект, и делать его не планируется.

Правильный ответ для облака — **перевернуть направление**: не они стучатся, а программа раз в N
минут сама забирает новое (`pull`). Так работает Power Query в Excel и почти вся настольная
интеграция. Остается редкий случай, когда облако умеет только вебхук и не отдает список — тогда
нужен посредник с постоянным адресом: любой сервер принимает вебхук и кладет файл в
папку-приемник. Со стороны программы это тот же канал, доработок не требует.

### 6.5. Сводно

|                                              | Кто может прислать                    | Права админа    | Работает при закрытой программе | Мгновенно        |
| -------------------------------------------- | ----------------------------------------------------- | -------------------------- | ----------------------------------------------------------- | ------------------------- |
| **Только этот ПК**         | программы на этой же машине    | не нужны            | нет                                                      | да                      |
| **По сети**                      | любой ПК локальной сети           | нужны один раз | нет                                                      | да                      |
| **Папка-приемник**        | кто угодно с доступом к папке | не нужны            | **да**                                              | нет (раз в 30 с)  |
| **Опрос чужого API (pull)** | — (забираем сами)                        | не нужны            | нет                                                      | по расписанию |

### 6.6. Раскладка под боевую среду

Права администратора идут через службу ИТ и долго — заявка на каждый ПК. Значит **сетевой
слушатель отпадает как массовое решение**, и маршруты получаются такие:

| Кто присылает                              | Как доходит                                                  | Согласования         |
| ------------------------------------------------------ | ---------------------------------------------------------------------- | -------------------------------- |
| 1С / скрипт / Excel на том же ПК       | HTTP на`127.0.0.1`                                                 | никаких                   |
| Сервер или другой ПК в сети      | **папка-приемник**                                  | никаких                   |
| Внешний сайт / облако                 | опрос по расписанию (pull)                            | никаких                   |
| Облако, умеющее только вебхук | релей на сервере кладет файл в папку     | по месту, один раз |
| Мгновенный обмен с сервером    | сетевой HTTP на**одной** машине обмена | одна заявка в ИТ    |

**Вывод: папка-приемник перестает быть запасным вариантом и становится основным транспортом.**
HTTP остается быстрым путем для того, что стоит рядом.

## 7. Технические решения по приему данных

- **Чем слушать** — `HttpListener` из состава .NET, без новых зависимостей. Kestrel ради десятка
  эндпоинтов в Avalonia-приложение не тянуть. Адрес `http://127.0.0.1:8787/` открывается **без**
  прав администратора, `http://+:8787/` — требует `urlacl` и брандмауэра.
- **Куда писать** — только через [ConstructorRepository](../Database/Repositories/ConstructorRepository.cs),
  никогда напрямую в SQLite. Иначе мимо пройдут права, `change_log`, проекция `calendar_index` и
  живое обновление у соседей. Побочная выгода: чужая запись честно попадет в историю изменений и
  доедет до коллег поллером без единой новой строки кода.
- **Кто пишет** — **токен = пользователь-робот** в `db_users` с обычной маской `PermAction`.
  Параллельной системы прав не заводить: в истории изменений будет «1С Обмен создал запись»,
  админ отзовет доступ роботу той же панелью, что и человеку, а недопущенная база останется
  недоступной и по API.
- **Что отдавать наружу** — описание API генерируется из схемы коллекций, как в NocoDB, Baserow и
  PocketBase: создал коллекцию с полями — на вкладке готовые адреса, примеры запроса и ответа,
  кнопка «Скопировать». Без этого сторонней программист не подключится.
- **Повторы** — сторонняя система при таймауте пошлет запрос дважды, это норма. Нужен ключ
  идемпотентности (`Idempotency-Key` либо поле-ключ коллекции для upsert), иначе первый же обрыв
  связи на `P:` даст дубли.
- **Один приемник, два транспорта** — файл из папки и тело HTTP-запроса попадают в один и тот же
  код записи. Иначе получатся две расходящиеся реализации.

## 8. Папка-приемник — это протокол, а не «читаем файлы из папки»

Четыре подводных камня, каждый из которых на SMB выстрелит обязательно.

1. **Недописанный файл.** Приемник увидит файл раньше, чем отправитель закончил писать. Правило:
   отправитель пишет `заказы.json.tmp` и **переименовывает** в `заказы.json` (переименование
   атомарно), приемник берет только готовые имена. Запасное правило для тех, кто так не умеет:
   файл считается готовым, если размер не менялся 5 секунд и его удается открыть монопольно.
2. **Две копии программы на одну папку.** База открыта на нескольких машинах — файл увидят все.
   Захват через переименование: `заказы.json` → `заказы.json.занял-ПК17`. Кто успел, тот и
   обрабатывает; остальные получают отказ и идут дальше. На сетевой шаре это надежнее любых
   блокировок — тот же прием, что и с «исполнителем» сценариев.
3. **Повторы.** Отправитель при обрыве пришлет файл дважды: спасает ключ сопоставления (обновить
   запись по «Номеру», а не создать вторую) плюс ключ идемпотентности внутри файла.
4. **Отправитель не знает результат.** Рядом кладется квитанция `заказы.result.json`: сколько
   принято, сколько обновлено, что не прошло валидацию и почему.

Структура: `Входящие/` · `Обработанные/` · `Ошибки/` · `Квитанции/`; обработанный исходник
уезжает в `Обработанные/2026-09/` или `Ошибки/`. Внутри файла — коллекция, режим (добавить /
обновить по ключу), сам ключ и строки. Большие файлы — существующим потоковым импортом
([import-export/overview.md](developer/features/import-export/overview.md)).

### Связь с расширениями без потери изоляции

Тем же приемом, что и `Settings => []` в контракте: необязательное свойство `Actions => []`, где
расширение объявляет, что умеет делать над коллекцией или записью. Тогда сценарий вызывает
расширение шагом, а расширение по-прежнему зависит только от `IExtension`.

**В сеть расширение не ходит — и готового HTTP-клиента ему не дается.** Раньше здесь стояло
обратное обещание, и оно противоречило требованию, написанному пятнадцатью строками ниже; код
выбрал требование. Выбор этот правильный и остается: дай расширению клиента — и «одна дверь
наружу» кончится, а сторож `OneDoorOutwardTests` перестанет что-либо значить. Обмен наружу делает
шаг-запрос рядом с шагом-расширением, и расширение получает уже полученные данные.

### Два вида шага-расширения

Разница принципиальная, и по ней проходит граница ответственности:

| Вид                                                  | Вход → выход                                                     | Кто пишет в базу                                            | Пример                                                                                                  |
| ------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| **Преобразователь формата** | поток или текст → строки таблицы                | оболочка, обычным сопоставлением полей | разбор PDF, нестандартный XML, чужой бинарник                                 |
| **Операция (процесс)**             | заполненная запись → результат операции | само расширение через`ConstructorRepository`        | «Регистрация КД»: присвоить обозначение и завести документ |

Второй вид важнее и встречается чаще: у операции есть собственные правила, которые в
сопоставлении колонок не выразить. Требование к обоим одно — **в сеть расширение не ходит и
запрос не принимает**: транспорт остается у оболочки, иначе белый список, журнал и политика
размножаются по числу расширений и перестают быть проверяемыми (раздел 10.2).

### Разбор на живом примере: «Регистрация КД» из сообщения

Приходит сообщение вида:

```
Проект: Молоток
Децимальный номер: АААА.000000.ХХХ
ФИО Регистрирующего: Иванов Иван Иванович
```

Путь данных:

```
мессенджер → релей кладет файл → папка-приемник (или локальный HTTP)
   → сценарий: разбор строк сообщения в RegistrationInput
   → шаг «Регистрация КД» → DocRegistrar
   → запись в коллекцию-журнал + ответ: АААА.000000.001 либо текст ошибки
```

**Ничего из этого писать заново не нужно — расширение уже такой формы:**

- [Designation.cs](../Extensions/DocRegistry/Designation.cs) — «чистая логика без UI и без базы»:
  разбор обозначения, занятые номера серии, первый свободный, исполнения;
- [DocRegistrar.cs](../Extensions/DocRegistry/DocRegistrar.cs) — принимает `RegistrationInput`
  (`Name`, `Org`, `Eskd`, `Fio`, `Project`, …) и возвращает результат с присвоенным обозначением
  и id созданной записи; пишет через `ConstructorRepository`, то есть по правильной двери;
- [RegistryFile.cs](../Extensions/DocRegistry/RegistryFile.cs) — тот же реестр пачкой из Excel.

Сообщение — просто **четвертый способ вызвать то же самое**, рядом с окном и загрузкой файла;
`АААА.000000.ХХХ` ложится на контракт как есть: `Org` = `АААА`, `Eskd` = `000000`,
`Number = null` → подобрать первый свободный. Нового кода — только разбор трех строк сообщения в
`RegistrationInput`, и это настройка сопоставления, а не программирование.

**Правило, по которому проверяется вся раскладка:** логика регистрации не дублируется. Если ради
API ее пришлось повторить рядом — граница проведена неверно.

### Три правила, которых нет у ручного ввода

Окно и сообщение отличаются ровно тремя вещами, и все три надо решить до первого пилота:

1. **Гонка номеров.** Два сообщения в одну секунду не должны получить один номер: подбор
   свободного и запись идут под одним захватом, тем же, что и ручная регистрация.
2. **Подтверждать некому.** В окне есть `ConfirmedDuplicate` — человек соглашается писать поверх
   занятого исполнения. По API согласиться некому: занятое исполнение = ошибка в ответе, и
   никогда молчаливая перезапись.
3. **Повтор сообщения.** Мессенджер повторит при обрыве связи. Без ключа идемпотентности один
   документ получит два номера, а это уже испорченный реестр (раздел 7).

### Кому принадлежит точка входа

**Сценарию, а не расширению.** Адрес эндпоинта и подпапку выбирают при настройке сценария,
поэтому одно расширение можно повесить на несколько каналов, а на один канал — разные расширения
по правилу разбора. Если точка входа принадлежала бы расширению, два расширения не поделили бы
один порт и одну папку.

### Как обкатать — три шага, порядок принципиален

1. **Без сети вообще.** Папка `Входящие/КД/`, файл кладется руками, сценарий → «Регистрация КД» →
   запись в коллекцию, ответ квитанцией рядом. Проверяет всю цепочку, кроме транспорта, и не
   требует ни политики, ни прав администратора, ни мессенджера.
2. **Файл кладет релей** — скрипт на машине с интернетом, слушающий мессенджер. В программе не
   меняется ничего.
3. **Локальный HTTP на `127.0.0.1`** — только если нужен мгновенный ответ отправителю.

**Критерий приемки:** при переходе 1 → 2 → 3 не меняются ни расширение, ни сопоставление полей —
меняется только канал. Пришлось править расширение — транспорт протек в обработку. И до всего
этого: прогнать пачкой два десятка реальных сообщений и посмотреть, сколько разобралось, а сколько
ушло в отчет ошибок.

## 10. Контур безопасности: наружу — только через одну дверь и только по списку

Требование службы безопасности («программа не должна ничего передавать сама») и требование
пользователя («хочу настраивать интеграции сам») противоречат друг другу лишь на первый взгляд.
Развязка в разделении ролей: **пользователь настраивает интеграции внутри рамок, а рамки задает
не он и не из программы.** Ни одна возможность из разделов 1–9 при этом не исчезает — меняется
только множество адресов и полей, доступных для выбора.

### 10.1. От чего защищаемся

| Сценарий                                                                                                                                                           | Чем закрывается                                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Пользователь по неосторожности настроил выгрузку не туда (перепутал адрес, вставил чужой cURL) | Белый список адресов, подтверждение направления, сухой прогон                                   |
| Сотрудник сознательно выносит данные через «легальную» интеграцию                                               | Метки конфиденциальности, квоты объема, журнал безопасности, зеркало исходящего |
| Разрешенная система на том конце скомпрометирована                                                                            | Минимум полей в запросе, квоты, срок действия направления, журнал                              |
| Служба безопасности подозревает саму программу в скрытой передаче                                                | Единственная дверь наружу + тест сборки + пустой список исходящих по умолчанию      |
| Кто-то с доступом к общей папке читает файл базы напрямую                                                                   | **Вне зоны программы**: права на папку, BitLocker, пароль базы (раздел 10.15)                      |

### 10.2. Единственная дверь наружу

Весь исходящий трафик проходит через один класс — `EgressGate`. Больше нигде в решении не
создается `HttpClient`, `Socket`, `TcpClient`, `WebClient` и не разрешается имя. **Дверей две, и
вторая — внутрь**: слушателю позволен ровно один поименный файл (`Integrations/IngressHttp.Open.cs`),
а решает, кого пускать, отдельный `IngressGate`. Правило у входящей двери строже исходящей:
у той разрешена вся папка `Integrations/`, у этой — один файл, потому что второй слушатель означал
бы второй набор правил о том, кого пускать в базу. На пути обмена — в шлюзе, движке сценариев и приеме файлов — вдобавок не запускается
посторонний процесс: шаг «выполнить команду» назван в разделе 13 среди того, чего не будет, и
сценарий, приехавший файлом из папки обмена, не должен получать исполнение на машине. Вне пути
обмена запуск процесса — обычное дело (открыть файл или ссылку в системе), и запрета на него нет.

Это не соглашение на словах, а проверяемое утверждение, и рубежа два:

- **Анализатор запрещенных вызовов** (`Microsoft.CodeAnalysis.BannedApiAnalyzers` +
  [BannedSymbols.txt](../BannedSymbols.txt)) — сборка **падает**, если сетевой тип использован
  вне шлюза: `RS0030` объявлено ошибкой, а не предупреждением. Правило действует и на
  [Extensions/](../Extensions/), где расширения пишутся отдельно от ядра. Снятий запрета в
  репозитории ровно два — сама дверь и проба порта PostgreSQL (своя база приложения, а не сторонняя
  программа), — и появление третьего роняет тест.
- **Текстовый тест** [OneDoorOutwardTests.cs](../Tests/Unit/OneDoorOutwardTests.cs) читает
  исходники и ловит даже упоминание сетевого типа в комментарии, а заодно стережет сам
  анализатор: подключен ли он, объявлен ли ошибкой, не расползлись ли снятия запрета.

Рубежи не дублируют друг друга, а ловят разное. Текст видит намерение — упоминание типа в любом
виде, включая комментарий и строку. Анализатор видит употребление — тип, использованный БЕЗ
своего имени: через `var`, псевдоним `using`, наследника или обобщенный параметр. Такой вызов
текстовым поиском не находится вовсе.

Ценность для проверки: на вопрос «где программа выходит наружу» ответ — один файл и один тест,
а не «надо посмотреть весь проект». Все дальнейшие ограничения ставятся в этой единственной точке
и потому не могут быть обойдены новым кодом по невнимательности.

### 10.3. Политика организации

Файл `policy.json`, который **пользователь не может ни изменить, ни подделать**:

- **Где лежит** (читаются все источники, применяется пересечение — то есть самое строгое):
  `HKLM\SOFTWARE\SmartBase\Policy` (запись только с правами администратора), файл в папке
  установки, файл рядом с дистрибутивом в сетевой папке раздачи — там же, откуда уже идет
  автообновление. На macOS и Linux — `/etc/smartbase/policy.json` с владельцем `root`.
- **Подпись.** Политика подписана закрытым ключом организации, открытый ключ вшит в программу.
  Подпись не сошлась — политика не применяется, режим самый строгий. Так подложенный рядом
  собственный файл ничего не дает.
- **Нет политики — не «все можно», а «ничего нельзя».** Исходящих направлений нет вообще.
  Отсутствие настройки обязано быть безопасным состоянием, иначе любая новая машина становится
  дырой.
- **Пропала сеть — политика не смягчается.** Действует последняя известная (с ее сроком
  действия), а не «источник недоступен, значит ограничений нет». Для среды с выключаемым
  диском `P:` это обязательное условие.
- **Что внутри:** режим контура · белый список адресов · разрешенные корни папок · квоты ·
  хэш мастер-пароля · срок действия политики · флаги «пользователю разрешено добавлять адреса»
  (по умолчанию нет) и «требовать второе подтверждение».

### 10.4. Три режима контура

| Режим                                                     | Что разрешено наружу                                                                                                                                                                               | Кому                                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **Изолированный** (по умолчанию) | ничего. Работают локальные шаги: папка-приемник, запись в базу, уведомления, расширения, экспорт в разрешенные папки | рабочее место с секретными данными |
| **Внутренний контур**                    | только адреса организации: приватные диапазоны и свой DNS-суффикс                                                                                               | типовая машина                                      |
| **Согласованные внешние**            | поименные хосты, добавленные ответственным                                                                                                                                     | машина обмена                                        |

Пункта «разрешить все» в интерфейсе нет ни в каком виде. Расширить список можно только политикой.

### 10.5. Проверка адреса, а не имени

Белый список по именам хостов обходится тривиально, поэтому проверка идет по фактическому адресу
соединения:

- имя разрешается в IP **до** проверки, и соединение устанавливается именно на проверенный адрес
  (`SocketsHttpHandler.ConnectCallback`) — иначе подмена DNS между проверкой и запросом сводит
  список на нет;
- автоматический переход по редиректам выключен, а каждый переход проверяется заново — своим
  кодом: имя по белому списку, затем фактический адрес. За переходом программа идет только у
  GET и не больше трех раз подряд; у запроса с телом переход — отказ, потому что тело ушло бы
  туда, куда его не посылали;
- IP-литералы, сокращенные и IPv6-формы адресов, `localhost`-синонимы — приводятся к одному виду
  и сверяются со списком;
- прокси организации задается политикой, свой прокси пользователь указать не может;
- в изолированном режиме дверь закрыта до разрешения имени: DNS-запросов тоже нет.

### 10.6. Что именно уходит — ограничение не только «куда»

Разрешенный адрес не должен означать «можно отправить туда все».

- **Метки конфиденциальности — два уровня, база и поле.** У базы: «Открыто» · «Для служебного
  пользования» · «Закрытый контур». У поля — та же шкала, но по умолчанию поле метки не имеет и
  наследует базу; коллекция своей метки не получает вовсе, иначе появляется третья точка, где
  надо разбираться в наследовании. Помеченное поле невозможно подставить в исходящий шаг: оно
  просто не появляется в списке при настройке привязки, с пояснением почему. Запрет срабатывает
  при настройке, а не в момент отправки — пользователь не должен узнавать об ограничении из
  ошибки в журнале. Модель повторяет уровни конфиденциальности источников в Power Query,
  знакомые инженерам по Excel.
  **Разделение обязанностей:** метку базы ставит администратор базы, метку поля — тот, кто
  правит структуру коллекции; понижение метки (со «Секретно» на «Открыто») требует мастер-пароля
  и попадает в журнал безопасности. Иначе обойти запрет можно снятием метки.
- **Только явная привязка полей.** Ни «отправить запись целиком», ни «весь ответ как есть»:
  тело запроса собирается из перечисленных полей, поэтому состав выгрузки всегда виден списком и
  проверяем глазами.
- **Квоты**: строк за запуск, байт в сутки на направление, запусков в час. Превышение — стоп
  направления и уведомление, а не молчаливое продолжение. Вынести базу «по капле» через
  разрешенный канал становится долго и заметно. В объем идут ОБА тела — и ушедшее, и пришедшее
  в ответ, — а размер отправляемого спрашивается до сокета: квота против выноса данных, которая
  срабатывает после отправки, от выноса не защищает.
- **Зеркало исходящего** (включается политикой): копия каждого отправленного тела ложится в
  папку аудита в контуре организации. Служба безопасности видит не «был запрос на 14 КБ», а
  ровно то, что ушло.

### 10.7. Закрытые базы

Верхняя метка базы из 10.6 — **«закрытый контур»** — не просто пометка, а отдельный режим. Для
такой базы исходящие шаги недоступны в принципе: ни выбрать, ни включить, независимо от режима
машины, политики и прав пользователя. Заодно блокируется перенос записей из закрытой базы в
открытую существующим механизмом `ConstructorRepository.CrossMove` — иначе запрет обходится в два
приема: перенес и выгрузил.

Это самый дешевый и самый понятный для проверяющего контроль: секретная база физически не имеет
исходящих путей, а обычные базы продолжают работать со всеми интеграциями.

### 10.8. Кто разрешает и какими паролями

| Роль                                                                                                      | Что может                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ответственный за интеграции** (ИТ / служба безопасности) | правит политику вне программы, знает мастер-пароль, утверждает направления            |
| **Администратор базы**                                                                 | настраивает сценарии в пределах политики, включает направления с подтверждением |
| **Пользователь**                                                                            | запускает сценарии вручную, видит журнал своих запусков                                               |

- Отдельное действие в `PermAction` — «Интеграции: настройка» и «Интеграции: исходящие»,
  выдается той же панелью допуска, что и остальные права
  ([users-permissions.md](developer/architecture/users-permissions.md)).
- **Мастер-пароль политики** хранится хэшем (PBKDF2 из состава .NET, соль на установку) в самой
  политике. Он требуется, чтобы включить новое исходящее направление, снять блокировку или
  повысить квоту. Пароля нет в базе, и подобрать его, правя файл базы, нельзя.
- **Срок действия направления.** У каждого исходящего направления есть дата окончания и
  автоотключение после N дней простоя. Разрешение, выданное один раз навсегда, через год уже
  никто не помнит.
- **Правка направления сбрасывает подтверждение.** Изменили адрес, поля или условия — направление
  выключается до нового подтверждения. Иначе согласовывается одно, а работает другое.

### 10.9. Сухой прогон и карантин

Новое исходящее направление сначала работает **вхолостую**: собирает запрос, показывает его
целиком (адрес, заголовки со скрытыми секретами, тело, число строк), пишет в журнал — и ничего не
отправляет. Отправка включается отдельным действием с паролем. Тот же режим доступен всегда
кнопкой «Показать, что уйдет».

### 10.10. Два журнала: рабочий и безопасности

**Журнал запусков** — рабочий, для отладки интеграций. Свой, а не «Диагностика»: Serilog хранит
текст, а здесь нужны пары «запрос — ответ» с телами, ротацией и повтором шага. Секрет не попадает
ни в него, ни в `logs.db`, ни в экспортируемый JSON сценария. Повтор с бэкоффом, потолок попыток и
правило «база недоступна — не запускаемся»: иначе за ночь пропажи диска `P:` в журнале окажется
тысяча одинаковых ошибок ([network-shares.md](developer/architecture/database/network-shares.md)).
Чистить его пользователю можно.

**Журнал безопасности** — для проверки, отдельный от обоих:

- пишутся **и разрешенные, и заблокированные** попытки: кто, когда, какой сценарий, адрес,
  сколько строк и байт, какие поля, код ответа, SHA-256 тела;
- **только добавление, с цепочкой хэшей** (каждая запись включает хэш предыдущей) — вырезать
  строку задним числом незаметно не выйдет;
- пользователь журнал не чистит; ротация — по правилам политики;
- секреты и значения помеченных полей в журнал не попадают ни при каких настройках;
- выгрузка для проверки одной кнопкой: период, направления, объемы, подтверждения.

**Где лежат.** Оба — в локальной папке данных приложения (`AppSettings.AppDataDir`, там же
`app.db` и `logs.db`), и **ни один не внутри файла базы**: иначе тела запросов поедут по сети в
общую папку и раздуют ее.

| Что                                                                                                                                  | Файл                                                                      | Кто чистит                                        |
| --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Журнал запусков (тела запросов и ответов, повтор шага)                                      | `integrations.db`                                                           | пользователь, плюс своя ротация |
| Журнал безопасности (попытки, блокировки, подтверждения, понижения меток) | `security.db`, только добавление, цепочка хэшей | никто; ротация по политике           |
| Диагностика (факт «сценарий упал», без тел)                                                          | существующий`logs.db`                                           | как сейчас                                        |

Журнал общий на все базы, а не по базе: сценарии и соединения тоже локальные (раздел 3), а один
запуск может задеть несколько баз — идентификатор базы пишется полем записи. Копия журнала
безопасности в папке аудита организации (10.6) нужна именно здесь: цепочка хэшей ловит правку
строки, но не удаление файла целиком.

**Как показывается — стандартной таблицей с фильтрами**, по образцу «Диагностики»
([SettingsLogsTable.cs](../Views/Settings/SettingsLogsTable.cs)), а не таблицей коллекции: у
журнала нет ни полей, ни записей конструктора, он читается сырым SQL по своему файлу. Берется
оттуда все:

- **Excel-фильтр с сортировкой в заголовке колонки** — тот же, что в «Истории изменений»;
  активный фильтр помечается иконкой в заголовке.
- **Keyset-страницы по 200 строк** при прокрутке к концу — журнал за год не должен читаться
  целиком.
- **Панель деталей выбранной строки** — в ней тела запроса и ответа целиком, с вырезанными
  секретами.
- **Выгрузка в CSV ровно того, что показано на экране** — с теми же фильтрами и сортировкой, как
  сделано кнопкой выгрузки логов.

Колонки журнала запусков: время · сценарий · шаг · канал · адрес · результат · строк · байт ·
длительность. Журнала безопасности: время · кто · сценарий · решение (разрешено или
заблокировано) · адрес · поля · объем · кто подтвердил. Смена вкладки закрывает панель деталей
(раздел 4).

### 10.11. Файлы и папки — тот же принцип

Автоматический экспорт и папка-приемник работают только внутри корней, перечисленных в политике
(например, `P:\Обмен\`). Съемные диски и адреса вне разрешенных серверов недоступны сценариям.
**Ручной экспорт человеком остается как есть** — его убирать нельзя, это рабочая функция, — но
попадает в журнал безопасности: кто, когда, какая коллекция, сколько строк.

### 10.12. Входящий канал тоже под замком

- По умолчанию — только папка-приемник и `127.0.0.1`; сетевой режим включается политикой, а не
  пользователем.
- Токен-робот — обычный пользователь в `db_users` с маской прав, поэтому по умолчанию ему можно
  выдать **только запись** и ни одного чтения: класть данные внутрь можно, вычитывать базу
  наружу — нет.
- База, помеченная закрытым контуром, недоступна входящим токенам ВСЕГДА: политика разрешить это
  не может — поля у нее для этого нет, и ответ на такой запрос один (403).
- Автогенерируемое описание API отдает схему полей, но не данные, и не показывает коллекции, к
  которым у токена нет доступа.

### 10.13. Расширения и набор действий

- Расширения ходят в сеть только через тот же шлюз — прямые вызовы им запрещает анализатор.
- **Набор шагов сценария закрытый.** Нет и не будет действий «выполнить команду», «запустить
  файл», «выполнить скрипт»: любое из них превращает всю раскладку в фикцию, потому что через
  него уйдет что угодно и куда угодно.
- Расширения поставляются в составе дистрибутива и не загружаются из интернета.

### 10.14. Что программа не делает никогда

Список для первого вопроса проверяющего — и одновременно набор утверждений, закрытых тестами:

- нет телеметрии, аналитики и отправки отчетов о сбоях;
- нет обращений к интернету при старте и работе: обновление берется из сетевой папки
  организации, шрифты и стили — из дистрибутива, внешних CDN нет;
- нет учетных записей и облачной синхронизации: данные лежат только в файлах организации;
- в состоянии по умолчанию число исходящих соединений равно нулю — это проверяется тестом,
  а не декларируется.

### 10.15. Данные в покое

Здесь честная граница: часть защиты — не в программе.

- **Файл базы** защищается правами на папку и шифрованием диска (BitLocker или средство
  организации) — это уже принятая практика для общих папок
  ([network-shares.md](developer/architecture/database/network-shares.md)).
- **Пароль базы** и права внутри файла уже есть; секреты соединений в базу не попадают вовсе
  (раздел 3).
- **Резервные копии политикой НЕ ограничены, и это решение, а не упущение** (13.09.2026).
  Прежняя формулировка обещала обратное — «политика ограничивает и их каталог», — и код ей не
  соответствовал: копия всей базы, включая помеченную «закрытый контур», уходит по расписанию в
  любую выбранную папку, без проверки шлюзом и без строки в журнале безопасности; след остается
  только в «Диагностике». Асимметрия с ручным экспортом (тот требует записи в журнал ДО создания
  файла и удаляет файл, если строка не легла) названа здесь прямо.

  Почему решено оставить: контур сторожит АВТОМАТИЧЕСКИЙ вынос данных — то, что уходит без
  человека и о чем он может не знать. Резервное копирование человек настраивает сам, видит папку
  и складывает в нее копию своей же базы. Запретить копии на машине без политики — а без нее
  шлюз запирает все — значило бы отнять резервное копирование у всех, у кого политики нет, ради
  рубежа, который обходится копированием файла базы мимо программы. Границу держат права на
  папку и шифрование диска, как и у самого файла базы двумя строками выше.
- **Шифрование самого файла базы** (SQLite с шифрованием) — возможный шаг, но с честными
  минусами: ключ надо где-то хранить и раздавать, потеря ключа означает потерю базы, общая папка
  усложняется, а от легального пользователя с доступом это не защищает. Предложение: не делать,
  пока служба безопасности не потребует прямо, и закрывать вопрос шифрованием диска.

### 10.16. Что показать службе безопасности

- **Экран «Интеграции → Безопасность»** — только для чтения: применена ли политика, откуда взята,
  верна ли подпись, режим контура, белый список, действующие направления с датами и подтвердившими,
  квоты и расход, последние блокировки.
- **Паспорт интеграций** — выгрузка того же в файл: с чем соединяется программа, кто разрешил,
  что уходит по полям, объемы за период.
- **Сборка для закрытого контура** — принято, закладывается сразу (см. ниже).

### 10.16.1. Сборка для закрытого контура

Отдельный дистрибутив, в котором **сетевого кода физически нет**. Это единственное утверждение о
безопасности, которое не нужно принимать на веру: спорить не с чем, проверяется за минуту.

- **Как собирается.** Одна конфигурация в [SmartBase.csproj](../SmartBase.csproj):
  `-p:ClosedLoop=true`. Она делает две вещи. Первая — определяет константу `CLOSED_LOOP`, по
  которой шлюз отвечает отказом на любую проверку; условная компиляция живет ровно в этом одном
  файле, иначе ветки начнут расходиться поведением в местах, о которых никто не помнит. Вторая —
  **подменяет файл** отправляющего слоя: вместо `Integrations/EgressHttp.Open.cs` собирается
  `Integrations/EgressHttp.Closed.cs`, заглушка без единого сетевого типа. Подмена файлом, а не
  условной компиляцией, именно затем, чтобы сетевого кода в дистрибутиве не осталось совсем.
  **Сделано.**
- **Как доказывается.** В закрытой сборке нет ни сетевого клиента, ни сокета, ни разрешения имен
  — искать в манифесте нечего. Тесты сторожат само устройство: заглушка не должна обзавестись
  сетевым кодом, строки подмены — пропасть из проекта, а `#if CLOSED_LOOP` — расползтись за
  пределы шлюза (`Tests/Unit/OneDoorOutwardTests.cs`). **Сделано**, вместе со своей строкой
  матрицы CI: закрытая конфигурация собирается на каждом прогоне, а встречный шаг проверяет, что
  файл отправляющего слоя на месте и обычная сборка идет.
- **Что остается.** Весь интерфейс, все разделы, автоматизация, папка-приемник, локальный прием
  на `127.0.0.1`, расширения — без изъятий. Исчезает только исходящий канал: вкладка
  «Соединения» показывает пояснение вместо кнопки «Добавить».
- **Открытый вопрос — входящий слушатель.** Прием на `127.0.0.1` данные наружу не отдает, но
  открытый порт на секретной машине вызовет вопросы. Предложение: слушателя оставить, а
  выключать вторым флагом `-p:NoListener=true`, если служба безопасности потребует; массовый
  канал в закрытом контуре все равно папка-приемник (раздел 6.6).
- **Чем платим.** Второй артефакт релиза, вторая строка в матрице CI и правило «изменения в
  шлюзе — только через его интерфейс». Дисциплина та же, что уже есть у расширений с
  [IExtension](../Extensions/IExtension.cs).
- **Как отличить на месте.** «О программе» и имя файла дистрибутива несут пометку «закрытый
  контур», иначе через полгода никто не скажет, какая из сборок стоит на машине.

### 10.17. Границы применимости — что программа не гарантирует

Обещать «данные не утекут» нельзя, и на проверке такое обещание сразу разваливается. Программа
закрывает утечку **через себя**: сценарий не отправит данные на неразрешенный адрес, помеченное
поле не попадет в запрос, каждая попытка записана. Вне ее зоны остаются: пользователь с правами
администратора на своей машине, копирование файла базы, снимок экрана, пересылка вручную. Это
задача прав на папки, шифрования дисков, контроля съемных носителей и корпоративной DLP — и так и
надо написать в документе для службы безопасности, отдельно перечислив, что закрывает программа.

### 10.18. Как это выглядит для пользователя

Ограничение обязано объяснять себя, иначе его обходят или считают поломкой:

```
Новое соединение

  Адрес   https://api.postavshik.ru/v2
          ⛔ Адрес не входит в белый список организации.
             Разрешены: *.zavod.local, 10.0.0.0/8, api.1c-obmen.local
             Чтобы добавить адрес, обратитесь к ответственному за интеграции.
             [Скопировать заявку]        [Показать политику]
```

Кнопка «Скопировать заявку» кладет в буфер готовый текст с адресом, целью, коллекцией и списком
полей — то, что ответственному все равно пришлось бы спрашивать.

  Заведена модель сценария: триггер (вручную · каждые N минут · ежедневно в HH:MM), линейные шаги
  (запрос в коллекцию · сообщение человеку), расписание с якорем при включении и однократным
  догоном пропущенного, хранение в `app.db` рядом с запросами. Шаг «запрос» не несет раскладки —
  он берет привязку карточки запроса, ту самую, которую человек однажды проверил глазами: автомат
  не выдумывает соответствие колонок. Триггер «календарное событие» и шаги «создать запись» и
  «экспорт выборки» заведутся вместе со своими исполнителями — настройка, которая ничего не
  делает, читается как поломка.
  Сделано и выполнение: шаги идут по порядку, первый неудавшийся останавливает цепочку (следующий
  работал бы с данными, которых не пришло), в журнал идут две строки — своя у запроса и итоговая у
  сценария, ради неудач, случившихся до первого запроса. Что мешает запуску, называется одним
  текстом: службе он означает «пропусти тик молча», человеку — почему ничего не произошло. Заодно
  исправлено место, которое со сценариями стало бы ловушкой: в накопительный расход теперь идет
  только то, что дошло до сети, — иначе отказ по квоте продлевал бы сам себя и часовое окно не
  опустело бы никогда.
  Готова и служба: раз в полминуты смотрит, у кого наступил срок, ставит отметку МОМЕНТОМ НАЧАЛА
  (иначе долгий обмен растягивал бы период, а падение посреди работы повторяло бы запуск), а
  сценарий, которому что-то мешает, пропускает тик молча — без строки журнала и без сдвига
  отметки, чтобы пропущенное догналось, когда помеха уйдет. Запуск руками расписания не двигает и
  работает даже у выключенного сценария: тумблер про расписание, а не про запрет.
  Сделана вкладка «Сценарии»: список карточек с тумблером прямо в строке (выключить обмен нужно
  чаще, чем править его), строка «не сработает», посчитанная вживую тем же `Blocker`, которым
  пользуется служба, кнопка «Запустить» и окно правки — расписание готовыми интервалами (набирать
  «5» вместо «50» тут нечем), шаги стрелками, запрос без привязки помечен прямо в списке выбора.
  Полосы «ЕСЛИ» в окне нет: условиям нужно то, что течет между шагами.
  Заведен контракт `Actions` (раздел 9): необязательное свойство `IExtension.Actions` тем же
  приемом, что и `Settings`, два вида — преобразователь формата (пишет оболочка сопоставлением) и
  операция (пишет расширение через `ConstructorRepository`), репозиторий дает оболочка, точка
  входа принадлежит сценарию, а неудача возвращается результатом, а не исключением: ее ждут в
  квитанции отправителю. Первое действие — «Зарегистрировать документ» в «Регистрации КД»: тонкая
  прослойка над тем же `DocRegistrar`, которым пользуется окно. Логика регистрации не
  дублируется — это и был критерий верно проведенной границы. Занятое исполнение действие
  отклоняет: подтверждать некому.
  Поверх контракта сделан **шаг сценария «действие расширения»**. Вместе с ним появилось то, что
  течет между шагами: шаг передает следующему таблицу (колонки и строки), а шаг «сообщение» поток
  не обрывает. Строки поднимаются в память, только если дальше есть шаг-действие, — иначе укладка
  идет потоком, как раньше. Значения полей задаются одним текстом с подстановками `{{колонка}}`:
  постоянная часть и колонка в жизни встречаются вместе, а два элемента управления на один смысл
  пришлось бы объяснять. Словари подстановок шага и запроса намеренно не слиты — иначе колонка с
  именем «сегодня» молча подменилась бы датой. Три правила выполнения: все подстановки считаются
  ДО первой записи, первая отказавшая строка останавливает шаг и называет свой номер (сделанное
  остается сделанным — откатывать чужую работу оболочка не берется), упавшее расширение не уносит
  службу. Потолок 500 строк на шаг — не про память, а про то, что действие над каждой строкой
  заводит запись. Преобразователь формата шагом пока не ставится: подать ему на вход нечего, и в
  список выбора он не попадает. Список расширений приходит в исполнителя параметром, а не берется
  из глобального реестра; реестр называет только точка сборки. Окно настройки шага показывает
  поля, объявленные самим действием, — новое расширение его правки не требует.
  **Приемка шага пройдена: пилот «Регистрация КД» из папки работает — шаг 1 обкатки, без сети
  вообще.** Заведен шаг «файл из папки»: точка входа принадлежит сценарию, файловая работа
  берется у готового протокола папки (выдержка, монопольное открытие, захват переименованием,
  уборка брошенных захватов, квитанция как память о повторах). Отличий от службы приема два, и
  оба следуют из того, что здесь работает сценарий: берется ЛЮБОЙ файл, а не только `.json`
  (формат задает шаг-преобразователь), и за один запуск берется ОДИН файл — единица работы
  сценария есть сообщение целиком: одна цепочка шагов, одна квитанция. Пустая папка кончает
  сценарий тихо, без строки журнала: проверка каждые пять минут иначе оставляла бы к утру три
  сотни строк «делать было нечего». Ответ отправителю пишется по итогу ВСЕХ шагов, и в нем едет
  то, что сказало действие, — присвоенное обозначение. В «Регистрации КД» появился
  преобразователь «Разобрать сообщение»: строки «Ключ: значение» становятся колонками, а
  децимальный номер раскладывается на код организации, код ЕСКД, номер и исполнение — единственное
  знание о предметной области в разборе, и оно на своем месте. Разбор ничего не знает про
  регистрацию, регистрация — про формат сообщения; какая колонка в какое поле ложится, решает
  шаг сценария. Это и есть критерий приемки: при переходе к другому каналу меняется канал, а не
  расширение и не сопоставление.
  Заведены **условия — «ЕСЛИ» из раздела 2**. В плане они нарисованы полосой карточки, между
  «когда» и «что делать»; стали ШАГОМ, и причина не в удобстве: условию нужны данные, а данные
  появляются только после того, как их кто-то принес. Полоса в шапке обязана была бы угадывать, к
  какому шагу относится, — а отбор между «разобрать сообщение» и «зарегистрировать» не гадает ни
  о чем. Шаг оставляет строки, на которых выполнились все условия; союз один — «и», потому что
  «или» пришлось бы рисовать скобками, а два отбора подряд читаются лучше. У сообщения из папки
  строка одна, и «не подошла ни одна» читается там как «условие не выполнилось», так что условием
  шаг работает сам собой. Три решения против молчаливой потери данных: отброшенные строки названы
  числом, колонка, которой в строках нет, останавливает шаг (опечатка иначе выглядела бы как
  честно не подошедшие данные), а «не подошла ни одна» не считается неудачей — журнал и квитанция
  пишутся, жаловаться не на что. Вопросов шесть, регистр не учитывается нигде; сравнений «больше»
  и «меньше» нет — в таблице шага все значения текст, и «10» там меньше «9»; маска — два знака,
  `*` и `?`, а не регулярное выражение, которому нужен отладчик.
  **Триггер «изменение данных» был отложен намеренно, и это оказалось не забывчивостью, а
  порядком работ.** Исполнителя у него не было: шаги, которые существовали тогда, данные
  ПРИНОСЯТ (запрос, файл из папки) — запускать их от правки записи бессмысленно. Единственный
  шаг, которому такой триггер нужен, — отправка наружу, а она была предметом шага 5. **Сделан
  после него, 11.09.2026.** Заводится он СВОИМИ правками (`ChangeBus`), а не чужими
  (`ChangePoller`): база открыта на нескольких машинах, и правка, видимая всем, запустила бы
  сценарий на каждой — один обмен превратился бы в пять. Ждет ТИШИНЫ, а не паузы: отсчет идет от
  последней правки, поэтому правка десяти строк подряд дает один обмен, а загрузка на тысячу
  записей уходит одним куском после того, как закончится; плата названа честно и в коде, и на
  экране — пока правки идут непрерывно, обмен ждет, потому что отправлять посреди загрузки
  значит отправлять половину. Обработчик шины только запоминает факт и уходит (событие
  поднимается внутри `SaveChanges` на потоке записи), а решает «пора ли» обычный тик службы.
  Считаются правки ДАННЫХ, не строения: добавленная колонка не меняет того, что уйдет.
  Круг «сценарий заводится правками в коллекции и сам же в нее пишет» ловится при сохранении, а
  не в работе: замеченный на боевой машине, он к тому моменту уже выбрал бы часовой потолок
  политики и остановил ВЕСЬ обмен, а не только себя.
  **Шаг 4 на этом закрыт.**
- [x] **5. Исходящее под замком.** Подтверждение направления мастер-паролем, сухой прогон, квоты
  объема, срок действия направления, журнал безопасности с цепочкой хэшей, экран «Безопасность»

  рабочего журнала и от «Диагностики». Только добавление, каждая строка включает хэш предыдущей, и
  проверка проходит цепочку с начала, называя первую разошедшуюся строку: ловятся и поправленное
  содержимое, и вырезанная строка. Чего цепочка не ловит — подмену файла целиком, и написано это
  прямо: от нее спасала бы копия вне машины, но такой копии программа не ведет (см. 12.1) —
  вынос остается задачей организации. Пишутся пять видов событий (следующими шагами их стало
  десять), включая ЗАБЛОКИРОВАННЫЕ попытки — ради них журнал во многом и ведется. Ни секретов, ни значений полей:
  адрес замаскирован, поля только именами, тело одним SHA-256. Правило **«не записалось — не
  отправляем»** сделано исполнимым: запись честно возвращает «следа не осталось», а не глушит сбой,
  как рабочий журнал, и не открывшийся при запуске журнал означает отсутствие исходящего обмена.
  Заведены **исходящие направления и мастер-пароль**. Белый список отвечает «куда можно ходить»,
  направление — «этому обмену разрешено уносить данные»: первое одинаково для всех, второе
  подтверждается по одному и на срок. Граница «что считается исходящим» проходит по методу: `GET`
  спрашивает, остальные меняют что-то на той стороне; честно записано и то, чего эта граница не
  ловит, — данные можно вписать руками и в путь `GET`, и от этого защищает белый список плюс
  журнал, а не подтверждение. Три правила: правка сбрасывает подтверждение (направление помнит
  отпечаток метода, пути, заголовков и тела — но не имени карточки, иначе люди привыкли бы
  подтверждать не глядя), срок не дальше года и автоотключение после 30 дней простоя, считая от
  последнего использования, а если его не было — от подтверждения. Мастер-пароль лежит хэшем
  (PBKDF2, соль на политику) в самой политике, под подписью: пароля в программе нет, и подобрать
  его, правя базу, нельзя. Пересечение источников работает и здесь — пароль обязан подойти
  каждому источнику, который его назвал; ни один не назвал — подтверждать нечем, и исходящих
  направлений нет вовсе. Подтверждения лежат в `app.db`, потому что выдаются на этой машине и
  этому человеку.
  Готов **сухой прогон** — кнопка «Что уйдет» на карточке запроса: запрос собирается целиком, с
  раскрытыми подстановками, заголовками и телом, и не отправляется. Собирается ТЕМ ЖЕ кодом, что
  и настоящая отправка, — иначе экран показывал бы одно, а уходило другое; проверено это
  единственным способом, каким вообще можно, — сравнением с телом, дошедшим до настоящего
  сервера. Ни одного сокета при этом не открывается: даже имя узла не разрешается, потому что
  сам запрос к DNS уже говорит наружу, что программа этим адресом интересуется. Секрет заменен
  тем же слоем, который маскирует его для журнала. Рядом — окно подтверждения направления:
  мастер-пароль и срок, ошибка не закрывает окно (неверный пароль — обычная опечатка), а след
  подтверждения и отзыва идет в журнал безопасности.
  Попутно закрыта дыра, которую нашел сам сухой прогон: заголовок не из латиницы `HttpClient`
  отвергает исключением в момент записи в сокет — то есть ночью, из фонового сценария, и в виде,
  который человеку ничего не объясняет. Теперь имя и значение заголовка проверяются при
  сохранении карточки, а секрет, которого в карточке нет, — при сборке вызова: набранный
  кириллицей токен кончается отказом со словами.
  **Замок повернут:** проверка направления стоит в самой отправке. Один вызов (`OutwardGuard`)
  отвечает сразу на оба вопроса — подтверждено ли направление и лег ли след, — потому что
  спрошенные по отдельности они однажды спросятся по одному. Параметр отказа у
  `RequestRunner.RunAsync` сделан ОБЯЗАТЕЛЬНЫМ: значение по умолчанию означало бы, что вопрос
  «этому обмену разрешено уносить данные?» можно не задать, просто забыв про него в новом месте
  вызова, — так замок и обходят, не взломом, а вызовом в обход. Отказ приходит до первого сокета
  и в накопительный расход не идет: иначе неподтвержденный сценарий, стучащийся раз в пять минут,
  к обеду выбирал бы часовой потолок и вставал бы весь обмен, включая настроенный правильно.
  Строка журнала безопасности пишется ДО отправки, и правило «не записалось — не отправляем»
  живет там же: журнал не открылся — исходящего обмена на этой машине нет. Читающие запросы
  замка не касаются и следа не оставляют — обмен, опрашивающий стороннюю программу каждые пять минут,
  за сутки утопил бы журнал проверяющего в трех сотнях строк «сходили и вернулись».
  Готов **экран журнала безопасности** — вторым видом вкладки «Журнал», переключателем
  «Запуски | Безопасность», как и было нарисовано в разделе 4 (шаг 15 увез его в «Профиль →
  панель администратора», переключателя в «Журнале» больше нет). Первой строкой проверка цепочки
  (по кнопке: она проходит файл целиком, а файл копится годами) с честным ответом в обе стороны —
  «цела» не означает «все хорошо», потому что удаление файла целиком хэши не ловят. Сужение по
  роду события, периоду и «только заблокированные» уходит в SQL, а не в память: потолок строк
  применяется ПОСЛЕ условий, иначе одно заблокированное событие полугодовой давности просто не
  нашлось бы. Выгрузка в CSV отдает все отобранное, а не показанные две сотни строк, и читает
  журнал лениво страницами, беря замок на каждую отдельно: держать его на все время выгрузки
  значило бы остановить запись в журнал, то есть остановить исходящий обмен.
  Готов **паспорт интеграций** — кнопка на вкладке «Безопасность» рядом с «Перечитать политику»
  (обе ничего не разрешают, и в этом смысл вкладки; с шага 15 это раздел «Профиль →
  Безопасность»). Простой текст, а не таблица и не JSON:
  документ читают глазами, печатают и подшивают. Четыре вопроса в том порядке, в каком их
  задают, — что разрешено, с чем программа соединяется, кому разрешено уносить данные (вместе с
  НЕподтвержденными направлениями: паспорт, показывающий только согласованное, отвечал бы на
  другой вопрос), что и сколько ушло за месяц. Объемы сведены по адресу без параметров запроса —
  иначе один обмен рассыпается на тридцать строк; имена полей названы, значений нет. Последним
  разделом — **чего этот документ не доказывает**: его составила та самая программа, о которой он
  рассказывает, и умолчать об этом значило бы выдать сводку за доказательство.

  только напечатанное руками: замок стоял на двери, через которую нечего было вынести. Теперь у
  карточки запроса есть кнопка «Что уносит» — список полей коллекции, каждое со своим именем в
  JSON. **Список, а не правило:** ни «отправить запись целиком», ни «все, кроме помеченных» —
  правило выглядит удобнее ровно до дня, когда в коллекции заводят новое свойство, и оно уходит
  наружу в тот же день, никого не спросив. Помеченное свойство показано серым с причиной, и это
  осознанное уточнение 10.6: убрать его из списка вовсе формально ближе к тексту, но человек
  искал бы пропавшее поле вместо того, чтобы прочитать причину; второй рубеж стоит у чтения
  записей — метку могли поставить уже после того, как привязку собрали. Закрытая база привязку
  не дает собрать вовсе. Тело бывает трех видов (массив, массив внутри поля, одна запись
  объектом), значения типизируются по типу СВОЙСТВА теми же правилами, что и выгрузка коллекции
  в JSON: угадывание по значению отправило бы артикул `007` числом `7`. Потолок строк считается
  по факту прочитанного — лишняя запись отменяет весь запуск, а не обрезает его. Тело собирается

  всех трех обязательные, иначе экран показывал бы одно, а ушло бы другое. Состав входит в
  отпечаток запроса, поэтому дописанное поле роняет подтверждение направления — иначе он остался
  бы единственной частью отправки, которую можно поменять после согласования.

  порядке, а не в порядке выделения, и записи чужой коллекции отбрасываются молча.
  Попутно вынесен общий `RequestLauncher`: замок, отправка, строка журнала и отметка о простое

  которую можно включить, — адрес `/v1/records` отвечает «такого адреса нет», потому что его не
  существует. Наружу уходит ровно одно — схема собственных коллекций, имена и типы без единого

  Обратиться к `127.0.0.1` может только программа, уже работающая на этой машине, то есть та,
  которая и так читает файл базы; данные при этом идут внутрь. Сетевой режим — другое дело, его
  разрешает организация, и до шага 8 он отвечает отказом, а на экране показан серой строкой с
  причиной. Состояние по умолчанию — выключено.
  **Токен — это пользователь-робот,** а не вторая система прав: у каждого своя строка в
  `db_users` ЦЕЛЕВОЙ базы с обычной маской. Отсюда все остальное — в истории изменений стоит имя
  робота, допуск ему отзывает администратор той же панелью, что и человеку, а недопущенная база
  недоступна и по сети. Маска по умолчанию — только запись, и заводится она ОТДЕЛЬНОЙ строкой
  прав: у пользователя без такой строки маска считается полной, и «робот только пишет»
  превратилось бы в «робот может все». Самого токена в программе нет — хранится тот же PBKDF2,
  что у мастер-пароля; текст существует один раз, в момент выдачи. Токен выдается под ОДНУ базу.
  **Один код записи на два транспорта:** файл из папки и тело запроса ложатся общей укладкой,
  потому что две реализации разошлись бы на первой же правке — и сообщение, принятое папкой,
  стало бы отклоняться по сети. Своим у транспортов осталось чтение, проверка формата до памяти

  приходит именно затем, чтобы ответ прочитать.

  квоты они не идут — квоты ограничивают то, что уходит наружу.

  такого-то числа»: подтверждается мастер-паролем, простой гасит — все как у исходящего
  направления. Помеченное поле в выдачу не попадает вовсе, база «закрытый контур» — отказ
  целиком; роботу нужна маска чтения, и выдает ее администратор той же панелью пользователей,
  что и человеку. Каждый ответ — строка в журнале безопасности (кто, какие поля, сколько строк,
  отпечаток ответа) и расход суточного потолка своей выдачи. Сам канал: `GET /v1/records` —
  коллекция, `since` по времени правки (сторонняя программа забирает только новое, а не все каждый
  час), постранично с курсором; второй ступенью `GET /v1/changes` поверх `change_log` — «что
  изменилось», включая удаления, на которые простое чтение не отвечает. Описание для
  отправителя дополняется разделом о чтении само. На экране — блок «Что можно читать» на
  «Доступе извне», рядом с токенами.

  «токен + коллекция»: повторное подтверждение заменяет состав, а не заводит второе разрешение;
  выдачи уходят вместе со своим токеном. Одно отличие от направления, и оно записано в модели:
  отпечатка нет — направление подтверждает ЧУЖУЮ карточку, которую потом правят, а выдача сама
  источник истины, и единственное, что меняется за ее спиной, — метки, их проверяет каждое
  чтение вторым рубежом (тем же, что у исходящей привязки). Правило «не записалось — не
  отправляем» перенесено на чтение дословно: строка журнала безопасности пишется ДО ответа, и
  без нее данные не отдаются; отказы журналируются наравне с удачами. Потолок выдачи считается

- [x] **16. Менеджер паролей — опись, а не просмотрщик.** «Профиль → Менеджер паролей»: один
  список всех секретов машины — секреты соединений, токены роботов, пароли баз, мастер-пароли, —
  чтобы не путаться, где что заведено. По каждому: название с родом секрета, состояние словами
  («установлен», «не установлен», «давно не нужен», у пароля базы — дата последнего входа по
  паролю), путь или адрес, где он лежит, и подсказкой — для чего он и почему его можно или
  нельзя показать; действия — завести, сменить и удалить. Показать значение можно
  только там, где оно восстановимо по построению (секреты соединений: ими подписываются
  запросы), только под мастер-паролем и со строкой в журнале безопасности. Мастер-пароль и
  токены роботов не показываются никогда: от них хранится один отпечаток, и это не ограничение
  экрана, а устройство хранения. Главная польза описи — мертвые секреты: то, чем давно не
  пользовались, видно списком, и его пора отзывать.
  **Сделано 13.09.2026.** Список вышел шире обещанного на один род: к четырем названным
  добавились **пароли серверов PostgreSQL** — они такой же секрет машины, лежат в том же
  хранилище ОС, что и секреты соединений, и опись без них отвечала бы на вопрос «что у нас
  заведено» неполно.
  Главным решением оказалось не «показывать или не показывать», а **что написать там, где
  показать нельзя**. Отсутствие кнопки без объяснения читается как недоделка, и человек идет
  искать ее в другом месте — поэтому у каждой непоказываемой строки лежит фраза, почему ее нет:
  «хранится только отпечаток», «лежит в хранилище операционной системы», «задается вне
  программы». Граница показа при этом ровно та, что обещана: секрет соединения восстановим ПО
  ПОСТРОЕНИЮ, потому что программа расшифровывает его при каждой отправке, и прятать от человека
  то, что она достает сама, было бы притворством.
  Показ идет под мастер-паролем и оставляет строку в журнале (`SecurityEvent.Reveal`) — в обоих
  исходах. **Неудачная попытка нужнее удачной:** подбор мастер-пароля выглядит именно как череда
  отказов, и запись только об успехе показывала бы ровно ту половину, которую подбирающий и так
  переживет. Правило «не записалось — не показываем» то же, что у отправки и ручной выгрузки.
  Мертвый секрет пришлось определить аккуратнее, чем «давно не использовался»: у пароля базы и
  пароля сервера программа пользование НЕ отмечает, и назвать их мертвыми значило бы звать
  человека отзывать то, чем пользуются каждый день. Поэтому в описи три ответа вместо двух: дата,
  «ни разу» и «не отмечается», и в мертвые попадают только первые два.
  **Поправлено в тот же день по замечанию:** сперва опись показывала только ЗАПОЛНЕННЫЕ места —
  соединение без секрета, база без пароля и сервер без пароля из нее выпадали, а закрытые базы
  не попадали вовсе. Между тем вопрос, ради которого список и заводят, звучит «где я пароль
  поставил, а где нет», и молчание на него читается как «такого места нет», а не «пароля тут
  нет». Теперь в списке все места, а состояний три: «установлен», «не установлен» и
  «неизвестно» — последнее у закрытой базы, чей пароль лежит внутри ее файла. Заодно ушла
  строка-обманка: пароль сервера PostgreSQL показывался и там, где его не задавали.
  **Переделано 16.09.2026.** Экран пересобран **списком, как «Управление базой данных»**: строка

  **Подсказка при наведении не прижилась и убрана.** Сперва пояснения переехали в плашку на

  30 дней и цепочки хэшей не ведет. **Решено 13.09.2026 оставить как есть** — см. 10.15: запрет
  копий на машине без политики отнял бы у людей резервное копирование ради рубежа, который
  обходится копированием файла базы мимо программы.
- ~~**Большие файлы в папке обмена не принимаются**~~ (раздел 8 обещает «существующий потоковый
  импорт»). Потолок 32 МБ, файл читался в память целиком. Ночная выгрузка учетной системы на

  Обход токенов вынесен из `JsonTableSource` в `JsonCursor` — общий помощник поверх потока. У него
  появился `Skip()`: пропуск значения БЕЗ чтения в память, возвращающий число элементов массива.
  Именно он снял потолок: поля конверта отправитель вправе написать после массива записей, значит
  массив приходится проходить, а «прочитать и выбросить» пропуском не является.

  `InboxMessage.TryParseFile` читает конверт из файла тем же курсором; массив записей остается в
  файле, сообщение несет путь (`RowsFile`), а записи потом читает `JsonTableSource(path, "rows")`.
  Разбор при этом ОДИН на оба транспорта — `TryParse(string)` и `TryParseFile(path)` идут через
  общий `Read(Stream)`, и второго понимания формата не завелось. Число записей считается даром, тем
  же пропуском. Потолка у этого канала больше нет; `InboxFolder.MaxFileBytes` остался у

  строка целиком.

  сосед счел бы захват брошенным, вернул файл и разобрал его второй раз параллельно с первым.
  `InboxFolder.Touch` каждые `InboxIntake.BeatEvery` строк. Подается из обхода строк, а не
  таймером: он обязан означать «работа идет», а не «программа жива».

  **Дальше — то, ради чего потолок и стоило снимать.** Замер укладки показал, что упиралось все не
  в размер файла: время на запись РОСЛО вместе с числом уже уложенных. Каждая запись оставляла за
  собой отслеживаемые EF сущности, а `SaveChanges` обходит весь накопленный список, — общее время
  росло квадратично.

  | Записей | Было | Стало |
  |---|---|---|
  | 250 | 13,0 мс/зап | 7,2 мс |
  | 1 000 | 22,3 мс | 2,4 мс |
  | 5 000 | 104 мс (8 мин 40 с) | 3,5 мс (17 с) |
  | 20 000 | ≈ 2,3 ч (расчет) | 4,1 мс (82 с) |

  уже стоял у переноса коллекции между базами. Поставлена в трех циклах записи: укладка ответа,
  удаление по ключу, шаг «создать или обновить запись». Сто тысяч записей теперь — минуты, а не

  платой был бы замок записи на всю укладку — при `busy_timeout` в 10 с интерфейс получает не

## 13. Чего делать не планируется

- **Графовый редактор узлов** как в n8n — сценарии линейные, редактор графа отдельный проект.
- **Свой полный язык выражений** — не планируется. Планка поднята шагом 12 ровно до выражений
  над строкой без ввода-вывода: арифметика, строки, даты, условия. Циклов, переменных и доступа
  к чему-либо, кроме значений строки, не будет — на этой границе выражения остаются данными, а
  не программой.
- **OAuth2 с браузерным редиректом** на первом заходе — только ключи и Bearer-токены.
- **Слушатель на `0.0.0.0` по умолчанию** — только явным выбором пользователя и разрешением политики.
- **Прием вебхуков из интернета напрямую** — вместо этого опрос или релей.
- **Триггер «при остановке приложения»** (обещан разделом 2 в паре с «при старте»; парный триггер
  старта сделан 13.09.2026). Обещание невыполнимо по существу: выключение питания, закрытие
  сеанса и снятие процесса не дают программе ни одного шанса отработать, а закрытие окна пришлось
  бы задерживать на время сетевого обмена — до полуминуты на каждый шаг. Триггер, срабатывающий
  «обычно, но не всегда», хуже отсутствующего: опереться на него нельзя, а выглядит он как
  гарантия. То, ради чего его просили — «отдать накопившееся», — закрывает триггер старта:
  отдается при следующем запуске, и отдается всегда.

Запрещено намеренно и навсегда — это не «пока не сделали», а условие, на котором держится
раздел 10:

- **Шаги «выполнить команду», «запустить файл», «выполнить скрипт»** и любой встроенный
  интерпретатор. Один такой шаг обнуляет весь белый список. Развилка «а если C#-скрипты для
  автоматизаций» рассмотрена отдельно 12.09.2026 и решена в пользу расширений (шаг 13):
  песочницы в .NET нет, запретить скрипту сокет мимо шлюза нельзя, а расширение дает тот же
  C# под анализатором запрещенных вызовов — с типами, отладкой и историей в репозитории.
  Простые пересчеты закрывает шаг «преобразовать строки» (шаг 12), у которого ввода-вывода
  нет по построению.
- **Пункт «разрешить любые адреса»** в интерфейсе — расширение списка только политикой.
- **Свой прокси, свои корневые сертификаты и отключение проверки TLS** пользователем.
- **Загрузка расширений, пресетов и обновлений из интернета** — только из дистрибутива и сетевой
  папки организации.
- **Телеметрия, аналитика, отправка отчетов о сбоях** — в любом виде и под любым предлогом.

## Технические риски

| Риск                                                                                                                     | Митигация                                                                                                                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сценарий в файле базы срабатывает на каждой открытой копии                 | Сценарии и соединения — локальные (`app.db`); позже поле «исполнитель» + захват блокировки                                                                                     |
| Секрет уезжает в общую папку внутри файла базы                                        | Секреты только в`app.db` через `SecretProtector`; экспорт сценария — без секретов                                                                                                                 |
| Токен в журнале,`logs.db` или квитанции                                                           | Вырезание при записи, а не при показе                                                                                                                                                                                 |
| Недописанный или дважды обработанный файл в папке                                 | Запись через`.tmp` + переименование, захват переименованием, ключ идемпотентности                                                                                                |
| Тысяча одинаковых ошибок за ночь при пропаже`P:`                                     | Бэкофф, потолок попыток, «база недоступна — не запускаемся»                                                                                                                                       |
| Запись мимо репозитория ломает права и`calendar_index`                                    | Единственная дверь —`ConstructorRepository`, один приемник на оба транспорта                                                                                                                         |
| Сетевой режим требует заявки на каждый ПК                                                 | Массовый канал — папка-приемник; HTTP по сети только на машине обмена                                                                                                                          |
| Пользователь не может настроить чужой API                                                   | Вставка cURL, пресеты, кнопка «Проверить» с сырым ответом, автогенерируемое описание своего API                                                                           |
| Новый код в обход шлюза заводит свой`HttpClient`                                             | Анализатор запрещенных вызовов на сборке + тест архитектуры; правило действует и на`Extensions/`                                                                            |
| Подмена DNS или редирект уводят запрос мимо белого списка                      | Проверка после разрешения имени, соединение на проверенный IP, редиректы не автоматические                                                                              |
| Пропала сетевая папка — политика «не нашлась» и ограничения сняты    | Fail-closed: нет политики или не сошлась подпись — исходящих нет; при недоступном источнике действует последняя известная                              |
| Пользователь подкладывает свой`policy.json`                                                    | Подпись ключом организации, источники читаются все сразу, применяется пересечение (самое строгое)                                                                |
| Секретное поле попадает в разрешенный запрос                                          | Метки конфиденциальности: помеченное поле не появляется в списке при настройке привязки                                                                                 |
| Запрет обходят снятием метки с поля                                                            | Понижение метки — по мастер-паролю и с записью в журнал безопасности                                                                                                                       |
| Данные переносят из закрытой базы в открытую и выгружают оттуда        | Режим «закрытый контур» блокирует и исходящие шаги, и`CrossMove` в открытую базу                                                                                                        |
| Обычная и закрытая сборки расходятся поведением                                    | Условная компиляция ровно в одном файле (заглушка шлюза), обе конфигурации в матрице CI, встречный тест «в обычной сборке ссылка есть» |
| Вынос базы «по капле» через легальное направление                                 | Квоты строк, байт в сутки и запусков в час; стоп направления и уведомление при превышении                                                                                  |
| Согласовали одно направление, а работает другое                                     | Правка адреса, полей или условий сбрасывает подтверждение; срок действия и автоотключение по простою                                                          |
| Журнал подчищают задним числом                                                                    | Только добавление, цепочка хэшей, чистка недоступна пользователю                                                                                                                            |
| Обещание «данные не утекут» не выдержит проверки                                   | Раздел 10.17: явно перечислено, что закрывает программа, а что — права на папки, шифрование дисков и контроль носителей                                |
| Два сообщения подряд получают один номер КД                                             | Подбор свободного номера и запись — под одним захватом с ручной регистрацией                                                                                                       |
| Повтор сообщения из мессенджера дает второй номер одному документу | Ключ идемпотентности на сообщение; повтор возвращает ранее выданное обозначение                                                                                               |
| По API некому подтвердить запись поверх занятого исполнения                 | `ConfirmedDuplicate` недоступен извне: занятое исполнение — ошибка в ответе, а не перезапись                                                                                           |
| Логика расширения продублирована ради API                                                  | Шаг вызывает тот же`DocRegistrar`, что и окно; дубль логики — признак неверной границы                                                                                                  |
