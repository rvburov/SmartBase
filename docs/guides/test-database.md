# Тестовая БД на 10 млн записей (Tests/)

## Назначение

Стенд для проверки производительности календаря и таблиц на предельных объёмах:
виртуализация «Расписания»/«Журнала», offset/keyset-страницы, посекундная карта
гигантского дня, массовые удаление/дублирование, поиск LIKE по всему окну
(см. [performance.md](../architecture/performance.md)). Все замеры «до ~10 млн записей»
в docs сделаны на этом файле.

## Файл

- Путь: `Tests/test_database.db` (**не коммитится** — в `.gitignore` игнорируются
  `Tests/*.db`; сам генератор и эта документация в репозитории).
- Размер: **~4,6 ГБ**; создание — **~10–20 минут** (зависит от диска).
- Обычная БД приложения (схема EF Core с историей миграций) — подключается как любая
  существующая база: сайдбар → «Подключить базу данных» (или настройки). Более новые
  миграции приложение применит само при первом подключении.

## Профиль данных (10 000 000 записей)

Одна коллекция **«Задачи»** (#007AFF) с одним полем-датой **«Дата»** (источник календаря).
Все события timed (не «весь день»), длительность 1 час:

| Записи (Id) | Название | Распределение |
|---|---|---|
| 1..5 000 000 | «Событие N» | разброс по годам: старт `2020-01-01T00:00:00` + (N−1)×68 с — равномерно покрывает ~2020–2030 (≈1270 событий в день) |
| 5 000 001..10 000 000 | «День N» | **гигантский день** `2026-07-01`: старт `00:00:00` + ((N−5 000 001) mod 86400) с — ≈58 записей на КАЖДУЮ секунду суток |

Форматы значений — ровно как пишет приложение: `db_records.StartDt/EndDt` и
`calendar_index.StartIso/EndIso` — ISO `"o"` (7 знаков дробных секунд), значение
поля-даты в `db_field_values` — `DateValue` «start/end» с точностью до минут.

## Как воссоздать на другом ПК

Генератор закоммичен рядом с файлом — воспроизводит стенд **точь-в-точь**
(схема, включая текст DDL, история миграций, данные):

```bash
python3 Tests/generate_test_database.py           # создаёт Tests/test_database.db
python3 Tests/generate_test_database.py --force   # пересоздать существующий
```

Нужен только Python 3 (стандартная библиотека, без пакетов). Скрипт создаёт таблицы
БЕЗ индексов, льёт данные батчами по 100 тыс. в трёх таблицах (`db_records`,
`db_field_values`, `calendar_index`) с прогрессом раз в миллион и строит индексы в конце —
так на порядок быстрее. Спецификация данных — в шапке
[generate_test_database.py](../../Tests/generate_test_database.py): если файла/скрипта нет
под рукой, по ней стенд можно восстановить любым инструментом.

## Замечания

- Рабочая копия файла «живёт»: правки/дубли/удаления в тестах меняют содержимое
  (например, счётчик записей гигантского дня уже не ровно 5 000 000). Генератор всегда
  даёт исходное состояние.
- Рядом с файлом при работе приложения появляются `test_database.db-wal`/`-shm` —
  тоже игнорируются git.
- Первое открытие «Журнала»/мультибазного «Расписания» на гигантском дне строит
  посекундную карту (~5–7 с фоном) — это ожидаемо (см.
  [journal.md](../features/calendar/journal.md), [schedule.md](../features/calendar/schedule.md)).
- Сетка (День/Неделя/Месяц/Год) на окне с гигантским днём получает только первые
  `GridDayCap` (2000) событий дня + честный «+N ещё» по карте счётчиков; карта на таком
  окне считается ~2–3 с в фоне (оверлей «Загрузка…»), см.
  [performance.md](../architecture/performance.md).
