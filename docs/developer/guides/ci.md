# Полная проверка на GitHub

## Назначение

Прогнать сборку и все тесты на всех операционных системах сразу, на чистой машине, одной
командой — и не запускать это на каждый обычный push.

Локально доступна одна ОС за раз и одно рабочее дерево, накопившее `artifacts/`, `packages/`
и правки за день. Отдельная причина: на локальной машине `dotnet build` умеет отрапортовать
«Ошибок: 0», ничего не перекомпилировав — iCloud откатывает время файлов, и MSBuild считает
сборку свежей. На раннере кэша нет вовсе, соврать нечем.

Это **не** выпуск релиза: здесь ничего не публикуется и не собирается в установщики,
права прогона — только чтение.

## Где в коде

| Файл                                                                | Роль                                             |
|---------------------------------------------------------------------|--------------------------------------------------|
| [.github/workflows/build.yml](../../../.github/workflows/build.yml) | сам прогон: три job'а, шесть раннеров             |
| [Scripts/ci/setup-remote.sh](../../../Scripts/ci/setup-remote.sh)   | заводит команду `git push actions`, один раз      |
| [Scripts/ci/ci-test.sh](../../../Scripts/ci/ci-test.sh)             | тесты модуля, чистый bash                         |
| `docs/developer/guides/ci.md`                                       | этот файл — вся документация модуля               |

Ни один существующий файл проекта модуль не меняет.

## Как запустить

Один раз в каждой копии репозитория:

```bash
Scripts/ci/setup-remote.sh
```

Дальше:

```bash
git push            # отправить main; проверка не запускается
git push actions    # отправить main и запустить полную проверку
```

Результат — вкладка **Actions** в репозитории: шесть строк, по одной на раннер. Красная
показывает, на какой ОС и на каком шаге сломалось.

Автоматически прогон не запускается никогда: триггера на main в workflow нет. Проверка идёт
тогда, когда её запросили.

> Если код не менялся с прошлого раза, `git push actions` отработает молча — git не увидит,
> что двигать. Перезапуск в этом случае — кнопка **Run workflow** на вкладке Actions.

## Что проверяется

| Job                         | Раннеры                                          | Что делает                                                          |
|-----------------------------|--------------------------------------------------|---------------------------------------------------------------------|
| **Сборка и тесты**          | Linux, Windows, macOS Apple Silicon, macOS Intel | сборка обоих таргетов, `Tests/Unit`, `Tests/Integration`             |
| **PostgreSQL**              | Linux + контейнер `postgres:16`                  | девять тестов провайдера на живой базе                               |
| **Вспомогательные проекты** | Linux                                            | сборка `Tests/Benchmarks`, `Tests/DbGenerator`, `Tests/MultiProcess` |

Матрица идёт с `fail-fast: false`: упавшая платформа не отменяет остальные — смысл прогона
в том, чтобы увидеть все поломки сразу.

**macOS Intel** — единственное место, где код вообще запускается под x86_64: сборка `osx-x64`
для раздачи кросс-компилируется на arm64-раннере. Образ `macos-13` последний Intel-образ
GitHub; когда его выведут, строку матрицы придётся убрать.

**PostgreSQL** идёт одним job'ом под Linux: сервис-контейнеры это docker, а docker на раннерах
GitHub есть только там. Прогонять их с трёх ОС и незачем — тесты бьют по живому серверу через
TCP, то есть проверяют один и тот же код независимо от системы. От ОС зависят пути, регистр
имён и нативная сборка SQLite — это `Tests/Integration`, и он идёт на всех четырёх раннерах.

**Вспомогательные проекты** в приложение не входят и обычной сборкой не затрагиваются, из-за
чего тихо гниют: правка в модели ломает генератор стенда, и выясняется это через полгода.

## Сколько это стоит

Прогон занимает около десяти минут по часам, но **порядка 240 оплачиваемых минут**: Linux
считается с множителем ×1, Windows ×2, macOS ×10.

Для публичного репозитория это не имеет значения — минуты бесплатны и не ограничены. Для
приватного существенно: на бесплатном тарифе 2000 минут в месяц, то есть около восьми полных
прогонов. Способ ужаться ровно один — убрать из матрицы две строки macOS, остаток обойдётся
примерно в сорок минут.

## Не пересекается с выпуском релиза

Выпуск — отдельный модуль со своим workflow. Общего нет ничего:

- выпуск отправляет main и тег `v*`, а этот прогон стартует только от служебной ветки `ci` —
  так что выпуск проверку не запускает, а `git push actions` не запускает выпуск;
- отсюда не вызывается ни один скрипт репозитория, только `dotnet` и `psql`;
- ни одного общего файла: удаление любого из модулей не задевает второй.

Дублирование тестов при этом намеренное — выпуск гоняет свои сам, до сборки. Общими их делать
нельзя, иначе удаление одного модуля обезоружило бы второй.

## Тесты модуля

```bash
Scripts/ci/ci-test.sh
```

Семь проверок, чистый bash: ни .NET, ни сети не требуется. Смотрят, что workflow разбирается
как YAML, стартует только от ветки `ci`, не вызывает скриптов, называет существующие проекты,
покрывает все ОС и остаётся отделяемым.

Проверка синтаксиса не формальность: сломанный YAML GitHub не запускает молча, и увидеть это
можно только по тому, что «ничего не произошло».

## Если прогон покраснел

1. Открыть красную строку на вкладке **Actions** — видно ОС и шаг.
2. Раскрыть шаг: в логе полный вывод `dotnet`, включая имена упавших тестов.
3. Воспроизвести локально той же командой — они здесь ровно те, что набирают руками.
4. Падает только на одной ОС — это то, ради чего прогон и заводился. Чаще всего регистр
   в путях (Linux к нему чувствителен, macOS нет) или разделитель пути.
5. Падает только PostgreSQL — сначала посмотреть шаг «Базы стенда»: не поднявшийся контейнер
   выглядит как ошибка соединения, а не как ошибка теста.

Красный прогон ничего не ломает на GitHub: прав на запись у него нет.

GUI и установщики здесь не проверяются — окна и вёрстку смотрят руками
([qa-checklists](../qa-checklists/)), упаковка это работа выпуска релиза.

## Как удалить модуль

```bash
rm -rf Scripts/ci
rm .github/workflows/build.yml docs/developer/guides/ci.md
rmdir -p .github/workflows 2>/dev/null   # если других workflow не осталось
git push origin --delete ci              # служебная ветка на сервере
git status --porcelain                   # только строки «D» — ни одного «M»
```

На каждой машине, где запускался `setup-remote.sh`, останется запись в `.git/config` — она вне
версионного контроля и сама не уйдёт: `git remote remove actions`.

Проект возвращается в прежнее состояние: модуль не менял ни одного существующего файла и ничто
вне него на модуль не ссылается — проверка 7 в `ci-test.sh` следит именно за этим. Из-за этого
гайд намеренно **не** значится в оглавлениях [docs/README.md](../../README.md) и корневого
README: он находится по листингу папки `guides/`.
