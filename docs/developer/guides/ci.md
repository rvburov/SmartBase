# Полная проверка на GitHub

Сборка и все тесты на четырёх операционных системах, на чистой машине, по одной команде.
Автоматически не запускается никогда — только когда попросили.

Ничего не публикует и не собирает в установщики: права прогона — только чтение.

## Где в коде

| Файл                                                                | Роль                                        |
|---------------------------------------------------------------------|---------------------------------------------|
| [.github/workflows/build.yml](../../../.github/workflows/build.yml) | сам прогон: три job'а, шесть раннеров        |
| [Scripts/ci/setup-remote.sh](../../../Scripts/ci/setup-remote.sh)   | заводит команду `git push actions`, один раз |
| [Scripts/ci/ci-test.sh](../../../Scripts/ci/ci-test.sh)             | тесты модуля, чистый bash                    |
| `docs/developer/guides/ci.md`                                       | этот файл                                    |

Существующие файлы проекта модуль не меняет.

## Как запустить

Один раз в копии репозитория:

```bash
Scripts/ci/setup-remote.sh
```

Дальше:

```bash
git push            # отправить main, проверка не запускается
git push actions    # отправить main и запустить проверку
```

Результат — вкладка **Actions**: шесть строк, по одной на раннер.

Если код не менялся, `git push actions` отработает молча — двигать нечего. Перезапуск в этом
случае — кнопка **Run workflow** там же.

## Какие проверки идут

**1. Приложение компилируется.**
`dotnet build SmartBase.csproj -c Release`, оба таргета — `net10.0` и `net10.0-windows10.0.17763`.
Ловит поломку Windows-таргета с нативными тостами: локально его почти никогда не собирают.

**2. Модульные тесты.**
`dotnet test Tests/Unit`.

**3. Интеграционные тесты.**
`dotnet test Tests/Integration` — SQLite во временных файлах. Тесты PostgreSQL здесь уходят
в Skipped, их гоняет пункт 5.

**4. Пункты 1–3 повторяются на четырёх раннерах.**
Linux, Windows, macOS Apple Silicon, macOS Intel. Ловит то, что видно только на конкретной
системе: регистр в путях, разделители, нативные сборки SQLite и SkiaSharp под свою архитектуру.
`fail-fast: false` — упавшая платформа не отменяет остальные.

**5. Тесты PostgreSQL на живой базе.**
Контейнер `postgres:16` на порту 5455, базы `smartbase` и `smartbase2` — та же конфигурация,
что у локального стенда. Девять тестов провайдера, которые без базы всегда Skipped.
Только под Linux: сервис-контейнеры это docker, а docker на раннерах GitHub есть только там.

**6. Тесты PostgreSQL действительно выполнились.**
Отдельный шаг падает, если в отчёте не «Skipped: 0». Без него не поднявшаяся база давала бы
зелёный прогон, не проверивший ничего.

**7. Вспомогательные проекты собираются.**
`Tests/Benchmarks`, `Tests/DbGenerator`, `Tests/MultiProcess`. В приложение они не входят
и обычной сборкой не затрагиваются, поэтому тихо гниют: правка в модели ломает генератор
стенда, и выясняется это через полгода.

Не проверяется: GUI (окна и вёрстку смотрят руками — [qa-checklists](../qa-checklists/))
и упаковка в установщики — это работа выпуска релиза.

## Сколько это стоит

Десять минут по часам, но **порядка 240 оплачиваемых минут**: Linux ×1, Windows ×2, macOS ×10.

Публичному репозиторию всё равно — минуты бесплатны. Приватному нет: 2000 минут в месяц
на бесплатном тарифе, то есть около восьми прогонов. Ужаться можно одним способом — убрать
из матрицы две строки macOS, останется примерно сорок минут.

## Не пересекается с выпуском релиза

- выпуск отправляет main и тег `v*`, проверка стартует только от ветки `ci` — друг друга
  они не запускают;
- отсюда не вызывается ни один скрипт репозитория, только `dotnet` и `psql`;
- общих файлов нет: удаление любого из модулей не задевает второй.

Тесты у выпуска свои, и это намеренно — общими их делать нельзя, иначе удаление одного модуля
обезоружило бы второй.

## Тесты модуля

```bash
Scripts/ci/ci-test.sh
```

Семь проверок, чистый bash: workflow разбирается как YAML, стартует только от ветки `ci`,
не вызывает скриптов, называет существующие проекты, покрывает все ОС, остаётся отделяемым.
Сломанный YAML GitHub не запускает молча — увидеть это можно только по тому, что ничего
не произошло.

## Если прогон покраснел

1. Открыть красную строку на вкладке **Actions** — видно ОС и шаг.
2. Раскрыть шаг: в логе полный вывод `dotnet` с именами упавших тестов.
3. Повторить локально той же командой — они здесь те же, что набирают руками.
4. Упало на одной ОС из четырёх — это то, ради чего прогон и заводился.
5. Упал только PostgreSQL — смотреть шаг «Базы стенда»: не поднявшийся контейнер выглядит
   как ошибка соединения, а не как ошибка теста.

Красный прогон ничего не ломает на GitHub: прав на запись у него нет.

## Как удалить модуль

```bash
rm -rf Scripts/ci
rm .github/workflows/build.yml docs/developer/guides/ci.md
rmdir -p .github/workflows 2>/dev/null   # если других workflow не осталось
git push origin --delete ci              # служебная ветка на сервере
git status --porcelain                   # только строки «D» — ни одного «M»
```

На каждой машине, где запускался `setup-remote.sh`, останется запись в `.git/config` —
она вне версионного контроля: `git remote remove actions`.

Гайд намеренно не значится в оглавлениях [docs/README.md](../../README.md) и корневого README:
модуль удаляется без битых ссылок, проверка 7 в `ci-test.sh` следит за этим.
