# Полная проверка на GitHub

Сборка и все тесты на четырех операционных системах по одной команде. Сама не запускается —
только когда попросили. Ничего не публикует и не собирает в установщики.

## Где в коде

| Файл                                                           | Роль                                                            |
| ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| [.github/workflows/build.yml](../../../.github/workflows/build.yml) | сам прогон: четыре job'а, семь раннеров |
| [Scripts/ci/setup-remote.sh](../../../Scripts/ci/setup-remote.sh)   | заводит команду `git push actions`, один раз |
| [Scripts/ci/ci-test.sh](../../../Scripts/ci/ci-test.sh)             | тесты модуля                                             |
| `docs/developer/guides/ci.md`                                    | этот файл                                                   |

Существующие файлы проекта модуль не меняет.

## Настройка — один раз на машине

```bash
Scripts/ci/setup-remote.sh
```

Без нее `git push actions` отвечает `'actions' does not appear to be a git repository`.

## Запуск

```bash
git add .
git commit -m "fix: ..."
git push actions
```

Дальше — вкладка **Actions** → запуск **Build**: семь строк, около трех минут.

- набирать из корня репозитория, находясь в `main`;
- `git push` без `actions` не запускает ничего;
- код не менялся → прогон не начнется, перезапуск кнопкой **Run workflow** на вкладке Actions.

## Какие проверки идут

**1. Сборка.**
`dotnet build SmartBase.csproj -c Release` — оба таргета, `net10.0` и `net10.0-windows10.0.17763`.

**2. Модульные тесты.**
`dotnet test Tests/Unit`.

**3. Интеграционные тесты.**
`dotnet test Tests/Integration` — SQLite во временных файлах.

**4. Тесты расширений.**
`bash Tests/run-extensions.sh` — по проекту на расширение (`Tests/Extensions/*`). Список наборов
скрипт берет глобом, поэтому заведение и удаление расширения этот workflow не задевают.

**5. Проверка, что тесты ядра не знают про расширения.**
`grep 'SmartBase\.Extensions' Tests/Unit Tests/Integration` обязан быть пустым. Граница между
наборами — не соглашение, а проверяемый инвариант: иначе удаление расширения снова начнет ронять
сборку тестов программы (см. [testing/extension-tests.md](../testing/extension-tests.md)).

**6. Пункты 1–5 на четырех раннерах.**
Linux, Windows, macOS Apple Silicon, macOS Intel. Упавшая платформа не отменяет остальные.

**7. PostgreSQL на живой базе.**
Контейнер `postgres:16`, порт 5455, базы `smartbase` и `smartbase2` — как у локального стенда.
Тесты провайдера (`PgProviderTests`) и создания баз из приложения (`PgCreateDatabaseTests`) —
фильтр `PgProviderTests|PgCreateDatabaseTests`. Только Linux: сервис-контейнеры работают
лишь там.

**8. Проверка, что тесты PostgreSQL не пропущены.**
Шаг падает, если в отчете не «Skipped: 0»: не поднявшаяся база иначе дала бы зеленый прогон,
не проверивший ничего.

**9. Связка с D-Bus для уведомлений Linux.**
Под `dbus-run-session` на Linux-раннере. Ловит разъезд версий `DesktopNotifications.FreeDesktop`
и `Tmds.DBus`: сборка при нем проходит, а менеджер баннеров падает уже у пользователя, причем
молча — исключение проглатывается. Отдельный шаг падает, если тест ушел в Skipped.

**10. Вспомогательные проекты.**
`dotnet build` для `Tests/Benchmarks`, `Tests/DbGenerator`, `Tests/MultiProcess`.

**11. Уборка ветки `ci`.**
Удаляется после прогона, в том числе после красного и отмененного.

Не проверяется: GUI ([qa-checklists](../qa-checklists/)) и упаковка в установщики.

## Сколько это стоит

Около двух с половиной минут по часам — раннеры работают параллельно.

Оплачиваемых минут больше: они считаются по каждому job'у отдельно, округляются вверх до
минуты и умножаются — Linux ×1, Windows ×2, **macOS ×10**. На семь job'ов выходит
**порядка пятидесяти минут** за прогон.

Публичный репозиторий — бесплатно и без ограничений. Приватный — 2000 минут в месяц
на бесплатном тарифе, то есть примерно сорок прогонов; убрать из матрицы две строки macOS →
останется около десяти минут за прогон.

Точная цифра — **Run details → Usage** на странице прогона.

## Не пересекается с выпуском релиза

- триггеры разные: выпуск — `main` и тег `v*`, проверка — ветка `ci`;
- скриптов репозитория не вызывает, только `dotnet` и `psql`;
- общих файлов нет: удаление любого из модулей не задевает второй.

Но перед выпуском прогон обязателен: между выпусками тесты видят только Windows разработчика,
а `gate` релиза идет на ubuntu. Тест, впервые встретивший Linux в момент выпуска, — это красный
релиз и перевыпуск (см. [release.md](release.md), «Пройденные грабли»).

## Тесты модуля

```bash
Scripts/ci/ci-test.sh
```

Восемь проверок, чистый bash. Нужны, только если правили сам модуль — код проекта они
не проверяют.

## Если прогон покраснел

1. **Actions** → красная строка: видно ОС и шаг.
2. Раскрыть шаг — в логе имена упавших тестов.
3. Повторить локально той же командой.
4. Упал только PostgreSQL — смотреть шаг «Базы стенда».

## Как удалить модуль

```bash
rm -rf Scripts/ci
rm .github/workflows/build.yml docs/developer/guides/ci.md
rmdir -p .github/workflows 2>/dev/null   # если других workflow не осталось
git remote remove actions                # на каждой машине, где была настройка
git status --porcelain                   # только строки «D» — ни одного «M»
```

Ветку `ci` удалять не нужно — прогон убирает ее сам.

Гайд намеренно не значится в оглавлениях [docs/README.md](../../README.md) и корневого README:
модуль удаляется без битых ссылок.
