# Полная проверка на GitHub

## Назначение

Прогнать сборку и все тесты на **всех операционных системах сразу**, на чистой машине,
одной командой — и не запускать это на каждый обычный push.

Локально доступна одна ОС за раз и одно рабочее дерево, накопившее `artifacts/`, `packages/`
и правки за день. Здесь каждая платформа получает голый checkout и свой раннер, а результат
складывается в один экран.

Отдельная причина, ради которой всё это и затевалось: на локальной машине `dotnet build` умеет
отрапортовать «Ошибок: 0», ничего не перекомпилировав. iCloud откатывает время файлов, MSBuild
считает сборку свежей, и зелёный результат оказывается фикцией. На раннере кэша нет вовсе —
соврать нечем.

Это **не** выпуск релиза. Здесь ничего не публикуется, не тегируется и не собирается в
установщики; права прогона — только чтение.

## Где в коде

| Файл                                                                     | Роль                                              |
|--------------------------------------------------------------------------|---------------------------------------------------|
| [.github/workflows/build.yml](../../../.github/workflows/build.yml)      | сам прогон: три job'а, шесть раннеров              |
| [Scripts/ci/setup-remote.sh](../../../Scripts/ci/setup-remote.sh)        | настройка команды `git push actions`, один раз на машину |
| [Scripts/ci/ci-test.sh](../../../Scripts/ci/ci-test.sh)                  | тесты модуля, чистый bash                          |
| `docs/developer/guides/ci.md`                                            | этот файл — вся документация модуля                |

Четыре файла, ни один существующий файл проекта модуль не меняет.

## Как запустить

### 1. Один раз на каждой машине

```bash
Scripts/ci/setup-remote.sh
```

Скрипт заводит удалённый репозиторий `actions`, смотрящий на тот же адрес, что и `origin`,
но отправляющий две ссылки вместо одной. Настройки лежат в `.git/config`, а он не под
версионным контролем — поэтому на новом компьютере команду надо повторить.

### 2. Дальше — обычная работа

```bash
git push            # отправить main; GitHub не запускает ничего
git push actions    # отправить main и запустить полную проверку
```

`git push actions` отправляет main как обычно и заодно перематывает служебную ветку `ci`
на тот же коммит. Пуш ветки `ci` — единственный сигнал, по которому прогон стартует.

### 3. Смотреть результат

Вкладка **Actions** в репозитории. Шесть строк, по одной на раннер; красная показывает,
на каком шаге и какой ОС сломалось.

### 4. Перезапустить

Кнопка **Run workflow** на той же вкладке — она запускает прогон вручную, на любой ветке
и без пуша.

Это же и обходной путь для одной ловушки: если код не менялся с прошлого раза, ветка `ci`
уже указывает на нужный коммит, ссылка не сдвигается, события пуша не возникает — и
`git push actions` отработает молча, ничего не запустив.

## Что проверяется

| Job                       | Раннеры                                          | Что делает                                                            |
|---------------------------|--------------------------------------------------|-----------------------------------------------------------------------|
| **Сборка и тесты**        | Linux, Windows, macOS Apple Silicon, macOS Intel | сборка обоих таргетов, `Tests/Unit`, `Tests/Integration`               |
| **PostgreSQL**            | Linux + контейнер `postgres:16`                  | девять тестов провайдера на живой базе                                 |
| **Вспомогательные проекты** | Linux                                          | сборка `Tests/Benchmarks`, `Tests/DbGenerator`, `Tests/MultiProcess`   |

Матрица идёт с `fail-fast: false`: упавшая платформа не отменяет остальные. Иначе за прогон
видно одну поломку из четырёх, а весь смысл — увидеть все сразу.

**Оба таргета.** `dotnet build SmartBase.csproj` собирает и `net10.0`, и
`net10.0-windows10.0.17763`. Второй нужен ради нативных тостов; тесты его не трогают, поэтому
шаг вынесен отдельно. На Linux и macOS он компилируется благодаря `EnableWindowsTargeting`.

**macOS Intel.** Единственное место, где код вообще **запускается** под x86_64-macOS: сборка
`osx-x64` для раздачи кросс-компилируется на arm64-раннере, и там сверяется только архитектура
бинаря. Здесь под x64 работают нативные SQLite и SkiaSharp. Образ `macos-13` — последний
Intel-образ GitHub; когда его выведут, строку матрицы придётся убрать.

**PostgreSQL.** Тесты провайдера — `SkippableFact`: без поднятого стенда они молча уходят
в Skipped. Локально стенд — docker-контейнер, на раннере — сервис-контейнер, проброшенный
на тот же порт 5455, так что в коде тестов ничего настраивать не нужно. Контейнеры-сервисы
работают только на Linux-раннерах, поэтому это отдельный job, а не шаг матрицы.

Отдельный шаг после прогона убеждается, что тесты **не** ушли в Skipped. Без него job был бы
зелёным и в случае, когда база не поднялась, — зелёный прогон, не проверивший ничего, хуже
красного.

**Вспомогательные проекты** в приложение не входят и обычной сборкой не затрагиваются.
Из-за этого они тихо гниют: правка в модели ломает генератор стенда, и выясняется это через
полгода, когда стенд понадобился срочно.

## Почему прогон не запускается сам

Триггер — только `push: branches: [ci]` и ручной запуск. Ни `push` в main, ни `pull_request`
здесь нет намеренно.

Причина не в экономии минут, а в том, что автоматический прогон на каждый коммит быстро
становится фоном: половина запусков идёт на промежуточные коммиты, красный цвет перестают
читать. Явная команда делает проверку событием — её запускают, когда есть что проверять.

## Почему это не пересекается с выпуском релиза

Выпуск — отдельный модуль со своим workflow. Пересечений с ним нет ни во времени, ни по файлам:

- выпуск отправляет main и тег `v*`; под фильтр `branches: [ci]` не подпадает ни то, ни другое,
  так что выпуск этот прогон не запускает, а `git push actions` не запускает выпуск;
- отсюда не вызывается ни один скрипт репозитория — только `dotnet` и `psql`;
- ни один файл не общий: удаление любого из двух модулей не задевает второй.

Проверки 3 и 4 в `ci-test.sh` следят за этим машинно, а не на слово.

Дублирование при этом есть и оно намеренное: выпуск гоняет свои тесты сам, до сборки. Общими
их делать нельзя — иначе удаление одного модуля обезоружило бы второй.

## Сколько идёт и сколько стоит

Полный прогон занимает около **десяти минут**: раннеры работают параллельно, дольше всех идут
macOS.

Оплачиваемых минут получается **порядка двухсот сорока** за прогон — минуты считаются
с множителем: Linux ×1, Windows ×2, **macOS ×10**.

Для **публичного** репозитория это не имеет значения: минуты бесплатны и не ограничены.

Для **приватного** — существенно: на бесплатном тарифе даётся 2000 минут в месяц, то есть
примерно **восемь полных прогонов**. Способ ужаться ровно один: убрать из матрицы две строки
macOS — остаток обойдётся примерно в сорок минут. Точный расход показывает
**Settings → Billing**.

## Тесты модуля

```bash
Scripts/ci/ci-test.sh
```

Семь проверок, чистый bash: ни .NET, ни сети, ни `gh` не требуется. Прогон ничего не меняет —
проверка 7 подтверждает это машинно.

| # | Проверка |
|---|---|
| 1 | Workflow разбирается как YAML (`actionlint`, PyYAML или ruby — что найдётся) |
| 2 | `bash -n` по скриптам модуля |
| 3 | Триггеры: только ветка `ci` и ручной запуск, ни main, ни тегов |
| 4 | Ни одного вызова скриптов репозитория — только `dotnet` и `psql` |
| 5 | Все проекты и наборы тестов, названные в workflow, существуют |
| 6 | Матрица покрывает Linux, Windows и обе архитектуры macOS |
| 7 | Отделяемость: файлы на месте, git их не игнорирует, ссылок извне нет, дерево не тронуто |

Проверка 1 не формальность. Значение `if` с двоеточием внутри строки, многострочный `options`
у сервиса — такие вещи ломают YAML молча, а GitHub при неразбираемом файле просто не запускает
workflow. Ошибку видно только по тому, что «ничего не произошло».

## Если прогон покраснел

1. Открыть красную строку на вкладке **Actions** — сразу видно ОС и шаг.
2. Раскрыть шаг: в логе полный вывод `dotnet`, включая имена упавших тестов.
3. Воспроизвести локально той же командой из шага — они здесь ровно те, что набирают руками.
4. Если падает **только на одной ОС** — это то, ради чего прогон и заводился. Чаще всего
   регистр в путях (на Linux файловая система чувствительна к нему, на macOS — нет) или
   разделитель пути.
5. Если падает **только PostgreSQL** — сначала проверить шаг «Базы стенда»: не поднявшийся
   контейнер выглядит как ошибка соединения, а не как ошибка теста.
6. Починить, закоммитить, снова `git push actions`.

Красный прогон ничего не ломает на GitHub: прав на запись у него нет.

## Известные ограничения

- **GUI не проверяется.** Тесты покрывают логику; окна, вёрстку и поведение при зуме проверяют
  руками — см. [qa-checklists](../qa-checklists/).
- **Установщики не собираются.** Упаковка и подпись — работа выпуска релиза. Здесь только
  `dotnet build`, без `publish`.
- **Пакеты не кэшируются.** `cache: true` у `setup-dotnet` выставляет `NUGET_PACKAGES` и
  перебивает `globalPackagesFolder` из `nuget.config` — поведение прогона разошлось бы
  с локальным. Плата — примерно полторы минуты restore на каждом раннере.
- **`macos-13` конечен.** Последний Intel-образ GitHub; после вывода строку матрицы надо убрать.
- **Повторный запуск на том же коммите** через `git push actions` не срабатывает — ссылка
  не сдвигается. Кнопка **Run workflow** на вкладке Actions.

## Как удалить модуль

```bash
rm -rf Scripts/ci
rm .github/workflows/build.yml docs/developer/guides/ci.md
rmdir -p .github/workflows 2>/dev/null   # если других workflow не осталось
git status --porcelain                   # только строки «D» — ни одного «M»
```

На каждой машине, где запускался `setup-remote.sh`, останется настройка в `.git/config`:

```bash
git remote remove actions
git push origin --delete ci   # служебная ветка на сервере
```

Проект возвращается в прежнее состояние: модуль не менял ни одного существующего файла и ничто
вне него на модуль не ссылается — проверка 7 в `ci-test.sh` следит именно за этим. Из-за этого
гайд намеренно **не** значится в оглавлениях [docs/README.md](../../README.md) и корневого
README: он находится по листингу папки `guides/`.

## Взаимодействия

Модуль ничего не вызывает и ничего не меняет. Он читает репозиторий и запускает `dotnet` —
те же команды, что набирают руками:

- собирает `SmartBase.csproj` — см. [build-and-run.md](build-and-run.md);
- гоняет `Tests/Unit` и `Tests/Integration` — см.
  [automated-tests.md](../testing/automated-tests.md);
- поднимает PostgreSQL той же конфигурации, что локальный стенд — см.
  [postgresql-setup.md](postgresql-setup.md).

Обратной связи нет: ни один файл проекта не знает о существовании этого модуля.
