# Проверки на GitHub

Один workflow **«Проверки»** в [.github/workflows/build.yml](../../../.github/workflows/build.yml)
проверяет ветки агентов, PR и выпуск. Быстрый профиль выполняет Unit и тесты расширений на Linux;
полный добавляет четыре ОС, живой PostgreSQL, закрытые конфигурации и стенд панели чтения.
Workflow ничего не публикует и не удаляет ветки.

## Когда запускается

| Событие | Профиль |
|---|---|
| push ветки, кроме `main` и `ci` | быстрый |
| PR в `main` | быстрый |
| push `ci` | полный |
| **Actions → Проверки → Run workflow** | полный |
| вызов из Release с `full: true` | полный, на SHA разрешенного тега |
| обычный push `main` | не запускается |
| push тега | самостоятельно не запускается; Release вызывает полный профиль |

Push ветки и ее PR делят группу `concurrency`: новый прогон отменяет предыдущий. Репозиторий
исходной ветки входит в имя группы, поэтому одинаковые имена в fork не пересекаются. Полный и
быстрый профили разделены; повторные проверки выпуска разделены по переданному SHA.

## Устройство

| Файл | Назначение |
|---|---|
| [.github/workflows/build.yml](../../../.github/workflows/build.yml) | общий workflow |
| [Scripts/ci/select-scope.sh](../../../Scripts/ci/select-scope.sh) | выбор quick/full |
| [Scripts/ci/check-results.sh](../../../Scripts/ci/check-results.sh) | итоговый обязательный гейт |
| [Scripts/ci/check-trx.py](../../../Scripts/ci/check-trx.py) | контроль результатов и пропусков PG/D-Bus |
| [Scripts/ci/setup-remote.sh](../../../Scripts/ci/setup-remote.sh) | необязательная команда `git push actions` |
| [Scripts/ci/ci-test.sh](../../../Scripts/ci/ci-test.sh) | проверки самого CI без .NET и сети |

Job `scope` выбирает профиль. `agent-tests` выполняет быстрые проверки при каждом запуске.
Полные jobs `test`, `closed-loop`, `postgres`, `tools` зависят от `scope`, а не друг от друга.
Job `checks` (**«Итог проверок»**) запускается всегда и требует успеха всех jobs выбранного
профиля. Запрос полного профиля также проверяется независимо от результата `scope`:
подмена его быстрым профилем, отмененный или пропущенный обязательный job дают красный итог.

## Что входит в полный профиль

`LANG=ru_RU.UTF-8` задает культуру Linux. Windows и macOS могут использовать системную
культуру; тесты с ожиданиями конкретного формата задают `CurrentCulture` явно.

- **Linux, Windows, macOS Apple Silicon и macOS Intel:** сборка обоих таргетов приложения,
  Unit, Integration и все проекты `Tests/Extensions/*`. `fail-fast: false` сохраняет результаты
  остальных ОС при падении одной.
- **Граница ядра и расширений:** на Linux проверяется отсутствие обращений к конкретным
  расширениям и `ExtensionRegistry` в Unit/Integration.
- **Уведомления Linux:** отдельный тест под `dbus-run-session`; TRX должен содержать реальный
  успешный тест без пропусков.
- **Закрытые конфигурации:** сборки с `ClosedLoop=true`, `NoListener=true`, обоими флагами;
  затем проверка исходных Open-файлов и обычная сборка.
- **PostgreSQL:** контейнер `postgres:16` на `localhost:5455`, пользователь стенда `postgres`,
  базы `smartbase` и `smartbase2` по контракту `PgTestServer`. На Ubuntu 24.04 устанавливаются
  нативные `pg_dump` и `pg_restore` версии 16, их каталог ставится первым в PATH, а ссылки
  `/usr/bin/pg_dump` и `/usr/bin/pg_restore` закрепляются за этой версией на одноразовом раннере. Поэтому
  выполняются и проверки резервного копирования/восстановления настоящими клиентами.
- **Весь Integration с PostgreSQL:** без фильтра имен классов, под D-Bus. Новые PG-теории
  библиотеки, связей, целостности и восстановления автоматически входят в этот прогон.
- **Вспомогательные проекты:** сборка `Tests/Benchmarks`, `Tests/DbGenerator`, `Tests/MultiProcess`
  и `Tests/DocReader`; стенд `DocReader` также запускается. `Tests/RecordPage` собирается для
  `net10.0`, затем последовательно выполняет headless-режимы `relations`, `relationcomputed`
  и `relationintegrity`: права доступа, ручные и автоматические связи, вычисления и проверка
  целостности. Эти режимы создают свои базы; результаты и каталог эталонов находятся в `RUNNER_TEMP`.

TRX-проверка PG требует выполненных `PgProviderTests`, `PgBackupTests` и `LinuxNotificationsTests`.
Разрешены только пять уже известных пропусков: три Windows-проверки `PgLocalInstallTests`,
`UserValueTests.Author_column_is_filterable_sortable_and_exported` и
`TaskRecordsTests.Task_creation_fills_other_user_fields_the_same_with_and_without_due`.
Две последние проверки явно помечены в исходниках как дефекты продукта. Любой другой пропуск
делает job красным; недоступный PostgreSQL не превращается в успешный пустой прогон.

## Полный запуск по команде

Кнопка **Run workflow** запускает полный профиль на выбранной ветке. Для отправки локального
`main` и запуска полной проверки можно один раз настроить отдельный remote:

```bash
Scripts/ci/setup-remote.sh
git push actions
```

`actions` указывает на тот же сервер, что `origin`; отправляет локальный `main` в `main`
обычной перемоткой и обновляет только служебную `ci`. Содержимое текущей агентской ветки вместо
`main` скрипт не подставляет. Если SHA `ci` не изменился, нового push-события нет — используйте
кнопку **Run workflow**.

`ci` остается после прогона. Автоматической уборки нет: отмененный старый запуск не должен
удалять ссылку, которую уже обновил другой пользователь. `main`, `work` и чужие ветки CI
не удаляет. Ручное удаление `ci` допустимо только по отдельной просьбе, после проверки владельца
и текущего SHA; наличие старого прогона само по себе такого разрешения не дает.

## Повторное использование при выпуске

Release вызывает этот же файл как reusable workflow:

```yaml
checks:
  needs: gate
  uses: ./.github/workflows/build.yml
  with:
    full: true
    ref: ${{ needs.gate.outputs.sha }}
```

`ref` — неизменяемый SHA проверенного тега, а не SHA ветки, с которой нажали ручной перевыпуск.
Все checkout используют `inputs.ref || github.sha`. Для обычной агентской ветки это SHA события;
для выпуска — явно переданный SHA. `full: true` выбирает полный профиль даже при исходном событии
push тега. Фильтр веток самостоятельного запуска не ограничивает reusable-вызов.

Workflow проверок имеет только `contents: read`. Упаковка и публикация остаются в Release;
успешные проверки сами по себе ничего не выпускают.

## Проверка и диагностика CI

```bash
bash Scripts/ci/ci-test.sh
```

Скрипт проверяет маршрутизацию, обязательность итоговых jobs, YAML при наличии actionlint/PyYAML
и TRX на маленьких фикстурах. Он не собирает приложение, не запускает его тесты, не обращается
к серверу и не меняет git-настройки или ветки.

При красном прогоне откройте **Actions → Проверки**, нужный job и шаг. Повторите команду шага
локально. Матрица сохраняет Unit/Integration TRX во временном каталоге, быстрый профиль — Unit.
Оба профиля сохраняют отдельные TRX всех проектов расширений в `RUNNER_TEMP/extensions-results`
с уникальными именами. При ошибке общий formatter читает эти отчеты и выводит в публичные
annotations первые 10 имен упавших тестов с сообщениями до 1500 символов.
Для PG сначала смотрите установку клиентов и создание обеих баз; для пропусков —
сообщение `check-trx.py`. Длительность полного профиля зависит от Integration и очереди раннеров;
точные время и расход минут видны в **Run details → Usage**.
