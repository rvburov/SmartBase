# Выпуск релиза на GitHub

Как выпустить готовые сборки для всех операционных систем одной командой, ничего не собирая на
своей машине. Собирает GitHub: вы отправляете тег, через ~12 минут на странице релизов лежат
четыре архива с программой.

Устроено отдельным **отделяемым модулем**: восемь новых файлов, ни один существующий файл
проекта не изменен. Удаляется четырьмя `rm` — см. [«Как удалить модуль»](#как-удалить-модуль).

## Назначение

Раздача программы посторонним. До этого модуля получить SmartBase можно было только одним
способом: склонировать репозиторий, поставить .NET SDK 10 и собрать самому.

**Чем это НЕ является.** Автообновление внутри программы по-прежнему берет файлы из сетевой или
файловой папки (ключ `updatePath`, см. [auto-update.md](auto-update.md)) и на GitHub не смотрит.
GitHub Releases — **дополнительный** канал раздачи, а не замена. Чтобы обновить пользователей,
архив из релиза распаковывают в ту самую сетевую папку.

Модуль также не собирает ничего на каждый `git push`: ни CI на ветки, ни проверок pull request
здесь нет намеренно. Не каждый push — релиз.

> ⚠ Папка называется `github-release`, а не `release`, не для красоты. В
> [.gitignore](../../../.gitignore) есть стандартное для .NET правило `[Rr]elease/`, и папка
> `Scripts/release/` целиком выпала бы из git — молча, без единого предупреждения. Переименовать
> ее обратно нельзя; проверка 8 в `release-test.sh` за этим следит.

## Как работает

### Одна команда

```bash
# 1. Переименовать «## [Не выпущено]» в release-history.md в «## [1.0.4]» и описать изменения

# 2. Закоммитить это описание и отправить все накопленное.
#    Без этого шага release.sh откажется работать: он требует, чтобы main совпадала
#    с origin/main, иначе тег уедет на коммит, которого на GitHub нет.
git add Scripts/github-release/release-history.md
git commit -m "docs(release): описание версии 1.0.4"
git push origin main

# 3. Выпустить:
Scripts/github-release/release.sh 1.0.4
```

Скрипт проверит предусловия, покажет план, спросит подтверждение — и дальше сам:

| Что делает                                     | Где                 |
| ------------------------------------------------------- | ---------------------- |
| `<Version>` → 1.0.4                                  | `SmartBase.csproj`   |
| бейдж →`version-1.0.4-blue`                     | `README.md`          |
| дата в заголовке секции             | `release-history.md` |
| коммит`release: v1.0.4`                         | git                    |
| аннотированный тег`v1.0.4`           | git                    |
| `push origin main`, затем `push origin v1.0.4` | git                    |

Порядок push важен: если ветку отклонили (кто-то опередил), тег в удаленку не уедет и версию
можно перевыпустить, ничего не разбирая на сервере.

Полезные ключи:

```bash
Scripts/github-release/release.sh 1.0.4 --dry-run      # только проверки, ни один файл не изменен
Scripts/github-release/release.sh 1.0.4 --skip-tests   # без прогона Tests/Unit
Scripts/github-release/release.sh 1.0.4 --allow-dirty  # разрешить незакоммиченные правки
```

`gh` CLI локально не нужен — все на голом git.

### Что проверяется до выпуска

Любая непройденная проверка останавливает скрипт **до** первой записи в файлы:

1. Версия строго в формате `X.Y.Z`. Суффиксы вроде `1.0.4-rc.1` запрещены: у shields.io дефис —
   разделитель полей, и бейдж `version-1.0.4-rc.1-blue` распался бы на message `1.0.4` и цвет
   `rc.1`. Бейдж сломался бы молча, а сверка версий прошла бы ложно.
2. Ветка `main`, рабочее дерево чистое.
3. Локальная `main` совпадает с `origin/main`.
4. Тег не занят ни локально, ни на GitHub.
5. Новая версия строго больше текущей (защита от опечатки `1.0.4` → `1.0.3`).
6. Текущее состояние согласовано и в `release-history.md` есть **непустая** секция новой версии.
7. `dotnet test Tests/Unit` проходит.

Чего скрипт проверить не может — зеленую матрицу на четырех ОС. Локально тесты идут только на
Windows разработчика, а job `gate` на GitHub — на ubuntu, поэтому тест, написанный между
выпусками, впервые встречает Linux в момент выпуска. Перед `release.sh` — `git push actions` и
зеленый Build ([ci.md](ci.md)); иначе красный `gate` и перевыпуск по сценарию 2.

### Что происходит на GitHub

Push тега `v1.0.4` ловит `release.yml`. Три стадии:

| Стадия | Где                       | ~Время | Что делает                                                                                                                                                                    |
| ------------ | ---------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gate`     | ubuntu                       | 4 мин    | сверяет тег с`<Version>` в коде, проверяет что тег стоит на коммите из `main`, гоняет `Tests/Unit` и `Tests/Integration` |
| `build`    | windows + ubuntu + macOS ×2 | 8 мин    | четыре платформы параллельно: сборка, проверка артефакта, упаковка                                                            |
| `publish`  | ubuntu                       | 1 мин    | контрольные суммы, тело релиза, создание релиза                                                                                                |

`gate` стоит первым потому, что собрать четыре платформы и опубликовать релиз с заведомо
сломанным кодом — самая дорогая из возможных ошибок.

Сверка «тег == код» есть только здесь: локальный `release.sh` ее сделать не может, он тег и
создает. При расхождении — отказ, без попыток что-либо починить: иначе опубликованный релиз
перестал бы соответствовать коммиту, на который указывает тег.

> ⚠ Тесты PostgreSQL (`Tests/Integration/PgProviderTests.cs`) в CI уходят в Skipped — стенда на
> `localhost:5455` там нет. Это штатно: релизная сборка провайдер не меняет.

Право на запись в репозиторий включено ровно в одном job — `publish`. Публикация идет
предустановленным на runner'е `gh`, стороннего кода с доступом к репозиторию в цепочке нет.

### Нумерация версий

SemVer в трактовке настольного приложения без публичного API:

| Компонента | Когда увеличивается                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MAJOR**      | несовместимая миграция базы или смена формата данных — откатиться назад нельзя |
| **MINOR**      | новый раздел, тип поля, расширение, заметная возможность                                            |
| **PATCH**      | исправления, производительность, рефакторинг                                                               |

Коммиты `docs:` и `chore:` сами по себе релиз не оправдывают.

Дата в тег не кладется: аннотированный тег хранит ее внутри (`git show v1.0.4`), GitHub рисует
ее рядом с релизом, и она стоит в заголовке секции истории релизов. Тег `v1.0.4`, заголовок релиза
`SmartBase 1.0.4`, коммит `release: v1.0.4`.

### История релизов

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) с русскими заголовками.
По ходу работы правки пишутся в секцию `## [Не выпущено]`. Перед выпуском ее переименовывают в
номер версии — дату проставит `release.sh`, ссылки-сноски внизу файла он же и перепишет.

```markdown
## [Не выпущено]

## [1.0.4] — 2026-08-08

### Добавлено
- Расширение «Документы в коллекцию».

### Исправлено
- Автообновление не роняет приложение при тихом старте из автозапуска.
```

Разделы — только непустые: **Добавлено**, **Изменено**, **Исправлено**, **Удалено**,
**Безопасность**. Пустая секция считается ошибкой: релиз без описания никому не нужен, и выпуск
на этом останавливается.

Тело релиза = секция истории релизов + таблица установки + предупреждение о подписи + как обновить
сетевую папку + контрольные суммы + полный список коммитов под спойлером. Посмотреть заранее:

```bash
Scripts/github-release/release-notes.sh 1.0.4
```

### Артефакты

Раздается **ровно один файл на платформу** — установщик. Обычный `SmartBase` из `dist/`
не публикуется: это тот же бинарь, и установщик ставит его сам.

| Вложение релиза        | Что внутри                                          |
| ------------------------------------ | ------------------------------------------------------------ |
| `SmartBase-Setup.exe`              | сам установщик, без архива             |
| `SmartBase-1.0.4-osx-arm64.dmg`    | `SmartBase-Setup.app` + окно с инструкцией |
| `SmartBase-1.0.4-osx-x64.dmg`      | то же                                                    |
| `SmartBase-1.0.4-linux-x64.tar.gz` | `SmartBase-Setup`                                          |

Во вложениях **только программа**, больше ничего. Ни файла контрольных сумм — GitHub
показывает `sha256` рядом с каждым вложением сам, — ни `LICENSE`, ни
`THIRD-PARTY-NOTICES.txt`: оба лежат в корне репозитория и доступны со страницы проекта.
Списка коммитов в теле релиза тоже нет: что изменилось, сказано человеческим языком в разделе
из истории релизов, а полная история на расстоянии одной ссылки. Страница релиза — место, где
скачивают программу, и ничем больше.

**Папка при распаковке не создается ни на одной системе.** Windows скачивает готовый `.exe` —
распаковывать нечего. macOS монтирует образ. Linux после `tar -xzf` кладет `SmartBase-Setup`
в текущий каталог.

- **macOS** — `.dmg`, а не архив, и дело не в формате: **окно образа — единственное место, где
  можно показать инструкцию до того, как Gatekeeper заблокирует запуск.** Само приложение
  этого сделать не может, его к тому моменту еще не запустили. См. следующий раздел.
- **Linux** — скачанный напрямую бинарь приходит без бита запуска, и `./SmartBase-Setup`
  отвечает `Permission denied`. `tar` бит сохраняет, а распаковка все равно дает один файл
  без папки.

Три правила, каждое выстрадано:

1. **Имя `SmartBase-Setup` менять нельзя.** Режим установки включается по окончанию имени
   (`Program.cs`, `ResolveMode`, строка 141) — на Windows и Linux по имени файла, на macOS по
   имени бандла. Поэтому версия и платформа уходят в имя **архива**, а файл внутри остается
   как есть. По той же причине Windows-установщик кладется без архива: имя доезжает до
   пользователя нетронутым, и его можно сразу положить в сетевую папку обновлений.
2. **В архиве ровно один элемент.** Тогда распаковка не создает папку-обертку. Пока в архиве
   лежало четыре файла, macOS создавал каталог **`SmartBase-1`** — Archive Utility обрезает
   имя архива по первой точке, и `SmartBase-1.0.3-osx-arm64.zip` превращался в `SmartBase-1`.
   Проверяется машинно: после упаковки архив распаковывается обратно и элементы считаются.
3. **Упаковка у каждой ОС своя.** `ditto` на macOS — обычный `zip` теряет расширенные атрибуты
   внутри бандла, после чего `.app` не стартует. `tar.gz` на Linux — zip теряет бит запуска, и
   после «Извлечь» в GNOME бинарь оказывается незапускаемым. Windows — без упаковки вовсе.

`LICENSE` и `THIRD-PARTY-NOTICES.txt` в раздачу не входят вовсе — ни в архивы, ни во
вложения. Решение владельца проекта. Оба файла остаются в корне репозитория.

> ⚠ Установщик нельзя переименовывать. `SmartBase-Setup (1).exe`, который создает браузер при
> повторном скачивании, уже не оканчивается на `-Setup` и запустится обычной программой, а не
> установщиком — молча, без ошибки. Предупреждение об этом входит в тело каждого релиза.

### Первый запуск и предупреждения системы

Скачанный файл получает метку «пришло из интернета», и система требует подтверждения. Обойти
это без платных сертификатов нельзя — можно только не бросать человека одного перед окном,
где кнопка по умолчанию называется «Переместить в Корзину».

**macOS.** Инструкция нарисована фоном окна образа: человек читает четыре шага **раньше**,
чем увидит предупреждение. Фон рисует
[dmg-background.swift](../../../Scripts/github-release/dmg-background.swift) — кодом, а не
картинкой в репозитории: текст правится как обычный исходник, в диффах видно, что поменялось,
бинарных блобов не заводится. Из инструментов нужен только `swift`, он есть и на раннере.
Формулировки и названия кнопок — дословно из интерфейса macOS 26, включая «Все равно открыть».

Само окно раскладывает Finder через `osascript`: размер, вид значками, подпись под значком,
фон и позиция значка. **Это единственное место во всем модуле, которое может не сработать на
раннере** — Finder требует графического сеанса. Поэтому шаг не валит сборку: без оформления
образ остается рабочим, просто без инструкции, и в лог уходит `::warning::`.

Предупреждение появляется **один раз**, только для установщика. Раньше их было два: macOS
переносит метку карантина на все, что записывает карантинный процесс, и установленная
`~/Applications/SmartBase.app` тоже оказывалась заблокированной. Это починено в
`Setup/InstallService.cs` (`ClearQuarantine`) — правка вне модуля, отдельным коммитом.

**Windows.** Аналога окна образа нет: SmartScreen показывает свое окно, и сказать что-либо
заранее негде. Пошаговое описание («Подробнее» → «Выполнить в любом случае») входит в тело
релиза.

**Linux.** Ничего не блокирует, инструкция не нужна.

> ⚠ Бинарники не подписаны сертификатом. `.app` подписываются ad-hoc — это не снимает карантин,
> но отличает «неизвестный разработчик» (обходится) от «приложение повреждено» (не обходится
> вовсе). Инструкция по обходу SmartScreen и Gatekeeper входит в тело каждого релиза.

### Команды: пошагово

Четыре сценария. Первый — рабочий, остальные три нужны, когда что-то пошло не так.

#### 1. Выпустить новую версию

```bash
# 1. Описать изменения: переименовать «## [Не выпущено]» в release-history.md
#    в «## [1.0.4]» и заполнить разделы.

# 2. Проверить, не запуская выпуск (ничего не меняет):
Scripts/github-release/release.sh 1.0.4 --dry-run

# 3. Выпустить:
Scripts/github-release/release.sh 1.0.4
```

Скрипт спросит подтверждение, поднимет версию, закоммитит, поставит тег и отправит.
Дальше GitHub соберет четыре платформы и опубликует релиз — примерно двенадцать минут.

#### 2. Перевыпустить ту же версию

Нужно, когда сборка упала или в релизе нашлась ошибка, а **версией еще никто не пользуется**.
Идея: удалить тег и релиз, поправить, поставить тег заново.

```bash
# 1. Удалить релиз на GitHub — страница релиза, кнопка с корзиной справа вверху.
#    Без этого новый прогон допишет файлы в старый релиз вместо создания нового.

# 2. Поправить код и закоммитить, как обычно.

# 3. Одной строкой: отправить код, снять старый тег, поставить заново, запустить сборку.
git push origin main; git push --delete origin v1.0.4 2>/dev/null; git tag -d v1.0.4 2>/dev/null; git tag -a v1.0.4 -m "SmartBase 1.0.4" && git push origin v1.0.4
```

Разделители в строке **не одинаковые, и это важно**. Первые три шага идут через `;` —
«выполняй дальше в любом случае». Через `&&` цепочка обрывалась бы на попытке удалить тег,
которого на сервере уже нет: `error: unable to delete 'v1.0.4': remote ref does not exist`.
Так и произошло при первом перевыпуске. `2>/dev/null` прячет ругань про отсутствующие ссылки.

Последние два шага соединены `&&` намеренно: если тег не создался, пушить нечего.

#### 3. Пересобрать бинарники, не двигая тег

Когда код правильный, а сломался сам процесс сборки (упал раннер, поправили workflow
в отдельной ветке). Тег остается на месте, релиз обновляется:

**Actions → Release → Run workflow**, поле `tag` = `v1.0.4`, галочку `draft` не ставить.

Тот же результат дает «Re-run failed jobs» на упавшем прогоне — но она берет workflow из
коммита, на который указывает тег. Если чинили сам `release.yml`, перезапуск подхватит старую,
несломанную версию файла: нужен сценарий 2.

#### 4. Отменить релиз полностью

```bash
# 1. Удалить релиз на GitHub — кнопка с корзиной на его странице.
# 2. Снять тег:
git push --delete origin v1.0.4
git tag -d v1.0.4
```

Только если версией еще никто не пользовался. Опубликованный и скачанный релиз удалять нельзя:
у людей останутся битые ссылки.

### Что запрещено

| Ситуация                                                 | Что произойдет                                                                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `release.sh` с занятым тегом                      | отказ, ничего не меняется                                                                |
| повторный push того же тега                   | git откажет сам                                                                                     |
| **сдвиг тега** `git push --force origin v1.0.4` | должно быть запрещено на сервере, см. ниже                                  |
| релиз уже существует                           | файлы и заметки перезаписываются, тег и коммит не трогаются |

Опубликованный релиз GitHub привязывает к тегу навсегда: `gh release edit` не может изменить
коммит. Это и есть гарантия «сборка перевыпускается, тег не двигается». Чтобы ее нельзя было
обойти, включите защиту тегов: **Settings → Rules → New ruleset**, Target: Tags, шаблон `v*`,
галочки **Restrict updates** и **Restrict deletions**. Делать это стоит **после** первых
экспериментов, иначе тестовые теги не удалятся.

### Черновик — главная ловушка

И push тега, и ручной запуск публикуют релиз **сразу**: галочка `draft` при ручном запуске
есть, но снята по умолчанию. Знать про нее все равно нужно, потому что **черновик виден
только владельцу репозитория**.

Как это выглядит: прогон зеленый, файлы на месте, на странице релиза рядом с заголовком
серая плашка **Draft**. А анонимный посетитель на странице Releases видит
«There aren't any releases here», на вкладке Tags — только автоматические архивы исходников.

Что делать: нажать **Publish release** на странице релиза. Или, если файлы устарели, пройти
сценарий 2.

Шаг публикации печатает фактический статус последней строкой лога — проверять браузером
в режиме инкогнито не нужно:

```
черновик: false  https://github.com/rvburov/SmartBase/releases/tag/v1.0.4
```

### Тесты модуля

```bash
Scripts/github-release/release-test.sh
```

Восемь проверок, чистый bash: ни .NET, ни сети, ни `gh` не требуется. Прогон ничего не меняет —
это проверяется отдельным пунктом, как и то, что на модуль ниоткуда не ссылаются.

| # | Что проверяет                                                                                                                                           |
| - | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | синтаксис всех скриптов модуля                                                                                                           |
| 2 | `check-version.sh` согласен с текущим состоянием и находит три расхождения на выдуманной версии |
| 3 | `release.sh` отвергает `1.0`, `1.0.4-rc.1`, `1.0.4.5` и версию не больше текущей                                             |
| 4 | `release.sh --dry-run` доходит до конца или честно останавливается на незаполненной истории           |
| 5 | тело релиза собирается целиком, без незаполненных заготовок                                                     |
| 6 | в release-history.md есть непустая секция текущей версии                                                                            |
| 7 | триггеры workflow — только теги и ручной запуск (либо полный`actionlint`, если установлен)                |
| 8 | модуль отделяем: файлы на месте, ссылок извне нет, дерево не тронуто                                         |

`actionlint` ставится по желанию: `brew install actionlint`. Без него проверка 7 сводится к
контролю триггеров и помечается как пропущенная.

### Обкатка без настоящего релиза

Тегируйте **текущую** версию — ту, что уже в csproj, README и release-history.md:

```bash
git tag -a v1.0.3 -m "SmartBase 1.0.3"
git push origin v1.0.3
```

Гейт пройдет, соберутся четыре платформы, релиз создастся. Что смотреть:

- `gate` падает, если подменить версию в csproj, — значит гейт живой;
- четыре архива на месте, размеры сопоставимы;
- macOS: распакованный `SmartBase-Setup.app` запускается, не «поврежден»;
- Linux: `./SmartBase-Setup` исполняем;
- Windows: `SmartBase-Setup.exe` показывает версию в свойствах файла;
- тело релиза отрендерилось — таблицы на месте;
- в теле релиза нет ни списка коммитов, ни лишних разделов;
- macOS: в окне образа видна инструкция целиком, а не обрезанная снизу;
- рядом с заголовком релиза **нет** плашки `Draft`, и в логе публикации `черновик: false`;
- повторный ручной запуск на том же теге не создает дубль, а перезаписывает файлы.

Уборка — удалить релиз в UI, затем снять тег:

```bash
git push --delete origin v1.0.3 2>/dev/null; git tag -d v1.0.3
```

Через `;`, а не `&&`: тег на сервере может уже отсутствовать (например, его убрали вместе
с релизом), и `&&` оборвал бы уборку на полпути — см. [сценарий 2](#2-перевыпустить-ту-же-версию).

## Перспектива

Что осознанно отложено. Ничего из этого не мешает раздавать программу сегодня.

### Подпись бинарников

Ни `.exe`, ни `.app` не подписаны сертификатом. Обход описан в теле каждого релиза и нарисован
в окне установочного образа, но объяснять его каждому — плохо. Настоящее решение на каждой
системе свое и стоит денег.

| Система                    | Что блокирует                            | Решение                                                                                                                                                                                                   | Цена                                                             |
| --------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **macOS**                   | Gatekeeper: нет нотаризации            | Apple Developer Program → сертификат Developer ID Application → подпись и нотаризация через`notarytool` + `stapler`                                                      | **99 $/год**                                                |
| **Windows**                 | SmartScreen: у файла нет репутации | Сертификат подписи кода. OV дешевле, но репутация набирается неделями скачиваний; EV дает доверие сразу                       | **~200–400 $/год** (OV), **~300–600 $/год** (EV) |
| **Windows, дешевле** | то же                                            | Azure Trusted Signing — подписка вместо покупки сертификата, но нужна верификация организации или ИП с историей от трех лет | **~10 $/мес**                                               |
| **Linux**                   | ничего не блокирует                 | —                                                                                                                                                                                                               | бесплатно                                                   |

Начинать стоит с macOS: там кнопка по умолчанию называется «Переместить в Корзину», и человек
ее нажмет. SmartScreen пугает мягче и проходится двумя кликами без захода в настройки.

Когда сертификат появится, работы примерно на полчаса: секреты в **Settings → Secrets and
variables → Actions**, два шага в `release.yml` после сборки — подпись настоящим сертификатом
вместо ad-hoc и нотаризация. Остальное менять не придется.

### Автообновление через GitHub

Сейчас обновлятор ходит в сетевую или файловую папку (`updatePath`, см.
[auto-update.md](auto-update.md)), а не на GitHub. Релизы это не сломали и не заменили: чтобы
обновить пользователей, архив из релиза распаковывают в ту самую папку.

Переучить обновлятор на GitHub Releases можно потом, отдельным шагом: у API есть эндпоинт
`releases/latest`, версия и ссылка на файл берутся из ответа. Это заметная правка боевого кода
(сеть, таймауты, поведение без интернета) и к релизному модулю отношения не имеет.

### Прочее

- **Полная проверка кода на всех ОС** — сделана, но отдельным независимым модулем: свой workflow,
  свой гайд, свои тесты, ни одного общего файла с этим. Запускается не на каждый push, а
  по команде, и с выпуском не пересекается — ее триггер не ловит ни main, ни теги.
- **Шаблоны issue** — форма «версия / ОС / что делали» появится, когда появятся пользователи.
- **PostgreSQL в гейте** — тесты провайдера уходят в Skipped. Поднять `services: postgres`
  можно, но это минута на прогон ради кода, который в релизной сборке не меняется.

## Как удалить модуль

```bash
rm -rf Scripts/github-release            # скрипты + release-history.md
rm .github/workflows/release.yml docs/developer/guides/release.md
rmdir -p .github/workflows 2>/dev/null   # если других workflow не осталось
git status --porcelain                   # только строки «D» — ни одного «M»
```

Удаляется именно `workflows/release.yml`, а не папка `.github` целиком: рядом может лежать
чужой workflow, и `rm -rf .github` унес бы его вместе с релизным модулем.

Проект возвращается в состояние байт в байт: модуль не менял ни одного существующего файла и
ничто вне него на модуль не ссылается (проверка 8 в `release-test.sh` следит именно за этим).
Из-за этого гайд намеренно **не** значится в оглавлениях [docs/README.md](../../README.md) и
корневого README — он находится по листингу папки `guides/`.

Единственное, что модуль правит **при запуске** (не при установке) — номер версии в
`SmartBase.csproj` и бейдж в `README.md`. Это существующие строки, новых не появляется, и
скрипты сборки уже делают ровно то же самое тем же `sed`.

Проверить удаляемость, ничего не удаляя:

```bash
git stash -u && dotnet build && dotnet test Tests/Unit && git stash pop
```

## Взаимодействия

- **Сборка** — workflow вызывает те же `Scripts/{windows,linux,macos}-build.sh`, что и локальная
  сборка ([build-and-run.md](build-and-run.md)); версию третьим аргументом им **не передает**,
  иначе они переписали бы csproj и README прямо на runner'е и сверка тега с кодом потеряла бы смысл.
- **Автообновление** ([auto-update.md](auto-update.md)) — релизный архив служит источником файлов
  для сетевой папки; распаковывать так, чтобы `SmartBase-Setup*` был в ее корне.
- **Тесты** ([automated-tests.md](../testing/automated-tests.md)) — `Tests/Unit` и
  `Tests/Integration` работают гейтом перед сборкой. В сами наборы модуль ничего не добавляет:
  его собственные тесты живут в `release-test.sh`.

## Известные ограничения

- **Версия в Linux-сборке точно не проверяется.** У single-file ELF нет штатных метаданных
  версии, а прочитать ее из приложения можно было бы только флагом `--version` — его намеренно
  не добавляли, чтобы модуль не правил боевой код. Остается проверка структуры и мягкий поиск
  строки. Дыра узкая: Windows и macOS сверяют версию точно, а все четыре платформы собираются
  из одного коммита с уже проверенным `<Version>`.
- **Intel-сборка не запускается при проверке**: `macos-latest` работает на arm64, Rosetta на
  runner'ах не установлена. Версия `osx-x64` читается только из `Info.plist`.
- **Оформление окна образа может не примениться на раннере.** `osascript` разговаривает с
  Finder, а тому нужен графический сеанс. Шаг не валит сборку: в лог уходит
  `::warning::Finder не оформил окно`, образ выходит рабочим, но с пустым окном вместо
  инструкции. Запасной путь на этот случай — заранее подготовленный `.DS_Store` вместо
  разговора с Finder.
- **Архивы исходников убрать нельзя.** GitHub всегда прикладывает к релизу `Source code (zip)`
  и `Source code (tar.gz)`. Это его поведение, отключить его нечем.
