# Выпуск релиза на GitHub

Как выпустить готовые сборки для всех операционных систем одной командой, ничего не собирая на
своей машине. Собирает GitHub: вы отправляете тег, через ~12 минут на странице релизов лежат
четыре архива с программой.

Устроено отдельным **отделяемым модулем**: восемь новых файлов, ни один существующий файл
проекта не изменён. Удаляется четырьмя `rm` — см. [«Как удалить модуль»](#как-удалить-модуль).

## Назначение

Раздача программы посторонним. До этого модуля получить SmartBase можно было только одним
способом: склонировать репозиторий, поставить .NET SDK 10 и собрать самому.

**Чем это НЕ является.** Автообновление внутри программы по-прежнему берёт файлы из сетевой или
файловой папки (ключ `updatePath`, см. [auto-update.md](auto-update.md)) и на GitHub не смотрит.
GitHub Releases — **дополнительный** канал раздачи, а не замена. Чтобы обновить пользователей,
архив из релиза распаковывают в ту самую сетевую папку.

Модуль также не собирает ничего на каждый `git push`: ни CI на ветки, ни проверок pull request
здесь нет намеренно. Не каждый push — релиз.

## Где в коде

| Файл | Роль |
|---|---|
| [Scripts/github-release/release.sh](../../../Scripts/github-release/release.sh) | команда выпуска: версия → коммит → тег → push |
| [Scripts/github-release/check-version.sh](../../../Scripts/github-release/check-version.sh) | сверка csproj ↔ README ↔ CHANGELOG, общая для скрипта, CI и тестов |
| [Scripts/github-release/release-notes.sh](../../../Scripts/github-release/release-notes.sh) | сборка тела релиза |
| [Scripts/github-release/release-test.sh](../../../Scripts/github-release/release-test.sh) | тесты модуля |
| [Scripts/github-release/dmg-background.swift](../../../Scripts/github-release/dmg-background.swift) | фон окна установочного образа macOS |
| [.github/workflows/release.yml](../../../.github/workflows/release.yml) | облачная часть: гейт → сборка ×4 → публикация |
| [CHANGELOG.md](../../../CHANGELOG.md) | описания версий, из которых собирается тело релиза |
| этот файл | документация модуля целиком |

Существующие скрипты сборки ([build-and-run.md](build-and-run.md)) модуль **вызывает, но не
меняет** — workflow запускает те же `Scripts/{windows,linux,macos}-build.sh`, которыми вы
собираете локально.

> ⚠ Папка называется `github-release`, а не `release`, не для красоты. В
> [.gitignore](../../../.gitignore) есть стандартное для .NET правило `[Rr]elease/`, и папка
> `Scripts/release/` целиком выпала бы из git — молча, без единого предупреждения. Переименовать
> её обратно нельзя; проверка 8 в `release-test.sh` за этим следит.

## Как работает

### Одна команда

```bash
# 1. Переименовать «## [Не выпущено]» в CHANGELOG.md в «## [1.0.4]» и описать изменения
# 2. Выпустить:
Scripts/github-release/release.sh 1.0.4
```

Скрипт проверит предусловия, покажет план, спросит подтверждение — и дальше сам:

| Что делает | Где |
|---|---|
| `<Version>` → 1.0.4 | `SmartBase.csproj` |
| бейдж → `version-1.0.4-blue` | `README.md` |
| дата в заголовке секции | `CHANGELOG.md` |
| коммит `release: v1.0.4` | git |
| аннотированный тег `v1.0.4` | git |
| `push origin main`, затем `push origin v1.0.4` | git |

Порядок push важен: если ветку отклонили (кто-то опередил), тег в удалёнку не уедет и версию
можно перевыпустить, ничего не разбирая на сервере.

Полезные ключи:

```bash
Scripts/github-release/release.sh 1.0.4 --dry-run      # только проверки, ни один файл не изменён
Scripts/github-release/release.sh 1.0.4 --skip-tests   # без прогона Tests/Unit
Scripts/github-release/release.sh 1.0.4 --allow-dirty  # разрешить незакоммиченные правки
```

`gh` CLI локально не нужен — всё на голом git.

### Что проверяется до выпуска

Любая непройденная проверка останавливает скрипт **до** первой записи в файлы:

1. Версия строго в формате `X.Y.Z`. Суффиксы вроде `1.0.4-rc.1` запрещены: у shields.io дефис —
   разделитель полей, и бейдж `version-1.0.4-rc.1-blue` распался бы на message `1.0.4` и цвет
   `rc.1`. Бейдж сломался бы молча, а сверка версий прошла бы ложно.
2. Ветка `main`, рабочее дерево чистое.
3. Локальная `main` совпадает с `origin/main`.
4. Тег не занят ни локально, ни на GitHub.
5. Новая версия строго больше текущей (защита от опечатки `1.0.4` → `1.0.3`).
6. Текущее состояние согласовано и в `CHANGELOG.md` есть **непустая** секция новой версии.
7. `dotnet test Tests/Unit` проходит.

### Что происходит на GitHub

Push тега `v1.0.4` ловит `release.yml`. Три стадии:

| Стадия | Где | ~Время | Что делает |
|---|---|---|---|
| `gate` | ubuntu | 4 мин | сверяет тег с `<Version>` в коде, проверяет что тег стоит на коммите из `main`, гоняет `Tests/Unit` и `Tests/Integration` |
| `build` | windows + ubuntu + macOS ×2 | 8 мин | четыре платформы параллельно: сборка, проверка артефакта, упаковка |
| `publish` | ubuntu | 1 мин | контрольные суммы, тело релиза, создание релиза |

`gate` стоит первым потому, что собрать четыре платформы и опубликовать релиз с заведомо
сломанным кодом — самая дорогая из возможных ошибок.

Сверка «тег == код» есть только здесь: локальный `release.sh` её сделать не может, он тег и
создаёт. При расхождении — отказ, без попыток что-либо починить: иначе опубликованный релиз
перестал бы соответствовать коммиту, на который указывает тег.

> ⚠ Тесты PostgreSQL (`Tests/Integration/PgProviderTests.cs`) в CI уходят в Skipped — стенда на
> `localhost:5455` там нет. Это штатно: релизная сборка провайдер не меняет.

Право на запись в репозиторий включено ровно в одном job — `publish`. Публикация идёт
предустановленным на runner'е `gh`, стороннего кода с доступом к репозиторию в цепочке нет.

### Нумерация версий

SemVer в трактовке настольного приложения без публичного API:

| Компонента | Когда увеличивается |
|---|---|
| **MAJOR** | несовместимая миграция базы или смена формата данных — откатиться назад нельзя |
| **MINOR** | новый раздел, тип поля, расширение, заметная возможность |
| **PATCH** | исправления, производительность, рефакторинг |

Коммиты `docs:` и `chore:` сами по себе релиз не оправдывают.

Дата в тег не кладётся: аннотированный тег хранит её внутри (`git show v1.0.4`), GitHub рисует
её рядом с релизом, и она стоит в заголовке секции CHANGELOG. Тег `v1.0.4`, заголовок релиза
`SmartBase 1.0.4`, коммит `release: v1.0.4`.

### CHANGELOG

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) с русскими заголовками.
По ходу работы правки пишутся в секцию `## [Не выпущено]`. Перед выпуском её переименовывают в
номер версии — дату проставит `release.sh`, ссылки-сноски внизу файла он же и перепишет.

```markdown
## [Не выпущено]

## [1.0.4] — 2026-08-08

### Добавлено
- Расширение «Документы в коллекцию».

### Исправлено
- Автообновление не роняет приложение при тихом старте из автозапуска.
```

Разделы — только непустые: **Добавлено**, **Изменено**, **Исправлено**, **Удалено**,
**Безопасность**. Пустая секция считается ошибкой: релиз без описания никому не нужен, и выпуск
на этом останавливается.

Тело релиза = секция CHANGELOG + таблица установки + предупреждение о подписи + как обновить
сетевую папку + контрольные суммы + полный список коммитов под спойлером. Посмотреть заранее:

```bash
Scripts/github-release/release-notes.sh 1.0.4
```

### Артефакты

Раздаётся **ровно один файл на платформу** — установщик. Обычный `SmartBase` из `dist/`
не публикуется: это тот же бинарь, и установщик ставит его сам.

| Вложение релиза | Что внутри |
|---|---|
| `SmartBase-Setup.exe` | сам установщик, без архива |
| `SmartBase-1.0.4-osx-arm64.dmg` | `SmartBase-Setup.app` + окно с инструкцией |
| `SmartBase-1.0.4-osx-x64.dmg` | то же |
| `SmartBase-1.0.4-linux-x64.tar.gz` | `SmartBase-Setup` |
| `SHA256SUMS.txt`, `LICENSE`, `THIRD-PARTY-NOTICES.txt` | отдельными файлами |

**Папка при распаковке не создаётся ни на одной системе.** Windows скачивает готовый `.exe` —
распаковывать нечего. macOS монтирует образ. Linux после `tar -xzf` кладёт `SmartBase-Setup`
в текущий каталог.

- **macOS** — `.dmg`, а не архив, и дело не в формате: **окно образа — единственное место, где
  можно показать инструкцию до того, как Gatekeeper заблокирует запуск.** Само приложение
  этого сделать не может, его к тому моменту ещё не запустили. См. следующий раздел.
- **Linux** — скачанный напрямую бинарь приходит без бита запуска, и `./SmartBase-Setup`
  отвечает `Permission denied`. `tar` бит сохраняет, а распаковка всё равно даёт один файл
  без папки.

Три правила, каждое выстрадано:

1. **Имя `SmartBase-Setup` менять нельзя.** Режим установки включается по окончанию имени
   (`Program.cs`, `ResolveMode`, строка 141) — на Windows и Linux по имени файла, на macOS по
   имени бандла. Поэтому версия и платформа уходят в имя **архива**, а файл внутри остаётся
   как есть. По той же причине Windows-установщик кладётся без архива: имя доезжает до
   пользователя нетронутым, и его можно сразу положить в сетевую папку обновлений.
2. **В архиве ровно один элемент.** Тогда распаковка не создаёт папку-обёртку. Пока в архиве
   лежало четыре файла, macOS создавал каталог **`SmartBase-1`** — Archive Utility обрезает
   имя архива по первой точке, и `SmartBase-1.0.3-osx-arm64.zip` превращался в `SmartBase-1`.
   Проверяется машинно: после упаковки архив распаковывается обратно и элементы считаются.
3. **Упаковка у каждой ОС своя.** `ditto` на macOS — обычный `zip` теряет расширенные атрибуты
   внутри бандла, после чего `.app` не стартует. `tar.gz` на Linux — zip теряет бит запуска, и
   после «Извлечь» в GNOME бинарь оказывается незапускаемым. Windows — без упаковки вовсе.

`LICENSE` и `THIRD-PARTY-NOTICES.txt` идут отдельными вложениями, а не внутри архивов:
требование MIT/BSD/Apache — чтобы уведомления сопровождали распространяемую копию, и файл
на странице релиза его выполняет, не засоряя скачанную папку.

> ⚠ Установщик нельзя переименовывать. `SmartBase-Setup (1).exe`, который создаёт браузер при
> повторном скачивании, уже не оканчивается на `-Setup` и запустится обычной программой, а не
> установщиком — молча, без ошибки. Предупреждение об этом входит в тело каждого релиза.

### Первый запуск и предупреждения системы

Скачанный файл получает метку «пришло из интернета», и система требует подтверждения. Обойти
это без платных сертификатов нельзя — можно только не бросать человека одного перед окном,
где кнопка по умолчанию называется «Переместить в Корзину».

**macOS.** Инструкция нарисована фоном окна образа: человек читает четыре шага **раньше**,
чем увидит предупреждение. Фон рисует
[dmg-background.swift](../../../Scripts/github-release/dmg-background.swift) — кодом, а не
картинкой в репозитории: текст правится как обычный исходник, в диффах видно, что поменялось,
бинарных блобов не заводится. Из инструментов нужен только `swift`, он есть и на раннере.
Формулировки и названия кнопок — дословно из интерфейса macOS 26, включая «Все равно открыть».

Само окно раскладывает Finder через `osascript`: размер, вид значками, подпись под значком,
фон и позиция значка. **Это единственное место во всём модуле, которое может не сработать на
раннере** — Finder требует графического сеанса. Поэтому шаг не валит сборку: без оформления
образ остаётся рабочим, просто без инструкции, и в лог уходит `::warning::`.

Предупреждение появляется **один раз**, только для установщика. Раньше их было два: macOS
переносит метку карантина на всё, что записывает карантинный процесс, и установленная
`~/Applications/SmartBase.app` тоже оказывалась заблокированной. Это починено в
`Setup/InstallService.cs` (`ClearQuarantine`) — правка вне модуля, отдельным коммитом.

**Windows.** Аналога окна образа нет: SmartScreen показывает своё окно, и сказать что-либо
заранее негде. Пошаговое описание («Подробнее» → «Выполнить в любом случае») входит в тело
релиза.

**Linux.** Ничего не блокирует, инструкция не нужна.

> ⚠ Бинарники не подписаны сертификатом. `.app` подписываются ad-hoc — это не снимает карантин,
> но отличает «неизвестный разработчик» (обходится) от «приложение повреждено» (не обходится
> вовсе). Инструкция по обходу SmartScreen и Gatekeeper входит в тело каждого релиза.

### Повторный выпуск и что запрещено

| Ситуация | Что произойдёт |
|---|---|
| `release.sh` с занятым тегом | отказ, ничего не меняется |
| повторный push того же тега | git откажет сам |
| **сдвиг тега** `git push --force origin v1.0.4` | должно быть запрещено на сервере, см. ниже |
| workflow упал на середине | «Re-run failed jobs» на вкладке Actions |
| пересобрать бинарники, не двигая тег | Actions → Release → Run workflow, поле `tag` = `v1.0.4` |
| релиз уже существует | файлы и заметки перезаписываются, тег и коммит не трогаются |
| отменить релиз | удалить в UI, затем `git push --delete origin v1.0.4 && git tag -d v1.0.4` — только если версией ещё никто не пользуется |

Ручной запуск по умолчанию создаёт **черновик** (галочка `draft`), push тега публикует сразу.

Опубликованный релиз GitHub привязывает к тегу навсегда: `gh release edit` не может изменить
коммит. Это и есть гарантия «сборка перевыпускается, тег не двигается». Чтобы её нельзя было
обойти, включите защиту тегов: **Settings → Rules → New ruleset**, Target: Tags, шаблон `v*`,
галочки **Restrict updates** и **Restrict deletions**. Делать это стоит **после** первых
экспериментов, иначе тестовые теги не удалятся.

### Тесты модуля

```bash
Scripts/github-release/release-test.sh
```

Восемь проверок, чистый bash: ни .NET, ни сети, ни `gh` не требуется. Прогон ничего не меняет —
это проверяется отдельным пунктом, как и то, что на модуль ниоткуда не ссылаются.

| # | Что проверяет |
|---|---|
| 1 | синтаксис всех скриптов модуля |
| 2 | `check-version.sh` согласен с текущим состоянием и находит три расхождения на выдуманной версии |
| 3 | `release.sh` отвергает `1.0`, `1.0.4-rc.1`, `1.0.4.5` и версию не больше текущей |
| 4 | `release.sh --dry-run` доходит до конца или честно останавливается на незаполненном CHANGELOG |
| 5 | тело релиза собирается целиком, без незаполненных заготовок |
| 6 | в CHANGELOG есть непустая секция текущей версии |
| 7 | триггеры workflow — только теги и ручной запуск (либо полный `actionlint`, если установлен) |
| 8 | модуль отделяем: файлы на месте, ссылок извне нет, дерево не тронуто |

`actionlint` ставится по желанию: `brew install actionlint`. Без него проверка 7 сводится к
контролю триггеров и помечается как пропущенная.

### Обкатка без настоящего релиза

Тегируйте **текущую** версию — ту, что уже в csproj, README и CHANGELOG:

```bash
git tag -a v1.0.3 -m "SmartBase 1.0.3"
git push origin v1.0.3
```

Гейт пройдёт, соберутся четыре платформы, релиз создастся. Что смотреть:

- `gate` падает, если подменить версию в csproj, — значит гейт живой;
- четыре архива на месте, размеры сопоставимы;
- macOS: распакованный `SmartBase-Setup.app` запускается, не «повреждён»;
- Linux: `./SmartBase-Setup` исполняем;
- Windows: `SmartBase-Setup.exe` показывает версию в свойствах файла;
- тело релиза отрендерилось — таблица и спойлер на месте;
- `sha256sum -c SHA256SUMS.txt` проходит;
- повторный ручной запуск на том же теге не создаёт дубль, а перезаписывает файлы.

Уборка: удалить релиз в UI, затем `git push --delete origin v1.0.3 && git tag -d v1.0.3`.

### Если workflow упал

| Где упало | Обычная причина |
|---|---|
| `gate`, «Согласованность версий» | тег и `<Version>` разошлись — удалите тег и перевыпустите |
| `gate`, тесты | код сломан, релиз правильно остановлен |
| `build`, одна платформа | смотреть лог именно этой ячейки матрицы: остальные не отменяются |
| `build`, «файл не найден» на Windows | почти всегда пути с пробелом (`dist/Version 1.0.4/win-x64`) — где-то потеряны кавычки |
| `build`, проверка провалилась при заведомо верном артефакте | конструкция `команда \| grep -q …` в шаге. Шаги идут в шелле с `-o pipefail`: `grep -q` закрывает канал на первом совпадении, источник получает SIGPIPE и падает, и шаг объявляется неуспешным **именно потому, что совпадение нашлось**. В конвейере grep обязан дочитывать поток — без `-q`, с перенаправлением в `/dev/null`, либо через `awk`. Проверка 7 в `release-test.sh` за этим следит |
| `publish` | обычно нехватка прав; `contents: write` есть только у этого job |

После починки: «Re-run failed jobs» — тег и коммит не трогаются.

## Как удалить модуль

```bash
rm -rf .github Scripts/github-release
rm docs/developer/guides/release.md CHANGELOG.md
git status --porcelain     # только строки «D» — ни одного «M»
```

Проект возвращается в состояние байт в байт: модуль не менял ни одного существующего файла и
ничто вне него на модуль не ссылается (проверка 8 в `release-test.sh` следит именно за этим).
Из-за этого гайд намеренно **не** значится в оглавлениях [docs/README.md](../../README.md) и
корневого README — он находится по листингу папки `guides/`.

Единственное, что модуль правит **при запуске** (не при установке) — номер версии в
`SmartBase.csproj` и бейдж в `README.md`. Это существующие строки, новых не появляется, и
скрипты сборки уже делают ровно то же самое тем же `sed`.

Проверить удаляемость, ничего не удаляя:

```bash
git stash -u && dotnet build && dotnet test Tests/Unit && git stash pop
```

## Взаимодействия

- **Сборка** — workflow вызывает те же `Scripts/{windows,linux,macos}-build.sh`, что и локальная
  сборка ([build-and-run.md](build-and-run.md)); версию третьим аргументом им **не передаёт**,
  иначе они переписали бы csproj и README прямо на runner'е и сверка тега с кодом потеряла бы смысл.
- **Автообновление** ([auto-update.md](auto-update.md)) — релизный архив служит источником файлов
  для сетевой папки; распаковывать так, чтобы `SmartBase-Setup*` был в её корне.
- **Тесты** ([automated-tests.md](../testing/automated-tests.md)) — `Tests/Unit` и
  `Tests/Integration` работают гейтом перед сборкой. В сами наборы модуль ничего не добавляет:
  его собственные тесты живут в `release-test.sh`.

## Известные ограничения

- **Версия в Linux-сборке точно не проверяется.** У single-file ELF нет штатных метаданных
  версии, а прочитать её из приложения можно было бы только флагом `--version` — его намеренно
  не добавляли, чтобы модуль не правил боевой код. Остаётся проверка структуры и мягкий поиск
  строки. Дыра узкая: Windows и macOS сверяют версию точно, а все четыре платформы собираются
  из одного коммита с уже проверенным `<Version>`.
- **`LICENSE` попадает в Windows-архив с CRLF**, а в остальные — с LF: файл без расширения
  подпадает под `* text=auto` в `.gitattributes`. На содержимое не влияет, но хеши LICENSE в
  разных архивах различаются. Чинится строкой `LICENSE text eol=lf`, но это правка
  существующего файла — вне границ модуля.
- **Intel-сборка не запускается при проверке**: `macos-latest` работает на arm64, Rosetta на
  runner'ах не установлена. Версия `osx-x64` читается только из `Info.plist`.
