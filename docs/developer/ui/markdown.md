# Markdown: единый вид

## Назначение

Markdown в приложении показывается в трех местах, и выглядеть он обязан одинаково:

| Где | Контрол |
|---|---|
| Настройки → «Инструкция пользователя» | [SettingsGuide.cs](../../../Views/Settings/SettingsGuide.cs) (`RenderMarkdown`) |
| Расширения — описание расширения | [ExtensionsView.axaml](../../../Views/Extensions/ExtensionsView.axaml) (`DescriptionMd`) |
| Панель записи — просмотр описания | [RecordPageView.axaml](../../../Views/ConstructorDb/RecordPageView.axaml) (`MarkdownPreview`) |

Вид описан **в одном файле** — [Assets/Styles/Markdown.axaml](../../../Assets/Styles/Markdown.axaml).
Правка в нем меняет все три места разом; своего оформления markdown нигде больше нет.

## Правило

**Markdown ставится только виджетом [AppMarkdown](../../../Controls/Widgets/AppMarkdown.cs).**
Голый `MarkdownScrollViewer` в разметке — ошибка: он придет со встроенной темой пакета и
будет выглядеть иначе, чем остальное приложение. Так и разошлись описания расширений и
превью записи с инструкцией — стиль был подключен только в инструкции.

Новое место с markdown:

```xml
xmlns:w="using:SmartBase.Controls.Widgets"
...
<w:AppMarkdown x:Name="Text" Markdown="" />
```

Больше ничего не нужно — вид уже правильный.

## Как это работает

`AppMarkdown` делает две вещи, которые иначе повторялись бы в каждом месте:

1. **Гасит встроенную тему пакета** — `MarkdownStyle = new Styles()` (пустой набор ВМЕСТО
   `MarkdownStyleGithubLike` и прочих). Тема живет ВНУТРИ контрола и потому сильнее любых
   наших стилей: пока она на месте, заголовки идут ее размером, а таблицы рисуются черными
   рамками с «зеброй». Через `Application.Styles` ее не перебить, только заменить.
2. **Вешает на себя `Markdown.axaml`** — стили родителя действуют на все поддерево, а
   поддерево markdown рендер строит сам, иначе до его элементов не добраться.

Отсюда и устройство файла стилей: раз тема заменена целиком, в нем описан **весь** вид —
заголовки, абзацы, цитаты, код, таблицы, списки. Не описанное там остается на общих стилях
приложения.

### Селекторы

Рендер вешает на элементы классы: `Heading1`…`Heading6`, `Paragraph`, `Blockquote`,
`CodeBlock`, `Table`, `TableHeader`, `TableRowOdd`/`TableRowEven`, `List`, `ListMarker`,
`Note`. По ним и стилизуем.

Текст — `CTextBlock` из ColorTextBlock.Avalonia, а НЕ Avalonia-шный `TextBlock`, поэтому
селекторы пишутся по `ctxt|CTextBlock`.

Селектор пишется в ОДНУ строку: перенос внутри `Selector` ломает разбор, и стиль молча не
применяется (так пропали линии таблицы в первом заходе).

Размеры шрифта — только `{DynamicResource FontSizeXxx}` (живой «Размер шрифта», см.
[[theming]]), цвета и линии — токены `Colors.axaml` и `Controls.axaml`. Иерархия заголовков
потребовала промежуточного размера между `FontSizeBase` (12) и `FontSizeLarge` (20) — токен
**`FontSizeMedium`** (16), перечислен поименно в [FontScale](../../../Utils/FontScale.cs):
без этого «Размер шрифта» его бы не двигал.

### Когда стиль вешается на хост, а не на контрол

`AppMarkdown(inheritStyles: true)` — вид берется с предка, свой набор виджет не заводит.
Так сделана «Инструкция пользователя»: документ режется на секции, контролов на экране
десятки, и набор стилей висит один раз на общем хосте (`AppMarkdown.ApplyStyles(GuideHost)`).
Файл стилей тот же, расхождению взяться неоткуда.

Отдельный экземпляр `Styles` на каждый вызов — не случайность: один набор может
принадлежать ровно одному владельцу («The Styles already has a owner»), раздать его
нескольким контролам нельзя.

## Прокрутка: обычный `ScrollViewer`, а не своя

Собственную прокрутку контрола НЕ используем — markdown кладется в обычный `ScrollViewer`
приложения:

```xml
<ScrollViewer VerticalScrollBarVisibility="Auto" HorizontalScrollBarVisibility="Disabled">
    <w:AppMarkdown x:Name="Text" Markdown="" Margin="16,16,16,32" />
</ScrollViewer>
```

Причина — стандарт прокрутки ([[scrolling]]): полоса идет во всю высоту блока и прилегает к
краю, а воздух вокруг содержимого висит ВНУТРИ области прокрутки. С собственной прокруткой оба пункта
нарушались: отступ приходилось вешать на сам контрол (`Padding` у типа нет вовсе), из-за
чего полоса начиналась ниже линии шапки и не доходила до низа, а текст при прокрутке
обрывался на 16px ниже линии — белый зазор оставался всегда, вместо того чтобы уходить
вместе с текстом.

Своя прокрутка контролу при этом не мешает: внутри `ScrollViewer` высота не ограничена,
поэтому он разворачивается на весь текст, а прокручивает внешний. Отступы (`16,16,16,32` —
как в панелях настроек) видны только в крайних положениях, в середине текст идет от линии.

Если содержимое меняется на лету (выбор другого расширения), прокрутку надо сбрасывать
руками: `Offset = new Vector(0, 0)` — внешний `ScrollViewer` о смене текста не знает.

Так сделаны все три места. В инструкции пользователя внешний `ScrollViewer` был всегда — он
нужен и для навигации по оглавлению. На панели записи прокрутка общая с редактором: полоса
там вынесена отдельной колонкой (`ScrollBarLink`) и обслуживает то превью, то редактор — см.
[[../features/constructor/record-page]].

## Что виджет НЕ делает

- **Не трогает выделение текста.** `SelectionEnabled` ставится по месту: в инструкции текст
  выделяется и копируется, в остальных местах — как было.
- **Не дает отступа содержимому.** У `MarkdownScrollViewer` нет `Padding` и вообще свойства
  для отступа содержимого — воздух задается `Margin` самого контрола внутри `ScrollViewer`
  (см. раздел выше).
- **Не отвечает за разбор текста.** Нумерация заголовков, деление на секции и вики-ссылки
  `[[имя]]` — это логика справочника, она живет в `SettingsGuide` и только там
  (см. [[../features/user-guide-section]]).

## Ввод markdown

Текст описания **вводится** в обычный `TextBox` — оформления markdown при вводе нет нигде:

- панель записи — `MarkdownEditor`, класс `notesEditor` (безбордерный, «как письмо в
  заметках»), переключатель «редактор ↔ просмотр» в футере (см. [[../features/constructor/record-page]]);
- диалоги записи и задачи — `DescBox`, класс `multiline`, только ввод, без просмотра
  (см. [[dialogs]]).
