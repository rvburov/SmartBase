# Бенчмарки (Tests/Benchmarks)

Замеры производительности — **не автотесты**: работают на больших объемах (гигабайты,
минуты), запускаются точечно и вручную. Один консольный проект с диспетчером команд;
общие мелочи (парсинг аргументов, форматирование) — в `BenchUtil`.

Запуск из корня репозитория:

```bash
dotnet run -c Release --project Tests/Benchmarks -- sidebar [--db PATH] [--target PATH] [--light]
dotnet run -c Release --project Tests/Benchmarks -- import  [--rows N] [--dir PATH]
dotnet run -c Release --project Tests/Benchmarks -- export  [--rows N] [--dir PATH]
dotnet run -c Release --project Tests/Benchmarks -- pgload  [клиентов] [секунд] [--db ИМЯ]
dotnet run -c Release --project Tests/Benchmarks -- pgperf  [--rows N] [--db ИМЯ]
dotnet run -c Release --project Tests/Benchmarks -- csvlog  [--rows N] [--dir PATH]
dotnet run -c Release --project Tests/Benchmarks -- dbsize  --db PATH [--top N] [--fast]
dotnet run -c Release --project Tests/Benchmarks -- bloat   [--count N] [--dir PATH] [--keep]
dotnet run -c Release --project Tests/Benchmarks -- delete  --db PATH [--batch N] [--col ИМЯ]
dotnet run -c Release --project Tests/Benchmarks -- pgdelete [--rows N] [--db ИМЯ]
dotnet run -c Release --project Tests/Benchmarks -- wide    --db PATH [--columns N]
```

Цена широкой таблицы в НАСТОЯЩЕМ UI-дереве (а не в ядре) меряется отдельным стендом —
`Tests/WideGui` на headless-платформе Avalonia, как `Tests/MarkupLayout`:

```bash
dotnet run -c Release --project Tests/WideGui -- --db PATH
```

| Команда | Что мерит | Требования |
|---------|-----------|-----------|
| **sidebar** | операции сайдбара на большом стенде (чтения дерева, календарь, дубль/перенос/удаление коллекций и групп) | заранее сгенерированный стенд — см. [test-database.md](test-database.md) |
| **import** | импорт большого CSV (Analyze + чтение/запись, строк/с) | — |
| **export** | экспорт коллекции во все форматы (CSV/JSON/XLSX/XLSM) | — |
| **pgload** | нагрузка PostgreSQL: N клиентов со своими подключениями, сверка целостности | стенд `sb-pg` (порт 5455) — см. [../guides/postgresql-setup.md](../guides/postgresql-setup.md) |
| **pgperf** | производительность PostgreSQL путями приложения (репозиторий, не голый SQL): массовая заливка `BulkAddRecords`, одиночные вставки, keyset-страницы (первая против самой глубокой), offset для контраста, значения пакета, фильтр колонки, точечные правки, дубль/удаление пакета. Сбрасывает схему `public`, в конце подчищает | стенд `sb-pg` (порт 5455) |
| **csvlog** | выгрузка в CSV журнала изменений и диагностики (строк/с, размер файла, живая куча) | — (сеет свои temp-базы) |
| **dbsize** | из чего состоит файл SQLite: живые данные / свободные страницы / накладные B-деревьев, объем каждой таблицы и индекса, разрез по коллекциям (байт на запись) и полям (средняя/максимальная длина, доля длинных > 120 байт, уникальных — потенциал словаря). Открывает файл **только для чтения** — можно запускать на настоящей базе в сетевой папке во время работы людей; `--fast` пропускает `COUNT(DISTINCT)` по полям | любой файл `.db` |
| **bloat** | сценарий раздувания через путь свода трудоемкости (`BulkAddRecords`): свод → второй свод → удаление первого → правки 10 % ячеек и очистка 5 % → 1000 честных `SetFieldValue` (байт журнала на правку) → заливка при открытом читателе (рост `-wal`) → чекпоинт → `VACUUM`; затем тот же прогон с `auto_vacuum=INCREMENTAL`. Таблица «файл / живые / свободно / -wal / время» по шагам | — (свои temp-базы, `--keep` оставляет) |

| **delete** | удаление большой коллекции (`DeleteCollectionIsolated`): время целиком, темп по пакетам, размеры `.db` и `-wal` до/во время/после, память процесса; `--batch` сравнивает размеры пакета | стенд из `Tests/DbGenerator` |
| **pgdelete** | то же удаление на PostgreSQL: время, мертвые кортежи, что дает `VACUUM ANALYZE` | стенд `sb-pg` (порт 5455) |
| **wide** | цена ШИРОКОЙ коллекции в ядре: снимок открытия, страницы записей, значения, список значений колонки — против узкой для сравнения | стенд профиля `wide` из `Tests/DbGenerator` |
| **WideGui** (отдельный проект) | цена широкой таблицы в живом UI: время и аллокации на построение колонок и первую раскладку, куча и рабочий набор после открытия | стенд профиля `wide`, Avalonia.Headless |

### Что показали `delete`, `wide` и `WideGui` (09.2026, MacBook, локальный SSD)

- **Широкая таблица.** 1000 свойств против 16 колонок: первая раскладка **6,4 с против
  1,1 с**, управляемая куча **1108 МБ против 113 МБ**, рабочий набор **1526 МБ против
  213 МБ**, повторное открытие 12,3 с против 1,4 с. Цена привязана к числу СВОЙСТВ и не
  зависит от числа записей — см. [[../architecture/performance/overview]].
- **Удаление коллекции.** SQLite и PostgreSQL удаляют примерно с одной скоростью на
  строку (3,4 против 3,5 мкс), но пик памяти КЛИЕНТА — **1674 МБ против 145 МБ**: у
  файловой базы работа идет в процессе программы, у сервера — на сервере. После удаления
  файл SQLite не уменьшается (901 МБ как был), место возвращает `VACUUM` при следующем
  монтировании (8,3 с на 1,8 ГБ); PostgreSQL чистит мертвые кортежи фоновым autovacuum,
  ручной `VACUUM ANALYZE` — 1,1 с.
- **Синхронный порог.** Удаление 20 тыс. записей (240 тыс. строк значений) на прежнем
  пороге `BulkProgressThreshold` шло **711 мс на UI-потоке** без окна и индикатора —
  из-за этого порог опущен до 2000.

### Что показал `bloat` (50 тыс. строк на свод, локальный SSD)

| Шаг | Файл | Живые | Свободно | -wal |
|---|---|---|---|---|
| свод №1 | 38,8 МБ | 38,8 МБ | 0 | 13 МБ |
| свод №2 | 78,1 МБ | 78,1 МБ | 0 | 13 МБ |
| удален свод №1 | 78,1 МБ | 39,5 МБ | **38,6 МБ (49 %)** | 13 МБ |
| правки 10 % + очистка 5 % | 78,1 МБ | 40,1 МБ | 38,0 МБ | 16 МБ |
| свод №3 при открытом читателе | 78,1 МБ | 80,0 МБ | 0 | **57 МБ** |
| читатель закрыт, чекпоинт | 80,0 МБ | 80,0 МБ | 0 | 0 |
| VACUUM + чекпоинт (пул закрыт) | 73,5 МБ | 73,5 МБ | 0 | 0 |

Один свод с шестью свойствами — **≈ 815 байт на запись** (650 тыс. строк ≈ 0,5 ГБ); честная
правка ячейки — ≈ 420 байт строки журнала; удаление свода оставляет ровно его объем в
freelist (49 % файла — прежний порог «> 50 %» не срабатывал); открытый читатель держит
`-wal` размером со всю заливку до чекпоинта. Прогон с `auto_vacuum=INCREMENTAL` дал те же
времена вставки и тот же размер (±0,1 %), а `incremental_vacuum` + чекпоинт вернул 38,6 МБ за
1,3 с: файл 78,2 → 39,6 МБ.

Строка «пул закрыт» — не мелочь: в первых прогонах файл после VACUUM оставался 80 МБ при
пустом freelist. Windows не усекает файл, пока его держит отображенным в память любое другое
подключение (простаивающее в пуле подключение главного контекста с `mmap_size`), а у сильно
опустевшей базы автоматический чекпоинт после VACUUM и вовсе не запускается (журнал короче
1000 страниц) — усечение откладывалось до чужого чекпоинта, где молча не проходило. Поэтому
`DatabaseManager.Vacuum` закрывает пул и делает `wal_checkpoint(TRUNCATE)` сам; стенд
повторяет это. Подробности — [storage-and-migrations.md](../architecture/database/storage-and-migrations.md#свободное-место-сжатие-wal).

Чтения подтверждают конструкцию: keyset-страница стоит одинаково на любой глубине
(row-value сик O(take)), счетчик и фильтр на десятках тысяч строк — миллисекунды.
Одиночные записи упираются не в сервер, а в **задержку раунд-трипа до стенда в
colima-VM**: каждая операция репозитория — несколько отдельных стейтментов в
автокоммите (запись + значение + журнал изменений + аудит), и при ~1 мс на
раунд-трип получаются десятки операций в секунду на одном подключении. Для UI
этого достаточно (человек правит одну ячейку), а суммарная пропускная способность
сервера видна по `pgload` на том же стенде: ~15 000 оп/с на сотне подключений.
На нативном сервере в локальной сети задержка ниже и одиночные операции быстрее.

### Проверка `auto_vacuum=INCREMENTAL` на сетевой папке

Цифры выше сняты на локальном SSD; для общей базы решение принимается по прогону на
настоящей сетевой папке. Стенд распознает сетевой путь сам и открывает файлы в режиме
общей базы (журнал DELETE, `synchronous=FULL`, без mmap); настоящую базу он не трогает,
людей с нее снимать не нужно.

1. На ПК с доступом к папке: `git pull`, .NET 10 SDK.
2. Запуск в папке на сетевом диске — сначала 50 тыс. строк (сравнимо с таблицей выше;
   через SMB это заметно дольше минуты, миллион по умолчанию сразу не брать):
   `dotnet run -c Release --project Tests/Benchmarks -- bloat --count 50000 --dir "P:\путь\bloat-test" --keep`
3. Смотреть в двух итоговых таблицах:
   - **накладные на вставку** — строка «свод №1»: INCREMENTAL против NONE; порог
     принятия — время дольше не более чем на 10 %, файл больше не более чем на 1 %;
   - **возвращается ли место** — строка «incremental_vacuum порциями по 2000 страниц +
     чекпоинт»: колонка «файл» должна упасть примерно с 78 до 40 МБ; осталась прежней —
     папка не усекает файл, и INCREMENTAL там бесполезен;
   - **цена ручного сжатия** — строка «VACUUM + чекпоинт» первой таблицы: столько на
     этом сервере стоит «Сжать файл» на таком объеме (для 1,7 ГБ — умножить на ~22).
4. Чего прогон не показывает: стенд работает один, «не мешает ли `incremental_vacuum`
   соседям» им не проверяется. Для этого нужен стенд с писателями и читателями на том
   же файле во время очистки — его пока нет (`Tests/MultiProcess --load` создает свой
   файл), добавляется вместе с включением.

Если пороги пройдены — включение: новые файлы с `auto_vacuum=INCREMENTAL` (прагма на
пустом файле до `Migrate()`), существующие — при ближайшем «Сжать файл»
(`PRAGMA auto_vacuum=INCREMENTAL` перед `VACUUM`), после пакетных удалений —
`incremental_vacuum` порциями в той же фоновой операции. Файлы стенда (`bloat_none.db`,
`bloat_incr.db`) после проверки удалить.

Функциональная корректность импорта/экспорта/PG проверяется автотестами (см.
[automated-tests.md](automated-tests.md)); здесь только скорость.

выгрузка идет ОДНИМ запросом с ORDER BY, а не keyset-страницами. Страницами каждая
из них пересортировывала бы всю таблицу заново (индексов на этих колонках нет) —
на 300 тыс. строк это 14,7 с против 1,6 с, дальше квадратично.

Куча после выгрузки — главный показатель: она обязана оставаться единицами мегабайт.
Рост означал бы, что поток строк где-то материализуется целиком (тогда 10 млн строк
положат приложение по памяти). Счет строк для окна подтверждения — 0,5–1 с на 10 млн.
Выгрузка журнала намеренно идет на обычных прагмах, а не bulk: темп тот же, а рабочий
набор втрое меньше (687 МБ против 2,2 ГБ).
