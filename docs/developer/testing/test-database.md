# Тестовая БД-стенд (Tests/DbGenerator)

## Назначение

Стенд для проверки производительности календаря и таблиц на предельных объемах:
виртуализация «Расписания»/«Журнала», offset/keyset-страницы, посекундная карта
гигантского дня, массовые удаление/дублирование, поиск LIKE по всему окну,
мгновенные фильтры видимости (см. [performance.md](../architecture/performance/overview.md)).

> Замеры «до ~10 млн записей» в performance.md сделаны на предыдущем профиле стенда
> (10 млн записей, одно поле-дата). Текущий генератор — C#,
> по умолчанию **20 млн записей** со всеми типами свойств и тремя полями-датами
> (~240 млн строк в БД); `--count` масштабирует профиль вплоть до 100 млн и выше.

## Генератор

[Tests/DbGenerator](../../../Tests/DbGenerator/) — консольный проект C# (в `SmartBase.sln`).
Схему он **не дублирует руками**: файл создает `AppDbContext.Database.Migrate()` основного
проекта — ровно те же миграции EF, что применяет приложение, поэтому генератор не может
разойтись со схемой (новые миграции подхватываются автоматически). Для скорости все
вторичные индексы снимаются на время заливки (DDL читается из `sqlite_master`) и строятся
заново в конце; вставка — raw SQL multi-row prepared-statement'ами, транзакции по 100 тыс.
записей.

Запуск из корня репозитория:

```bash
dotnet run -c Release --project Tests/DbGenerator                      # 20 млн → Tests/test_database.db
dotnet run -c Release --project Tests/DbGenerator -- --count 2000000   # уменьшенный стенд
dotnet run -c Release --project Tests/DbGenerator -- --count 100000000 --out /Volumes/Disk/test_database.db --force
```

`--force` пересоздает существующий файл, `--count N` масштабирует профиль, `--out PATH`
задает путь к файлу (файл подключается из настроек приложения, лежать в `Tests/` ему
не обязательно).

> **Размер.** Дефолтные 20 млн — это файл ~30 ГБ, и в рабочей папке ему не место.
> Большие объемы задавайте через `--out` ВНЕ репозитория (внешний диск `/Volumes/…`
> или `~/TestData/`).

## Профиль данных (по умолчанию 20 000 000 записей)

Одна коллекция **«Задачи»** (#007AFF) со **всеми типами свойств конструктора**:

| Поле | Тип | Значение записи N |
|---|---|---|
| «Дата» | date, видима в календаре, системная | основная дата события (см. ниже) |
| «Напоминание» | date, видима в календаре | основная дата **−1 день** |
| «Дедлайн» | date, видима в календаре | основная дата **+7 дней** |
| «Заметка» | text | `Заметка N` |
| «Количество» | number | `N mod 100000` |
| «Статус» | select («Новая», «В работе», «Готово», «Отложена») | `N mod 4` |
| «Выполнено» | checkbox | четные — `1`, нечетные — `0` |
| «Ссылка» | url | `https://example.com/task/N` |

Все три поля-даты видимы ⇒ каждая запись дает **3 события** календаря и 3 строки
`calendar_index` (на 20 млн записей — 60 млн строк проекции; всего в БД ~240 млн строк).

Основная дата, все события timed (не «весь день»), длительность 1 час:

| Записи (Id) | Название | Распределение |
|---|---|---|
| первая половина | «Событие N» | разброс по годам: старт `2020-01-01T00:00:00` + (N−1)×шаг; шаг подбирается от `--count` так, чтобы покрыть ~11 лет (при 10 млн — 35 с, ≈2470 событий в день) |
| вторая половина | «День N» | **гигантский день** `2026-07-01`: старты по секундам суток по кругу (при 10 млн — ≈116 записей на КАЖДУЮ секунду); «Напоминание»/«Дедлайн» дают еще два гигантских дня — `2026-06-30` и `2026-07-08` |

Форматы значений — ровно как пишет приложение: `db_records.StartDt/EndDt` и
`calendar_index.StartIso/EndIso` — ISO `"o"` (7 знаков дробных секунд), значения
полей-дат в `db_field_values` — `DateValue` «start/end» с точностью до минут.

## Время и размер

Замерено на macOS (Apple Silicon, внутренний NVMe), вставка ~4 млн записей/мин:

| `--count` | Вставка | Индексы | Всего | Размер файла |
|---|---|---|---|---|
| 2 000 000 | 0,5 мин | 0,6 мин | **1,1 мин** | 2,93 ГБ |
| 10 000 000 | 2,5 мин | 5,4 мин | **7,9 мин** | 14,91 ГБ |
| **20 000 000** (дефолт) | ~5 мин (экстраполяция) | ~12–14 мин | **~17–20 мин** | **~30 ГБ** |
| 100 000 000 | ~25 мин (экстраполяция) | ~1,5–2,5 ч | **~2–3 ч** | **~150 ГБ** |

Вставка масштабируется строго линейно (~1,5 ГБ на млн записей), фаза индексов —
быстрее линейной (внешняя сортировка сотен миллионов строк: 2→10 млн дала ×9 времени
при ×5 объема), отсюда вилка для 100 млн. Запас свободного места на время генерации —
~200 ГБ (temp-файлы сортировки SQLite на десятки ГБ живут на том же томе, где temp).
На внешнем диске (USB-SSD/HDD) время заметно вырастет — обе фазы упираются в диск.

## Профиль `wide` — широкая разреженная коллекция

Второй профиль генератора (`--profile wide`) — для проверки раздувания файла и скорости
ядра на пределе по обеим осям: много записей И много колонок.

```bash
dotnet run -c Release --project Tests/DbGenerator -- --profile wide --count 10000000 --columns 2000 --fill 20 --out D:\stand\wide.db
dotnet run -c Release --project Tests/DbGenerator -- --profile wide --count 20000 --columns 100 --out /tmp/wide_small.db   # быстрая проверка
```

Одна коллекция **«Широкая»**: по одному свойству **каждого типа** конструктора — `text`,
`number`, `date` (видима в календаре → строка `calendar_index`), `select`, `status`,
`multiselect` (JSON-массив), `checkbox`, `url`, `file` (абсолютный путь, 3000 разных — как
у свода трудоемкости), `user` (20 имен), `relation` (ребро `db_record_links` на более раннюю
запись этой же коллекции) и четыре вычисляемых (`created_at` / `updated_at` / `created_by` /
`updated_by`, значений не хранят); остальные `--columns − 15` колонок — текст «Текст N».

Заполнение **разреженное**: у записи заполнены все типизированные ячейки (10 значений +
ребро + строка календаря) и `--fill − 11` текстовых колонок, выбранных детерминированно
от номера записи (у соседних записей — разные колонки; каждая текстовая колонка
заполнена у ~fill/columns записей, значения — ~1000 разных на колонку). Полное
заполнение 10 млн × 2000 = 20 млрд значений (> 1 ТБ) на рабочей машине невозможно, а
разреженная матрица — обычный вид «широких» таблиц. Аудит записи — как пишет приложение
(даты ISO «o», снимки имени). Техника та же: индексы снимаются на время заливки, multi-row
prepared INSERT, транзакции по 50 тыс. записей, индексы в конце.

Ожидание при 10 млн / 2000 / 20: ~200 млн значений, файл ~15–20 ГБ, 30–45 мин; на время
построения индексов нужен запас места под temp-файлы сортировки (~размер индексов) —
`--out` на диск с запасом ≥ 60 ГБ. Что получилось по байтам на запись/значение — смотрите
`dbsize` ([benchmarks.md](benchmarks.md)). Таблица приложения с 2000 колонок открывается за
один кадр: рисованная сетка (ROADMAP, мера 9) рисует и читает только видимое окно колонок.

### Как прогнать `wide` на 10 млн и что смотреть

1. Диск с запасом ≥ 60 ГБ: файл ≈ 20 ГБ и примерно столько же временно под сортировку
   индексов в конце — на тесном системном диске генерация падает на последних минутах.
   Только локальный диск: 20 ГБ через SMB пишутся часами, а меряется хранение, не сеть.
2. Быстрая проверка сборки, около минуты:
   `dotnet run -c Release --project Tests/DbGenerator -- --profile wide --count 20000 --columns 100 --out D:\stand\wide_small.db`
3. Полный стенд, 35–45 мин (папку создаст сам; существующий файл — только с `--force`):
   `dotnet run -c Release --project Tests/DbGenerator -- --profile wide --count 10000000 --columns 2000 --fill 20 --out D:\stand\wide.db`
   Прогресс — каждые 50 тыс. записей; в конце «Готово»: записей, значений, размер,
   байт на запись и на значение, время вставки и индексов.
4. Состав файла (только чтение, минуты):
   `dotnet run -c Release --project Tests/Benchmarks -- dbsize --db D:\stand\wide.db --fast`
5. В приложении: «Добавить базу данных» → «Подключить базу данных SQLite» → `wide.db`.

Ориентир — 1 млн × 2000 × 20 на Windows/SSD: файл 2,03 ГБ, **2 179 байт на запись,
115 байт на значение**, вставка 2,2 мин + индексы 1,0 мин; таблица значений и ее индекс —
71 % файла поровну (индекс дублирует каждое значение), записи с аудитом — 8,5 %, длинные
значения (> 120 байт) — 3,2 %.

На что смотреть:
- **байт на запись / на значение** — на 10 млн должны быть примерно те же; рост означал
  бы масштабирование хуже линейного;
- **доли в `dbsize`** — те же ≈ 70 % на значения с индексом и ≈ 8 % на записи;
- **монтирование и календарь** — появление базы в сайдбаре и открытие месяца с
  записями: секунды, не минуты;
- **фильтр по типизированной колонке** — отбор по статусу или пользователю в «Широкой».

Не считать результатом: открытие самой таблицы на 2000 колонок (сетка создает ячейки
всех колонок — известное ограничение, ROADMAP) и поведение общей базы по сети (стенд
одного пользователя на локальном диске; для сети — `bloat`, см.
[benchmarks.md](benchmarks.md#проверка-auto_vacuumincremental-на-сетевой-папке)).

## Замечания

- Файл БД **не коммитится** (`Tests/*.db` в `.gitignore`), генератор и этот документ —
  в репозитории.
- Рабочая копия «живет»: правки/дубли/удаления в тестах меняют содержимое. Генератор
  всегда дает исходное состояние.
- Рядом с файлом при работе приложения появляются `*.db-wal`/`-shm` — тоже игнорируются git.
- Подключение — как любой существующей базы: сайдбар → «Подключить базу данных» (или
  настройки). Более новые миграции приложение применит само при первом подключении.
- Каждая запись видна в календаре трижды (3 видимых поля-даты — задокументированное
  поведение, см. [overview.md](../features/calendar/overview.md)); «Напоминание» и
  «Дедлайн» можно мгновенно скрыть тумблером «Отображать в календаре» — видимость полей
  и галки коллекций теперь фильтры чтения, проекция не пересобирается.
- Первое открытие «Журнала»/мультибазного «Расписания» на гигантском дне строит
  посекундную карту — на 100 млн это дольше, чем на старом 10-млн стенде
  (см. [journal.md](../features/calendar/journal.md), [schedule.md](../features/calendar/schedule.md)).
- Сетка (День/Неделя/Месяц/Год) на окне с гигантским днем получает только первые
  `GridDayCap` (2000) событий дня (Месяц — `MonthDayCap`, 256) + честный «+N еще» по карте
  счетчиков (см. [performance.md](../architecture/performance/overview.md)).
- Сценарный прогон всей программы на этой базе вместе с копиями рабочих — стенд
  `Tests/Sections` (этап 8 плана [drawn-grid.md](../architecture/performance/drawn-grid.md)).
