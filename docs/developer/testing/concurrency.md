# Многопользовательские проверки

> **30.10.2026:** сценарий `access` заменен на `people`: проверяются имена участников,
> авторство и операции без старых ограничений. Исторические таблицы прогонов ниже описывают
> соответствующие даты; они не доказывают новый прогон после удаления прав.


## Назначение

Проверки одновременного создания, изменения, удаления и переноса записей на SQLite и
PostgreSQL. Малые регрессии входят в `Integration`; отдельная команда `multiuser` запускает
до 1000 независимых сессий и сохраняет отчет о нагрузке и состоянии данных.

Состав покрытия уточнен 26.10.2026. Полная карта разделов и границ —
[concurrency-coverage.md](concurrency-coverage.md).

Наличие сценария в этом документе описывает покрытие, а не успешный прогон на конкретной
машине. Размер нагрузки, результаты, отказы и ограничения среды должны сопровождать отчет.
Тестовые фикстуры не заменяют проверку пользовательской сетевой папки и настоящих баз.

## Как работает

### Малые регрессии

```bash
dotnet test Tests/Integration --filter FullyQualifiedName~ConcurrentLifecycleTests
```

27 вариантов сценариев: три профиля для жизненного цикла, переноса и первого заполнения
общей ячейки; еще двенадцать — сохранение устаревшего редактора после удаления, отдельно
текст и дата, с отслеживаемым и отсоединенным значением на каждом профиле. Каждый участник получает свой поток и `AppDbContext`; общий
барьер освобождается после подготовки всех участников. Еще шесть вариантов проверяют
атомарность неуспешной правки: настоящий триггер отклоняет запись аудита после сохранения
значения, а тест требует неизменности значения, журнала и календарной проекции. Это
контролируемая имитация сбоя, а не нагрузка восьми пользователей. Ошибки и BUSY не подавляются.
Проверяется ожидаемый результат, а не только отсутствие исключений: точные записи и
значения, отсутствие восстановленных удаленных данных, аудит переноса, проекция календаря,
дубликаты и осиротевшие строки. SQLite дополнительно проходит `integrity_check` и
`foreign_key_check`, PostgreSQL — сверку сводок календаря.

Тесты PostgreSQL создают собственную базу с уникальным именем и удаляют только ее. Если
локальный стенд недоступен, PostgreSQL-варианты помечаются `Skipped`; это не подтверждение
работы PostgreSQL. Варианты входят в обычный набор `Integration` и полный профиль CI.

Дополнительные наборы `ConcurrentFieldTypes/StaleRecovery/Structure/Planning/Library/Access/Integration/Backup/ConnectionRecovery/PersonalFilesTests`
расширяют проверку на модули, права, собственные файлы и конкретные аварии. Их состав и число
участников перечислены в [матрице покрытия](concurrency-coverage.md#наборы-расширенного-этапа).
Это малые управляемые проверки, а не утверждение о 1000 одновременно работающих GUI.

### Нагрузочный прогон

Последовательную матрицу запускает [Tests/run-concurrency.sh](../../../Tests/run-concurrency.sh):

```bash
./Tests/run-concurrency.sh --out /tmp/sb-concurrency-small
./Tests/run-concurrency.sh --clients 1000 --out /tmp/sb-concurrency-thousand
./Tests/run-concurrency.sh --provider postgres --scenario library --clients 1000 --out /tmp/sb-library-pg
```

По умолчанию — 8 клиентов, все восемь сценариев на SQLite WAL, SQLite DELETE+FULL и PG
`server`. Скрипт собирает стенд один раз, запускает проверки последовательно и сохраняет
`matrix.tsv`, журнал каждой попытки и ее JSON. Падение не останавливает остальные случаи,
но общий код возврата остается ненулевым. Поддерживаются также `--rounds`,
`--timeout-seconds` и `--p95-ms`; `--out` должен указывать на новую папку.

Сначала небольшой прогон, затем тот же сценарий с нужным числом сессий:

```bash
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --clients 32
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile wal --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile shared --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider postgres --clients 1000
```

Команды запускаются последовательно, без другого тестового прогона или сборки в той же
копии. PostgreSQL использует только локальный тестовый сервер проекта `127.0.0.1:5455`:
создает новую базу `sb_multiuser_<guid>`, не сбрасывает `public` существующей базы. Роли
стенда нужны права создать собственную тестовую базу. Для 1000 готовых подключений нужны
соответствующие `max_connections`, память и лимиты ОС; отказ сервера считается отказом
нагрузки, а не успешным обслуживанием оставшихся участников.

У каждого участника отдельный поток, контекст и синтетический пользователь. Фикстура заранее
создает участников; `CurrentUser.ActAs` задает имя и ключ для аудита, `UserDirectory.Reload` обновляет справочник имен. Старые роли и маски прав не применяются.
В сценарии `people` все участники работают с данными, а старые роли, допуски и маски
не ограничивают операции. Это проверка авторства и конкурентной записи, а не входа
с разных учетных записей операционной системы.

Перед стартом все готовые сессии одновременно держат открытые подключения. После общего
барьера EF открывает и возвращает их в пул обычным путем приложения. Готовность 1000 сессий
и успешное завершение 1000 сессий — разные показатели. `PeakActiveSessions` считает сессии
внутри своих циклов; это не количество запросов, одновременно исполняемых сервером.

| Параметр | Значение |
|----------|----------|
| `--provider sqlite\|postgres` | По умолчанию `sqlite` |
| `--profile wal\|shared` | Только SQLite: локальный WAL или эмуляция общей базы DELETE+FULL; по умолчанию WAL. PostgreSQL использует `server` |
| `--clients N` | От 1 до 1000, по умолчанию 1000 |
| `--rounds N` | Полных циклов у каждого участника; по умолчанию 1 |
| `--scenario lifecycle\|hotcell\|rollback\|planning\|library\|integrations\|people\|structure` | По умолчанию `lifecycle` |
| `--timeout-seconds N` | Лимит подготовки потоков/подключений после создания фикстуры и отдельный лимит самого прогона; по умолчанию 180 секунд |
| `--p95-ms N` | Необязательный верхний предел p95 каждой операции, миллисекунды |
| `--out ПАПКА` | Новая папка данных и отчета; существующая отклоняется. Без параметра создается уникальная временная папка |

Сценарии:

| Сценарий | Команды и ожидаемое состояние |
|----------|-----------------------------|
| `lifecycle` | Создать свою запись → заполнить текст и видимую дату → изменить текст → прочитать страницу, значения и дерево коллекций → дублировать → перенести оригинал в общую целевую коллекцию → удалить дубль. После полного цикла остается одна перенесенная запись с нужными значениями и автором |
| `hotcell` | Все участники впервые пишут одну общую ячейку; после прогона ровно одно целое значение одного из участников |
| `rollback` | Создать запись и значения внутри транзакции, затем откатить; записи, значения, календарная проекция и журнал этой попытки не должны остаться |
| `planning` | Создать задачу с исполнителем/назначающим/сроком, изменить стадию/исполнителя/описание/даты, читать страницы/карточки и календарь; сверить каждую задачу, автора, событие получателя и проекцию |
| `library` | Создать файловую запись, изменить источник автоподбора и ручное приложение, читать библиотечную ленту, искать по тексту, удалить временные данные; сверить пути/типы/карточки и общую очередь FTS |
| `integrations` | Принять свою строку по привязке, повторно обновить по ключу, применить шаг записи, подготовить и разобрать исходящий JSON с кавычками/переносами строк; сверить все подтвержденные значения и авторов |
| `people` | Все участники создают, меняют и удаляют записи независимо от старых масок, авторство сохраняется |
| `structure` | В общей коллекции создать/заполнить/переименовать/оформить свое свойство, создать/изменить собственную ветку группы/коллекции и настройки, прочитать дерево и удалить созданное; сверить живые объекты и очистку метаданных |

Для каждого нового сценария сначала укажите `--clients 8`, затем нужный размер нагрузки.
Например, последовательный запуск `planning` на трех профилях:

```bash
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile wal --scenario planning --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider sqlite --profile shared --scenario planning --clients 1000
dotnet run -c Release --project Tests/Benchmarks -- multiuser --provider postgres --profile server --scenario planning --clients 1000
```

Те же команды применимы к `library`, `integrations`, `people` и `structure`. PostgreSQL
не принимает SQLite-профиль `wal`: используйте `server` или опустите `--profile`.

Стенд вызывает настоящие `ConstructorRepository`. Дополнительных повторов ошибок в стенде
нет; внутренние повторы самого приложения сохраняются. В `lifecycle` подтверждение каждой
команды обновляет ожидаемое состояние участника. Свежий контекст сверяет точный набор
записей, коллекции, тексты, даты, авторов, число ячеек и проекцию календаря. Отдельно
проверяются журнал, дубликаты, осиротевшие строки и сводки дней календаря; для SQLite — физическая целостность и FK.

### Отчет и критерий успеха

`report.json` и консоль разделяют:

- запрошенные, подключившиеся, готовые и начавшие работу сессии;
- участников с хотя бы одной успешной операцией и участников, завершивших все циклы;
- успешные и ошибочные операции, их p50/p95/p99/max, общий темп и время подготовки;
- ошибки каждого клиента с типом или кодом SQLite/PostgreSQL и неудачной операцией;
- подтвержденные записи каждого участника и числа фактических/ожидаемых строк при расхождениях;
- результат каждой проверки данных и общий `Passed`;
- исключения самой итоговой сверки в `VerificationFailures`: ошибка проверки не теряет уже собранные метрики и не становится успешным результатом.

Успех требует готовности всех запрошенных участников, завершения всех их циклов без ошибок
и таймаутов и успешной сверки данных. Сохранный файл при отказах BUSY или части неподключенных
участников не означает, что заявленная нагрузка обслужена. Без `--p95-ms` задержки сохраняются
как замеры и не сравниваются с произвольным продуктовым порогом.

При ошибке подготовки сохраняется `setup-error.json`; если сессии не остановились и безопасная
сверка невозможна — `incomplete.json`, ненулевой код возврата и указание, что данные не проверены.
Новые SQLite-файлы, PostgreSQL-база и отчеты сохраняются для разбора; стенд их автоматически
не удаляет. Имя PostgreSQL-базы и папка данных выводятся в консоль и отчет.

### Что покрыто и что остается

| Ситуация | Покрытие |
|----------|----------|
| Разные пользователи создают, правят, читают, дублируют и удаляют свои записи | Малые регрессии и `lifecycle` |
| Одновременный перенос разных записей в одну коллекцию с готовыми целевыми свойствами | Малые регрессии и `lifecycle` |
| Первое заполнение общей ячейки | Малые регрессии и `hotcell` |
| Редактор сохраняет значение после чужого удаления записи | Малые регрессии, отдельно текст и дата |
| Полный откат создания вместе со значениями, проекцией и журналом | `rollback`; конфликт снимка дополнительно проверяет `PgWriteTransactionTests` |
| Отказ записи аудита после изменения текста/даты | Малые регрессии с настоящим отказом триггера, отдельно оба типа на трех профилях |
| Разные процессы читают и пишут один SQLite-файл | Существующий `MultiProcess --load`; это другой профиль нагрузки |
| Удаление поля/коллекции против записи значения или создания записи | `ConcurrentStructureTests`: управляемое удаление после подготовки редакторов; отдельный режим `structure` проверяет независимые изменения схемы |
| Два переноса одного источника, удаление против дублирования, одновременное создание недостающих полей назначения | `ConcurrentStructureTests`: отдельные регрессии и сохранность данных независимо от ошибки API |
| Аварийное завершение клиента внутри транзакции | `ConcurrentBackupTests`: настоящий дочерний процесс на трех профилях, kill против контролируемого commit; повтор произвольной пользовательской команды после потери подтверждения отдельно |
| Добавление локальной связи после проверки цели, удаленной соседом | `ConcurrentStructureTests`: управляемое пересечение с проверкой отсутствия висячего ребра; безопасный отказ не объявляется выполнением двух команд |
| Задачи/календарь, библиотека/индекс, обмен и различные права | Малые модульные наборы и пять дополнительных `multiuser`-сценариев; точные исходы берутся из отчета, не из наличия режима |
| Потеря сети, SMB/NFS, перезапуск сервера, 1000 окон на разных машинах | Новым стендом не проверяются |

## Результаты 25.10.2026

Облачная Linux-машина: доступно 5 CPU, 32 ГиБ RAM, локальный диск, .NET SDK 10.0.402,
PostgreSQL 17.11 на той же машине. Сервер: `max_connections=1100`, `shared_buffers=256MB`,
`work_mem=2MB`, `fsync` / `synchronous_commit` / `full_page_writes` включены. Клиенты и сервер
делят ресурсы машины. Это не сравнение предельной производительности двух провайдеров.

В каждой строке запрошены и подготовлены **все 1000 сессий**, один цикл на участника.
Время — фаза команд без миграций и подготовки подключений. В таблице указаны полностью
завершившие цикл / запрошенные; успех означает отсутствие ошибок и успешную сверку данных,
но не соблюдение пользовательского SLA.

| Сценарий | SQLite WAL | SQLite DELETE+FULL, локальная эмуляция общей базы | PostgreSQL |
|----------|------------|--------------------------------------------------|------------|
| Создание → правки → чтение → дубль → перенос → удаление | 1000/1000, 19,5 с | 413/1000, 46,6 с, 587 BUSY | 1000/1000, 36,3 с |
| Первое заполнение одной общей ячейки | 1000/1000, 3,1 с | 994/1000, 17,2 с, 6 BUSY | 1000/1000, 5,1 с |
| Создание со значениями/датой и откат транзакции | 998/1000, 10,1 с, 2 BUSY | 1000/1000, 8,9 с | 1000/1000, 12,1 с |

Во всех девяти прогонах прошли проверки осиротевших значений/проекций, принадлежности полей,
дубликатов и сводок календаря; у SQLite также прошли `integrity_check` и `foreign_key_check`.
В сценариях явного отката нигде не осталось записей, значений, проекций или строк журнала.

При смешанной нагрузке DELETE+FULL **точная сверка с подтвержденными командами не прошла**:
763 фактические записи против 749 подтвержденных в реестре участников, 14 лишних записей,
126 отличий значений; пропавших подтвержденных записей не найдено. Часть команды успевала
закоммититься до BUSY на следующем шаге. Ошибка не гарантирует, что ничего не сохранилось.
Это логическая проблема результата операции, хотя физической порчи файла тест не обнаружил.

Длительные ожидания есть и в успешных прогонах: p95 вызовов смешанного сценария — примерно
2,0–6,7 с у WAL и 1,1–22,7 с у PostgreSQL. Поэтому результат нельзя пересказывать как
«1000 людей будут работать быстро». Это короткий одновременный всплеск на маленькой
фикстуре: две коллекции и два свойства, а не большая пользовательская база и не UI.

Существующие и новые малые тесты проверялись вместе: до добавления контролируемого отказа
из 70 тестов прошли 60, 10 выявили ошибку сохранения после удаления записи соседом, пропусков
не было. Ошибка проявляется и при конфликте трекера, и при FK на уже удаленную запись.
Проверки отсутствия восстановленных данных и физической/FK-целостности при этом проходят.
Окончательный результат новых 27 сценариев: **11 прошли, 16 упали, 0 пропущены**.
Десять падений воспроизводят сохранение после чужого удаления; шесть — частично сохраненную
правку при отказе аудита. Контролируемый отказ подтверждает проблему и на PostgreSQL:
значение и журнал уже изменены, а проекция даты еще прежняя. Эти тесты намеренно оставлены
красными и не помечены `Skip`: ошибки приложения в этой задаче не исправлялись.
Общий Unit-гейт: **2927 прошли, 0 упали, 0 пропущены**. Сборки тестовых инструментов
прошли; полный Integration-набор и реальные пользовательские данные этим отчетом не покрыты.

Новые положительные регрессии проверены мутантом: временная потеря значений при дублировании
дала три ожидаемых падения на трех профилях. Исходник затем восстановлен побайтно, повторный
прогон подтвердил успешность сценариев создания/переноса/общей ячейки. Дополнительно проверены
отказы неверных параметров, существующей папки, превышенного p95 и таймаута, малый `pgload`,
смешанный `MultiProcess --load` и режим только чтения.

Полные JSON, SQLite-фикстуры и журналы в среде прогона: `/workspace/.setup/concurrency-final-*`;
сводка — `/workspace/.setup/concurrency-final-summary.json`. В отчете каждого PG-прогона
сохранено имя его отдельной базы. Эти пути относятся к машине проверки, в Git данные не входят.
Два найденных продуктовых дефекта остаются открытыми в [Roadmap](../../ROADMAP.md).

## UI-наблюдатель расширенного этапа

```bash
dotnet run -c Release --project Tests/ConcurrentUi -- --mode all --out /tmp/sb-concurrent-ui-new
```

Папка должна быть новой. Допустимы отдельные `--mode jobs-live`, `jobs-snapshot` и
`notifications`. Стенд использует настоящие Avalonia dispatcher/контролы/шрифты, ограниченную
очередь производителей и отдельный watchdog процесса. Результаты каждого режима сохраняются
в JSON: функциональные проверки, длительность, heartbeat, максимальные разрывы UI и задержки
очереди. Fake notifier/badge проверяет решение и маршрутизацию, а не доставку системного баннера.

В прогоне 26.10.2026 все три режима прошли функциональные проверки. `jobs-live` занял
9,1247 с, максимальный разрыв heartbeat — 8617,9 мс; `jobs-snapshot` — 1,0003 с и 786,9 мс;
`notifications` — 17,6 мс и 8,1 мс соответственно. Файлы прогона:
`/workspace/.setup/concurrent-ui-first/*.json`. Это результаты одной среды, не пороги SLA.
Большая пауза живого обновления остается отдельным вопросом производительности даже при
верных итоговых строках. Стенд не подтверждает отзывчивость всех разделов при 1000 DB-писателях,
прокрутку панели на 1000 строк или работу 1000 отдельных окон.

## Исправления 26.10.2026

После исходных прогонов добавлены следующие изменения. Числа отказов выше описывают
состояние до исправлений; результаты повторных проверок собраны отдельно в
[карте покрытия](concurrency-coverage.md).

- **Атомарная запись.** Значение, аудит, журнал, задача и календарная проекция сохраняются
  в одной транзакции. Строка обмена и строка шага сценария также коммитятся целиком;
  счетчики меняются после commit. У импорта больше нет отдельного сохранения журнала после
  уже подтвержденных данных. Отмена между строками сохраняет подтвержденный префикс.
- **Свежие родители и источник.** Перед записью перечитываются запись и свойство; удаленная
  соседом цель не восстанавливается из трекера. Чужое свойство по-прежнему отклоняется.
  PostgreSQL удерживает запись и метаданные свойства блокировками до конца правки. Дубль
  читает живой источник, перенос захватывает его до копирования. В одной базе перенос
  атомарен; межбазовый путь сохраняет порядок «копия, затем удаление» и не становится
  распределенной транзакцией. Повтор создания целевого свойства перечитывает готовую схему.
- **Ссылки, календарь и номера.** Локальные цели ссылок согласованы с удалением через
  блокировки родителей; это не транзакционная защита удаленной базы. Чтение дней календаря
  использует один снимок: SQLite deferred, PostgreSQL RepeatableRead. Проверка и выдача
  номера в `DocRegistry`/`PdfWatermark` идут вместе с записью полного резерва под блокировкой
  коллекции. Устаревшая ведомость перечитывается; штатный PDF-движок обновляет ее после
  commit собственного резерва.

Внешняя транзакция остается у вызывающего кода. Обертки записи `InWriteTransaction`,
`InCollectionWriteTransaction` и `ExecuteAtomicWrite` используют savepoint для вложенного
шага: его отказ восстанавливает трекер, навигации и отложенные уведомления, сохраняя прежние
pending-правки владельца. Целиком повторяется только собственная транзакция при допустимом
конфликте SQLite/PostgreSQL. Ошибка освобождения ресурса после успешного commit журналируется
как ошибка очистки и не превращает подтвержденную запись в сообщение «не сохранено».

У API `IssueJournal.Reserve` с переданной `NumberLedger` есть отдельная граница: если
вызывающий код уже открыл внешнюю транзакцию, возврат из `Reserve` подтверждает только
успешный вложенный шаг, а окончательным commit/rollback управляет владелец транзакции.
Ведомость консервативна в пределах прогона: после отката владельца номер может остаться в
ее памяти и быть пропущен. Это не разрешение повторно выдать его. Намеренно освободить номер
через `Free` либо пересоздать ведомость можно только после подтверждения, что готовый PDF
с ним не опубликован; существующий резерв при снятии также удаляется через `Release`.
`data_version` закрепленного SQLite-подключения отслеживает чужие записи, а не commit
собственной внешней транзакции. Штатный `PdfWatermarkEngine` завершает транзакцию резерва
до публикации каждого PDF и не использует такую внешнюю транзакцию на всю пачку.

`WriteAdmission` передает разрешения в порядке FIFO; отмененный или просроченный участник
удаляется из очереди. В одном процессе очередь допускает одного SQLite-писателя на файл;
у PG через `WriteScope` допускается до 16 писателей на базу. У SQLite вход централизован
у подготовленного EF `BEGIN`, включая caller-owned `BeginTransaction`.
У SQLite включен `AutoTransactionBehavior.Always`:
даже одиночный EF `SaveChanges` для настроек коллекции или ширины колонок теперь создает
транзакцию и проходит ту же FIFO-очередь. Раньше такой одиночный SQL мог обходить `BEGIN`
и конкурировать с уже допущенным писателем. Разрешение освобождается при commit, rollback,
dispose, отмене ожидания или отказе `BEGIN`. Оно освобождается до commit callbacks, которые могут
открыть другой контекст. Прямой native deferred read snapshot не занимает очередь писателей.
Произвольный native SQL и другие процессы этой очередью не управляются: межпроцессную
защиту обеспечивают настоящие транзакции и блокировки СУБД.

Для границ добавлены 8 случаев `AtomicWriteBoundaryTests`, 10
`SqliteTransactionAdmissionTests` и 5 Unit-случаев `WriteAdmissionTests`.
Отдельно добавлены 4 проверки `CalendarReadSnapshotTests` и 24
`ConcurrentExchangeAtomicityTests`: поздний отказ поля/журнала, повтор после отката и гонка
одного ключа с регистром кириллицы, пробелами и буквальными `%`, `_`, `\`.
Пятнадцать `ConcurrentTableStyleTests` проверяют очередь оформления ячейки/строки/колонки,
внешний rollback, повтор после отказа и устаревший style tracker. Три
`ConcurrentAutoRelationParentTests` проверяют удаление локальной цели после просмотра;
шесть `ConcurrentMoveAtomicityTests` — поздний отказ переноса и конкуренцию двух баз.
Это состав проверок; наличие теста само по себе не объявляет повторный прогон успешным.

## Взаимодействия

`pgload` остается измерением PostgreSQL прямыми SQL-вставками и инкрементами, не CRUD
приложения. Его строгий результат требует подключения и полезной работы каждого клиента:
`53300`, таймаут или клиент без завершенной пары операций исключают успех. Его секундный
интервал по-прежнему включает подключение.

`MultiProcess --load` запускает настоящий отдельный процесс на SQLite-участника и измеряет
правки ячеек, страницы, дерево и `data_version`. Для полного успеха нужны корректные отчеты
и полезная работа каждого процесса, ноль BUSY и других ошибок. Сохранность данных показывается
отдельно; общего барьера старта процессов там нет. Новый `multiuser` дополняет этот стенд
составными командами и общим стартом, но работает в одном процессе.

SQLite сериализует писателей. Локальный `shared` проверяет профиль DELETE+FULL, а не
надежность блокировок конкретного файлового сервера. Обслуживание 1000 одновременных
писателей нельзя обещать по результату локального WAL-прогона или по отсутствию повреждения.
