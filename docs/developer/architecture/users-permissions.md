# Пользователи и история изменений

## Назначение

Имена участников общей базы, авторство, исполнители и история фактических изменений.
С 30.10.2026 внутренние допуски, роли, пароли и маски прав SmartBase не применяются.
Права подключения PostgreSQL задает сервер; права файлов SQLite задает операционная система.
Сетевые пути, потеря и возврат папки описаны в [[database/network-shares]].

## Идентичность (без входа)

Пользователь определяется автоматически: ключ = `учетка@компьютер`
(`Environment.UserName` + `MachineName`, нижний регистр) — [Utils/CurrentUser.cs](../../../Utils/CurrentUser.cs).
ФИО заполняется в «Профиль → Общие данные» и хранится в app.db (ключи `profile.*`);
`DisplayName` = «Фамилия Имя Отчество» или ключ. Там же — необязательные **подразделение**
и **должность** (`profile.department`, `profile.position`): справочные поля самого
пользователя, они не влияют на идентичность и отображаемое имя и в `db_users`
не попадают. Значения кешируются в полях —
чтение потокобезопасно (журнал пишут и фоновые потоки).

## Справочник участников

`DatabaseManager.Users` — `UserDirectory` из `Database/Repositories/UserDirectory.cs`.
При монтировании `EnsureCurrentUserRegistered()` находит строку по `CurrentUser.Key`
или создает ее в `db_users`. Регистрация не ожидает разрешения и не выдает никаких ролей.
Уникальный ключ защищает от двойной регистрации; гонка SQLite/PostgreSQL обрабатывается
повторным чтением без отката чужих изменений.

`CurrentUserId` нужен для авторства. `GetUsers()` возвращает всех участников,
`GetUserOptions(includeValue)` — имена плюс историческое текущее значение ячейки.
`SyncDisplayName()` обновляет имя и пишет `user.rename`; `Changed` обновляет открытые редакторы.
`LastSeenAt` отражает последнее монтирование и не порождает событие на каждую активность.

## Совместимость старых баз

`db_users.IsAdmin/IsApproved/AccessDecided`, `db_permissions`, прежние ключи паролей,
метки и прочие исторические данные сохраняются без использования как ограничений.
Схему и пользовательские файлы не очищаем автоматически, существующие миграции не переписываем.
Старая история остается читаемой. Подключение PostgreSQL сохраняет свой пароль роли сервера,
внешние соединения — свои секреты; они относятся к протоколам подключения.

## Журнал изменений (change_log)

**Факты** + компактное «до → после» у правок: `Ts` (ISO UTC), снапшоты `UserKey/UserName`,
`Action` (`create/update/delete/duplicate/import/move` + `user.*` — см. «Допуск к базе»),
`TargetType` (`collection/group/field/record/records/user`), `TargetName`,
`CollectionName`, `Count`, `Detail`. `Detail` ([Utils/ChangeDetail.cs](../../../Utils/ChangeDetail.cs))
пишется у переименований (коллекция/группа/свойство/запись, `user.rename`) и правок
значений (ячейка, описание) — старое значение в этих точках уже в руках, доплаты нет;
длинные тексты сворачиваются до изменившегося фрагмента с контекстом
(«…срок оплаты 30…» → «…срок оплаты 45…») ЕЩЕ ПРИ ЗАПИСИ — журнал не раздувается.
Полных снапшотов объектов нет — журнал не система отката.

- пишется через **тот же контекст**, что и операция (в т.ч. изолированный фоновый) —
  `Log` до `SaveChanges` коммитится вместе с операцией, `LogNow` — для bulk-путей;
- **пакетные операции — одна строка с Count** (импорт, массовое удаление/дублирование,
  дубль/удаление/перенос коллекций и групп, вставка/очистка/вырезание ячеек таблицы и их
  отмена) — массовые пути журналом не замедляются. У ячеек в `Detail` — образец правок «до →
  после», сколько влезает в предел строки, и счет остальных (`ChangeDetail.Batch`);
- **копирование ячеек в буфер сюда НЕ пишется**: это не правка, а строка с `TargetType =
  records` будила бы сценарии с триггером «изменение данных» и перечитывание таблицы у соседей.
  Событие копирования не создается. Подпись `copy` в `ChangeLogLabels` оставлена ради старых строк;
- перестановки (Position) и правки без изменения значения не журналируются;
- **побуквенные правки сливаются**: заголовок/описание/поля панели записи сохраняются
  на каждую букву — журнал держит одну строку на цель («исходное → конечное»,
  `BeginEditMerge`, окно 30 с). Слияние — удаление+вставка, не UPDATE: новый Id будит
  поллер соседей; возврат к исходному значению убирает строку совсем;
- чтение — `GetChangeLogPageAsync(ChangeLogQuery)`: фильтры по колонкам (IN;
  дата — по дню через `substr(Ts,1,10)`) и сортировка считаются в SQL, страницы —
  keyset (по `Id`, при сортировке — по паре «значение колонки + Id») на отдельном
  подключении: миллионы строк листаются без фриза. Значения для окна фильтра —
  `GetChangeLogCountsAsync` (SQL-агрегат по колонке, фоновый поток).

**Очистка истории** настраивается в «Профиль → История изменений» для выбранной базы.
`ConstructorRepository.GetChangeLogRetention()` / `SetChangeLogRetention(enabled, months)`
работают с `changelog.retention.enabled/months` в `db_meta`.
При монтировании `ApplyChangeLogRetention` удаляет старые строки на отдельном подключении.
Разовая `PurgeChangeLog(cutoff)` использует один DELETE без загрузки журнала в память.

Панель «История изменений»: таблица в стиле таблицы конструктора (колонки
Пользователь/Действие/Тип/Объект/Коллекция/Дата и время), фильтр-чеклист и сортировка
в шапке каждой колонки, выбор открытой базы — в навбаре, страницы по 200
догружаются при прокрутке.

## Тип свойства «Пользователь» (`user`)

Как `select`, только опции живые: участники базы
(`GetUserOptions(includeValue)` → отображаемые имена). Значение хранится **строкой-именем** —
фильтр/сортировка/экспорт/импорт работают без доработок; удаленный/переименованный
пользователь остается историческим снапшотом: `includeValue` — текущее значение ячейки —
добавляется к опциям, даже если такого пользователя в справочнике уже нет (иначе
редактор показал бы пустоту, а первый клик затер бы значение). При ручном создании из таблицы,
календаря и задач (со сроком и без) все user-поля новой записи получают текущего пользователя;
выбранные значения диалога и роли задачи затем заменяют начальные. Инициализация сама не
отправляет уведомлений о назначении задачи. Перенос существующей записи не является новым
созданием: сохраняет исторические имена и пустые ячейки, в том числе не заполняет user-поля,
которых не было в источнике. В базе, которую открывал только один участник, список содержит только его.

**Опции читаются в момент построения редактора, а не кешируются вьюхой** (запрос
дешевый — десятки строк): состав пользователей меняется, пока таблица/раздел открыты.
Точки: таблица конструктора (`TableView` — при входе в правку ячейки; `TableColumnDef.Options`
у user-колонки лишь снимок на момент построения колонок), панель записи (`RecordPageView`),
диалог записи календаря (`RecordDialog`), диалог задачи и строка быстрого добавления
(`TaskDialog`, `TasksControllerView.UpdateChrome`).

Уже построенные списки обновляет `UserDirectory.Changed`. `MainWindow.HookUserEvents`
подписывается на каждую открытую базу, а `Reload()` вызывается при чужих событиях пользователей.
Открытые задачи и редакторы получают свежие имена без перезапуска.

## Осознанные ограничения

- Идентификатор `учетка@компьютер` описывает участника, а не подтверждает его личность.
- Один человек на двух машинах может иметь две записи справочника.
- История — журнал изменений, а не система отката и не защита от прямой правки файла.
- В Debug app.db лежит в `.localdata`, в Release — в пользовательской папке приложения.
