# Свойство: «Связь» (`relation`)

Часть [реестра типов свойств](overview.md). Единый источник классификации — [`FieldTypeInfo`](../../../../Core/Models/FieldTypeInfo.cs).

**Ссылка на записи другой (или своей) коллекции.** Ячейка хранит не текст, а набор ссылок на
записи; показывается «чипами» с названием (Title) связанной записи. Many-to-many из коробки;
one-to-many/one — ограничения кардинальности. Разблокирует `lookup`/`rollup`/формулы (Этап 5).

## Хранение — отдельная таблица ребер (не `db_field_values`)

Связи лежат в `db_record_links` ([`DbRecordLinkEntity`](../../../../Database/Entities/CoreEntities.cs)),
а не в EAV-значениях: так работают каскады и обратные ссылки.

| Колонка | Смысл |
|---|---|
| `Id` | суррогатный PK |
| `FieldId` | поле-связь, породившее ребро |
| `FromRecordId` | запись-источник (в чьей ячейке связь) |
| `ToRecordId` | связанная запись (цель) — id в целевой БД |
| `TargetDbId` | БД цели: `0` — эта же БД; `>0` — реестровый DbId другого `.db` (см. [межбазовые](#межбазовые-связи-db)) |
| `Position` | порядок чипов в ячейке |

- **FK-каскады** (`ON DELETE CASCADE`) на `FieldId` и `FromRecordId` — удаление поля-связи или
  записи-источника чистит ребра автоматически. FK на `ToRecordId` **снят** (цель может быть в другом
  файле — FK между `.db` невозможен): удаление цели в этой же БД (`TargetDbId=0`) чистит **прикладной
  код** в путях удаления записей (`DeleteRecord`/`DeleteRecordsData`/`DeleteCollectionRows`:
  `DELETE … WHERE TargetDbId=0 AND ToRecordId IN(…)`).
- **Уникальность** `(FieldId, FromRecordId, TargetDbId, ToRecordId)` — не дает задвоить связь и
  различает одинаковые id в разных целевых БД.
- **Индексы**: `(FieldId, FromRecordId, Position)` — горячий показ чипов; `ToRecordId` — очистка при
  удалении цели в этой же БД.
- **Title не дублируется** — резолвится на лету по **собственному `TargetDbId` каждого ребра**
  (`0` → локальная `db_records`, `>0` → целевая БД из реестра), а НЕ по цели текущего конфига поля.
  Поэтому пере-настройка цели поля не «переклеивает» старые ребра к чужим записям: ребро, созданное
  на другую БД, всегда резолвится из ТОЙ БД (нет ложных совпадений `Id` и ложного «связи нет»).
  Переименование цели сразу видно в показе.

Настройка поля — [`RelationConfig`](../../../../Core/Models/RelationConfig.cs) в ConfigJson:
`{ "targetCollectionId": N, "single": true, "separator": "comma" }` (для межбазовой добавляется
`"targetDbId": M`). `single` — true: ровно одна связь (выбор замещает прежнюю); false: несколько
(many-to-many); **дефолт диалога — «Одну» (`single: true`)**. `separator` — ключ склейки названий при
показе, общий с «Мультисписком»
([`MultiSelectValue.SeparatorFor`](../../../../Core/Models/MultiSelectValue.cs)) — **7 вариантов**:

| Ключ | Склейка | Подпись в диалоге |
|---|---|---|
| `comma` | `", "` | Через запятую *(дефолт)* |
| `dot` | `". "` | Через точку |
| `space` | `" "` | Через пробел |
| `semicolon` | `"; "` | Через точку с запятой |
| `newline` | `"\n"` | С новой строки |
| `comma_tight` | `","` | Через запятую без пробела |
| `dot_tight` | `"."` | Через точку без пробела |

Порядок пунктов ComboBox совпадает с массивом ключей в
[`PropertyEditorDialog`](../../../../Controls/Dialogs/PropertyEditorDialog.axaml.cs) (индекс → ключ),
поэтому добавлять варианты нужно в оба места согласованно. Тип — «вычисляемо-подобный»
(`FieldTypeInfo.IsRelation`): значения в `db_field_values` нет, ячейка правится выбором в списке, не
текстом.

## Методы репозитория

[`ConstructorRepository.Relations`](../../../../Database/Repositories/ConstructorRepository.Relations.cs):
`GetLinks` (связи одной ячейки, Id+Title — **только внутрибазовые ребра `TargetDbId=0`**, JOIN к своим
`db_records`), `GetLinksBatch` (то же по набору строк — батч видимой страницы таблицы), `GetLinkEdges`
(все ребра ячейки `(ToRecordId, TargetDbId)` в порядке Position — по ним ячейка резолвит КАЖДОЕ ребро в
его БД), `SetLinks` (заменить набор — основной путь: отсев само-ссылок/дублей/чужих
коллекций, для single максимум одна, точечная разница + журнал «до → после» именами),
`AddLink`/`RemoveLink` (по одной связи), `SearchRecordTitles` (кандидаты для списка выбора: поиск
по Title, кап результатов).

## Интерфейс

Показ — в стиле «Мультисписка» (см. [multiselect.md](multiselect.md)):

- **Диалог свойства** — тип «Связь»: «Целевая база» (своя или любая из реестра — межбазовая связь),
  «Целевая коллекция» (любая, включая свою — self-relation), «Количество связей» (Несколько / Одну;
  **дефолт — «Одну»**, не сбрасывается при смене целевой БД) и «Разделитель названий» (7 вариантов,
  см. таблицу выше).
- **Ячейка / страница записи** ([`RelationSelectBox`](../../../../Controls/Widgets/RelationSelectBox.cs)):
  названия связанных записей **текстом через разделитель** (пусто → серое **«связи нет»**), фон
  прозрачный (как у ячейки таблицы). В таблице устроено **как «Мультисписок»**: колонка
  редактируемая, показ (`CellTemplate`) — только текст (`editing:false`), а сам список — в РЕЖИМЕ
  ПРАВКИ ячейки (`CellEditingTemplate`, `editing:true`): справа появляется **иконка-связь** (та же,
  что в шапке колонки — как «календарь» у поля даты), по клику по ней открывается выпадающий чеклист —
  поиск по названию + виртуализирующий список записей целевой коллекции с галочками (уже связанные
  предвыбраны; single — выбор одной сбрасывает прочие; правка пишется сразу через `SetLinks`). У
  каждого пункта — стрелка **«→»** перехода к записи (`Navigate` → `RecordClicked`/
  `RelatedRecordRequested` → `OpenRecordPanel`, коллекция резолвится у самой записи, поэтому переход
  между коллекциями работает). На панели записи контрол всегда в режиме правки (`editing:true`).
  Данные редактор тянет сам по RecordId строки (`GetLinks`); read-ячейка перечитывает связи по
  `AttachedToVisualTree` (после выхода из правки) и по уведомлению строки `"Item"` (Fill заглушки).

## Копирование связей при дублировании / переносе записи

- **Дубль записи** копирует ее ИСХОДЯЩИЕ связи (копия ссылается на те же цели; входящие ссылки на
  оригинал не копируются). Работают все пути: одиночный `DuplicateRecord` (EF) и пакетные
  `DuplicateRecordsData` (SQLite `INSERT…SELECT` по ранговой карте / PG по `_dup_rmap`).
- **Перенос записи в другую коллекцию/БД** (`MoveRecordsCore`) переносит связи и **переписывает
  `TargetDbId` под целевую базу**: «абсолютная» БД цели (`0` = БД источника) в целевой базе снова `0`,
  если совпала с назначением, иначе — межбазовая. Одна формула покрывает внутрибазовый перенос (`0→0`)
  и межбазовый (внутрибазовая связь на источник → межбазовая на источник; связь на базу-назначение →
  внутрибазовая; на третью базу — без изменений). Конфиг создаваемого поля-связи переписывается так же.
  Требует известных `sourceDbId`/`targetDbId` (UI передает из окна «Расположение»).
- **Перенос записи из КАЛЕНДАРЯ и ЗАДАЧ** идет другим путем: смена коллекции/базы в окне записи
  пересоздает запись (`UpdateCalendarRecord` → `AddCalendarRecord` + `CopyFieldValuesByName` +
  `DeleteRecord`), минуя `MoveRecordsCore`. `CopyFieldValuesByName` копирует только `db_field_values` —
  ребра лежат в `db_record_links` и терялись молча, поэтому рядом обязателен
  **`CopyRelationLinksByName`** (`ConstructorRepository.Relations`). Правила у него те же, что у
  `MoveRecordsCore` (одноименные поля, оба «Связь», совпадение целевой коллекции и пересчитанной
  целевой БД) — расходятся правила, расходится и поведение двух путей. `sourceDbId == targetDbId`
  (в т.ч. `0,0`) — перенос внутри базы, `TargetDbId` ребер не трогаем.
- **Дубль в календаре — те же методы, что у таблицы**: `DuplicateRecord` для одиночного и
  `DuplicateRecordsMappedIsolated` для пакетного, поэтому копия несет все свойства и исходящие
  связи. Отдельной «календарной» копии (шапка + поле-дата) больше нет — она давала другой
  результат, чем дубль той же записи из таблицы. Календарь дублирует ЗАПИСЬ, а не событие:
  выбор двух событий одной записи (два поля-даты) дает одну копию, а не две.

## Батч-показ связей в таблице

Видимая страница таблицы прогревается ОДНИМ `GetLinksBatch` на каждое поле-связь
([`RelationLinksCache`](../../../../ViewModels/ConstructorDb/RelationLinksCache.cs)) — вместо N
точечных `GetLinks` по строке (проблема N+1, заметна на больших таблицах и PG по сети).
[`VirtualRowList`](../../../../ViewModels/ConstructorDb/VirtualRowList.cs) пишет кеш при наполнении
страниц, ячейка ([`RelationSelectBox`](../../../../Controls/Widgets/RelationSelectBox.cs)) читает его
при установке `RecordId`; правка ячейки инвалидирует свою запись, повторный показ (выход из правки,
`AttachedToVisualTree`) читает мимо кеша (свежее из БД). Кеш табличный (не глобальный) — панель
записи связи тянет напрямую.

## Фильтр и сортировка по связи

В `db_field_values` связей нет (они в `db_record_links`), поэтому у типа своя ветка фильтра/сортировки
(общая инфраструктура автофильтра переиспользуется, «значение» = **название связанной записи**):

- **Фильтр** — чеклист (Excel-стиль): пункты = названия связанных записей с счетчиками
  ([`GetRelationValueCounts`](../../../../Database/Repositories/ConstructorRepository.cs)) + «(нет
  связей)». Отметка нескольких — семантика **ИЛИ** (строка проходит, если связана хотя бы с одной
  отмеченной; [`GetFilteredRecordIds`](../../../../Database/Repositories/ConstructorRepository.cs)
  branch по `db_record_links`). «(нет связей)» — источники без ребер к именованным целям.
- **Сортировка** — «по показанному тексту»: названия связанных записей через разделитель поля (как в
  ячейке), А→Я / Я→А ([`GetColumnValues`](../../../../Database/Repositories/ConstructorRepository.cs)
  branch — склейка Title целей в порядке Position). Записи без связей → `""` (в конец при А→Я).
- **Межбазовые цели резолвятся** — счетчики, фильтр и сортировка идут через ОДИН приватный резолвер
  `RelationTitlesBySource` (id источника → список названий целей): внутрибазовые ребра берутся JOIN'ом
  к своим `db_records`, межбазовые — пакетно по `(TargetDbId → набор id)` через
  `RelationDbResolver.RepoFor(dbId)?.GetRecordTitles(ids)`. Поэтому фильтр/сортировка показывают те же
  названия, что и ячейка, а не «(нет связей)». Недоступная база дает значение **«(база недоступна)»**;
  цель, которой нет в доступной базе, — ребро пропускается (источник уходит в «(нет связей)»).
- Оговорка: одинаковые названия целей в фильтре — один пункт (домен строковый, как у прочих типов);
  цели с пустым Title относятся к «(нет связей)».

## Межбазовые связи (.db)

Цель связи может жить в другом `.db`. Идентичность цели — `(TargetDbId, ToRecordId)`, где `TargetDbId`
— стабильный DbId из реестра `app.db` (переживает переименование файла). Ребро по-прежнему хранится в
`db_record_links` НАШЕЙ базы, `ToRecordId` — id записи в целевом файле.

- **Резолвер** [`RelationDbResolver`](../../../../Database/RelationDbResolver.cs) (статический, настроен
  при старте `MainWindow` через `Workspace`): по `TargetDbId` дает репозиторий целевой БД. Если база не
  смонтирована — **монтирует из реестра** (названия целей появляются, даже если базы нет в сайдбаре).
- **Показ** ([`RelationSelectBox.LoadSelected`](../../../../Controls/Widgets/RelationSelectBox.cs)):
  берет ребра ячейки (`GetLinkEdges`), группирует по `TargetDbId` и резолвит названия **каждой группы
  из ее БД** (`0` → свой `_repo`, `>0` → `RelationDbResolver.RepoFor`). Быстрый путь таблицы (батч-кеш)
  держит только внутрибазовые ребра; все остальное (и всегда межбазовое поле) идет через
  `LoadSelected`. **Пикер** кандидатов — из ЦЕЛЕВОЙ коллекции текущего конфига
  (`SearchRecordTitles`). `SetLinks` пишет `TargetDbId` из конфига, само-ссылку и локальную валидацию
  для межбазовой пропускает (5.2).
- **Навигация**: чип межбазовой связи несет `(DbId, RecordId)` → отдельные cross-DB события таблицы/
  панели → `MainWindow.OpenRecordPanel(dbId, recordId)`: панель открывается из репозитория целевой БД
  (ее схема/правки), активную коллекцию не переключает.
  - **`DbId` нельзя терять по пути.** Состояние панели (`_lastOpened`) хранит пару `(DbId, RecordId)`,
    а не голый id: `OpenRecordPanel` в конце зовет `SetRecordPanelOpen(true)`, кнопка навбара поднимает
    `RecordPanelToggled`, и его обработчик ПЕРЕОТКРЫВАЕТ последнюю запись. Пока хранился только id,
    переоткрытие шло через перегрузку с `dbId=0`, межбазовая запись искалась в ТЕКУЩЕЙ базе, не
    находилась — и пустая панель перерисовывалась поверх уже правильно открытой. Симптом
    («запись открывается пустой») проявлялся ТОЛЬКО на межбазовой связи: при `dbId=0` второй вызов
    повторяет первый. Любой новый путь открытия панели должен передавать `DbId`.
  - Запись не найдена в своей БД или БД недоступна → тост, а НЕ фолбэк на текущую коллекцию:
    подстановка чужого `CollectionId` в чужой репозиторий дает пустую карточку вместо явной ошибки.
  - **Панель тоже знает свою базу** (`RecordPageView._dbId`, ставится в `Show`). `DbId=0` у чипа
    означает «в базе ЭТОЙ записи», а она не обязательно активная: панель могла быть открыта
    межбазовым переходом. Без `_dbId` внутрибазовая связь ЧУЖОЙ записи уводила бы в АКТИВНУЮ базу.
- **Обрыв связи — единая логика с внутрибазовой** (каскада между файлами нет, поэтому решаем на показе
  по доступности базы-цели):
  - база-цель **доступна, но записи нет** (удалена/перенесена) → чип **пропадает** (`LoadSelected`
    не кладет его в `_selected`) → пусто = **«связи нет»**, как внутри базы. Ребро вычищается само на
    следующей правке ячейки (`SetLinks` по `_selected`).
  - база-цель **недоступна** (сервер лег / файл-путь пропал / грузится / отключена в настройках) →
    **«(база недоступна)»**, ребро **держим** (база вернется — связь восстановится). Отключение базы —
    именно этот случай (обратимо, «подключить снова»), связи НЕ режет.
  - Прежнего состояния «(запись удалена)» больше нет.
- **Фильтр/сортировка** межбазовой связи — полноценные: названия целей из другой БД резолвятся тем же
  путем, что и в ячейке (см. [Фильтр и сортировка по связи](#фильтр-и-сортировка-по-связи)).

## Предупреждение об обрыве связей (удаление / перенос)

Операции, при которых на объект теряются ВХОДЯЩИЕ связи, дописывают в окно подтверждения строку «связи
будут удалены» — показываем лишь **факт** наличия связей, без числа (проще и без перф-риска). Проверка —
[`RelationDeleteImpact`](../../../../Database/RelationDeleteImpact.cs): внутрибазовые входящие + межбазовые
из **ОТКРЫТЫХ** баз (закрытые не проверяем — их ребра вычистятся лениво; best-effort). Репо-методы (в
[`ConstructorRepository.Relations`](../../../../Database/Repositories/ConstructorRepository.Relations.cs)) —
`HasIncomingLinks`, `HasIncomingLinksToCollections`, `HasExternalIncomingLinksToCollection`,
`IncomingLinkCountsByTarget`+`RecordIdsInCollections`, `CollectionIdsInGroup`; перечень открытых баз —
`RelationDbResolver.MountedReposExcept`. Проверка через `Any`/`EXISTS` обрывается на первом ребре, поэтому
дешева даже на больших базах (полный скан не нужен).

**Точек входа в межбазовый перенос три** — «Расположение» (`RelocateSelectionOrNode`) и «Изменение»
коллекции/группы (`EditCollection`/`EditGroup`, смена базы в диалоге). Все три зовут общий
`SidebarTree.ConfirmCrossDbLinkBreak` ДО любых изменений; звать его нужно перед КАЖДЫМ вызовом
`MoveNodesCrossDb`, иначе путь рвет связи молча.

| Операция | Что теряется | Проверка |
|---|---|---|
| Удалить запись (пакет / одиночную / со страницы записи) | все входящие | `ForRecords` (одиночная/страница — окно лишь при наличии связей) |
| Удалить коллекцию/группу | все входящие на ее записи | `ForCollections` (дедуп группа+вложенная коллекция, обрыв на первой) |
| Перенести запись (таблица) | все входящие (новый id, не следуют) | `ForRecords` |
| Удалить / перенести запись **из окна записи календаря или задачи** | все входящие | `ForRecords` в контроллере (`CalendarControllerView.ConfirmIncomingLinkBreak`, `TasksControllerView.OpenEditDialog`) |
| Межбазовый перенос ОДНОЙ коллекции | только ВНЕШНИЕ входящие (само-связи внутри переписываются) | `ForCollectionExternalCrossMove` |
| Межбазовый перенос ГРУППЫ (любой провайдер) | ВСЕ связи ветки: ребра не копируются вовсе | `ForCrossMoveDroppingAllLinks` |
| Перенос с участием **PostgreSQL** (коллекция или группа) | то же | `ForCrossMoveDroppingAllLinks` |

Последние две строки — про пути, где ребра **не копируются вообще**: generic-путь PG (ATTACH есть
только у SQLite) и перенос ветки группы даже на SQLite (`CopyGroupFromAttached` зовет копирование
коллекций с `0,0`). Обычная проверка смотрит лишь ВНЕШНИЕ ВХОДЯЩИЕ и молчит в двух случаях, где связи
реально теряются: коллекция с одними **само-связями** и ветка, ссылающаяся только **наружу**. Поэтому
`ForCrossMoveDroppingAllLinks` опирается на `HasAnyLinksInCollections` (исходящие + входящие).
Провайдер UI определяет через `ConstructorRepository.IsPostgres` у источника ИЛИ приемника; текст окна
там строже — предупреждает и о связях ВНУТРИ переносимого. Тест —
`Cross_move_dropping_all_links_catches_what_external_check_ignores`.

### Перенос ЗАПИСИ: еще и потеря свойств

Окно переноса записей собирает ВСЕ потери в одно подтверждение (кнопка «Перенести»):

- **не перенесутся свойства** — у которых нет одноименного поля в целевой коллекции, а галочка
  «Перенести все свойства» снята (значения молча пропадали);
- **потеряются связи в полях** — одноименное поле есть, но несовместимо: не «Связь», либо другая
  целевая коллекция/БД (ребра молча не переносились);
- **оборвутся входящие связи** — прежнее предупреждение (`RelationDeleteImpact.ForRecords`).

Первые два считает [`FieldsLostOnMove`](../../../../Database/Repositories/ConstructorRepository.cs) —
по СХЕМЕ (два списка `db_fields`, десятки строк), а не по данным: стоимость не зависит от числа
переносимых записей. Поэтому здесь, в отличие от проверки входящих ребер (миллионы строк → только
ФАКТ через EXISTS), показываются полные ИМЕНА: решение «отменять ли перенос» зависит именно от того,
какие свойства пропадут. Список в окне обрезается на 8 именах + «и еще N» — ограничение визуальное.

**Правила `FieldsLostOnMove` обязаны совпадать с планом `MoveRecordsCore`** (сопоставление по имени +
для связей совместимость целевой коллекции и переписанной целевой БД) — иначе окно соврет. Меняешь
план — меняй проверку; на связке есть тест
`FieldsLostOnMove_reports_missing_fields_and_incompatible_relations`.

Не теряют связи (окна нет): перенос коллекции/группы **внутри** базы (id не меняются), отключение базы
(«недоступна», возвращается), дубль. Перетаскивание и ресайз события по датам тоже безопасны: id
записи не меняется, ребра не трогаются — окна там быть не должно.

### Календарь и задачи: проверка живет в контроллере, не в диалоге

Кнопки «Удалить» и смена коллекции/базы в `RecordDialog` (календарный конструктор) и `TaskDialog`
сами ничего не пишут — возвращают результат, а решение принимает контроллер. Проверку связей ставим
**там**, а не в диалоге: у контроллера есть `_dbs` и `DbId` записи, поэтому `ForRecords` видит и
межбазовые входящие из открытых баз. Репозиторий берется ПРЯМЫМ поиском по `_dbs`, а не через
`RepoOf`/`RepoFor`-с-фолбэком: подстановка базы по умолчанию проверила бы чужую базу и совпала бы по
коллизии id. Окно показывается только при наличии связей — обычная правка записи спрашивать не должна.

Отдельная оговорка про схема-конструктор `RecordDialog` (`RecordDialog(repository, collectionId,
recordId)`): его кнопка «Удалить» проверяет только внутрибазовые входящие (`HasIncomingLinks`, DbId
окну не передан). В UI этот конструктор сейчас не создается — код живой, но недостижимый.

`DeleteCalendarRecord` чистит входящие ребра явно, как `DeleteRecord`/`DeleteRecordsData`: FK на
`ToRecordId` снят, и без чистки удаление из календаря/задач оставляло в `db_record_links` висячие
строки. В ячейке они невидимы (при показе такое ребро пропускается) и подменить цель не могут —
`db_records.Id` объявлен `AUTOINCREMENT`, id не переиспользуются, — но копились бы без нужды.

**Окно одноразовое — это ожидаемо, не баг.** Проверяется наличие ВХОДЯЩИХ ребер (`ToRecordId` ∈
переносимые), а не собственных связей записи (свои ИСХОДЯЩИЕ перенос как раз сохраняет и переписывает,
см. [выше](#копирование-связей-при-дублировании--переносе-записи)). Первый перенос эти входящие ребра
рвет насовсем — у записи новый id, ссылавшиеся уже показывают «связи нет». Поэтому **повторный перенос
той же записи (в т.ч. возврат в исходную коллекцию) окна не показывает**: рвать больше нечего, id снова
новый, а старые источники обратно не «приклеиваются» — им нужно заново выбрать цель в пикере. Чтобы
увидеть окно снова, надо сперва создать новую входящую связь на запись.

## Известное ограничение: совпадение id в смешанной ячейке

`SetLinks` сопоставляет существующие ребра с желаемым набором **только по `ToRecordId`**, без
`TargetDbId` (сам набор приходит списком голых id). Если у одного поля одной записи есть два ребра с
ОДИНАКОВЫМ `ToRecordId`, но разными `TargetDbId`, при первой же правке ячейки одно из них молча
исчезнет, а показ до этого дублирует название.

**Оставлено сознательно.** Через интерфейс такой дубль не создать: контрол держит выбранное списком
id и показывает кандидата с занятым id уже отмеченным, а для внутрибазовых связей `SetLinks`
ограничивает цели одной коллекцией конфига. Достижимо лишь стечением трех условий: поле перенастроено
между базами (ребра смотрят в разные коллекции), затем межбазовый перенос коллекции переписал
`ToRecordId` само-связей, и новый id численно совпал с id внешней цели. Починка требует перевести
набор выбранного в контроле на пары `(id, база)` — переписывание галочек, показа и `Toggle` в горячем
пути ради тройного совпадения.

Если браться: ключом сопоставления в `SetLinks` должна стать пара, а `RelationSelectBox._selected`
хранить пары вместо `List<int>`.

## Не планируется / отложено

- **Обратные ссылки** («Упоминания») и **создание записи прямо из списка выбора** — **не планируются**
  (осознанное решение: избыточно для задач продукта). ⚠️ Сверка 06.08.2026 предлагает пересмотреть
  оба — см. «Пересмотреть отказ» в конце документа: читающие примитивы и индекс уже есть, отказ
  обходится дороже реализации.
- **Перенос ГРУППЫ и PG-generic** пока не переносят РЕБРА: перенос ОДИНОЧНОЙ коллекции между `.db`
  (ATTACH, SQLite↔SQLite) связи переносит и переписывает — ребра в `CopyOneCollectionFromAttached`
  (карта `_move_rmap`: само-связь → внутрибазовая с ремапом `ToRecordId`; внешняя цель → межбазовая на
  источник), конфиги полей — `RewriteMovedRelationConfigs` (согласованно). Перенос **ветки-группы**
  между базами ребра отбрасывает (межколлекционный ремап `ToRecordId` в пределах ветки — отдельным
  заходом), но **КОНФИГИ полей-связей правит**: `RewriteMovedGroupRelationConfigs` по карте
  `старая коллекция → новая` из `CopyGroupFromAttached` (цель внутри ветки → внутрибазовая на новый id;
  цель снаружи → межбазовая на источник; база источника неизвестна → сброс в «не настроено»). Без этого
  `TargetCollectionId` источника читался бы в целевой базе как id ЛОКАЛЬНОЙ коллекции и поле молча
  показывало бы ЧУЖИЕ записи. PG-generic-путь (`CopyCollectionGeneric`) не копирует ни ребра, ни конфиги.

## План развития типа «Связь» (не реализовано)

Составлено 06.08.2026 сверкой нашей реализации с тем, что умеют связи в Notion, Airtable, Baserow,
NocoDB, Teable, SeaTable, Grist, Directus и в классических PLM/ERP (Teamcenter, SAP, 1С, Odoo).
Каждый пункт проверен по коду: перечислено то, чего у нас нет или что сделано частично.
Оценка объема: **S** — день-два, **M** — неделя, **L** — 2–4 недели, **XL** — месяц+.

Ничего из списка не запланировано на ближайший цикл — это отложенный бэклог типа.
Отдельно: пять пунктов оказались не «фичами мира», а тихой потерей данных и обходом прав
в уже написанном коде — они вынесены в «Известные дефекты» [[../../../ROADMAP]] и здесь помечены 🐞.

### Вычисления по связям (Этап 5 ROADMAP)

- **Lookup — вывод поля связанной записи** (L). Связь показывает только `db_records.Title`; на нем же
  завязаны фильтр, сортировка (`RelationTitlesBySource`), пикер (`SearchRecordTitles`) и копирование
  ячейки. По значению поля цели нельзя ни показать, ни отфильтровать, ни выгрузить. Нужны: код типа
  в `FieldTypeInfo`, конфиг `{relationFieldId, targetFieldId}`, батч-читатель поверх `GetLinksBatch` +
  `GetFieldValuesBatch` с резолвом чужой БД через `RelationDbResolver`, read-only колонка.
  Инфраструктура уже есть: вычисляемые read-only типы, батч ребер, межбазовый резолв.
  Есть у всех аналогов.
- **Rollup / Count — агрегаты по связям** (L). Ни count числа связей, ни sum/avg/min/max по полю цели,
  ни итогов в подвале колонки. `GetRelationValueCounts` переиспользовать нельзя — он считает уникальные
  записи-ИСТОЧНИКИ, а не ребра. Джойн `db_record_links → db_field_values` корректен только для
  `TargetDbId = 0`; межбазовый случай — отдельный проход (чистый count вычислим и одним запросом,
  `TargetDbId` лежит в ребре). Зависит от lookup.
- **Показ альтернативного поля вместо Title** (M). В `RelationConfig` нет «какое поле цели показывать».
  Классическая боль PLM: primary — артикул «ДЕТ-001294», человеку нужно «Кронштейн левый, сталь 3».
  Менять надо согласованно в четырех источниках показа (`GetLinks`/`GetLinksBatch` + тип
  `RelationLinksCache`, `SearchRecordTitles`, `RelationTitlesBySource`, `GetRecordTitles`), иначе
  ячейка разойдется с сортировкой и фильтром. В конфиге хранить имя/роль поля, а не id — id поля
  чужой БД после переноса укажет в никуда. Airtable, Teable, SeaTable, Grist.

### Модель связи

- **Атрибуты на ребре** — количество, роль, период (XL). Ребро несет только системные `Position`
  и `TargetDbId`; ни `ConfigJson`, ни значений. BOM без количества бессмыслен: одна деталь входит
  в разные узлы в разном количестве — это свойство ПАРЫ, а не детали. Эскиз: собственный EAV ребра
  (`link_field_values (LinkId, FieldId, Value)`) + список полей ребра в `RelationConfig`; UI —
  раскрытие ячейки в мини-таблицу «цель | количество | позиция» с точечной правкой через
  `AddLink`/`RemoveLink`, а не перезаписью набора. **Нет ни у одного табличного конструктора** —
  это отличие, а не догоняние; есть в Teamcenter BOMLine, SAP STPO, 1С «Спецификации», Odoo mrp.bom.line.
- **Иерархия по само-связи** (XL). Само-связь настраивается и переживает переносы, но ребра —
  плоское множество: нет разузлования вниз, транзитивного where-used вверх, уровней и ограничения
  глубины. Защита от циклов работает только на глубину 1 (`SetLinks` отсекает прямую само-ссылку,
  пикер прячет текущую запись) — цепочка `A→B→A` создается беспрепятственно, а это мина под любым
  рекурсивным агрегатом. Рекурсивного CTE в проекте нет нигде. Эскиз: флаг «иерархическая само-связь»
  в конфиге + рекурсивный CTE по `db_record_links` (`TargetDbId = 0`), проверка «цель не является
  предком источника» в `SetLinks`, режим таблицы «только корни / с отступами».
- **Ограничение допустимых целей** (M). `SearchRecordTitles` фильтрует только по коллекции и `LIKE`
  по Title; нельзя «только активные поставщики», «только компоненты Released», каскад «клиент → его
  договоры». ⚠️ Переиспользовать фильтр таблицы нечего: он устроен как набор допустимых ЗНАЧЕНИЙ
  (`GetFilteredRecordIds` принимает `колонка → множество строк`), операторов в модели нет вовсе —
  задача шире заявленной и упирается в Этап 3. Валидацию на записи оставить мягкой (видимость,
  не запрет), иначе порвем существующие ребра. Airtable, Baserow, NocoDB, Teable, SeaTable, Grist.
- **Политика ссылочной целостности** (L). Захардкожена единственная политика — «clear»: цель удаляется
  всегда, входящие ребра сносятся; ключа `onDelete` нет ни в конфиге, ни в диалоге. Нет `restrict`
  («нельзя удалить: используется в 12 спецификациях») и нет `cascade`. Предупреждение показывает
  только ФАКТ входящих — без числа и без списка ссылающихся записей (по `ToRecordId` в репозитории
  есть только EXISTS-предикаты и один счетчик). Эскиз: политика в `RelationConfig` + метод
  `GetIncomingLinks(recordId)` с названиями и коллекциями источников, `RelationDeleteImpact`
  расширить с `bool` до списка. Есть у Directus и всех PLM; **нет ни у одного табличного конструктора**.
- **Полиморфная цель — несколько коллекций у одного поля** (L). Цель задается одним
  `targetCollectionId`. Нужно для «прикрепленный объект» (статья ИЛИ документ ИЛИ задача), «объект
  обращения» в CRM. Читающая сторона УЖЕ полиморфна: `GetLinks`/`GetLinksBatch` джойнят `db_records`
  по Id без фильтра коллекции, навигация резолвит коллекцию у самой записи, колонки коллекции в ребре
  нет — миграция схемы не нужна. Работа: массив `targetCollectionIds` в конфиге (скаляр читается как
  список из одного), валидация в `SetLinks`, группировка кандидатов по коллекции в пикере и подпись
  коллекции у значения. Из аналогов есть только у Directus (M2A) — опережающая функция.

### Интерфейс

- **Чипы вместо плоской строки** (M). Ячейка — один `TextBlock` со склейкой Title и обрезкой
  многоточием: нет крестика снятия, нет «+N еще» при переполнении, нет перестановки. Порядок задается
  косвенно — очередностью галочек в пикере; `Position` в схеме есть и работает, но пользователь им
  управлять не может. `RemoveLink` реализован и покрыт тестом, но из UI не вызывается ни разу.
  ⚠️ Текст диалога свойства и этот документ обещают «чип» — обещание расходится с кодом.
  Порядок значим в спецификациях (номера позиций) и маршрутах техпроцесса.
- **Вложенная таблица связанных записей в карточке** (L). Поле-связь на странице записи имеет ровно
  один вид показа — строку названий. Строки спецификации, позиции заказа, задачи по проекту нельзя
  увидеть и править таблицей внутри карточки родителя, только перейти в панель каждой записи.
  Серверные кирпичи готовы (`GetLinkTargetIds`, `GetFieldValuesBatch`, `RelationDbResolver`);
  нужен режим показа в конфиге + набор видимых колонок. Airtable, Notion, Teable, SeaTable, Directus.
- **Пикер: подкачка, debounce, внятная деградация** (S). Жесткий кап 200 без подгрузки при прокрутке
  (keyset-инфраструктура в репозитории есть, но на `SearchRecordTitles` не распространена); `LIKE`
  выполняется синхронно на КАЖДОЕ нажатие клавиши — debounce есть в календаре (90 мс), в связях нет.
  ⚠️ Отдельный дефект: `LIKE` идет без `lower()`/коллации, поэтому **поиск по кириллице
  регистрозависим** (на SQLite `LIKE` регистронезависим только для ASCII, на PostgreSQL — вообще),
  вопреки doc-комментарию «регистронезависимо»; при этом отсев уже выбранных в том же методе идет
  `CurrentCultureIgnoreCase` — два разных правила в одной выдаче. При недоступной целевой базе список
  кандидатов молча пуст (сообщение «(база недоступна)» есть только для уже выбранных ребер).
- **Массовые операции над связями** (M). Все пишущие API — на одну запись-источник (`SetLinks`,
  `AddLink`, `RemoveLink`); батчевого аналога и глобальной замены цели X→Y нет, в контекстном меню
  строк пунктов про связи нет. **Частично закрыто таблицей:** ячейки-связи копируются названиями
  связанных записей и вставляются по ним обратно (`ResolveRelationTitles` + `SetLinksBulk` — ребра
  пакетом в одной транзакции, с отменой Ctrl+Z), очистка снимает связи — см.
  [features/constructor/table.md](../../features/constructor/table.md). Межбазовые связи вставкой
  не заполняются (`PasteSkipReason.NotTextColumn`): цель лежит в другом файле, и найти ее по
  названию отсюда нельзя. Глобальной замены одной цели X→Y внутри набора связей по-прежнему нет:
  вставка заменяет набор ячейки целиком.

### Дефекты, найденные этой сверкой 🐞

Вынесены в «Известные дефекты» [[../../../ROADMAP]] — это не отставание от рынка, а потеря данных
и обход прав в уже написанном коде.

- 🐞 **Экспорт выгружает колонку-связь пустой**; импорта связей нет вовсе.
- 🐞 **Смена типа поля не мигрирует данные**: `text→relation` не создает ребра, `relation→text`
  не пишет названия и не удаляет ребра — они воскресают при возврате типа.
- 🐞 **Дубль коллекции / группы / поля теряет ребра** без предупреждения; у копии коллекции поле
  само-связи продолжает указывать на исходную коллекцию.
- 🐞 **Права на целевую коллекцию не проверяются нигде** — чипы и пикер отдают названия записей
  закрытой коллекции, `RelationDbResolver.RepoFor` монтирует базу мимо допуска.
- 🐞 **Нет проверки целостности ребер**: висячие межбазовые не чистятся, `Single` не гарантирован
  вне `SetLinks`, перенастройка поля ребра не трогает.

Сюда же примыкает уже описанное выше: фильтр по связи адресует цель **названием**, а не парой
`(TargetDbId, ToRecordId)` — две записи-тезки склеиваются в один пункт (M).

### Пересмотреть отказ

Два пункта из «Не планируется» стоит перепроверить — сверка показала, что они дешевле, чем казалось:

- **Обратные ссылки / where-used** (M). Индекс по `ToRecordId` уже есть, пять читающих методов
  по нему уже написаны — но только как да/нет для предупреждений. Это единственный базовый
  PLM-сценарий «перед изменением детали увидеть все затронутые изделия». Минимальная форма —
  `GetIncomingLinks(recordId)` + блок «Ссылаются на эту запись» на странице записи, только чтение:
  данные не двоятся, зеркальное поле и поддержка симметрии не нужны.
- **Создание записи-цели из пикера** (S). Для CRM контрагент заводится в момент создания сделки.
  `AddRecord` сам делает `Demand(CreateRecord)`, `TargetRepo()` уже отдает нужный репозиторий —
  работы на пункт «+ Создать „<текст поиска>“» в конце списка. Обратная сторона — рост дублей
  в справочниках, поэтому уместно вместе с проверкой уникальности по бизнес-ключу.
