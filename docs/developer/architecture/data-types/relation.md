# Свойство: «Связь» (`relation`)

Часть [реестра типов свойств](overview.md). Связь хранит ссылки на записи своей или другой
коллекции, в том числе в другой базе. Для показа и поиска можно выбрать любое свойство цели;
по умолчанию используется «Название». Изменение подписи не меняет выбранную запись.

Ручной выбор и автоматическое сопоставление используют одну модель ребер. Отдельные
вычисляемые типы [lookup](lookup.md) и [rollup](rollup.md) читают значения по уже существующим
связям; собственные ребра эти типы не создают. Без своей связи они не считаются: удаление связи
и смена ее типа удаляют их вместе с метаданными колонок
([`RelationDependents`](../../../../Database/Repositories/ConstructorRepository.RelationDependents.cs)),
окна удаления и свойства перечисляют их заранее.

## Хранение и идентичность

Связи лежат в `db_record_links`
([`DbRecordLinkEntity`](../../../../Database/Entities/CoreEntities.cs)), а не в `db_field_values`.

| Колонка | Смысл |
|---|---|
| `Id` | Первичный ключ ребра |
| `FieldId` | Свойство-связь |
| `FromRecordId` | Запись-источник |
| `ToRecordId` | Идентификатор записи в целевой базе |
| `TargetDbId` | `0` — база источника; от `1 000 000` — постоянный номер целевой базы |
| `Position` | Порядок целей в ячейке |

Цель определяется парой `RelationTarget(DbId, RecordId)`. Одинаковые численные `RecordId`
разных баз обозначают разные записи. Контрол выбора, запись ребер, буфер обмена и отмена
сохраняют полную пару; подпись, разделитель и значение выбранного свойства идентичностью
не являются. Для межбазового переноса относительный `DbId=0` пересчитывается относительно
базы назначения.

Уникальный индекс `(FieldId, FromRecordId, TargetDbId, ToRecordId)` запрещает дубли. Индекс
`(FieldId, FromRecordId, Position)` обслуживает показ в порядке ребер, покрывающий индекс
`(ToRecordId, TargetDbId, FieldId, FromRecordId)` — поиск входящих: окно удаления, чистку
входящих и блок «Ссылаются на эту запись» (миграции `RecordLinksIncomingIndex` и
`RecordLinksIncomingIndexPg` заменили им прежний индекс `ToRecordId`, который стал его началом;
строки не меняются). На миллионе ребер он строится за 0,8 с на локальном диске и добавляет
около 19 МБ. Каскады на свойство и запись-источник удаляют исходящие ребра. Внешнего ключа
на цель нет: межбазовую ссылку нельзя проверить одним FK. Локальные входящие очищает код
удаления записи, коллекции или группы.

### Номер базы для межбазовых связей

Межбазовая цель адресует базу постоянным номером из самой базы: `db_meta["relation.base"]`
([`ConstructorRepository.RelationBase`](../../../../Database/Repositories/ConstructorRepository.RelationBase.cs)).
Номер заводится при первом подключении базы на запись (`EnsureRelationBaseId`, случайное число
от `RelationDbResolver.MinLinkId` = 1 000 000), одинаков у SQLite-файла и базы PostgreSQL на всех
компьютерах и переживает удаление базы из списка, повторное подключение и смену пути к файлу.
Номер реестра `app.db` для этого не годится: это счетчик одной установки, у коллеги, открывшего
ту же общую базу, он означал бы другую базу. База без права записи номера не получает и не может
стать целью новой межбазовой связи.

[`RelationDbResolver`](../../../../Database/RelationDbResolver.cs) ищет базу по номеру среди
подключенных, затем по запомненной паре «номер реестра → номер базы» (`app_settings`,
`relation.bases`, сохраняет UI-поток при смене набора баз) подключает ее запись реестра. Две
подключенные базы с одним номером — копия файла: выбирается та, что раньше встала с этим номером.
Номера реестра (последняя открытая запись, обмен, расширения) — у методов `Registry*`.

Старые ребра и настройки хранили номер реестра того компьютера, где их создали (меньше
1 000 000). Фоновый проход `MainWindow.RelationBases` после подключения всех баз вызывает
`MigrateLegacyRelationTargets`
([`RelationBaseMigration`](../../../../Database/Repositories/ConstructorRepository.RelationBaseMigration.cs)):
группа ребер одного свойства переводится на номер базы, только если на этом компьютере под старым
номером подключена база, где есть целевая коллекция, все связанные записи и свойства показа, поиска
и автоподбора, и ни одна другая подключенная база этим признакам не отвечает. Ребро, уже
записанное с новым номером, считается дублем старого. Остальные группы перечислены в
`db_meta["relation.base.legacy"]`: следующий проход проверяет только их, полный просмотр ребер
идет один раз. Такая цель показывается «(база не определена)», ребра не удаляются. В окне свойства
базу можно выбрать вручную: `RebindLegacyRelationField` переводит ребра, если все связанные записи
лежат в целевой коллекции выбранной базы, иначе отказывает без изменений.

Значения целей не дублируются в ребрах. Читатель разрешает каждое ребро по его собственному
`TargetDbId`, включая смешанные исторические наборы. Переименование или правка свойства цели
меняет показ, сохраняя идентичность связи.

У исторического смешанного набора численный selector свойства имеет смысл только в базе,
для которой он настроен. Ребро из другой базы получает «(свойство недоступно)»: совпавший
численный ID чужого свойства не используется. Существование цели и права по-прежнему
проверяются; недоступность базы и запрет доступа сохраняют свои отдельные признаки.
`__title__` безопасно разрешается для каждой базы. Локальный `0` и абсолютный ID своей базы
считаются одной базой. Хранить отдельный selector для каждой исторической цели модель пока
не умеет; полная идентичность самого ребра при этом сохраняется.

## Настройка свойства

[`RelationConfig`](../../../../Core/Models/RelationConfig.cs) хранится в `ConfigJson`:

```json
{
  "targetCollectionId": 42,
  "targetDbId": 7,
  "single": false,
  "separator": "comma",
  "displayField": "123",
  "searchField": "124",
  "auto": { "sourceField": "15", "targetField": "125" },
  "where": [{ "field": "126", "op": "eq", "values": ["Активен", "На продлении"] }]
}
```

`targetDbId` можно опустить для своей базы. `single=true` означает не более одной цели,
`false` — несколько. Новое свойство в диалоге по умолчанию допускает одну цель; старый JSON
без `single` по-прежнему читается как несколько.

Ключ свойства — `__title__` для названия либо строковый ID обычного или вычисляемого
свойства. `displayField` по умолчанию равен `__title__`; отсутствующий `searchField`
использует `displayField`. Показ и поиск могут обращаться к разным свойствам.

Показ — до трех свойств (`displayFields`), поиск — до пяти (`searchFields`). Массив пишется
рядом с одиночным ключом его первого свойства: прежняя версия программы читает
`displayField`/`searchField` и работает по первому. В памяти список — составной ключ
`RelationConfig.DisplayField` вида `"123|__title__"` (`DisplayKeys`, `SearchKeys`,
`TargetPropertyKeys`), поэтому все читатели получают его как обычный ключ:
`ReadRelationPropertyValues` склеивает непустые значения через « · » (отсутствующее свойство
пропускается), `SearchRelationRecordsCore` ищет «или» по каждому свойству и возвращает записи в
порядке коллекции. Перенос, проверка целостности и защита от циклов перебирают все ключи. Отсутствие
`auto` означает ручной режим. `RelationAutoRule` содержит только ключи исходного и целевого
свойств, без побочных эффектов при создании или разборе настройки.

Нечитаемый JSON и неверный тип идентификатора цели дают ненастроенное свойство, а не
исключение из `JsonElement`. Старые настройки сохраняют прежний показ по названию.
Селекторы свойств при копировании и переносе переписываются по картам ID, а не угадываются
по совпавшему численному идентификатору в новой базе.

Разделитель влияет только на показ нескольких значений:

| Ключ | Разделитель |
|---|---|
| `comma` | `, ` — по умолчанию |
| `dot` | `. ` |
| `space` | пробел |
| `semicolon` | `; ` |
| `newline` | перевод строки |
| `comma_tight` | `,` |
| `dot_tight` | `.` |

Общий источник — `MultiSelectValue.SeparatorFor`. Порядок пунктов диалога и ключей должен
совпадать. Разделитель не используется как структурный формат набора ссылок.

## Общий читатель и поиск

Основной код —
[`ConstructorRepository.RelationProperties`](../../../../Database/Repositories/ConstructorRepository.RelationProperties.cs)
и [`RelationProperty`](../../../../Core/Models/RelationProperty.cs).

- `GetRelationPropertyOptions` возвращает доступные свойства целевой коллекции.
- `ReadRelationPropertyValues` возвращает `RecordId`, исходный `Title`, `Raw`, `Display`,
  `FieldType` и `ConfigJson`. Сырое значение служит типизированному сопоставлению, текст — показу.
- `GetRecordPropertyValues` разрешает набор целей из их собственных коллекций.
- `GetRelationLinks` / `GetRelationLinksBatch` возвращают полные пары целей и выбранный показ.
- `SearchRelationRecords` и асинхронный вариант ищут по выбранному свойству. Title и текстовые
  свойства используют SQL; форматированные значения читаются ограниченными страницами.
- `GetLinkEdges` возвращает хранимые пары без разрешения подписей. `SetLinkEdges` записывает
  полный набор с порядком, проверкой источника и целей, удалением дублей и прямой ссылки на себя.

Старые `GetLinks` / `GetLinksBatch` оставлены как локальные обертки: только `TargetDbId=0`,
но подпись уже учитывает `displayField`. `GetRecordTitles` и `SearchRecordTitles` сохраняют
сигнатуры для старых клиентов. Старый `SetLinks` адаптирует численные ID к базе текущего
конфига; новый код с межбазовыми или смешанными ребрами использует `SetLinkEdges`.

Число показывается с форматом поля, дата — в пользовательском формате, мультисписок — через
его разделитель, файл — именами файлов, пользователь — сохраненным именем. Аудит берется из
метаданных записи; lookup и rollup передают исходное типизированное значение отдельно от
показа. Для relation исходное значение содержит полные пары целей. Вложенное разрешение
использует общий `RelationPropertyResolution`: посещенные свойства и ограничение глубины
защищают от рекурсии.

Таблица, страница записи, копирование, экспорт и `RelationTitlesBySource` используют общий
показ. Последний обслуживает сортировку, фильтр и счетчики столбца-связи. Фильтр по нескольким
подписям использует «или»; счетчик подписи считает записи-источники, имеющие такую цель.
Это отличается от `rollup:count`, который считает цели одной записи.

## Интерфейс

Диалог свойства задает целевые базу и коллекцию, одну или несколько целей, свойства для
показа и поиска, разделитель, ручной либо автоматический режим и данные из связанных записей:
строки «свойство цели + что показать», каждая — столбец [lookup](lookup.md) или
[rollup](rollup.md), который сохраняется вместе со связью (`SaveRelationDataColumns`, одна
транзакция, новые столбцы встают сразу за связью). Отдельных типов для них в списке нет. Собственная коллекция
допустима; непосредственная ссылка записи на себя исключается.

[`RelationSelectBox`](../../../../Controls/Widgets/RelationSelectBox.cs) показывает подписи
через разделитель; пустой набор обозначается «связи нет». Иконка связи открывает список
с поиском и галочками. В режиме одной цели выбор заменяет прежнюю, снятие галочки очищает
связь. Если показывается другое свойство, подпись дополняется названием записи, чтобы
различать одинаковые статусы, даты и пустые значения. Карандаш открывает целевую запись.

В поиске есть задержка объединения ввода 150 мс, отмена и проверка поколения запроса.
Закрытие списка и снятие контрола отменяют незавершенный поиск; устаревший результат не
перекрывает новый. Кандидатов не более 200; при превышении показана просьба уточнить поиск.
Форматированные значения просматриваются страницами по 256 записей, с проверкой отмены
между страницами. Чтение идет на отдельных подключениях в фоне; UI применяет готовый результат.

Без `EditRecord` и в автоматическом режиме выбор недоступен, но разрешенный переход к цели
сохраняется. Проверка прав выполняется до изменения выбранного набора; отказ записи не
оставляет ложное состояние галочек. Read-only показ без редактора содержит только текст.

## Автоматическое сопоставление

[`ConstructorRepository.RelationAuto`](../../../../Database/Repositories/ConstructorRepository.RelationAuto.cs)
подбирает цели по правилу [`RelationAutoRule`](../../../../Core/Models/RelationAutoRule.cs): от
одной до трех пар «свойство записи-источника — свойство целевой коллекции», запись связывается,
когда совпали все пары (ИНН + КПП). Предварительный просмотр не меняет настройку и ребра. Диалог
показывает изменения и причины, которые мешают применению; настройка и полный результат
сохраняются после «Сохранить».

Пустое значение первой пары не связывается (в окне подтверждения — «из них не заполнено «ИНН»»);
в остальных парах пустое совпадает только с пустым: индивидуальный предприниматель без КПП
связывается по ИНН. Ключ записи — части всех пар с длиной (`RelationAutoMatch.TryRuleKey`), поэтому
(«a;s:b», «c») не совпадает с («a», «b;s:c»); у правила из одной пары ключ прежний. Любая
поврежденная часть — отказ всего подбора, а не «пусто». Пары читаются по очереди; если состав
записей между чтениями разошелся, подбор отказывает с просьбой повторить просмотр.

Флажок правила «Не различать регистр и пробелы по краям» (`RelationAutoRule.Fold`) сворачивает
текст общей функцией `RelationAutoMatch.FoldText` — той же, что у условия выбора: края без
пробельных и невидимых знаков (U+00A0, U+200B, U+2060, U+FEFF), составные буквы в одном виде
(NFC), нижний регистр, «е с точками» как «е»; пробелы внутри не трогаются. Свертка действует на
текст, ссылку, список, статус, Markdown, текстовый аудит, пункты мультисписка и текст из
связанных записей; пользователь (снимок имени), пути файлов, числа, даты, флажки и связи
сравниваются как раньше. Сравнение идет только в C#: `lower()` в SQLite сворачивает лишь
латиницу, в PostgreSQL зависит от локали. У новых правил флажок включен; без текстовых пар он
неактивен и сохраняется снятым. Окно подтверждения называет, сколько записей совпало только
благодаря свертке (`detailed` — второй, точный индекс целей строится только для окна).

Неоднозначность называет до трех записей: «Для 4 записей найдено несколько целей, например
«Заказ 15», «Заказ 16». Добавьте пару свойств или выберите «Несколько».» У правила из нескольких
пар отказы называют пару: «Пара 2: свойство для сопоставления не найдено.»

Сравнение по типам задает [`RelationAutoMatch`](../../../../Core/Models/RelationAutoMatch.cs);
совместимость пары — `Compatible` (одно правило для подбора, окна и проверки связей; итог
«самая ранняя/поздняя дата» — семейство даты):

- Текст, URL, список, статус и текстовый аудит без свертки сравниваются точно, с учетом регистра.
- Числа сравниваются по числовому значению независимо от формата показа; даты — по
  каноническим границам и признаку целого дня; чекбокс различает истинное и ложное значения.
- Мультисписки и наборы файлов сравниваются как полные наборы без дублей и зависимости от
  порядка. У файла ключом служит путь, а не только показанное имя.
- Пользователь сравнивается по историческому имени из ячейки: действующая модель не хранит
  ссылку на учетную запись, поэтому одинаковые имена не доказывают одинаковую личность.
- Связи сравниваются по полным целям с абсолютной базой. Вычисляемые свойства передают
  типизированные ключи; формат валюты или даты не становится ключом сопоставления.

Пустое значение не совпадает со всеми пустыми записями. Для нескольких целей сохраняются
все совпадения в определенном порядке; для одной несколько совпадений дают неоднозначность,
блокирующую применение всего результата. Несовместимый тип, цикл зависимости, поврежденное
значение, потеря доступа или недоступная база также сохраняют прежние ребра.

Перед применением повторно проверяются настройка, значения всех пар и прежние ребра по
отпечатку предварительного просмотра. Конфликт требует нового просмотра; отмена и ошибка не
оставляют часть нового результата. Настройка и ребра записываются в одной транзакции. Фоновый
пересчет без изменений (настройка та же, просмотр только что сделан, менять нечего) завершается
без транзакции записи и второго чтения — на сетевом диске это большинство пересчетов. Просмотр,
сделанный раньше (`ApplyAutoRelation(preview)`), так не пропускается: его снимок перепроверяется
в транзакции, чужая правка дает Conflict.

### Совместимость правила автоподбора

Формат 1 — одна пара с точным сравнением, как в прежних версиях:
`"auto": {"sourceField": "12", "targetField": "34"}`. Правило, которое прежняя версия посчитала
бы иначе (несколько пар или свертка), пишется форматом 2: в старое место кладется заглушка
`"__title__"` → `"2147483647"`, пары и `"text": "fold"` — рядом, `"format": 2`. Прежняя версия
читает заглушку как правило на несуществующее свойство цели и отказывает до чтения данных:
ребра остаются, ячейки только для чтения. Первая пара в старое место не пишется никогда — иначе
прежняя версия пересчитала бы связи по одному ИНН. Любое изменение смысла сопоставления
повышает `format`.

| Что лежит в `auto` | Состояние (`RelationAutoState`) |
|---|---|
| нет `format`, настоящие ключи | `Ready`, одна пара, точное сравнение |
| нет `format`, заглушка | `Lost` — правило копировали или меняли в прежней версии |
| `format` = 2, все верно | `Ready` |
| `format` > 2 | `Newer` — хранится как есть (`Raw`) |
| `format` не число или меньше 2; в старом месте не заглушка; больше трех пар; лишний ключ; другое `text` | `Damaged` — хранится как есть, лишние пары не обрезаются |

Кроме `Ready` подбор не идет, ребра остаются, поле остается автоматическим, зависимые правила
считаются (`RefreshAutoRelationFields`, граф пересчета). `AddField` сохраняет такое правило без
подбора; `UpdateField` пропускает его только без изменений (переименование) и с прежней целью
(номера свойств в его парах относятся к ней; исключение — выбор базы старой межбазовой связи),
иначе — «Выберите пары свойств автоподбора.» или, у правила новее, «…чтобы сменить цель связи,
выберите «Ручной выбор» или обновите программу». Окно показывает у такого правила пустые
списки пар (сохранение без выбора просит выбрать пары, а не подбирает по названию), а при смене
цели у правила новее сбрасывает его и просит выбрать пары заново. Копия с непрочитанным правилом получает `Lost`
(`RelationAutoRule.MapKeys`): номера свойств в копии указали бы на чужие свойства. Проверка
связей: `Lost` и `Damaged` — `InvalidConfiguration`, `Newer` — сведение `NewerAutoRule`.

| Действие | Эта версия | Прежняя версия (1.3) |
|---|---|---|
| Правило формата 1 | считает как раньше | считает так же |
| Пересчет формата 2 | считает по всем парам | отказ «Свойство для сопоставления не найдено.», ребра на месте |
| Ручная правка ячейки | запрещена | запрещена |
| Окно свойства | пары и флажок | слева «Название», справа пусто: сохранение требует выбрать пару или «Ручной выбор» |
| Копия, перенос, импорт в прежней версии | — | заглушка переписывается как есть → здесь `Lost`, ребра скопированы |
| Экспорт JSON связи на свою коллекцию | работает | отказ «включите используемые ей свойства» |

Перенос записей с созданием недостающих свойств создает свойства и переписывает их ключи одной
транзакцией; поле-автосвязь — без подбора
(`AddField(…, copy: true)`, условие выбора заново не проверяется — оно уже принято, нечитаемое
копируется как есть): ключи правила — номера свойств источника, их переписывает
`RemapCopiedRelationConfigs`, подбор запускает уведомление после переноса. Столбец данных из связи
тоже создается без проверки и получает связь приемника. Раньше подбор шел со старыми номерами,
столбец данных не проходил проверку, и перенос отказывал.

`NotifyRelationDataChanged` сообщает об изменениях после сохранения; внутри внешней
транзакции уведомление откладывается до ее коммита и отбрасывается при откате. В окне события
объединяются и пересчет идет в фоне на отдельных подключениях. Без окна API выполняет
соответствующую работу после успешной записи. Чужие изменения и зависимые вычисления
попадают в тот же механизм. Недоступность цели откладывает пересчет, сохраняя прежние связи.

## Условие выбора записей

`RelationConfig.Where` — до пяти условий [`RelationCondition`](../../../../Core/Models/RelationCondition.cs)
(`field` — ключ свойства цели, как у показа; `op`; `values`), соединенных «и». Ключ `where`
пишется последним и только при условии, поэтому прежняя версия программы его не видит и
читает остальную настройку как раньше.

| Тип свойства цели | Сравнения (`op`) | Значения |
|---|---|---|
| Название, текст, Markdown, ссылка | `eq`, `ne`, `contains`, `notEmpty`, `empty` | одно; без учета регистра и крайних пробелов |
| Список, статус, пользователь | `eq`, `ne`, `notEmpty`, `empty` | один или несколько пунктов — «или»; точное совпадение |
| Флажок | `notEmpty` (отмечено), `empty` (не отмечено) | нет |

Числа, даты и другие типы в первую версию не вошли. Условие, которое не читается (лишний ключ,
неизвестное сравнение, больше пяти условий или двадцати значений, значение длиннее 200 знаков,
не список), не превращается в «без условия»: `RelationCondition.Read` возвращает его исходный
текст в `WhereUnreadable`, настройка сохраняет его как есть, а новые связи не выбираются, пока
условие не уберут. `ValidateRelationCondition` (в `AddField`/`UpdateField`) не дает сохранить
свойство цели, которого нет в коллекции, сравнение не по типу, пустое значение и измененный
нечитаемый текст.

Решает одна функция —
[`EvaluateRelationCondition`](../../../../Database/Repositories/ConstructorRepository.RelationCondition.cs)
на репозитории целевой базы: по набору id (порциями по 500) или по всей коллекции она читает
названия и значения нужных свойств и возвращает `RelationConditionVerdict` — подходящие id,
текст условия («Статус» равно «Активен» или «На продлении») и `Broken`, если решать нельзя
(нечитаемое условие, удаленное свойство, сравнение больше не подходит к типу). Сломанное
условие закрывает новые связи всегда.

Ворота новых связей — `NormalizeRelationTargets`: цели, которые уже были в ячейке (и возврат
отмены), проходят без проверки; новые обязаны подходить, иначе `RelationConditionException`
с названием записи и условием. Через них идут `SetLinkEdges`, старые `SetLinks`/`AddLink`,
пакетная запись ячеек и преобразование «Текст → Связь». Недоступная целевая база при условии —
отказ («условие выбора проверить нельзя»), а не доверие, как у старого API без условия.
Остальные пути:

- `SetLinksBulk` (вставка, заполнение) пропускает ячейку целиком, если в ней есть неподходящая
  новая цель, и считает такие ячейки в `LinkBulkResult.ConditionRefused`; отчет вставки называет
  их «связей не подходят под условие выбора записей». Сломанное условие и недоступная база цели
  не роняют вставку: ворота складывают отказ в `RelationConditionRefusals.Problem`, ячейка
  уходит в `ConditionUnchecked`, отчет добавляет причину; уже вставленные значения остаются с
  отменой. Остальные пути получают `RelationConditionException`, ее показывает `DbErrors`.
- Автоподбор связывает только подходящие записи, прежние связи ячейки оставляет; число
  отклоненных — `RelationAutoPreview.OutsideCondition` («не подходят под условие выбора — N» в
  окне просмотра). Подходящие id входят в отпечаток просмотра, свойства условия — в зависимости
  пересчета: смена статуса цели перепроверяет связи.
- Дубль записи и набора записей (SQLite и PostgreSQL) не копирует связи на неподходящие цели
  (`RefusedDuplicateTargets`, `DropRefusedDuplicateLinks`); решение — до сохранения копии.
- Перенос записей в другую коллекцию (`MoveRecordsCore`) и пересоздание записи календаря или
  задачи (`CopyRelationLinksByName`) — тоже новые записи: связи вне условия свойства-приемника
  не переносятся. Решается до транзакции, по всем переносимым записям.
- Дубль, перенос и импорт решают условие на базе цели через `EvaluateConditionOnTarget`: своя
  база — этот репозиторий, другая — свое подключение к уже открытой базе (они идут в фоне, общий
  контекст окна туда не уходит, базу отсюда не монтируют). Сбой чтения — «условие выбора
  проверить нельзя», а не отказ всей операции.
- Число пропущенных связей и причина — в уведомлении через `ConditionNotice`: «Копия создана. /
  Копии созданы. / Записи перенесены. Не скопировано (перенесено) связей — N («Клиент»): записи
  не подходят под условие выбора.»; при сломанном условии или недоступной базе — их текст.
  Операция из многих шагов (дубль по одной записи в календаре и задачах) копит фразы в
  `BatchConditionNotices` и показывает одно уведомление.
- Импорт переносимого JSON проверяет ребра свойств с условием по целевой базе и не создает
  неподходящие; сообщение — «Коллекция загружена. Не создано связей — N».
- Копирование коллекции и группы переписывает ключи условия на свойства копии для внутренних
  целей; экспорт своей коллекции требует включить свойства условия.

Поиск в окне выбора (`SearchRelationRecords(…, condition)`) отдает только подходящие записи в
порядке коллекции. Условие разбирается один раз на поиск (`PrepareRelationCondition`), записи
решаются порциями по 500 (`AllowedByCondition`). Точное «равно» по списку, статусу,
пользователю и «отмечено» у флажка берет кандидатов из индекса `(FieldId, Value)` — до 4096;
если совпадений больше, пробуется следующее точное условие. Набранный запрос сужает записи тем же
SQL, что поиск без условия (`TermFilteredRecords`: название и текстовые свойства без учета
регистра); иначе коллекция читается окнами по 500 до набора результата. SQL лишь сужает
кандидатов — решает та же функция, что держит ворота. «Название» — запись «Без названия»
считается пустой. `GetRelationPickerDataAsync` возвращает текст условия, причину поломки
и выбранные раньше цели вне условия; `RelationSelectBox` пишет под поиском «Только записи, где
…», помечает такие цели строкой «не подходит под условие выбора» и перед их снятием или заменой
спрашивает, потому что вернуть их будет нельзя. Отказ ворот после чужой правки статуса
показывается уведомлением, список обновляется.

Уже выбранные связи условие не снимает. Проверка связей показывает их как
`ConditionMismatch` — сведение, а не дефект: исправления нет, в отпечаток отчета не входит,
поэтому смена статуса цели не делает план исправления устаревшим. Сведения не входят ни в
подтвержденные, ни в непроверенные замечания (считаются по видам) и не занимают потолок списка
`MaxIssues`: в список их идет не больше 20 на свойство, после настоящих дефектов. Нечитаемое условие —
`InvalidConfiguration`, удаленное свойство условия — `MissingDependency`, сравнение не по
типу — `InvalidDependency`.

В окне свойства блок «Условие выбора записей» (`PropertyEditorDialog.RelationCondition`)
стоит перед «Режим связи»: строки «свойство · сравнение · значение», между ними «и»; у списка,
статуса и пользователя значения — галочками пунктов, сохраненный пункт, которого уже нет в
списке, остается отмеченным с пометкой «(нет в списке)». Смена целевой коллекции или базы
сбрасывает строки. Нечитаемое условие строками не показывается — только пояснение и
«Убрать условие»; хранится оно в одном виде записи (`JsonSerializer`), поэтому сохранение без
изменений не спотыкается о пробелы или экранирование файла другой версии. Текстовое условие с
несколькими значениями (из файла, после смены типа свойства) показывает первое в поле, остальные
— строкой под ним, и сохраняет все, пока поле не меняли. Если под новое условие сейчас не
подходит ни одна запись, сохранение переспрашивает; проверка идет в фоне на своих подключениях
(`SearchRelationRecordsAsync`), дольше 0,2 с — окно хода с отменой, сбой базы сохранению не
мешает.

## Права, межбазовые связи и недоступность

Показ, поиск кандидатов, выбор свойства, вычисления и переход требуют `ViewCollection`
у соответствующей цели. Запрещенная коллекция не отдает заголовок или значение свойства;
существующее ребро показывается как «(нет доступа)». Ручная правка дополнительно требует
`EditRecord` источника. Сохранение настройки автосвязи требует права создания/изменения
свойства и правки записей. Проверки репозитория повторяют UI-проверки на случай изменения прав.

[`RelationDbResolver`](../../../../Database/RelationDbResolver.cs) разрешает базы по номеру для
связей (см. «Номер базы для межбазовых связей»). `RepoFor` может открыть зарегистрированную базу;
`MountedRepoFor` и `MountedReposExcept` читают только уже открытые. Фон захватывает адреса и снимки прав заранее, создает собственные
контексты и устанавливает `UseScopedResolver`; вложенные связи не используют общий контекст окна.
`RelationLinksCache` хранит полные пары и подписи видимой страницы, включая пустые наборы.

Навигация передает базу вместе с записью. Панель сохраняет собственный `DbId`, поэтому
локальная ссылка из открытой чужой записи остается в ее базе. Несуществующая цель не
подменяется записью с тем же численным ID активной базы.

Доступная база без записи-цели означает обрыв: цель пропускается в показе. Недоступная база
дает «(база недоступна)», старый номер без определенной базы — «(база не определена)»; ребро в
обоих случаях сохраняется. Локальное удаление чистит входящие явно;
межбазового каскада нет. Предупреждение `RelationDeleteImpact` проверяет входящие из своей и
уже открытых баз. Оно не перечисляет все закрытые базы и не заменяет проверку целостности
всего реестра.

### Удаление цели: снять связь или запретить

`RelationConfig.RestrictDelete` (JSON `"onDelete": "restrict"`, пишется только при запрете;
по умолчанию и при незнакомом значении — снять связь) выбирается в окне свойства:
«При удалении связанной записи» → «Снять связь» / «Запретить удаление».

Кто ссылается, считает `ConstructorRepository.RelationReferences`: `IncomingReferences`
(записи; источники из удаляемого набора не считаются) и `IncomingReferencesToCollections`
(коллекции и ветки; ссылки изнутри набора уходят вместе с ним). Каждая ссылка —
`RelationReference`: свойство, его коллекция, число записей-источников и флаг запрета. Ребра в
память не выгружаются: один запрос группирует их по `FieldId` и считает `COUNT(DISTINCT
FromRecordId)`. Он идет от целей по индексу `ToRecordId`, а цели-записи коллекций задаются
некоррелированным подзапросом (`ToRecordId IN (SELECT Id …)`). Фильтр по свойству в SQL или
коррелированный `EXISTS` по записям коллекции увели бы SQLite без статистики `ANALYZE` в
перебор всех ребер свойства или базы — отбор свойств идет в памяти. Цена растет только с
числом настоящих ссылок: на миллион ребер у соседнего свойства удаление цели с одной ссылкой
занимает десятки миллисекунд. Свойства закрытых для пользователя коллекций называются одной
фразой «связи закрытых коллекций», без имен и чисел; у изолированного подключения права для
этого передает общий репозиторий (`ReferenceViewer`).

Удаление и перенос различаются ссылками изнутри набора. При удалении источник из того же набора
не мешает. Наборы, которые удаляются по частям, держат это так: входящее сообщение удаляет
записи по одной с `deletedTogether` внутри одной транзакции; календарь и задачи удаляют набор
каждой базы одной операцией `DeleteCalendarRecords` (права на все коллекции и запрет — до
первой записи, удаление — одной транзакцией); сайдбар передает узлам `collectionsTogether` и
до первого удаления проверяет права на все узлы. Иначе отказ на середине оставил бы источник со
ссылкой на уже удаленную цель. Перенос записей копирует их с новыми номерами, ссылка между
переносимыми записями обрывается, поэтому при переносе (`move: true`) считаются и они; проверка
идет до копии, а удаление оригиналов после копии запрет уже не проверяет. Перенос в другую базу
идет по узлу сайдбара за раз со своей картой копии: ссылки внутри узла переписываются, а ссылки
между узлами обрываются, и окно их считает. Служебная уборка (откат копии, остаток прерванного
переноса) вызывает удаление с `enforceRestrict: false`.

Окна удаления и переноса в таблице ждут фоновую проверку и вопрос, поэтому держат базу и
коллекцию, где выделены записи: открыли другую — действие не выполняется; повторное нажатие,
пока идет первое, игнорируется. Ошибка фоновой операции (запрет, поставленный, пока шел вопрос,
занятость базы) показывается окном, счетчик строк и лента календаря перечитываются.

Запрет держит репозиторий, поэтому его не обойти ни окном, ни обменом данными: удаление
записи, пакета, записи календаря, коллекции, группы, перенос записей в другую коллекцию и
перенос коллекции или ветки в другую базу (`EnsureDeleteAllowed`,
`EnsureDeleteAllowedForCollections`, `EnsureMoveAllowed`) бросают
`RelationDeleteRestrictedException` до первой измененной строки. Входящее сообщение
«delete» отказывает целиком, до первой удаленной записи. `DbErrors.Handle` показывает текст
отказа окном. Репозиторий видит только ребра своей базы.

Окна удаления зовут `RelationDeleteImpact.CheckRecordsAsync` / `CheckCollectionsAsync`: в фоне на
своих подключениях они собирают ссылки своей базы и открытых чужих (с именем базы; источники,
удаляемые в той же операции в чужой базе, тоже не считаются) и возвращают `RelationDeleteCheck`:
`Blocked` — текст отказа, если есть связь с запретом, иначе `References` — перечень ссылок, а
`Warning(кого, перенос)` собирает из него дописку к вопросу («На нее ссылается «Счета · Клиент»
(3 записи) — эта связь будет удалена.»; при переносе — «оборвется»).
Ссылки из закрытой базы не видны: запрет из нее сработает, когда база подключена.

### Обратные ссылки на странице записи

Блок «Ссылаются на эту запись» показывает, какие записи ссылаются на открытую запись. Карточка
— одно свойство-связь одной базы-источника, нацеленное на коллекцию записи: «Счета · Клиент»,
число записей-источников и первые три названия, сначала новые («3 записи: Счет №41, Счет №40,
Счет №39»; без ссылок — «ссылок нет»; больше 1 000 — «более 1 000 записей: …»). Карточка есть у
каждой такой связи, даже без ссылок. Тексты — `RelationBacklinkText`
([`RelationBacklink`](../../../../Core/Models/RelationBacklink.cs)).

Чтение — [`ConstructorRepository.RelationBacklinks`](../../../../Database/Repositories/ConstructorRepository.RelationBacklinks.cs),
два шага, оба точечные. Сначала номера источников по убыванию — только из покрывающего индекса
входящих (`ToRecordId = @r AND TargetDbId = @t AND FieldId = @f AND FromRecordId < @before
ORDER BY FromRecordId DESC LIMIT n`), без чтения таблицы и без сортировки; план от объема и
`ANALYZE` не зависит, его держит тест. Затем сверка по первичному ключу `db_records`: источник
лежит в коллекции свойства. Ребро записи, перенесенной в другую коллекцию, не считается и не
называется. Карточка читает не больше 1 001 источника на форму цели, страница списка — 201.

Своя база хранит ребра на свою запись с базой цели 0 и, у старых ребер, со своим номером. Обе
формы читаются отдельными запросами и сливаются без повторов: порция кончается на большем из
последних номеров полных ответов, следующая идет строго ниже. Непосредственная ссылка записи на
себя не показывается. Другая подключенная база ссылается только номером базы записи
(`TargetDbId = номер`); ее ребро с базой цели 0 ведет в ее собственную запись и не считается.
Номер ведет в основную копию файла: у второй подключенной копии с тем же номером ссылок из
других баз нет. Неподключенные базы и базы без допуска не читаются.

Свойства коллекций, закрытых для пользователя, не показываются вовсе: ни имени, ни числа.
Список источников и точное число требуют `ViewCollection` коллекции-источника.

Фон — [`RelationBacklinkReader`](../../../../Database/RelationBacklinks.cs): снимок баз
(`RelationBaseRef`, общий с окном удаления: путь, номер, имя и права) берется на UI-потоке,
чтение идет на своих подключениях. Права проверяются по снимку службы прав: `PermissionService`
держит допуск и маски одним неизменяемым объектом, и проверка из фона не застает половину
перечитывания. База, которую не удалось прочитать, дает карточку «Ссылки не прочитаны» —
«база занята или недоступна».

Список источников ([`RelationBacklinkBox`](../../../../Controls/Widgets/RelationBacklinkBox.cs))
открывается нажатием на карточку: поиск по названию без учета регистра (и у кириллицы), сначала
новые записи, страницами по 200 при прокрутке, под списком «Показаны 200 из 1 234». Точное число
считается в фоне, только пока открыт список и показаны не все. Поиск просматривает источники
порциями по 4 096 с отменой между ними; ключ следующей страницы — последняя показанная запись.
Клик по строке, карандаш или Enter открывают запись-источник в ее базе. Галочек нет: ссылку
ставят и снимают в самой записи-источнике.

Как блок встает в список свойств и обновляется — в
[record-page](../../features/constructor/record-page.md).

## Диагностика и безопасное исправление

«Настройки → Управление базой данных → Проверить связи» вызывает
`ScanRelationIntegrityAsync`. Стартовый проход `MainWindow.RelationIntegrity` запускается
после подключения баз; возвращение базы и смена прав отменяют старый снимок и назначают новый.
Проверка читает данные на отдельных фоновых подключениях ограниченными страницами, хранит
полные счетчики и ограниченную выборку примеров, поддерживает прогресс и отмену. Проверка
ничего не записывает и не подключает закрытые базы. Чтобы проверить их исходящие ссылки,
сначала подключают соответствующую базу и запускают команду для нее.

Окно свойства-связи открывает то же окно отчета для одного свойства:
`RelationIntegrityScanOptions.FieldId` ограничивает проход этим полем, его столбцами данных
(`lookup`/`rollup` с его `relationFieldId`) и его ребрами. Опции идут в отчет, поэтому
предварительный просмотр и применение перепроверяют тот же срез. Запуск, резервная копия и
сброс при смене прав — общие у обоих входов (`RelationIntegrityDialog.ShowForAsync`); базу и
строку реестра окно свойства берет у `RelationDbResolver.MountedEntryFor`, без рабочего
пространства кнопки нет.

Отчет различает подтвержденные дефекты и непроверенные цели. Проверяются источник, свойство,
целевая запись и коллекция, полная идентичность, канонические дубли локальных адресов,
одиночность, настройки, зависимости и циклы вычисляемых свойств. Названия закрытых коллекций
и записей не раскрываются. Отсутствие подключения или права просмотра не доказывает удаления.
Старые связи на разные базы с одинаковыми числовыми id сохраняют полную идентичность.

`PreviewRelationIntegrityRepairAsync` повторно проверяет выбранные факты. Автоматически
исправляются только случаи с однозначным результатом: доказанные осиротевшие ребра,
канонические дубли и недопустимая прямая ссылка записи на себя. Одиночность, неоднозначные
настройки и зависимости остаются в отчете для ручного решения. Предварительный просмотр и
применение требуют администратора базы и прав изменения источника: полная резервная копия
не должна предоставлять пользователю доступ к скрытым коллекциям.

`ApplyRelationIntegrityRepairAsync` проверяет отпечаток плана, вызывает
`RelationIntegrityBackupService`, проверяет принадлежность и SHA-256 готового артефакта,
повторно сверяет исходные данные и выполняет выбранный пакет в транзакции с аудитом.
Ошибка, отмена, изменение прав или снимка приводят к отказу всего пакета. Успешная повторная
проверка не предлагает уже удаленные ребра. Никакой автоматической очистки при запуске нет.

SQLite-копия проверяется штатным путем `BackupTo`; PostgreSQL использует `pg_dump` и полный
разбор архива через соответствующий `pg_restore`. Проверка архива в рабочей программе не
восстанавливает пользовательскую базу. Отдельные интеграционные тесты выполняют настоящее
восстановление в изолированную базу и сравнивают записи, свойства, настройки и ребра.

Между независимыми серверами нет общей транзакции: изменение цели сразу после последней
проверки может создать новый обрыв. Следующий проход обнаружит его; недоступность цели
никогда не служит основанием для удаления. Проверка всех закрытых баз без их подключения
и бесконечное наблюдение за состоянием файлов в этот механизм не входят.

## Копирование связей при дублировании / переносе записи

Дубль отдельной записи сохраняет ее исходящие ссылки на прежние цели; входящие остаются
у оригинала. Календарь и задачи используют те же данные, а при пересоздании записи в другой
коллекции вызывают `CopyRelationLinksByName` вместе с копированием обычных значений.

Дублирование свойства копирует его ребра. Для копирования коллекции или всей группы
[`RelationLifecycle`](../../../../Database/Repositories/ConstructorRepository.RelationLifecycle.cs)
сначала строит карты коллекций, свойств и записей, затем переносит ребра. Внутренние цели
направляются в копию, внешние остаются прежними. Общая карта всей ветки позволяет сохранить
ссылку в коллекцию, которая копируется позже источника. Переписываются также display/search,
исходное и целевое свойства автосвязи и зависимости lookup/rollup.

Те же правила действуют при переносе одной коллекции или группы между базами: SQLite ATTACH
использует SQL по временным картам, общий путь SQLite/PostgreSQL читает ограниченные страницы
и завершает граф после построения полной карты. Цели внутри переносимого набора получают
новые ID и локальную базу; внешние сохраняют абсолютную базу, пересчитанную относительно
назначения. Неизвестная база внешней цели вызывает отказ вместо подстановки локального ID.

При переносе записей между коллекциями свойства сопоставляются по имени и совместимой
целевой коллекции/базе. Несколько ребер нельзя молча перенести в свойство с одной целью:
операция требует устранить противоречие. Входящие извне ссылки на удаляемый оригинал не
следуют за новым ID; предупреждение проверяется до переноса. При переносе целой ветки
внутренние входящие сохраняются, предупреждение относится к связям снаружи ветки.

Снимки коллекций/групп тоже включают конфиги, исходные ID и полные ребра. Импорт проверяет
внешние базы и разрешения до записи, затем восстанавливает граф по полным картам.

## Смена типа, буфер обмена и экспорт

[`RelationConversion`](../../../../Database/Repositories/ConstructorRepository.RelationConversion.cs)
проверяет смену типа внутри транзакции `UpdateField`:

- `text`/`markdown` → `relation` требует настроенной цели и однозначного сопоставления всех
  непустых значений. Ошибка не оставляет часть созданных ребер.
- `relation` → `text`/`markdown` материализует выбранные подписи через разделитель и удаляет
  ребра. Недоступное значение не превращается молча в пустой текст.
- Смена цели заполненной связи и переход «несколько → одна» с лишними ребрами блокируются
  до явной очистки или исправления данных. Возврат типа не воскрешает старые скрытые ребра.

Таблица копирует читабельный текст и отдельный структурный `RelationClipboard` с координатами
ячеек, полными целями и проверяемыми идентичностями баз. Структурная вставка сохраняет
пунктуацию, пустые значения и одинаковые подписи разных записей. Для обычного внешнего текста
используется сопоставление подписей; неоднозначность отклоняется. `SetLinksBulk` и история
отмены сохраняют полные пары, ожидаемые прежние ребра и настройку свойства; конфликт схемы
или чужая правка не затираются. Лимит истории учитывает и ребра.

CSV/XLSX и обычная текстовая проекция экспорта используют актуальный показ связей, включая
межбазовые цели. Импорт обычной таблицы без схемы не восстанавливает идентичность по подписи.

Для JSON с relation/lookup/rollup экспорт таблицы использует переносимый формат
[`RelationPortableSchema`](../../../../Core/Models/RelationPortable.cs): версия, схема типов и
конфигов, ID записей, исходные значения и упорядоченные полные ребра. Вычисленные подписи не
подменяют исходные данные. Экспорт требует включить используемые свойства этой коллекции;
импорт проверяет внешние базы, доступность целей и ограничение одной связи до завершения
транзакции, а внутренние ID переписывает по карте. Идентичность базы проверяется непрозрачным
отпечатком; один реестровый номер другой установки сам по себе недостаточен. Не удалось
подтвердить внешнюю базу — импорт отклоняется, а не связывает запись по случайному ID.

## Проверки и дальнейшее развитие

Модель и форматирование проверяют `RelationPropertyConfigTests`, `RelationConfigTests`,
`RelationPropertyTests`; автоматический режим — `RelationAutoMatchTests`, `RelationAutoTests`
и `RelationReactiveTests`; жизненный цикл — `RelationCopyLifecycleTests` и
`RelationCrossMoveLifecycleTests`; преобразование и IO — `RelationIoSafetyTests` и
`RelationPortableJsonTests`. Вычисления покрывают `RelationComputedConfigTests` и
`RelationComputedTests`. UI-стенд `Tests/RecordPage --only relations` проверяет выбор,
навигацию, readonly и смену запроса; `--only relationcomputed` — вычисляемые карточки;
`--only relationintegrity` — диагностику, подтверждение, копию, отзыв прав и проверку одного
свойства из его окна. Показ и поиск по нескольким свойствам проверяет
`RelationMultiPropertyTests`; несколько пар автоподбора и свертку — `RelationAutoRuleTests`
(Unit) и `RelationAutoPairsTests` (Integration); запрет удаления и окна ссылок — `RelationRestrictDeleteTests`,
`InboxModesTests` (входящее удаление) и `RelationResolverWorkspaceTests` (ссылки из другой
открытой базы); проверку одного свойства — `RelationIntegrityFieldScanTests`; условие выбора —
`RelationConditionTests` (Unit: разбор, сравнения, нечитаемое условие; Integration: ворота,
вставка, поиск, окно выбора, автоподбор, дубль, импорт, копия коллекции, проверка связей);
обратные ссылки — `RelationBacklinkTextTests` (Unit: тексты и сравнение ответов),
`RelationBacklinkTests` (Integration: карточки, обе формы цели, ссылка на себя, чужая
коллекция, больше тысячи, страницы, поиск, отмена, закрытая коллекция, план запроса, снимок
прав, PostgreSQL), `RelationBacklinkWorkspaceTests` (другая подключенная база, база без допуска)
и стенд `Tests/RecordPage --only backlinks`.
`RelationIntegrityScanTests` и `RelationIntegrityRepairTests` проверяют доказательства дефектов,
конфликты снимков и прав, отмену и откат при отказе аудита. `RelationIntegrityBackupTests`
восстанавливают настоящие копии; `RelationBulkPgTests` проверяют пакетные ячейки, полную
идентичность целей и отмену на PostgreSQL.
Отдельный PG-сценарий прерывает соединения только собственной временной базы после создания
копии, проверяет сохранность данных и успешное повторное исправление после восстановления доступа.

Это перечень покрытия, а не утверждение о запуске проверок в конкретной среде.

Пока не реализованы:

- Свойства самого ребра: количество, роль, период и другие значения пары записей.
- Иерархические ограничения, разузлование и транзитивный обход. Защита вычисления от рекурсии
  не запрещает циклы в произвольном графе данных.
- Показ записей-источников обратных ссылок таблицей с отбором (пока — список в карточке) и
  ссылки из неподключенных баз.
- Произвольные формулы по связанным значениям сверх lookup и заданных агрегатов rollup.
- Проверка всех закрытых баз реестра без их предварительного подключения.
- Несколько целевых коллекций в одном правиле, условия выбора по числам и датам и условия,
  соединенные «или», редактируемая вложенная таблица целей и перестановка отдельных видимых
  элементов.
