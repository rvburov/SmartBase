# Сетевые папки: общая база SQLite на шаре

Сводный документ о том, как программа работает с файлами баз, лежащими в сетевых папках
(SMB-шара сервера или NAS, подключенный диск `P:`, UNC-путь `\\server\share\…`). Здесь —
вся картина целиком и ссылки на подробности; отдельные механизмы описаны в
[[multi-database]] (монтирование, монитор, поллер, конфликты) и
[[storage-and-migrations]] (журнал, прагмы, миграции, свободное место).

## Назначение

Одна база нужна нескольким людям сразу, а сервера PostgreSQL у отдела может не быть.
Тогда файл `.db` кладут в общую папку, и каждый подключает его в «Настройки → Управление
базой данных». SQLite сам по себе многопользовательский — писатели сериализуются файловым
замком, — но на сетевой файловой системе часть его механизмов ломается молча. Программа
берет эти риски на себя: определяет, что путь сетевой, переключает файл в безопасный режим
и держит его в нем, переживает пропажу и медленную работу сервера, а все отклонения
записывает в журнал диагностики.

## Что программа считает сетевой папкой

Решение принимает [NetworkPath](../../../../Database/NetworkPath.cs) по полному пути файла:

| Признак пути | Вердикт |
|---|---|
| Windows: UNC-путь `\\server\share\…` | сеть |
| Windows: буква диска с типом `Network` | сеть |
| Windows: буква с типом `Fixed` / `Removable` / `CDRom` / `Ram` | не сеть |
| Windows: буква с типом `NoRootDirectory` / `Unknown` (диска сейчас нет) | сеть; уверенно, если буква есть в постоянных подключениях пользователя `HKCU\Network\<буква>`, иначе «до выяснения» — ответ не кешируется и переспрашивается, когда диск появится |
| macOS: все под `/Volumes/…` | сеть (внешние диски тоже: та же модель отказа «том пропал») |
| Linux: точка монтирования типа `cifs`/`smb3`/`nfs`/`sshfs`/`davfs`/… по `/proc/mounts` | сеть |
| Путь не разобрать, ОС неизвестна, ошибка определения | сеть (консервативно: журнал DELETE безопасен всегда, лишь медленнее) |

Уверенные ответы кешируются на сеанс по пути. Чистая классификация —
`NetworkPath.ClassifyDrive`, под юнит-тестом ([NetworkPathTests](../../../../Tests/Unit/NetworkPathTests.cs)).

**Признак в самом файле сильнее определения по пути.** При монтировании по сетевому пути
`DatabaseManager` ставит в `db_meta` ключ `storage.shared = 1`; при каждом следующем
монтировании признак читается сырым read-only подключением еще до открытия контекста, и
если он есть, а путь показался локальным, путь принудительно помечается сетевым
(`NetworkPath.ForceNetwork`) с предупреждением в журнале. Так файл общей базы не может
превратиться в локальный из-за ошибки определения: автозапуск раньше восстановления
сетевого диска, локальный путь на машине, где физически лежит папка, стенд с подменой.

Что **никогда** не бывает сетевым: файлы самой программы в папке данных
(`%APPDATA%\SmartBase`): `database.db` (дефолтная база), `app.db` (реестр баз, настройки),
`logs.db` (журнал диагностики), `integrations.db` (журнал обмена), `security.db` (журнал
безопасности), `instance.lock`. Они у каждого пользователя свои.

Стенды и тесты помечают локальный файл сетевым руками: `NetworkPath.ForceNetwork(path)`,
`ForceServerRoot(path, root)` (группировка «соседей по серверу»), `Forget(path)` — забыть все.

## Чем общая база отличается от локальной

Флаг `DatabaseManager.IsShared` (сетевой путь или признак в файле) переключает поведение:

| Аспект | Локальная база | Общая база (сетевая папка) |
|---|---|---|
| Режим журнала | WAL (`-wal`/`-shm` рядом с файлом) | DELETE — WAL требует когерентной разделяемой памяти между машинами, которой на SMB/NFS нет; переключение при монтировании, если файл в другом режиме |
| Прагмы подключения | `busy_timeout` 10 с, `synchronous=NORMAL`, `mmap` включен, лимит WAL 64 МБ | `busy_timeout` 15 с (чужие писатели по сети держат замок дольше), `synchronous=FULL` (NORMAL в rollback-режиме рискует файлом при сбое питания сервера), `mmap_size=0` (mmap поверх сетевой ФС не рекомендован SQLite) |
| Автосжатие при монтировании | да, по порогу свободных страниц | никогда — VACUUM переписывает весь файл через сеть под эксклюзивным замком; только «Сжать файл» администратором |
| Резервная копия | `VACUUM INTO` | то же, без отключения базы; можно копировать и не смонтированную |
| Сигнал BUSY из рабочего кода | игнорируется (штатная конкуренция копий на одном ПК) | срочная проба монитором и сброс пула подключений (мертвые хендлы после перезагрузки сервера) |
| Проба папки перед монтированием | нет | да, 15 с; не ответила — «недоступна (папка не отвечает)» |
| Запись о монтировании в журнале | «локальный путь …, журнал wal» | «сетевой путь …, журнал delete» |
| Пользователи и права | таблица `db_users` внутри файла — ключ `учетка@компьютер`, первый открывший становится администратором | то же, но это и есть механизм допуска коллег: см. [[../users-permissions]] |

Все остальное одинаково: схема, миграции, репозитории, поллер чужих правок, журнал
изменений, экспорт и импорт.

## Жизненный цикл общей базы

**Подключение.** «Управление базой данных → Подключить базу данных SQLite» открывает
системный диалог выбора файла; годится и файл на подключенном диске, и по UNC-пути. Запись
попадает в реестр `app.db` (путь как выбран, без нормализации), база встает в хвост очереди
монтирования. Пересоздать файл в сетевой папке можно тем же диалогом — журнал DELETE и
признак общей базы файл получит при первом же монтировании.

**Монтирование** ([MountQueue](../../../../Database/MountQueue.cs) → `Workspace.Mount` →
`DatabaseManager.Open`), строго по одной базе:

1. Проба пути с ожиданием `MountQueue.PreMountProbeWait` (15 с): `File.Exists` + свежее
   read-only подключение + `SELECT 1`. Не ответила — монтирование не начинается, база под
   ретраями монитора. Проба идет на своей нити, а не в пуле потоков: нить, застрявшая в ядре на
   зависшей папке, просто остается стоять и не отнимает у пула рабочий поток, а занятый пул
   (старт с десятком баз, экспорт) не превращает здоровую папку в «не отвечает».
2. Признак `storage.shared` в файле → `IsShared`.
3. Схема: legacy-мост истории миграций; строка замка `__EFMigrationsLock` проверяется чтением,
   есть — удаляется (владелец мертв), удаление уперлось в BUSY — владелец жив и мигрирует на
   другом компьютере: монтирование прерывается с причиной «схему базы обновляет другой
   компьютер». `Migrate()` вызывается только при ожидающих миграциях (EF 9 ждет чужой замок
   бесконечно даже вхолостую). Тяжелая `SchemaCompact` идет своим возобновляемым конвейером с
   процентами в статусе базы.
4. Признак общей базы записывается, если его еще нет (одна запись на жизнь файла; отказ на
   файле только для чтения не мешает).
5. Журнал: читается текущий режим, меняется только при расхождении (смена требует эксклюзивного
   замка, а общую базу открывают десятки копий). Файл в WAL и его держит другое подключение →
   «файл в режиме WAL, его держит другой компьютер».
6. Профиль прагм, контроль прагм (`busy_timeout`, лимит WAL), регистрация текущего
   пользователя в `db_users`, уборка незавершенных переносов, индексация календаря, фоновые
   чистки. Сведения о файле (размер, свободно) снимаются здесь же.
7. Одна запись в журнал: «База «…» открыта за N мс: sqlite, сетевой путь …, журнал delete,
   файл …». Дольше минуты — предупреждение.

Сторож очереди следит за сигналами прогресса: тишина дольше `MountQueue.StallLimit` (5 мин)
— база помечается недоступной, очередь идет дальше; брошенное монтирование не прерывается
(операцию в ядре не отменить), а завершится позже — само подключит базу.

**Работа.** Чтения и записи идут через пул подключений Microsoft.Data.Sqlite к файлу;
каждая операция — транзакция, писатели сериализуются замком файла, читатели ждут писателя
до `busy_timeout`. Чужие правки подхватывает [ChangePoller](../../../../Database/ChangePoller.cs)
(`PRAGMA data_version` на постоянном read-only подключении, хвост `change_log`), конфликт
ячейки решается «последний побеждает», удаленные соседом строки отцепляются при сохранении
(подробно — [[multi-database]]). Открытие коллекции читает данные одним снимком в фоне
(`ReadOpenSnapshotAsync`), чтобы медленная папка не замораживала окно; страницы таблицы,
календарь и задачи читаются в фоне и раньше.

**Потеря и возврат.** [DbHealthMonitor](../../../../Database/DbHealthMonitor.cs) пробует
каждую недефолтную базу раз в 10 с; две неудачи подряд (или сигнал об ошибке из рабочего
кода) — база отцепляется, под именем «недоступна (связь потеряна / файл не найден) с 14:05 ·
переподключится сама», закрытие и сброс пула — в фоне. Соседи по серверу
(`NetworkPath.ServerRoot`: `\\server\share`, `P:\`) проверяются той же пачкой. Ретраи с бэкофом
5 → 15 → 60 с; файл вернулся — база встает в очередь и оживает, под именем на несколько секунд
«снова доступна». Записи в журнале: «потеряна» и «снова доступна через … (попытка N)».

**Перезагрузка сервера.** Пул держит хендлы, которые после перезагрузки мертвы; SQLite на
Windows отвечает на них `SQLITE_BUSY`, а не ошибкой ввода-вывода. Рабочий код сообщает о BUSY
общей базы (`DbErrors.ReportBusy`, поллер), монитор пробует файл свежим подключением: проба
прошла — сбрасывает пул (`AppDbContext.ResetPool`), запросы оживают; не прошла — база
объявляется потерянной без ожидания второй неудачи. Серия «BUSY, но проба прошла» пять раз за
десять минут означает, что сброс не лечит: файл держит другой процесс или компьютер — одно
предупреждение в журнале с подсказкой и надпись «занята другим компьютером» под именем базы,
снимается через две минуты тишины.

**Выход.** `App` освобождает `instance.lock` первым, затем `Workspace.CloseAll` закрывает базы
в фоне с общим бюджетом 15 с; не успевшие остаются системе — в режиме DELETE все
зафиксированное уже на диске, а закрытие хендла на зависшей папке не вернулось бы никогда.
Раньше это давало процесс без окна, который держал `exe` и `instance.lock`: обновление падало
«файл занят», повторный запуск молча выходил.

**Обновление программы.** Апдейтер ждет старый процесс минуту и при неудаче перезапускает
прежнюю версию с причиной (`--update-failed old-process|file-locked`), см.
[[../../guides/auto-update]]. Все пользователи общей базы должны работать на одной сборке:
сборки старше июля 2026 открывали файл в WAL всем без разбора.

## Файлы рядом с базой

| Файл | Кто создает | Что значит |
|---|---|---|
| `база.db` | программа | сам файл; заголовок хранит режим журнала |
| `база.db-journal` | SQLite в режиме DELETE | живет только на время транзакции записи и удаляется при коммите; остался лежать — кто-то оборвался посреди записи, следующий открывший откатит его сам («горячий журнал», нужен замок на файл) |
| `база.db-wal`, `база.db-shm` | SQLite в режиме WAL | **у общей базы их быть не должно**: кто-то открыл файл как локальный (старая сборка, сторонняя программа, копия с ошибкой определения пути) — пока он держит файл, остальные не переведут журнал в DELETE; после ухода зависшего клиента файлы могут остаться лежать, программа уберет их при следующем удачном переводе |
| `crossmove.pending.*` | программа | маркер незавершенного переноса между базами; частичная копия доудаляется при монтировании |
| копии `*.db` от «Резервное копирование» | программа | компактный консистентный снимок (`VACUUM INTO`), проходит `integrity_check` |

## Что может пойти не так и как это видно

| Симптом у пользователя | Причина | Что делает программа | В журнале диагностики |
|---|---|---|---|
| База «недоступна (файл не найден)» / «(связь потеряна)» | сервер выключен, папка отключена, файл переименован | ретраи с бэкофом, автоматический возврат | «База «…» потеряна (…)», «снова доступна через …» |
| После возврата сервера запросы падают «database is locked» | мертвые хендлы в пуле | сигнал BUSY → проба → сброс пула; сайдбар сам перечитывает базу через 4 с | «отвечала BUSY, свежая проба прошла — пул подключений сброшен» |
| «занята другим компьютером» под именем базы | файл держит чужой процесс дольше, чем лечит сброс пула | одно предупреждение, надпись, снятие через 2 мин тишины | «отвечала BUSY 5 раз за 10 мин — сброс пула не помогает…» |
| «недоступна (папка не отвечает)» | сервер не отвечает, но связь не рвет (перегрузка, зависший клиент с оплоком) | монтирование не начато или брошено по сторожу, очередь идет дальше | «не начато: папка не ответила за 15 с», «не продвигается 5 мин (этап …)» |
| «недоступна (файл в режиме WAL, его держит другой компьютер)» | рядом с файлом `-wal`/`-shm`, файл открыт кем-то в WAL | отказ с причиной, повтор через минуту | «файл в режиме wal, перевести в delete не удалось — файл держит другой компьютер» |
| «недоступна (схему базы обновляет другой компьютер)» | коллега с новой сборкой мигрирует файл | отказ с причиной, повтор через минуту | «замок миграций держит живой процесс — … монтирование отложено» |
| Открытие коллекции долгое, но окно живое | медленная папка | данные читаются в фоне одним снимком | «Медленно: чтение коллекции — N мс при пороге 2 000 мс» |
| Окно замирало на секунды | синхронное чтение с UI-потока (устранено для открытия коллекции) | сторож UI-потока пишет, что выполнялось | «Интерфейс не отвечал N с — выполнялось: …» |
| «база занята другим пользователем — изменение не сохранено» | чужой писатель держал замок дольше 15 с | карточка, сигнал монитору | «БД занята при записи» |
| После обновления «предыдущий процесс SmartBase не завершился» | старая копия стояла на операции к зависшей папке | апдейтер ждал минуту, версия прежняя, окно с причиной | «Обновление не применилось (old-process)» |
| В записи о монтировании «локальный путь P:\…» | путь определился как локальный (диск не восстановлен при автозапуске) | признак в файле все равно откроет базу как общую | «путь … определен как локальный, но файл помечен как общий — открываю как сетевую» |

## Проверка на боевой машине

На клиенте:

```powershell
net use                                                    # состояние подключенных дисков
Measure-Command { Copy-Item "P:\путь\база.db" $env:TEMP } # отвечает ли папка и как быстро
Get-ChildItem "P:\путь" -Filter "база.db*"                 # нет ли -wal / -shm / -journal
```

Диспетчер задач → «Подробности»: `SmartBase.exe` с несколькими МБ памяти, который не
снимается, — процесс, стоящий на операции к зависшей папке; он держит `exe` до тех пор, пока
Windows не отпустит операцию. Просмотр событий → Журналы приложений и служб → Microsoft →
Windows → SMBClient → Connectivity — обрывы связи с сервером по времени.

На сервере (PowerShell от администратора; на NAS — раздел открытых файлов в консоли):

```powershell
Get-SmbOpenFile | Where-Object Path -like "*.db*" | Select ClientComputerName, ClientUserName, Locks, Path
Get-SmbSession
```

Так видно, какой компьютер держит файл базы (и в WAL ли он), и можно закрыть сессию
выключенной или зависшей машины (`Close-SmbSession`, `Close-SmbOpenFile`).

В самой программе: «Настройки → Диагностика» — записи из таблицы выше, и запись о
монтировании каждой базы с путем и режимом журнала.

## Ограничения и рекомендации

- Качество байт-диапазонных блокировок зависит от сервера или NAS; DELETE-журнал и
  `synchronous=FULL` — максимум возможного для SQLite на шаре, при кривых прошивках порча под
  тяжелой конкуренцией все же возможна. Держите резервные копии (служба «Резервное копирование»
  умеет копировать общие базы по расписанию).
- Комфортный предел — единицы одновременных писателей. При большем — база на сервере
  PostgreSQL ([[../../guides/postgresql-setup]]): тот же интерфейс, конкуренцию разводит сервер.
- Массовые операции (импорт миллионов строк, своды) по сети заметно медленнее: удобнее делать
  локально и переносить коллекцию.
- Не открывайте файл общей базы сторонними программами (DB Browser и т. п.) во время работы
  коллег и не копируйте его на ходу средствами ОС: копия может быть неконсистентной, а открытое
  чужое подключение блокирует перевод журнала. Для копии есть «Резервная копия» в настройках.
- Все пользователи — на одной сборке; обновление раздается через ту же сетевую папку.
- Автозапуск при входе и сетевой диск: программа стартует раньше, чем Windows восстановит диск.
  Это учтено (см. выше), но первое монтирование общей базы после входа занимает до минуты —
  столько монитор ждет перед повтором после «файл не найден».

  `--check-pragmas` (профили журнала и прагм, конвертация WAL → DELETE «при переносе на шару»),
  `--contend` (два процесса в одну ячейку), `--writer` («второй пользователь» для живой
  проверки поллера), `--hold-write-lock` (карточка «занята»), `--load` (N писателей, M читателей,
  p50/p95/p99; запускается и на настоящей шаре, ключ `--journal` сравнивает режимы журнала).
- [SharedDbResilienceTests](../../../../Tests/Integration/SharedDbResilienceTests.cs) — фантомы
  трекера, пул отпускает файл, потеря проверяет соседей, поллер переживает BUSY.
- [MountResilienceTests](../../../../Tests/Integration/MountResilienceTests.cs) — признак общей
  базы в файле, живой и протухший замок миграций, файл в WAL у другого подключения, проба папки
  перед монтированием, закрытие с бюджетом.
- [PragmaTests](../../../../Tests/Integration/PragmaTests.cs) — профили прагм, лимит WAL.
- [NetworkPathTests](../../../../Tests/Unit/NetworkPathTests.cs) — классификация типа диска.
- Настоящую шару в тестах не поднять: файл открытого SQLite на Windows не удалить и не
  переименовать, поэтому потеря эмулируется `DbHealthMonitor.ProbeOverride`, а сетевой профиль —
  `NetworkPath.ForceNetwork`. Проверка `auto_vacuum` на настоящей папке — руками, см.
  [[../../testing/benchmarks]].

## Где в коде

| Класс | За что отвечает |
|---|---|
| [NetworkPath](../../../../Database/NetworkPath.cs) | сетевой ли путь, кеш, принудительные пометки, ключ сервера |
| [DatabaseManager](../../../../Database/DatabaseManager.cs) | монтирование: признак `storage.shared`, замок миграций, режим журнала, профиль прагм, запись о монтировании, «Сжать файл», `BackupTo` |
| [AppDbContext](../../../../Database/AppDbContext.cs) | прагмы на каждое открытие подключения по типу пути, `ResetPool`, чекпоинт WAL локальной базы |
| [MountQueue](../../../../Database/MountQueue.cs) | очередь по одной, проба перед монтированием, сторож зависания, статусы «недоступна (…)» |
| [Workspace](../../../../Database/Workspace.cs) | смонтированные базы, повтор после BUSY, причины отказа, `CloseAll` с бюджетом |
| [DbHealthMonitor](../../../../Database/DbHealthMonitor.cs) | пробы, потеря и возврат, соседи по серверу, сигнал BUSY, эскалация серии BUSY |
| [ChangePoller](../../../../Database/ChangePoller.cs) | чужие правки, переоткрытие наблюдения после серии BUSY |
| [DbErrors](../../../../Utils/DbErrors.cs) | классификация ошибок записи и чтения, сигналы монитору, карточки |
| [MountBlockedException](../../../../Database/MountBlockedException.cs) | причины отказа монтирования словами |
