# Мультибаза

## Назначение

Приложение умеет работать сразу с несколькими файлами БД: дефолтная плюс
подключенные пользователем (в т.ч. в сетевых папках). События календаря
агрегируются из всех, а CRUD маршрутизируется в нужный файл.

## Действующие лица

| Класс | Роль |
|---|---|
| [DatabaseRegistry](../../../../Database/DatabaseRegistry.cs) | реестр БД поверх app.db; гарантирует единственную **дефолтную** БД (ее нельзя удалить); `Add`/`Remove`/`GetAll` |
| [DatabaseManager](../../../../Database/DatabaseManager.cs) | одна **открытая** БД: контекст + репозитории + путь; миграции/WAL/сидинг при открытии; стабильный `DbId` из реестра |
| [Workspace](../../../../Database/Workspace.cs) | набор **смонтированных** БД: `Default`, `Mounted`, `Mount`/`Unmount`/`Get` (потокобезопасно: монтирует фоновая очередь, читает UI) |
| [MountQueue](../../../../Database/MountQueue.cs) | фоновая очередь монтирования: по одной, мелкие файлы первыми, живые статусы для заглушек |
| [EntityRef](../../../../Database/EntityRef.cs) | составной id `(DbId, Id)` — id уникальны только внутри своего файла |

## Как работает

Сплэш (`Workspace.Open`) монтирует **только дефолтную** БД (по актуальному пути
приложения, но с идентичностью из реестра) — старт всегда быстрый, сколько бы баз
ни было в реестре. Остальные после показа главного окна встают в
[MountQueue](../../../../Database/MountQueue.cs) и монтируются в фоне **строго по одной**
(параллельность умножила бы память кеша миграции и заставила бы сортировки драться
за диск), стартовая партия отсортирована по размеру файла — мелкие оживают почти
сразу. Пока база не готова, во всех сайдбарах видна ее заглушка: приглушенное имя
и статусная строка «в очереди…» → «Обновление · 45% · ≈ 2 мин» (короткая форма
тех же stage-фраз `DatabaseManager.Open`, живет от тех же колбэков) →
«недоступна (файл не найден)» красным при ошибке. Клик по заглушке — подсказка со
статусом; содержимое не строится, модули базу не видят до готовности. По завершении
`SyncMountedToUi` оживляет узел: календарь/задачи подхватывают данные. Сбой
монтирования одной БД **не роняет старт и не блокирует очередь** — она помечается
недоступной, в настройках доступно «Подключить заново» (встает в ту же очередь).

`Unmount` закрывает контекст; дефолтную размонтировать нельзя. Подключение новой
базы из настроек тоже идет через очередь (в хвост) — даже если сейчас мигрирует
другая база, UI не блокируется. Выход во время фоновой миграции безопасен:
транзакция откатится, брошенный `__EFMigrationsLock` снимется при следующем
открытии, миграция продолжится.

### Изоляция id

Локальные `Id` повторяются между файлами, поэтому в UI сущности адресуются парой
`(DbId, Id)` (`EntityRef`). У `CalendarRecord` для этого есть поле `DbId`.

## Многопользовательский режим (общая база в сетевой папке)

Один .db-файл могут одновременно открыть несколько пользователей с разных машин
(или несколько копий приложения — один локальный файл). Акторы:

| Класс | Роль |
|---|---|
| [NetworkPath](../../../../Database/NetworkPath.cs) | сетевой ли путь → журнал DELETE + консервативные прагмы (см. [databases](storage-and-migrations.md)); `ServerRoot` — ключ «сервера» (`\\server\share`, `P:\`) для группировки баз одной шары |
| [DbHealthMonitor](../../../../Database/DbHealthMonitor.cs) | пробы доступности (~10 с: `File.Exists` + read-only `SELECT 1`); потеря → размонтирование, надпись «недоступна…» у базы; фоновые ретраи с бэкофом 5→15→60 с и автоматический возврат базы; сигнал BUSY от сетевой базы (`ReportBusy`) → срочная проба и сброс пула подключений |
| [ChangePoller](../../../../Database/ChangePoller.cs) | чужие правки (~3 с; в фоне окна — 15 с): постоянное read-only подключение на БД (`busy_timeout` 2 с), `PRAGMA data_version` как дешевый детектор, хвост `change_log` после последнего виденного Id, свои правки отфильтрованы по `UserKey`; BUSY не сбрасывает курсор, три BUSY подряд переоткрывают соединение |
| [DbErrors](../../../../Utils/DbErrors.cs) | ошибки записи на действиях пользователя: BUSY → карточка «база занята, изменение не сохранено» + сигнал монитору; CANTOPEN/IOERR/NOTADB → карточка + сигнал монитору; `DbUpdateConcurrencyException` → карточка «изменил другой пользователь» |
| [AppNotifications](../../../../Controls/Widgets/AppNotifications.cs) | карточки сообщений в правом верхнем углу окна (стопкой, сами гаснут) — см. [[../../features/notifications]] |

Жизненный цикл потери: монитор (или ошибка в рабочем коде) фиксирует пропажу →
MainWindow отцепляет базу (`Workspace.Detach`; закрытие и сброс пула — в фоне, чтобы
ожидание чисток на мертвой папке не легло на UI-поток; запись реестра остается),
`MountQueue.MarkFailed` показывает заглушку в сайдбаре и настройках → монитор ретраит
путь → файл вернулся → база встает в очередь монтирования и оживает сама. Всплывашек
про доступность нет: вся хроника — надписью под именем базы, одной и той же во всех
трех сайдбарах и в «Управление базой данных» (`DbHealthMonitor.LostStatus`,
`MountQueue.UpdateFailedText`): «недоступна (связь потеряна) с 14:05 · переподключится
сама» → «… · повтор через ≈ 1 мин» → «… · проверяю…» → «в очереди…» → «подключается…»
→ узел оживает, на несколько секунд под ним «снова доступна». Не смонтированные при
старте базы (выключенный сервер) монитор подхватывает под те же ретраи.

**Перезагрузка сервера.** Два эффекта, которых по одной пробе не видно:

- **Мертвые хендлы в пуле.** Microsoft.Data.Sqlite держит открытые native-соединения в
  пуле по строке подключения и переиспользует их для каждого `new AppDbContext(path)` и
  каждого открытия соединения общего контекста. После перезагрузки сервера хендлы SMB
  недействительны, а SQLite на Windows при отказе `LockFileEx` отвечает **SQLITE_BUSY**, не
  IOERR: каждый запрос ждет `busy_timeout` и падает «database is locked», хотя сервер уже
  поднялся и свежее соединение работает; повторное монтирование брало из пула тот же
  хендл. Лечение — `AppDbContext.ResetPool(path)`: при размонтировании/потере
  (`Workspace.Release`), при BUSY на монтировании сетевого файла (`Workspace.Mount` —
  сброс и одна повторная попытка) и по сигналу `ReportBusy` от рабочего кода (DbErrors,
  поллер), если свежая проба монитора прошла. При штатной конкуренции сброс — лишь
  дешевое переоткрытие соединений.
- **Базы одного сервера пропадают вместе.** Потеря одной базы сразу пробует ее соседей
  по `NetworkPath.ServerRoot` (параллельно, до 5 с): упавшие объявляются той же пачкой,
  уцелевшим сбрасывается пул. MainWindow сливает пачку в одну пересборку сайдбаров
  (`RequestSyncMountedToUi`) уже без мертвых баз — иначе сайдбар читал бы соседние базы
  на UI-поток и ждал таймаут каждой. Сам сайдбар читает структуру базы один раз за
  `Refresh` и держит снимок (`MountedDb.Groups/Collections`): галочки, активные наборы и
  чистка ключей к базе не ходят.

Ожидание занятой базы: `busy_timeout` 15 с на сети / 10 с локально, и `CommandTimeout`
с `Default Timeout` подключения ему **равны** — Microsoft.Data.Sqlite после SQLITE_BUSY
повторяет шаг, пока не выйдет CommandTimeout, и с «чуть большим» значением ожидание
удваивалось (замер: 33 с до «database is locked»).

Синхронизация UI: структурные чужие правки (группы/коллекции/поля) перестраивают
сайдбары и открытую коллекцию; правки записей обновляют строки открытой коллекции
на месте (без пересборки колонок; пока открыт редактор ячейки — обновление
откладывается, ввод не затирается); видимый календарь/задачи перечитывают события.

Конфликты: **последний побеждает** — на уровне ячейки это атомарно
(`SetFieldValue`: гонка на первое значение конвертирует INSERT в UPDATE по
PK-конфликту). Строку, которую мы правим или удаляем, сосед мог уже удалить: токенов
конкурентности у модели нет, поэтому «затронуто 0 строк» означает ровно «строки нет», и
`AppDbContext.SaveReconcilingPhantomDeletes` отцепляет такие строки (и `Deleted`, и
`Modified`) и досохраняет остальное — воскрешать удаленное нельзя, а вставка новой записи
при сдвиге позиций удаленных соседей обязана доехать; о выброшенных правках человеку
сообщает хук `PhantomRowsDropped` (карточка), а поллер через пару секунд уберет удаленное
из UI. Кто и когда правил — видно в «Истории изменений» (`change_log`). ACID дает сам
SQLite: каждая операция — транзакция, писатели сериализуются файловым замком
(`busy_timeout` 15 с), частичных записей не бывает. Стенд: `Tests/MultiProcess`
(`--check-pragmas`, `--contend` — два процесса в одну ячейку, `--writer` — «второй
пользователь» для живой проверки, `--hold-write-lock` — проверка карточки «занята»,
`--load` — N писателей и M читателей одновременно со сводкой задержек p50/p95/p99;
см. [[../../testing/multi-process]]).

**Честные ограничения.** Качество байт-диапазонных блокировок SMB зависит от
сервера/NAS: DELETE-журнал + `synchronous=FULL` — максимум возможного для SQLite
на шаре, при кривых прошивках порча под тяжелой конкуренцией все же возможна —
держите бэкапы. Все пользователи общей базы должны работать на версии приложения
с этим изменением (смешение WAL/DELETE-открывателей конфликтует). Комфортный
предел — единицы одновременных писателей; при большем подключайте базу на сервере
PostgreSQL (см. ниже). Массовые операции (импорт миллионов строк) на шаре заметно
медленнее — удобнее импортировать локально и перенести коллекцию.

### Серверный провайдер PostgreSQL

Вторая ветка тех же действующих лиц: запись реестра с `Provider = "postgres"`
монтируется тем же `MountQueue`/`Workspace`, а `DatabaseManager.Open` вместо
файла открывает сервер. Канонический разбор ветки (один `AppDbContext` на оба
провайдера, lowercase-имена, отдельный набор миграций `Migrations/Pg`, пул,
переносы между провайдерами) — [storage-and-migrations.md](storage-and-migrations.md),
раздел «Провайдеры». Для мультибазы важно: у PG-записей нет файла — здоровье
проверяет та же служба `DbHealthMonitor`, но пробой `SELECT 1` вместо проверки
файла (недоступность — классы SqlState 08*/28*/57P0x, переполнение
`max_connections` 53300 — тоже «недоступна» с бэкоффом), а чужие изменения
`ChangePoller` ловит по `MAX(id)` журнала `change_log` вместо
`PRAGMA data_version`. Сервер разводит конкурентных писателей сам — ограничение
«единицы писателей» на PG-базы не распространяется.

### Обслуживание файла общей базы

Общая база при монтировании **не сжимается** (VACUUM через сеть под эксклюзивным замком
остановил бы всех); свободные страницы после удалений возвращает администратор кнопкой
«Сжать файл» в «Управлении базой данных» — база отцепляется, как при потере, VACUUM идет
через очередь монтирования (`MountQueue.RunMaintenance`, состояние `Maintenance`, надпись
«сжимаю файл · 45 % · ≈ 2 мин» в сайдбарах и настройках), затем база монтируется обратно;
занятый чужим писателем файл — карточка и возврат без сжатия. «Резервная копия…» —
`VACUUM INTO`, без отключения. Политика и цифры — [[storage-and-migrations]]
(«Свободное место, сжатие, WAL»).

## Где это видно в фичах

- **Календарь** ([CalendarControllerView](../../../../Views/ConstructorDb/Calendar/CalendarControllerView.axaml.cs)):
  `RefreshCurrent()` собирает события из всех смонтированных БД, помечает каждое
  `DbId` и фильтрует по активным коллекциям этой БД. CRUD идет в БД события
  (`RepoOf(record)`); выбор целевой БД встроен в окно записи
  ([RecordDialog](../../../../Controls/Dialogs/RecordDialog.axaml.cs)) — комбобокс «База данных»
  при нескольких смонтированных БД (при изменении — перенос записи в другую базу).
- **Конструктор** ([ConstructorControllerView](../../../../Views/ConstructorDb/ConstructorControllerView.axaml.cs)):
  в основной области открыта одна коллекция, поэтому держится один активный
  репозиторий; `OpenFrom(repo, collectionId)` переключает БД, `DetachDatabase` —
  при размонтировании текущей.

Управление списком БД — в настройках («Управление базой данных»), см.
[../features/settings.md](../../features/settings.md).

Функциональность вводилась поэтапно (см. комментарии в коде «Этап 3/5» и

сделаны, обработка недоступности и статусов закрыта многопользовательским режимом
(July 2026: `MountQueue` + `DbHealthMonitor` + `ChangePoller`, см. выше).
