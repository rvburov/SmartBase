# Хранилище, миграции, пути

## Назначение

Как и где физически лежат данные, как обновляется схема без потери данных и как
читаются/пишутся настройки.

## Что лежит в папке данных

Полный состав `AppSettings.AppDataDir`: пять баз SQLite и три служебных файла. Ничего
из этого не появляется «само» — у каждого файла есть конкретное место в коде, которое
его создает.

### Базы SQLite

| Файл | Контекст | Что внутри |
|---|---|---|
| `database.db` | [AppDbContext](../../../../Database/AppDbContext.cs) | пользовательские данные (коллекции, поля, записи, события календаря) |
| `app.db` | [SystemDbContext](../../../../Database/SystemDbContext.cs) | системное: реестр БД (`databases`) + настройки (`app_settings`) |
| `logs.db` | [AppLog](../../../../Logging/AppLog.cs) | диагностический лог Serilog для «Настройки → Диагностика»; автоочистка записей старше 30 дней — [features/logging.md](../../features/logging.md) |
| `integrations.db` | [RunJournal](../../../../Database/RunJournal.cs) | журнал запусков обмена: что дергали, чем кончилось, сколько строк и байт. По нему же считаются накопительные квоты политики; уборка — последние 20 000 строк. Секрета в нем нет ни при каких настройках — [features/integrations/overview.md](../../features/integrations/overview.md) |
| `security.db` | [SecurityJournal](../../../../Database/SecurityJournal.cs) | журнал безопасности: попытки отправки — и разрешенные, и заблокированные, — подтверждения направлений, понижения меток, ручной экспорт, копирование ячеек таблицы в буфер обмена. Только добавление, каждая строка включает хэш предыдущей; пользователь его не чистит. Ни секретов, ни значений полей: адрес замаскирован, тело — одним SHA-256 — [features/integrations/overview.md](../../features/integrations/overview.md) |

`app.db` — независимое хранилище: никогда не показывается в сайдбаре и не удаляется.

`integrations.db` и `security.db` лежат здесь, а не внутри файла базы, намеренно: файл базы ездит
по сетевой папке и открыт на нескольких машинах разом, а числа обмена и следы отправок раздули бы
его у всех сразу. Оба журнала общие на все базы — один запуск задевает несколько, и ключ базы
пишется полем строки.

Рядом с каждой открытой базой SQLite держит `*.db-wal` и `*.db-shm` — это штатный режим
WAL, вручную их удалять не нужно.

### Служебные файлы

| Файл | Кто создает | Когда появляется | Размер |
|---|---|---|---|
| `instance.lock` | [SingleInstance.TryAcquire](../../../../Utils/SingleInstance.cs) | при каждом запуске в App-режиме | 0 байт |
| `show.signal` | [SingleInstance.SignalShow](../../../../Utils/SingleInstance.cs) | только когда вторую копию запускают поверх работающей | 18 байт |
| `crash.log` | [Program.LogCrash](../../../../Program.cs) | только при необработанном исключении | растет дозаписью |

Все три **остаются на диске после выхода из приложения** — это норма, а не мусор:

- `instance.lock` защищает от второго экземпляра **эксклюзивным дескриптором**
  (`FileShare.None`), а не фактом наличия файла: `Dispose()` отпускает дескриптор, файл
  остается лежать. Пустой, потому что внутрь ничего не пишется. Зачем нужен —
  [features/autostart-background.md](../../features/autostart-background.md).
- `show.signal` хранит `DateTime.UtcNow.Ticks`. Работающий экземпляр ловит и `Created`,
  и `Changed`, поэтому удалять файл между запусками не требуется — перезапись
  срабатывает не хуже создания.
- `crash.log` пишется **синхронно** в момент падения и намеренно дублирует Fatal-запись
  в `logs.db`: он работает, даже если Serilog еще не поднялся. Внимание при сверке:
  время в нем **локальное**, а в `logs.db` — UTC, поэтому одно и то же падение выглядит
  как `00:15` и `21:15`. Подробнее — [features/logging.md](../../features/logging.md).

### Осиротевшие `.db` вне папки данных

Отключение базы в «Настройки → Управление базой данных» удаляет только строку реестра —
**файл на диске остается** (диалог подтверждения прямо это обещает). После экспериментов
может остаться пустой `имя.db` в произвольной папке, в том числе в корне репозитория:
0 байт, потому что схема создается при монтировании, а до него база не дошла. На работу
не влияет, удаляется руками. См. [multi-database.md](multi-database.md).

## Пути ([AppSettings](../../../../Utils/AppSettings.cs))

- **Release:** `%AppData%\SmartBase\` (Windows; `%AppData%` — это уже
  `C:\Users\<Имя>\AppData\Roaming`); `~/.config/SmartBase/` (Linux —
  .NET `ApplicationData` = XDG_CONFIG_HOME); `~/Library/Application Support/SmartBase/`
  (macOS — там `ApplicationData` указывает на нативную папку Apple, а не на `~/.config`).
- **Debug:** папка `.localdata/` в корне проекта (находится по маркеру
  `SmartBase.csproj`) — изолированно «как venv», переживает `dotnet clean` и снос
  `artifacts/`.

`database.db` → `AppSettings.DbPath`, `app.db` → `AppSettings.SystemDbPath`,
`integrations.db` → `AppSettings.RunJournalPath`, `security.db` →
`AppSettings.SecurityJournalPath`; `logs.db` и
все служебные файлы — прямо в `AppSettings.AppDataDir`.

## Миграции схемы (database.db)

Накатываются автоматически при открытии каждой БД в
[DatabaseManager](../../../../Database/DatabaseManager.cs) (`ApplySchemaMigrations`):

- **Новый файл** — `Migrate()` создает БД и применяет все миграции по порядку.
- **Старый файл из времен `EnsureCreated()`** (нет таблицы `__EFMigrationsHistory`,
  но есть `db_records`) — вручную создается таблица истории и `InitialCreate`
  помечается как уже примененная, после чего `Migrate()` накатывает только
  недостающие миграции. Так схема обновляется, **не пересоздавая** существующие данные.

Новые правки сущностей → `dotnet ef migrations add ...` → применятся при следующем
запуске. См. также [ROADMAP.md](../../../ROADMAP.md) и инструменты EF в гайде разработчика.

Перед `Migrate()` снимается протухший замок `__EFMigrationsLock`
(`ClearStaleMigrationsLock`): EF 9 держит строку-замок на время миграции, и убитый
посреди нее процесс оставляет замок навсегда — без очистки следующий запуск висел бы
вечно. Живого мигратора очистка не задевает: он держит файловый write-замок SQLite,
и чужой `DELETE` честно ждет/падает по `busy_timeout`.

Когда есть ожидающие миграции, перед `Migrate()` разово поднимаются кеш и mmap
(`AppDbContext.ApplyMigrationPragmas`) — table-rebuild миграции на дефолтном кеше
SQLite ~2 МБ шли часами вместо минут; после наката файл ужимается
(`CompactWithProgress`: пересоздания оставляют свободные страницы ниже порога
планового самолечения).

**Тяжелая SchemaCompact — возобновляемая** (партиал
[DatabaseManager.SchemaCompact.cs](../../../../Database/DatabaseManager.SchemaCompact.cs)):
EF выполняет миграцию одной транзакцией, и на больших базах (16 ГБ — десятки минут)
выключение программы откатывало все — обновление могло не завершиться никогда.
Перекладка идет порциями ~200 тыс. строк с коммитом каждой: выключение в любой
момент теряет максимум последнюю порцию, при следующем запуске процент СРАЗУ
продолжается с места остановки (точка возобновления — хвост новой таблицы по PK,
счетчики в `db_meta` `compact.*`). Конечное состояние задает файл миграции
(движок обязан ему следовать!), по завершении миграция помечается примененной в
`__EFMigrationsHistory` (паттерн моста InitialCreate). Финальное сжатие — по флагу
`db_meta compact.vacuum`: VACUUM неделим, но флаг переживает выключение — при
следующем запуске повторится только сжатие. Проверено kill-тестом на стенде
(1,6 ГБ / 12,7 млн значений, убийства на 20/50/80%: продолжение с точного места,
данные сходятся до строки; полный прогон ~50 с — паритет с одной транзакцией).
MainWindow при выходе во время обновления показывает подтверждение с напоминанием,
что прогресс сохранен. Все долгие этапы старта — разовая миграция, VACUUM,
бэкафилл календаря — репортятся через `stage`-колбэк `DatabaseManager.Open`
с живым процентом (гибрид VM-шагов SQLite и прироста журнала, см.
`SqliteStageProgress`) и оценкой времени во второй строке («Обновление «имя»» /
«Сжимаю файл «имя»» + «осталось ≈ N мин») — застывший индикатор неотличим
от зависания, поэтому этапов без движения быть не должно. Потребители колбэка:
сплэш (только дефолтная БД) и статусные строки заглушек в сайдбаре — остальные
базы мигрируют в фоновой очереди [MountQueue](../../../../Database/MountQueue.cs)
уже после показа окна (см. [multi-database](multi-database.md)), пользователь
ожидания на критическом пути не видит.

> **Правило:** любая миграция должна сохранять данные — никаких затертых строк.
> Пересоздание таблицы допустимо только с полной перекладкой данных
> (`CREATE … → INSERT … SELECT → DROP → RENAME`, так SQLite меняет PK; пример —
> `SchemaCompact`: слияние трех таблиц колонок в `column_meta` и перевод
> `db_field_values`/`calendar_index` на `WITHOUT ROWID`). Для app.db — только
> аддитивно (`CREATE TABLE IF NOT EXISTS` / `ALTER ADD`).

> **Правило дешевых миграций.** Изменения схемы бывают двух классов, и по умолчанию
> разрешен только первый:
> - **дешевые** — новая таблица, новая колонка (`ADD COLUMN`), новый индекс:
>   выполняются мгновенно или быстро на базе любого размера, пользователь ничего
>   не замечает;
> - **дорогие** — table-rebuild (перекладка всех строк существующей таблицы):
>   на больших базах это минуты ожидания у пользователя при первом запуске.
>
> Дорогая миграция — исключение, и она обязана: иметь письменное обоснование в
> шапке файла миграции; читать источник последовательно (`NOT INDEXED` + внешняя
> сортировка, не по индексу); полагаться на `ApplyMigrationPragmas` (кеш/mmap
> ставятся до `Migrate()`); репортить этап и живой процент на сплэш (рост WAL,
> `StartMigrationProgressReporter`); быть замеренной на большой базе до релиза
> (эталон: `SchemaCompact` — 12,7 млн значений / 1,6 ГБ ≈ 53 с вместе с VACUUM).
>
> `AddCalendarDayCounts` (сводка дней календаря, этап 8 плана drawn-grid.md) — дешевая по
> классу (новая таблица и триггеры), но ее первое заполнение читает всю проекцию календаря
> одним `GROUP BY`: 10 млн событий — 13,4 с при первом подключении базы (замер стенда
> `Tests/Sections`), база в сотни событий — мгновенно. Обоснование — в шапке файла миграции.
>
> `AddCalendarSpans` (сводка длительностей календаря) — тоже новая таблица и триггеры; первое
> заполнение — один проход по покрывающему индексу проекции: 10 млн событий — 7 с при первом
> подключении базы, обычная база — мгновенно.
>
> `RepairRecordPositions` (только SQLite) чинит номера записей за пределами int, которые
> оставляли прежняя перенумерация коллекции («ранг × 1000») и сдвиг хвоста при массовом дубле
> на коллекциях больше 2,1 млн записей: такие записи не читались (переполнение при чтении).
> Проверка — по индексу `(CollectionId, Position)`, мгновенно; затронутые коллекции получают
> номера по прежнему порядку. Испорченная коллекция в 9,2 млн записей — 110 с один раз под
> сплэшем, целая база — мгновенно. В PostgreSQL столбец int4 — туда такие номера не попадали.

## Гарантии ACID

Базовые гарантии дает сам SQLite, приложение их не ослабляет, а в ключевых местах —
усиливает. По буквам, с привязкой к коду:

- **A — атомарность.** Каждая запись — транзакция: `SaveChanges` EF атомарен, составные
  операции идут через явный `BeginTransaction` (репозитории), убитый процесс откатывается
  журналом SQLite — «полузаписанных» данных не бывает. Возобновляемая миграция — цепочка
  атомарных порций (см. ниже), финальная подмена таблиц — одна короткая транзакция.
  Известное исключение: перенос коллекции МЕЖДУ базами (`MoveCollectionIsolated`) — два
  файла, общей транзакции нет (WAL не атомарен между БД): копия и удаление разделены,
  при сбое удаления копия откатывается компенсацией.
- **C — согласованность.** Внешние ключи с `ON DELETE CASCADE` включаются на каждом
  подключении (`foreign_keys=ON`, ApplyPerformancePragmas) — осиротевших значений/полей
  не остается; PK и уникальные индексы (естественный ключ `(RecordId, FieldId)` и др.)
  проверяет SQLite. `PRAGMA integrity_check` = ok подтвержден стендами после миграций и
  конкурентных прогонов.
- **I — изоляция.** SQLite сериализует писателей файловым замком: два пользователя
  никогда не пишут одновременно, второй ждет (`busy_timeout` 10 с локально / 15 с на
  сети), читатели в WAL видят консистентный снимок. Гонки уровня «прочитал-изменил»
  между процессами закрыты в горячей точке (`SetFieldValue`: PK-конфликт → UPDATE,
  удаленное не воскрешается) — политика «последний побеждает», см.
  [multi-database](multi-database.md).
- **D — долговечность.** Локально — `synchronous=NORMAL` + WAL: коммит переживает крах
  приложения всегда; при внезапном отключении питания возможна потеря последних
  мгновений работы, но НЕ порча файла. На сетевых путях (общая база) — `synchronous=FULL`:
  каждый коммит дожидается диска сервера, окно потери закрыто ценой скорости.

Проверено стендом `Tests/MultiUserHarness --contend`: два процесса, 12 тыс.+ записей в
одну ячейку без падений, файл цел; kill-тесты миграции — данные сходятся до строки.

## Режимы журнала: WAL локально, DELETE на сетевых путях

Сводная картина работы с сетевыми папками (определение пути, отличия общей базы, жизненный
цикл, файлы рядом с базой, симптомы) — [network-shares.md](network-shares.md); здесь —
режимы журнала и прагмы.

Локальные БД работают в `PRAGMA journal_mode=WAL` — параллельные чтения во время
записи и быстрые коммиты (рядом с файлом появляются `*.db-wal` / `*.db-shm`).

Файлы на **сетевых путях** ([NetworkPath](../../../../Database/NetworkPath.cs): UNC/сетевой
диск на Windows, `/Volumes/…` на macOS, cifs/nfs/sshfs по `/proc/mounts` на Linux;
сомнение трактуется как «сеть») открываются в `journal_mode=DELETE`. Важно: SQLite
**не** отказывается ставить WAL на SMB/NFS — он ставится, но когерентность разделяемой
памяти `-shm` между машинами молча ломается, и одновременная работа с разных
компьютеров портит файл. Поэтому `DatabaseManager.ApplyJournalMode` активно
конвертирует журнал по типу пути (созданный локально файл несет WAL в заголовке —
первое открытие с шары переводит его в DELETE; если WAL держит старая версия
приложения — монтирование честно падает со статусом «недоступна»).

Профиль прагм тоже ветвится по типу пути внутри `AppDbContext.ApplyPerformancePragmas`
(все фоновые `new AppDbContext(path)` получают его автоматически): на сети —
`busy_timeout=15000`, `synchronous=FULL` (NORMAL в rollback-режиме рискует файлом при
сбое питания сервера), `mmap_size=0` (mmap поверх сетевой ФС не рекомендован SQLite).
`CommandTimeout` EF и `Default Timeout` строки подключения равны `busy_timeout` (15/10 с):
Microsoft.Data.Sqlite после SQLITE_BUSY повторяет шаг, пока не выйдет CommandTimeout, а
каждый шаг сам ждет полный `busy_timeout` внутри SQLite — «чуть большее» значение давало
два цикла ожидания (замер: 33 с до «database is locked» при чужом `BEGIN IMMEDIATE`).
Режим журнала при монтировании сначала читается и меняется только при расхождении:
смена требует эксклюзивного замка, а общую базу открывают десятки копий приложения.
Пул подключений Microsoft.Data.Sqlite к сетевому файлу сбрасывается при размонтировании и
по сигналу BUSY (`AppDbContext.ResetPool`) — после перезагрузки сервера хендлы в пуле
мертвы, и SQLite отвечает на них BUSY (подробно — [[multi-database]]).
Проверяется стендом `Tests/MultiUserHarness --check-pragmas`. Про совместную работу
нескольких пользователей — [multi-database](multi-database.md).

**Определение по пути ненадежно само по себе — признак живет в файле.** Для буквы диска
`NetworkPath` спрашивает у Windows тип диска; пока подключенный диск `P:` еще не восстановлен
после входа в систему (автозапуск стартует раньше), ответ — `NoRootDirectory`, и прежняя
логика считала путь локальным, кешировала это на весь сеанс и при следующем монтировании
переводила общий файл в WAL: рядом появлялись `-wal`/`-shm`, остальные копии не могли взять
эксклюзив для обратного перевода («не удалось смонтировать», шторм BUSY), а закрытие
разделяемой памяти через SMB вешало процесс при выходе. Теперь:

- `NetworkPath.ClassifyDrive` (чистая, под юнит-тестом): `Network` — сеть; `Fixed`/`Removable`/
  `CDRom`/`Ram` — не сеть; `NoRootDirectory`/`Unknown` — сеть, причем уверенно, если буква
  числится в постоянных подключениях пользователя (`HKCU\Network\<буква>`), иначе — сеть «до
  выяснения» **без кеша**: ответ переспрашивается, когда диск появится.
- `DatabaseManager` при монтировании по сетевому пути ставит в `db_meta` признак
  `storage.shared = 1` (одна запись на жизнь файла; отказ на файле только для чтения не мешает),
  а ДО открытия контекста читает его сырым read-only подключением: признак есть, а путь
  «локальный» → `NetworkPath.ForceNetwork(path)`, база открывается как общая (DELETE, сетевой
  профиль прагм, сигналы BUSY монитору) с предупреждением в журнале. Никакая ошибка определения
  больше не переведет общий файл в WAL. Тест —
  [MountResilienceTests](../../../../Tests/Integration/MountResilienceTests.cs).
- Файл общей базы уже в WAL и его держит другое подключение (копия со старой сборкой, сторонняя
  программа): `PRAGMA journal_mode=DELETE` падает BUSY → `MountBlockedException` с причиной
  «файл в режиме WAL, его держит другой компьютер» вместо «не удалось открыть»; монитор
  повторит через минуту.

**Замок миграций EF (`__EFMigrationsLock`).** `Migrate()` вставляет строку на время работы и
ждет чужую строку **бесконечно** — проверено на EF 9.0.1, даже когда ожидающих миграций нет.
Поэтому: (1) при пустом списке ожидающих миграций `Migrate()` не вызывается вовсе (заодно минус
две записи в общий файл на каждое монтирование каждым пользователем); (2) перед миграцией строка
замка проверяется чтением и, если есть, удаляется — владелец мертв (убитый посреди миграции
процесс); удаление уперлось в BUSY — владелец жив и прямо сейчас мигрирует на другом компьютере,
монтирование прерывается с причиной «схему базы обновляет другой компьютер» (раньше — тихое
вечное «подключается…» с нулевой загрузкой). Кража замка у живого мигратора возможна лишь в паузе
между его вставкой строки и первой записью — тогда одна из миграций упадет с ошибкой DDL без
порчи данных, что несравнимо лучше зависания.

## Свободное место, сжатие, WAL

Из чего складывается размер файла и почему он «раздувается» — на примере свода
трудоемкости (650 тыс. строк × 6 свойств): один такой свод — около 800 байт на запись
(замер `bloat`, см. ниже), то есть ~0,5 ГБ, а каждый прогон расширения создает НОВУЮ
коллекцию. Три свода в одном файле — уже 1,5 ГБ, и удаление старых само по себе файл не
уменьшает: SQLite без `auto_vacuum` складывает освобожденные страницы в freelist и
переиспользует их только под новые данные. Внутри записи байты делятся так (стенд
10 млн записей, `dbsize`): `db_records` с аудитом (две даты ISO «o» по 33 символа, два
снимка имени) — до трети файла; `db_field_values` и ее индекс `(FieldId, Value)` —
поровну, потому что индекс **дублирует каждое значение целиком**; проекция календаря с
четырьмя индексами — еще столько же, сколько значения, у коллекций с видимой датой.

**Политика свободных страниц** ([DatabaseManager](../../../../Database/DatabaseManager.cs),
`NeedsCompaction`): файл стоит сжать, когда свободно больше 64 МБ И (не меньше четверти
файла ИЛИ больше 512 МБ). Прежний порог «> 50 %» ровно в типичном случае «залил заново,
старое удалил» не срабатывал никогда.

- **Локальная база** ужимается сама при монтировании (`VACUUM` с этапом «Сжимаю файл» и
  живым процентом на сплэше/в заглушке сайдбара) — как и раньше, только по новому порогу и
  если живых данных не больше 4 ГБ (`DatabaseManager.AutoCompactMaxLiveBytes`). Сжатие
  переписывает живые данные целиком, и база все это время недоступна: база 31 ГБ после
  удаления столбца на 10 млн записей (свободно 0,7 ГБ, 2 %) сжималась при подключении больше
  10 минут. Большой базе — подсказка «стоит сжать» и кнопка «Сжать файл», в журнал — одна
  запись за сеанс, почему база сама не сжата.
- **Места на диске для сжатия** нужно еще два объема живых данных: копия во временном файле и
  та же копия в журнале базы (`DatabaseManager.CompactRoomProblem`). Не хватает — сжатие при
  монтировании пропускается с предупреждением в журнале, а «Сжать файл» сразу говорит, сколько
  нужно и сколько свободно, не отключая базу. Копию `VACUUM` строит на диске
  (`temp_store=FILE` на время сжатия): на подключениях программы `temp_store=MEMORY`, и сжатие
  держало бы в памяти копию всей базы — процесс рос на гигабайты.
- **Общая база (сетевой путь) при монтировании не сжимается никогда.** `VACUUM`
  переписывает весь файл через сеть под эксклюзивным замком: первый смонтировавший
  заставил бы остальных двадцать человек минуты смотреть на «database is locked». Вместо
  этого в «Управление базой данных» у каждой SQLite-базы третья строка — «размер файла 1,7 ГБ ·
  свободно 1,1 ГБ (64 %) — стоит сжать» (снимок `DatabaseManager.Storage`, снятый при
  монтировании: с UI-потока в файл не ходим) и кнопка **«Сжать файл»** для администратора
  базы. Она отцепляет базу от рабочего пространства (как при потере), ведет `VACUUM`
  через очередь монтирования (`MountQueue.RunMaintenance`, состояние `Maintenance`,
  надпись «сжимаю файл · 45 % · ≈ 2 мин» в сайдбаре и настройках) и монтирует базу обратно;
  занятый файл (чужой писатель) — карточка «файл занят другими пользователями», база
  возвращается без сжатия. `DatabaseManager.CompactFile` — сама операция на свежем
  подключении.
- **Резервная копия** — `VACUUM INTO` в файл-цель (`DatabaseManager.BackupTo`):
  компактная консистентная копия на момент начала, писателей не блокирует, базу не
  отключает; после копирования — `integrity_check` копии. Это и страховка, и способ
  получить компактный файл общей базы, когда `VACUUM` на месте нежелателен. Зовет ее
  служба раздела «Настройки → Резервное копирование» — по расписанию и кнопкой
  «Копировать сейчас» (см. [features/backup.md](../../features/backup.md)).
- Сжатие после миграций (флаг `compact.vacuum`) остается на обеих: миграция и так
  держит файл.
- **Перед любым `VACUUM` пул подключений к файлу закрывается** (`AppDbContext.ResetPool`
  внутри `DatabaseManager.Vacuum`). Причина — Windows: физически усекает файл чекпоинт
  после VACUUM, а `SetEndOfFile` молча не срабатывает, пока файл отображен в память любым
  другим открытым подключением — в том числе простаивающим в пуле Microsoft.Data.Sqlite (наш
  профиль ставит `mmap_size` на каждое подключение, отображение живет до закрытия). Без
  сброса пула получалось «freelist пуст, `page_count` меньше, а файл на диске прежний —
  навсегда» (опыт: 39 МБ вместо 20 даже после закрытия всех подключений). Свое отображение
  VACUUM снимает сам; на сетевом пути mmap выключен. Занятые прямо сейчас подключения сброс
  не трогает — поэтому «Сжать файл» сначала отцепляет базу, а монтирование сжимает до того,
  как база отдана модулям.

**Пустые ячейки не хранятся.** Импорт таблиц (`WriteRowsBatched`), свод (`BulkAddRecords`)
и очистка ячейки (`SetFieldValue` с пустым значением удаляет строку) держат инвариант
«нет строки = пусто» — так читают страницы, счетчики фильтра и экспорт. На импорте с
редкими колонками пустые ячейки были десятками процентов таблицы значений и ее индекса.

**WAL локальной базы ограничен.** На каждом подключении ставится
`journal_size_limit = 64 МБ` (`AppDbContext.WalSizeLimitBytes`): SQLite после чекпоинта не
усекает `-wal`, а переиспользует, и после свода на 600 тыс. строк рядом с базой лежали
сотни мегабайт журнала. На сетевом пути журнал DELETE, лимит не ставится.

**Журнал переносит в файл фоновая задача, а не коммит.** Автоперенос SQLite
(`wal_autocheckpoint`) выключен на всех подключениях программы к локальным базам: он идет внутри
коммита той правки, которой выпало перевалить порог, — после дубля столбца на 100 тыс. записей
(журнал 400 МБ) его сделала мелкая правка интерфейса, 17 с на UI-потоке, а сами массовые правки
ждали в окне прогресса перенос, который занимает 80 % их времени (замер на коллекции в 1000
свойств: дубль столбца на 20 тыс. записей — 0,5 с работы, 0,3 с коммита и 3 с переноса 80 МБ
журнала). Журнал переносит [`WalCheckpointer`](../../../../Database/WalCheckpointer.cs):
- после массовых правок — закрытие их контекста (`AppDbContext.Dispose` у массового профиля и у
  `DeferCheckpoint`: столбцы, диапазоны ячеек) ставит перенос, когда правка уже закоммичена и видна;
- по размеру журнала — у открытых баз (`DatabaseManager` включает `Watch`, закрытие — `Unwatch`)
  раз в секунду: журнал больше `journal_size_limit` (64 МБ) — перенести. Порог во весь
  дозволенный размер журнала — прежнее окно массового профиля: повторные правки одной страницы
  схлопываются в журнале и переносятся однажды (перенос после каждого пакета давал на удалении
  коллекции в 650 тыс. записей ~5-6 ГБ физической записи на 0,5 ГБ данных).

Перенос — `wal_checkpoint(PASSIVE)` на отдельном соединении вне пула (закрытая база не остается
открытой): не ждет читателей и не мешает писателям, повторяется, пока журнал не перенесен целиком;
чужой автоперенос его бы не дублировал — SQLite пропускает перенос, если он уже занят. Долгий
перенос пишется в «Диагностику» как «перенос журнала базы» (порог фоновой работы, 5 с).
Транзакционных гарантий это не меняет — только момент и поток переноса. Столбец больше 500 тыс.
значений (дубль, удаление) коммитится порциями: одна транзакция держала бы в журнале страницы всей
таблицы до конца операции — на 10 млн записей десятки гигабайт рядом с базой. Между порциями
операция сама переносит журнал (PASSIVE): за непрерывной записью фоновый перенос не успевает, и
журнал рос бы дальше порции.

Перенос после массовой правки начинается через 3 с (`WalCheckpointer.Schedule` с отсрочкой;
проверка по размеру журнала раньше срока его тоже не начинает). Перенос гигабайта журнала
занимает диск целиком, и любое чтение ждет его: опыт на отдельной базе — чтение нового
подключения до 2 с (без сброса файла на диск — 0,9 с), на базе 31 ГБ перечитывание колонок
после удаления столбца ждало на UI-потоке 7 с. За отсрочку интерфейс перечитывает колонки и
первые строки, пока диск свободен. Замков перенос не держит: читатель с нулевым ожиданием
замка во время переноса ни разу не получил «database is locked».

**`auto_vacuum=INCREMENTAL` — не включен.** Стенд `bloat` показал, что накладные на
вставку и объем у него незаметны, а `incremental_vacuum` возвращает место порциями без
эксклюзива на минуты — это привлекательно для общей базы. Но включение требует
`VACUUM` каждого существующего файла (то есть того же ручного сжатия), а после него
страницы, освобожденные удалением, все равно возвращаются только явным
`incremental_vacuum`. Решение отложено до замеров на настоящей сетевой папке: пока
общая база сжимается кнопкой, локальная — сама. Как снять замер и по каким порогам решать — [testing/benchmarks.md → «Проверка INCREMENTAL на сетевой папке»](../../testing/benchmarks.md#проверка-auto_vacuumincremental-на-сетевой-папке).

**Диагностика.** `dotnet run -c Release --project Tests/Benchmarks -- dbsize --db PATH`
открывает файл только для чтения (годится для настоящей базы на сетевой папке во время
работы людей) и печатает: размер, живые данные, свободные страницы, накладные
B-деревьев, объем каждой таблицы и индекса, разрез по коллекциям (байт на запись) и по
полям (байт, средняя/максимальная длина, доля длинных значений, уникальных — потенциал
словарного сжатия). `bloat` прогоняет сценарий «свод → второй свод → удаление → правки →
заливка при открытом читателе → VACUUM» и печатает таблицу размеров по шагам
(см. [testing/benchmarks.md](../../testing/benchmarks.md)).

**Что дальше (по замеру `dbsize` на реальном файле, отдельным решением):** частичный
индекс значений без длинных строк (`WHERE length(Value) <= 120` + узкий индекс по
`FieldId`) — если длинные значения держат заметную долю индекса; словарь значений
(`ValueId` вместо строки) — максимальный выигрыш на повторяющихся ФИО/проектах/путях, но
перестройка самой большой таблицы и правка raw SQL репозитория — отдельный трек.

## Объем кеша и mmap

`cache_size` и `mmap_size` считаются от **памяти машины**
(`GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`), а не константами, как было раньше:

| | обычный профиль | массовый профиль |
|---|---|---|
| доля памяти под кеш | 1/512, потолок 64 МБ, пол 16 МБ | 1/64, потолок 512 МБ, пол 64 МБ |
| доля памяти под mmap | 1/128, потолок 256 МБ, пол 64 МБ | 1/16, потолок 2 ГБ, пол 256 МБ |
| на машине с 32 ГБ и выше | 64 МБ / 256 МБ (потолки) | 512 МБ / 2 ГБ (потолки) |
| на машине с 8 ГБ | 16 МБ / 64 МБ | 128 МБ / 512 МБ |

Потолки равны прежним константам, поэтому на рабочей станции поведение прежнее. Ровно
в потолок машина упирается, когда ОС отчиталась о полных 32 ГиБ: реальный отчет бывает
на проценты ниже номинала (память прошивки и ядра), и тогда значения отличаются на те же
проценты. Смысл шкалы — слабая машина: подключений в сеансе не одно (свое у каждой
смонтированной базы, у поллера на каждую базу, у каждой фоновой операции), и на ноутбуке
с 8 ГБ, где память занята на три четверти, фиксированные сотни мегабайт под кеш
выталкивали процесс в своп. Замер удаления коллекции на 650 тыс. записей: пик 1,67 ГБ у
SQLite против 145 МБ у PostgreSQL, который те же данные удаляет на сервере.

Страницы `mmap` — чистые файловые, ОС вытесняет их без свопа, поэтому доля под них
щедрее, чем под кеш. `TotalAvailableMemoryBytes` — это физическая память машины (или
лимит контейнера), а не «свободно сейчас»: свободное меняется каждую секунду, и
настраивать по нему прагмы, которые живут все время подключения, было бы гаданием.

## Настройки приложения

`DatabaseRegistry` реализует [ISettingsDatabase](../../../../Utils/ISettingsDatabase.cs)
(`Get`/`Set`/`Remove` по ключу поверх `app_settings`, плюс `KeysWithPrefix` — обход группы
ключей с общей приставкой). [AppSettings](../../../../Utils/AppSettings.cs) дает
типизированный доступ: масштаб интерфейса (`scale`), состояние и ширина правой панели записи
(`recordPanelOpen`, `recordPanelWidth`). Контекст app.db живет все время работы приложения,
поэтому настройки читаются/пишутся через него.

В таблице хранятся только отличия от стандарта: значение, равное дефолту из кода, не пишется,
а удаляет ключ. Поэтому пустая `app_settings` — это полностью стандартные настройки.

Особняком стоит группа `ext.<id расширения>.<имя настройки>` — значения, которые расширения
объявили сами. Фиксированного списка таких ключей в коде нет: `AppSettings` хранит строку, не
зная ее смысла, а на старте перебирает группу через `KeysWithPrefix` и убирает строки
расширений, которых в сборке больше нет. Зачем так —
[features/extensions/overview.md](../../features/extensions/overview.md#настройки-расширения).

## Провайдеры

Два провайдера пользовательских БД: **SQLite** (файл, по умолчанию) и **PostgreSQL**
(сервер). Ветка выбирается в `DatabaseManager.Open` по `Provider` записи реестра;
вызывающий код (очередь монтирования, сайдбар, календарь, репозитории) провайдера
не различает. Системная app.db всегда остается SQLite. Настройка сервера и
подключение глазами администратора —
[../guides/postgresql-setup.md](../../guides/postgresql-setup.md).

Как устроена PG-ветка:

- **Один контекст — два провайдера.** `AppDbContext(string)` принимает путь к файлу
  ЛИБО строку подключения Npgsql (признак — `Host=`, см. `PgConnectionInfo`); все
  фоновые места `new AppDbContext(db.DbPath)` работают без изменений. Кеш EF-модели
  разделен по провайдеру (`ProviderModelCacheKeyFactory`) — без него первый открытый
  провайдер «застолбил» бы модель и для второго.
- **PG-модель: lowercase-имена колонок + флаги integer.** PostgreSQL сворачивает
  неэкранированные идентификаторы к нижнему регистру, поэтому общий raw SQL
  репозиториев (`WHERE CollectionId = @c`, keyset `(Position, Id) > (@p, @id)`)
  работает на обоих провайдерах как есть; bool-свойства маппятся в integer 0/1
  (как SQLite хранит их физически) — сравнения `= 1` в raw SQL остаются общими.
  Отсюда правила для ПАРАМЕТРОВ сырых команд, которые SQLite не проверяет, а PG
  проверяет строго: флаг биндится ЧИСЛОМ (`DbType.Int32`, значение 0/1) —
  `DbType.Boolean` падает с 42804 «столбец имеет тип integer, а выражение — boolean»
  (урок `BulkSetRowStyle`: на SQLite ошибка не всплывала, поймал только PG-стенд);
  команде с `Prepare()` тип КАЖДОГО параметра задается явно ДО подготовки — Npgsql
  обязан знать типы в Parse-сообщении, без них Prepare бросает «must have its
  NpgsqlDbType … set»; подзапрос во FROM всегда с алиасом (SQLite прощает, PG — 42601);
  PRAGMA — только за guard'ом `IsPostgres`. Регресс на все четыре правила —
  `Tests/Integration/PgBulkWriteTests.cs`.
- **Свой набор миграций**: `PgAppDbContext` + `Database/Migrations/Pg`
  (чистый `InitialCreatePg` — PG-базы всегда новые, ни legacy-моста, ни SchemaCompact).
  Каждое изменение сущностей = два запуска `migrations add`
  (см. [developer-guide](../../guides/developer-guide.md)).
- **Пропускается все файловое**: PRAGMA-профили (guard `IsPostgres` в
  `ApplyPerformancePragmas` и родственных), journal_mode, VACUUM-самолечение,
  `SqliteStageProgress`, `ClearStaleMigrationsLock` (замок миграций на PG —
  advisory-lock сессии, смерть убитого процесса снимает его сама).
- **Непрерывных блоков id нет**: identity-последовательность общая для всех клиентов,
  поэтому пути с арифметикой `last_insert_rowid − N + 1` имеют PG-ветки — импорт
  и переносы получают id из `INSERT … RETURNING`, дубли строят явную карту id через
  `nextval()` во временной таблице (`CopyCollectionDataPg`, `DuplicateRecordsDataPg`).
- **Массовые пути шлют команды пакетами DbBatch.** На файле поштучная
  prepared-команда в транзакции — самый быстрый путь; на сервере каждый `Execute*` —
  синхронный сетевой раунд-трип, и свод в 600 тыс. строк превращался в ~4,2 млн ходов
  (десятки минут одной латентности). Заливка (`BulkAddRecords`, `WriteRowsBatched`)
  и массовая раскраска (`RunBatched`) при `CanCreateBatch` (Npgsql умеет,
  Microsoft.Data.Sqlite — нет, так и ветвимся) собирают до 2000 команд в один сетевой
  ход; id записей читаются из `RETURNING` по одному результату на команду — строго
  в порядке команд пакета. Повторяющийся SQL пакета авто-препарится сервером
  (`MaxAutoPrepare` в `PgConnectionInfo`).
- **Многопользовательский слой общий**: `DbHealthMonitor` пробует сервер `SELECT 1`
  (вместо файла), `ChangePoller` вместо `PRAGMA data_version` следит за курсором
  `MAX(id)` журнала `change_log`, фильтры `IsUnavailableError`/`IsBusyError` знают
  коды Npgsql — `DbErrors`, тосты и авто-переподключение работают без изменений.
  Конкурентную запись сериализует MVCC самого сервера: одновременных пользователей
  может быть на порядки больше, чем у файла в сетевой папке (пул подключений клиента
  ограничен 16; для тысяч пользователей на одном сервере — PgBouncer).
- **Перенос между провайдерами** (SQLite ↔ PG, PG ↔ PG) — generic-путь на двух
  подключениях вместо ATTACH: чтение источника keyset-страницами в одном снимке
  (`REPEATABLE READ`), запись пакетами с per-batch транзакциями, карта id из
  `RETURNING`. Копия и удаление источника раздельны с той же компенсацией, что у
  ATTACH-переноса; от kill посреди заливки — маркер `crossmove.pending.*` в db_meta
  приемника и свип при монтировании (частичная копия не выживает, источник цел).
  Пары SQLite→SQLite идут прежним быстрым ATTACH-путем.
- **Подключение в настройках**: «Управление базой данных» → «Подключить PostgreSQL…»
  (сервер/порт/база/пользователь/пароль/SSL, проверка соединения с русскими текстами
  ошибок). Базу на сервере создает администратор (`CREATE DATABASE`); схему внутри
  пустой базы приложение строит само при монтировании. Параметры хранятся в реестре
  app.db (Pg*-колонки добавлены аддитивно); пароль — через `Utils/SecretProtector`:
  macOS — Связка ключей (в app.db только ссылка `keychain:v1:{id}`, удаление базы
  чистит элемент), Windows — DPAPI CurrentUser (`dpapi:v1:{base64}`), Linux/сбой
  хранилища — открытый текст. Читает пароль единственная точка —
  `DatabaseRefEntity.ToPgInfo()`; старые открытые пароли разово защищаются при
  открытии реестра (`ProtectLegacyPasswords`).

Тесты провайдера — `Tests/Integration` (`[SkippableFact]`: без стенда помечаются
Skipped): `PgProviderTests` — монтирование/CRUD/гонки/дубли/переносы во всех
направлениях/свип, `PgBulkWriteTests` — сырые массовые пути (заливка + раскраска
свода, prepared-правки значений при смене настроек поля, сортированный CSV журнала,
капнутый счет пилюль задач) на docker-стенде `sb-pg` (порт 5455) — как поднять, см.
[testing/automated-tests.md → PostgreSQL](../../testing/automated-tests.md#postgresql).
Нагрузочный режим — команда `pgload` в `Tests/Benchmarks`
(`dotnet run -c Release --project Tests/Benchmarks -- pgload [клиентов] [секунд]`): каждый
клиент — свое физическое подключение, вставки + конкурентные инкременты, сверка «ни одна
подтвержденная операция не потерялась»; лишние клиенты сверх `max_connections` получают
53300 — он входит в `IsUnavailableError` (переполненный сервер = «недоступна» с
backoff-ремонтом). См. [testing/benchmarks.md](../../testing/benchmarks.md).
