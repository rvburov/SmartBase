# Производительность — горячие пути

Часть [обзора производительности](overview.md): самые нагруженные пути данных (таблица, фильтр/сортировка, импорт, экспорт). Календарь — в [calendar.md](calendar.md).

## Горячие пути

| Путь | Масштаб | Что держит скорость | Код |
|---|---|---|---|
| Таблица коллекции | до ~10 млн записей | `VirtualCollectionView` (DataGrid не материализует источник) + keyset + фоновая подгрузка | [TableView](../../../../Views/ConstructorDb/TableView.axaml.cs), [VirtualRowList](../../../../ViewModels/ConstructorDb/VirtualRowList.cs), [VirtualCollectionView](../../../../ViewModels/ConstructorDb/VirtualCollectionView.cs) |
| Фильтр / сортировка | до ~10 млн | фильтр в SQL → список id → виртуализация; выпадающий список значений — SQL-агрегат в фоне | [TableView](../../../../Views/ConstructorDb/TableView.axaml.cs), [ConstructorRepository](../../../../Database/Repositories/ConstructorRepository.cs) |
| Импорт таблиц | 10 млн+ строк | двухпроходный стриминг + пакет=транзакция | [TableSources](../../../../Core/Importers/TableSources/), `ImportStreamedCollection` |
| Экспорт таблиц | 10 млн+ строк | keyset-страницы чтения + SAX/поток-писатели, память O(страницы) | [TableWriters](../../../../Core/Exporters/TableWriters/), `ReadExportRowsIsolated` |
| Календарь (окна День/Неделя/Месяц/Год) | до ~10 млн записей | индексная проекция `calendar_index` + сплит-запрос окна (timed с нижней границей + all-day) по `(CollectionId, AllDay, StartIso)` | [ConstructorRepository](../../../../Database/Repositories/ConstructorRepository.cs) |
| Календарь «Диаграмма» (окно месяц…10 лет) | до ~10 млн записей | чтение «по коллекциям»: 3 индексных сика с LIMIT на коллекцию (не по дням — окно бывает десятилетием); точные счётчики/охваты групп — фоновая фаза 2 покрывающими скансами (`GetDiagramStats`) | `GetDiagramRecordsCapped` |
| Календарь «Расписание» (день) | миллионы событий в дне | `IList`-виртуализация: полоса на весь объём + offset/keyset-страницы в фоне с «Загрузка…»; несколько БД — порядок по времени через посекундную карту (как «Журнал»); правки — мутацией списка НА МЕСТЕ (`ApplyDeltaAsync`: удаления без БД, вставка — ранг записи одним COUNT по индексу) | [CalendarDayVirtualList](../../../../Views/ConstructorDb/Calendar/CalendarDayVirtualList.cs) |
| Календарь «Журнал» (вся история данных) | миллионы событий | плоская `IList`-виртуализация: карта из счётчиков по дням (async GROUP BY) + страницы дней в фоне; порядок по времени между БД — слитые дни ≤ 10k / посекундная карта гигантских дней; правки — мутацией списка НА МЕСТЕ (`ApplyDeltaAsync`: страницы/кеши дней переживают правку, без волны «Загрузка…») | [JournalVirtualList](../../../../Views/ConstructorDb/Calendar/JournalVirtualList.cs) |
| Поиск по заголовкам (Расписание/Журнал) | 10 млн записей ~12 с в фоне | нативный LIKE-скан с регистровыми вариантами (кириллица), первые 1000 совпадений; FTS5-trigram откатили: минуты бэкафилла + деградация на частых подстроках | `SearchCalendarEventsAsync` |

### Таблица коллекции

**Avalonia DataGrid не умеет виртуализацию данных.** Если в `ItemsSource` положить
обычный список (даже ленивый `IList`), `DataGridCollectionView` в конструкторе
перебирает источник **целиком** → на 100k+ открытие занимает минуты. Обход:
[VirtualCollectionView](../../../../ViewModels/ConstructorDb/VirtualCollectionView.cs)
реализует `IDataGridCollectionView` + `IList` — такой источник DataGrid берёт **как есть,
без копирования** и запрашивает строки **по индексу только для видимых** (презентер строк
UI-виртуализирован).

Данные тянет [VirtualRowList](../../../../ViewModels/ConstructorDb/VirtualRowList.cs)
постранично (страница — 200 строк, в кеше до 50 страниц ≈10k с LRU):
- `Count` — из `CountRecords` без загрузки строк;
- последовательный скролл — **keyset в обе стороны** (`GetRecordsPageAfter` /
  `GetRecordsPageBefore`): вперёд — сик ПОСЛЕ последней строки предыдущей страницы, вверх —
  сик ПЕРЕД первой строкой следующей (курсоры краёв страниц живут в `_pageStart`/`_pageEnd`
  и переживают вытеснение из LRU). O(take) на любой глубине — **0.3 мс** на 10 млн;
- произвольный прыжок по скроллбару — offset (`GetRecordsPage`): смещение идёт по
  **покрывающему** индексу `(CollectionId, Position)` — подзапрос отбирает только `Id`,
  пропускаемые записи не читаются из таблицы, join достаёт колонки лишь для строк страницы
  (~200 мс на глубине 10 млн, разово на прыжок);
- значения страницы — один пакетный запрос (`GetFieldValuesBatch`, `IN` по индексу
  `(RecordId, FieldId)`).

Страницы таблицы — **raw SQL** (`ReadRecordRows`): row-value сравнение
`(Position, Id) > ($p, $id)` даёт индексный сик, а OR-форма
`Position > $p OR (Position = $p AND Id > $id)`, в которую EF транслирует LINQ-keyset,
на индекс НЕ ложится — SQLite сканирует коллекцию с начала, и «keyset» был O(глубины):
на 10 млн каждая страница скролла стоила ~470 мс (сотни мс и в фоне ощущаются как
«Загрузка…», не поспевающая за колесом; на 100k это были ~5 мс, поэтому не всплывало).

**Реализация строки обязана быть O(1) — в `OnLoadingRow` НЕЛЬЗЯ ходить в БД.** DataGrid
реализует строки по-разному: прыжок ползунком — только конечное окно (да и то заглушками
«Загрузка…» с `RecordId=0`), а колесо/кнопки скроллбара — КАЖДУЮ пересечённую строку, уже
заполненную реальным id. Пункты меню «Сдвинуть вверх/вниз» проверяли соседей при ПОСТРОЕНИИ
меню в `OnLoadingRow`: `GetRecordPosition` (ранг = COUNT до глубины строки) + полный
`CountRecords` — **~470 мс на строку** на 10 млн → колесо «висило», кнопки подтормаживали,
драг летал. Исправлено: проверка — только в `menu.Opening` (правый клик), и это O(1)-сик
соседа `HasNeighborRecord` (`EXISTS … (Position, Id) < (…)` по индексу, 0.01 мс) вместо
рангов и COUNT'ов.

Подгрузка строк идёт в **фоновом потоке** (`LoadPageAsync` — отдельное read-only
подключение, WAL допускает параллельное чтение): строки сразу показывают «Загрузка…»
(`TableRowVm.IsLoading`), данные приходят и заполняют их на UI-потоке (`Fill`) → ноль
микроподвисаний при скролле. Параллелизм ограничен семафором; загрузки, устаревшие после
`Reset` (правка/перезагрузка), отбрасываются по счётчику поколений, а загрузки страниц,
вытесненных из кеша при быстром скролле, пропускаются (проверка `_pending`/`_pages` после
семафора) — чтобы страница, на которой пользователь остановился, грузилась без очереди из
устаревших. Фоновая подгрузка, как и сама виртуализация, — часть программы, всегда включена
(настройки-переключателя нет; бывший флаг `asyncRowLoad` удалён).

> **Важно (Avalonia).** `Fill` уведомляет об изменении ячеек через `OnPropertyChanged("Item")`
> — именно имя индексатора. Привязка `Binding("[key]")` обновляется только по нему;
> WPF-стиль `"Item[key]"` Avalonia игнорирует (`ReflectionIndexerNode.ShouldUpdate`), и тогда
> «Загрузка…» не сменялась бы данными на месте, только при пересоздании ячейки скроллом.

### Фильтр и сортировка

При активном фильтре/сортировке таблица **не грузит все строки в память**. Фильтр уходит
в SQL (`GetFilteredRecordIds` — EAV-условия через `EXISTS`/`IN`, пустые значения учтены),
возвращает только id совпавших записей в порядке `Position`; сортировка применяется тем же
компаратором по значениям **одной** колонки (`GetColumnValues`). Показ виртуализируется по
списку id (`VirtualRowList` в режиме списка id + `GetRecordsByIdsOrdered`).

Выпадающий список значений в заголовке открывается **мгновенно**: значения считаются
SQL-агрегатом (`GetFieldValueCounts` / `GetTitleCounts` / `GetDescriptionCounts`, GROUP BY
по индексу `(FieldId, Value)`) на **фоновом потоке** (`GetColumnCountsAsync`), до прихода —
«Загрузка…». Значения идут в **порядке таблицы** (по `MIN(Position)`), «(Пусто)» — в конце;
список **виртуализирован** (`ListBox`), показываются все уникальные значения без лимита.

Старый материализованный путь (`LoadAllRows` — все строки в память) остаётся только как
fallback при **выключенной** виртуализации.

### Импорт таблиц

Конвейер **двухпроходный и потоковый** ([TableSources](../../../../Core/Importers/TableSources/)):
проход 1 (`Analyze`) читает файл целиком, но в память складывает только схему и счётчики
(точное число записей — для процентов, счётчик пустых названий); проход 2 (`ReadRows`)
переоткрывает файл и отдаёт записи `IEnumerable`-потоком прямо в запись. Память O(1) на
любом объёме — старый путь материализовал ВСЕ строки (10 млн строк CSV ≈ гигабайты).
Excel читается ExcelDataReader (строка за строкой, книга в память не поднимается),
CSV — свой StreamReader-автомат, JSON — `Utf8JsonReader` поверх FileStream.
Границы (`lastCol`/`lastRow`) — по **реальному непустому содержимому**, а не по dimension
листа и не по максимальной длине строки CSV: иначе хвост пустых столбцов превращал
526×10 в ~1 млн пустых значений полей.

`ImportStreamedCollection` (в [ConstructorRepository](../../../../Database/Repositories/ConstructorRepository.cs)):
маленькая shell-транзакция (коллекция + поля через EF), затем строки пакетами по 20k —
**каждый пакет в своей транзакции** (модель батч-удаления: WAL не разрастается на весь
объём, отмена срабатывает между пакетами; отмена/ошибка → коллекция удаляется целиком).
Записи и значения — **сырым ADO.NET** prepared-`INSERT`, НЕ через EF: EF на каждую из
миллионов сущностей тратит построение графа и чтение сгенерированного Id (≈60× медленнее).
В своей транзакции импорт — единственный писатель, id пакета непрерывны: `RecordId =
firstNew + индекс` (`firstNew = last_insert_rowid − размер_пакета + 1`), как в bulk-копии
дубля. Шаг `Position` при > 2 млн строк — 1 вместо 1000 (`(idx+1)*1000` в `int`
переполнялся после ~2,1 млн). Импорт идёт на **отдельном** контексте с bulk-прагмами
(`ImportStreamedCollectionIsolated`, см. принцип 5) на фоновом потоке.

Замер ([Tests/ImportPerf](../../../../Tests/ImportPerf/Program.cs) `--perf`): CSV 1 млн строк ×
8 колонок — 116 с; 10 млн (1 ГБ) — 21 мин (~70 тыс. INSERT/с, скорость не падает с ростом
объёма; пик памяти — mmap-окно SQLite, не строки).

Подробнее: [[../../features/import-export/overview]].

### Экспорт таблиц

Чтение — **keyset-страницами** (`ReadExportRowsIsolated` в
[ConstructorRepository](../../../../Database/Repositories/ConstructorRepository.cs)): страницы
`GetRecordsPageAfter` по 2000 записей (row-value сик по индексу `(CollectionId, Position)` —
O(страницы) на любой глубине) + значения пакетом `GetFieldValuesBatch` (EF9 транслирует
`Contains` в `json_each` — один параметр, лимита 999 нет). Отдельное подключение с
bulk-прагмами (принцип 5): чтение `db_field_values` на десятках ГБ в стандартный кеш не
влезает.

Запись — потоковые писатели ([TableWriters](../../../../Core/Exporters/TableWriters/)):
xlsx/xlsm — `OpenXmlWriter` (SAX; ClosedXML — DOM, миллионы строк не переживает), без
shared strings (каждая строка inline — память O(1)), пустые ячейки не пишутся (сетку
держат ссылки `r=`); CSV — StreamWriter с буфером 1 МБ; JSON — `Utf8JsonWriter` с
принудительным `Flush` каждые 500 строк (иначе он копит ВЕСЬ вывод в памяти — O(n)).
Переполнение листа Excel (1 048 576 строк) писатель обрабатывает сам — продолжение
«Имя 2», «Имя 3»… Память процесса не растёт с объёмом: страница чтения + буферы писателя.
`GetFieldValuesBatch` при этом обязан быть `AsNoTracking`: экспорт зовёт его сотни раз
на одном контексте, и change tracker копил бы все значения до конца операции (до фикса —
пик 7,9 ГБ и вдвое медленнее).

Замер ([Tests/ExportPerf](../../../../Tests/ExportPerf/Program.cs) `--perf`, коллекция 1 млн
строк × 8 столбцов): CSV — 53 с (~19 тыс. строк/с), JSON — 48 с (~21 тыс.),
XLSX/XLSM — 73–78 с (~13 тыс.); пик памяти процесса ~1,6 ГБ (фикстура-импорт + mmap).

Подробнее: [[../../features/import-export/overview]] (раздел «Экспорт таблиц»).
