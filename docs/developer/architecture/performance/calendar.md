# Производительность — календарь

Часть [обзора производительности](overview.md).

### Календарь

Календарь поддерживает **несколько дат на запись** (любое число полей-дат коллекции с
флагом `IsCalStart` показываются как отдельные события). Чтобы это масштабировалось, как
таблица, события материализуются в индексную таблицу-проекцию **`calendar_index`** (строка
на запись × видимое поле-дата: `RecordId, FieldId, CollectionId, StartIso, EndIso, AllDay`).

`GetCalendarRecordsByRange(start, end)` → `ReadCalendarEvents` читает из `calendar_index`
индексным range-query: пересечение окна = `StartIso < конец` И `EndIso >= начало` (ISO-строки
сравниваются лексикографически). Трогаются только события окна, а не все значения — прежний путь
(скан `db_field_values` с разбором в C#) был тяжёл на больших коллекциях.

**Сплит окна на два под-запроса** (raw-SQL, индекс `(CollectionId, AllDay, StartIso)`), иначе на
больших объёмах запрос сканировал бы **всё от начала таймлайна**: у `StartIso` есть верхняя
граница окна, но не нижняя, поэтому индекс перебирал все события до конца окна (на 10 млн один
«День» открывался и за 0.4 с у начала данных, и за ~9 с у конца). Разбивка:
- **timed (`AllDay=0`)** — с нижней границей `StartIso >= начало окна − буфер` (`CalendarTimedBufferDays`,
  62 дня): быстрый двусторонний seek, основная масса событий;
- **all-day (`AllDay=1`)** — **без** нижней границы (их мало → дёшево): многодневные события,
  начавшиеся до окна (панель AllDayBar), не теряются.

Буфер 62 дня отсекает только timed-под-запрос (не-all-day событий такой длины не бывает —
длинное всегда `AllDay`), поэтому корректность сохранена, а не-all-day событие любой реалистичной
длины попадает в результат. Замер на 10 млн: «День»/«Неделя» — ~50–140 мс (было 4.5–9 с, ×100+),
результат по строкам **идентичен** старому. «Год» (~900k строк) упирается уже в материализацию,
не в скан.

**Сетка (День/Неделя/Месяц/Год) читает окно В ФОНЕ и с ограничением на день**
(`GetCalendarRecordsByRangeCapped` + `LoadCalendarGridRangeAsync`, изолированные подключения):
день-гигант (5 млн событий в одном дне) материализовывал весь день на UI-потоке — окно
месяца/недели/года, накрывающее такой день, вешало приложение на минуты (в т.ч. при
подключении большой БД из настроек: `SyncMountedToUi` → `RefreshCurrent`). Теперь timed-события
читаются **per-day × per-collection** запросами `… ORDER BY StartIso LIMIT GridDayCap` (2000):
каждый фиксирует `(CollectionId, AllDay)` одним значением, ложится сиком на индекс
`(CollectionId, AllDay, StartIso, …)` и обрывается LIMIT'ом, не сканируя день (общий `ORDER BY`
с `IN` по коллекциям сортировал бы миллионы строк во временной таблице — LIMIT не спасал бы;
замер: день-гигант с cap — 3 мс). Для дней внутри окна `EndIso >= начало` выполняется
автоматически — фильтр целиком индексный; спилловеры (timed, начавшиеся ДО окна и
пересекающие его) — сиком по индексу `(CollectionId, AllDay, EndIso, …)`: `EndIso ∈ [начало
окна, начало+буфер)` (верхняя граница следует из инварианта «timed длиннее буфера не бывает»).
Прежний проход сканировал весь 62-дневный StartIso-буфер с проверкой `EndIso` чтением строк —
день-гигант в буфере стоил секунд при КАЖДОМ открытии «Дня»/«Недели» следующие 62 дня после
него (замер: 3.15 с → 7 мс; поэтому «День» 5 июля показывал «Загрузку…», а «Неделя» с гигантом
ВНУТРИ окна — нет). All-day — тоже per-collection с cap и тоже сиком по EndIso-индексу:
у StartIso нет нижней границы (многодневное могло начаться сколь угодно давно), и прежний
StartIso-скан шёл от начала таймлайна с чтением строк — миллионы прошлых all-day (импорт дат
«без времени» даёт `AllDay=1`) стоили секунды на каждое окно после них (замер: 2.2 с → 0 мс);
верхней границы по EndIso у all-day нет — он, в отличие от timed, не ограничен буфером. Панель «весь день» (AllDayBar) дополнительно ограничивает
ОТРИСОВКУ: не больше `MaxRenderedEvents` (300) блоков + «+N ещё» — контрол на каждое событие
и квадратичный поиск свободной строки на тысячах повесили бы UI уже после чтения.
Часовая сетка Дня/Недели ограничивает ПАРАЛЛЕЛЬНЫЕ под-колонки (`MaxEventColumns`: 12/6) —
сверх лимита события не рисуются: день-гигант давал 2000 под-колонок = тысячи субпиксельных
контролов, и КАЖДАЯ перерисовка (открытие, любая операция) подвешивала UI на секунды, хотя
данные уже приходили за миллисекунды; `GroupOverlapping` заодно переведён с O(n²) на бегущий
максимум конца интервала.
Недоставленное сверх cap показывает честный «+N ещё» по **карте счётчиков дней**
(тот же `GROUP BY substr(StartIso,1,10)`, что у Журнала; ~2.6 с на окне с днём-гигантом).
Загрузка окна — **двумя фазами**: события (индексные сики, мс) применяются сразу — оверлей
«Загрузка…» (>400 мс) в норме не возникает; карта (только Месяц/Год) доезжает фоном второй
фазой и тихо уточняет «+N ещё». **Год события окна не читает вовсе** (сотни тысяч строк за
год, ~0.7–1.5 с — оверлей успевал появляться при листании лет): числам достаточно карты,
попап дня грузится по требованию per-day сиками (мс), поиск в попапе — SQL LIKE по всему
дню. Устаревшие загрузки отменяет поколение.

**Диаграмма читает окно «по коллекциям», не «по дням»** (`GetDiagramRecordsCapped`):
её окно бывает годом и десятилетием, и per-day чтение сеток стоило бы 3653 дня ×
коллекции запросов (секунды «Загрузки…» даже на пустой БД) и до `GridDayCap` строк
с каждого дня (миллионы строк в памяти) — при потолке отрисовки ~200 строк на
группу. Вместо этого 3 индексных сика с `LIMIT MaxRecordsPerCollection` на
коллекцию (timed окна / timed-спилловеры / all-day) — время и память не зависят
ни от длины окна, ни от объёма БД. Счётчики групп, «+N ещё» и охват суммарных
баров при этом считаются по ВСЕМ событиям окна — точные агрегаты
(`GetDiagramStats`: COUNT/MIN/MAX по классам timed/all-day, покрывающие индексные
сканы; COUNT пропорционален строкам окна) доезжают **фоновой фазой 2**, как карта
счётчиков Месяца/Года, и тихо уточняют показанное; точечные правки корректируют
агрегаты дельтой (±счётчик, расширение охвата) без пересчёта.

**Точечные правки сетки — на месте** (`TryApplyGridDelta` в контроллере): операции
(создание/изменение/удаление/дубль; перенос/растяжение времени в Дне/Неделе; перенос между
днями в Месяце — drag отдаёт исходные даты для точной дельты) мутируют снимок последней
загрузки (`_gridRecords`/`_gridTotals`) и синхронно перерисовывают вид — ни чтения окна,
ни оверлея; карта счётчиков правится дельтой по дню начала записи. Исключения (полная
загрузка): навигация/смена вида, поиск.

**«Расписание» (список одного дня) полностью виртуализировано** ([CalendarDayVirtualList](../../../../Views/ConstructorDb/Calendar/CalendarDayVirtualList.cs)),
т.к. в одном дне событий могут быть миллионы (материализация окна разом «вешала» UI). Список
реализует `IList` — полоса прокрутки на ПОЛНОЕ число событий дня (можно перетащить в самый низ),
`VirtualizingStackPanel` реализует только видимые строки. Два режима по числу событий дня:
- **InMemory** (≤ 10 000 или поиск): день грузится сразу, **слияние по времени** между БД (точный
  порядок); поиск — фильтр по заголовку с ограничением скана;
- **Offset** (> 10 000): страница грузится на изолированном подключении **в фоне** с заглушками
  «Загрузка…». Порядок «Расписания» — фаза all-day, затем timed, каждая по `(StartIso, RecordId,
  FieldId)` (ложится на индекс `(CollectionId, AllDay, StartIso, RecordId, FieldId)` — seek без
  сортировки; общий `ORDER BY AllDay DESC` заставлял SQLite сортировать все строки дня во временной
  таблице = секунды фриза). Способ чтения страницы: **прыжок** полосой → offset (пропуск по
  покрывающему индексу, join к `db_records` только для строк страницы → прыжок в конец дня на
  миллионы событий доли секунды); **последовательная прокрутка** → keyset от последней строки
  предыдущей страницы (O(страницы), не зависит от глубины → гладкий скролл колесом). Хвост индекса
  `(RecordId, FieldId)` даёт общий ключ, поэтому offset и keyset идут ОДНИМ порядком и стыкуются без
  дублей/пропусков. Загрузка **с дебаунсом** (пауза после скролла): при быстром перетаскивании
  транзитные страницы вытесняются и запрос не тратят.

Счётчики дня «Расписания» **кешируются** (`_dayCountsCache` в ListView): навигация Prev/Next/
«Сегодня» и возврат из поиска не пересчитывают COUNT повторно посещённых дней; дельта правок
держит кеш актуальным, смена источников/активных коллекций и пересборка без дельты сбрасывают.
Каждая операция (создание/правка/удаление/дубль) даёт **ровно один** refresh: дельта ставится
ДО `CollectionsMayHaveChanged` (`NotifyChangedAndRefresh`) — раньше событие запускало холостую
пересборку без дельты, и её фоновый COUNT дня-гиганта уходил впустую на каждую правку.

Проекция поддерживается **инкрементально** (не пересобирается целиком на каждый чих):
upsert одной строки при правке значения (`SyncCalendarIndexValue` из
`SetFieldValue`/`SetCalendarDateValue` — для ЛЮБОГО поля-даты, включая скрытые); пересбор
поля только при смене ТИПА (`RebuildCalendarIndexForField`); пересбор коллекции/записи при
дубле и переносе между БД; удаления — каскадом по FK (`ON DELETE CASCADE` +
`PRAGMA foreign_keys=ON`). Однократный потоковый бэкафилл (keyset + пакетный prepared
`INSERT`, как импорт) в `MigrateAndBackfillCalendarDates`, если проекция пуста.

**Видимость — фильтры чтения, не пересборки.** Тумблер «Отображение свойств даты»
(`SetDateFieldVisible`) лишь переключает флаг `IsCalStart`: скрытые поля отсекает
`HiddenFieldsClause` во ВСЕХ читателях `calendar_index` (проекция остаётся полной) — раньше
клик чекбокса удалял/заливал строки поля синхронно на UI-потоке, на 10 млн — минуты фриза.
Коллекции, у которых **все** поля-даты скрыты, отсекаются целиком на уровне `CollectionId`
(`VisibilityFilter`/`FullyHiddenDateCollections`): фильтр по `FieldId` — residual, и «галка
включена, но поля скрыты» сканировала бы весь диапазон (день-гигант — секунды «Загрузки…»)
ради пустого результата. Единственный тяжёлый случай — включение поля, чью проекцию удалила
старая версия: разовая фоновая заливка с окном прогресса (`FillCalendarIndexForFieldAsync`).
Галки коллекций в сайдбаре — фильтр активных id, причём **пустой набор = ни одной**
(`AND 1=0`): раньше пустой `IN` «отключал» фильтр, и снятие всех галок БД показывало все
события вместо ни одного. Буферы окна считаются через `SafeAddDays`: Журнал маленьких баз
(InMemory) читает «всю историю» с 0001 года — вычитание 62-дневного буфера кидало
`ArgumentOutOfRange`, и Журнал показывался пустым (исключение глотал catch построения).

> Колонки `db_records.StartDt/EndDt` остались от модели «одна дата на запись» и больше
> не читаются календарём.
