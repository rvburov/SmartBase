- ✅ Дубль коллекции — bulk-SQL + окно прогресса для больших, мгновенно для малых.
  `CopyCollectionData` (одна транзакция): **все записи одним `INSERT … SELECT … ORDER BY Position, Id`**
  (`firstNew = last_insert_rowid − recCount + 1`), затем значения **крупными пакетами (10 000 записей),
  ВСЕ поля за один `INSERT`** через временную карту полей `_dup_fmap` (old→new fid по `Position`);
  новый `RecordId = firstNew + processed + локальный ранг(ROW_NUMBER) − 1`. Пакеты — только для
  гранулярности процентов. Бенч (iCloud, 2M значений): **4.7–5.0 с против 16.8 с** у прежнего варианта
  «мелкие пакеты по 2000 × по одному полю с `ROW_NUMBER` на каждом» (≈3.4× быстрее, сравнимо с импортом).
  Дубль — **ПОЛНАЯ копия**: после записей/значений `CopyDuplicatedUi` (в той же транзакции) копирует и
  UI-настройки (ширины/порядок/видимость колонок, высоты/видимость строк, режим просмотра, подписи системных
  колонок) — id полей через `_dup_fmap`, id записей по рангу `(Position, Id)`; колонка-/коллекция-level
  копируется даже для пустой коллекции. Зеркало `CopyMovedUi` (перенос в другую БД). Раньше дубль в той же
  БД UI НЕ переносил (только cross-БД перенос). **Проекция календаря копируется в тех же пакетах** —
  `INSERT … SELECT` из `calendar_index` источника с тем же перемэппингом id, что у значений: проекция
  источника всегда полная (видимость поля — фильтр чтения), пересобирать ее незачем. Прежняя пересборка
  (чтение значений EF-страницами + парсинг дат + по-строчный INSERT) шла ПОСЛЕ последнего процента — бар
  висел на 100% (замер 200k: хвост 14,4 с → 1,1 с, дубль целиком 18,5 с → 7,6 с). Изолированные подключения
  массовых операций (дубль/перенос/удаление/импорт/бэкафилл проекции) получают `ApplyBulkPerformancePragmas`
  (кеш ~512 МБ + mmap 2 ГБ поверх стандартных прагм): на десятках ГБ глобальные индексы (`db_field_values`,
  `calendar_index`) не влезают в стандартные 64 МБ, и вставка деградирует в случайный дисковый I/O
  (замер на стенде 10 млн записей: дубль коллекции шел ~35 мин).
  UI-поток (`Sidebar.DuplicateSelectionOrNode`):
  счетчики по выделению считает В ФОНЕ на отдельных подключениях (`CountNodeAsync` → `CountRecordsAsync`/
  `CountGroupSubtreeAsync`; COUNT по коллекции в 10 млн — сотни мс, на UI-потоке это был фриз между кликом
  и окном прогресса, умножался при мультивыборе); **≤ 20 000 — копирует синхронно мгновенно без окна**;
  **больше — окно прогресса с % (как импорт)**, копии идут ПО ОЧЕРЕДИ в фоне на отдельных подключениях
  (`DuplicateCollectionIsolated` → свежий `AppDbContext`, не трогает общий — см. принцип 5), проценты —
  общий прогресс по всем целям (`IProgress<int>` → `Dispatcher.UIThread.Post`). Работает и для
  мультивыбора, и для **групп** (дубль группы СО ВСЕЙ веткой: `DuplicateGroupCore`/`DuplicateGroupIsolated`
  — структуру групп и шеллы коллекций создает EF, данные каждой коллекции копирует тем же `CopyCollectionData`;
  верхняя группа получает «(копия)», вложенное — свои имена; индикатор показывает «Коллекций: X · Записей: Y»).
  По завершении — `ReloadAndNotify` + показ результата (коллекцию открыть, группу раскрыть; для одной цели).
  Прежний дубль группы создавал ПУСТУЮ копию (без вложений); еще раньше дубль коллекции шел по-записно через
  EF (2× `SaveChanges` на запись), зависание 5–10 с.
- ✅ Удаление коллекций И групп — по аналогии с дублем: не блокирует UI, с окном прогресса. `Sidebar.DeleteNodes`
  после подтверждения считает суммарное число записей В ФОНЕ (для группы — по ВСЕЙ ветке, `CountGroupSubtreeAsync`);
  **≤ 20 000 — синхронно мгновенно** (`DeleteCollection`/`DeleteGroup`, каскадный DELETE); **больше — окно
  прогресса с %** (`Title="Удаление"`; при группах строка «Коллекций: X · Записей: Y», иначе «Количество
  записей: N»), удаление ПО ОЧЕРЕДИ в фоне на отдельных подключениях (`DeleteCollectionIsolated`/
  `DeleteGroupIsolated` → свежий `AppDbContext`). Записи удаляются ПАКЕТАМИ по 10 000 (`DeleteCollectionRows`),
  **каждый пакет — СВОЯ транзакция**: одна гигантская держала весь объем изменений в WAL (десятки ГБ на
  многомиллионных коллекциях); частичное удаление при сбое не страшно — повтор операции доудаляет остаток.
  Значения и строки `calendar_index` удаляются ЯВНЫМ bulk-DELETE до записей (каскаду по FK остается проверить
  пустоту), затем строка коллекции (каскад — поля) и **UI-строки без FK** (`ui_row_heights`, `record_display`,
  `ui_col_widths`, `ui_collection_settings`, `column_meta`) — раньше они сиротели,
  а id коллекций SQLite переиспользует (фантомные настройки у будущей коллекции с тем же id); затем строки групп
  ветки (`DeleteGroupData`: `ParentId` — SET NULL, не каскад, поэтому набор групп удаляем явно). Каскад держится
  на `PRAGMA foreign_keys=ON` (в `ApplyPerformancePragmas` на каждом подключении — иначе записи/значения
  «осиротели» бы). Раньше группы удалялись синхронно на UI-потоке через EF (фриз на больших ветках, без индикатора).
- ✅ Перенос коллекции И группы (контекстное меню «Расположение», окно `LocationDialog` — БД + расположение,
  без названия; для коллекции расположение = ее группа, для группы = родитель; мультивыбор, как дубль/удаление;
  ветки перемещаемых групп исключены из назначения — нельзя вложить в себя/потомка). **В той же БД — мгновенно**
  (коллекция: `UPDATE GroupId`; группа: `UPDATE ParentId` — ветка/записи на месте). **Перенос в другую БД** —
  `MoveCollectionIsolated`/`MoveGroupIsolated`: на подключении ЦЕЛЕВОЙ БД делаем `ATTACH src` и копируем bulk-ом
  `INSERT … SELECT` из присоединенного файла (записи одним INSERT в порядке `Position,Id`, значения И строки
  `calendar_index` крупными пакетами через temp-карту полей `_move_fmap` — проекция копируется из src 1:1,
  НЕ пересобирается; id полей по `Position`, id записей по рангу `Position,Id` →
  `firstNew + ранг − 1`; ключи `column_meta` — числовой → новый id поля, системные как есть; UI
  переносится). Группа: сначала структура групп (`CloneGroupTreeAttached`, имена через `INSERT…SELECT`), затем
  все коллекции ветки по очереди в одной транзакции с общим %. Затем удаление источника на ОТДЕЛЬНОМ подключении
  (каскад). **≤ 20 000 записей суммарно — синхронно мгновенно, больше — окно прогресса** (`Title="Перемещение"`;
  при группах «Коллекций: X · Записей: Y») + фон. **Индикатор покрывает ОБЕ фазы**: на цель 2× записей — копия
  это 0..Records (фаза «Перемещение…»), удаление исходника Records..2·Records (фаза «Удаление из исходной базы…»,
  через `BaseProgress`-сдвиг на `Move*Isolated`). Иначе бар замирал на 100% на все время удаления (каскад
  записей/значений — минуты). Копия и удаление раздельны (в WAL межбазовая транзакция не
  атомарна) с компенсацией (при сбое удаления — откат копии). ≈5 с/2 млн значений (как дубль). Раньше — EF-снимок
  в память + по-записная вставка (минуты, без индикатора). Тот же быстрый путь использует и **смена БД из окна
  «Изменить»** (`EditCollection`/`EditGroup`): кросс-БД перенос и «Расположение» делят общий помощник
  `Sidebar.MoveNodesCrossDb` (порог/прогресс/фон); новое имя из диалога применяется на цели после переноса
  (быстрый путь копирует имя как есть). Раньше «Изменить» шло через статические `MoveCollection`/`MoveGroup`
  (EF-снимок в память, минуты, без индикатора). **Конфликт имен в целевой группе/уровне** обрабатывается
  по-разному в зависимости от наличия поля имени: **«Расположение»** (контекстное меню, без ввода имени) при
  совпадении дает «(копия)»/«(копия) N» — как дубль (`UniqueCollectionName`/`UniqueGroupName` → `NextCopyName`;
  для bulk-переноса в другую БД — `UniquifyCollectionName`/`UniquifyGroupName` после копии; для группы
  уникализируется только корень ветки — вложенное легло в новую пустую ветку без конфликтов). **«Изменить»**
  и **«Создать»** (диалоги с полем имени) проверяют уникальность в выбранной БД/группе и при конфликте
  показывают баннер «Коллекция/Группа с таким названием уже существует», не сохраняя (в своей БД — исключая сам
  редактируемый узел; `CollectionDialog`/`GroupDialog`/`CreateItemDialog`). То же — у инлайн-переименования
  коллекции через заголовок над таблицей (`ConstructorControllerView.RenameCurrentCollection`): при конфликте
  имя в заголовке откатывается и у самого заголовка всплывает уведомление — переиспользуемый `Toast.Error(anchor,
  message)` (Flyout, привязанный к контролу, как tooltip; стиль `FlyoutPresenter.toast`; автоскрытие). `Toast` —
  общий помощник для всплывающих уведомлений у любого контрола (расширяется под Info/Success).
- ✅ Операции со свойствами (колонками) и записями (строками) В САМОЙ таблице — без фриза UI и без
  «белого» мелькания на больших коллекциях. [TableView](../../../../Views/ConstructorDb/TableView.axaml.cs) +
  [ConstructorControllerView](../../../../Views/ConstructorDb/ConstructorControllerView.axaml.cs).
  **Разделенная перезагрузка.** `Reload()` = колонки + строки, но операции зовут только нужную половину:
  `ReloadColumns()` (пересобрать колонки, кэш строк НЕ сбрасывать) для колоночных, `ReloadRows()` (пересоздать
  источник строк, колонки НЕ трогать) для строковых. Полная пересборка строк сбрасывала бы их в заглушки
  «Загрузка…» (мелькание), полная пересборка колонок (`Columns.Clear`) рушит дерево грида → белый экран 1–2 с
  на 456k строк × много колонок.
  **Точечные изменения набора колонок** (грид выровнен с `_colDefs` 1:1, без `Columns.Clear`): создание/«создать
  после»/дубль — вставка одной колонки (`AddColumnForField`); правка/переименование системной — замена одной на
  месте (`RebuildColumn`); сдвиг влево/вправо — `RemoveAt`+`Insert` одной колонки (`MoveColumn`, своп с соседом).
  У всех — безопасный фоллбек (`SameOrderExcept`) на полную пересборку, если набор/порядок разошелся.
  **Тяжелые операции с полем (удаление/дубль) — мимо EF, пакетами, в фоне.** `DeleteFieldData`/`DuplicateFieldData`:
  RecordId значений поля одним индексным запросом по `(FieldId, Value)` + сортировка → пакеты `RecordId IN (…)` по 10 000
  (последовательные обновления индексов; прежний OFFSET давал O(n²) — удаление 425k значений ~4 мин → стало ~12 с).
  Удаление поля — каскад на `calendar_index` по FK + чистка `column_meta`. Большой объем — на ОТДЕЛЬНОМ подключении
  (`DeleteFieldIsolated`/`DuplicateFieldIsolated`, см. принцип 5).
  **Мультиколоночные удаление и дубль** (`PropertiesDeleteRequested`/`PropertyDuplicateRequested` несут СПИСОК id):
  меню «Удалить»/«Дублировать» обрабатывают все мультивыделение колонок (системные/обязательные отсекаются); каждая
  копия встает сразу за своим исходником одним `SaveColumnOrder`, после дубля — `ReloadColumns`+`ReloadRows` (у копий
  есть значения для уже отрисованных строк, иначе показывали бы пусто до перезапуска).
  **Прогресс без фриза и без блокировки UI до индикатора** (`RunBulkOp`): и подсчет значений (`CountFieldValuesIsolated`
  — один `GROUP BY` на отдельном подключении), и сама работа идут в фоне (`Task.Run`, изолированные контексты), главный
  контекст из фона не трогаем. Окно прогресса показывается ОТЛОЖЕННО — только если работа не уложилась в ~200 мс
  (мелкие операции проходят без окна). Раньше `COUNT(*)` по каждому полю шел СИНХРОННО на UI-потоке ДО показа окна → на
  >4 колонках по 456k значений фриз 5 с, и лишь потом индикатор. Фазы: «Подсчет значений…» (бегущая полоса, пока «всего»
  неизвестно) → проценты → «Сохранение…» (`ProgressDialog.SetSaving`, бегущая полоса на время коммита большой
  транзакции, чтобы 100% не выглядели зависшими; фаза «N/M столбцов» при нескольких полях). Окно МОДАЛЬНОЕ — вторую
  операцию нельзя начать, пока текущая не закрылась (нет накопления параллельной нагрузки), а работа идет строго по
  очереди на одном подключении. Лишний кросс-БД `CollectionsChanged` после колоночных операций убран (давал «зависон»
  после 100%) — зовется только если удалили поле-источник календаря (`IsCalStart`).
  **Контекстное меню строки** резолвит `RecordId` лениво из `DataContext` в момент клика (`RowRecordId`): при
  async-подгрузке строка realized как заглушка с `RecordId=0` и заполняется реальным id уже без повторного
  `OnLoadingRow` — из-за захвата старого id дубль падал «Record 0 not found», а удаление было тихим no-op.
- ✅ Пакетное удаление и дубль ВЫБРАННЫХ записей (мультивыделение строк) — bulk-SQL мимо EF, в фоне, с
  индикатором (общий помощник `RunBulkOp`, что и у свойств). Прежний путь — `DeleteRecord`/`DuplicateRecord`
  в цикле с `SaveChanges` на КАЖДУЮ запись — на 1000+ строк давал сотни/тысячи транзакций и фриз UI.
  `DeleteRecordsData` — каскадный DELETE пакетами `Id IN (…)` (значения и `calendar_index` уходят по FK
  ON DELETE CASCADE; `record_display`/`ui_row_heights` FK-связи с записью НЕ имеют — чистим явно, иначе
  осиротевшие настройки прилипли бы к новой записи с тем же rowid — этого не делал и прежний `DeleteRecord`).
  `DuplicateRecordsData` — копии встают СРАЗУ ПОСЛЕ последней (самой нижней по Position, Id) выбранной записи
  (как дубль одной записи, а не в конец таблицы): освобождаем `count` слотов сдвигом ТОЛЬКО хвоста
  (`UPDATE … SET Position += (count+1)*1000 WHERE Position/Id > якоря`, без перенумерации всей коллекции), затем
  записи одним `INSERT…SELECT` в `anchorPos + ранг*1000` + значения пакетами по рангу (новый RecordId = `firstNew` + ранг − 1; `firstNew = last_insert_rowid − count + 1`),
  поля те же (одна коллекция) → FieldId не перемэппливаем; календарь — `FillCalendarIndex` по диапазону новых
  id. Обе — на ОТДЕЛЬНОМ подключении (`DeleteRecordsIsolated`/`DuplicateRecordsIsolated`). Одна запись из меню
  строки — прежний мгновенный путь (удаление сразу; дубль — копия СРАЗУ ПОСЛЕ исходной); много — bulk в фоне.
  **С 26.09.2026 хвост не сдвигается** (этап 8 плана drawn-grid.md): номера копий выдает `AllocatePositions` —
  между якорем и следующей записью, при нехватке места раздвигаются не больше 1024 следующих записей, иначе
  копии получают номер якоря (их `Id` больше всех). Сдвиг хвоста на 10 млн записей был таким же долгим, как
  перенумерация, и выводил номера за int; `RenumberPositions` (ребаланс всей коллекции шагом 1000) удален.
- ✅ Массовое удаление И дублирование выделенных записей из КАЛЕНДАРЯ («Расписание»/«Журнал») —

- ✅ Перенос ВЫБРАННЫХ записей в другую коллекцию/БД (контекстное меню «Расположение», окно

- ✅ **Оценка числа записей на больших коллекциях** (27.09.2026): `EstimateRecordCount` делит
  позицию последней записи на шаг позиций по первой записи (не больше 1000), а не всегда на
  1000. Коллекция больше 2,1 млн записей получает шаг мельче 1000, чтобы номера уложились в int
  (10 млн — 214), и оценивалась впятеро меньше: до прихода точного счета полоса прокрутки была
  короче, а прыжок в конец попадал в пятую часть коллекции. Найдено на стенде
  `~/TestData/wide10m.db` (10 млн × 1000 колонок, [test-database.md](../../testing/test-database.md)).
- ✅ **Боковая панель, перенос с PostgreSQL и резервная копия** (19.10.2026). Замеры —
  [benchmarks.md](../../testing/benchmarks.md) («Что показали `sidebar`, `backup` и `pgmove`»),
  стенд `Tests/Sections --only sidebarops` (с `--shared` — профиль общей базы в сетевой папке).
  - Дубль, удаление и перенос в другую базу из дерева баз (`SidebarTree`) — **всегда в фоне** на
    отдельных подключениях, при любом объеме (прежний порог 2000 записей с синхронным путем снят);
    окно прогресса — если работа дольше 400 мс; счетчики узлов — внутри фоновой работы, разом.
    Паузы UI на стенде с профилем общей базы: малые действия 150–190 мс → 0, большие (300 тыс.
    записей) — до 68 мс. Файловые действия дерева заметок (`SidebarFiles`: перенос, дубль,
    удаление в корзину) — тоже в фоне, с тем же правилом окна.
  - Дубль коллекции (`CopyCollectionData`, SQLite) — **транзакция на пакет** и карта рангов
    `_dup_rmap`, снятая вместе со вставкой записей: одной транзакцией дубль на 2 млн записей
    раздувал `-wal` до 9,4 ГБ, а у общей базы (журнал DELETE) запирал базу для интерфейса и
    соседей до конца копии. Сбой — копия убирается, выход из программы — маркер
    `duplicate.pending.collection` (свип при монтировании; с 20.10.2026 — маркер операции `pending.*`).
  - Перенос SQLite ↔ PostgreSQL (generic-путь) — приемник PG пишется потоком `COPY` с id из
    последовательности, приемник SQLite — prepared-командой вместо multi-row `INSERT` с 1500
    именованными параметрами (квадратичная привязка): 300 тыс. записей PG → SQLite 3 мин 37 с →
    1 мин 37 с, SQLite → PG 3 мин 24 с → 2 мин 17 с.
  - Резервная копия SQLite — проверка частями параллельно (`quick_check` + `integrity_check` по
    таблицам), сетевая база — через последовательный снимок на своем диске, копия получает имя
    только после проверки (`.part`): 1,36 ГБ — 23,5 → 20,5 с локально.
- ✅ **Массовые копии миллионов записей, маркеры и триггеры PostgreSQL** (20.10.2026). Замеры —
  [benchmarks.md](../../testing/benchmarks.md) («Что показали `dup` и триггеры PostgreSQL»),
  стенд `Tests/DbGenerator --shuffle`.
  - Дубль коллекции (SQLite): записи вставляются своими пакетами в заранее зарезервированный блок
    id (`ReserveRecordIds`), а не все в первой транзакции; пакет — по времени транзакции
    (`BatchPacer`, 8 с у локальной базы и 4 с у общей), проверка внешних ключей на время заливки
    снята. 300 тыс. записей вразнобой — 87 → 35,5 с.
  - Журнал WAL при дубле, удалении и переносе пакетами — не больше ~1 ГБ: операция сама переносит
    его между пакетами, когда он больше 512 МБ (`CheckpointIfWalLarge`). Дубль 1 млн записей
    вразнобой прежде кончался «database or disk is full» (журнал 15,4 ГБ), теперь — 4 мин 40 с.
  - Удаление коллекции пакетами: записи пакета — первые по индексу коллекции во временной
    таблице, вместо границы по Id, сортировавшей весь остаток коллекции на каждом пакете; пакет —
    по времени. 1 млн записей вразнобой — 5 мин 46 с и 10,7 ГБ журнала → 4 мин 57 с и 0,9 ГБ.
  - Перенос SQLite ↔ SQLite (ATTACH) — пакетами со своей транзакцией приемника вместо одной на всю
    копию: база назначения больше не заперта до конца копии, источник заморожен отдельным
    подключением. Удаление источника — под своим маркером; сбой, пока исходник не тронут,
    откатывает перенос, а после начала удаления копия больше не удаляется (прежде удалялась —
    данные пропадали в обеих базах).
  - Маркеры незавершенных копий — строка на операцию с владельцем и временем отметки
    (`pending.*`): монтирование общей базы коллегой больше не удаляет копию, которая еще идет.
  - PostgreSQL: триггеры сводок календаря на целый запрос (`CalendarStatementTriggersPg`) —
    1 млн строк проекции: вставка 75 → 10 с, удаление 57 → 1,6 с.
