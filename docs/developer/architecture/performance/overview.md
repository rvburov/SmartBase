# Производительность

Сквозной обзор: где приложение чувствительно к объему данных, какие приемы держат
скорость и какие узкие места еще открыты. Детали по конкретным фичам — в их
документах (подраздел «Производительность»); здесь — общая картина и принципы.

## Принципы

1. **Границы по содержимому, а не по форматированию.** Размер обрабатываемых данных
   считается по реально непустым ячейкам, а не по «следам» форматирования или
   набивке пустыми полями. Иначе объем раздувается на порядки (см. импорт).
2. **Виртуализация вместо «все в память».** Большие таблицы грузятся постранично из
   БД; в памяти держится ограниченное окно строк, а не вся коллекция.
3. **Батч-операции вместо по-записных.** Массовая вставка идет пачками в одной
   транзакции, с отключенным авто-отслеживанием изменений EF.
4. **Запросы по индексам и диапазонам.** Выборки фильтруются/сортируются по индексам
   и берут только нужный срез, а не «все подряд» с последующей фильтрацией в памяти.
5. **Фоновая работа с БД — только на отдельном подключении.** Общий `AppDbContext`
   ([DatabaseManager](../../../../Database/DatabaseManager.cs)) один на смонтированную БД и его
   делят ВСЕ репозитории (конструктор, календарь, категории). Он не потокобезопасен:
   обращение к нему с фонового потока, пока им же пользуется UI (дерево/календарь), валит EF
   («A second operation was started on this context instance»). Поэтому любая тяжелая операция
   с потока (импорт, копирование дубля, подгрузка страниц/значений) создает **свежий**
   `new AppDbContext(db.DbPath)`; WAL + `busy_timeout` дают параллельность без `SQLITE_BUSY`.
   Общий контекст трогаем строго из UI-потока.
6. **Перетаскивание ручки не переверстывает текст.** Ширина панели меняется на каждое
   движение мыши, а переверстка markdown стоит около 1,5 мс на килобайт (описание на 14 КБ —
   22 мс на кадр, на 28 КБ — 47 мс; обычный текст вдвое дешевле, высота не стоит ничего).
   Поэтому ручки ширины на время перетаскивания **замораживают ширину содержимого**
   (`RecordPageView.FreezeContentWidth`, `SettingsGuide.FreezeGuideWidth`): кадр падает до
   0,1 мс, текст встает по новой ширине один раз, при отпускании.

## Индексы БД

Текущие индексы на «данных» (см. [AppDbContextModelSnapshot](../../../../Database/Migrations/AppDbContextModelSnapshot.cs)):

| Таблица | Индекс | Назначение |
|---|---|---|
| `db_records` | `(CollectionId, Position)` | записи коллекции в порядке отображения (страницы, keyset) |
| `db_field_values` | `(RecordId, FieldId)` UNIQUE, `(FieldId, Value)` | значения записи / фильтр и подсчет по значению поля |
| `calendar_index` | `(RecordId, FieldId)` PK, `(CollectionId, StartIso)`, `(CollectionId, AllDay, StartIso, RecordId, FieldId)`, `(CollectionId, AllDay, EndIso, StartIso, RecordId, FieldId)`, `(FieldId)` | проекция событий: range-query окна (сплит по AllDay) / offset+keyset «Расписания» (хвост-ключ) / спилловеры окна сетки сиком по EndIso (без него день-гигант в 62-дневном буфере = секунды чтений строк) / FK-каскады |
| `db_fields` | `(CollectionId, Name)` UNIQUE | поля коллекции, уникальность имени |
| `db_collections` | `(GroupId)` | коллекции группы |
| `db_groups` | `(ParentId)` | дерево групп |

Миграции применяются автоматически при монтировании БД (`db.Database.Migrate()` в
[DatabaseManager](../../../../Database/DatabaseManager.cs)); см. [[database/storage-and-migrations]]. Прагмы скорости
([DatabaseManager](../../../../Database/DatabaseManager.cs)): `journal_mode=WAL` (параллельные
чтения во время записи), `synchronous=NORMAL` (быстрее коммиты при WAL), `temp_store=MEMORY`,
`mmap_size` и `cache_size` — **по объему памяти машины** (см.
[[database/storage-and-migrations]], «Объем кеша и mmap»): на рабочей станции прежние
256 МБ и ~64 МБ, на ноутбуке с 8 ГБ вчетверо меньше.

### Компактность файла

`auto_vacuum` выключен, поэтому после массовых удалений SQLite **не возвращает**
освобожденные страницы в ОС — файл остается размером с максимум своей истории (наблюдали
`database.db` = 705 МБ при 0.14 МБ данных; 1,7 ГБ у общей базы после трех сводов
трудоемкости по 650 тыс. строк). Политика — в [storage-and-migrations →
«Свободное место, сжатие, WAL»](../database/storage-and-migrations.md#свободное-место-сжатие-wal):
локальная база ужимается сама при монтировании (свободно > 64 МБ и ≥ 25 % файла, либо
> 512 МБ — `DatabaseManager.NeedsCompaction`), общая — только кнопкой «Сжать файл»
администратора (через очередь монтирования, с живым процентом), плюс «Резервная копия…»
(`VACUUM INTO`). Системная `app.db` — прежний тихий `SqliteMaintenance.CompactIfBloated`
(порог 1 МБ, она всегда мала). Из чего складывается байт на запись и где смотреть
(`dbsize`, `bloat`) — там же.

### Стоимость монтирования БД (подключение)

Монтирование гоняет конвейер в [DatabaseManager](../../../../Database/DatabaseManager.cs)
(миграции → прагмы → компактизация → бэкафилл календаря → сидинг). `MigrateAndBackfillCalendarDates`
— **одноразовая** миграция старых данных; ее тяжелый скан `db_field_values` теперь
пропускается, если индекс календаря уже построен (`if (db.CalendarIndex.Any()) return;`) —
новые данные (создание/импорт/правка) поддерживают `StartDt` и индекс инкрементально, так
что повторный скан на каждом подключении не нужен. Размонтирование (`Unmount`) — просто
`Dispose` контекста.

**Сетевые базы (общие)**: профиль медленнее локального — `synchronous=FULL` (каждый
коммит ждет диска сервера), `mmap_size=0`, журнал DELETE (писатели грубее исключают
читателей, чем WAL). Это цена целостности общего файла (см.
[multi-database](../database/multi-database.md)); массовый импорт на шаре ощутимо медленнее —
рекомендация: импортировать в локальную базу и перенести коллекцию. Фоновая
проверка чужих правок (ChangePoller, ~3 с) стоит одну `PRAGMA data_version` на
открытом соединении — микросекунды, нагрузки на шару практически нет.

Все недефолтные БД (старт и подключение из настроек) монтируются **фоновой очередью**
([MountQueue](../../../../Database/MountQueue.cs)): строго по одной (один тяжелый конвейер
в фоне максимум; параллельность умножила бы ~512 МБ кеша миграции и столкнула бы
сортировки на диске), стартовая партия — мелкие файлы первыми. UI-поток не блокируется:
у SQLite блокировки пофайловые, миграция базы Б не мешает запросам к базе А. Прогресс
виден в заглушках сайдбара и списке БД настроек. Обновление UI (`SyncMountedToUi`
→ сайдбары, календарь) — по завершении каждой; сетка календаря при этом сама грузит
окно в фоне (см. «Календарь»), поэтому подключение 10-млн БД не замораживает приложение.


## Известные узкие места / TODO

- **Строковые `Value` (EAV).** Фильтр по равенству и сортировка работают, но «число > N»,
  «дата в диапазоне» по строкам некорректны и не индексируются типобезопасно. Решение —
  типизированные колонки `ValueNumber/ValueDate` + индексы (Этап 4, см. [[../../../ROADMAP]]).
- **1000+ колонок — решено своей рисованной сеткой** (мера 9 дорожной карты,
  [drawn-grid.md](drawn-grid.md), этапы 0–6а ✅ 26.09.2026). Прежняя таблица на `DataGrid`
  создавала ячейки всех колонок для каждой видимой строки: замер на живом окне (2026-09)
  при **1000 свойств** против 16 — первая раскладка **6,4 с против 1,1 с**, куча **1108 МБ
  против 113 МБ**, рабочий набор **1526 МБ против 213 МБ** («программа съела 1,2-1,4 ГБ и
  подвисает»); скрытие колонок в «Отображении» памяти не экономило (`PopulateCellContent`
  наполнял ячейку до `IsVisible=false`). Рисованная сетка рисует только видимое окно строк ×
  колонок и читает значения только для него: 1000 колонок открываются за 0,03–0,15 с, кадр
  прокрутки 2–4 мс, куча таблицы — единицы мегабайт при любой ширине коллекции.

  Список свойств «Страницы записи» — рисованная поверхность (этап 7 плана, 26.09.2026):
  карточки рисуются только в окне прокрутки, контролов у них нет, редакторы — прежние контролы
  значений под указателем и при фокусе. Открытие записи на 1000 свойств 0,32 с холодно и
  26–34 мс тепло вместо 9,6 с, 109 объектов в дереве вместо 35 тысяч, шаг прокрутки на экран
  7–9 мс. Дальше по треку — пороги `Diag` по всей программе (этап 8).

## Как мерить

- `Stopwatch` вокруг методов репозитория (чтение страницы, импорт, выборка диапазона).
- У пользователя: пороги медленности и сторож UI-потока пишут отклонения в «Настройки →
  Диагностика» (`Logging/Diag`, `UiWatchdog` — см. [[../../features/logging]]): открытие раздела/коллекции/окна
  дольше 2 с, фильтр дольше 5 с, страница при прокрутке дольше 1 с, интерфейс не отвечал дольше 3 с.
- Синтетика: генерировать 100k+ записей/строк и воспроизводить сценарий (так уже
  замеряли чтение Excel и взрыв числа столбцов CSV).
- На что смотреть: число SQL-запросов на действие, рост памяти, скрытые O(n²)
  (пагинация, трекер EF, перебор всех строк в UI).
