# Уведомления

## Назначение

Уведомления приходят из **двух источников**, у каждого свой тумблер в «Настройки → Общее»:

| Источник | Тумблер (стандарт) | Повод | Кому |
|---|---|---|---|
| Календарь | «Уведомления календаря» (включено) | наступило событие (`StartDt`) | тому, у кого открыто приложение |
| Задачи · назначение | «Уведомления задачи «Исполнитель»» (выключено) | исполнителем задачи поставили другого человека | новому исполнителю |
| Задачи · стадия | «Уведомления задачи «Смена стадии»» (выключено) | у задачи сменилось значение свойства-статуса | тому, кто указан в «Назначил» |

Задачные виды выключены по стандарту сознательно: они осмысленны в общей базе с несколькими
людьми, поэтому включает их тот, кому они нужны, а не обновление приложения.

Оркестратор и значок-счетчик у них общие, логика отбора — разная: календарь отбирает по
времени, задачи — по очереди событий в базе. Разделы ниже: сперва календарь, затем
[уведомления по задачам](#уведомления-по-задачам).

## Календарь: напоминания о событиях

Когда у записи задано поле-дата и событие видно в
календаре, в момент его наступления показывается **нативный баннер ОС** (Windows / macOS /
Linux) с наименованием и деталями (время · коллекция) и **иконкой приложения**, а на иконке
приложения — **значок с количеством** непросмотренных уведомлений.

**Клик по баннеру** активирует окно приложения и открывает окно с полной информацией о
записи (наименование, дата/время, коллекция, описание) и кнопкой **«Принято»**
([NotificationRecordDialog](../../../Controls/Dialogs/NotificationRecordDialog.axaml.cs)). Чтобы
это работало (иконка приложения + клик обратно в программу), уведомление посылает САМ процесс
приложения; шелл-команды (`osascript`/`notify-send`) так не умеют — они рисуют чужую иконку и
по клику открывают чужую программу.

Служба живет вместе с процессом приложения. Пока приложение работает — баннер выходит в момент
события; события, наступившие пока приложение было закрыто, показываются при следующем запуске
(догон). Включается тумблером в **Настройки → Общее** (стандарт — включено).

Чтобы напоминания приходили и **при старте системы**, и **когда окно закрыто**, в том же
разделе «Общее» есть еще два независимых тумблера — **«Автозапуск при входе в систему»** и
**«Фоновый режим»** (оба по умолчанию выключены). Подробнее — раздел «Автозапуск, фон и трей».

## Как работает

`NotificationService` заводится в `MainWindow` и запускается в `Opened` (рядом с монитором БД
и поллером правок), останавливается в `Closed`.

> `Opened` приходит **не только на старте**: в фоновом режиме ([[autostart-background]]) «крестик»
> скрывает окно, а возврат из трея — это снова `Window.Show()`, который заново поднимает событие.
> Поэтому `Start()` **идемпотентен** (`if (_timer is not null) return`): иначе каждое открытие
> окна заводило бы еще один `DispatcherTimer` поверх работающего — старый никто не останавливал,
> тики (а значит и баннеры) множились бы, а метка откатывалась к последней сохраненной на диск.
> `Dispose()` симметрично обнуляет таймер.

**Проход** (`TickBackground`, раз в 30 с и один раз на старте):

1. Собрать кандидатов за окно `(watermark, now]` по всем допущенным БД — **вне UI-потока**
   (`Task.Run`), каждая БД читается на свежем подключении
   `ConstructorRepository.GetCalendarRecordsByRangeIsolated(from, to, activeIds: null)`. `null` =
   все видимые поля-даты (то же, что показывает календарь; временные галки сайдбара не учитываем —
   напоминания не должны пропадать оттого, что коллекцию убрали из вида). Показ плашек, значок и
   запись метки затем возвращаются в UI-поток (`Dispatcher.UIThread.Post`).
2. `NotificationScheduler.Decide` делает **точную отсечку** по `StartDt ∈ (watermark, now]`
   (источник намеренно отдает лишнее — буфер многодневных ±62 дня), дедуп по `(БД, Id, поле)`,
   и решает: показать по плашке на событие или, если наступивших больше порога (5, обычно —
   догон после закрытия), одну сводку «Пропущенные события / Наступило событий: N».
3. Показать баннеры (`INativeNotifier`), увеличить значок на число наступивших (`IAppBadge`),
   сдвинуть метку в `now`. В плашку кладется метка записи `db:id:field`, а сама запись
   запоминается в `NotificationService` — чтобы по клику открыть окно без запроса в БД.

**Клик по баннеру** приходит колбэком `INativeNotifier.Activated(tag)` (macOS — из делегата
Cocoa, Windows/Linux — из события библиотеки). `NotificationService` находит запись по метке и
поднимает `RecordActivated(record)`; `MainWindow` маршалит в UI-поток, активирует окно и
открывает `NotificationRecordDialog` с кнопкой «Принято». Сводка (догон) метки не несет —
клик по ней только активирует приложение.

**Водяная метка** (`notifyWatermark` в app.db) — инстант, до которого события уже обработаны.
В памяти двигается каждый проход; на диск пишется только когда что-то показали — при падении
не будет повторного показа. Первый запуск (метки нет) фиксирует «сейчас», чтобы не показать
всю историю разом. Живое включение тумблера ставит метку = «сейчас» (без разбора того, что
прошло, пока было выключено).

**Значок** = число показанных, но еще не просмотренных уведомлений. Активация окна
(`Activated`) означает «пользователь увидел» → значок гасится в 0. Выключение тумблера тоже
гасит значок.

Срабатывание — строго в `StartDt`. События «весь день» имеют старт в 00:00 своего дня, т.е.
уведомление о них приходит в начало дня (уточнить «предпочтительное время» — задача на потом).

### Платформенные бэкенды

Баннер (с иконкой приложения и колбэком клика) шлет сам процесс приложения:

| ОС      | Баннер (`INativeNotifier`)                                   | Значок на иконке                                   |
|---------|-------------------------------------------------------------|----------------------------------------------------|
| macOS   | свой код `MacNotifier`: `NSUserNotificationCenter` (libobjc, делегат клика) | Dock badge (`NSApp.dockTile.badgeLabel`, libobjc)  |
| Windows | `LibraryNotifier` → DesktopNotifications (WinRT-тост)        | overlay-иконка таскбара (`ITaskbarList3`, GDI)      |
| Linux   | `LibraryNotifier` → DesktopNotifications (freedesktop D-Bus) | Unity LauncherEntry через `gdbus` (best-effort)    |

Библиотека [**DesktopNotifications**](https://github.com/pr8x/DesktopNotifications) (пакеты
`DesktopNotifications` + `.Windows` + `.FreeDesktop`) дает нативные баннеры с иконкой и колбэк
клика для Windows/Linux; ее менеджер создается в `Program.BuildAvaloniaApp`. Пакет `.Avalonia`
НЕ подключен (завязан на Avalonia 0.10, у нас 11.2.3) — менеджеры создаем вручную. Apple-бэкенд
библиотеки — нефункциональная заглушка, поэтому **macOS реализован своим кодом**. Все бэкенды
никогда не бросают; фабрика `PlatformNotifications` выбирает по ОС, неподдержанная среда — no-op.

> ⚠️ **Windows требует своего таргета сборки** — `net10.0-windows10.0.17763`. NuGet выбирает
> файлы пакета по таргету: под голым `net10.0` от `DesktopNotifications.Windows` и
> `Microsoft.Toolkit.Uwp.Notifications` приезжают сборки БЕЗ WinRT, менеджер падает на старте
> с `TypeLoadException` (нет `ToastNotificationManagerCompat`), и баннеров нет вовсе — при
> живом значке-счетчике. Скрипт `Scripts/windows-build.sh` передает `-f` сам; при ручном
> `dotnet run`/`build` таргет надо указывать. Подробности — [build-and-run](../guides/build-and-run.md).
> Проверка на старте — строка в логе «Менеджер нативных уведомлений создан: …»
> (при сбое — предупреждение с исключением).

**Иконка приложения:** macOS берет ее из `.app`-бандла (`CFBundleIconFile`), Windows — из
ярлыка/AUMID (создает `WindowsApplicationContext`), Linux — из `.desktop`.

**Ограничения / на потом:**
- **macOS:** `NSUserNotification` помечен deprecated (с macOS 11), но работает из подписанного
  `.app`. В dev-режиме (`dotnet run`, без бандла) иконки/доставки может не быть — проверять на
  собранном `.app`. Современная замена — `UNUserNotificationCenter` (задача на потом).
- **Windows-тост** через библиотеку требует ярлыка в меню «Пуск» с AppUserModelID (создает
  контекст библиотеки) — иначе система покажет отправителем не приложение. Проверено на
  Windows 10 22H2 (04.08.2026): тост доходит до Центра уведомлений, ярлык создается сам.
- **Linux-значок** (Unity LauncherEntry) работает только в окружениях с его поддержкой (GNOME
  Dash-to-Dock, KDE, Unity) и требует `smartbase.desktop`.
- **Linux** (библиотека, D-Bus) **проверяется на своей ОС** — на dev-машине (macOS) не верифицируется.

### Производительность

Окно `(watermark, now]` крошечное, но источник намеренно отдает буфер многодневных событий
(±62 дня), поэтому timed-ветка **сканирует StartIso-диапазон в 62 дня** по `calendar_index`
(на плотных данных — десятки тысяч строк, десятки мс) и отбрасывает лишнее residual-фильтром
`EndIso`. На UI-потоке это давало микро-подвисание («колесико») раз в 30 с и на старте, тем
заметнее, чем больше БД и плотнее данные. Поэтому **чтение уведен с UI-потока** (`TickBackground`
→ `Task.Run` + `GetCalendarRecordsByRangeIsolated` на свежем `AppDbContext`), а на UI-поток
возвращается только показ плашек, значок и метка. Общий однопоточный контекст при этом не
трогается — правило «общий контекст только из UI-потока» соблюдено, см.
[../architecture/performance.md](../architecture/performance/overview.md).

Число баннеров ОС ограничено `NotificationScheduler.Decide`: при более чем 5 наступивших разом
показывается **одна сводка** «Наступило событий: N», а не N плашек — сколько бы событий (сотни,
тысячи) ни совпало по времени, нативный вызов ОС происходит не больше 5 раз за проход.

## Уведомления по задачам

Два вида: **«Вам назначена задача»** новому исполнителю и **«Задача сменила стадию»** тому, кто
указан в свойстве «Назначил». Работают на всех поверхностях, где значение свойства вообще можно
изменить: раздел «Задачи» (быстрое добавление и диалог), ячейка таблицы конструктора, страница и
панель записи, календарь — потому что событие рождается в единой точке записи значения.

### Конвейер

```
SetFieldValue → task_events (очередь в базе) → TaskEventReader (курсор на базу)
              → TaskEventScheduler (отбор и текст) → баннер ОС → клик → карточка задачи
```

Очередь в базе выбрана вместо сравнения слепков состояния на клиенте по двум причинам: строка
знает **автора** правки (иначе «я назначил задачу сам себе» неотличимо от «меня назначили»,
особенно с учетом того, что `AddRecord` автозаполняет user-поля текущим пользователем) и
**старое значение**; а стоимость опроса не зависит от размера базы — обычный тик это один
`SELECT MAX(Id)` обратным сканом PK, как в [ChangePoller](../../../Database/ChangePoller.cs).

### Когда событие пишется

Внутри `SetFieldValue`, если правили поле-роль. Роль = флаг **и** подходящий тип (правило
`HasRole`): флаг, оставшийся на поле после смены типа, роли не несет. На обычной правке ячейки
новых запросов не появляется — метаданные поля этот метод читал и раньше, для журнала.

- **assigned** — новое значение непустое и получатель **не автор**. Свое назначение не пишется
  вовсе: баннер о задаче, которую сам себе и завел, — чистый шум.
- **status** — старое значение **непустое** (первичная простановка при создании задачи — не
  смена стадии, иначе каждое добавление давало бы баннер «стадия: Запланировано») и у задачи
  заполнено «Назначил». Автора здесь **не исключаем**: назначивший ждет сигнала о движении
  задачи, даже когда двигает ее сам.

Имя из ячейки разрешается в `UserKey` по `db_users` — сравнением **в памяти** без учета
регистра (SQL-сравнение кириллицы без учета регистра SQLite не умеет, тот же довод, что у
`MeVariants`). Не нашли — ключ пустой, и получателя опознает по имени сам клиент.

### Что уведомлений НЕ дает

| Путь | Почему |
|---|---|
| Автозаполнение user-полей при создании записи (`AddRecord`) | пишет мимо `SetFieldValue` и вписывает СЕБЯ — получатель совпал бы с автором |
| Дублирование записи и пакетное дублирование | копия — не назначение; на 100k записей это 100k строк очереди |
| Пакетный перенос записей, импорт, дубль и межбазовый перенос коллекции | массовый bulk-SQL мимо `SetFieldValue` |
| Перенос одиночной записи (`CopyFieldValuesByName`) | явно подавлено `SuppressTaskEvents`: значения переезжают в ДРУГУЮ запись, исполнитель не менялся |
| Смена типа свойства (перезапись значений) | служебная операция, а не действие над задачей |

> **Известное поведение.** Смена коллекции у задачи пересоздает запись (календарный путь), и
> исполнитель получит «Вам назначена задача», даже если сам исполнитель не менялся: в новой
> записи значение проставляется впервые. Операция редкая, а текст по смыслу не врет — задача
> действительно переехала. Убирается передачей прежнего исполнителя как явного «было» в
> `UpdateTaskRecord`, если это начнет мешать.

### Курсоры и догон

Курсор прочитанного — **на каждую базу**, в app.db одним ключом `notifyTaskCursors` (формат
`db:id;db:id`, как галочки коллекций). Первое знакомство с базой историю не проигрывает: курсор
садится на текущий хвост очереди. Курсор фиксируется **каждым проходом** (а не только когда
что-то показали): за прочитанным диапазоном стоят и чужие события, которые иначе перечитывались
бы каждым тиком. Персистентность курсора и дает догон — события, случившиеся при закрытом
приложении, доедут при следующем запуске.

Включение тумблера на лету не вываливает накопленное: ближайший тик вместо чтения сдвигает
курсоры на хвост (`Reseed`) — симметрия с «включили календарь → метка = сейчас».

### Отбор, тексты, клик

`TaskEventScheduler.Decide` фильтрует по включенным видам и **сворачивает повторы** по ключу
`(БД, запись, поле, вид)`: за время простоя стадия могла пройти «Запланировано → В работе →
Выполнено», поэтому плашка одна, но «было» берется от первого события — иначе текст соврет,
откуда задача пришла.

| Вид | Заголовок | Тело |
|---|---|---|
| Назначение | `Вам назначена задача` | `{Название} · {Кто назначил}` (нет автора → коллекция) |
| Стадия | `Задача сменила стадию` | `{Название}: {Было} → {Стало}` |
| Сводка (> 5) | `Обновления по задачам` | `Назначено задач: N · Смен стадии: M` |

Метка плашки — `task:{DbId}:{EventId}`, с приставкой: календарная выглядит как `db:id:field`, и
по приставке служба понимает, куда вести. Клик поднимает `TaskActivated`, `MainWindow`
переключает раздел «Задачи» и открывает **карточку задачи** — тот же диалог, что по двойному
клику в списке. Задача перечитывается из базы (`GetTaskRecordsByIds`), а не берется из
показанного списка: раздел мог быть не загружен, задача — не попасть в фильтр, а название и
стадия за время показа баннера уже поменяться. Задачи нет (удалили, перенесли) — строка ошибки
в списке.

### Ретеншен и права

Очередь чистится при монтировании базы: события старше 90 суток удаляются (`ApplyTaskEventsRetention`,
фон, best-effort — как автоочистка журнала). Отдельной настройки нет: события — расходный
материал доставки, а не история.

Изолированное чтение очереди прав не проверяет (у фоновых репозиториев их нет), поэтому баннер
показывается, только если у пользователя есть `ViewCollection` на коллекцию события: доступ мог
быть отозван уже после записи.

## Автозапуск и фоновый режим

Чтобы напоминания приходили при старте системы и когда окно закрыто, служат еще два тумблера в
«Общее» — «Автозапуск при входе в систему» и «Фоновый режим» (значок в трее + скрытие окна).
Устройство вынесено в отдельный документ: [[autostart-background]].

## Сообщения внутри окна

Отдельно от нативных баннеров ОС живут **сообщения приложения человеку** — карточки в
правом верхнем углу главного окна ([AppNotifications](../../../Controls/Widgets/AppNotifications.cs)):
стопкой (новые встают под старыми, видно до четырех), друг друга не перекрывают, сами
гаснут через 6 с, длинный текст переносится. Механизм — встроенный
`WindowNotificationManager` Avalonia, установленный в слой оверлея окна внутри обертки
с зумом приложения (`WindowZoom.WrapPopupContent`, иначе карточки не масштабировались бы
вместе с интерфейсом). Содержимое каждой карточки — обычный
[NoticeBanner](../../../Controls/Widgets/NoticeBanner.axaml) (красный `Error` для ошибок,
синий `Info` для сведений), сама карточка `NotificationCard` оформления не имеет (стиль в
`Assets/Styles/Controls.axaml`) — вид тот же, что у баннеров в диалогах.

Кто пользуется: ошибки записи в базу (`DbErrors`: «база занята», «недоступна»,
«изменил другой пользователь»), отброшенные правки удаленных соседом строк
(`AppDbContext.PhantomRowsDropped`), допуск администратора, переходы по чипам связи,
непредвиденные ошибки UI-потока (хук `Dispatcher.UIThread.UnhandledException` в `App`:
след в crash.log, процесс продолжает работать). Вызывать можно с любого потока.

Чего здесь **нет**: статуса доступности базы. Он живет надписью под именем базы в
сайдбаре и в «Управление базой данных» (см. [[../architecture/database/multi-database]]).
Раньше те же сообщения были всплывашками (`Toast`) у панели разделов в левом нижнем углу:
каждая — отдельный Flyout на одном якоре, два сообщения подряд ложились друг на друга и
резались краем окна. `Toast.Error` у конкретного якоря (строка дерева, заголовок,
редактор) остается для локальных ошибок на месте действия.

## Взаимодействия

- **Календарь** ([[calendar/overview]]) — источник событий (`calendar_index`, `GetCalendarRecordsByRange`).
- **Задачи** ([[tasks]]) — второй источник: правка свойств-ролей «Исполнитель» и «Статус»
  кладет строку в `task_events`, клик по баннеру открывает карточку задачи.
- **Настройки** ([[settings]]) — три тумблера в разделе «Общее»; хранение в app.db через `AppSettings`.
- **Значок приложения** ([[icons]]) — та же иконка, что в доке/таскбаре, поверх нее рисуется счетчик.
- **Автозапуск и фон** ([[autostart-background]]) — доставка напоминаний без открытого окна / после входа в систему.
