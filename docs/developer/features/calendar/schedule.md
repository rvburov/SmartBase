# Режим «Расписание»

## Назначение

Плоский список событий **одного дня** (повестка дня). Заголовок в навбаре —
дата с цветовой подсказкой: сегодня — красная, прошлое — серое, будущее — обычная.

> В коде режим называется `ListView` (индекс 0). В интерфейсе — «Расписание».

## Где в коде

- View + логика: [ListView.axaml.cs](../../../../Views/ConstructorDb/Calendar/ListView.axaml.cs)
- Элемент списка: класс `EventListItem` (там же)
- Виртуальный список: [CalendarDayVirtualList.cs](../../../../Views/ConstructorDb/Calendar/CalendarDayVirtualList.cs)
- Данные: `ListViewCtrl.LoadFrom(sources, dayStart, dayEnd, currentDate, search)`; диапазон от
  контроллера — один день, `sources` — список подключённых БД с активными коллекциями
- Запросы: `GetCalendarDayEventsByOffset` / `LoadCalendarDayPageAsync` / `CountCalendarDayEvents`
  в [ConstructorRepository.cs](../../../../Database/Repositories/ConstructorRepository.cs)

## Как работает

В одном дне событий могут быть **миллионы**, поэтому список **полностью виртуализирован**
(аналог `VirtualRowList` таблицы): `CalendarDayVirtualList` реализует `IList`, знает лишь ПОЛНОЕ
число событий дня — полоса прокрутки соответствует всему объёму (можно перетащить в самый низ),
а `VirtualizingStackPanel` реализует только видимые строки. Порядок: «весь день» первыми, затем
по времени начала. Число событий считается **асинхронно до построения списка** (изолированные
подключения, в списке на это время «Загрузка…»): холодный COUNT по дню с миллионами событий —
секунды, UI-поток не блокируется (иначе старт приложения замирал на «Запуске интерфейса…»).
Счётчики **кешируются по дням** (`_dayCountsCache` в ListView): повторный визит дня (Prev/
Next/«Сегодня», возврат из поиска) строит список сразу, без повторного COUNT; дельта правок
держит кеш актуальным точечно (по дню начала записи — в т.ч. оба дня при переносе даты), а
смена источников/активных коллекций или пересборка без дельты (внешнее изменение) сбрасывает
его целиком. Два режима (по суммарному числу событий дня):

- **InMemory** (≤ 10 000): день грузится сразу и **сливается по времени** между
  БД — точный порядок «Расписания». Покрывает все реальные дни. Поиск — отдельный путь:
  фоновый SQL по всему дню (`SearchCalendarEventsAsync`, нативный LIKE с регистровыми
  вариантами), первые 1000 совпадений — находит в любом месте дня даже на миллионах.
- **Offset** (> 10 000): экстремальный день. Страница грузится на изолированном подключении
  **в фоне**; до прихода данных — строки-заглушки «Загрузка…» (слева, вровень с заголовком).
  **Одна БД** — способ чтения:
  - **прыжок** полосой прокрутки (нет соседней загруженной страницы) → **offset**: пропуск по
    покрывающему индексу `calendar_index(CollectionId, AllDay, StartIso, RecordId, FieldId)`, join к
    `db_records` — только для строк страницы, поэтому прыжок даже в конец дня — доли секунды;
  - **последовательная прокрутка** (страница идёт за уже загруженной) → **keyset** от последней
    строки предыдущей: O(страницы) ≈ мс, не зависит от глубины (гладкий скролл колесом).
  Оба способа читают по одному ключу `(StartIso, RecordId, FieldId)` (хвост индекса), фазы
  all-day→timed совпадают → страницы keyset и offset стыкуются **без дублей/пропусков**.
  **Несколько БД** — **порядок по времени между базами** даёт ПОСЕКУНДНАЯ карта, как в гигантском
  дне «Журнала» (`LoadCalendarDayTimeHistogramAsync`: гистограммы секунд от каждого источника
  сливаются в бакеты с префикс-суммами, строится один раз на день в фоне — на это время
  «Загрузка…»): события идут строго по секундам, конкатенация источников остаётся только внутри
  одной и той же секунды (раньше базы шли целыми блоками — время «прыгало» между БД); карта
  правится точечно при правках. Загрузка **с дебаунсом** (пауза после скролла): при быстром
  перетаскивании транзитные страницы вытесняются и запрос не тратят — грузятся только осевшие
  видимые (свежие первыми); «дырявые» после точечной правки страницы дочитываются по требованию.

Каждое событие оборачивается в `EventListItem` (`Fill` заполняет заглушку на месте):

- `Title` = `DisplayTitle` события;
- `DateTimeText` = «Весь день» или `HH:mm – HH:mm`;
- `Description` = текст без markdown-разметки ([MarkdownUtils.StripMarkdown](../../../../Utils/MarkdownUtils.cs));
- `ColorBrush` = цвет события ([EventColors.Display](../../../../Core/Models/EventColors.cs));
- прошедший день → заголовок серый (`#8E8E93`).

Если событий нет — показывается подсказка `EmptyHint`.

## Взаимодействия

- **Клик** — выделить; **Shift+клик** — добавить/снять (множественное выделение);
  **Ctrl+Shift+клик** — выделить диапазон от последней выделенной записи до кликнутой.
- **Двойной клик по событию** → выделяет запись и открывает редактирование (`RecordClicked`);
  после «Сохранить»/«Отмена» запись остаётся подсвеченной.
- **Двойной клик по фону** / пункт «Создать» в меню фона → `CreateRequested(currentDate)`.
- **Delete/Backspace** — удалить выделенное (с подтверждением; выделение видно, пока открыт диалог).
- **Правый клик** — контекстное меню ([EventContextMenu](../../../../Controls/Components/)): по
  событию — «Редактировать»/«Дублировать»/«Удалить», по нескольким — «Дублировать»+«Удалить»,
  по фону — «Создать».

### Тихое обновление (правка/дублирование — как в «Журнале»)

Создание/правка/удаление/дублирование правят список **НА МЕСТЕ** (`ApplyDeltaAsync` в
`CalendarDayVirtualList`), не пересоздавая его: реализованные строки переживают правку, поэтому
даже в offset-режиме гигантского дня (миллионы событий) нет волны «Загрузка…», позиция и
выделение сохраняются в том же кадре. InMemory-день мутируется прямо в списке (без БД);
в offset-режиме удаления пересаживают строки арифметикой (позиции удаляемых известны из кеша),
а вставка выбирает позицию по приоритету: правка без смены времени — ТА ЖЕ позиция, что у
старой строки (без БД — только текст меняется, страницы остаются полными); копия при
дублировании — СРАЗУ ПОД строкой с теми же временем и названием (прямо под оригиналом — а не
в конец группы записей с одинаковой секундой; истинный порядок БД восстановится при следующем
открытии дня), поэтому и массовый дубль (сотни копий) правится на месте без пересборки; иначе —
`CountCalendarDayEventsBeforeAsync`: ранг записи в дне её источника одним COUNT по покрывающему
индексу, без перечитывания дня (таких вставок за раз не больше 8 — дальше тихая пересборка). Созданная/изменённая запись (или копия) появляется
сразу выделенной; к ней (или к последней по времени копии) список едет по центру, только если
строка ПОЛНОСТЬЮ не видна — частично срезанная краем строка считается видимой, правка видимой
записи экран не двигает. Дублирование — с подтверждением («Вы дублируете N записей», кнопка
«Дублировать»), выделение ПЕРЕХОДИТ с оригиналов на копии. Прокрутка наверх остаётся для
«свежих» загрузок: другой день, смена поиска, первый показ.

Каждая операция даёт **ровно один** refresh: дельта ставится ДО `CollectionsMayHaveChanged`
(`NotifyChangedAndRefresh` в контроллере) — обновление сайдбара потребляет её и правит ленту
на месте, а страховочный `RefreshCurrent` срабатывает, только если дельту никто не съел.
Прежний порядок запускал на каждую правку холостую пересборку без дельты: её отменяло
поколение (моргания не было), но фоновый пересчёт дня уходил впустую и не давал кешу
счётчиков жить.

Подробнее об общих правилах — [interactions.md](interactions.md).
