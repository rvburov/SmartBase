# Таблица коллекции (TableView)

## Назначение

Основной режим коллекции — таблица (спредшит): строки-записи × колонки-поля.
Поддерживает редактирование значений прямо в ячейках, изменение ширины колонок и
высоты строк, переупорядочивание и скрытие колонок/строк, мультивыделение.

Показ — **своя рисованная сетка** (план и история переезда — [drawn-grid.md](../../architecture/performance/drawn-grid.md)):
рисуется только видимое окно строк × колонок, контролов у ячеек нет, поэтому таблица открывается
и прокручивается за один кадр при любом числе колонок и записей.

## Как работает

### Колонки

Колонки строятся из полей коллекции (`GetFields`) плюс системная «Название»
(`__title__`) — единственная, что не является полем. «Описание» — обычное поле
(роль `IsDescription`), в новой коллекции его нет: см. [[../../architecture/data-types/description]].
Порядок, ширины, видимость и уровни колонок берутся из UI-настроек коллекции:

- порядок — `GetColumnOrder` / `MoveColumn` / `MoveColumnAfter` / `SaveColumnOrder`;
- ширины — аспект `Width` в `column_meta`: `GetColumnWidths` / `SaveColumnWidths` / `ClearColumnWidths`;
- видимость/уровни — `SaveColumnDisplay`;
- подпись системной колонки — `GetSystemFieldNames` / `SetSystemFieldName`.

Все это читается одним снимком открытия (`ReadOpenSnapshot`, в фоне — `ReadOpenSnapshotAsync`,
без COUNT) и одной точкой `LoadColumnState` при любой пересборке колонок. Фасад строит
определения (`TableColumnDef`: тип, опции, формат, меню шапки, хуки клика) и отдает их сетке —
та раскладывает их по ширинам и рисует. Готовый список отдается наверх через событие
`ColumnsBuilt`, а `MovableKeysInOrder()` / `MovableColumnsInOrder()` дают текущий порядок для
диалогов.

**Операции над колонками** (сдвиг, «Отображение», создание в конце и после, дубль, смена типа,
удаление, переименование «Названия») сходятся в одном `ReloadColumns`: состояние колонок
читается один раз, сетка получает новую раскладку, **строки и прокрутка остаются** — список
строк узнает новые поля на месте (`VirtualRowList.SetFields`, для новой колонки-связи догревает
связи), ручные ширины живут по ключам, выделение ячеек и колонок едет за своими ключами, отбор по
удаленной колонке снимается (`PruneFilters`). Скрытая в «Отображении» колонка остается в
`_colDefs` (порядок, фильтры, перемещение), но в раскладке ее нет: ни ширины, ни ячеек, ни
значений в странице.

### Сетка: что рисуется и кто за что отвечает

| Часть | Ответственность |
|---|---|
| `GridSurface` | рисует шапку (иконка типа, название, кнопка фильтра с шевроном или воронкой), фоны и цвета ячеек, наведение, текст и глифы (галочка, скрепка, плашки связи), линии на физической пиксельной сетке, рамку и тонировку выделения, заглушки «Загрузка…»; попадание (`HitTest` → `GridHit`: ячейка, «№», шапка, кнопка фильтра, зоны захвата ширины и высоты); наведение с курсором и подсказкой; единственный фокусируемый элемент тела таблицы; перечитывает токены на зум, DPI, шрифт, плотность и тему |
| `ColumnLayout` | видимые колонки в порядке показа, ширины целыми квантами (стандартные поровну от ширины окна, ручные из модели с раздачей остатка), префиксные суммы, ключ ↔ позиция, хит-тест по X |
| `RowLayout` | стандартный шаг и разреженные ручные высоты по индексам с префиксными суммами: положение строки за O(log n) на 10 млн строк |
| `GridPanel` | модель таблицы: определения колонок, ширины и высоты с сохранением, оформление строк и колонок, режимы, отбор и сортировка (`SetQuery` → `RowSourcePlanner` в фоне с отменой), счетчик записей из фона, две полосы с автоскрытием, навигация нижней панели, прокрутка к записи и ячейке, якорь для окна фильтра |
| `EditorHost` | один накладной редактор над ячейкой: едет за прокруткой, ширинами и высотами, над шапкой обрезан |
| `SelectionOverlay` | рамка выделения кодом поверхности над редактором — в правке не гаснет |

Кадр перерисовывается по приходу страницы (одна перерисовка на кадр, сколько бы строк ни
дозаполнилось), по прокрутке и по смене раскладки; событий на каждую ячейку нет. Все
рисование и хит-тест — на UI-потоке, данные — в фоне.

### Редактирование значений

Значения сохраняются в БД без кнопки «сохранить» (`SetFieldValue` через сеттер индексатора
`TableRowVm`). Редакторы с выбором (дата, список, галочка, мультисписок, связь) пишут при каждом
изменении — оно у них одно на правку. Текстовые редакторы (текст, ссылка, число, «Название») к
строке НЕ привязаны и пишут ОДИН раз, при выходе из правки — см. «Текстовые редакторы пишут при
коммите» ниже. Тип ввода зависит от `FieldType` поля.

> Реестр типов свойств (коды, хранение, семантика) — сквозной и описан один раз в
> [data-model.md → «Типы полей»](../../architecture/data-model.md#типы-полей-свойств)
> (единый источник [`FieldTypeInfo`](../../../../Core/Models/FieldTypeInfo.cs)). Ниже — только то,
> как типы **представлены в таблице**. Round-trip запись→чтение по всем типам проверяет
> `FieldTypeMatrixTests`.

### Редакторы ячеек по типам

Показ всех типов рисует сетка (текст, галочка, скрепка и имя файла, плашки связи). Правка —
накладной редактор по типу (`BuildCellEditor`):

| Тип | Редактор ячейки в таблице |
|---|---|
| `text` | текстовое поле (многострочный текст — в нижнем блоке панели записи) |
| `number` | текстовое поле с фильтром ввода, число правится в показанном формате |
| `date` | `DateEditor` (диапазоны, время, «весь день») |
| `select` | ComboBox из опций |
| `status` | ComboBox из опций (как `select`) |
| `multiselect` | показ — значения через разделитель; правка — `MultiSelectBox` (выпадающий чеклист с поиском); значение JSON-массивом |
| `checkbox` | редактора нет: клик по квадрату или пробел на выделенной ячейке переключают |
| `url` | текстовое поле (watermark `https://`) |
| `user` | ComboBox из `GetUserOptions()` |
| `file` | редактора по Enter нет: в ручном режиме скрепка — системный выбор файла, клик по имени — открыть файл или поправить путь (`FileEditor` над ячейкой); несколько файлов авто-привязки — отдельные имена-ссылки через запятую |
| `relation` | `RelationSelectBox`: показ и поиск по выбранным свойствам цели; ручной чеклист, автосвязь — только просмотр и переход |
| `lookup` / `rollup` | **нет** — вычисление по связанным записям, только чтение |
| `created_*` / `updated_*` | **нет** — read-only (см. ниже) |

### Вычисляемые типы (авто-метаданные записи)

Типы `created_at/updated_at/created_by/updated_by` — **read-only**, значение из аудит-метаданных
записи (реестр и источники — [data-model.md](../../architecture/data-model.md#типы-полей-свойств)).
Как таблица их показывает:

- колонка `IsReadOnly` (редактор не открывается); ячейка — текст из свойств строки
  (`TableRowVm.CreatedAt/UpdatedAt/CreatedBy/UpdatedBy`), приглушенный, даты — `дд.MM.гггг чч:мм`.
  То же read-only в панели записи ([[record-page]]);
- в диалоге «Тип» стоят внизу — четвертой группой списка, отделенной чертой
  (`ItemContainerTheme` — вне подсветки пункта и поля выбора; про группы см.
  [ui/dialogs.md](../../ui/dialogs.md#группы-типов-в-списке-свойства));
- **стамп** метаданных: создание — `AppDbContext.SaveChanges` (+ `AddRecord`); правки —
  `TouchUpdated` (название/описание/дата) и сырой `UPDATE db_records` в `SetFieldValue` (только при
  реальной смене значения; синхронизирует EF-трекер, иначе `GetRecord` вернул бы старое «изменено»);
- **фильтр/сортировка** по этим колонкам пока не функциональны (значения не в `db_field_values`).

### Вычисления по связанным записям

`lookup` («Данные из связи») читает выбранное свойство целей связи;
`rollup` («Итог по связи») считает количество, сумму, среднее, минимум, максимум,
самую раннюю или самую позднюю дату. Оба столбца создаются и настраиваются в окне своей
связи (блок «Данные из связанных записей»), а не отдельными типами. Оба типа доступны только для чтения: значение берется через
`GetRelationComputedValues`, отдельного значения в `db_field_values` нет.
`FieldTypeInfo.IsAuditComputed` отделяет их от аудит-метаданных.

Чтение целей пакетное, с учетом пары `(DbId, RecordId)`, прав на целевую коллекцию
и защиты от циклов. Отсутствие доступа или базы показывается как состояние ошибки,
а не превращается в совпадение автосвязи. В фоне используются отдельные контексты
с проверкой прав и заранее снятой картой подключений.

Сырые значения и подписи разделены: одиночный lookup сохраняет тип и исходное
значение цели, множественный — типизированный JSON-массив, показ соединяет подписи.
Rollup хранит ключ фильтра в числовом каноне (`1.5`), показывает `1,5` и сортируется
как число; итог по датам хранит дату цели в ISO-каноне, показывается и сортируется как дата
(`ColumnSort.RollupKey`). Чтение страницы, фильтр, сортировка и экспорт используют актуальные
вычисления. Для переноса настроек и идентичности связей нужен переносимый JSON;
CSV содержит текст показа (см. [импорт и экспорт](../../../user/import-export.md)).

### Смена типа поля (текст ↔ дата)

При смене типа поля в «Изменить свойство» (`UpdateField`) уже сохраненные значения
**приводятся к новому типу без потери данных** — `ConstructorRepository.ConvertFieldValuesForTypeChange`:

- **текст → дата:** значение разбирается (`DateValue.TryParse`, понимает и `дд.MM.гггг`,
  и ISO) и переписывается в ISO-канон (`ToStorage`, например `2026-02-01`) — тот же вид,
  что пишет редактор даты; дата сразу читается таблицей, календарем и редактором;
- **дата → текст:** ISO-канон разбирается и переписывается в человекочитаемое
  `дд.MM.гггг` (`ToDisplay`), чтобы текст сохранил дату в привычном виде, а не как
  `2026-02-01`.

Неразбираемое значение остается как есть (произвольный текст — просто не дата, потери нет).
Конвертация идет сырым ADO.NET-пакетом в одной транзакции (значений может быть много) и
**до** пересборки `calendar_index`, чтобы индекс строился по каноническим значениям. Это и
есть штатный путь после импорта: столбец приходит текстом (см. [[../import-export/overview]]),
затем переводится в дату и обратно без искажений.

### Цвет строк, ячеек и текста

Меню строки → «Изменить цвет» дает четыре подменю, меню заголовка колонки — еще два.
Все они строятся общей фабрикой [ColorMenu](../../../../Controls/Components/ColorMenu.cs)
поверх палитры [AppPalette](../../../../Core/Models/AppPalette.cs) — той же, что красит
коллекции в сайдбаре. В пунктах один цветной чекбокс по стандарту календаря и задач:
цветная рамка без заливки у снятого, цветная заливка и белая галочка у текущего цвета.
«Без цвета» показано нейтральным серым. Отдельных цветных квадратов и букв для текста нет;
назначение цвета остается одиночным выбором. Тот же `ColorMenu.CreateCheckBox` используется
в цветовом фильтре и меню коллекции сайдбара.

| Пункт | Что красит | Где хранится |
|---|---|---|
| «Фон строки» / «Цвет текста строки» | строку в ЭТОЙ таблице | `record_display.Bg/Fg` |
| «Фон ячейки» / «Цвет текста ячейки» | ячейку, по которой был правый клик | `cell_style` |
| «Фон колонки» / «Цвет текста колонки» | всю колонку | `column_meta.Bg/Fg` |

Все это — оформление ОДНОЙ таблицы: наружу (в календарь, задачи, «Список», панель записи)
не выходит и в журнал не пишется. Сквозной цвет записи был отдельным уровнем и убран —
почему, см. data-model.md ниже.

Модель хранения и каскад приоритетов — [data-model.md → «Цвет»](../../architecture/data-model.md#цвет-оформление-таблицы).
Каждый пункт применяется ко ВСЕМУ выделению — как удаление и дубль: строки к выделенным
строкам (`TargetRecordIds`), колонки к выделенным колонкам (`TargetColumnKeys`, вместе с
системной «Название» — ее, в отличие от удаления, красить можно), ячейка — к той же колонке
во всех выделенных строках. Отмечен галочкой цвет ТОЙ строки/колонки, по которой кликнули.
После смены цвета колонок выделение снимается: голубая заливка выделения лежит под
полупрозрачным цветом, и на выделенной колонке разницу «покрасил / снял» почти не видно.
Права: цвет строки и ячейки — `EditRecord`, цвет колонки — `EditField`; новых битов маски
не заводилось.

**Что выставлено последним, то и видно** — общее правило цвета и расположения текста (решение
пользователя от 15.10.2026: искать ячейку с особой настройкой среди миллионов строк невозможно):

- выставление строке или колонке (`SetRowStyle` / `SetColumnStyle`) снимает этот аспект у ее
  ячеек — двумя командами базе (`ExecuteUpdate` / `ExecuteDelete` по `cell_style`, список
  записей или ключей колонок уходит одним параметром), по всем записям, а не по загруженным;
  загруженные строки сетка правит сама (`TableRowVm.DropCellAspects`), не перечитывая;
- снимается только тот аспект, что меняли: горизонталь колонки не трогает вертикаль и цвет ячеек;
- между строкой и колонкой побеждает выставленное позже — по отметкам выставления
  (`record_display` / `column_meta`: `BgAt`, `FgAt`, `HAlignAt`, `VAlignAt`, тики UTC,
  `StyleStamps.Next` строго растет). «По умолчанию» / «Без цвета» строке или колонке — отметка
  без значения: оно перебивает выставленное раньше другим уровнем. Такую отметку пишут, только
  если перебивать есть что (у какой-то колонки, соответственно строки, аспект задан значением),
  иначе сброс просто снимает аспект и строка-дельта уходит;
- ячейка отметок не несет: она всегда последняя в своей строке и колонке, потому что их смена
  ее сбрасывает. «По умолчанию» ячейке открывает то, что выставлено позже, — строку или колонку;
- оформление до этого правила отметок не несет — там строка сильнее колонки, как было;
- пакетная раскраска строк (`BulkSetRowStyle`, свод трудоемкости) отметку ставит, а ячейки не
  трогает: она красит только что созданные записи и следом свои ячейки;
- отметки едут с коллекцией при дубле и переносе (обе базы, оба провайдера, снимок `UiSnapshot`);
  старые версии программы их не читают и на пересечениях показывают строку.

Как это нарисовано:

- цвет — **заливка и кисть текста при рисовании ячейки** (`GridSurface`): каскад
  `RowStyle.Resolve` (ячейка → выставленное позже из строки и колонки) считается на кадре, заливка полупрозрачна
  (`ColorTools.Fill`) — наведение, выделение строки и колонки просвечивают сквозь цвет; цвет
  текста перекрывает серый плейсхолдер «Без названия» и приглушенность вычисляемых;
- оформление строк и колонок живет словарями в `GridPanel` (читаются при открытии и
  перезагрузке, меняются точечно `ApplyRowStyle` / `ApplyColumnStyle` → перерисовка);
  оформление ячеек — в самих строках (`TableRowVm.CellStyles`), приезжает батчем на страницу
  (`GetCellStylesBatch`) и меняется `SetStyle` с уведомлением «Item», по которому сетка
  перерисовывает кадр;
- сетка рисует правящуюся ячейку без значения и цвета: заливку под редактор кладет держатель
  правки на всю ячейку (`EditorHost` ← `GridSurface.EditorFill`; редакторы прозрачные — так цвет
  не пропадает и у редактора в полосе у края, см. «Расположение текста» ниже), цвет текста
  редактор ставит себе сам (`ApplyEditorCellStyle`);
- полоски цвета в колонке «№» НЕТ. Она была у сквозного цвета записи (приглушенная заливка
  под выделением строки читается плохо) и уехала вместе с ним: у оформления таблицы
  «пометки на полях» не ждут.

### Расположение текста

Меню ячейки, строки («№») и заголовка колонки → «Форматирование текста» → «Расположение текста»:
«Горизонтально слева / по центру / справа», «Вертикально сверху / по центру / снизу» и «По
умолчанию». Пункт стоит сразу под «Изменить цвет» и устроен так же: те же три уровня, тот же
адресат (все выделение — `TargetRecordIds`, `TargetColumnKeys`, выделенные ячейки) и те же права
(`EditRecord` у строки и ячейки, `EditField` у колонки; запрещенный пункт не гаснет, а объясняет
причину). Код — [TableView.TextFormat.cs](../../../../Views/ConstructorDb/TableView.TextFormat.cs).

| Уровень | Где хранится |
|---|---|
| ячейка | `cell_style.HAlign/VAlign` |
| строка | `record_display.HAlign/VAlign` |
| колонка | `column_meta.HAlign/VAlign` |

- **Каскад — тот же `RowStyle.Resolve`** и то же правило «выставленное последним» (см. «Цвет строк, ячеек и
  текста» выше): строка или колонка снимает расположение своих ячеек, на пересечении — выставленное
  позже; горизонталь и вертикаль отдельно. Не задано нигде — правило типа `CellAlign.DefaultH`:
  число вправо, остальное влево; по вертикали центр. «По умолчанию» снимает оба аспекта уровня
  одной записью (перегрузки `SetCellStyle` / `SetRowStyle` / `SetColumnStyle` со списком изменений).
- **Хранится словами** (`left/center/right`, `top/center/bottom`), мусор при чтении отбрасывает
  `RowStyle.Clean`. Строка оформления живет, пока задан хоть один аспект (`HasTableStyle`):
  снятие цвета не уносит расположение и наоборот, а окна «Отображение» не стирают ни то, ни другое.
- **Галочки**: в меню ячейки — у того, что видно в ячейке (каскад + правило типа); в меню
  колонки — у расположения колонки (не задано — правило типа); в меню строки — у заданного строке
  (не задано — галочек нет: у строки разнотипные ячейки). Пересчитываются на каждое открытие.
- **Галочке расположение не нужно** (`CellAlign.Applies`): в ее меню пункта нет, ее ячейки и
  колонки из выделения пропускаются. Служебные таблицы оформления не имеют — у них всегда правило типа.
- **Вертикаль видна только в строке выше текста** (ручная высота или увеличенная высота строк
  в настройках). `CellAlign.TextTop`: «сверху» ставит первую строку туда же, где она стоит в
  строке обычной высоты, «снизу» — на тот же отступ от низа (отступ `SurfaceStyle.TextEdge`),
  поэтому соседние колонки держат одну линию; ближе к центру, чем центр, край не заходит — в
  обычной строке все три положения совпадают. По центру — прежнее правило, кадры без
  расположения не меняются (стережет `Tests/GridProto --snap`).
- **Клавиши** Ctrl+L / Ctrl+E / Ctrl+R (`table.alignLeft/Center/Right`, переназначаются в
  «Сочетаниях клавиш») — горизонталь выделенного: выделенные колонки, иначе выделенные ячейки
  (при фокусе в таблице, как у буфера), иначе выделенные записи (`HandleAlignShortcut`). После
  расположения выделение колонок не снимается — в отличие от цвета, результат виден и под ним, а
  клавишами его пробуют подряд.

**Правка не сдвигает текст.** Сетка рисует значение, редактор над ячейкой обязан поставить его туда же:

- по вертикали — держатель правки ставит редактор не во всю ячейку, а в полосу у края
  (`GridSurface.EditorInset` → `CellAlign.EditorInset`) высотой «текст плюс два отступа края»;
  каждый редактор центрует свое содержимое, поэтому в полосе оно встает ровно туда, где нарисован
  текст, вместе с кнопкой редактора. Полоса поля ввода растет с набранными переводами строки
  (`EditorHost.Relayout` по `TextChanged`);
- по горизонтали у полей ввода («Название», текст, ссылка, число, поле даты) — `TextAlignment`;
  «по центру» сетка рисует так же, как поле: каждая строка по центру полосы шириной, округленной
  вверх до целого DIP (`SurfaceStyle.DrawText`, `centerLines`), «справа» поле подгоняет свой
  отступ к показу (`KeepRightTextInPlace`). У списков, мультисписка и связи значение — надпись
  (`TextBlock`), и сетка центрует его как надпись (`TextCentering.BlockInArea`): ширина блока
  округлена вверх до целого DIP, на целый пиксель ложится смещение от края ячейки (раскладка
  округляет положение в координатах родителя), а не абсолютная координата;
- у редакторов с кнопкой справа (дата, списки, мультисписок, связь) «по центру» — по центру всей
  ячейки: полоса значения получает слева отступ на ширину кнопки (`CellDropdownCenteredPadding`,
  `SetValueAlignment` виджетов). «Справа» значение встает у кнопки — на кнопку текст не ложится,
  поэтому при входе в правку оно сдвигается влево на ее ширину; вертикаль на месте и здесь.

Проверяет `Tests/EditGeometry` (высокая строка, девять сочетаний на «Названии», тексте, числе,
списке и дате, заливка под редактором у края ячейки) и `Tests/GridProto --keys` (пункты меню,
галочки, клавиши, запись в базу). Наружу (календарь, задачи, панель записи, выгрузка в Excel)
расположение не выходит, в журнал не пишется и Ctrl+Z не отменяется — как цвет.

### Выделение ячеек и буфер обмена

**Три модели выделения.** Ячейки — РОВНО ОДИН прямоугольник
[`CellRange`](../../../../Core/Models/CellRange.cs) (якорь + фокус) или ничего. Ставится он
кликом, Shift-кликом, протягиванием, клавишами и Ctrl+A, и все эти пути дают сплошной
прямоугольник — поэтому рамка на экране всегда одна, и «прямоугольник в прямоугольнике»
невозможен структурно, а не по договоренности. Ctrl-набора вразнобой нет сознательно: он заводил
бы разрозненные куски. Записи — множество id в `GridPanel` (`SetRecordSelection` /
`ToggleRecordSelection`; на нем держатся все пакетные операции: удаление, дубль,
«Расположение», «Действия»; подсветка появляется у записи, как только ее строка в кадре).
Колонки — список ключей в фасаде (`SelectColumn`: Shift или Ctrl точечно), заливка при рисовании.
**Диапазон Ctrl+Shift+клик** — как в задачах (`TaskSelection.SelectRange`): от якоря — последней
записи или колонки, выделенной кликом (обычным или добавлением; снятие якорь не двигает), — до
кликнутой добавляется к выделенному. У «№» якорь — id записи (`_recordAnchor`), строки между ним
и кликом дочитываются тем же `RowsOfRangeAsync`, что и у ячеек (`SelectRecordRange`); якоря нет в
загруженных — клик работает как Ctrl-клик. У колонок (`SelectColumnRange`) диапазон идет по
видимым колонкам: скрытая в «Отображении» в него не входит. Боковая панель
(`SidebarTree.SelectRange`) — то же по видимым строкам дерева, только группы и коллекции одной
базы.
Три выделения гасят друг друга: `SetCellSelection` зовет `ClearRecordSelection`, клик по «№»,
`SelectRecords` и `SelectColumn` — `ClearCellSelection`. Иначе **Delete** было бы
двусмысленным: при выделенной колонке он стирал бы значения выделенных раньше ячеек вместо
удаления свойства. `SelectedRecordIds()` при выделенных ячейках возвращает пусто.

**Нажатия** приходят от поверхности одним событием `Pressed` с результатом попадания
(`GridHit`) и разбираются в `OnGridPressed` (`TableView.GridInput.cs`): шапка — клик по
заголовку выделяет колонку, кнопка фильтра — кнопка (окно на отпускании), правый клик — меню
шапки (колонка вне выделения выделяется одна, внутри набор сохраняется — как у «№»: пункты
набора, `TargetColumnKeys`, работают по всему выделению); «№» — строки (`OnNumPressed`: Shift/Ctrl точечно, Ctrl+Shift — диапазон, правый клик вне выделения выделяет
запись одну, внутри сохраняет набор); ячейка — выделение и протягивание, второй клик по той
же выделенной ячейке — правка на отпускании (см. «Правка ячейки»); пустое место и строка «+» —
меню пустого места. Меню открываются у указателя (`ContextMenu.Open(surface)`); пересчеты «при
открытии» — цвета, доступность сдвига, «Действия», буфер — зовет сам путь открытия
(`RunMenuOpening`): `Open` событие `Opening` не поднимает. Меню открывается на нажатии правой
кнопки, поэтому правый щелчок мимо открытого меню открывает новое еще до того, как Avalonia
закроет старое. То, что открыто одно меню и клик мимо его закрывает, держит общее правило
программы `ContextMenuDismiss` ([ui/theming.md](../../ui/theming.md)); без него на Windows меню
копились поверх друг друга.

**Протягивание** (`_dragSelecting`, захват указателя поверхностью) на каждом шаге ведет себя как
Shift-клик: якорь стоит, фокус едет за ячейкой под курсором (`CellNear` — по раскладкам:
служебные «№» и «+» и строка «+» прижимаются к ближайшей ячейке значения). Указатель за краем
области строк — **автопрокрутка** в его сторону по таймеру (`DragScroll.Step`, 60 мс), и фокус
переезжает на ячейку под прижатой к краю точкой. Кончается на отпускании кнопки, на первом
движении, когда кнопка уже не нажата (отпустили вне таблицы), и с началом правки — в редакторе
мышь выделяет текст.

**Координаты — позиции, а не идентификаторы.** В `CellRange` лежат индексы строки и колонки
в ПОКАЗАННОЙ таблице. Записи виртуализованы (`VirtualRowList`), строки списка переиспользуются
при прокрутке — держать в выделении `RecordId` значило бы каждый раз искать строку заново.
Идентификаторы резолвятся в момент операции (`SelectedCellsAsync`, `RowsOfRangeAsync`) — по
ВСЕМ строкам диапазона, а не только по прокрученным. Индексатор списка для этого не годится: он
на каждой незагруженной странице стартует фоновую загрузку, и обход столбца на 9 млн записей
заводил около 46 тысяч загрузок, а операция молча обрабатывала только прогретую часть.

| Строк в диапазоне | Как читаются |
|---|---|
| до `SyncRangeRows` (2 000) | `VirtualRowList.MaterializeRange` сразу: загруженные страницы — из кеша (только если страница несет все нужные поля — при окне колонок кеш держит лишь видимые), недостающие — из базы синхронно и в кеш не кладутся |
| до `MaxRangeRows` (100 000) | `MaterializeRangeAsync` в фоне, порциями по 2 000 на отдельном подключении (`ReadCellRowsAsync`: keyset или срез списка id в режиме отбора) и только с нужными полями (`FieldIdsOf`; очистке, цвету и вставке нужны лишь id записей) — под `WithProgressAsync` |
| больше | отказ с объяснением (`TooManyRows`) до чтения и до планирования вставки |

Второй предел — `MaxRangeCells` (200 000 ячеек, `TooManyCells`): строки ограничены, а столбцов в
коллекции бывают сотни. Потолок, а не «сколько угодно в фоне», поставлен сознательно: столбец в
миллионы записей — это минуты работы и сотни мегабайт строк в памяти, и честнее предложить
фильтр.

**`WithProgressAsync`** показывает `ProgressDialog`, только если работа не уложилась в 400 мс:
окно, мелькающее на каждую вставку пары ячеек, раздражало бы сильнее ожидания. Окно модальное —
второе действие поверх недописанного первого перепутало бы результаты. Чтение отменяемо
(`null` — операция ничего не делает), запись — нет (`cancellable: false`).

**Выделение следует за своими данными** (`SelectionIdentity`: запись под якорем и ключи столбцов
якоря и фокуса). Позиции после сортировки, фильтра, фонового обновления от соседа или сдвига
колонки указывают на ДРУГИЕ данные — и Delete стер бы не то, что выделяли.
`FollowSelectionIdentity` зовется по `RowsChanged` сетки (новый список, заполнение страницы,
структурное обновление), после пересборки колонок и перед каждой операцией. Столбцы ищутся по
ключу всегда, запись — только среди загруженных строк (`FindCachedByRecordId`, загрузку не
заводит). Нашлась в другой позиции — прямоугольник сдвигается целиком, сохраняя форму; не
нашлась или столбец пропал — выделение снимается. Пока строка под якорем не загружена,
`AnchorRecordId` = 0, и метка дописывается при первой возможности.

**Рамка — часть кадра.** Фасад отдает сетке строки среза и ключи крайних ВИДИМЫХ колонок
диапазона (`PushCellSelection` → `GridPanel.SetCellSelection`), позиции считаются на кадре из
раскладок; отдельного слоя, пересчета из `LayoutUpdated` и обрезки нет — рамка не может лечь ни
на шапку, ни на полосы по построению.

- **Толщина — два физических пикселя** от эффективного масштаба (зум × DPI): толщина в DIP при
  зуме и масштабе экрана размывалась бы.
- **Тонировка** — цветом акцента с прозрачностью 0,08, только у диапазона больше одной видимой
  ячейки: размер прямоугольника виден сразу, значения под ней читаются.
- **Над редактором** рамку рисует отдельный слой (`SelectionOverlay`): в правке она не гаснет
  и стоит по тем же границам ячейки — своей рамки у редактора нет (стережет `Tests/EditGeometry`).

**Скрытые колонки остаются в `_colDefs`** (там держатся порядок, фильтры и перемещение), но для
выделения и буфера их нет: `IsDataColumn` их отсекает; копирование, подпись «Выделено» и рамка
берут столбцы диапазона через `CellRange.VisibleColumns(VisibleDataColumns())`, а вставка идет
через `TablePastePlanner.PlanInGrid`: блок встает от первого видимого столбца не левее выделения,
ширина выделения считается в видимых столбцах, и в плане столбец — уже позиция в сетке. Раньше
скрытая колонка занимала позицию как read-only: копирование ее пропускало, вставка — нет, и
скопированный блок ложился обратно со сдвигом на чужие столбцы. Сценарий закреплен тестом
`TablePastePlannerTests.Hidden_column_takes_no_place_in_the_pasted_block`.

> **`IsReadOnly` у колонки ≠ «значение менять нельзя».** Это про отсутствие текстового
> редактора: `checkbox` и `file` помечены read-only (правятся кликом), и
> `PasteColumnOf` снимает признак с галочки — иначе вставка и очистка молча обходили бы все
> колонки-чекбоксы.

### Правка ячейки

Правка — один накладной редактор на таблицу (`EditorHost`): контрол создается на входе в правку
и снимается на выходе, сетка его не держит. Правила:

- **Раскрытие под длинный текст** (`ConstructorSettings.ExpandCellEditor`, стандартно включено):
  поле ввода текста, ссылки и «Названия», прижатое влево и по центру строки, растет, когда текст
  не помещается в ячейку (`EditorHost.Grow` мерит его `TextLayout` шрифтом поля). Сначала вправо
  целыми колонками до края видимой области (`GridSurface.EditorGrowRect`; правее последней
  колонки — по пустому месту), дальше перенос строк и рост вниз. Первая строка остается где была:
  у выросшего вниз поля содержимое прижато к верху с отступом половины разницы высоты ячейки и
  строки. Под полем — непрозрачная подложка фона таблицы (соседние ячейки не просвечивают),
  рамка выделения обводит раскрытую область (`SetEditorOverflow` → `FrameChanged` слоя рамки).
  Пересчет — на каждое `TextChanged` (`Relayout`). Число, список и прочие редакторы не
  раскрываются. Стенд — `GridProto --edit` («Раскрытие ячейки при вводе»).
- **Открыть**: второй клик по ТОЙ ЖЕ выделенной ячейке (медленный или двойной) — правка на
  ОТПУСКАНИИ, если выделение не утянули в другую ячейку (нажать на выделенную и потянуть —
  протягивание); Enter или F2 на якоре выделения. Клик по соседней ячейке — только выделение,
  даже в той же строке. Решает пара «прошлый клик / выделенная ячейка» (`_pressPrevCell` /
  `_pressLastCell`), см. `OnGridPressed` и `BeginEdit`. Без права `EditRecord` — окно с
  причиной, если правку просили мышью; клавиатура молчит. Read-only столбцы (галочка, файл,
  вычисляемые) редактор не открывают.
- **Набор** на выделенной ячейке открывает правку якоря с набранным вместо прежнего значения,
  как в табличном редакторе (`TableView.CellTyping.cs`). Ввод текста слушается туннелем на
  таблице (`OnTableTextInput`) и принимается, только если пришел в саму сетку, а не в поле
  внутри нее. Какой тип как открывается — чистые правила `CellTyping.Start` (покрыты
  `CellTypingTests`): текст, ссылка и «Название» — любым символом; число — цифрой, минусом и
  разделителем (`IsPartialNumber`, тот же фильтр, что у поля числа); дата — цифрой, сразу ручной
  ввод (`DateEditor.BeginManualInput`); список, статус и пользователь — видимым символом:
  список раскрывается на первом пункте, начинающемся с набранного; мультисписок и связь —
  видимым символом: раскрывается их выбор с набранным в поле поиска (`MultiSelectBox.OpenSearch`,
  `RelationSelectBox.OpenSearch`; до раскрытия — `UpdateLayout`, иначе окну негде встать). Галочка,
  файл и вычисляемые набором не открываются; управляющие символы (Ctrl+Backspace приходит
  символом DEL) — тоже. Без права правки набор молчит, как Enter.
- **Режимы стрелок.** Правка, начатая набором, — режим «ввод» (`_enterMode`): стрелки, в том
  числе с Shift и Ctrl, записывают значение (`CommitEditAndFocusGrid`) и отдают ту же клавишу
  `HandleSelectionKey`. F2 в поле переключает «ввод» и «правку» (стрелки по тексту), клик в поле
  переводит в «правку». Правка, открытая вторым кликом, Enter или F2, сразу в «правке».
- **Список по набору** ищет пункт сам (`CellTyping.FindOption`), а не встроенным поиском
  `ComboBox`: тот смотрит только показанные пункты и «е с точками» к «е» не приравнивает.
  Набранное в правке копится: следующие буквы уточняют, не подошло ни к чему — набор заново с
  новой буквы, повтор
  одной буквы перебирает пункты на нее; пробел и Backspace при непустом наборе правят набранное,
  стрелки по пунктам начинают набор заново. Перед раскрытием список раскладывается
  (`UpdateLayout`): иначе он раскроется, не поставив фокус на пункт, и стрелки по нему не пойдут.
  В списке, открытом Enter или кликом, буквы выбирают пункт, не раскрывая список.
- **Одно правило записи для списков** (решение 08.10.2026): как бы список ни открыли — набором,
  Enter, F2 или кликом, — выбор пишется при записи правки (`FlushDeferredList`) и при уходе
  фокуса из списка и его пунктов (`FlushListWhenFocusLeft`, как `LostFocus` у текста: правка
  остается открытой), Escape уходит без записи.
- **Фокус**: в поле у текстовых типов и в список у списков; у даты, мультисписка и связи
  остается в таблице — их открывают кликом, а Enter, Tab и Escape работают с таблицы. Цифра,
  набранная при такой открытой дате, переводит фокус в ее ручной ввод, символ при открытом
  мультисписке или связи — в поиск их выбора. Сетка — единственный фокусируемый элемент тела
  таблицы, кнопок в ячейках нет.
- **Записать и закрыть** (`CommitEdit`): Enter, Tab, клик мимо редактора (в другую ячейку, шапку,
  «№», пустое место; линия самой правящейся ячейки — часть ячейки), подмена строк
  (`RowsReplacing` — набранное пишется в строку, пока она жива), закрытие окна, в режиме «ввод» —
  стрелка. Escape — закрыть без записи (`CancelEdit`, всплытием; у списка, мультисписка и связи —
  туннелем, раньше их всплывающих окон: правка закрывается одним нажатием, даже когда окно
  раскрыто). Уход фокуса в панель записи пишет, не закрывая (`LostFocus` поля, у списка —
  `FlushListWhenFocusLeft`).
- **Строки перестроились** под редактором (заполнение страницы, структурное обновление):
  редактор едет за своей записью (`FollowEdit`); строке досталась другая запись — правка
  закрывается без записи (набранное ушло бы в чужую); строки больше нет в списке — с записью.
- **Галочка** — кнопка на отпускании над квадратом (как `CheckBox`), пробел на выделенной
  галочке переключает. **Файл** — скрепка на отпускании (системный выбор), имя файла: одиночный
  клик ждет 250 мс, не станет ли двойным, и открывает файл, отсутствующий — правит путь руками
  (`FileEditor` над ячейкой); двойной — правит путь; авто-привязка — плашка «Папка недоступна»
  под ячейкой или открыть найденный файл. При нескольких авто-файлах `FileEditor` показывает
  отдельные имена через запятую: нажатие открывает соответствующий путь, ручной правки нет.
  Диск спрашивается в фоне.
- **Число** правится в показанном формате; прижатый вправо текст поля не уезжает на полпикселя
  (`KeepRightTextInPlace`: дробный остаток ширины уходит в левый отступ). Текст при входе в
  правку не сдвигается ни на пиксель — стережет `Tests/EditGeometry` (по пикселям при масштабе 2).

Стили редактора — только про него (`Canvas.cellEditor` в `TableView.axaml`): без скруглений и
своей рамки, прозрачный фон (цвет ячейки ставит `ApplyEditorCellStyle`), целая высота строки
`LineHeightBase` — та же, что у текста ячеек сетки.

`RefreshRecordRow` (панель записи → таблица) отменяет открытую правку ТОЛЬКО если правится та
же запись; правка другой записи к обновлению отношения не имеет (иначе набор в ячейке обрывался
на паузе — панель перечитывается по `ChangeBus` через 300 мс).

### Клавиши таблицы

Клавиши слушаются туннелем на `TopLevel` (`OnTopLevelKeyDown`) и на самой таблице
(`OnTableKeyDown`). Условия, которые нельзя ослаблять:

- **`IsEffectivelyVisible`, а не `IsVisible`.** Разделы прячутся через предка
  (`ConstructorModule.IsVisible`), у самой таблицы `IsVisible` остается true. С прежней проверкой
  Delete в «Задачах» стирал значения невидимой таблицы и удалял задачу.
- **Действия над ячейками — только при `IsKeyboardFocusWithin`.** Иначе Delete по выделенным
  свойствам в панели записи уходил бы в выделенные когда-то ячейки. Удаление записей по Delete
  по-прежнему слушается на уровне окна (фокус после выделения строк бывает вне сетки), но
  пропускает фокус в `RecordPageView` — у панели свой Delete, а туннель окна идет раньше.
- **Модификаторы — ровно Ctrl (Cmd), без Shift и Alt**, Delete/Backspace — без модификаторов.
  Пока открыт редактор (`IsCellEditing`), окно клавиши таблицы не трогает вовсе.
- **Enter и F2 на выделенной ячейке** — `BeginEdit` якоря; **буква, цифра, знак** —
  `BeginEditByTyping` якоря (ввод текста приходит после нажатия, только если нажатие никто не
  забрал: клавиша, ставшая командой, текстом уже не придет).
- **Enter в редакторе** (`OnEnterWhileEditing`) — `CommitEdit` и фокус сетке; выделена остается
  та же ячейка (Enter — не «стрелка вниз»: иначе рамка и активная ячейка разошлись бы).
  Раскрытый `ComboBox` Enter себе не оставляет: пункт под фокусом берет `TakeFocusedListItem` —
  так же, как сам список по Enter, — и правка записывается одним нажатием (так же Tab).
- **Клавиши, зависящие от того, как начата правка и что правится** (`HandleTypingKey`, первым в
  `OnTableKeyDown`): стрелки «ввода», F2-переключатель, Escape списка и выбора, пробел и
  Backspace набранного в списке.
- **Alt+Enter** — перевод строки на месте каретки в `TextBox` текстового столбца и ссылки
  (`InsertLineBreak`); в остальных редакторах и в «Названии» не делает ничего. Многострочное
  значение сетка показывает столькими строками, сколько влезает в высоту ячейки.
- Действия запускаются через `Fire` (`async void`): непредвиденное исключение уходит в общий
  обработчик, а не в незамеченную задачу.
- **Ctrl+Z** (`HasUndo && IsKeyboardFocusWithin`) выделения не требует — после вставки его могли
  снять. **Ctrl+X** → `CutCellsAsync`: копирование, и только при его успехе — очистка под именем
  «Вырезание».
- **Shift+F10** — меню колонки при выделенных колонках, иначе меню строки активной ячейки (или
  первой выделенной записи), иначе меню пустого места (`OpenContextMenuByShortcut`).
- **Ctrl+L / Ctrl+E / Ctrl+R** — горизонталь текста выделенных колонок, иначе ячеек, иначе
  записей (`HandleAlignShortcut`, см. «Расположение текста»).

### Текстовые редакторы пишут при коммите

`TextBox` текста, ссылки, числа и «Названия» в `BuildCellEditor` получает начальное значение
(`Text = row[key]`) и к строке НЕ привязан. Раньше он был привязан `TwoWay`, и каждая буква шла в
базу отдельной транзакцией (`SetFieldValue`: до трех `SaveChanges`, аудит, календарь, строка
журнала): на сетевой папке — заметная задержка на нажатие, а каждый коммит еще и поднимал
`ChangeBus` и `RecordValueEdited` — панель записи перестраивалась на каждую букву.

Значение уходит в базу из `FlushEditingBox` (`row[key] = box.Text`, строка сама пропускает
совпавшее) в трех точках:

| Когда | Откуда |
|---|---|
| коммит правки — Enter, Tab, клик мимо редактора, закрытие окна | `CommitEdit`; на Escape (`CancelEdit`) не пишется |
| фокус ушел из редактора (клик в панель записи, боковую панель) | `LostFocus` самого `TextBox` — редактор живет дальше, и без записи здесь набранное держалось бы только в нем |
| редактор снимается вместе со строками (новый список, отбор, пересборка колонок, `Clear`) | `ForgetCellEditing` по `RowsReplacing` — пишет ДО подмены списка, пока строка жива |

Закрытие окна и уход в трей коммитят открытую правку заранее (`MainWindow.Closing` →
`ConstructorControllerView.CommitCellEdit`), иначе набранное пропало бы вместе с окном.

Список тоже пишет при коммите (`FlushDeferredList`), а не на каждое изменение выбора, и только
если выбор в правке менялся: значение не из пунктов (пункт убрали из настроек свойства) иначе
стерлось бы пустым выбором. Мультисписок, связь и выбор даты в календаре по-прежнему пишут на
каждом изменении. Ручной ввод даты `CommitEdit` принимает явно (`DateEditor.CommitManualInput`), а
`CancelEdit` от него отказывается (`CancelManualInput`): поле узнает об уходе фокуса уже после
снятия редактора, и прежде Escape после набранной руками даты все равно ее записывал.

Проверено безголовым стендом (`Tests/GridProto --edit`): набор с паузами при закрытой панели,
при панели на той же и на другой записи, Escape без записи, уход фокуса в панель с записью и
живым редактором, стрелка + Enter; правка набором — текст, стрелки «ввода» и F2, число,
«Название», прямоугольник, список и статус, мультисписок и связь, дата, типы без набора;
одно правило записи списка (Enter, Escape, уход фокуса). С `--pg` — то же на PostgreSQL.

**Движение выделения** — `HandleSelectionKey` → [`CellRangeNavigation`](../../../../Core/Models/CellRangeNavigation.cs),
чистая арифметика без сетки (покрыта `CellRangeNavigationTests`). Активная ячейка — якорь: без
Shift клавиша двигает его и схлопывает выделение в одну ячейку, с Shift двигается фокус, и
Shift+↓ после Shift+→ растягивает тот же прямоугольник. Столбцы идут по списку
`VisibleDataColumns()`, поэтому скрытый столбец перешагивается, а не «съедает» нажатие. Все
считается за O(столбцов) и от числа строк не зависит: Ctrl+End на 10 млн записей стоит столько
же, сколько на десяти, — прокрутка к ячейке тоже арифметика раскладок (`GridPanel.ScrollToCell`),
страницу заведет само окно.

| Клавиша | Куда |
|---|---|
| стрелки | на соседнюю ячейку, у края стоит |
| Ctrl + стрелки | к краю ТАБЛИЦЫ, а не блока данных: край блока потребовал бы читать значения всей строки или столбца |
| Home / End, Ctrl+Home / Ctrl+End | к краям строки / в углы таблицы |
| PageUp / PageDown | на `PageRows()` — сколько строк сейчас в окне сетки |
| Tab / Shift+Tab | от якоря вправо / влево с переходом строки; выделение всегда схлопывают, Shift не растягивает |
| Ctrl+A | `SelectAll`: якорь в левом верхнем углу, и следующий Shift+стрелка сжимает от правого нижнего |
| Enter, F2 | `BeginEdit` якоря |
| буква, цифра, знак | `BeginEditByTyping` якоря: правка с набранным вместо значения |
| Пробел | переключить выделенную галочку; в тексте — правка набором с пробелом |
| Escape | `ClearCellSelection` |

- **Tab гасится дважды.** Нажатие забирает `HandleSelectionKey`, отпускание — туннельный
  `OnTopLevelKeyUp`: иначе фокус ушел бы с сетки на следующий контрол окна.
- **Tab в редакторе** (`OnTableKeyDown`) — `CommitEdit`, фокус сетке и переход выделением
  (`CellRangeNavigation`, Tab / Shift+Tab).

**Счетчик выделения.** `CellSelectionChanged` поднимает подпись `SelectionLabel()` —
«Выделено: R × C» (столбцы — только видимые) или `null` для одной ячейки и пустого выделения — и
только при изменении (`RaiseSelectionLabel`). `ConstructorControllerView` передает подпись в
`FooterConstructor.SetSelection`, в виде «Список» ставит `null`.

**Вставка** — [`TablePastePlanner`](../../../../Core/Models/TablePastePlan.cs), чистая логика без
ViewModels, поэтому проверяется тестами целиком. Выделенная ячейка = левый верхний угол, блок
разливается вниз и вправо. Размер выделения передается отдельно (`selectionRows`/`selectionColumns`,
по умолчанию 1×1): если выделение БОЛЬШЕ блока и вмещает его целиком, блок размножается по
выделению (одно значение — на все ячейки, пара — парами по кругу). Выделение меньше блока или
равное ему — не в счет. Планировщик строк и колонок не добавляет: вышедшее за края идет в
`OutsideTable`. Досоздание — шаг фасада ДО планирования (`GrowForPaste`, настройка
`ConstructorSettings.PasteGrowsTable`, стандартно выключена): недостающие записи —
`AddEmptyRecords` (одна транзакция, «Без названия», без значений по умолчанию), недостающие
колонки — `AddPasteTextFields` (текст, «Колонка N» с первым свободным номером); дальше таблица
перечитывает колонки и строки, и план считается по выросшей. Строки — только у источника
`PlainRowSource` (без отбора и сортировки), размножение по выделению таблицу не растит. Отмена
(`UndoStep.Growth`) после возврата значений зовет `RemoveUntouchedPasteGrowth`: удаляются только
записи и свойства без данных — заполненное после вставки остается. Код —
`ConstructorRepository.PasteGrowth.cs`, тесты — `PasteGrowthTests`, стенд — `GridProto --keys`
(«Вставка за край таблицы»). Значения приводятся к формату ХРАНЕНИЯ
(дата каноном `DateValue`, число с разделителем своей колонки, чекбокс `1`/`0`) — иначе
сортировка и фильтр видели бы два представления одного значения. `IsWritable` отсекает
вычисляемые, файлы и автосвязи. Для обычного текста также исключены межбазовые связи
(`PasteColumn.IsCrossDatabaseRelation`, сюда же — связь без настроенной цели);
структурированный буфер переносит межбазовые связи по полной идентичности.
Наивная вставка иначе завела бы фантомные строки в `db_field_values`. Текст и
ссылка пишутся как есть, без `Trim` (пробелы — данные); обрезаются только типизированные
значения. Пустое значение в «Названии» (`PasteColumn.IsTitle`) ложится как «Без названия»
(`TitleText.Stored`) — так же его пишет очистка. «Пользователь» сверяется со
списком допущенных (`GetUserOptions`, один раз на вставку) — иначе любой текст выглядел бы
исполнителем. Итог вставки перечисляет причины пропуска (`ReportPaste`, текст —
`PasteSummary`), у связей каждую своей фразой: название не нашлось или неоднозначно, запись не
подходит под условие выбора или условие не проверить, несколько записей в связь на одну (текстом —
`TitleMatch.SeveralForSingle`, из своего буфера — `LinkBulkResult.SeveralForSingle`), записи нет в
связанной коллекции (`TargetsMissing`), связь записи на саму себя (`SelfLinks`), база цели пропала
посреди вставки (`TargetUnavailable`). Разбор — `TableView.OutcomeOf`; раньше отказы связи
складывались с неоднозначными названиями. Базы скопированных целей проверяет до записи
`RebaseRelationClipboardTargets`: недоступная в начале вставки база отменяет вставку целиком
(«Не удалось проверить целевую базу связи»), а `TargetUnavailable` пропускает ячейку, если база
пропала уже по ходу. Чужую правку ячейки вставка не замечает: прежних ребер она не сверяет,
значение ложится поверх (сверку прежних ребер делает только отмена).

Разбор значений строгий там, где неправильно понятое значение хуже отказа:

| Тип | Разбор | Почему так |
|---|---|---|
| число | `NumberFormatValue.TryParseDisplay`: разряды пробелом, неразрывным пробелом, апострофом или точкой/запятой с проверкой групп по три; знак валюты и «%»; минус и скобки. Не вышло — прежний `TryNumber` | в буфере число лежит ПОКАЗАННЫМ (`1 234,50 ₽`), и без этого круг «скопировал — вставил» в своей же таблице ломался. Неоднозначное `1.234` решает `DecimalSeparator` столбца |
| дата | `DateValue.TryParseExact` — дата обязана быть всей строкой | терпимый `TryParse` ручного ввода вынимает дату из «Отчет от 01.02.2026», и слова молча теряются |
| мультисписок | слева направо берется САМАЯ ДЛИННАЯ опция, за которой идет разделитель столбца, `,`, `;`, перевод строки, пробел или конец; незнакомый кусок — пропуск всей ячейки | резать по разделителю нельзя: опция сама может содержать запятую («Ул. Ленина, 5»); оставить «Красный» из «Красный, Отменено» — потерять половину без следа |
| галочка | `1/true/да/yes/истина/вкл/✓/✔/☑/✅/x` и `0/false/нет/no/ложь/выкл/-/☐/✗/✘` | копирование и из чужой таблицы, и из своей (`✓`) |
| связь | структурированный буфер передает `(DbId, RecordId)`; обычный текст разбирает `ResolveRelationTitles` по выбранному свойству показа | подпись может быть неуникальной или содержать разделитель |

**Запись — только пакетная.** `SetCellsBulk` (партиал
[ConstructorRepository.CellRange.cs](../../../../Database/Repositories/ConstructorRepository.CellRange.cs)).
Поштучный `SetFieldValue` дает около 18 значений в секунду (до трех `SaveChanges`, сырой UPDATE
аудита, запрос к `calendar_index` и чтение файл-столбцов на КАЖДУЮ ячейку): диапазон в пару
тысяч ячеек подвесил бы окно на минуты, а на сетевой папке дал бы тысячи исключительных
блокировок. Здесь все — одна транзакция, открытая ДО чтения (на SQLite транзакция EF —
`BEGIN IMMEDIATE`, и сосед не вклинится между сверкой и записью):

1. `AliveRecordIds` — только живые записи этой коллекции; `LastWins` — если ячейка пришла в
   пакете дважды, решает последнее значение;
2. `DiffCells` / `DiffTitles` — совпавшие с текущими значения не пишутся и в счет не идут (иначе
   повторная вставка того же блока поднимала бы «изменено» у всех записей); не совпал
   `ExpectedOld` — ячейка уходит в `Conflicts`;
3. `WriteValues` — подготовленные INSERT/UPDATE/DELETE и названия, сырыми командами через
   `tx.GetDbTransaction()`;
4. аудит последней правки (`UpdatedAt`/`UpdatedBy`);
5. `SyncCalendarForDateFields` — в той же транзакции: раньше проекция шла после коммита отдельной
   записью на каждую ячейку-дату, и сбой посередине оставлял значения новыми, а календарь старым;
6. `WriteTaskEvents` — уведомления о смене исполнителя и стадии, пока таких правок не больше
   `BulkTaskEventsLimit` (200): двадцать баннеров осмысленны, двадцать тысяч — очередь, которую
   никто не прочтет;
7. **одна** строка журнала со `Count` и `ChangeDetail.Batch` в `Detail` — «Вставка: Договор 12
   (Телефон: «123» → «456»); … и еще N», сколько влезает в предел строки;
8. `SaveChanges`, `Commit`.

После коммита: `UpdatedAt`/`UpdatedBy` у отслеживаемых записей; `_editMerges.Remove` по
затронутым ячейкам (иначе следующая побуквенная правка той же ячейки удалила бы строку журнала о
пакете и записала «до» из времени ПЕРЕД вставкой — вставка пропала бы из истории);
`SyncLocalCache` (сырые команды локальный кеш EF не видит); `ReactToBulkSourceEdits` — пересчет
файл-столбцов с авто-привязкой, у которых поменялся столбец-источник. Итог `CellBulkResult` несет
старые и новые значения (`Changes`), если их не больше `UndoChangesLimit` (100 000), иначе —
`ChangesTruncated`.

> **Сосед мог удалить запись, пока ее строка была на экране.** Простой INSERT упирался во
> внешний ключ и откатывал ВЕСЬ пакет вместе с живыми записями, а `DbErrors` такой отказ не
> обрабатывает — исключение уходило в `UnobservedTaskException`. Теперь записи сначала
> сверяются (`AliveRecordIds`: живые и из этой коллекции), а вставка идет через
> `INSERT … SELECT … WHERE EXISTS (…) ON CONFLICT (RecordId, FieldId) DO UPDATE` — на случай,
> если запись удалят уже между сверкой и транзакцией или сосед заведет ту же ячейку. `WHERE` у
> `SELECT` обязателен и ради SQLite: без него парсер не отличает `ON` конфликта от `ON`
> соединения. Счет изменений — по диффу, снятому внутри той же транзакции.

**Связи — вторым пакетом**
([ConstructorRepository.CellLinks.cs](../../../../Database/Repositories/ConstructorRepository.CellLinks.cs)).
Связь живет ребрами в `db_record_links`, и писать ее текстом нельзя.

- Структурированный формат буфера `application/x-smartbase-relation-cells+json` несет
  координаты ячеек, пары `(DbId, RecordId)` и идентичности баз. Перед записью скалярных
  значений и ребер проверяется соответствие баз; неизвестная внешняя база отменяет
  вставку целиком. Текст буфера сверяется с полезной нагрузкой, подписи для поиска
  при этом не используются.
- `ResolveRelationTitles(fieldId, texts)` — резервный путь для обычного текста по
  выбранному свойству показа. Проверяются все разбиения по разделителю поля, включая
  цель с разделителем в самой подписи. Второе допустимое разбиение или одинаковые
  подписи дают `Ambiguous`, отсутствие цели — `NotFound`. Сравнение точное; для
  названий запросы идут порциями по 500, для других свойств — через общий читатель.
- `SetLinksBulk` — одна транзакция: живые записи, ручные поля-связи этой коллекции,
  проверенные цели из настроенной базы и коллекции, без ссылки на себя и дублей.
  Структурированная вставка нескольких целей в одиночную связь отклоняется без
  усечения. Разница ребер точечная, оставшиеся ребра сохраняются и переставляются.
  Отмена сверяет полный упорядоченный набор целей (`ExpectedTargetsKey`) и конфиг
  поля (`ExpectedConfig`), чтобы не перезаписать чужую правку или измененное правило.
  Аудит и одна строка журнала (`LinkBatchDetail`, названиями записей).
- Значения и связи пишутся РАЗНЫМИ транзакциями, значения первыми: сбой на связях не должен
  лишать отмены уже записанные значения.

**Отмена** — [TableView.CellUndo.cs](../../../../Views/ConstructorDb/TableView.CellUndo.cs).
Пакетная запись и так читает старые значения, чтобы не писать совпадающие, — она возвращает их в
итоге, и отмена пишет их обратно тем же пакетным путем с `ExpectedOld` = новое значение. Ячейку,
которую после вставки поправил сосед или сам человек в панели записи, отмена не трогает и
называет в итоге («уже поменяли после этого — их не трогали»): иначе Ctrl+Z молча стер бы чужую
свежую правку.

- Шаги — в памяти этой таблицы, глубина `UndoDepth` (20), и только для текущей коллекции:
  `ForgetUndo` при смене коллекции и в `Clear()` — отмена «из прошлого», которую человек уже не
  видит, скорее навредила бы.
- Шаг запоминается, только если его можно вернуть целиком (`!ChangesTruncated`). Поэтому
  подтверждение спрашивается ровно там, где отменить нельзя: очистка и вставка больше
  `UndoChangesLimit`. Остальная вставка идет без вопроса — вопрос на каждую вставку стал бы
  рутиной, которую перестают читать. Очистка больше `ClearConfirmThreshold` (10) по-прежнему
  спрашивает при настройке «Спрашивать подтверждение при удалении».
- В предел `UndoChangesLimit` входят и скалярные значения, и старые/новые цели
  связей: одна ячейка с большим набором ребер не считается одним малым изменением.
- База занята (`DbErrors.Handle`) — шаг возвращается в стек: уже вернувшееся повтор пропустит по
  ожидаемому значению, оставшееся вернет.
- Отмена пишется в журнал своей строкой («Отмена: вставка»).

**Большой пакет — в фоне.** До `SyncWriteCells` (5 000 значений) запись идет сразу на общем
подключении (`WriteNow`); больше — `WriteInBackgroundAsync` под `WithProgressAsync` без отмены, на
клоне репозитория со своим `AppDbContext`
([ConstructorRepository.CellRangeAsync.cs](../../../../Database/Repositories/ConstructorRepository.CellRangeAsync.cs):
`SetCellsBulkIsolatedAsync`, `SetLinksBulkIsolatedAsync`, `ResolveRelationTitlesIsolatedAsync`).
Общий контекст с фонового потока трогать нельзя: интерфейс использует его параллельно, и EF
отвечает «A second operation was started on this context instance».

> **Права — на входе у общего репозитория.** Клон создан без `Permissions`, и `Demand` в нем
> пропускает все: спросить права внутри клона значит не спросить их вовсе. После записи общий
> контекст не знает, что поменялось, — `ForgetTracked` снимает с учета затронутые значения и
> записи и чистит `_editMerges`, и следующее чтение берет свежие данные.

**Копирование оставляет след в журнале безопасности** (`CopyTrace.Note` → `SecurityEvent.Copy`),
а не в журнале изменений. Раньше `LogCellsCopied` писал действие `copy` с целью `records`, и
каждый Ctrl+C будил сценарии с триггером «изменение данных» (`ChangeWatch.IsData`) и
перечитывание таблицы у соседей, хотя копирование не правка. След пишется ДО буфера: объем и
отпечаток текста известны заранее, и если журнал не открыт или строка не легла, в буфер ничего не
попадает, а вырезание ничего не стирает. Подробности следа —
[features/integrations/overview.md](../integrations/overview.md), «След копирования в буфер».

**Стертое `__title__` пишется как «Без названия».** Очистка ставит в ячейки названия
`TitleText.Placeholder`, а не пустую строку; пустое значение из буфера `TablePastePlanner.Convert`
превращает в то же самое (причины пропуска «пустое название» больше нет). Правило общее для всех
мест правки названия — см. [record-page.md](record-page.md), раздел «Заголовок». Связи очистка
снимает (пустой набор ребер).

**«Без названия» в ячейке — серая подсказка.** Сетка рисует его кистью `BrushSecondaryText`;
цвет текста, выбранный пользователем, перекрывает серый. Редактор такой ячейки открывается пустым
с подсказкой «Без названия»; `TableRowVm` сохраняет стертое как «Без названия», а выход из правки
без набора у записи без названия не пишет ничего — даже если в базе у нее пусто.

### Ресайз и режимы

- Ширина колонок: стандартная или ручная (`SetColResizeMode`) — см. следующий подраздел.
- Высота строк: автоматическая или ручная (`SetRowResizeMode`, `SaveRowHeights`).
  Режимы переключаются из контекстных меню заголовка колонки и строки и запоминаются за
  коллекцией (`SaveUiSettings`); выключение ручного режима сбрасывает сохраненные ширины
  (`ClearColumnWidths`) или высоты на стандарт.

### Ширина колонок

**Требуемое поведение.** Тянем границу вправо — колонка растет, соседи сохраняют ширину и
уезжают вправо, появляется горизонтальная прокрутка. Тянем влево — колонки справа
расширяются, пустоты справа не остается. Служебная «+» прижата к правому краю, пока
таблица помещается в окно.

**Раскладка** (`ColumnLayout.Build`) считается заново на каждую смену ширины окна, модели или
набора колонок — это арифметика на число видимых колонок, не раскладка контролов. Ширины
кладутся на физическую пиксельную сетку целыми квантами (квант — `1 / LineMetrics.EffectiveScale`,
то есть один физический пиксель при любом DPI и зуме): сумма ширин обязана точно равняться
ширине окна, пока таблица помещается, — иначе справа от «+» остается полоса или на пиксель
вылезает горизонтальная прокрутка. Стандартный режим делит окно поровну (остаток — первым
колонкам), но не уже стандартной ширины из настроек раздела (`ConstructorSettings.ColWidth`,
допустимые значения — список `ConstructorColWidths`); ручной — берет модель и раздает остаток
методом наибольших остатков пропорционально ширинам, ниже своей ширины колонка не опускается.

**Модель.** `_widths` в `GridPanel` (ключ колонки → ширина в DIP) меняется ТОЛЬКО жестом
пользователя; ресайз окна ее не трогает — поэтому «развернул окно и свернул обратно» возвращает
ту же картинку. Пока модель пуста, ручной режим выглядит как стандартный: включение режима вид
таблицы не меняет. Сохранение — один `SaveColumnWidths` на отпускание мыши, точечным upsert'ом.
После пересборки колонок ширины находятся по ключам.

**Жест** — зоны захвата у правой границы заголовка (±4 px, курсор «↔») в самой сетке
(`GridSurface.HitTest`), арифметика — `ColumnResize.Apply` (чистая, покрыта `ColumnResizeTests`).
На старте модель заполняется тем, что человек видит (до первого перетаскивания она пуста).
Дальше на каждое движение: `raw = старт + dX + сдвиг прокрутки` (поправка нужна, чтобы граница
не отлипала от курсора при клампинге прокрутки), `target = max(floor, raw)`,
`surplus = ширина_заполнения − (остальные + target)`. Колонки СЛЕВА не трогаются никогда —
иначе граница уехала бы из-под курсора; `surplus > 0` раздается колонкам справа пропорционально
их ширине; при росте соседи уезжают вправо, таблица становится шире окна. У самой правой
движимой колонки `floor` — точка «таблица ровно заполнена»: справа некому принять место.
`PointerCaptureLost` завершает жест без записи — иначе Alt+Tab посреди перетаскивания оставил
бы висеть флаг.

**Константы.** Стандартная ширина — из настроек (`MinColWidth`, стандарт 160): минимум
стандартного режима и ширина колонки, для которой ручная еще не задана;
`MinManualWidth = 48` — пол ручного перетаскивания. Верхнего предела у движимых колонок нет.
Ширину «№» под самый длинный номер (число записей) меряет сама сетка по счету из фона.

Ручные сценарии — в [qa-checklists/table-columns.md](../../qa-checklists/table-columns.md).

### Высота строк

Ручные высоты (`ui_row_heights`) — разреженный словарь по id записи. Раскладка `RowLayout` знает
только индексы: положение строки это шаг × индекс плюс сумма отклонений строк выше
(отсортированный массив с префиксными суммами, двоичный поиск), 10 млн строк с десятком ручных
высот стоят O(log n). Перевод id → индекс в текущем срезе идет в фоне
(`ConstructorRepository.RankRecordsAsync`: счет записей раньше данной по индексу
`(CollectionId, Position)`, в сортированном виде — по индексу `(FieldId, Value)` плюс хвост;
список id — словарем); до ответа строки стандартной высоты. Жест — зоны захвата у нижней границы
строки (курсор «↕»), живая высота тянущейся строки в раскладке, сохранение на отпускание;
пол — стандартная высота, потолок 600.

### Сохранение прокрутки

При создании/удалении/дублировании записи в середине больших таблиц контроллер
снимает и восстанавливает вертикальную позицию (`CurrentVerticalOffset` /
`RestoreVerticalOffset` — смещение доезжает по мере уточнения счета записей из фона), а при
добавлении в конец — прокручивает к новой строке (`ScrollToRecord`: строка в кеше — сразу,
иначе ее индекс в срезе считается в фоне; при незавершенном расчете нового списка прокрутка
ждет его подключения) или к колонке «+» (`ScrollToAddPropertyColumn`), чтобы кнопки
добавления оставались в зоне видимости. Перезагрузка строк (`ReloadRows`) сохраняет обе
прокрутки; новый отбор сбрасывает вертикальную и сохраняет горизонтальную; открытие другой
коллекции сбрасывает обе.

### Производительность

Таблица рассчитана на коллекции до ~10 млн записей и тысячи колонок. Рисуется только видимое
окно строк × колонок (`GridSurface`; ячеек в кадре ~250 при любом числе колонок), контролов у
ячеек нет, раскладки — арифметика. Данные тянет [VirtualRowList](../../../../ViewModels/ConstructorDb/VirtualRowList.cs)
постранично (200 строк; значения — только для окна видимых колонок; страниц в кеше — от
бюджета в ячейках, см. [[../../architecture/performance/hot-paths]]) — последовательный скролл по
keyset **в обе стороны** (row-value сик `(Position, Id)`, 0.3 мс на любой глубине), прыжки —
offset по покрывающему индексу `(CollectionId, Position)`, упреждающая страница в сторону
прокрутки. Подгрузка строк — в фоновом потоке с заглушками «Загрузка…». Снимок открытия
читается без COUNT (точное число записей приходит из фона со сверкой поколения; ширина «№» и
индикатор обновляются по нему). Отбор и сортировка считаются в фоне с отменой устаревшего
(`RowSourcePlanner`: сортировка индексируемых типов — keyset по индексу без материализации,
иначе — список id); пока считается, на экране прежние строки. Выпадающий список значений в
заголовке открывается мгновенно, значения считаются в фоне в порядке таблицы — по срезу
фильтров остальных колонок (каскад фильтров, см. ниже).

**Операции со свойствами/записями — без фриза и мелькания.** Перезагрузка разделена:
`ReloadColumns()` пересобирает только раскладку колонок (список строк и прокрутка остаются),
`ReloadRows()` — только строки (колонки не трогаются), `ReloadRowsStructural()` — создание,
удаление и дубль без пересоздания списка (число строк и загруженные страницы обновляются на
месте, теплый кеш, без заглушек). Число строк при этом не пересчитывается: свои операции передают,
на сколько оно изменилось (`countDelta`: создание +1, дубль +N, удаление −N), а чужие правки
(`RefreshRowsRemote`) оставляют прежнее и уточняют его фоновым счетом — синхронный COUNT на
10 млн записей стоил 0,85 с UI-потока после каждого дубля, сдвига и удаления записи. Тяжелые
удаление/дубль поля идут пакетами мимо EF на отдельном подключении в фоне; копия поля создается в
транзакции своих значений (прерванный дубль не оставляет пустого столбца), столбец больше
500 тыс. значений коммитится порциями — журнал базы не держит страницы всей таблицы до конца
операции. Перенос журнала в файл после правки идет в фоне (`WalCheckpointer`, см.
[storage-and-migrations](../../architecture/database/storage-and-migrations.md)): на коллекции
100 тыс. × 1000 свойств дубль столбца 66 → 8 с, очистка 28 → 9 с, вставка 29 → 9 с, удаление
24 → 6 с (стенд `Tests/Sections --only tableops`). Удаление и дубль ВЫБРАННЫХ записей (мультивыделение строк) — тоже bulk-SQL
мимо EF в фоне (`DeleteRecordsData`/`DuplicateRecordsData`), а не цикл с `SaveChanges` на каждую
запись. Подсчет и работа уходят в фон, окно прогресса (`RunBulkOp`) появляется отложенно —
мелкие операции проходят без него. Правка записи в правой панели обновляет ОДНУ строку на месте
(`RefreshRecordRow` → `RefreshRecord`), сдвиг строки — перечитывает только загруженные страницы
(`RefreshLoadedPages`), создание — без кросс-БД рефреша. Окно «Отображение записей» держит в
памяти только id записей в порядке таблицы (грузит их в фоне), названия подгружает порциями для
видимых строк, состояние — только у записей, отличных от умолчания; поиск — по названиям в базе,
«Сохранить» пишет отличия и повторяет перестановки по одной (`MoveRecord`). На 10 млн записей
окно открывается за 4–5 с вместо 32 и без гигабайта памяти. Есть ли файл у ячейки «файла» — из кеша с фоновой
проверкой пачкой (`FileProbe`), диск с UI-потока не спрашивается.

Замеры — [testing/benchmarks.md](../../testing/benchmarks.md); подробности и оставшиеся узкие
места — в [[../../architecture/performance/overview]].

## Фильтр колонки: чеклист значений

Окно фильтра (`BuildFilterPanel`) — сортировка сверху, поиск и чеклист значений снизу,
применение по «Готово» или Enter в поиске. Открывается кнопкой заголовка (нарисованной сеткой;
флайаут якорится невидимой рамкой на месте кнопки — `GridPanel.AnchorAt`). Чеклист живет
**сырыми** значениями колонки: отмеченное множество уходит в `_filters[key]`, копия отбора и
сортировка — сетке (`ApplyFilters` → `GridPanel.SetQuery`), та считает источник строк в фоне.
Воронка в шапке — и у отбора, и у сортировки. Память отбора (`ConstructorFilterMemory`)
восстанавливается при открытии: та же коллекция показывает прежние строки до расчета, другая —
пустую таблицу, а не все записи на миг.

**Правила галочек — в чистой модели** [`FilterSelection`](../../../../Core/Models/FilterSelection.cs)
(покрыта `FilterSelectionTests`), общей для плоского списка и дерева дат; окно лишь сообщает
ей, что показано сейчас (`MatchedRaws()`):

- ввод в поиске отмечает все найденное на каждое изменение текста (`OnSearch`); первый ввод
  запоминает галочки «до поиска», очищенный поиск возвращает их. По приходе данных снимок
  сбрасывается (`Reset`) — печатать могли раньше, чем загрузились значения;
- «Готово» и Enter в поиске — один `Apply()`. `Effective()` при поиске берет отмеченное среди
  найденного (режим «Заменить»), без поиска — все отмеченное, в том числе значения
  прежнего фильтра, которых нет в списке (их строки спрятал фильтр другой колонки); отмечено
  все, что есть в колонке (надмножество `domain`), — фильтр снимается;
- при открытии значения действующего фильтра идут первыми (`ChosenFirst`; снимок на момент
  открытия, от щелчков строки не прыгают). Дерево дат порядок не меняет;
- строки списка перечитывают галочку по `FilterValueVm.Refresh()`, дерево — по
  `DateFilterTreeBox.RefreshChecked()`: контейнеры виртуализированного списка
  переиспользуются, и без события привязка не узнает о правке общего набора;
- «(Выделить все)» при поиске подписан «(Выделить все найденное)» и действует на найденное.

**Колонка с тысячами разных значений — первые 1000 и поиск по базе.** Если разных непустых значений
больше `FilterValueCap` (1000), список не строится целиком: на 10 млн разных значений полный список
строился 105 с, подвешивал окно на 25 с и занимал до 6 ГБ. `GetColumnValueListAsync` отдает первые
1000 по алфавиту (`ColumnValueList.Capped`; проверка «больше предела» — `DISTINCT … LIMIT` по индексу
`(FieldId, Value)`, стоп на первом лишнем), под списком — «Показаны первые 1000 из N значений —
остальные ищите поиском». Число значений и «(Пусто)» досчитываются после показа
(`GetColumnValueTotalsAsync`). Поиск — запросом к базе с паузой 0,25 с на набор, без учета регистра
и у кириллицы: функция `sb_contains` на подключении SQLite (`SqlText.ContainsIgnoreCase`; на
PostgreSQL — `ILIKE`), отмена прерывает запрос из самой функции. Галочки — правило «все, кроме
снятых» или «только отмеченные» ([`CappedFilterSelection`](../../../../Core/Models/CappedFilterSelection.cs),
`CappedFilterSelectionTests`): снятое из «всех» значение дает отбор «кроме» —
[`FilterExclusion`](../../../../Core/Models/CappedFilterSelection.cs), метка в том же наборе фильтра,
его понимает `FilteredRecords` (`NOT IN`) и сохраняет память отбора. Полный список снова знает все
значения и превращает такой отбор в обычный. Даты и связи — всегда полным списком. На 10 млн
записей: «Текст» (все значения разные) — 0,17 с до списка, поиск — 11–15 с без пауз UI
(`ColumnValueListTests`).

**Чекбокс — две строки.** Окно фильтра чекбокса показывает «✓» и «(Не отмечено)», а не значения как
есть (`CheckboxCounts`, отбор — `CheckboxFilter` в `FilteredRecords`, правило «отмечено» —
[`CheckboxValue`](../../../../Core/Models/CheckboxValue.cs): `1`/`true`/`True`). До 20.10.2026 каждое
записанное значение было своей строкой: снятая в таблице галочка пишется `0`, нетронутая ячейка
пуста, после смены типа столбца остается прежний текст — и в списке стояли три «—» рядом с
«(Пусто)», а отобрать все неотмеченные одной галочкой было нельзя. Отбор по группе понимает и
прежние сохраненные фильтры со значениями как есть (`0` — «не отмечено»); снятая галочка из отбора
«не отмечено» не выпадает. Покрыто `ColumnFilterCascadeTests.Checkbox_column_filters_by_two_groups`.

Колонка до 1000 значений на всей коллекции (без фильтров других колонок и скрытых записей) считается
по индексу `(FieldId, Value)` без обхода записей (`FieldValueCountsWhole`), порядок таблицы — по
первому появлению в первых 20 тыс. записей, остальные значения — по алфавиту следом (на коллекции
до 20 тыс. записей — ровно порядок таблицы). На 10 млн записей колонка из четырех значений —
26,5 → 7,8 с: дальше упирается в чтение всего индекса.

**Каскад фильтров считается в SQL.** `GetColumnCountsAsync(collectionId, key, _filters,
excludeHidden)` → `GetColumnCounts`: срез записей строит `FilteredRecords` — тот же запрос,
что и у отбора таблицы, — по фильтрам ОСТАЛЬНЫХ колонок (свой ключ репозиторий
отбрасывает сам: иначе снятое значение нельзя вернуть) и без скрытых в «Отображении
записей». Счетчики поля — JOIN `db_field_values` со срезом, группировка по индексу
`(FieldId, Value)`, «(Пусто)» = `scope.Count()` минус непустые; «Название» — группировка
среза; связь — `RelationTitlesBySource`, отсеченный по id среза. Снимок фильтров берется на
UI-потоке (`OtherFilters`), фон живой словарь не читает; пути чужих баз снимаются для ВСЕХ
полей-связей, участвующих в запросе (считаемого и фильтрующих). Покрыто
`ColumnFilterCascadeTests`. Служебные таблицы («Диагностика», «История изменений»,
«Пользователи» панели администратора) ведут себя так же: у них одно общее окно
[`ColumnFilterPanel`](../../../../Controls/Components/ColumnFilterPanel.cs) на той же модели
`FilterSelection` — каскад (журналы считают его в SQL: `GetChangeLogCountsAsync` и
`LogReader.GetCountsAsync` с фильтрами остальных колонок; пользователи — в памяти,
`ColumnCascade`), автоотметка найденного, Enter и отобранные первыми. Отличие одно: даты без
выбранной сортировки идут новыми сверху — служебные таблицы и сами показывают свежие строки первыми.
Раньше у каждой из трех была своя копия окна, и все три разошлись с конструктором.

**Форма условия фильтра решает, подъемен ли каскад.** Набор значений уходит в SQLite как
`IN (SELECT value FROM json_each(@p))`, и внутри КОРРЕЛИРОВАННОГО `EXISTS` SQLite перебирает
его заново на каждую строку. На стенде `Tests/test_database.db` (10 млн записей, фильтр «один
день» = 1444 сырых значения даты, 5 млн строк) прежняя форма фильтра — `EXISTS (... AND Value
IN (...))` — не укладывалась в 5 минут; так вела себя и сама таблица при таком отборе, каскад
лишь унаследовал бы это. `FilteredRecords` теперь проверяет строку некоррелированным
`r.Id IN (SELECT RecordId FROM db_field_values WHERE FieldId = ? AND Value IN (...))` (и так же
для внутрибазовой связи — по ребрам): список id строится один раз по индексу `(FieldId, Value)`.
Замер там же (через `GetColumnCounts`/`GetFilteredRecordIds`): список id фильтра — 12 с,
каскадный список колонки по этому срезу — 14–16 с, список колонки дат без фильтров (5 млн
уникальных значений, как и раньше) — 22 с; самый тяжелый случай — те же 5 млн уникальных дат
по срезу «(Пусто)» другой колонки на все 10 млн записей — 42 с. То есть окно с каскадом
открывается не дольше, чем без него (порядок тот же), а фильтр таблицы стал считаться на
порядки быстрее. Ветка «(Пусто)» осталась коррелированной — в ней нет списка, только проба по
первичному ключу.

> Ручная проверка склейки с UI — [qa-checklists/filter-column.md](../../qa-checklists/filter-column.md);
> безголовый стенд — `Tests/GridProto --ops`.

**Колонка-дата — исключение по виду, но не по механике.** Вместо плоского списка строится
дерево «год → месяц → день» ([`DateFilterTreeBox`](../../../../Controls/Components/DateFilterTreeBox.cs)
поверх чистого [`DateFilterTree`](../../../../Core/Models/DateFilterTree.cs)):

- отмечается **день**, но в `checkedSet` кладутся все сырые значения этого дня — фильтр,
  сортировка и SQL не меняются вовсе;
- галочка родителя = «отмечено все поддерево» (`DateFilterTree.IsFullyChecked`), без
  промежуточного состояния: снят хоть один день — у месяца и года галочки нет. Клик
  решает по фактическому состоянию (отмечено все → снять ветку, иначе → отметить
  целиком), а не по значению, которое прислал чекбокс;
- свернутые ветки в `ItemsSource` не попадают, поэтому виртуализация списка работает как
  на плоском чеклисте;
- раскладка строки повторяет дерево сайдбара: слот стрелки шириной ровно в шаг отступа
  (`IndentStep`), стрелка — `IconSizeSmall`/`IconStrokeSmall`. Слот сохраняется и у дня,
  где стрелки нет, иначе лесенка чекбоксов ломается на листьях;
- порядок годов/месяцев/дней следует выбранной сортировке колонки, поэтому смена
  «Сначала старые ↔ Сначала новые» **пересобирает** дерево (`MountTree`);
- поиск ищет по номеру дня, полной дате `дд.MM.гггг`, названию месяца и году
  (`DateFilterTree.Search`), найденные ветки раскрываются;
- «(Выделить все)» и режим «Заменить» работают через `MatchedRaws()` — общий язык
  обоих режимов: показанные сейчас сырые значения.

Тот же компонент стоит в фильтрах «Диагностики» (колонка «Время»), «Истории изменений»
(«Дата и время») и таблицы пользователей («Подключен», «Последняя активность» — день по местному
времени); там сырое значение — сама дата `yyyy-MM-dd`, поэтому фабрика другая
(`ForIsoDates` против `ForStorageDates`), а все остальное общее.

### По цвету

«Фильтр по цвету» (`TableView.ColorFilter.cs`) открывает подменю справа с чекбоксами цветов:
отдельно фон и текст, с названием и числом записей. Сам чекбокс показывает цвет, без отдельного
образца-квадрата или буквы: цветная рамка у снятого, та же заливка с белой галочкой у отмеченного.
Метки «Без заливки» и «Стандартный» используют нейтральный серый. Несколько галочек можно поставить
без закрытия меню; выбор копится до «Готово». Отбор сохраняет действующую сортировку и не
переставляет подходящие строки наверх. «Снять фильтр по цвету» очищает цветовые галочки в
подменю; условие снимается после «Готово».

Условия — модель [`ColorQuery`](../../../../Core/Models/ColorQuery.cs) и особый ключ
`color:<колонка>` в `_filters`, набор значений — метки `bg:#RRGGBB`, `fg:#RRGGBB`, `bg:` (без
заливки), `fg:` (стандартный текст). Цвета внутри одного аспекта объединяются через ИЛИ,
между фоном и текстом — через И; аспект без выбранных цветов не ограничивает строки.
Пустой набор снимает только условие цвета колонки. Условия значений и других колонок продолжают
работать через И. Память отбора, снятие условий по удаленной колонке (`PruneFilters` смотрит
`ColorQuery.ColumnOf`) и воронка (`GridPanel`: `IsColumnFiltered` по колонке ключа) используют
тот же ключ.

При восстановлении коллекции `TableView.Load` вызывает `ColorQuery.MigrateSortToFilter`:
старый ключ `color:<колонка>|<метка>` переводится в цветовой фильтр той же колонки, а сортировка
снимается. Уже сохраненный набор цветовых галочек важнее старой сортировки и не заменяется.
Перенос выполняется перед `PruneFilters`, поэтому условия удаленных свойств затем убираются;
измененное состояние сохраняется в память коллекции. Обычные ключи сортировки не затрагиваются.

Подменю — отдельный `Flyout` с размещением `RightEdgeAlignedTop`, оберткой `WindowZoom` и учетом
в `TransientPopups`. Чекбоксы меняют только копию набора текущего окна; закрытие без «Готово»
отменяет правки. Закрытие основного окна скрывает дочернее и отменяет фоновую загрузку цветов.

Цвет — видимый (`RowStyle.Resolve`: ячейка → строка/колонка, что позже). Записи не перебираются
(`ConstructorRepository.ColorQuery.cs`): своих цветов у большинства записей нет, и они видят цвет
колонки, поэтому считаются только «особые» записи — с цветом ячейки этой колонки или строки.
Условие уходит в запрос списком особых id: «все, кроме особых, что не подошли», когда цвет колонки
подходит, иначе «только особые, что подошли» (`ColorMatches` → `ColorFilter` в `FilteredRecords`).
Список цветов окна (`GetColumnColorsAsync`) считается по срезу отбора остальных
колонок; свой отбор колонки — и по значениям, и по цвету — не режет ни его, ни список значений
(`OtherFilters` сравнивает колонку ключа). Пункт меню виден всегда, включая загрузку и колонки
без заданных цветов: у них доступны метки отсутствия заливки и стандартного текста.
`ColorSection` показывает загрузку, а при отказе — сообщение с повторным запросом; сохраненные
галочки остаются доступны до прихода счетчиков. Отмена при закрытии окна не считается ошибкой.
Тесты — `ColorQueryTests`, `ColorQueryFilterTests`, стенд —
`GridProto --ops` («По цвету»).

## Навигация нижней панели

Нижняя панель ([FooterConstructor](../../../../Controls/Components/Footer/FooterConstructor.axaml))
показывает «‹‹ ‹ 10 – 50 из 125 437 › ››» и — только при нескольких выделенных ячейках — их
размер «Выделено: 3 × 2» (`SetSelection`, см. «Клавиши таблицы»). **Страниц фиксированного
размера у таблицы нет** — она виртуализирована и прокручивается непрерывно, поэтому
индикатор показывает номера строк, которые сейчас в окне, а кнопки двигают то же
смещение, что и колесо мыши.

> Кнопки «Фильтр» и «Сортировка» из панели **удалены**: события они поднимали, но их
> никто не слушал — живые фильтр и сортировка вызываются из меню заголовка колонки.
> Счетчик «Всего: N» убран как дубль (то же число стоит после «из»); число записей приходит
> из фона, а не COUNT'ом на UI-потоке при открытии и каждом структурном обновлении.

### Откуда берется диапазон

Номера видимых строк считаются **из раскладки арифметикой**: первая и последняя строка, чьи
границы попадают в окно при текущем смещении (`RowLayout.VisibleRange` — шаг и ручные высоты
с префиксными суммами). Никакого обхода дерева и никаких строк-контролов нет, поэтому «сирот»
после прыжка и строк, застрявших в правке, не бывает по построению.

Перевод слотов в номера строк — `TableViewportRange.FromSlots`, чистый и покрытый тестами:
слот = индекс строки, номер = индекс + 1. Отдельно оговорены два края:

- **строка «+»** стоит последним слотом (ее индекс = число записей) — ее номер срезается по
  общему числу, поэтому у самого низа индикатор показывает последнюю ЗАПИСЬ. Если в окне
  осталась одна «+», диапазон все равно `N – N`, а не «0 из N»: иначе погасли бы все четыре
  кнопки и вернуться наверх было бы нечем;
- **ничего не разложено** (список еще не подключен): «0 из N», число записей к этому моменту
  уже известно из снимка (оценка) и уточняется из фона.

Номера — порядковые в текущем срезе: `VirtualRowList` проставляет `RowNumber = индекс + 1` и
для отфильтрованного списка тоже, поэтому при фильтре индикатор считает от единицы, а `Total`
берется из `Rows.Count - 1` (минус строка «+»). Пока счет записей — оценка, край таблицы
уточняется прочитанными страницами и ответом COUNT из фона; отложенное восстановление смещения
доезжает вместе с ним.

### Прокрутка — смещение сетки

Вертикальная прокрутка — пиксельная: протяженность = сумма высот строк (10 млн × высота —
обычное `double`), «экран» = высота окна строк, «в конец» = максимум смещения. Кнопки, колесо
(три строки), ползунок и клавиши двигают одно и то же смещение поверхности; страницу новой
позиции заводит само окно (`EnsureRange` с упреждающей страницей), до ее прихода — заглушки
«Загрузка…». Прыжок в конец на 9 млн строк — заглушки за миллисекунды, данные — одна страница
глубины по индексу. Наверх событие `VisibleRangeChanged` уходит только на изменение диапазона.

## Взаимодействия (события наверх)

| Событие | Назначение |
|---|---|
| `RecordClicked` | открыть запись в правой панели |
| `VisibleRangeChanged` | видимый кусок таблицы сменился — нижняя панель обновляет индикатор и активность кнопок |
| `RecordCreateRequested (Open, AfterId)` | создать запись (в конце / после строки) |
| `RecordsDeleteRequested` / `RecordDuplicateRequested` | удалить / дублировать записи (оба несут СПИСОК id — все мультивыделение строк) |
| `RecordRelocateRequested` | «Расположение»: перенести записи в другую коллекцию/БД (СПИСОК id — мультивыделение строк); контроллер открывает [RecordLocationDialog](../../../../Controls/Dialogs/RecordLocationDialog.axaml.cs) |
| `PropertyCreateRequested` / `PropertyCreateAfterRequested` | новое свойство (в конец / после колонки) |
| `PropertyEditRequested` / `PropertyDuplicateRequested` / `PropertiesDeleteRequested` | правка / копия / удаление свойств; дубль и удаление несут СПИСОК id (все мультивыделение колонок) |
| `SystemFieldRenameRequested` | переименовать «Название» |
| `ColumnDisplayRequested` / `RecordDisplayRequested` | окна «Отображение» колонок / записей |

Мультивыделение строк + клавиша Delete → `RecordsDeleteRequested`; то же для
свойств → `PropertiesDeleteRequested` (обязательные поля защищены).

Столбец с ролью раздела удаляется как обычный, но окно подтверждения называет потерю
(«Исполнитель» — записи коллекции перестанут отображаться в задачах) — см.
[[../tasks]] → «Удаление ролевого столбца».

## Перенос записи («Расположение»)

Контекстное меню записи → «Расположение» открывает [RecordLocationDialog](../../../../Controls/Dialogs/RecordLocationDialog.axaml.cs)
(целевая БД + коллекция, как у коллекций в сайдбаре). Перенос — это copy + удаление исходной, работает
и внутри одной БД, и между БД; пакетно на изолированных подключениях в фоне
(`MoveRecordsToCollectionIsolated` → `MoveRecordsCore`, окно прогресса только на большом объеме, как
дубль/удаление). Производительность по тем же правилам, что у `DuplicateRecordsData` — план сопоставления
полей считается один раз, значения каждой записи пишутся одним `AddRange`, копия в одной транзакции,
`calendar_index` наполняется разом по диапазону новых id, исходные удаляются `DeleteRecordsData` (см.
[[../../architecture/performance/overview]]).

Перенос значений **грамотный** — устойчив к разным схемам коллекций:

- Сопоставление полей **по имени** (без учета регистра).
- **Приведение типов** при пересечении границы «дата» (`ConvertValueForType` поверх [DateValue](../../../../Core/Models/DateValue.cs));
  остальные типы хранятся как обычные строки и копируются как есть.
- Несовпадающие свойства источника: галочка **«Перенести все свойства»** в окне — выкл → отбрасываются
  (схема цели не меняется), вкл → создаются в целевой коллекции (`AddField`, полное сохранение данных).
- Поля цели, которых нет в источнике — остаются пустыми.

Тот же `CopyFieldValuesByName` чинит перенос значений при смене коллекции/БД из окна события
календаря (см. [[../calendar/interactions]]); там недостающие свойства не создаются (окно не меняется).
