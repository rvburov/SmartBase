# Таблица коллекции (TableView)

## Назначение

Основной режим коллекции — таблица (спредшит): строки-записи × колонки-поля.
Поддерживает редактирование значений прямо в ячейках, изменение ширины колонок и
высоты строк, переупорядочивание и скрытие колонок/строк, мультивыделение.

## Как работает

### Колонки

Колонки строятся из полей коллекции (`GetFields`) плюс системная «Название»
(`__title__`) — единственная, что не является полем. «Описание» — обычное поле
(роль `IsDescription`), в новой коллекции его нет: см. [[../../architecture/data-types/description]].
Порядок, ширины, видимость и уровни колонок берутся из UI-настроек коллекции:

- порядок — `GetColumnOrder` / `MoveColumn` / `MoveColumnAfter` / `SaveColumnOrder`;
- ширины — аспект `Width` в `column_meta`: `GetColumnWidths` / `SaveColumnWidths` / `ClearColumnWidths`;
- видимость/уровни — `SaveColumnDisplay`;
- подпись системной колонки — `GetSystemFieldNames` / `SetSystemFieldName`.

Готовый список колонок отдается наверх через событие `ColumnsBuilt`
(`TableColumnDef`), а `MovableKeysInOrder()` / `MovableColumnsInOrder()` дают
текущий порядок для диалогов.

### Редактирование значений

Значения сохраняются в БД сразу при изменении ячейки (`SetFieldValue`), без кнопки
«сохранить». Тип ввода зависит от `FieldType` поля.

> Реестр типов свойств (коды, хранение, семантика) — сквозной и описан один раз в
> [data-model.md → «Типы полей»](../../architecture/data-model.md#типы-полей-свойств)
> (единый источник [`FieldTypeInfo`](../../../../Core/Models/FieldTypeInfo.cs)). Ниже — только то,
> как типы **представлены в таблице**. Round-trip запись→чтение по всем типам проверяет
> `FieldTypeMatrixTests`.

### Редакторы ячеек по типам

| Тип | Редактор ячейки в таблице |
|---|---|
| `text` | текстовое поле (многострочный текст — в нижнем блоке панели записи) |
| `number` | текстовое поле с фильтром ввода |
| `date` | `DateEditor` (диапазоны, время, «весь день») |
| `select` | ComboBox из опций |
| `status` | ComboBox из опций (как `select`) |
| `multiselect` | значения через запятую (текст); edit — `MultiSelectBox` (выпадающий чеклист с поиском); значение JSON-массивом |
| `checkbox` | чекбокс (показ `✓`/пусто) |
| `url` | текстовое поле (watermark `https://`) |
| `user` | ComboBox из `GetUserOptions()` |
| `created_*` / `updated_*` | **нет** — read-only (см. ниже) |

### Вычисляемые типы (авто-метаданные записи)

Типы `created_at/updated_at/created_by/updated_by` — **read-only**, значение из аудит-метаданных
записи (реестр и источники — [data-model.md](../../architecture/data-model.md#типы-полей-свойств)).
Как таблица их показывает:

- колонка `IsReadOnly` (`CellEditingTemplate` не строится); ячейка — текст, биндинг к именованным
  свойствам строки (`TableRowVm.CreatedAt/UpdatedAt/CreatedBy/UpdatedBy`), даты — `дд.MM.гггг чч:мм`.
  То же read-only в панели записи ([[record-page]]);
- в диалоге «Тип» стоят внизу — четвертой группой списка, отделенной чертой
  (`ItemContainerTheme` — вне подсветки пункта и поля выбора; про группы см.
  [ui/dialogs.md](../../ui/dialogs.md#группы-типов-в-списке-свойства));
- **стамп** метаданных: создание — `AppDbContext.SaveChanges` (+ `AddRecord`); правки —
  `TouchUpdated` (название/описание/дата) и сырой `UPDATE db_records` в `SetFieldValue` (только при
  реальной смене значения; синхронизирует EF-трекер, иначе `GetRecord` вернул бы старое «изменено»);
- **фильтр/сортировка** по этим колонкам пока не функциональны (значения не в `db_field_values`).

### Смена типа поля (текст ↔ дата)

При смене типа поля в «Изменить свойство» (`UpdateField`) уже сохраненные значения
**приводятся к новому типу без потери данных** — `ConstructorRepository.ConvertFieldValuesForTypeChange`:

- **текст → дата:** значение разбирается (`DateValue.TryParse`, понимает и `дд.MM.гггг`,
  и ISO) и переписывается в ISO-канон (`ToStorage`, например `2026-02-01`) — тот же вид,
  что пишет редактор даты; дата сразу читается таблицей, календарем и редактором;
- **дата → текст:** ISO-канон разбирается и переписывается в человекочитаемое
  `дд.MM.гггг` (`ToDisplay`), чтобы текст сохранил дату в привычном виде, а не как
  `2026-02-01`.

Неразбираемое значение остается как есть (произвольный текст — просто не дата, потери нет).
Конвертация идет сырым ADO.NET-пакетом в одной транзакции (значений может быть много) и
**до** пересборки `calendar_index`, чтобы индекс строился по каноническим значениям. Это и
есть штатный путь после импорта: столбец приходит текстом (см. [[../import-export/overview]]),
затем переводится в дату и обратно без искажений.

### Цвет строк, ячеек и текста

Меню строки → «Изменить цвет» дает четыре подменю, меню заголовка колонки — еще два.
Все они строятся общей фабрикой [ColorMenu](../../../../Controls/Components/ColorMenu.cs)
поверх палитры [AppPalette](../../../../Core/Models/AppPalette.cs) — той же, что красит
коллекции в сайдбаре.

| Пункт | Что красит | Где хранится |
|---|---|---|
| «Фон строки» / «Цвет текста строки» | строку в ЭТОЙ таблице | `record_display.Bg/Fg` |
| «Фон ячейки» / «Цвет текста ячейки» | ячейку, по которой был правый клик | `cell_style` |
| «Фон колонки» / «Цвет текста колонки» | всю колонку | `column_meta.Bg/Fg` |

Все это — оформление ОДНОЙ таблицы: наружу (в календарь, задачи, «Список», панель записи)
не выходит и в журнал не пишется. Сквозной цвет записи был отдельным уровнем и убран —
почему, см. data-model.md ниже.

Модель хранения и каскад приоритетов — [data-model.md → «Цвет»](../../architecture/data-model.md#цвет-оформление-таблицы).
Каждый пункт применяется ко ВСЕМУ выделению — как удаление и дубль: строки к выделенным
строкам (`TargetRecordIds`), колонки к выделенным колонкам (`TargetColumnKeys`, вместе с
системной «Название» — ее, в отличие от удаления, красить можно), ячейка — к той же колонке
во всех выделенных строках. Отмечен галочкой цвет ТОЙ строки/колонки, по которой кликнули.
После смены цвета колонок выделение снимается: голубая заливка выделения лежит под
полупрозрачным цветом, и на выделенной колонке разницу «покрасил / снял» почти не видно.
Права: цвет строки и ячейки — `EditRecord`, цвет колонки — `EditField`; новых битов маски
не заводилось.

Как это нарисовано (важно при правках `TableView`):

- заливка и цвет текста ложатся на **свой `Border` внутри `ContentPresenter`** ячейки
  (`CellStyleHost`), а не на его фон — там уже живет заливка выделения колонки
  (`AttachColumnFill`);
- заливка **полупрозрачна** (`ColorTools.Fill`): наведение, выделение строки и выделение
  колонки просвечивают сквозь цвет. Поэтому трогать `DataGridRow.Background` и стили
  `Rectangle#BackgroundRectangle` не потребовалось;
- цвет текста ставится **локальным значением самим `TextBlock`'ам ячейки** (`PaintText`
  в `CellStyleHost`). НАСЛЕДОВАНИЕ здесь не работает в принципе, и это главная ловушка
  места: цвет всех надписей приложения задан стилем `Style Selector="TextBlock"`
  (`Assets/Styles/Typography.axaml`), а стиль в Avalonia приоритетнее унаследованного
  значения — до текста дошел бы он, а не цвет ячейки. Так молча не сработали обе первые
  попытки: `TextElement.Foreground` на слое-`Border` и `Foreground` самой `DataGridCell`
  (ее тема прокидывает в `ContentPresenter`, но дальше значение снова лишь наследуется).
  По той же причине не работает и штатный стиль `DataGridRow:selected DataGridCell` —
  текст выделенной строки синим не становится. Локальное значение перебивает стиль,
  поэтому цвет виден и на выделенной строке. Исходная кисть надписи запоминается: у
  «вычисляемых» ячеек она своя (приглушенная), и сброс обязан вернуть именно ее;
- контейнеры ячеек переиспользуются, поэтому цвет пересчитывается на смену `DataContext`
  И на «Item» строки (`TrackRowStyle`) — заглушка «Загрузка…» дозаполняется без смены
  `DataContext`, см. `TableRowVm.Fill`;
- полоски цвета в колонке «№» НЕТ. Она была у сквозного цвета записи (приглушенная заливка
  под выделением строки читается плохо) и уехала вместе с ним: у оформления таблицы
  «пометки на полях» не ждут.

Данные: оформление ячеек приезжает батчем на страницу (`GetCellStylesBatch` рядом с
`GetFieldValuesBatch`), оформление строк и колонок — разреженными словарями при загрузке
коллекции (как высоты строк). Точечное обновление после правки идет по `_activeRows` —
видимому списку: при фильтре или сортировке строки на экране берутся из него.

### Выделение ячеек и буфер обмена

**Две независимые модели выделения.** Ячейки — РОВНО ОДИН прямоугольник
[`CellRange`](../../../../Core/Models/CellRange.cs) (якорь + фокус) или ничего. Ставится он
только кликом и Shift-кликом, а оба дают сплошной прямоугольник — поэтому рамка на экране всегда
одна, и «прямоугольник в прямоугольнике» невозможен структурно, а не по договоренности.
Ни Ctrl-набора вразнобой, ни протягивания мышью нет сознательно: оба заводили бы разрозненные
куски. У колонок раскладка своя (`SelectColumn`: Shift точечный) — там нет ни якоря, ни
прямоугольника.
Записи — штатный `SelectedItems` грида, и на нем держатся все пакетные операции (удаление,
дубль, «Расположение», «Действия»). Обе живут в `TableView`, но гасят друг друга:
`SetCellSelection` зовет `ClearRecordSelection`, клик по «№» — `ClearCellSelection`. Иначе
**Delete** было бы двусмысленным.

**Клик в другую ячейку при открытой правке закрывает ее САМ** (`CommitEdit` в начале ветки
левого клика). Иначе правку закрывает грид — и по дороге открывает редактор в ячейке, по
которой кликнули, если она в той же строке (`flag2` в `UpdateStateOnMouseLeftButtonDown`
разрешает правку соседней ячейки, пока строка в режиме правки). Выделение подменялось бы
правкой, а Shift и вовсе не показывал бы, что выделяет.

**Shift-клик гасится (`Handled`) — в отличие от обычного.** Гриду его отдавать нельзя: он
передвинул бы «текущую» ячейку на дальний угол выделения, и повторный Shift-клик по той же
ячейке открыл бы там редактор — внутри выделения появлялась бы вторая рамка. Заодно якорь
остается на месте, и следующий Shift тянет от него же. Правку это не ломает: «текущей» ячейку
делает обычный клик, с которого выделение и начинается.

Метка «текущей» ячейки от темы (`Rectangle#CurrencyVisual`) скрыта там же, где `FocusVisual`:
это отдельная тонкая рамка ВНУТРИ выделения, а где стоит курсор, показывает наша рамка.

Выделение строк переехало на служебный столбец **«№»** целиком: `OnCellPointerPressed`
разбирает `colIdx == 0` отдельной веткой и гасит `PointerPressedEventArgs.Handled`, иначе
`DataGrid` поверх нашего toggle сделал бы собственное выделение диапазоном.

**Координаты — позиции, а не идентификаторы.** В `CellRange` лежат индексы строки и колонки
в ПОКАЗАННОЙ таблице. Записи виртуализованы (`VirtualRowList`), строки переиспользуются при
прокрутке — держать в выделении `RecordId` значило бы каждый раз искать строку заново, а
держать `DataGridRow` — указывать на чужую запись после прокрутки. Идентификаторы резолвятся
в момент операции (`CellsOf`), строки, не успевшие подгрузиться, пропускаются: ждать загрузку
посреди копирования — подвесить UI.

**Рамка — отдельный слой, а не стиль ячейки.** `CellSelectionLayer` (Canvas поверх грида,
`IsHitTestVisible=False`) рисует ОДИН `Rectangle` на весь диапазон. Причины: ячейка при
прокрутке достается другой строке; рамка вокруг каждой ячейки давала бы сетку линий внутри
выделения.

> **Слой пересчитывается из `LayoutUpdated` — и это ловушка.** Любая правка дерева Canvas
> оттуда запускает новый проход разметки, тот снова зовет пересчет, и Avalonia валит
> приложение с `Infinite layout loop detected`. Защита двойная и обязательная:
> `ScheduleCellOverlayRefresh` откладывает работу на тик диспетчера, а
> `RefreshCellSelectionOverlay` сперва считает геометрию и выходит, если она не изменилась
> (сравнение с допуском в полпикселя — точное сравнение `double` цикл не разрывает).
> Та же пара защит стоит у полосок ресайза строк и колонок; `IsStaleRow` пропускается по той
> же причине, что и там, — иначе уехавшая за экран строка в правке растягивала бы рамку и
> геометрия дрожала бы от прохода к проходу.

**Номер колонки у реализованной ячейки.** `DataGridCell.Column` в Avalonia 11.2.3 —
`internal`, поэтому `RealizedCells()` считает колонку по ПОРЯДКУ ячейки внутри строки: порядок
ячеек в презентере совпадает с порядком колонок. Порядок сходится и при скрытых колонках:
грид заводит ячейку на КАЖДУЮ колонку и лишь гасит ей `IsVisible` — но такие ячейки (и
служебная filler-ячейка строки) имеют нулевой размер, поэтому в `SelectionBounds` они
отсеиваются, иначе их прямоугольник тянул бы рамку к началу координат.

**Скрытые колонки остаются в `_colDefs`** (там держатся порядок, фильтры и перемещение), но для
выделения и буфера их нет: `IsDataColumn` их отсекает, а `PasteColumnOf` помечает read-only —
вставка разливается ПО ПОЗИЦИЯМ, и значение, попавшее на скрытую колонку, ушло бы в невидимое
поле.

> **`IsReadOnly` у колонки ≠ «значение менять нельзя».** Это про отсутствие текстового
> редактора: `checkbox` и `file` помечены read-only на уровне сетки (правятся кликом), и
> `PasteColumnOf` снимает признак с галочки — иначе вставка и очистка молча обходили бы все
> колонки-чекбоксы.

### Правка ячейки и выделение строки — почему они связаны

Клик по ячейке НЕ гасится (`Handled`), хотя выделять строку он не должен. Причина в устройстве
`DataGrid`:

| Шаг | Где | Что дает |
|---|---|---|
| `DataGridCell_PointerPressed` | при `e.Handled` выходит сразу | наш `Handled` отрезал бы все следующие шаги |
| `UpdateStateOnMouseLeftButtonDown` | делает ячейку «текущей» | без «текущей» ячейки правки нет вовсе |
| там же, второй клик по той же ячейке | `BeginCellEdit` | собственно открытие редактора |
| `DataGrid.BeginEdit` | `if (!GetRowSelection(CurrentSlot)) return false` | правка ТРЕБУЕТ выделенной строки |

Поэтому гриду дают отработать целиком, а выделение строки снимают следом
(`ScheduleRecordSelectionDrop`, тик диспетчера — наш обработчик вызывается раньше грида).
`ClearRowSelection` «текущую» ячейку не трогает, поэтому второй клик по-прежнему открывает
редактор. Во время правки строка обязана оставаться выделенной: `SelectedItems.Clear()` внутри
делает `CommitEdit` и закрыл бы редактор — отсюда проверка `IsCellEditing` и повторный сброс по
`CellEditEnded`.

> **Клик внутри открытого редактора тоже приходит в `OnCellPointerPressed`.** `DataGridCell`
> подписан классовым обработчиком с `handledEventsToo: true`, поэтому событие доходит до нас,
> даже когда его уже забрал `TextBox`. Без отсечки по `_editingCell` первый же клик по тексту
> (поставить каретку) закрывал бы правку — по той же цепочке через `CommitEdit`.

> **Фокус в обработчике клика по ячейке забирать НЕЛЬЗЯ.** `Button.OnLostFocus` в Avalonia
> сбрасывает `IsPressed`, а `OnPointerReleased` поднимает `Click` только `if (IsPressed)`.
> Ячейки «Чекбокс» (`CheckBox`) и «Файл» (кнопка-скрепка `Pick.Click`) — обычные кнопки, и
> `Focus()` между нажатием и отпусканием убивал у них клик насмерть. Фокус и так остается
> внутри таблицы: обычной ячейке его ставит сам грид (`DataGridCell_PointerPressed`), а в
> ячейке с кнопкой — сама кнопка.

**Подсветка строки при выделенных ячейках гасится СТИЛЕМ, а не кодом.** Строка внутри
`DataGrid` выделена по-настоящему (без этого нет правки), поэтому `SetCellSelection` вешает на
грид класс `cellselect`, а `TableView.axaml` под этим классом возвращает `:selected`-строке
обычный фон. Наведение при этом подсвечивает ячейку (`DataGridCell:pointerover`), а не строку —
подсветка строки убрана из копии темы.

**Своя рамка прячется, только когда выделена РОВНО правящаяся ячейка** (`HidesOverlayWhileEditing`):
у редактора есть собственная рамка, и две вокруг одной ячейки читаются как ошибка отрисовки.
Растянутое выделение при открытой правке прятать нельзя — человек тянет Shift'ом от ячейки, в
которой только что печатал, и обязан видеть, что выделяется. Обновление зовется из
`BeginningEdit` / `CellEditEnded`.
Скругления у редакторов ВНУТРИ ячейки сняты стилями (`DataGridCell TextBox`, `ComboBox`,
`Border.timeField`): рамка правки стоит там же, где рамка выделения, а та прямоугольная — одно
и то же место таблицы не должно выглядеть то квадратным, то круглым.

> **`CellEditEnded` приходит НЕ всегда.** При подмене `ItemsSource` (`ReloadRows`,
> `ApplyFilters`, `Clear`) редактор умирает вместе со старыми строками молча. Без явного
> `ForgetCellEditing` флаг `IsCellEditing` оставался бы true навсегда — а тогда рамка выделения
> больше никогда не рисуется и Ctrl+C с Delete молчат. Симптом ровно такой: «после удаления
> записи выделение пропало и не появляется».

**Перезагрузка той же коллекции выделение не гасит.** `Load` зовется на каждое фоновое
обновление — в том числе вызванное нашей же записью в журнал при копировании. Сброс рамки там
означал бы «скопировал — и выделение пропало под руками».

**Меню ячейки** (`ShowCellMenuOn`) вешается на саму `DataGridCell` в момент правого клика:
`ContextRequested` приходит на отпускании кнопки, к этому времени меню уже на месте, а запрос
всплывает от ячейки и до строки не доходит — меню записи поверх не открывается. Меню носит
ровно одна ячейка (`_cellMenuHost`), у прежней снимается: переиспользованная при прокрутке
ячейка иначе показала бы меню чужой записи.

**Формат буфера** — [`TableClipboardFormat`](../../../../Core/Models/TableClipboardFormat.cs):
табуляция между колонками, `\n` между строками, значения с разделителями — в кавычках с
удвоением внутренних. Это формат, который понимают Excel, Гугл-таблицы и Numbers. В буфер
уходит ПОКАЗАННЫЙ текст (`CellText`), а не хранение: человек ждет в буфере то, что видит.

**Вставка** — [`TablePastePlanner`](../../../../Core/Models/TablePastePlan.cs), чистая логика без
ViewModels, поэтому проверяется тестами целиком. Выделенная ячейка = левый верхний угол, блок
разливается вниз и вправо. Размер выделения передается отдельно (`selectionRows`/`selectionColumns`,
по умолчанию 1×1): если выделение БОЛЬШЕ блока и вмещает его целиком, блок размножается по
выделению (одно значение — на все ячейки, пара — парами по кругу), как в Excel. Выделение меньше
блока или равное ему — не в счет. Строки не добавляются
никогда: вышедшее за края идет в `OutsideTable`. Значения приводятся к формату ХРАНЕНИЯ
(дата каноном `DateValue`, число с разделителем своей колонки, чекбокс `1`/`0`) — иначе
сортировка и фильтр видели бы два представления одного значения. `IsWritable` отсекает
вычисляемые, связи и файлы: наивная вставка иначе завела бы фантомные строки в
`db_field_values`.

**Запись — только пакетная.** `SetCellsBulk` (партиал
[ConstructorRepository.CellRange.cs](../../../../Database/Repositories/ConstructorRepository.CellRange.cs)):
одна транзакция, подготовленные INSERT/UPDATE/DELETE, аудит последней правки, **одна** строка
журнала со `Count`, после коммита — синхронизация `calendar_index` для полей даты и локального
кеша EF. Поштучный `SetFieldValue` дает около 18 значений в секунду: диапазон в пару тысяч
ячеек подвесил бы окно на минуты.

**Копирование пишется в журнал** (`LogCellsCopied` → действие `copy`): выгрузка в файл
оставляет `ExportTrace`, и копирование не должно остаться единственным бесследным способом
вынести данные. Пишется факт и количество ячеек, значения — нет.

**Очистка не трогает `__title__`.** Запись без названия становится «Без названия» и теряется
в списках, боковой панели и связях; стереть название можно только правкой записи. Вставке это
не мешает — там название заменяется на другое.

**Тесты.** `CellRangeTests`, `TableClipboardFormatTests`, `TablePastePlannerTests` (чистая
логика, Tests/Unit), `CellRangeWriteTests` (Tests/Integration — пакетная запись, журнал,
календарь).

### Ресайз и режимы

- Ширина колонок: стандартная или ручная (`SetColResizeMode`) — см. следующий подраздел.
- Высота строк: автоматическая или ручная (`SetRowResizeMode`, `SaveRowHeights`).
  Режимы переключаются из контекстных меню заголовка колонки и строки.

### Ширина колонок в ручном режиме

**Требуемое поведение.** Тянем границу вправо — колонка растет, соседи сохраняют ширину и
уезжают вправо, появляется горизонтальная прокрутка. Тянем влево — колонки справа
расширяются, пустоты справа не остается. Служебная «+» прижата к правому краю, пока
таблица помещается в окно.

**Почему колонки остаются `Star` в обоих режимах.** Прижатие «+» к правому краю — не
разметка и не наш код, а побочный эффект звездной раскладки Avalonia: пока есть хотя бы
одна видимая `Star`-колонка, `DataGridColumnHeadersPresenter` каждым measure доводит сумму
ширин до ширины вьюпорта, и внутренняя filler-колонка получает нулевую ширину. Переведи
колонки в пиксельную ширину — справа от «+» появится полоса filler'а с лишней вертикальной
линией. Поэтому ручная ширина выражается иначе: **звездный вес колонки == ее ширина в
пикселях, и та же величина ставится в `MinWidth`**. Дальше все делает сам движок:

| Ситуация | Что делает Avalonia | Что видит пользователь |
|---|---|---|
| сумма ширин > вьюпорта | колонки упираются в `MinWidth`, не сжимаются | горизонтальная прокрутка, «+» в конце контента |
| сумма ширин < вьюпорта | остаток роздан пропорционально весам | пустоты справа нет, «+» у правого края |

Наш код задает базу, движок гарантированно попадает в ширину вьюпорта — промах нашей
арифметики на доли пиксела не создает ни полосы filler'а, ни фантомной полосы прокрутки.

**Модель.** `_colWidths` (ключ колонки → ширина в DIP) меняется ТОЛЬКО жестом пользователя;
ресайз окна ее не трогает — поэтому «развернул окно и свернул обратно» возвращает ту же
картинку. Пока модель пуста, ручной режим выглядит как стандартный: включение режима вид
таблицы не меняет. `ApplyColumnWidths` идет двумя проходами — сначала `MinWidth`, потом
`Width`: сеттер `MinWidth` изнутри пересчитывает ширины соседей справа и портит уже
выставленные веса. Запись ширины идет через `SetColWidth`, который сперва меняет ТИП длины:
присваивание `Width` с тем же типом Avalonia трактует как ресайз и перекладывает дельту на
соседей, со сменой типа — как обычную запись.

**Свои полоски-захваты.** Встроенный ресайз (`CanUserResizeColumns`) выключен навсегда: у
него нет события конца перетаскивания (ширину негде сохранить), он запрещает тянуть
последнюю видимую колонку и вообще любой ресайз при переполнении, и сжимает соседей вместо
расширения таблицы. Вместо него — `ColResizeLayer`, точная калька слоя ручной высоты строк
(`Schedule…Refresh` → `Refresh…Handles` → `…GripsEqual` → `Begin/Drag/End`). Отличия от
строк: полоски идут по X у ПРАВОЙ границы заголовка, а к жесту добавлен
`PointerCaptureLost` — иначе Alt+Tab посреди перетаскивания оставил бы висеть флаг.

**Арифметика жеста.** На старте `MaterializeColumnWidths` фиксирует в модели то, что человек
видит (до первого drag'а модель пуста). Дальше на каждый кадр: `raw = старт + dX + сдвиг
прокрутки` (поправка нужна, чтобы граница не отлипала от курсора при клампинге прокрутки),
`target = max(floor, raw)`, `surplus = ширина_заполнения − (остальные + target)`. Колонки
СЛЕВА не трогаются никогда — иначе граница уехала бы из-под курсора; `surplus > 0` раздается
колонкам справа пропорционально их ширине. У самой правой движимой колонки `floor` — точка
«таблица ровно заполнена»: справа некому принять место. Сохранение — один
`SaveColumnWidths` на отпускание мыши, точечным upsert'ом.

**Снап к физической сетке** (`SnapColumnWidths`) работает в ОБОИХ режимах (раньше ручной был
из него исключен). `totalUnits` берется из фактической раскладки (сумма `ActualWidth`), а
доли — из модели: так снап сходится за один проход и не копит дрейф при многократных
ресайзах окна. Стандартный режим делит поровну, ручной — методом наибольших остатков
пропорционально ширинам, никогда не опускаясь ниже `MinWidth`.

**Константы.** `MinColWidth = 160` — стандартная ширина (минимум стандартного режима и
ширина колонки, для которой ручная еще не задана); `MinManualColWidth = 48` — пол ручного
перетаскивания. Верхнего предела у движимых колонок нет: именно отсутствие `MaxWidth`
позволяет весам поглощать любой излишек.

### Сохранение прокрутки

При создании/удалении/дублировании записи в середине больших таблиц контроллер
снимает и восстанавливает вертикальную позицию (`CurrentVerticalOffset` /
`RestoreVerticalOffset`), а при добавлении в конец — прокручивает к новой строке
(`ScrollToRecord`) или к колонке «+» (`ScrollToAddPropertyColumn`), чтобы кнопки
добавления оставались в зоне видимости.

### Производительность

Таблица рассчитана на коллекции до ~10 млн записей. Источник DataGrid —
[VirtualCollectionView](../../../../ViewModels/ConstructorDb/VirtualCollectionView.cs)
(`IDataGridCollectionView`): DataGrid не материализует источник, а запрашивает строки по
индексу только для видимых. Данные тянет [VirtualRowList](../../../../ViewModels/ConstructorDb/VirtualRowList.cs)
постранично (200 строк, LRU ≈10k) — `Count` из `CountRecords` без загрузки, последовательный
скролл по keyset **в обе стороны** (row-value сик `(Position, Id)`, 0.3 мс на любой глубине),
прыжки — offset по покрывающему индексу `(CollectionId, Position)`. Подгрузка строк — в фоновом
потоке с заглушками «Загрузка…» (флаг в настройках). Фильтр/сортировка — в SQL (список id +
виртуализация), без загрузки всей коллекции в память. Выпадающий список значений в заголовке
открывается мгновенно, значения считаются в фоне в порядке таблицы — по срезу фильтров
остальных колонок (Excel-каскад, см. ниже).

**Операции со свойствами/записями — без фриза и «белого» мелькания.** Перезагрузка разделена:
`ReloadColumns()` пересобирает только колонки (кэш строк не сбрасывается), `ReloadRows()` —
только источник строк (колонки не трогаются). Колоночные операции точечные, без `Columns.Clear`:
вставка одной колонки (`AddColumnForField`), замена на месте (`RebuildColumn`), сдвиг `RemoveAt`+
`Insert` (`MoveColumn`) — иначе полная пересборка грида дает белый экран на больших коллекциях.
Тяжелые удаление/дубль поля идут пакетами мимо EF (Id значений по индексу + сортировка + `Id IN`,
без OFFSET-O(n²)) на отдельном подключении в фоне. Удаление и дубль ВЫБРАННЫХ записей (мультивыделение
строк) — тоже bulk-SQL мимо EF в фоне (`DeleteRecordsData`/`DuplicateRecordsData`), а не цикл с
`SaveChanges` на каждую запись (вешал UI на 1000+ строк). Подсчет и работа уходят в фон, окно прогресса
(`RunBulkOp`) появляется отложенно — мелкие операции проходят без него, фазы «Подсчет значений…» →
проценты → «Сохранение…». Правка записи в правой панели обновляет ОДНУ строку на месте
(`RefreshRecordRow` → `RefreshRecord`/`Fill`), сдвиг строки — перечитывает только загруженные страницы
(`RefreshLoadedPages`), создание — без кросс-БД рефреша; все без полной пересборки таблицы. Окно
«Отображение записей» грузит список в фоне (не подвешивает открытие).

Подробности и оставшиеся узкие места — в [[../../architecture/performance/overview]].

## Фильтр колонки: чеклист значений

Окно фильтра (`BuildFilterPanel`) — сортировка сверху, поиск и чеклист значений снизу,
применение по «Готово» или Enter в поиске. Чеклист живет **сырыми** значениями колонки:
отмеченное множество уходит в `_filters[key]` и дальше в `GetFilteredRecordIds` как `IN (...)`.

**Правила галочек — в чистой модели** [`FilterSelection`](../../../../Core/Models/FilterSelection.cs)
(покрыта `FilterSelectionTests`), общей для плоского списка и дерева дат; окно лишь сообщает
ей, что показано сейчас (`MatchedRaws()`):

- ввод в поиске отмечает все найденное на каждое изменение текста (`OnSearch`); первый ввод
  запоминает галочки «до поиска», очищенный поиск возвращает их. По приходе данных снимок
  сбрасывается (`Reset`) — печатать могли раньше, чем загрузились значения;
- «Готово» и Enter в поиске — один `Apply()`. `Effective()` при поиске берет отмеченное среди
  найденного (Excel-режим «Заменить»), без поиска — все отмеченное, в том числе значения
  прежнего фильтра, которых нет в списке (их строки спрятал фильтр другой колонки); отмечено
  все, что есть в колонке (надмножество `domain`), — фильтр снимается;
- при открытии значения действующего фильтра идут первыми (`ChosenFirst`; снимок на момент
  открытия, от щелчков строки не прыгают). Дерево дат порядок не меняет;
- строки списка перечитывают галочку по `FilterValueVm.Refresh()`, дерево — по
  `DateFilterTreeBox.RefreshChecked()`: контейнеры виртуализированного списка
  переиспользуются, и без события привязка не узнает о правке общего набора;
- «(Выделить все)» при поиске подписан «(Выделить все найденное)» и действует на найденное.

**Excel-каскад считается в SQL.** `GetColumnCountsAsync(collectionId, key, _filters,
excludeHidden)` → `GetColumnCounts`: срез записей строит `FilteredRecords` — тот же запрос,
что и у `GetFilteredRecordIds`, — по фильтрам ОСТАЛЬНЫХ колонок (свой ключ репозиторий
отбрасывает сам: иначе снятое значение нельзя вернуть) и без скрытых в «Отображении
записей». Счетчики поля — JOIN `db_field_values` со срезом, группировка по индексу
`(FieldId, Value)`, «(Пусто)» = `scope.Count()` минус непустые; «Название» — группировка
среза; связь — `RelationTitlesBySource`, отсеченный по id среза. Снимок фильтров берется на
UI-потоке (`OtherFilters`), фон живой словарь не читает; пути чужих баз снимаются для ВСЕХ
полей-связей, участвующих в запросе (считаемого и фильтрующих). Покрыто
`ColumnFilterCascadeTests`. Журналы («Диагностика», «История изменений», «Пользователи»)
каскад, автоотметку найденного и Enter не получили — их окна остались прежними.

**Форма условия фильтра решает, подъемен ли каскад.** Набор значений уходит в SQLite как
`IN (SELECT value FROM json_each(@p))`, и внутри КОРРЕЛИРОВАННОГО `EXISTS` SQLite перебирает
его заново на каждую строку. На стенде `Tests/test_database.db` (10 млн записей, фильтр «один
день» = 1444 сырых значения даты, 5 млн строк) прежняя форма фильтра — `EXISTS (... AND Value
IN (...))` — не укладывалась в 5 минут; так вела себя и сама таблица при таком отборе, каскад
лишь унаследовал бы это. `FilteredRecords` теперь проверяет строку некоррелированным
`r.Id IN (SELECT RecordId FROM db_field_values WHERE FieldId = ? AND Value IN (...))` (и так же
для внутрибазовой связи — по ребрам): список id строится один раз по индексу `(FieldId, Value)`.
Замер там же (через `GetColumnCounts`/`GetFilteredRecordIds`): список id фильтра — 12 с,
каскадный список колонки по этому срезу — 14–16 с, список колонки дат без фильтров (5 млн
уникальных значений, как и раньше) — 22 с; самый тяжелый случай — те же 5 млн уникальных дат
по срезу «(Пусто)» другой колонки на все 10 млн записей — 42 с. То есть окно с каскадом
открывается не дольше, чем без него (порядок тот же), а фильтр таблицы стал считаться на
порядки быстрее. Ветка «(Пусто)» осталась коррелированной — в ней нет списка, только проба по
первичному ключу.

> Ручная проверка склейки с UI — [qa-checklists/filter-column.md](../../qa-checklists/filter-column.md).

**Колонка-дата — исключение по виду, но не по механике.** Вместо плоского списка строится
дерево «год → месяц → день» ([`DateFilterTreeBox`](../../../../Controls/Components/DateFilterTreeBox.cs)
поверх чистого [`DateFilterTree`](../../../../Core/Models/DateFilterTree.cs)):

- отмечается **день**, но в `checkedSet` кладутся все сырые значения этого дня — фильтр,
  сортировка и SQL не меняются вовсе;
- галочка родителя = «отмечено все поддерево» (`DateFilterTree.IsFullyChecked`), без
  промежуточного состояния: снят хоть один день — у месяца и года галочки нет. Клик
  решает по фактическому состоянию (отмечено все → снять ветку, иначе → отметить
  целиком), а не по значению, которое прислал чекбокс;
- свернутые ветки в `ItemsSource` не попадают, поэтому виртуализация списка работает как
  на плоском чеклисте;
- раскладка строки повторяет дерево сайдбара: слот стрелки шириной ровно в шаг отступа
  (`IndentStep`), стрелка — `IconSizeSmall`/`IconStrokeSmall`. Слот сохраняется и у дня,
  где стрелки нет, иначе лесенка чекбоксов ломается на листьях;
- порядок годов/месяцев/дней следует выбранной сортировке колонки, поэтому смена
  «Сначала старые ↔ Сначала новые» **пересобирает** дерево (`MountTree`);
- поиск ищет по номеру дня, полной дате `дд.MM.гггг`, названию месяца и году
  (`DateFilterTree.Search`), найденные ветки раскрываются;
- «(Выделить все)» и Excel-режим «Заменить» работают через `MatchedRaws()` — общий язык
  обоих режимов: показанные сейчас сырые значения.

Тот же компонент стоит в фильтрах «Диагностики» (колонка «Время») и «Истории изменений»
(«Дата и время»); там сырое значение — сама дата `yyyy-MM-dd`, поэтому фабрика другая
(`ForIsoDates` против `ForStorageDates`), а все остальное общее.

## Навигация нижней панели

Нижняя панель ([FooterConstructor](../../../../Controls/Components/Footer/FooterConstructor.axaml))
показывает «‹‹ ‹ 10 – 50 из 125 437 › ››» и больше ничего. **Страниц фиксированного
размера у таблицы нет** — она виртуализирована и прокручивается непрерывно, поэтому
индикатор показывает номера строк, которые сейчас в окне, а кнопки двигают ту же
вертикальную полосу, что и колесо мыши.

> Кнопки «Фильтр» и «Сортировка» из панели **удалены**: события они поднимали, но их
> никто не слушал — живые фильтр и сортировка вызываются из меню заголовка колонки.
> Счетчик «Всего: N» убран как дубль (то же число стоит после «из»); вместе с ним ушли
> вызовы `CountRecords` при открытии коллекции и при каждом структурном обновлении строк —
> на большой коллекции это был заметный запрос на UI-потоке.

### Что где живет

| Слой | Ответственность |
|---|---|
| [TableViewportRange](../../../../Core/Models/TableViewportRange.cs) | чистая логика: текст индикатора, `AtStart`/`AtEnd` для гашения кнопок, нормализация «мусорного» диапазона, `FromSlots` — перевод слотов DataGrid в номера строк; `TableViewportScroll` — куда встает полоса. Покрыто `TableViewportRangeTests` |
| `TableView` | `VisibleRowRange()` + `VisibleRangeChanged`, методы `ScrollRowsPageBack/PageForward/ToStart/ToEnd` |
| `FooterConstructor` | кнопки (`FirstRowClicked`/`PrevPageClicked`/`NextPageClicked`/`LastRowClicked`) и `SetRange` |
| `ConstructorControllerView` | связывает одно с другим; в виде «Список» ставит `TableViewportRange.Empty` (кнопки гаснут — двигать нечего) |

### Откуда берется диапазон

Номера видимых строк спрашиваются **у самого DataGrid**: `DisplayData.FirstScrollingSlot`
и `DisplayData.LastScrollingSlot` — те самые слоты, по которым контрол раскладывает строки
и сам отвечает на `SlotIsDisplayed`. Доступ рефлексией (`DisplayData` internal), версия
Avalonia зафиксирована 11.2.x — имена и типы стережет `DataGridInternalsTests`.

Перевод слотов в номера строк — `TableViewportRange.FromSlots`, чистый и покрытый
`TableViewportRangeTests`; у `TableView` остается только доступ к гриду. Группировки у
таблицы нет (`VirtualCollectionView.Groups = null`), поэтому слот = индекс строки, а ее
номер = индекс + 1. Отдельно оговорены два края:

- **строка «+»** стоит последним слотом (ее индекс = число записей) — ее номер срезается по
  общему числу, поэтому у самого низа индикатор показывает последнюю ЗАПИСЬ. Если в окне
  осталась одна «+», диапазон все равно `N – N`, а не «0 из N»: иначе погасли бы все четыре
  кнопки и вернуться наверх было бы нечем;
- **`FirstScrollingSlot = -1`** — ничего не разложено (первый проход, пересборка строк):
  «0 из N», число записей к этому моменту уже известно.

Деление `offset / RowHeight` не годится: высота строк бывает **ручной** (своя у каждой), и
счет врал бы. Номера — порядковые в текущем срезе: `VirtualRowList` проставляет
`RowNumber = индекс + 1` и для отфильтрованного списка тоже, поэтому при фильтре индикатор
считает от единицы, а `Total` берется из `_activeRows.Count - 1` (минус строка «+»).

### Почему нельзя считать по визуальному дереву

Обход `DataGridRow` из дерева (`VisibleRowRangeByTree` — теперь только запасной путь на
случай отказа рефлексии) находит и строки, которых на экране давно нет. Их две породы.

**Сироты после прыжка к краю.** «‹‹» и «››» уводят грид в `ResetDisplayedRows` →
`DisplayData.ClearElements`, а тот только помечает старые строки переработанными и **чистит
стек переработки** — из `_rowsPresenter.Children` он их не убирает (в отличие от
`UnloadRow` на обычной прокрутке). Переиспользовать их уже некому — новые строки создаются
с нуля; раскладывать заново тоже: `DataGridRowsPresenter.ArrangeOverride` ходит только по
`DisplayData.GetScrollingElements()`. Строки так и висят в дереве со старыми `Bounds` и
старым `DataContext`. На экране их не видно лишь потому, что новые строки добавлены в
`Children` позже и рисуются поверх.

**Паркованная строка с фокусом или в правке.** Эти две DataGrid не перерабатывает вовсе
(`IsRowRecyclable` = строка не `EditingRow` и не `_focusedRow`): уехав за экран, она
закрывается пустым `Clip` и остается в дереве. Сам он ее не распаркует — фокус остается в
гриде, кнопки нижней панели его не забирают (Avalonia `Button` по клику не фокусируется),
так что `DataGrid_LostFocus` → `ResetFocusedRow` не срабатывает.

Обе породы давали в индикаторе смесь двух экранов: `«71 – 456 002 из 456 002»` после прыжка
в конец (`last` от настоящих строк, `first` от сироты) и `«1 – 455 774 из 456 002»` после
прыжка в начало. В запасном пути они отсеиваются `IsStaleRow` — `!IsVisible` для сирот в пуле
(их прячет `FullyRecycleElements`, показывает обратно `GetUsedRow`) и непустой `Clip` для
паркованных (живой строке `Clip` снимают в `InsertDisplayedElement`, а сами мы строкам `Clip`
нигде не задаем: `RoundedClip` живет на полях ввода и списках).

> **Судить по флагу `IsRecycled` нельзя.** Он ставится при уходе строки в пул и никогда не
> сбрасывается: любая переиспользованная строка помечена им навсегда. После первой же подмены
> `ItemsSource` (перезагрузка после вставки, очистки, фильтра) ВСЕ живые строки —
> переиспользованные, и проверка по флагу считала «застрявшим» весь экран: рамка выделения
> ячеек переставала рисоваться, а диапазон нижней панели пустел. Симптом: «после очистки или
> вставки клик перестает выделять ячейку».

Тот же `IsStaleRow` стоит в слое полосок ресайза строк — иначе в ручном режиме высоты
брошенная строка ставит полоску у чужой границы.

Поведение пришпилено к Avalonia 11.2.x — после апгрейда прогнать
[qa-checklists/table-navigation.md](../../qa-checklists/table-navigation.md) целиком.

### Почему прокрутка идет через полосу, а не ScrollIntoView

У Avalonia DataGrid вертикальная полоса пиксельная (`Value`/`Maximum`/`ViewportSize`), и
абсолютная прокрутка делается тем же приемом, что в `RestoreVerticalOffset`: выставить
`Value` и применить `ProcessVerticalScroll(ThumbTrack)` — ветка `ThumbTrack` инвалидирует
measure, поэтому виртуализация подтягивает страницы новой позиции. Доступ — рефлексией
(версия Avalonia зафиксирована 11.2.x). `ScrollIntoView` тут не подходит: он требует
материализованный элемент, а прыжок «в конец» на 125 тысячах строк как раз идет туда, где
ничего не материализовано.

Пересчет диапазона висит на `LayoutUpdated` грида (`OnGridLayoutUpdated`) — так индикатор
следит и за колесом, и за ресайзом окна, и за перезагрузкой строк. Наверх событие уходит
**только на изменение** диапазона: `LayoutUpdated` дергается на каждый проход разметки.

## Взаимодействия (события наверх)

| Событие | Назначение |
|---|---|
| `RecordClicked` | открыть запись в правой панели |
| `VisibleRangeChanged` | видимый кусок таблицы сменился — нижняя панель обновляет индикатор и активность кнопок |
| `RecordCreateRequested (Open, AfterId)` | создать запись (в конце / после строки) |
| `RecordsDeleteRequested` / `RecordDuplicateRequested` | удалить / дублировать записи (оба несут СПИСОК id — все мультивыделение строк) |
| `RecordRelocateRequested` | «Расположение»: перенести записи в другую коллекцию/БД (СПИСОК id — мультивыделение строк); контроллер открывает [RecordLocationDialog](../../../../Controls/Dialogs/RecordLocationDialog.axaml.cs) |
| `PropertyCreateRequested` / `PropertyCreateAfterRequested` | новое свойство (в конец / после колонки) |
| `PropertyEditRequested` / `PropertyDuplicateRequested` / `PropertiesDeleteRequested` | правка / копия / удаление свойств; дубль и удаление несут СПИСОК id (все мультивыделение колонок) |
| `SystemFieldRenameRequested` | переименовать «Название» |
| `ColumnDisplayRequested` / `RecordDisplayRequested` | окна «Отображение» колонок / записей |

Мультивыделение строк + клавиша Delete → `RecordsDeleteRequested`; то же для
свойств → `PropertiesDeleteRequested` (обязательные поля защищены).

Столбец с ролью раздела удаляется как обычный, но окно подтверждения называет потерю
(«Исполнитель» — записи коллекции перестанут отображаться в задачах) — см.
[[../tasks]] → «Удаление ролевого столбца».

## Перенос записи («Расположение»)

Контекстное меню записи → «Расположение» открывает [RecordLocationDialog](../../../../Controls/Dialogs/RecordLocationDialog.axaml.cs)
(целевая БД + коллекция, как у коллекций в сайдбаре). Перенос — это copy + удаление исходной, работает
и внутри одной БД, и между БД; пакетно на изолированных подключениях в фоне
(`MoveRecordsToCollectionIsolated` → `MoveRecordsCore`, окно прогресса только на большом объеме, как
дубль/удаление). Производительность по тем же правилам, что у `DuplicateRecordsData` — план сопоставления
полей считается один раз, значения каждой записи пишутся одним `AddRange`, копия в одной транзакции,
`calendar_index` наполняется разом по диапазону новых id, исходные удаляются `DeleteRecordsData` (см.
[[../../architecture/performance/overview]]).

Перенос значений **грамотный** — устойчив к разным схемам коллекций:

- Сопоставление полей **по имени** (без учета регистра).
- **Приведение типов** при пересечении границы «дата» (`ConvertValueForType` поверх [DateValue](../../../../Core/Models/DateValue.cs));
  остальные типы хранятся как обычные строки и копируются как есть.
- Несовпадающие свойства источника: галочка **«Перенести все свойства»** в окне — выкл → отбрасываются
  (схема цели не меняется), вкл → создаются в целевой коллекции (`AddField`, полное сохранение данных).
- Поля цели, которых нет в источнике — остаются пустыми.

Тот же `CopyFieldValuesByName` чинит перенос значений при смене коллекции/БД из окна события
календаря (см. [[../calendar/interactions]]); там недостающие свойства не создаются (окно не меняется).
