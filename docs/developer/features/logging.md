# Диагностическое логирование

## Назначение

Приложение раздается пользователям, и когда у кого-то что-то ломается, разработчику
нужно понять причину. Раньше в файл `crash.log` попадали только фатальные падения —
не-фатальные проблемы (не открылась база, битый файл импорта, сбой подключения к
PostgreSQL, ошибка расширения) нигде не фиксировались.

**Диагностический лог** пишет ошибки, предупреждения и ключевые события в отдельную
базу-файл **`logs.db`**. Читает их разработчик — внутри приложения в разделе
**«Настройки → Диагностика»** или снаружи, открыв `logs.db` в DB Browser for SQLite.
`crash.log` остается как независимый резерв для фатальных падений.

Технология — **Serilog** (стандарт логирования в .NET) + приемник
**Serilog.Sinks.SQLite** (пишет структурированные записи в таблицу SQLite).

## Как работает

### Файл и его расположение

`logs.db` создается приложением автоматически при первом запуске (как `app.db`),
лежит в папке данных `AppSettings.AppDataDir`:

| ОС / режим | Путь |
|---|---|
| Windows (у пользователя) | `%AppData%\SmartBase\logs.db` (`%AppData%` — это уже `…\AppData\Roaming`) |
| macOS | `~/Library/Application Support/SmartBase/logs.db` |
| Linux | `~/.config/SmartBase/logs.db` |
| Debug (у разработчика) | `<корень проекта>/.localdata/logs.db` |

Это **единый файл на приложение** — не привязан к пользовательским базам данных
(в отличие от «Истории изменений», которая живет в каждой базе).

Таблицу `logs` создает сам приемник; столбцы: `id` (автоинкремент, хронология),
`Timestamp` (UTC), `Level`, `RenderedMessage`, `Exception`, `Properties`. Автоочистка
записей старше **30 дней** (`retentionPeriod`) — файл не разрастается.

### Уровни и запись

Минимальный уровень — **Information** (Debug и ниже не пишутся, чтобы не было шума).
Используются: `Information` (события: старт и завершение, монтирование базы, службы, итоги массовых операций), `Warning` (штатные, но заметные
сбои), `Error` (реальные ошибки), `Fatal` (падения).

Приемник настроен на `batchSize: 1` — каждая запись пишется **сразу (~0,1 c)**, а не
копится пачкой (по умолчанию приемник ждет таймер ~10 c). Строки в шаблонах пишутся
со спецификатором `{Param:l}` — иначе Serilog оборачивает значения в кавычки.

### Экран «Диагностика»

Раздел **«Настройки → Диагностика»** (выше «О программе» — системная, а не
пользовательская вещь) показывает `logs.db` таблицей в том же виде, что «История
изменений»: колонки **Время · Уровень · Сообщение · Ошибка** (с иконками типов в
шапке), Excel-фильтр и сортировка в шапке каждой колонки, подгрузка страницами по 200
при прокрутке. Данные читает `LogReader` сырым SQL по `logs.db` (отдельное read-only
подключение на фоне).

Клик по строке открывает справа **панель «Детали»** во всю высоту (навбар вровень с
навбаром настроек, как панель записи в конструкторе): карточки полей сверху (клик по
карточке раскрывает поле снизу), ручка-разделитель тянет высоту блока карточек, снизу —
полный текст выбранного поля (перенос по словам, кнопка копирования). Ширину панели
тянет вертикальная ручка у ее левого края. Оформление 1-в-1 повторяет «Страницу записи»:
блок карточек на **серой подложке** (`BrushSecondaryBg`, залита вся звездная строка —
блок отбит от белой шапки сверху и текста снизу), сами карточки **белые**, наведение —
чуть притемненный белый (`BrushInactiveBg`; серый hover совпал бы с подложкой), выбор —
голубой фон с синей рамкой. Стиль карточек общий — `Border.detailRow` в
`Assets/Styles/Controls.axaml`, тот же в «Профиль → История изменений», где панель
деталей устроена так же; подложку задает разметка каждой панели (`ScrollViewer` вокруг
`*DetailCardsHost`).

### Выгрузка в CSV

Кнопка со стрелкой в правом краю навбара раздела (та же, что «Импорт/Экспорт» в сайдбаре)
выгружает журнал диагностики в файл. Порядок: окно подтверждения (сколько строк, формат,
учитываются ли фильтры) → выбор файла → окно прогресса с процентами, счетчиком строк
и оценкой оставшегося времени (`Utils/EtaEstimator`, те же фразы, что при монтировании баз) →
итоговое сообщение с путем. Отмена доступна на любом шаге; недописанный файл удаляется.

Выгружается ровно то, что показано: те же фильтры, та же сортировка, те же человеческие
подписи (`Logging/LogLabels` — общий источник для таблицы и файла). Строки читает
`LogReader.ReadCsvRows` — ленивый keyset-поток на своем read-only подключении, файл пишет
`Core/Exporters/CsvDump` (тот же `CsvTableWriter`, что у экспорта коллекций: UTF-8 с BOM,
разделитель «;», CRLF). Память при этом постоянная: на замере 10 млн строк —
16 с (~600 тыс. строк/с), файл 1,3 ГБ, живая куча 7 МБ
([benchmarks.md](../testing/benchmarks.md), команда `csvlog`). Хронология читается
keyset-страницами (короткие транзакции — Serilog продолжает писать лог во время выгрузки),
сортировка по строковой колонке — одним запросом с ORDER BY (индексов на них нет,
страницами каждая пересортировывала бы всю таблицу).

### Надежность (чтобы не потерять серьезную ошибку)

- `crash.log` пишется **синхронно** в момент падения — фатальная ошибка там есть
  всегда, независимо от буфера `logs.db`.
- Обработчик `unhandled` в `Program.cs` после записи зовет `AppLog.Shutdown()`
  (форс-сброс буфера в `logs.db`) — иначе `finally` в `Main` при падении с фонового
  потока мог бы не выполниться.
- `batchSize: 1` делает окно возможной потери ничтожным (запись уходит на диск сразу).
- Внутренние ошибки самого приемника (`logs.db` заблокирован, поврежден, диск полон) Serilog
  иначе роняет молча — `AppLog.Init` направляет его SelfLog в `crash.log` (`CrashLog.Append`,
  не больше 20 строк за сеанс): отказ журнала виден хотя бы там.

## Что логируется

Журнал охватывает работу программы целиком: не только сбои, но и состояния служб, историю
работы с базами и отклонения по скорости. Принцип прежний — пишется то, что нужно для
разбора, и не пишется шум: успешные быстрые операции, косметика интерфейса, каждое
обращение при недоступной базе. Полный перечень по областям:

**Жизненный цикл программы**

- Запуск с версией и ОС; штатное завершение с причиной (закрытие окна, выход из трея,
  перезапуск для обновления), временем работы и числом закрытых баз (`App`, `desktop.Exit`).
  Отсутствие записи о завершении после записи о запуске выдает убитый процесс или
  выключение питания.
- Любое падение → `Fatal` + `crash.log` (`Program.LogCrash`); непредвиденная ошибка UI-потока
  (`App`, `Dispatcher.UnhandledException`).
- Повторный запуск: второй экземпляр отклонен, окно работающего показано (`App`);
  наблюдатель сигнала не создан (`SingleInstance`).
- Системная база `app.db` не открылась (`App`); уборка настроек удаленных расширений.
- Автопроверка обновления: доступна версия / актуальна / не удалась; загрузка не удалась;
  апдейтер запущен, приложение закрывается для самозамены (`SettingsView`).

**Базы данных**

- **Монтирование — одна запись на базу**: имя, время, провайдер, «локальный путь» /
  «сетевой путь» / «сервер PostgreSQL», режим журнала (`wal` / `delete`), размер файла и доля
  свободных страниц, что сделали миграции (с какой версии на какую, сколько, за сколько) и
  индексация календаря, если дольше 2 с (`DatabaseManager.LogMounted`). Дольше минуты
  (`Diag.Mount`) — предупреждение вместо сведений.
- **Контроль прагм**: режим журнала не переключился (общая база осталась в WAL на сетевом
  пути — риск порчи), `busy_timeout` = 0, лимит WAL не применился, прагмы подключения не
  применились (одна запись на файл за сеанс), чекпоинт WAL не выполнен не из-за занятости
  (`DatabaseManager`, `AppDbContext`).
- Сжатие файла — «было → стало» и время, и автоматическое при монтировании, и по кнопке
  «Сжать файл» (`DatabaseManager`, `MainWindow`).
- **Резервное копирование** (см. [[backup]]): служба запущена с числом включенных
  расписаний / остановлена; копия базы начата (вручную или по расписанию); копия
  сохранена — путь, размер, время (`DatabaseManager.BackupTo` для SQLite, `PgDump` для
  PostgreSQL — строки одинаковые); удалено старых копий ротацией; копия не создана —
  `Error` с причиной (плановые сбои — не чаще раза в 10 минут на базу, `Diag.Throttle`;
  ручные — всегда). Строка подключения и пароль PG не пишутся никогда.
- Не удалось смонтировать, повтор после BUSY со сбросом пула, неожиданный сбой очереди,
  обслуживание файла не удалось, ошибка закрытия (`Workspace`, `MountQueue`).
- **Потеря и возврат**: база потеряна (всегда, с соседями по серверу или без), снова
  доступна — сколько была недоступна и с какой попытки, BUSY с последующим сбросом пула
  (`DbHealthMonitor`). Для PostgreSQL то же самое: «сервер недоступен» / «снова доступна».
- **Поллер чужих правок**: серия BUSY с переоткрытием соединения, наблюдение сброшено
  (одна запись на серию до возврата базы); отброшены правки строк, удаленных соседом
  (`ChangePoller`, `AppDbContext`).
- **Права и допуск**: первый пользователь стал администратором, пользователь
  зарегистрирован и ждет допуска, допуск выдан/отозван, роль изменена, пользователь удален,
  допуск по паролю, неверный пароль базы (`PermissionService`).
- Незавершенный перенос между базами: найден маркер, частичная копия удалена, свип не
  удался (`ConstructorRepository.CrossMove`).
- Ремонт пустых «Названий»; не прочитаны сведения о файле.

**Запись и чтение данных**

- Ошибки записи на действиях пользователя: отказ по правам, база занята, недоступна,
  конкурентная правка (`DbErrors.Handle`). **Повреждение файла** (CORRUPT/NOTADB) зовется
  своим именем уровнем `Error` — это данные, а не сеть.
- Ошибки чтения (фоновые подгрузки): недоступна / занята — **одна запись в минуту на базу**
  (`DbErrors.HandleRead`, `Diag.Throttle`): первый отказ виден, серия при скролле не забивает
  журнал. Страница таблицы, список значений фильтра, окно календаря, раздел «Задачи» не
  прочитаны по иной причине (наш дефект) — предупреждение с базой и коллекцией.
- Настройка свойства не разобрана (сломанный `ConfigJson` связи, числа, авто-привязки файла) —
  одна запись на отличающийся конфиг за сеанс (`ConfigJsonLog`).

**Массовые операции**

- Импорт: коллекция, строк, файл, время; экспорт: коллекция, строк, файл; дубль, перенос и
  удаление в фоне (большие объемы, с окном прогресса): целей, записей, время (`SidebarTree`);
  выгрузка журналов в CSV: строк, файл, время (`CsvExportRunner`). Ошибки — как раньше
  (`ImportErrors` / `ExportErrors`, сбои фоновых операций).

**Службы без окна**

- Фоновый режим: включен при старте (значок создан / недоступен), значок в трее не создан
  (крестик будет закрывать программу, уведомления не придут), тумблер переключен (`MainWindow`).
- Служба уведомлений: запущена с состоянием тумблеров и меткой, остановлена, тумблеры
  переключены, курсоры очередей задач сброшены; события календаря не прочитаны, очередь задач
  недоступна, курсор не сохранен, баннер ОС не показан, значок не обновлен — не чаще раза
  в 10 минут на причину (`NotificationService`). Менеджер нативных уведомлений создан / не
  создан (`Program`).
- Автозапуск: запись создана, снята, не принята системой, приведена в порядок (`Autostart`).
- Хранилище паролей ОС (`SecretProtector`); установщик (`InstallerWindow`).

**Интерфейс**

- **Пороги медленности** (`Diag.Measure`): операция закончилась, но дольше порога —
  предупреждение с длительностью, порогом и контекстом (база, коллекция, объем). Точки:
  открытие раздела, коллекции, страницы записи, окон записи / свойства / «Отображение» /
  фильтра колонки, загрузка календаря и раздела «Задачи» — порог `Diag.UiOpen` (2 с);
  фильтр и сортировка таблицы, список значений фильтра — `Diag.UiQuery` (5 с); страница
  строк при прокрутке — `Diag.UiPage` (1 с).
- **Сторож UI-потока** (`UiWatchdog`, порог 3 с): интерфейс не отвечал N секунд — после
  оттаивания, со списком операций, которые шли в момент обнаружения (`Diag.ActiveOperations`).
  С операциями — предупреждение; без них — сведения (паузу без операций дают перетаскивание
  окна за заголовок и сон компьютера; дольше 5 минут без операций — «похоже на сон»).
- Не удалось открыть системой файл, ссылку, папку данных, папку экспорта; хранилище заметок
  недоступно (одна запись на путь за сеанс); механизм расширений не смог создать или открыть
  окно расширения (это ядро, а не расширение — см. ниже).

**Сознательно НЕ пишется** (иначе журнал забьется шумом):

- **Каждое обращение при недоступной базе** — только первое за минуту (см. выше); сам факт
  недоступности фиксируется монитором один раз.
- **Штатно быстрые операции** — открылось за 40 мс никому не интересно; пороги ловят только
  отклонение. Скрытие и возврат окна, клики по значку, фокус, отрисовка, буфер обмена.
- **Бизнес-валидация** — «файл пустой», «нет прав», дубль имени: это сообщения
  пользователю, а не диагностические ошибки.
- **Строка подключения PostgreSQL** — в ней пароль; в записях вместо нее «PostgreSQL»
  (`DbErrors.Display`, `AppDbContext.DisplayPath`).
- **Расширения** — ни одно не пишет сюда НИЧЕГО, `Serilog` в папке `Extensions/` не
  подключен (ни в окнах, ни в общем `ExcelBook`). Все, включая стек сбоя, идет в собственный
  журнал или статус окна расширения. Причина в отделимости: папку расширения можно удалить из
  программы целиком, а записи в общей диагностике его переживут и станут мусором, который
  никто не свяжет с исчезнувшим расширением. Образец — [[extensions/time-collector]].

Замечание по коду: у `ConstructorRepository` есть собственный метод `Log(...)` (запись
в журнал изменений), поэтому там логгер вызывается полным именем `Serilog.Log.Error(...)`.

### Обвязка: пороги, сторож, защита от шума

[`Logging/Diag.cs`](../../../Logging/Diag.cs) — общая обвязка диагностики:

- `Diag.Measure(операция, порог, контекст)` — `IDisposable`-замер: по `Dispose` запись, если
  длительность превысила порог. Контекст можно дополнить до `Dispose` (`scope.Context += …`),
  когда объем стал известен. Пороги — константы `UiOpen` / `UiQuery` / `UiPage` / `Mount`;
  новые точки берут их, а не свои числа.
- Реестр активных операций (`Diag.ActiveOperations`) — что выполняется прямо сейчас; его
  читает сторож в момент обнаружения зависания. Стек чужого потока в .NET не снять, поэтому
  «что висело» известно только из этого реестра — новая тяжелая операция на UI-потоке без
  `Diag.Measure` в записи о зависании будет безымянной.
- `Diag.Once(ключ)` — одна запись за сеанс (нечитаемый конфиг свойства читается на каждую
  отрисовку ячейки); `Diag.Throttle(ключ, период)` — не чаще раза в период (серии отказов
  чтения, сбои тика уведомлений). `Diag.Size` / `Diag.Duration` — «1,7 ГБ», «2 ч 15 мин».

[`Logging/UiWatchdog.cs`](../../../Logging/UiWatchdog.cs) + [`FreezeDetector.cs`](../../../Logging/FreezeDetector.cs):
`DispatcherTimer` на UI-потоке ставит отметку каждые полсекунды, фоновый таймер раз в

## Как забрать логи у пользователя

Отдельной кнопки экспорта нет. Пользователь открывает папку данных кнопкой
**«Открыть папку с данными»** в Настройках, копирует `logs.db` и присылает.
Разработчик открывает файл в DB Browser for SQLite (или смотрит в разделе «Диагностика»).

## Взаимодействия

- **`crash.log`** ([../../Program.cs](../../../Program.cs)) — независимый синхронный резерв
  для фатальных падений; дублирует Fatal-запись в `logs.db`. Лежит там же, в
  `AppSettings.AppDataDir`, появляется только при необработанном исключении и растет
  дозаписью (ротации нет). При сверке с `logs.db` учитывать разные шкалы времени:
  `crash.log` пишет **локальное** время (`DateTime.Now`), приемник Serilog — **UTC**.
- **`DbErrors` / `ImportErrors` / `ExportErrors`** — центральные обработчики: логируют
  внутри себя, поэтому новые места, идущие через них, покрываются автоматически.
- **«Настройки»** ([[settings]]) — раздел «Диагностика» стоит выше «О программе»:
  системная вещь, единый файл на приложение (не привязан к базе, в отличие от «Истории
  изменений» в «Профиле»). Таблица построена как «История изменений» + панель деталей строки.
