# Диагностическое логирование

## Назначение

Приложение раздаётся пользователям, и когда у кого-то что-то ломается, разработчику
нужно понять причину. Раньше в файл `crash.log` попадали только фатальные падения —
не-фатальные проблемы (не открылась база, битый файл импорта, сбой подключения к
PostgreSQL, ошибка расширения) нигде не фиксировались.

**Диагностический лог** пишет ошибки, предупреждения и ключевые события в отдельную
базу-файл **`logs.db`**. Читает их разработчик — внутри приложения в разделе
**«Настройки → Диагностика»** или снаружи, открыв `logs.db` в DB Browser for SQLite.
`crash.log` остаётся как независимый резерв для фатальных падений.

Технология — **Serilog** (стандарт логирования в .NET) + приёмник
**Serilog.Sinks.SQLite** (пишет структурированные записи в таблицу SQLite).

## Как работает

### Файл и его расположение

`logs.db` создаётся приложением автоматически при первом запуске (как `app.db`),
лежит в папке данных `AppSettings.AppDataDir`:

| ОС / режим | Путь |
|---|---|
| Windows (у пользователя) | `%AppData%\SmartBase\logs.db` (`%AppData%` — это уже `…\AppData\Roaming`) |
| macOS | `~/Library/Application Support/SmartBase/logs.db` |
| Linux | `~/.config/SmartBase/logs.db` |
| Debug (у разработчика) | `<корень проекта>/.localdata/logs.db` |

Это **единый файл на приложение** — не привязан к пользовательским базам данных
(в отличие от «Истории изменений», которая живёт в каждой базе).

Таблицу `logs` создаёт сам приёмник; столбцы: `id` (автоинкремент, хронология),
`Timestamp` (UTC), `Level`, `RenderedMessage`, `Exception`, `Properties`. Автоочистка
записей старше **30 дней** (`retentionPeriod`) — файл не разрастается.

### Уровни и запись

Минимальный уровень — **Information** (Debug и ниже не пишутся, чтобы не было шума).
Используются: `Information` (старт приложения), `Warning` (штатные, но заметные
сбои), `Error` (реальные ошибки), `Fatal` (падения).

Приёмник настроен на `batchSize: 1` — каждая запись пишется **сразу (~0,1 c)**, а не
копится пачкой (по умолчанию приёмник ждёт таймер ~10 c). Строки в шаблонах пишутся
со спецификатором `{Param:l}` — иначе Serilog оборачивает значения в кавычки.

### Экран «Диагностика»

Раздел **«Настройки → Диагностика»** (выше «О программе» — системная, а не
пользовательская вещь) показывает `logs.db` таблицей в том же виде, что «История
изменений»: колонки **Время · Уровень · Сообщение · Ошибка** (с иконками типов в
шапке), Excel-фильтр и сортировка в шапке каждой колонки, подгрузка страницами по 200
при прокрутке. Данные читает `LogReader` сырым SQL по `logs.db` (отдельное read-only
подключение на фоне).

Клик по строке открывает справа **панель «Детали»** во всю высоту (навбар вровень с
навбаром настроек, как панель записи в конструкторе): карточки полей сверху (клик по
карточке раскрывает поле снизу), ручка-разделитель тянет высоту блока карточек, снизу —
полный текст выбранного поля (перенос по словам, кнопка копирования). Ширину панели
тянет вертикальная ручка у её левого края. Оформление 1-в-1 повторяет «Страницу записи»;
стиль карточек общий — `Border.detailRow` в `Assets/Styles/Controls.axaml`, тот же
в «Профиль → История изменений», где панель деталей устроена так же.

### Выгрузка в CSV

Кнопка со стрелкой в правом краю навбара раздела (та же, что «Импорт/Экспорт» в сайдбаре)
выгружает журнал диагностики в файл. Порядок: окно подтверждения (сколько строк, формат,
учитываются ли фильтры) → выбор файла → окно прогресса с процентами, счётчиком строк
и оценкой оставшегося времени (`Utils/EtaEstimator`, те же фразы, что при монтировании баз) →
итоговое сообщение с путём. Отмена доступна на любом шаге; недописанный файл удаляется.

Выгружается ровно то, что показано: те же фильтры, та же сортировка, те же человеческие
подписи (`Logging/LogLabels` — общий источник для таблицы и файла). Строки читает
`LogReader.ReadCsvRows` — ленивый keyset-поток на своём read-only подключении, файл пишет
`Core/Exporters/CsvDump` (тот же `CsvTableWriter`, что у экспорта коллекций: UTF-8 с BOM,
разделитель «;», CRLF). Память при этом постоянная: на замере 10 млн строк —
16 с (~600 тыс. строк/с), файл 1,3 ГБ, живая куча 7 МБ
([benchmarks.md](../testing/benchmarks.md), команда `csvlog`).

### Надёжность (чтобы не потерять серьёзную ошибку)

- `crash.log` пишется **синхронно** в момент падения — фатальная ошибка там есть
  всегда, независимо от буфера `logs.db`.
- Обработчик `unhandled` в `Program.cs` после записи зовёт `AppLog.Shutdown()`
  (форс-сброс буфера в `logs.db`) — иначе `finally` в `Main` при падении с фонового
  потока мог бы не выполниться.
- `batchSize: 1` делает окно возможной потери ничтожным (запись уходит на диск сразу).

## Что логируется

Покрытие — **значимые сбои** (~29 вызовов в 17 файлах). Ключевой принцип: логируем
то, что нужно для диагностики, и **не логируем** шум.

**Пишется:**

- **Любое падение где угодно** → `Fatal` + `crash.log` (глобальная ловушка в `Program.cs`).
- **Ошибки базы при редактировании** — занята/недоступна (`DbErrors`).
- **Импорт/экспорт** — файловые ошибки (`ImportErrors.Map` / `ExportErrors.Map`),
  открытие битого Excel (`ExcelTableSource`), сбой записи импорта в БД (`ConstructorRepository`).
- **Открытие/монтирование базы** — не удалось смонтировать (`Workspace.Mount`, `MountQueue`),
  сбой дефолтной базы на старте (`App`).
- **Подключение к PostgreSQL** — ошибка проверки соединения (`PgConnectDialog`).
- **Установка/обновление** — ошибка установки (`InstallerWindow`).
- **Расширения** — сбои всех четырёх окон (AssemblyCalc, ProductCompare, PdfAnalyzer, PdfRename).
- **Пароли** — недоступно хранилище ОС, не прочитать/расшифровать пароль (`SecretProtector`).
- **Фоновые операции сайдбара** — сбой копирования/переноса/удаления узла.

**Сознательно НЕ пишется** (иначе журнал забьётся шумом):

- **Чтение при недоступной базе** (загрузка календаря/журнала/таблицы) — срабатывает
  на каждый скролл при отключении базы; сам факт недоступности уже фиксируется.
- **Косметика** — фокус, буфер обмена, отрисовка, best-effort очистка.
- **Бизнес-валидация** — «файл пустой», «нет прав», дубль имени: это сообщения
  пользователю, а не диагностические ошибки.

Замечание по коду: у `ConstructorRepository` есть собственный метод `Log(...)` (запись
в журнал изменений), поэтому там логгер вызывается полным именем `Serilog.Log.Error(...)`.

## Как забрать логи у пользователя

Отдельной кнопки экспорта нет. Пользователь открывает папку данных кнопкой
**«Открыть папку с данными»** в Настройках, копирует `logs.db` и присылает.
Разработчик открывает файл в DB Browser for SQLite (или смотрит в разделе «Диагностика»).

## Взаимодействия

- **`crash.log`** ([../../Program.cs](../../../Program.cs)) — независимый синхронный резерв
  для фатальных падений; дублирует Fatal-запись в `logs.db`. Лежит там же, в
  `AppSettings.AppDataDir`, появляется только при необработанном исключении и растёт
  дозаписью (ротации нет). При сверке с `logs.db` учитывать разные шкалы времени:
  `crash.log` пишет **локальное** время (`DateTime.Now`), приёмник Serilog — **UTC**.
- **`DbErrors` / `ImportErrors` / `ExportErrors`** — центральные обработчики: логируют
  внутри себя, поэтому новые места, идущие через них, покрываются автоматически.
- **«Настройки»** ([[settings]]) — раздел «Диагностика» стоит выше «О программе»:
  системная вещь, единый файл на приложение (не привязан к базе, в отличие от «Истории
  изменений» в «Профиле»). Таблица построена как «История изменений» + панель деталей строки.
