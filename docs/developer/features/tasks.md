# Задачи — общий обзор

## Назначение

Раздел «Задачи» показывает записи конструктора списком карточек-задач: название,
исполнитель, кто назначил, срок, статус (**Запланировано / В работе / Выполнено**)
и чип остатка («Осталось N дн./ч», «Сегодня», «Просрочено на N дн.»). Карточки
сгруппированы по коллекциям — заголовок коллекции над ее задачами, кликом он
сворачивается; какие коллекции показывать, решают галочки в сайдбаре. Это полный аналог календаря, где источник
события — поле-дата с флагом `IsCalStart`: здесь источник задачи — **user-поле с
флагом `IsTaskExec`** («исполнитель»). Записи-задачи
остаются обычными записями своих коллекций — в таблице конструктора видны те же
«Исполнитель», «Назначил», «Статус», дата и описание.

## Как работает

### Модель: задача = (RecordId, exec-FieldId)

Задача — не отдельная сущность, а проекция записи через включенное user-поле.
У `db_fields` три флага (миграция `AddTaskFieldFlags`):

- `IsTaskExec` — user-поле «исполнитель»: **каждая запись коллекции** с таким полем видна в
  разделе задач, заполнено оно или нет (значение = исполнитель, пусто = прочерк на карточке).
  Исполнитель у коллекции **один**: пока тумблер стоит на одном user-поле, включить второе
  нельзя (`SetUserFieldTaskExec` отказывает, чекбоксы остальных полей в сайдбаре гаснут);
- `IsTaskAssigner` — поле «Назначил» (user);
- `IsTaskStatus` — поле «Статус» (тип свойства `status` с опциями Запланировано/В работе/Выполнено
  в `ConfigJson`; см. [data-model.md](../architecture/data-model.md#status--статус)).

Имя роли сравнивается **без учета регистра** (как занятые имена в `FreeFieldName`): SQL-сравнение
строк регистрозависимо, а `lower()` в SQLite кириллицу не трогает — поэтому поля коллекции для
разметки ролей читаются в память.

**Одно поле — одна роль.** Два значения в одном `FieldId` затирали бы друг друга, поэтому чужую
роль под исполнителя не берут ни тумблер сайдбара (`SetUserFieldTaskExec` отказывает с
сообщением), ни авто-усыновление в `EnsureTaskCollection`. «Назначил» отсекается И по флагу,
И по имени (у поля, заведенного руками до включения задач, флага еще нет, а авто-разметка найдет
его ПО ИМЕНИ и добавит вторую роль); «Статус» на user-поле — только по флагу: по имени его
усыновляют лишь среди `select`/`status`-полей, а флаг у user-поля бывает от ручной пометки или
копирования (`TaskRoleGuardTests`, `TaskRecordsTests.Field_named_assigner_never_becomes_the_executor_field`).

**Роль работает только на своем типе** — общий реестр
[`RoleAllowsType`](../../../Database/Repositories/ConstructorRepository.Roles.cs):

| Роль | Тип свойства |
|---|---|
| исполнитель, «Назначил» | `user` |
| «Статус» | `status` / `select` |
| «Дата» (событие, срок) | `date` |
| «Описание» | `text` |

Раньше тип проверялся только у «Даты» и «Исполнителя», а остальные роли жили при любом типе.
Получалась **роль-призрак**: столбец «Статус» типа «Текст» нес флаг, показывал плашку «привязано
к разделу», но списка статусов в нем не было и выбрать «Выполнено» было негде. Теперь несущим
роль (`HasRole`) считается только поле подходящего типа, кандидатом по имени — тоже
(см. ниже), а смена типа роль **снимает** (`UpdateField` → `ClearRolesIncompatibleWithType`).

**Старые базы лечатся при монтировании**: `RepairTaskFieldRoles` (зовет `DatabaseManager` — после
`MigrateAndBackfillCalendarDates`, та переводит legacy-«Дату» из `text` в `date`) приводит разметку
к нынешним правилам сразу по трем дефектам:

- поле с двумя ролями задач — исполнитель остается, чужая роль снимается (затертых исполнителей
  не вернуть: их перезаписали значения второй роли);
- несколько исполнителей в коллекции — остается первый по `RoleOrder`, с остальных снимается флаг
  (значения в столбцах не трогаются, это обычные user-поля);
- роль на несовместимом типе — флаг снимается.

Освободившиеся роли заводятся заново — но только там, где остался исполнитель: без него раздел
все равно молчит. Обычная база платит два индексных запроса; у пользователя без прав на схему
починка не доходит до конца, ее доведет следующий с правами, — а отказ остается сведением в
журнале диагностики с коллекцией и недостающим правом (`LogRepairNotDone`, общий с библиотекой;
раньше отказ глотался без следа). Покрытие —
`TaskRoleGuardTests.Mounting_heals_a_field_that_carries_both_roles`,
`Mounting_heals_extra_executors_and_roles_left_on_wrong_types` и
`DiagnosticsLogTests.A_task_role_repair_refused_by_rights_leaves_a_trace`.

**Порядок выбора роли — `(Position, Id)`** (`RoleOrder`). Флаг может оказаться сразу у двух полей
(копирование, ручная правка, старая база), и без явного порядка `FirstOrDefault`/`LIMIT 1`
отдавали произвольную строку: запись значения и его чтение расходились по разным полям, раздел
показывал то одно, то другое. Правило одно на весь модуль — его же повторяет `ORDER BY` в
коррелированных подзапросах `GetTaskRecords`.

### Полный набор ролей и подтягивание по имени

Включение задач (`SetUserFieldTaskExec`, `EnsureTaskCollection`) и создание задачи
(`AddTaskRecord`) доводят коллекцию до **полного набора ролей**: «Назначил», «Статус»,
«Дата» (срок) и «Описание» — исполнитель это само поле с тумблером. Поле-дата появляется
даже у задачи БЕЗ срока: дату вписывают позже, и колонка для нее должна быть.

Общий механизм — [`EnsureRoles`/`PlanRoles`](../../../Database/Repositories/ConstructorRepository.Roles.cs):

- **кандидат** — столбец, который так и называется («Назначил», «Статус», «Дата», «Описание»),
  регистр не важен, **и подходит по типу** (`RoleAllowsType`, таблица выше). Текстовый «Статус»
  кандидатом не станет: подтянув его, окно само создало бы ту самую роль-призрак, которую чинит
  смена типа, — роль уходит новому полю с суффиксом « 2»;
- поле, уже несущее ДРУГУЮ роль (в т.ч. исполнителя), кандидатом не будет — две роли на одном
  `FieldId` затирают друг друга (см. `RepairTaskFieldRoles`);
- UI сначала **спрашивает** (`PlanRoles` → `ConfirmDialog` в `PropertyEditorDialog`): показывает
  найденные столбцы и то, какие поля появятся при отказе. «Подтвердить» → столбцы получают роли
  и их данные едут в раздел; «Отменить» (`adoptByName: false`) → столбцы не трогаем, роли
  достаются новым полям с суффиксом « 2»;
- проверка идет при КАЖДОМ включении тумблера, а не только при первом: пользователь мог
  переименовать столбцы и захотеть переключить раздел на другой. Эксклюзивная роль
  («Назначил»/«Статус»/«Описание») при подтверждении **переезжает** — у прежнего носителя
  флаг снимается; «Дата» не эксклюзивна (несколько дат = несколько событий), там флаг просто
  добавляется.

Размеченный столбец не выглядит обычным: в окне свойства у него красная плашка «привязано к
разделу «Задачи» — статус задачи» ([ui/dialogs](../ui/dialogs.md#плашка-привязано-к-разделу)).
Она пропадает вместе с ролью — снятый тумблер, переезд роли на другой столбец, удаление свойства,
смена типа на несовместимый.

**Плашка говорит только о том, что раздел действительно читает** ([`FieldRoleText.Of`](../../../Utils/FieldRoleText.cs)):
роли «Назначил» и «Статус» заявляются, лишь пока в коллекции есть поле-исполнитель, «Описание» —
пока коллекция участвует хоть в одном из разделов. Флаги при этом остаются на полях: удалили
исполнителя — плашка молчит и раздел молчит, вернули (или включили тумблер на другом user-поле) —
прежняя разметка ожила сама, заводить «Назначил»/«Статус» заново не нужно. Покрытие —
`FieldRoleTextTests`.

Разметка идет **одной транзакцией**: раздельные `SaveChanges` при сбое не по правам (гонка,
`DbUpdateException`) оставляли коллекцию с одной ролью из двух, а следующий вызов считал набор
уже полным. Права спрашиваются до первой записи: пометка чужого поля — `EditField`, создание
недостающего — `CreateField`. Покрытие — `RoleAdoptionTests`.

### Создание задачи тоже спрашивает

Раньше набор полей молча доводило и **создание записи**: окно задачи закрывалось, а в чужой
коллекции появлялось пять новых столбцов — узнать об этом можно было, только вернувшись в
конструктор. Теперь UI считает план заранее — `PlanTaskSetup` (задачи) и `PlanCalendarSetup`
(события) — и показывает [окно подготовки](../ui/dialogs.md#подготовка-коллекции-к-разделу):
что будет создано, какие существующие столбцы станут полями раздела. **«Отмена» — запись не
создается**, коллекция остается нетронутой.

- окно показывается **только если коллекция реально изменится** (`ChangesCollection`): набор
  размечен — запись создается молча, иначе окно всплывало бы на каждое событие;
- план обязан совпадать с тем, что сделает запись, поэтому `PlanTaskSetup` повторяет правило
  `EnsureTaskCollection` для исполнителя: свободное user-поле («Менеджер») **станет** им, и окно
  об этом говорит; `adoptExec: false` — правило переноса задачи в постороннюю коллекцию, там
  заводится собственное «Исполнитель»;
- `FieldsToCreateIfAdopted` (создается при согласии) и `FieldsToCreateIfDeclined` (при отказе от
  подтягивания, с суффиксом « 2») — это разные списки: первый нужен окну создания записи, второй —
  окну тумблера;
- те же точки — **правка и перенос**: перенос готовит целевую коллекцию, а правка на месте
  возвращает удаленные роли. Без этого правка задачи с удаленным «Статусом» молча теряла
  введенное значение (`UpdateTaskRecord` пишет только в найденную роль).

Покрытие — `SectionSetupPlanTests`.

### Удаление ролевого столбца и смена его типа

Роль живет флагом на поле, поэтому удаление свойства уносит и ее — **это разрешено**: ролевой
столбец такое же свойство, как остальные. Но последствия у него шире обычных, и окно
подтверждения их называет (`FieldRoleText.DeletionImpact` → `DeletePropertiesWithConfirm`):

| Удалили | Что происходит |
|---|---|
| исполнитель | вся коллекция выпадает из раздела: задача это «запись × user-поле с `IsTaskExec`» |
| «Дата» | события пропадают из календаря, у задач исчезает срок |
| «Назначил» / «Статус» | карточки остаются, поля пустые |
| «Описание» | тексты описаний удаляются вместе со столбцом (каскад `db_field_values`) |

**Смена типа — то же самое для раздела**: читать данные ему станет неоткуда. Поэтому окно свойства
спрашивает теми же словами (`ConfirmRoleLossOnTypeChange` → `FieldRoleText.TypeChangeImpact`,
план считает `RolesLostByTypeChange`), а «Сохранить» снимает флаг. Разница одна: значения столбца
**остаются на месте** — у «Описания» тексты никуда не деваются, просто раздел перестает их
показывать. Про роли, которые раздел и так не читает (нет исполнителя / нет видимой даты), окно
не спрашивает — о них молчит и плашка.

Роль **не воскресает сама** — ни вернувшийся столбец, ни возвращенный тип: молча ожившая привязка
выглядела бы поломкой. Ее вернет следующее действие раздела: создание записи или правка задачи,
и оба сначала спросят (см. выше).

Флаги переносят копирующие пути **уровня коллекции** (дубль коллекции, ATTACH- и generic-перенос
между БД) — там коллекция остается собой. Перенос **записей** с созданием недостающих свойств
(`MoveRecordsCore`, `CopyFieldValuesByName`) флаги НЕ копирует: роль — свойство коллекции, а не
значений, и приемник («Клиенты», «Архив») иначе молча оказывался в разделе задач вместе со всеми
своими записями (`TaskRoleGuardTests.Moving_task_records_does_not_enroll_target_collection_into_tasks`).
То же правило и для календарного `IsCalStart`: приехавшая дата остается обычной колонкой, пока
владелец приемника не поднимет тумблер сам. `DuplicateField` флаги тоже сбрасывает (дубль поля
не плодит задачи).

### Срок задачи

Отдельного выбора дат у задач НЕТ: срок = **первая по началу календарная дата
записи** (строка `calendar_index` поля с `IsCalStart=1`; проекция полная, поэтому
фильтр по флагу обязателен). Нет календарных дат — задача «без даты» (в конце
списка). Правка даты в календаре/таблице сразу меняет срок задачи, и наоборот.

Из этого следует побочный эффект, который стоит помнить: тумблер «Отображать в календаре» у
новых свойств снят, но роль «Дата» включение задач создает ВИДИМОЙ — иначе у задач не было бы
срока. То есть коллекция, включенная в задачи, автоматически видна и в календаре. Развести это
можно только отдельным флагом источника срока (правка схемы + все raw-SQL задач и календаря).

### Чтение

`GetTaskRecords(activeIds, limit)` / `LoadTasksAsync` — прямой raw-SQL: ведущая таблица
`db_records` (покрывающий индекс `(CollectionId, Position)`) по коллекциям с включенным
exec-полем, значение исполнителя приезжает `LEFT JOIN`'ом сиком по PK `(RecordId, FieldId)`,
«Назначил»/«Статус»/срок — коррелированные подзапросы по PK-префиксам. Семантика
`activeIds` — как у календаря: `null` = все коллекции БД, пустой набор = ни одной.

> **Пустой исполнитель задачу не убирает.** Раньше запрос шел от `db_field_values` с условием
> `Value <> ''`, и запись без проставленного исполнителя в раздел не попадала — список молчал
> ровно о тех делах, которые еще никому не роздали. Теперь задача = каждая запись коллекции с
> полем-исполнителем; пустые исполнитель и «Назначил» рисуются прочерком (`TaskCardVm.Dash`).
> Цена — крышка чтения упирается в размер коллекции, а не в число розданных дел.
Фон — на отдельном `AppDbContext` (общий контекст однопоточный). Отдельной
проекции `task_index` нет: задача = запись коллекции один-в-один (исполнитель у коллекции
один), поэтому и порядок `(CollectionId, Position, Id)`, и точный счет ложатся на уже
существующий индекс `db_records(CollectionId, Position)`. Если раздел упрется в объемы —
денормализовать по образцу `calendar_index` (та же механика Sync/Fill); понадобится это
только ради порядка «по сроку», который ни одним индексом сейчас не выражается.

#### Два режима показа

Раздел живет в двух режимах — как «Расписание» и «Журнал» календаря, и с тем же порогом.

| | раздел ≤ `TaskLoadCap` | раздел > `TaskLoadCap` |
|---|---|---|
| список | весь набор в памяти | **виртуальный**, страницами ([TaskVirtualList](../../../Views/Tasks/TaskVirtualList.cs)) |
| порядок и группировка | `TaskGrouping` в памяти | те же правила, но собраны индексными запросами |
| поиск и пять фильтров | по всему набору | те же условия, но в SQL |
| счетчики фильтра | проход по набору | запросы под крышкой ПОКАЗА («999+») |

Порог один — `TaskLoadCap` = **10 000 задач на БД** (`TasksControllerView`), тот же `MemCap`,
что у календаря. До него набор держится в памяти целиком; поведение обычных баз не меняется
вовсе.

**Недостижимых задач в разделе нет.** Свыше порога страницами показывается ЛЮБОЙ вид — и «Все
задачи», и поиск, и каждый из пяти фильтров: полоса прокрутки соответствует полному размеру
того, что вид отобрал, и дойти можно до последней задачи. Порог решает только, где считать —
в памяти или в базе; ничего не прячет ни он, ни что-либо еще.

> Крышка здесь когда-то была: сперва тысяча задач на базу, потом десять тысяч со строкой
> «+N еще» под группой. Обе прятали работу — раздел молча показывал начало и делал вид, что это
> все. Ни крышки, ни «+N еще» больше нет: показывается ровно то, что есть в базе, а
> подтягивается — по мере прокрутки, как строки таблицы конструктора.

#### Что читается при показе

Размеры коллекций читаются всегда — счет по индексам дешев. А **сплошной прочит карточек идет
ровно пока раздел помещается в память** ([TaskLoadPlan](../../../Views/Tasks/TaskLoadPlan.cs),
покрытие `TaskLoadPlanTests`): дальше он не нужен ВООБЩЕ, каким бы ни был вид, — страницами
читается и «Все задачи», и поиск, и каждый из пяти фильтров.

> Раньше эти десять тысяч строк с коррелированными подзапросами читались ВСЕГДА — и при
> открытии раздела, и после каждой правки задачи, даже когда показывать их было некому.
> На базе в полмиллиона записей это и была та самая «загрузка» на пустом месте.

Еще две вещи, которые перестали читать лишнее:

- **`SetActiveIds` сравнивает набор галочек со своим** и на совпадении не делает ничего. Сайдбар
  присылает набор и когда ничего не менял (возврат в раздел, перемонтирование базы), а на
  большой базе каждый лишний заход — это лишний счет по всем коллекциям. Исключение —
  `force: true`: главное окно ставит его, когда с последнего чтения раздела (`DataStamp`) в
  базах что-то коммитили — правка в конструкторе или календаре, запись расширения, чужая
  правка из поллера. Без этого раздел показывал старые карточки, пока человек не переключит
  галочку. Такое перечитывание идет **тихо** (список на месте, без «Загрузка…»). Механика —
  [multi-database.md](../architecture/database/multi-database.md#многопользовательский-режим-общая-база-в-сетевой-папке),
  «Свои правки».
- **Счет по коллекциям больше не ищет поле-статус подзапросом.** Раньше `CountTasksByCollection`
  искал его коррелированным подзапросом внутри агрегата, и SQLite выполнял поиск на КАЖДУЮ
  запись: на полумиллионе — полмиллиона лишних выборок по `db_fields`. Теперь связь
  «коллекция → ее статус» снимается заранее одним запросом через EF и подставляется как
  `CASE r.CollectionId …`.
- **Выполненные считаются от значений, а не от записей** (этап 8 плана drawn-grid.md). Прежнее
  соединение шло от КАЖДОЙ записи коллекции к ее статусу — 3 с на коллекции в полмиллиона при
  каждом открытии раздела. Теперь «всего» — COUNT по индексу коллекции (заодно `MIN(Id)` —
  нижняя граница прохода страниц, см. ниже), а «выполнено» — строки «Выполнено» полей-статусов
  из индекса `db_field_values(FieldId, Value)` с соединением к записи: цена — число выполненных
  задач. Размеры баз считаются параллельно — ждать приходится самую медленную базу.
- **Скрытый раздел не читает.** Пока раздел не показан (на старте открыт конструктор), подключение
  баз и чужие правки только ставят отметку «перечитать при показе» (`RefreshCurrent` → `_loadDeferred`),
  а чтение идет при первом показе — одно и уже со свежими галочками. Раньше каждая подключенная
  база запускала полное чтение раздела, и на старте с тремя базами пять таких чтений шли
  параллельно по 20 с. Устаревшая загрузка бросает работу на границе базы и замер снимает без
  записи (`Diag.Scope.Discard`).

#### Тихое обновление после действия над задачей

Создание, правка, удаление и дублирование перечитывают раздел **тихо**
(`RefreshCurrent(quiet: true)`): оверлей «Загрузка…» не показывается, список остается на экране
и возвращается на прежнее место прокрутки (`TaskListView.RestoreScroll`, отложенно через
`Dispatcher` — до отрисовки у `ScrollViewer` еще нет высоты содержимого, и смещение он обрезал бы
нулем). Выделение переживает обновление само: ключи хранит `TaskSelection`.

> Человек только что нажал «Сохранить» и смотрит на карточку. Волна «Загрузка…» на ее месте
> читается как «раздел открылся заново» — а на большой базе он еще и уезжал прокруткой в начало,
> и найти правленую задачу приходилось руками. Правило взято из «Расписания» календаря, где оно
> называется пересборкой «без свежести»: оверлей и прокрутка наверх положены только тогда, когда
> сменился САМ вид (другой день, другой поиск), а не когда изменились данные внутри него.

#### Размеры групп

Заголовок группы называет размер коллекции ПО БАЗЕ, а не число карточек на экране: в
виртуальном режиме карточек в памяти нет вовсе, а в памятном это одно и то же.

- Вид «Все задачи» берет числа из общего счета коллекций
  [`CountTasksByCollection`](../../../Database/Repositories/ConstructorRepository.Tasks.cs) —
  COUNT по индексу `db_records(CollectionId, Position)` и выполненные от индекса значений (см.
  «Что читается при показе»).
- Поиск и пять фильтров считаются `CountTaskView` — тем же условием, каким читаются страницы,
  и ТОЧНО, без крышки: по этим числам строится полоса прокрутки, и обрезанное число сделало бы
  часть задач недостижимыми. Крышка живет только в пилюле навбара.
- **Виды без условия на срок считаются вычитанием** (`TryCountUndated`, этап 8): «Все задачи»,
  стадии, «Назначено мне», «Без срока» — со скрытыми выполненными и без — в потоке «без срока»
  равны счету по ВСЕЙ коллекции от индекса значений (гистограмма статуса «стадия → сколько»,
  «без статуса» = всего − сумма, исполнитель — сик по индексу) минус точный счет потока «со
  сроком» (идет по проекции и стоит по числу датированных задач). Раньше каждый вид проходил
  все записи с подзапросами на каждую: на коллекции в полмиллиона 4,5–9 с на вид и 11–14 с на
  восемь пилюль; теперь десятки миллисекунд. Значения без записи не живут (удаление записи
  уносит их явно или каскадом); сумма гистограммы больше числа задач или отрицательная
  разность — признак обратного или устаревшего общего счета, и тогда вид считается общим
  путем. Сверка с памятью — `TaskFilterCountsTests` (без календарной даты, с двумя датами,
  пилюли).
- Счет и список читаются одним заходом на БД: разъехавшись во времени, они дали бы счет от
  одного состояния базы поверх списка от другого.
- Пустая коллекция группы не получает: «0 из 0» показывать не о чем. Так же ведет себя
  коллекция, в которой текущему виду ничего не подошло.

### Виртуальный список (раздел больше прочитанного)

[TaskVirtualList](../../../Views/Tasks/TaskVirtualList.cs) — прямой аналог «Журнала» календаря:
`IList` поверх РАЗМЕРОВ коллекций, карточки подтягиваются страницами по требованию. Полоса
прокрутки соответствует полному объему раздела, а в памяти живет лишь несколько страниц.

Упрощение против «Журнала» одно, зато крупное: там день собирается из НЕСКОЛЬКИХ баз и внутри
дня их приходится сливать по времени (посекундные карты, слитые дни — около двухсот строк
машинерии). Здесь группа = пара (база, коллекция), то есть всегда ровно один источник, и
слияние не нужно вовсе.

**Порядок.** Тот же, что в памяти (срок ↑, «без даты» в конец, тай-брейк по `Id`), но одним
запросом он не выражается, поэтому группа читается **двумя потоками встык** — ровно как
календарь склеивает фазы all-day → timed
([ConstructorRepository.TasksPaging.cs](../../../Database/Repositories/ConstructorRepository.TasksPaging.cs)):

- «со сроком» — `calendar_index` по полю-дате коллекции, `ORDER BY StartIso, RecordId`. Это в
  точности порядок индекса `(CollectionId, StartIso)`: у таблицы WITHOUT ROWID хвостом каждой
  записи индекса идет PK `(RecordId, FieldId)`, поэтому сортировать нечего, а `FieldId`
  проверяется не выходя из индекса;
- «без срока» — записи коллекции без строки в проекции, `ORDER BY Id`. В SQLite страница этого
  потока — проход таблицы в порядке Id от первой записи коллекции (`FirstRecordId`, `NOT INDEXED`):
  ORDER BY совпадает с порядком прохода, и чтение останавливается на LIMIT. Через индекс
  коллекции СУБД брала все записи, считала условие на каждой и сортировала — 3 с на странице
  коллекции в полмиллиона; теперь первая страница — миллисекунды (глубокий прыжок ползунком
  по-прежнему стоит линейно от глубины). Редкая стадия и «Назначено мне» (совпадений меньше
  восьмой части коллекции) читаются от индекса значений — ими движут совпадения, а не записи.

Границу задает `TaskCollectionStats.Dated`: строки `[0, Dated)` идут из первого потока, дальше
из второго. Страница, попавшая на стык, читается двумя запросами и склеивается.

> **Совпадение режимов — не пожелание, а тест.** `TaskPagingTests.Pages_reproduce_the_in_memory_order_exactly`
> собирает список страницами по 1, 2, 3, 4, 7 и 100 строк и сверяет с прочитанным разом и
> отсортированным `ByDueThenId`. Разойдись они — человек, чья база переросла порог, увидел бы
> другой порядок задач без единого изменения в данных.

**Своей проекции `task_index` не понадобилось.** Задача = запись коллекции один-в-один, поэтому
и размер группы, и оба потока ложатся на уже существующие индексы. Проекция нужна была бы
только ради порядка, который ни одним из них не выражается.

**Коллекция с НЕСКОЛЬКИМИ календарными полями-датами** (`TaskCollectionStats.MultiDate`): сроком
там служит наименьшая из дат, и одна запись дает несколько строк проекции. Делится она так же,
двумя потоками: «со сроком» — записи, у которых есть хоть одна календарная дата (порядок по
наименьшей дате строит СУБД, но только на этих записях), «без срока» — остальные в порядке Id,
как у всех (этап 8; прежде поток был один на всю коллекцию, и каждая страница вычисляла срок и
сортировала ВСЕ записи — 3,5–4,4 с на полумиллионе). Порядок совпадает с сортировкой в памяти
(`TaskPagingTests.A_collection_with_two_calendar_dates_still_pages_in_the_right_order`,
`Every_view_pages_like_the_in_memory_filter` — все виды на трех формах коллекции). Тогда же
исправлен «Без срока» такой коллекции: общий путь терял условие «срока нет» и считал и
показывал все задачи. Обычная коллекция задач получает ровно одно поле-дату (его заводит
включение задач), так что случай редкий.

**Устройство.** Каркас перенесен из «Журнала» один в один:

- строки нумеруются подряд по всем группам; какая строка чья — считает
  [TaskRowMap](../../../Views/Tasks/TaskRowMap.cs) (префиксные суммы + двоичный поиск). Вынесен
  отдельно, потому что это чистая арифметика: ошибка на единицу здесь не падает, а молча
  показывает заголовок вместо карточки или теряет последнюю задачу коллекции. Покрытие —
  `TaskRowMapTests`;
- страница — 200 строк, в кеше до 40 страниц (LRU), дальше вытеснение;
- страница создается **мгновенно и без единого запроса**: заголовки групп готовы сразу,
  карточки — заглушками. Данные догружаются в фоне с дебаунсом 90 мс, семафором на 4 запроса и
  поколением; при быстром перетаскивании ползунка транзитные страницы вытесняются и запроса не
  тратят;
- заглушка превращается в задачу **на месте**: `TaskCardVm.Fill` меняет значения, а карточка
  привязана к ним, а не читает при постройке. Пересобирать список не нужно, и высота заглушки
  совпадает с высотой карточки (разметка одна и та же), поэтому прокрутка не дергается;
- заглушка не выделяется, не открывается двойным кликом и в меню не участвует: записи под ней
  еще нет.

> **`ItemsControl` обязан быть ПРЯМЫМ ребенком `ScrollViewer`.** Раньше между ними стоял
> `StackPanel` (ради подписи «Нет задач»), и `VirtualizingStackPanel` получала неограниченную
> высоту — то есть материализовала все строки: виртуализация была на бумаге и отсутствовала на
> деле. Подпись переехала отдельной строкой сетки поверх списка.

**Выделение.** Ключи выделенных задач список хранит отдельно (`TaskSelection.Keys`), и карточка,
вернувшаяся из-за края кеша страниц, приезжает уже подсвеченной. Прореживания по живым задачам
(`Retain`) в этом режиме нет: полного набора у нас нет, а чистить ключи по одному кешу значило бы
терять выделение просто оттого, что человек отлистал далеко. Меню, `Delete` и диапазон
Ctrl+Shift действуют только на **реализованные** строки — за пределы кеша список не заглядывает
и обещать там ничего не может.

**Сворачивание группы** пересобирает список целиком: свернули коллекцию — сместились все
последующие строки. Карточки при этом все равно не материализуются, а страницы перечитаются по
мере показа.

**Что проверяется чем.** Правила разнесены по чистым классам именно затем, чтобы их можно было
проверить без интерфейса:

| Что | Где живет | Чем закреплено |
|---|---|---|
| где начинается группа, что стоит в строке | `TaskRowMap` | `TaskRowMapTests` |
| разбиение страницы на два потока | `TaskStreams` | `TaskStreamsTests` |
| что читать перед показом, тот же ли набор галочек | `TaskLoadPlan` | `TaskLoadPlanTests` |
| порядок страниц = порядок в памяти | SQL постраничного чтения | `TaskPagingTests` |
| счетчики: SQL = проход по памяти | `CountTasksMatching` | `TaskFilterCountsTests` |
| размеры и форма коллекции | `GetTaskCollectionStats` | `TaskPagingTests` |

> **Сборка всего этого в живом интерфейсе автоматикой НЕ проверяется**: виртуальный список
> требует запущенного Avalonia и базы больше порога. Эту дыру закрывает ручной прогон —
> [qa-checklists/tasks.md](../qa-checklists/tasks.md). У виртуальных списков календаря
> («Расписание», «Журнал») своего чеклиста нет; их стоит гонять теми же пунктами.

### Сайдбар (режим Tasks)

Тот же `SidebarTree`, что у календаря: чекбоксы коллекций фильтруют агрегатный
список (`ActiveIdsChanged`), цвета — общий `BuildColorMenu`. Отличия:

- в контекстном меню вместо «Отображение свойств даты» — **«Отображение свойств
  исполнителя»** (`BuildUserFieldsMenu`): список user-полей коллекции, чекбокс =
  `IsTaskExec` (переключение — `SetUserFieldTaskExec`, мгновенно, это read-time фильтр).
  Исполнитель один, поэтому список ведет себя как выбор носителя, а не как набор фильтров:
  «(Выделить все)» здесь нет, а пока роль занята, остальные пункты **гаснут** с подсказкой
  «снимите переключатель с текущего свойства» (у полей-дат календаря все наоборот — их может
  быть сколько угодно);
- **клик по строке коллекции = ее галочка** (`ToggleCollection`), ровно как в календаре.
  Наборы галочек у календаря и задач независимы и **переживают перезапуск** — лежат в
  app.db (`hiddenCollections.tasks` / `hiddenCollections.calendar`, см. ниже).

> Раньше клик «открывал» коллекцию (событие `CollectionOpened`): список сужался до нее
> одной, заголовок навбара менялся на имя коллекции, а галки остальных коллекций ни на
> что не влияли — увидеть задачи двух коллекций разом было нельзя. Событие и режим
> открытой коллекции убраны; заголовок навбара всегда «Задачи».

#### Галочки между запусками

`AppSettings.Load/SaveHiddenCollections(scope)` — app.db, ключи `hiddenCollections.tasks`
и `hiddenCollections.calendar`. Читается один раз при первой инициализации панели
(`RestoreChecks`), пишется на каждое переключение (`PersistChecks`, включая «отметить все»).

- Хранятся **снятые** галочки, а не отмеченные: по умолчанию видно все, поэтому пустая
  настройка = стандарт (и ключа в базе нет), а новая коллекция появляется отмеченной сама.
  Обратное хранение требовало бы дописывать каждую созданную коллекцию, и любая пропущенная
  запись прятала бы ее от человека.
- Ключ пары — `(DbId реестра, id коллекции)`: id коллекций между базами пересекаются.
- Повторная инициализация панели (монтирование базы, получение допуска) **не перечитывает**
  настройку — иначе она затирала бы то, что нащелкано в этой сессии.
- При сохранении вычищаются ключи удаленных коллекций, но только по базам, которые сейчас
  смонтированы и читаемы: у запертой список коллекций пуст, и ее галочки стерлись бы за
  компанию, а ключи отключенной базы должны дождаться ее возвращения.

#### Только подключенные коллекции

Настройки «Только коллекции с датами в календаре» (`CalendarSettings.SidebarOnlyInSection`,
ключ `calendarSidebarOnlyInSection`) и «Только коллекции с исполнителем»
(`TaskSettings.SidebarOnlyInSection`, `tasksSidebarOnlyInSection`) прячут из панели своего
раздела коллекции, которые в него ничего не дают. Стандарт у обеих — выключено. Конструктор
их не читает.

- **Кто подключен.** Календарь — коллекция с хотя бы одним полем-датой `IsCalStart`
  (`GetCalendarCollectionIds`), задачи — с полем-исполнителем `IsTaskExec`
  (`GetTaskCollectionIds`). Один запрос на базу в `BuildDbChildren`, в том же `try`, что
  группы и коллекции; результат лежит в снимке `MountedDb.InSection` (null — без отбора).
- **Что прячется.** Коллекции вне набора и группы, в поддереве которых все коллекции
  спрятаны (`BuildGroupNode` возвращает null). В календаре и задачах скрывается и корень
  читаемой допущенной базы, если в ней нет подходящих коллекций, даже когда остались пустые
  группы. Подходящая коллекция без записей остается видимой; снятая галочка не прячет базу.
  Запертые, еще подключаемые и недоступные базы сохраняют корни с допуском или статусом:
  отсутствие прочитанной структуры не означает, что подходящих коллекций нет.
- **Снимок остается полным.** `MountedDb.Collections` — все коллекции, поэтому
  `PersistChecks` не стирает галочки спрятанных. Отбор идет через `ShownCollections`:
  `GetActiveIds` отдает разделу только показанные (цель быстрого добавления по умолчанию и
  подсказка «Отметьте коллекции» совпадают с тем, что видно), «Включить все / Выключить все»
  трогает только их. При включенной настройке «Включить все» снимает ключи видимых, а не
  чистит набор целиком.
- **Строка под открытым меню.** Снятый в меню последний тумблер поля — структурный коммит,
  и главное окно перестраивает дерево через 300 мс, не дожидаясь закрытия меню. Пока меню
  коллекции открыто, `_menuPinned` держит ее в дереве вместе с корнем базы; `ContextMenu.Closed`
  снимает пин, перестраивает дерево и поднимает `ActiveIdsChanged`, если набор поменялся.
- **Смена настройки.** Панель подписана на `CalendarSettings.Changed` и
  `TaskSettings.Changed`, но перестраивается, только когда поменялось значение ее настройки
  (`_renderedOnlyInSection`), и сразу отдает разделу новый набор.
- **Новая коллекция.** Кнопка «+» при включенной настройке подключает коллекцию к разделу
  (`ConnectToSection`): календарь — `EnsureCalendarCollection` (первое поле-дата или «Дата»
  с `IsCalStart`), задачи — `EnsureTaskCollection` (полный набор ролей задачи). Нет права на
  свойства — `PermissionDeniedException` уходит в `DbErrors.Handle`, коллекция остается
  созданной и спрятанной. Импорт не подключает (новые коллекции сразу спрятаны), дубль
  наследует флаги полей источника.

Покрытие: `SectionCollectionsTests` (Integration), `CalendarSettingsTests` и
`TaskSettingsTests` (Unit), самостоятельный стенд `Tests/Sections --only sidebarfilter`
(корни баз, вложенные группы, смена настройки, закрепленное меню и статусы подключения).

### Быстрый фильтр (навбар)

Выпадающий список рядом с поиском — пункт плюс счетчик задач, ему отвечающих. Список из
**двух групп через разделительную черту**, как список типов в окне свойства: стандартные
пункты **Все задачи · Сегодня · Мне назначено · Без срока · Просрочено**, черта, и **все
стадии** — пункты поля «Статус» отмеченных коллекций всех баз
([TaskFilters](../../../Views/Tasks/TaskFilters.cs), покрытие `TaskFiltersTests`).

- **Пункт — `TaskFilter`** (вид `TaskFilterKind` + имя стадии для вида `Stage`), не enum:
  стадий у коллекций сколько угодно. У пункта есть строковый `Key` («All», «Today», …,
  «Stage:В работе») — под него настройка стартового фильтра и словари репозитория; `ParseKey`
  разбирает обратно, мусор дает null. Прежний пункт «Выполнены» стал стадией «Выполнено» и живет
  только в группе стадий.
- **Роли коллекций** — исполнитель, статус, календарные даты — размеры раздела, стадии и
  условия видов берут из одного прямого запроса к `db_fields` (`ReadTaskRoleFields`, порядок
  `RoleOrder`), а не из запросов EF: их сборка при первом открытии раздела в процессе стоила
  0,2 с на четыре базы и 0,05 с на UI-потоке.
- **Стадии** отдает `ConstructorRepository.GetTaskStages(activeIds)`: пункты поля-статуса
  (`IsTaskStatus`, тип `status`/`select`, первое по `RoleOrder` — как при чтении задач) каждой
  коллекции с исполнителем, объединенные без повторов в порядке полей; коллекция без исполнителя
  стадий не дает (`TaskStagesTests`). Контроллер снимает их в `UpdateChrome` вместе с
  коллекциями и отдает навбару `SetStages`: пересобирается **только хвост стадий и только при
  смене набора**, выбранный пункт переживает пересборку по ключу, а пропавшая стадия (убрали из
  поля, сняли галочку с коллекции) возвращает выбор на «Все задачи» с `FilterChanged`.
- **Иконки стадий** (`TaskFilter.IconKey`): «Запланировано» — `IconCircleDashed` (lucide
  circle-dashed), «В работе» — `IconPlay`, «Выполнено» — `IconCheckCheck`, остальные — `IconClock`:
  стадии заводит человек, рисовать под каждую неоткуда. Пилюли — цветов чипов карточки:
  «Выполнено» зеленая, «В работе» акцентная, «Просрочено» красная, прочие серые.
- **Черта над первой стадией** — `ComboBox.ItemContainerTheme` в NavbarTasks.axaml с
  `IsVisible="{Binding StartsGroup}"`, скопирован из `PropertyEditorDialog`: черта стоит в зазоре
  над `ContentPresenter`, поэтому hover и выбор ее не захватывают, а к свернутому боксу тема
  контейнера не применяется.
- **Стадия — точное значение статуса**; пустой статус карточка показывает как «Запланировано»,
  поэтому и стадия «Запланировано» берет его (`MatchesStage`; в SQL — `IN ('', @stage)`).
- **Правила показа — `TaskRules`** из «Настройки → Задачи» (см. [«Настройки раздела»](#настройки-раздела)):
  `ShowDone = false` прячет выполненные из всех пунктов, кроме стадии «Выполнено»;
  `OverdueNextDay` двигает момент просрочки на следующий день после срока. Правила передаются
  явно (в `Matches`, `Counts`, `TaskView` и `TaskCardVm.Rules`), а не читаются из статики: чип
  срока на карточке, фильтр и SQL считают просрочку одним `TaskFilters.IsOverdue`.
- Счетчики считаются по набору **после поиска, но до самого фильтра**: цифра рядом с
  пунктом равна тому, что покажет его выбор, а остальные пункты остаются видны.
- Пункты **не разбивают набор на части** — одна задача попадает сразу в несколько
  (моя просроченная — это и «Мне назначено», и «Просрочено»).
- Определения совпадают с чипами карточки, иначе счетчик спорил бы со списком, который сам
  же открывает: просрочка — по КОНЦУ срока и только у незакрытых задач (у выполненной
  чипа просрочки нет), «Сегодня» — сегодняшний день внутри периода задачи (многодневная,
  идущая через сегодня, тоже попадает; она же может быть и «Просрочено», если время дня
  уже прошло).
- «Мне назначено» — сравнение исполнителя с отображаемым именем текущего пользователя без
  учета регистра.
- Счетчик живет в **пилюле** у правого края строки: число по центру по обеим осям, правый
  край ряда ровный при любой цифре. `MinWidth` привязана к собственной высоте пилюли
  (`$self.Bounds.Height`), поэтому одна цифра дает квадрат, а двузначное и трехзначное число
  раздвигают блок вширь; константой это задать нельзя — высота растет вместе с размером
  шрифта из «Оформления». Заливка — та же пара «светлая подложка + насыщенный текст», что у
  чипов карточки: просрочка красная, выполненные зеленые, остальные серые цветом наведения
  (`BrushHover`) с обычным черным числом. Иконка пункта берет цвет числа.
- Стандартные пункты списка создаются **один раз** и живут все время работы панели (стадии —
  см. выше, только при смене набора и не из обработчика выбора); `SetFilterCounts`
  правит счетчик в самих пунктах (они наблюдаемые) и не трогает ни `ItemsSource`, ни выбор,
  пока тот совпадает с фильтром контроллера. Так и надо: метод зовется из `ApplyToList`,
  то есть **в ответ на выбор пункта** — подменять коллекцию под руками `ComboBox` в момент
  обработки клика нельзя. Прежняя пересборка списка ломала свернутый бокс: в раскрытом
  списке числа были верные, а бокс застревал на более раннем наборе — выбрав пустой фильтр
  и вернувшись ко «Всем задачам», человек видел там «0».
- Свернутый бокс (`SelectionBoxItem`) — снимок выбранного пункта, который `ComboBox` делает
  в момент смены выбора, и обновления самого пункта до него доходят не всегда. Поэтому
  `RefreshSelectionBox` снимает и возвращает выбор отложенно (`Dispatcher.Post`, приоритет
  `Render`) — контрол перечитывает пункт заново уже после того, как закончил с кликом.
  Мигания не видно: все происходит до отрисовки кадра.
- **Ноль пилюли не получает вовсе**, а подпись и иконка пункта гаснут до вторичного цвета:
  пустой пункт читается как «нечего смотреть» еще до того, как искать глазами счетчик.
  «0» в рамке выглядел бы значением, на которое стоит нажать.
- **Потолок показа — `TaskFilterItem.CountCap` = 999**, свыше него в пилюле стоит «999+».
  Пилюля живет в свернутом боксе рядом с поиском, и точное четырех-пятизначное число там
  только распирает строку: по нему все равно не считают, по нему решают, стоит ли заходить.
  Разделитель разрядов после этого не нужен — до потолка число всегда трехзначное. Точное
  количество никуда не девается: его полностью называет заголовок коллекции в списке,
  где для этого есть место.
- **Где считать — решает размер раздела.** Пока он прочитан целиком, счетчики считает проход
  по памяти: точно и мгновенно. Как только чтение уперлось в крышку, проход стал бы считать по
  прочитанной части и занижать, поэтому счет уходит в БД — `CountTasksMatching`, по одному
  запросу на правило, каждый вида `SELECT COUNT(*) FROM (… LIMIT 1000)`. Считать точнее потолка
  пилюли незачем, а цена такого запроса от размера базы не зависит. Числа из базы приходят
  фоном и ложатся поверх посчитанных в памяти (поколение отсекает устаревшие ответы).
  Под поиском счет остается в памяти: поиск и сам видит только прочитанное, и счетчики обязаны
  говорить о том же наборе, что список.
- **Правила SQL слово в слово повторяют `TaskFilters.Matches`**, и это закреплено тестом:
  `TaskFilterCountsTests` строит набор со всеми состояниями и сверяет все пункты — стандартные
  и стадии — при всех сочетаниях правил показа разом с проходом по памяти. `TaskView`
  репозитория несет те же флаги (`Stage`, `HideDone`, `OverdueNextDay`), а `CountTaskViews`
  принимает список видов и отдает счет по `TaskView.Key`. Одно расхождение осталось намеренным:
  «Мне назначено» в памяти сравнивает
  имена без учета регистра, а SQLite так кириллицу не сравнивает — поэтому в БД уходит список
  имен пользователей базы, совпавших с текущим без учета регистра, и сверка идет точная.
  Исполнитель, вписанный руками и отличающийся только регистром, в счет не попадет.

### Группировка списка

Список — агрегат по отмеченным коллекциям, разложенный по ним же: над каждой пачкой
карточек идет заголовок со стрелкой (та же иконка и обводка, что у групп сайдбара),
названием коллекции (одной строкой, см.
[«Название: хранение против показа»](../architecture/data-model.md)) и **индикатором
выполненного** — полоска, залитая цветом коллекции на долю закрытых задач, и подпись
«2 из 7». Голое число задач на главный вопрос к списку дел (сколько уже сделано) не
отвечало. Знаменатель — **все, что отобрал текущий вид**, а не показанная его часть: числа
приходят из базы (`TaskGroup.Exact`, см. [«Размеры групп»](#размеры-групп)), иначе заголовок
пересчитывал бы то, что и так видно на экране, — а в виртуальном режиме пересчитывать было бы
и вовсе нечего. Под фильтром и поиском знаменатель — размер отобранного, а не всей коллекции.
Нераспределенные задачи (без исполнителя) в знаменатель входят — они такая же незакрытая
работа. При нескольких смонтированных БД к названию добавляется имя базы.

**Клик по заголовку сворачивает группу** — как строка группы в сайдбаре (кликается вся
строка, не только стрелка). Свернутость живет в самом `TaskListView` (`_collapsed`,
ключ `(DbId, ColId)`): это состояние показа, база о нем не знает, и оно переживает
перезагрузку списка — иначе группы раскрывались бы сами на каждый символ поиска. Ключи
исчезнувших коллекций вычищаются в `SetGroups`, чтобы набор не рос все время работы.
Свернутая группа — не пустой список: подсказка «Нет задач» показывается только когда
групп нет вовсе.

Правило порядка живет отдельно от отрисовки — [TaskGrouping](../../../Views/Tasks/TaskGrouping.cs),
покрытие `TaskGroupingTests`:

- порядок групп повторяет сайдбар (позиция коллекции в своей БД, базы — в порядке
  монтирования): пользователь отмечает коллекции сверху вниз и ищет их в том же порядке;
- коллекция, пропавшая между загрузкой и показом, уходит в конец, а не теряется;
- внутри группы — срок ↑, «без даты» в конец, тай-брейк по `Id`;
- ключ группы — `(DbId, ColId)`: id коллекций не уникальны между базами, а по индексу
  свернутость съезжала бы при появлении/исчезновении группы;
- цвет группы — цвет коллекции по общему правилу `EventColors` (дефолтный синий =
  «без цвета» → серый), им заливается индикатор; выполненные считаются по статусу
  «Выполнено» (`TaskGroupHeaderVm.DoneCount`).

Пустой список объясняет причину: «Ничего не найдено» при активном поиске, «Отметьте
коллекции в боковой панели» — когда сняты все галки, иначе «Нет задач».

### Создание, правка, удаление

В быстром добавлении название занимает всю ширину сверху. Ниже слева — срок, исполнитель,
назначивший и коллекция; кнопка «Добавить» прижата к правому краю строки. В узком разделе
параметры переносятся целыми группами, сохраняя подпись рядом с редактором и кнопку
в пределах доступной ширины. У названия тонкая акцентная рамка, при фокусе — толстая;
клик вне поля снимает фокус без потери черновика.

- **Быстрое добавление** (форма сверху): название + Enter (или «Добавить»), срок
  (пустая дата = «без даты», пустое время = весь день; дата по умолчанию — из настройки «Срок
  в быстром добавлении», подставляется при открытии раздела и после каждого добавления),
  исполнитель (пункт «Не назначен» + допущенные пользователи БД; по умолчанию — текущий либо
  «Не назначен» по настройке; «Не назначен» уходит пустым значением, и задача заводится
  нераспределенной), назначивший (те же пользователи, по умолчанию — текущий;
  явный «Не назначен» тоже сохраняется пустым) и **коллекция-цель** отдельным списком. В списке —
  ВСЕ коллекции допущенных баз (галочки сайдбара решают, что показано, а создавать можно
  и в скрытой); при нескольких БД к названию добавляется имя базы, а смена коллекции
  перечитывает оба списка пользователей — у другой базы свой состав допущенных. Выбор переживает
  перезагрузку списка, пока коллекция жива; по умолчанию (и когда выбранная исчезла) —
  первая отмеченная, дальше авто-«Без названия».
  `AddTaskRecord` включает коллекцию в задачи при необходимости;
  «Назначил» берется из формы (старый `QuickAddRequest` без этого аргумента сохраняет
  прежнее умолчание текущего пользователя), стадия — из настройки «Стадия новой задачи», если она есть
  среди пунктов поля-статуса коллекции, иначе первый пункт (`DefaultStageFor`).
- **Двойной клик по карточке** → `TaskDialog` (формат календарного окна записи +
  Статус/Исполнитель/Назначил + чекбокс «Без даты»; список «Статус» — пункты поля-статуса
  выбранной коллекции, `GetTaskStageOptions`, перечитывается при смене коллекции; стадия
  редактируемой задачи, которой в пунктах уже нет, добавляется сырой): кандидат-`TaskRecord` персистит
  контроллер через `UpdateTaskRecord` (даты/название/описание — календарным путем
  `UpdateCalendarRecord`, он же переносит запись при смене коллекции; роли — обычные
  `SetFieldValue`). Смена БД в диалоге доступна только при создании; смена коллекции
  у задачи «без даты» отключена (перенос идет календарным путем, которому нужна дата):
  комбо гасится, выбор **возвращается** к своей коллекции и рядом появляется подсказка,
  а `TrySave` берет коллекцию задачи независимо от состояния комбо. Раньше комбо только
  гасилось: пользователь выбирал коллекцию, снимал срок — и сохранение проходило
  «успешно», ничего не перенеся (репозиторий такой выбор игнорирует осознанно,
  `TaskRoleGuardTests.Dateless_task_ignores_collection_change_and_touches_nothing_in_target`).
  Перенос **пересоздает** запись в целевой коллекции, поэтому `UpdateTaskRecord` пишет
  исполнителя не в пришедший `ExecFieldId` (он от ИСХОДНОЙ коллекции — значение осело бы
  на невидимом чужом поле, а задача исчезла бы из раздела), а в поле цели: цель включается
  в задачи через `EnsureTaskCollection`, который заодно доводит «Назначил»/«Статус»
  (`TaskRecordsTests.Moving_task_to_another_collection_carries_executor_assigner_and_status`).
  Два условия этого пути (`TaskRoleGuardTests`):
  `EnsureTaskCollection(cid, adoptExisting: false)` — в посторонней коллекции НЕЛЬЗЯ «усыновить»
  под исполнителя ее собственное user-поле («Менеджер», «Согласующий»): оно молча стало бы полем
  задач и залило раздел чужими записями, поэтому заводится свое «Исполнитель»;
  и вызывается он **до** календарного пути — тот пересоздает запись тремя `SaveChanges` без общей
  транзакции, так что отказ по правам после него оставил бы задачу перенесенной, но без ролей.
  Аудит записи перенос сохраняет (`RestoreMovedRecordAudit`, см.
  [[calendar/interactions]]): иначе задача коллеги после переезда выглядела бы созданной вами
  (`UserValueTests.Moving_event_to_another_collection_in_calendar_keeps_original_author`).
- **Удалить** — кнопка в диалоге → `DeleteCalendarRecord` (запись удаляется целиком,
  из календаря и таблицы тоже).
- Поиск и сортировка — в памяти по загруженному: срок ↑, «без даты» в конце,
  выполненные на месте (заголовок зачеркнут, чип зеленый, без чипа остатка).

### Выделение, контекстное меню, массовые операции

Жесты — те же, что в «Расписании» и «Журнале» календаря, и собраны в общем
[`EventContextMenu`](../../../Controls/Components/EventContextMenu.cs):

- клик выделяет карточку (серая заливка + акцентная рамка), Shift+клик добавляет/снимает,
  Ctrl+Shift+клик берет диапазон от последней выделенной;
- клик мимо карточек снимает выделение, **правый** — нет: иначе меню открывалось бы над
  снятым выделением;
- правый клик по карточке → «Изменить» / «Дублировать» / «Удалить»; выделено несколько и
  клик пришелся по выделенной — меню множественного выбора («Дублировать» / «Удалить»);
- `Delete` (и `Backspace`) удаляет выделенное; клавиша игнорируется, когда фокус в поле
  ввода или в списке (`TextBox`/`AutoCompleteBox`/`ComboBox`) и когда раздел скрыт.

Выделение живет в [`TaskSelection`](../../../Views/Tasks/TaskSelection.cs) — множество ключей
`(DbId, RecordId, ExecFieldId)`, а не индексов строк: список перечитывается на каждый символ
поиска и после любой правки, и выделение обязано это пережить. `Retain` на каждой загрузке
выбрасывает ключи, ушедшие из набора, — «Удалить» действует только на видимое. Диапазон
считается по **плоскому** порядку показанных карточек, поэтому свободно пересекает границы
групп. Поле-исполнитель осталось в ключе, хотя карточка у записи теперь одна (исполнитель у
коллекции один): ключ переживает смену носителя роли, а старые базы до починки при монтировании
могут отдать и две карточки на запись.

Обе массовые операции спрашивают подтверждение с количеством («Вы удаляете 3 задачи…»,
счет — по **записям**, а не по карточкам) и идут по тем же двум путям, что в календаре:
до `SmallOpCap` = 100 записей — сразу на общем контексте (`DeleteCalendarRecord` /
`DuplicateRecord`), больше — bulk-SQL на изолированных подключениях в фоне
(`DeleteRecordsIsolated` / `DuplicateRecordsIsolated`) под оверлеем загрузки. Окна процентов
здесь нет: объем ограничен `TaskLoadCap` = 10 000 задач на БД. Перед удалением проверяются
входящие связи (`RelationDeleteImpact.ForRecords`, по каждой базе отдельно) — предупреждение
дописывается в текст подтверждения. Отказ по правам или занятая база → тост `DbErrors`,
прочие отказы репозитория → баннер списка; на первой неудаче цикл останавливается, а список
перечитывается и показывает фактическое состояние.

### Настройки раздела

«Настройки → Задачи» ([SettingsTasksPanel.cs](../../../Views/Settings/SettingsTasksPanel.cs),
ключи — [settings.md](settings.md#разделы)). Живой сервис
[TaskSettings](../../../Utils/TaskSettings.cs) по образцу `CalendarSettings`: кэш значений из
app.db, `Set*` сохраняют дельту и поднимают `Changed`, `Stamp` — для догоняющей перерисовки.
Сервис отдает примитивы; `TaskRules` и `TaskFilter` из них собирает контроллер — Utils не тянет
за собой Views. Контроллер подписан на `Changed`, пока раздел в визуальном дереве: правила
показа перечитывают список и счетчики (тихо), умолчания строки добавления переставляют ее поля.

| Настройка | Что делает | Где действует |
|---|---|---|
| Момент просрочки (`OverdueNextDay`) | «с момента срока» (стандарт) или «со следующего дня» | `TaskFilters.IsOverdue`: фильтр «Просрочено», чип карточки, SQL (`substr(end,1,10) < @today`) |
| Показывать выполненные (`ShowDone`) | выключено — выполненные только в стадии «Выполнено» | `Matches`, `TaskView.HideDone`; счет заголовка коллекции не меняется |
| Фильтр при открытии (`StartFilterKey`) | стандартный пункт или «последний выбранный» (`Last`, ключ хранится в `tasksLastFilter` без события) | `Initialize`: стандартный ставится сразу, стадия — одной попыткой, когда стадии впервые известны (`UpdateChrome`) |
| Стадия новой задачи (`DefaultStage`) | список — три стандартные + стадии всех допущенных баз (провайдер `taskStages` из `MainWindow`) | `QuickAdd` → `DefaultStageFor`, `TaskDialog(presetStage)` |
| Исполнитель в быстром добавлении (`QuickExecutorMe`) | я или «Не назначен» | `TaskListView.SetUserOptions` / `ApplyQuickDefaults` |
| Срок в быстром добавлении (`QuickDue`) | без срока / сегодня / завтра | `TaskListView`: при построении, после добавления, при смене настройки |

Строки «Отображение по умолчанию» и «Отображаемые виды» переехали сюда из «Оформления» без
переименования ключей (`tasksView`, `hiddenViews.tasks`); механизм `InitAppearance` общий.
Тумблеры уведомлений по задачам остаются в «Общее». Покрытие — `TaskSettingsTests`.

## Взаимодействия

- **Календарь**: общие даты (`calendar_index`) — задача со сроком видна в календаре
  и наоборот; правки синхронны, потому что хранилище одно.
- **Конструктор**: авто-поля появляются в таблице сразу (обычные `db_fields`);
  `CollectionsMayHaveChanged` из модуля задач обновляет сайдбары и открытую таблицу.
- **Обратное направление — через шину своих изменений** (`ChangeBus`): правка ячейки или
  панели записи в конструкторе, перенос события в календаре, запись расширения — все это
  коммиты, по которым главное окно перечитывает видимый раздел задач на лету (тихо, список
  на месте), а скрытый — при возврате в него, если его `DataStamp` старше последнего коммита.

- **Расширения**: пишут через тот же `AppDbContext`, поэтому их записи доходят до раздела
  тем же путем, без кода на стороне расширения.
- **Права**: пункты меню гейтятся `PermissionService.Can`; мутаторы репозитория
  зовут `Demand` (включение задач требует `EditField`, авто-создание полей —
  `CreateField`; проверка идет ДО записи флага). Ошибки прав показываются баннером.
  **Пометка существующего поля ролью и правка его опций — изменение схемы коллекции**,
  поэтому права спрашивает сам `EnsureTaskSupportFields`, а не вызывающие: путей два
  (тумблер в сайдбаре и «между делом» из `AddTaskRecord`, где проверен только
  `CreateRecord`), и через второй пользователь без прав на свойства молча размечал чужие
  поля и переписывал опции своего списка «Статус»
  (`TaskRecordsTests.Task_support_fields_marking_requires_field_rights_and_is_journalled`).
  Дыра того же класса закрыта в `GetOrCreateDefaultCollection`: задача/событие «без коллекции»
  заводили «Без названия» в обход прав — теперь ветка создания требует `CreateCollection`
  (существующая коллекция прав на схему не требует,
  `TaskRoleGuardTests.Auto_collection_is_not_created_without_the_collection_right`).
- **Уведомления** ([[notifications]]): правка свойств-ролей кладет строку в очередь
  `task_events` той же базы — исполнителю о назначении (кроме случая «назначил сам себе»),
  назначившему о смене стадии (в том числе когда стадию сменил он сам). Пишет `SetFieldValue`,
  поэтому уведомления дают ВСЕ поверхности правки (раздел, таблица, страница записи, календарь)
  и НЕ дают массовые пути (импорт, дубль, перенос) — они пишут значения мимо нее. Клик по
  баннеру открывает карточку задачи (`TasksControllerView.OpenTaskAsync` → `OpenEditDialog`).
- **Мультибаза**: раздел видит только допущенные БД (`MainWindow.GrantedDbs()`),
  агрегат собирается по всем, каждая задача несет `DbId`.
- **Пользователи**: значения «Исполнитель»/«Назначил» — строки-имена (снапшот, как
  тип `user`): удаленный/переименованный пользователь остается исторической строкой,
  диалог добавляет ее в опции сырой. Фильтров «мои задачи» в v1 нет — сравнение по
  строке имени было бы ненадежным.
