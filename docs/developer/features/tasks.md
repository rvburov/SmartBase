# Задачи — общий обзор

## Назначение

Раздел «Задачи» показывает записи конструктора списком карточек-задач: название,
исполнитель, кто назначил, срок, статус (**Запланировано / В работе / Выполнено**)
и чип остатка («Осталось N дн./ч», «Сегодня», «Просрочено на N дн.»). Карточки
сгруппированы по коллекциям — заголовок коллекции над её задачами, кликом он
сворачивается; какие коллекции показывать, решают галочки в сайдбаре. Это полный аналог календаря, где источник
события — поле-дата с флагом `IsCalStart`: здесь источник задачи — **user-поле с
флагом `IsTaskExec`** («исполнитель»). Записи-задачи
остаются обычными записями своих коллекций — в таблице конструктора видны те же
«Исполнитель», «Назначил», «Статус», дата и описание.

## Как работает

### Модель: задача = (RecordId, exec-FieldId)

Задача — не отдельная сущность, а проекция записи через включённое user-поле.
У `db_fields` три флага (миграция `AddTaskFieldFlags`):

- `IsTaskExec` — user-поле «исполнитель»: каждая запись с непустым значением такого
  поля видна в разделе задач (значение = исполнитель). Несколько exec-полей коллекции
  могут быть включены одновременно — запись даст задачу на каждое (как несколько
  видимых полей-дат в календаре);
- `IsTaskAssigner` — поле «Назначил» (user);
- `IsTaskStatus` — поле «Статус» (тип свойства `status` с опциями Запланировано/В работе/Выполнено
  в `ConfigJson`; см. [data-model.md](../architecture/data-model.md#status--статус)).

Имя роли сравнивается **без учёта регистра** (как занятые имена в `FreeFieldName`): SQL-сравнение
строк регистрозависимо, а `lower()` в SQLite кириллицу не трогает — поэтому поля коллекции для
разметки ролей читаются в память.

**Одно поле — одна роль.** Два значения в одном `FieldId` затирали бы друг друга, поэтому чужую
роль под исполнителя не берут ни тумблер сайдбара (`SetUserFieldTaskExec` отказывает с
сообщением), ни авто-усыновление в `EnsureTaskCollection`. «Назначил» отсекается И по флагу,
И по имени (у поля, заведённого руками до включения задач, флага ещё нет, а авто-разметка найдёт
его ПО ИМЕНИ и добавит вторую роль); «Статус» на user-поле — только по флагу: по имени его
усыновляют лишь среди `select`/`status`-полей, а флаг у user-поля бывает от ручной пометки или
копирования (`TaskRoleGuardTests`, `TaskRecordsTests.Field_named_assigner_never_becomes_the_executor_field`).

**Старые базы лечатся при монтировании**: `RepairDoubleRoleTaskFields` (зовёт `DatabaseManager`)
снимает чужую роль с exec-поля и заводит «Назначил»/«Статус» заново — запрет сам по себе такие
базы не чинил (`EnsureTaskCollection` находил exec по флагу и уходил в ранний возврат). Обычная
база платит один индексный запрос; у пользователя без прав на схему починка просто не происходит,
её сделает следующий с правами. Затёртых исполнителей не вернуть — их перезаписали значения
второй роли (`TaskRoleGuardTests.Mounting_heals_a_field_that_carries_both_roles`).

**Порядок выбора роли — `(Position, Id)`** (`RoleOrder`). Флаг может оказаться сразу у двух полей
(копирование, ручная правка, старая база), и без явного порядка `FirstOrDefault`/`LIMIT 1`
отдавали произвольную строку: запись значения и его чтение расходились по разным полям, раздел
показывал то одно, то другое. Правило одно на весь модуль — его же повторяет `ORDER BY` в
коррелированных подзапросах `GetTaskRecords`.

### Полный набор ролей и подтягивание по имени

Включение задач (`SetUserFieldTaskExec`, `EnsureTaskCollection`) и создание задачи
(`AddTaskRecord`) доводят коллекцию до **полного набора ролей**: «Назначил», «Статус»,
«Дата» (срок) и «Описание» — исполнитель это само поле с тумблером. Поле-дата появляется
даже у задачи БЕЗ срока: дату вписывают позже, и колонка для неё должна быть.

Общий механизм — [`EnsureRoles`/`PlanRoles`](../../../Database/Repositories/ConstructorRepository.Roles.cs):

- **кандидат** — столбец, который так и называется («Назначил», «Статус», «Дата», «Описание»),
  регистр не важен, **тип роли не мешает**: единственное исключение — «Дата», где
  `calendar_index` строится только по полям типа «Дата», поэтому текстовый столбец с таким
  именем сроком стать не может и роль уходит новому полю;
- поле, уже несущее ДРУГУЮ роль (в т.ч. исполнителя), кандидатом не будет — две роли на одном
  `FieldId` затирают друг друга (см. `FixDualRoleFields`);
- UI сначала **спрашивает** (`PlanRoles` → `ConfirmDialog` в `PropertyEditorDialog`): показывает
  найденные столбцы и то, какие поля появятся при отказе. «Подтвердить» → столбцы получают роли
  и их данные едут в раздел; «Отменить» (`adoptByName: false`) → столбцы не трогаем, роли
  достаются новым полям с суффиксом « 2»;
- проверка идёт при КАЖДОМ включении тумблера, а не только при первом: пользователь мог
  переименовать столбцы и захотеть переключить раздел на другой. Эксклюзивная роль
  («Назначил»/«Статус»/«Описание») при подтверждении **переезжает** — у прежнего носителя
  флаг снимается; «Дата» не эксклюзивна (несколько дат = несколько событий), там флаг просто
  добавляется.

Размеченный столбец не выглядит обычным: в окне свойства у него красная плашка «привязано к
разделу «Задачи» — статус задачи» ([ui/dialogs](../ui/dialogs.md#плашка-привязано-к-разделу)).
Она читается из флагов, поэтому пропадает вместе с ролью — снятый тумблер, переезд роли на
другой столбец, удаление свойства.

Разметка идёт **одной транзакцией**: раздельные `SaveChanges` при сбое не по правам (гонка,
`DbUpdateException`) оставляли коллекцию с одной ролью из двух, а следующий вызов считал набор
уже полным. Права спрашиваются до первой записи: пометка чужого поля — `EditField`, создание
недостающего — `CreateField`. Покрытие — `RoleAdoptionTests`.

### Создание задачи тоже спрашивает

Раньше набор полей молча доводило и **создание записи**: окно задачи закрывалось, а в чужой
коллекции появлялось пять новых столбцов — узнать об этом можно было, только вернувшись в
конструктор. Теперь UI считает план заранее — `PlanTaskSetup` (задачи) и `PlanCalendarSetup`
(события) — и показывает [окно подготовки](../ui/dialogs.md#подготовка-коллекции-к-разделу):
что будет создано, какие существующие столбцы станут полями раздела. **«Отмена» — запись не
создаётся**, коллекция остаётся нетронутой.

- окно показывается **только если коллекция реально изменится** (`ChangesCollection`): набор
  размечен — запись создаётся молча, иначе окно всплывало бы на каждое событие;
- план обязан совпадать с тем, что сделает запись, поэтому `PlanTaskSetup` повторяет правило
  `EnsureTaskCollection` для исполнителя: свободное user-поле («Менеджер») **станет** им, и окно
  об этом говорит; `adoptExec: false` — правило переноса задачи в постороннюю коллекцию, там
  заводится собственное «Исполнитель»;
- `FieldsToCreateIfAdopted` (создаётся при согласии) и `FieldsToCreateIfDeclined` (при отказе от
  подтягивания, с суффиксом « 2») — это разные списки: первый нужен окну создания записи, второй —
  окну тумблера;
- те же точки — **правка и перенос**: перенос готовит целевую коллекцию, а правка на месте
  возвращает удалённые роли. Без этого правка задачи с удалённым «Статусом» молча теряла
  введённое значение (`UpdateTaskRecord` пишет только в найденную роль).

Покрытие — `SectionSetupPlanTests`.

### Удаление ролевого столбца

Роль живёт флагом на поле, поэтому удаление свойства уносит и её — **это разрешено**: ролевой
столбец такое же свойство, как остальные. Но последствия у него шире обычных, и окно
подтверждения их называет (`FieldRoleText.DeletionImpact` → `DeletePropertiesWithConfirm`):

| Удалили | Что происходит |
|---|---|
| исполнитель | вся коллекция выпадает из раздела: задача это «запись × user-поле с `IsTaskExec`» |
| «Дата» | события пропадают из календаря, у задач исчезает срок |
| «Назначил» / «Статус» | карточки остаются, поля пустые |
| «Описание» | тексты описаний удаляются вместе со столбцом (каскад `db_field_values`) |

Роль **не воскресает сама** — молча вернувшийся столбец выглядел бы поломкой. Её вернёт
следующее действие раздела: создание записи или правка задачи, и оба сначала спросят (см. выше).

Флаги переносят копирующие пути **уровня коллекции** (дубль коллекции, ATTACH- и generic-перенос
между БД) — там коллекция остаётся собой. Перенос **записей** с созданием недостающих свойств
(`MoveRecordsCore`, `CopyFieldValuesByName`) флаги НЕ копирует: роль — свойство коллекции, а не
значений, и приёмник («Клиенты», «Архив») иначе молча оказывался в разделе задач вместе со всеми
своими записями (`TaskRoleGuardTests.Moving_task_records_does_not_enroll_target_collection_into_tasks`).
`DuplicateField` флаги тоже сбрасывает (дубль поля не плодит задачи).

### Срок задачи

Отдельного выбора дат у задач НЕТ: срок = **первая по началу календарная дата
записи** (строка `calendar_index` поля с `IsCalStart=1`; проекция полная, поэтому
фильтр по флагу обязателен). Нет календарных дат — задача «без даты» (в конце
списка). Правка даты в календаре/таблице сразу меняет срок задачи, и наоборот.

### Чтение

`GetTaskRecords(activeIds, limit)` / `LoadTasksAsync` — прямой raw-SQL по
`db_field_values` (индекс `(FieldId, Value)`): JOIN на exec-поля + записи + коллекции,
«Назначил»/«Статус»/срок — коррелированные подзапросы по PK-префиксам. Семантика
`activeIds` — как у календаря: `null` = все коллекции БД, пустой набор = ни одной.
Фон — на отдельном `AppDbContext` (общий контекст однопоточный). Отдельной
проекции `task_index` в v1 нет: exec-полей мало, объёмы задач невелики; если агрегат
на больших базах станет медленным (LIMIT 1000 на БД + оверлей «Загрузка…» при
>400 мс) — денормализовать по образцу `calendar_index` (та же механика Sync/Fill).

### Сайдбар (режим Tasks)

Тот же `SidebarTree`, что у календаря: чекбоксы коллекций фильтруют агрегатный
список (`ActiveIdsChanged`), цвета — общий `BuildColorMenu`. Отличия:

- в контекстном меню вместо «Отображение свойств даты» — **«Отображение свойств
  исполнителя»** (`BuildUserFieldsMenu`): чеклист user-полей коллекции, чекбокс =
  `IsTaskExec` (переключение — `SetUserFieldTaskExec`, мгновенно, это read-time фильтр);
- **клик по строке коллекции = её галочка** (`ToggleCollection`), ровно как в календаре.
  Наборы галочек у календаря и задач независимы и **переживают перезапуск** — лежат в
  app.db (`hiddenCollections.tasks` / `hiddenCollections.calendar`, см. ниже).

> Раньше клик «открывал» коллекцию (событие `CollectionOpened`): список сужался до неё
> одной, заголовок навбара менялся на имя коллекции, а галки остальных коллекций ни на
> что не влияли — увидеть задачи двух коллекций разом было нельзя. Событие и режим
> открытой коллекции убраны; заголовок навбара всегда «Задачи».

#### Галочки между запусками

`AppSettings.Load/SaveHiddenCollections(scope)` — app.db, ключи `hiddenCollections.tasks`
и `hiddenCollections.calendar`. Читается один раз при первой инициализации панели
(`RestoreChecks`), пишется на каждое переключение (`PersistChecks`, включая «отметить всё»).

- Хранятся **снятые** галочки, а не отмеченные: по умолчанию видно всё, поэтому пустая
  настройка = стандарт (и ключа в базе нет), а новая коллекция появляется отмеченной сама.
  Обратное хранение требовало бы дописывать каждую созданную коллекцию, и любая пропущенная
  запись прятала бы её от человека.
- Ключ пары — `(DbId реестра, id коллекции)`: id коллекций между базами пересекаются.
- Повторная инициализация панели (монтирование базы, получение допуска) **не перечитывает**
  настройку — иначе она затирала бы то, что нащёлкано в этой сессии.
- При сохранении вычищаются ключи удалённых коллекций, но только по базам, которые сейчас
  смонтированы и читаемы: у запертой список коллекций пуст, и её галочки стёрлись бы за
  компанию, а ключи отключённой базы должны дождаться её возвращения.

### Быстрый фильтр (навбар)

Выпадающий список рядом с поиском — пункт плюс счётчик задач, ему отвечающих:
**Все задачи · Сегодня · Мне назначено · Без срока · Просрочено · Выполнены**
([TaskFilters](../../../Views/Tasks/TaskFilters.cs), покрытие `TaskFiltersTests`).

- Счётчики считаются по набору **после поиска, но до самого фильтра**: цифра рядом с
  пунктом равна тому, что покажет его выбор, а остальные пункты остаются видны.
- Пункты **не разбивают набор на части** — одна задача попадает сразу в несколько
  (моя просроченная — это и «Мне назначено», и «Просрочено»).
- Определения совпадают с чипами карточки, иначе счётчик спорил бы со списком, который сам
  же открывает: просрочка — по КОНЦУ срока и только у незакрытых задач (у выполненной
  чипа просрочки нет), «Сегодня» — сегодняшний день внутри периода задачи (многодневная,
  идущая через сегодня, тоже попадает; она же может быть и «Просрочено», если время дня
  уже прошло).
- «Мне назначено» — сравнение исполнителя с отображаемым именем текущего пользователя без
  учёта регистра.
- Счётчик живёт в **пилюле** у правого края строки: число по центру по обеим осям, правый
  край ряда ровный при любой цифре. `MinWidth` привязана к собственной высоте пилюли
  (`$self.Bounds.Height`), поэтому одна цифра даёт квадрат, а двузначное и трёхзначное число
  раздвигают блок вширь; константой это задать нельзя — высота растёт вместе с размером
  шрифта из «Оформления». Заливка — та же пара «светлая подложка + насыщенный текст», что у
  чипов карточки: просрочка красная, выполненные зелёные, остальные серые цветом наведения
  (`BrushHover`) с обычным чёрным числом. Иконка пункта берёт цвет числа.
- Пункты списка создаются **один раз** и живут всё время работы панели; `SetFilterCounts`
  правит счётчик в самих пунктах (они наблюдаемые) и не трогает ни `ItemsSource`, ни выбор,
  пока тот совпадает с фильтром контроллера. Так и надо: метод зовётся из `ApplyToList`,
  то есть **в ответ на выбор пункта** — подменять коллекцию под руками `ComboBox` в момент
  обработки клика нельзя. Прежняя пересборка списка ломала свёрнутый бокс: в раскрытом
  списке числа были верные, а бокс застревал на более раннем наборе — выбрав пустой фильтр
  и вернувшись ко «Всем задачам», человек видел там «0».
- Свёрнутый бокс (`SelectionBoxItem`) — снимок выбранного пункта, который `ComboBox` делает
  в момент смены выбора, и обновления самого пункта до него доходят не всегда. Поэтому
  `RefreshSelectionBox` снимает и возвращает выбор отложенно (`Dispatcher.Post`, приоритет
  `Render`) — контрол перечитывает пункт заново уже после того, как закончил с кликом.
  Мигания не видно: всё происходит до отрисовки кадра.
- **Ноль пилюли не получает вовсе**, а подпись и иконка пункта гаснут до вторичного цвета:
  пустой пункт читается как «нечего смотреть» ещё до того, как искать глазами счётчик.
  «0» в рамке выглядел бы значением, на которое стоит нажать.

### Группировка списка

Список — агрегат по отмеченным коллекциям, разложенный по ним же: над каждой пачкой
карточек идёт заголовок со стрелкой (та же иконка и обводка, что у групп сайдбара),
названием коллекции (одной строкой, см.
[«Название: хранение против показа»](../architecture/data-model.md)) и **индикатором
выполненного** — полоска, залитая цветом коллекции на долю закрытых задач, и подпись
«2 из 7». Голое число задач на главный вопрос к списку дел (сколько уже сделано) не
отвечало. При нескольких смонтированных БД к названию добавляется имя базы.

**Клик по заголовку сворачивает группу** — как строка группы в сайдбаре (кликается вся
строка, не только стрелка). Свёрнутость живёт в самом `TaskListView` (`_collapsed`,
ключ `(DbId, ColId)`): это состояние показа, база о нём не знает, и оно переживает
перезагрузку списка — иначе группы раскрывались бы сами на каждый символ поиска. Ключи
исчезнувших коллекций вычищаются в `SetGroups`, чтобы набор не рос всё время работы.
Свёрнутая группа — не пустой список: подсказка «Нет задач» показывается только когда
групп нет вовсе.

Правило порядка живёт отдельно от отрисовки — [TaskGrouping](../../../Views/Tasks/TaskGrouping.cs),
покрытие `TaskGroupingTests`:

- порядок групп повторяет сайдбар (позиция коллекции в своей БД, базы — в порядке
  монтирования): пользователь отмечает коллекции сверху вниз и ищет их в том же порядке;
- коллекция, пропавшая между загрузкой и показом, уходит в конец, а не теряется;
- внутри группы — срок ↑, «без даты» в конец, тай-брейк по `Id`;
- ключ группы — `(DbId, ColId)`: id коллекций не уникальны между базами, а по индексу
  свёрнутость съезжала бы при появлении/исчезновении группы;
- цвет группы — цвет коллекции по общему правилу `EventColors` (дефолтный синий =
  «без цвета» → серый), им заливается индикатор; выполненные считаются по статусу
  «Выполнено» (`TaskGroupHeaderVm.DoneCount`).

Пустой список объясняет причину: «Ничего не найдено» при активном поиске, «Отметьте
коллекции в боковой панели» — когда сняты все галки, иначе «Нет задач».

### Создание, правка, удаление

- **Быстрое добавление** (строка сверху): название + Enter (или «Добавить»), срок
  (пустая дата = «без даты», пустое время = весь день), исполнитель (допущенные
  пользователи БД, дефолт — текущий) и **коллекция-цель** отдельным списком. В списке —
  ВСЕ коллекции допущенных баз (галочки сайдбара решают, что показано, а создавать можно
  и в скрытой); при нескольких БД к названию добавляется имя базы, а смена коллекции
  перечитывает список исполнителей — у другой базы свои пользователи. Выбор переживает
  перезагрузку списка, пока коллекция жива; по умолчанию (и когда выбранная исчезла) —
  первая отмеченная, дальше авто-«Без названия».
  `AddTaskRecord` включает коллекцию в задачи при необходимости;
  «Назначил» = текущий пользователь, статус — «Запланировано».
- **Двойной клик по карточке** → `TaskDialog` (формат календарного окна записи +
  Статус/Исполнитель/Назначил + чекбокс «Без даты»): кандидат-`TaskRecord` персистит
  контроллер через `UpdateTaskRecord` (даты/название/описание — календарным путём
  `UpdateCalendarRecord`, он же переносит запись при смене коллекции; роли — обычные
  `SetFieldValue`). Смена БД в диалоге доступна только при создании; смена коллекции
  у задачи «без даты» отключена (перенос идёт календарным путём, которому нужна дата):
  комбо гасится, выбор **возвращается** к своей коллекции и рядом появляется подсказка,
  а `TrySave` берёт коллекцию задачи независимо от состояния комбо. Раньше комбо только
  гасилось: пользователь выбирал коллекцию, снимал срок — и сохранение проходило
  «успешно», ничего не перенеся (репозиторий такой выбор игнорирует осознанно,
  `TaskRoleGuardTests.Dateless_task_ignores_collection_change_and_touches_nothing_in_target`).
  Перенос **пересоздаёт** запись в целевой коллекции, поэтому `UpdateTaskRecord` пишет
  исполнителя не в пришедший `ExecFieldId` (он от ИСХОДНОЙ коллекции — значение осело бы
  на невидимом чужом поле, а задача исчезла бы из раздела), а в поле цели: цель включается
  в задачи через `EnsureTaskCollection`, который заодно доводит «Назначил»/«Статус»
  (`TaskRecordsTests.Moving_task_to_another_collection_carries_executor_assigner_and_status`).
  Два условия этого пути (`TaskRoleGuardTests`):
  `EnsureTaskCollection(cid, adoptExisting: false)` — в посторонней коллекции НЕЛЬЗЯ «усыновить»
  под исполнителя её собственное user-поле («Менеджер», «Согласующий»): оно молча стало бы полем
  задач и залило раздел чужими записями, поэтому заводится своё «Исполнитель»;
  и вызывается он **до** календарного пути — тот пересоздаёт запись тремя `SaveChanges` без общей
  транзакции, так что отказ по правам после него оставил бы задачу перенесённой, но без ролей.
  Аудит записи перенос сохраняет (`RestoreMovedRecordAudit`, см.
  [[calendar/interactions]]): иначе задача коллеги после переезда выглядела бы созданной вами
  (`UserValueTests.Moving_event_to_another_collection_in_calendar_keeps_original_author`).
- **Удалить** — кнопка в диалоге → `DeleteCalendarRecord` (запись удаляется целиком,
  из календаря и таблицы тоже).
- Поиск и сортировка — в памяти по загруженному: срок ↑, «без даты» в конце,
  выполненные на месте (заголовок зачёркнут, чип зелёный, без чипа остатка).

### Выделение, контекстное меню, массовые операции

Жесты — те же, что в «Расписании» и «Журнале» календаря, и собраны в общем
[`EventContextMenu`](../../../Controls/Components/EventContextMenu.cs):

- клик выделяет карточку (серая заливка + акцентная рамка), Shift+клик добавляет/снимает,
  Ctrl+Shift+клик берёт диапазон от последней выделенной;
- клик мимо карточек снимает выделение, **правый** — нет: иначе меню открывалось бы над
  снятым выделением;
- правый клик по карточке → «Изменить» / «Дублировать» / «Удалить»; выделено несколько и
  клик пришёлся по выделенной — меню множественного выбора («Дублировать» / «Удалить»);
- `Delete` (и `Backspace`) удаляет выделенное; клавиша игнорируется, когда фокус в поле
  ввода или в списке (`TextBox`/`AutoCompleteBox`/`ComboBox`) и когда раздел скрыт.

Выделение живёт в [`TaskSelection`](../../../Views/Tasks/TaskSelection.cs) — множество ключей
`(DbId, RecordId, ExecFieldId)`, а не индексов строк: список перечитывается на каждый символ
поиска и после любой правки, и выделение обязано это пережить. `Retain` на каждой загрузке
выбрасывает ключи, ушедшие из набора, — «Удалить» действует только на видимое. Диапазон
считается по **плоскому** порядку показанных карточек, поэтому свободно пересекает границы
групп. Ключ включает поле-исполнитель: запись с двумя такими полями даёт две карточки, и
выделяются они порознь (но операция всё равно одна — над записью).

Обе массовые операции спрашивают подтверждение с количеством («Вы удаляете 3 задачи…»,
счёт — по **записям**, а не по карточкам) и идут по тем же двум путям, что в календаре:
до `SmallOpCap` = 100 записей — сразу на общем контексте (`DeleteCalendarRecord` /
`DuplicateRecord`), больше — bulk-SQL на изолированных подключениях в фоне
(`DeleteRecordsIsolated` / `DuplicateRecordsIsolated`) под оверлеем загрузки. Окна процентов
здесь нет: объём ограничен `TaskLimit` = 1000 задач на БД. Перед удалением проверяются
входящие связи (`RelationDeleteImpact.ForRecords`, по каждой базе отдельно) — предупреждение
дописывается в текст подтверждения. Отказ по правам или занятая база → тост `DbErrors`,
прочие отказы репозитория → баннер списка; на первой неудаче цикл останавливается, а список
перечитывается и показывает фактическое состояние.

## Взаимодействия

- **Календарь**: общие даты (`calendar_index`) — задача со сроком видна в календаре
  и наоборот; правки синхронны, потому что хранилище одно.
- **Конструктор**: авто-поля появляются в таблице сразу (обычные `db_fields`);
  `CollectionsMayHaveChanged` из модуля задач обновляет сайдбары и открытую таблицу.
- **Права**: пункты меню гейтятся `PermissionService.Can`; мутаторы репозитория
  зовут `Demand` (включение задач требует `EditField`, авто-создание полей —
  `CreateField`; проверка идёт ДО записи флага). Ошибки прав показываются баннером.
  **Пометка существующего поля ролью и правка его опций — изменение схемы коллекции**,
  поэтому права спрашивает сам `EnsureTaskSupportFields`, а не вызывающие: путей два
  (тумблер в сайдбаре и «между делом» из `AddTaskRecord`, где проверен только
  `CreateRecord`), и через второй пользователь без прав на свойства молча размечал чужие
  поля и переписывал опции своего списка «Статус»
  (`TaskRecordsTests.Task_support_fields_marking_requires_field_rights_and_is_journalled`).
  Дыра того же класса закрыта в `GetOrCreateDefaultCollection`: задача/событие «без коллекции»
  заводили «Без названия» в обход прав — теперь ветка создания требует `CreateCollection`
  (существующая коллекция прав на схему не требует,
  `TaskRoleGuardTests.Auto_collection_is_not_created_without_the_collection_right`).
- **Мультибаза**: раздел видит только допущенные БД (`MainWindow.GrantedDbs()`),
  агрегат собирается по всем, каждая задача несёт `DbId`.
- **Пользователи**: значения «Исполнитель»/«Назначил» — строки-имена (снапшот, как
  тип `user`): удалённый/переименованный пользователь остаётся исторической строкой,
  диалог добавляет её в опции сырой. Фильтров «мои задачи» в v1 нет — сравнение по
  строке имени было бы ненадёжным.
