# Папка-приемник: протокол обмена файлами

## Назначение

Способ передать данные в программу, у которого **нет двери**: чужая программа кладет файл в общую
папку, а программа раз в полминуты туда заглядывает. Ни портов, ни прав администратора, ни
согласований с ИТ — общий диск уже есть.

Уникальное свойство, ради которого канал и существует: **он асинхронный**. Файл дождется, пока
приемник включат. При выключаемом на ночь сервере это не мелочь, а главное отличие от любого
варианта с сокетом.

Этот файл — **контракт для отправителя**. Его читает разработчик чужой программы: 1С, скрипта,
планировщика. Устройство приемника с нашей стороны — в [overview.md](overview.md).

## Папки

Под выбранным корнем (например `P:\Обмен`) программа заводит четыре папки:

| Папка | Что в ней |
|---|---|
| `Входящие/` | сюда кладет файлы отправитель |
| `Обработанные/2026-09/` | принятые файлы, по месяцам |
| `Ошибки/` | файлы, которые принять не удалось |
| `Квитанции/` | ответы отправителю |

Имена папок **по-русски**, а ключи внутри файла — латиницей, и это не разнобой. Папки читает
человек, зашедший на общий диск посмотреть, что там лежит. Файл читает машина, и собирает его
чужой программист: латинские ключи не ломаются ни в одной кодировке и не требуют от отправителя
ничего особенного.

Корень обмена задает **политика организации**, а не пользователь: папка-приемник — такая же
дверь, как сетевой адрес, и открыть ее себе самому нельзя. Папка вне разрешенных корней не
откроется, и приемник даже не создаст в ней подпапок.

Отсюда два следствия, которые стоит знать администратору:

- **Обмен файлами живет и в сборке для закрытого контура.** В ней нет сетевого клиента, но папка —
  не сеть, и этот канал остается единственным работающим. Ради него закрытая сборка и остается
  пригодной для обмена.
- **Режим `isolated` закрывает и папки тоже.** Чтобы разрешить обмен файлами и запретить сетевой,
  ставится не `isolated`, а обычный режим с **пустыми** списками адресов и заполненным списком
  папок: тогда ни один адрес не пройдет, а папка откроется.

## Файл

```json
{
  "collection": "Заказы",
  "mode": "update",
  "key": "Номер",
  "id": "2026-09-10-0042",
  "rows": [
    { "Номер": "А-1", "Название": "Молоток", "Статус": "новый" },
    { "Номер": "А-2", "Название": "Отвертка", "Статус": "в работе" }
  ]
}
```

| Поле | Обязательно | Что значит |
|---|---|---|
| `collection` | да | имя коллекции. **Имя, а не номер:** номера коллекций у каждой базы свои, а отправитель про базы ничего не знает |
| `mode` | нет (по умолчанию `add`) | `add` — добавить как новые; `update` — найти по ключу и обновить, ненайденную завести |
| `key` | при `mode: "update"` | колонка, по значению которой ищется уже заведенная запись |
| `id` | при `mode: "add"` | идентификатор сообщения — защита от повторной доставки |
| `rows` | да | массив объектов; ключи объектов становятся колонками |

Незнакомый `mode` читается как `add` — самый безобидный: он ничего не перезаписывает. Строку мог
написать более новый выпуск программы-отправителя, и превращать это в отказ принять файл незачем.

### Почему `id` обязателен не всегда

В режиме `update` повтор безвреден: вторая доставка того же файла перезапишет те же записи теми же
значениями. В режиме `add` от повтора не защищает ничего — поэтому там идентификатор и требуется.

Идентификатор становится **именем файла квитанции**, поэтому в нем разрешены только буквы латиницы,
цифры, `-`, `_` и `.`, не длиннее 100 знаков. `../` и разделители пути увели бы запись из папки
обмена куда угодно.

## Как класть файл

**Пишите во временное имя и переименовывайте.**

```
заказы.json.tmp   →   заказы.json
```

Переименование атомарно; запись — нет. Приемник берет только имена с расширением `.json`, поэтому
недописанный `.tmp` он не увидит.

Если так не получается, работает запасное правило: файл берется, только когда его не трогали пять
секунд **и** он открывается монопольно. Пока отправитель держит файл открытым, приемник его не
тронет.

## Квитанция

Ответ кладется в `Квитанции/` под именем `<id>.json`, а если идентификатора не было — рядом с
именем исходного файла: `заказы.result.json`.

```json
{
  "file": "заказы.json",
  "id": "2026-09-10-0042",
  "accepted": true,
  "collection": "Заказы",
  "received": 2,
  "created": 1,
  "updated": 1,
  "skipped": 0,
  "ambiguous": 0,
  "empty": 0,
  "explanation": "",
  "at": "2026-09-10T08:30:00.0000000+00:00"
}
```

| Поле | Что значит |
|---|---|
| `accepted` | файл принят и записи уложены |
| `received` | сколько записей было в файле |
| `created` / `updated` | сколько заведено и сколько обновлено |
| `skipped` | пропущено по правилам привязки |
| `ambiguous` | в коллекции несколько записей с таким же значением ключа — какую править, приемник не решает |
| `empty` | у строки колонка ключа пустая: сопоставлять не по чему, а завести значило бы плодить дубль при каждой доставке |
| `explanation` | причина отказа либо пояснение к принятому файлу |

Квитанция пишется тем же приемом, что требуется от отправителя, — через временное имя и
переименование: приемник тоже не должен подсовывать половину файла тому, кто его читает.

## Повторы

Отправитель при обрыве связи пришлет файл дважды. Это норма, а не сбой, и обмен обязан ее
переживать.

**Память о принятых сообщениях — сами квитанции.** Перед разбором приемник смотрит, нет ли уже
`Квитанции/<id>.json`; есть — файл считается повтором, второй раз не обрабатывается и уезжает в
`Обработанные/`, а прежняя квитанция остается нетронутой. Отправитель, перечитав ее, получит тот же
ответ, что и в первый раз.

Память намеренно лежит **в папке обмена**, а не в локальной базе программы: папку видят все машины,
а локальную базу — только своя. Вторая доставка вполне может попасть на соседний компьютер, и
память на одной машине такой повтор пропустила бы.

## Несколько машин на одну папку

База открыта на нескольких компьютерах — файл увидят все. Захват идет **переименованием**:

```
заказы.json   →   заказы.json.занял-ПК17
```

Кто успел, тот и обрабатывает; остальные получают отказ файловой системы и идут дальше. На сетевой
шаре это надежнее любых блокировок: переименование либо случилось, либо нет.

Захват, брошенный дольше четырех часов назад (машину выключили посреди обмена), возвращается во
«Входящие». Окно намеренно большое: обмен на миллион строк идет долго, и отобрать файл у
работающего соседа хуже, чем подождать лишний час.

## Чего протокол не гарантирует

- **Мгновенного ответа.** Отправитель узнает результат только квитанцией, и только когда приемник
  до файла доберется.
- **Порядка между машинами.** Файлы одной машиной берутся по времени записи, но две машины могут
  разобрать два файла одновременно.
- **Ровно одной обработки при отключении питания.** Квитанция пишется сразу после укладки, но
  между ними есть окно шириной в один файл: упади программа именно там, повторная доставка в режиме
  `add` заведет записи второй раз. В режиме `update` это безвредно, и потому он предпочтительнее
  везде, где у записей есть свой ключ.
- **Проверки прав отправителя.** Кто может положить файл в папку, решают права на саму папку — тем
  же механизмом, что и доступ к базам.
