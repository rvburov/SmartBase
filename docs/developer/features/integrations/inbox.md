# Папка-приемник: протокол обмена файлами

## Назначение

Способ передать данные в программу, у которого **нет двери**: сторонняя программа кладет файл в общую
папку, а программа раз в полминуты туда заглядывает. Ни портов, ни прав администратора, ни
согласований с ИТ — общий диск уже есть.

Уникальное свойство, ради которого канал и существует: **он асинхронный**. Файл дождется, пока
приемник включат. При выключаемом на ночь сервере это не мелочь, а главное отличие от любого
варианта с сокетом.

Этот файл — **контракт для отправителя**. Его читает разработчик сторонней программы: учетной
системы, скрипта, планировщика. Устройство приемника с нашей стороны — в [overview.md](overview.md).

## Папки

Под выбранным корнем (например `P:\Обмен`) программа заводит четыре папки:

| Папка | Что в ней |
|---|---|
| `Входящие/` | сюда кладет файлы отправитель |
| `Обработанные/2026-09/` | принятые файлы, по месяцам |
| `Ошибки/` | файлы, которые принять не удалось |
| `Квитанции/` | ответы отправителю |

Имена папок **по-русски**, а ключи внутри файла — латиницей, и это не разнобой. Папки читает
человек, зашедший на общий диск посмотреть, что там лежит. Файл читает машина, и собирает его
сторонней программист: латинские ключи не ломаются ни в одной кодировке и не требуют от отправителя
ничего особенного.

Корень обмена задает **политика организации**, а не пользователь: папка-приемник — такая же
дверь, как сетевой адрес, и открыть ее себе самому нельзя. Папка вне разрешенных корней не
откроется, и приемник даже не создаст в ней подпапок.

Отсюда два следствия, которые стоит знать администратору:

- **Обмен файлами живет и в сборке для закрытого контура.** В ней нет сетевого клиента, но папка —
  не сеть, и этот канал остается единственным работающим. Ради него закрытая сборка и остается
  пригодной для обмена.
- **Режим контура папке не помеха.** Режим (`isolated` и остальные) спрашивают только сетевые
  двери; рамку папкам ставит список `folders` политики, и он остается их единственной рамкой.
  Чтобы разрешить обмен файлами и запретить сетевой, достаточно `isolated` с заполненным списком
  папок: ни один адрес не пройдет, а папка откроется. Отсутствие политики и истекший срок
  запирают обе двери.

## Файл

```json
{
  "collection": "Заказы",
  "mode": "update",
  "key": "Номер",
  "id": "2026-09-10-0042",
  "rows": [
    { "Номер": "А-1", "Название": "Молоток", "Статус": "новый" },
    { "Номер": "А-2", "Название": "Отвертка", "Статус": "в работе" }
  ]
}
```

| Поле | Обязательно | Что значит |
|---|---|---|
| `collection` | да | имя коллекции. **Имя, а не номер:** номера коллекций у каждой базы свои, а отправитель про базы ничего не знает |
| `mode` | нет (по умолчанию `add`) | `add` — добавить как новые; `update` — найти по ключу и обновить, ненайденную завести; `delete` — найти по ключу и удалить; `ensure-collection` — создать коллекцию и добрать недостающие поля |
| `key` | при `update` и `delete` | колонка, по значению которой ищется уже заведенная запись |
| `id` | при `mode: "add"` | идентификатор сообщения — защита от повторной доставки |
| `rows` | кроме `ensure-collection` | массив объектов; ключи объектов становятся колонками |
| `fields` | при `ensure-collection` | состав полей: `[{ "name": "Номер", "type": "text" }]`; типы — `text`, `number`, `date`, `checkbox`, `url` |

Незнакомый `mode` — **отказ словами**, а не тихое `add`. Пока режимов было два и оба клали данные,
деградация была безвредной; с появлением `delete` прочесть чужое намерение не тем действием стало
хуже, чем отказать: квитанция честно скажет, что приемник старее вашего формата. Пустой `mode`
остается `add` — так пишут с первого дня формата.

### `delete` — найти по ключу и удалить

Читается только колонка ключа, остальное в строках не смотрится. Правила те же, что у
сопоставления при `update`: пустой ключ — строка пропускается, несколько записей с тем же
значением — **не тронута ни одна** (в квитанции `ambiguous`), ненайденный ключ — `skipped`, и для
повтора это норма, а не беда. Удаленное попадает в журнал изменений с именем робота — его же отдаст
`/v1/changes`. По сети нужен допуск: роботу право «Удаление записи» выдает администратор базы
обычной панелью — в стандартной маске робота его нет.

Если на удаляемые записи ссылается свойство-связь с настройкой «Запретить удаление», сообщение
отклоняется **целиком**, до первой удаленной записи: ответ 422, в тексте отказа — какие связи
держат записи. Ссылки из записей того же сообщения не мешают — они удаляются вместе. Повтор
сообщения получит тот же отказ, пока ссылки не убраны или запрет не снят.

### `ensure-collection` — подготовить себе место

Одно сообщение при первом запуске сторонней программы: нет коллекции — создается, нет полей —
добираются. Существующие поля **не трогаются**: совпало имя при другом типе — отказ целиком, до
первого созданного поля. Записи этот режим не принимает — пришлите их отдельным сообщением:
«подготовь место» и «положи данные» — два разных права и два разных отказа. Словарь типов нарочно
короткий: списки требуют состава пунктов, связи — второй коллекции, и заводить их пустыми значило
бы оставить человеку ловушку вместо поля. По сети нужны права «Создание коллекции» и «Создание
свойства» — оба, всегда: иначе одно и то же сообщение проходило бы или нет в зависимости от того,
что уже есть в базе, а робот без прав выведывал бы состав базы по разнице отказов.

### Почему `id` обязателен не всегда

В режиме `update` повтор безвреден: вторая доставка того же файла перезапишет те же записи теми же
значениями. У `delete` повтор находит записи уже удаленными, у `ensure-collection` — все готовым.
В режиме `add` от повтора не защищает ничего — поэтому там идентификатор и требуется.

Идентификатор становится **именем файла квитанции**, поэтому в нем разрешены только буквы латиницы,
цифры, `-`, `_` и `.`, не длиннее 100 знаков. `../` и разделители пути увели бы запись из папки
обмена куда угодно.

## Как класть файл

**Пишите во временное имя и переименовывайте.**

```
заказы.json.tmp   →   заказы.json
```

Переименование атомарно; запись — нет. Приемник берет только имена с расширением `.json`, поэтому
недописанный `.tmp` он не увидит.

Если так не получается, работает запасное правило: файл берется, только когда его не трогали пять
секунд **и** он открывается монопольно. Пока отправитель держит файл открытым, приемник его не
тронет.

**Потолка размера у файла нет.** Конверт читается токен за токеном, записи остаются в файле и
читаются оттуда потоковым источником импорта, поэтому память не зависит от размера файла. Потолок
здесь был — 32 МБ, — и был честной защитой, пока конверт разбирался из строки, прочитанной целиком:
один файл стоил тогда нескольких своих размеров памяти. Упиралась в него, однако, не чужая шалость,
а обычная ночная выгрузка, и правильным ответом было убрать причину, а не поднять число.

Платой за это стал знак жизни: без потолка укладка может идти дольше четырех часов, и сосед счел бы
захват брошенным. Захват отмечается живым по ходу работы (`InboxFolder.Touch`), и отметка идет
из обхода строк, а не по таймеру: она обязана означать «работа идет», а не «программа жива».

Тот же протокол берет и шаг сценария «файл из папки» — с двумя поправками. Первая: он берет ЛЮБОЙ
файл, а не только `.json`, потому что формат ему задает следующий шаг-преобразователь. Вторая:
именно поэтому он читает файл В СТРОКУ целиком, и потолок в 32 МБ (`InboxFolder.MaxFileBytes`)
остается у него — читать потоком то, о формате чего ничего не известно, нечем. Захваты соседей и
недописанные `.tmp` при этом отсеиваются по-прежнему, только явно. Остальное — выдержка,
монопольное открытие, захват, квитанция, помесячные папки — общее, и общим оно и должно остаться:
две реализации одного протокола на одну папку разошлись бы на первой правке. Подробности —
[overview.md](overview.md), раздел «Шаг „файл из папки“».

## Квитанция

Ответ кладется в `Квитанции/` под именем `<id>.json`, а если идентификатора не было — рядом с
именем исходного файла: `заказы.result.json`.

```json
{
  "file": "заказы.json",
  "id": "2026-09-10-0042",
  "accepted": true,
  "collection": "Заказы",
  "received": 2,
  "created": 1,
  "updated": 1,
  "skipped": 0,
  "ambiguous": 0,
  "empty": 0,
  "explanation": "",
  "at": "2026-09-10T08:30:00.0000000+00:00"
}
```

| Поле | Что значит |
|---|---|
| `accepted` | файл принят и записи уложены |
| `received` | сколько записей было в файле |
| `created` / `updated` | сколько заведено и сколько обновлено |
| `deleted` | сколько удалено (режим `delete`); в старых квитанциях поля нет — читайте как ноль |
| `skipped` | пропущено по правилам привязки; у `delete` — ключи, по которым удалять было нечего |
| `ambiguous` | в коллекции несколько записей с таким же значением ключа — какую править, приемник не решает |
| `empty` | у строки колонка ключа пустая: сопоставлять не по чему, а завести значило бы плодить дубль при каждой доставке |
| `explanation` | причина отказа либо пояснение к принятому файлу |

Квитанция пишется тем же приемом, что требуется от отправителя, — через временное имя и
переименование: приемник тоже не должен подсовывать половину файла тому, кто его читает.

## Повторы

Отправитель при обрыве связи пришлет файл дважды. Это норма, а не сбой, и обмен обязан ее
переживать.

**Память о принятых сообщениях — сами квитанции.** Перед разбором приемник смотрит, нет ли уже
`Квитанции/<id>.json`; есть — файл считается повтором, второй раз не обрабатывается и уезжает в
`Обработанные/`, а прежняя квитанция остается нетронутой. Отправитель, перечитав ее, получит тот же
ответ, что и в первый раз.

Память намеренно лежит **в папке обмена**, а не в локальной базе программы: папку видят все машины,
а локальную базу — только своя. Вторая доставка вполне может попасть на соседний компьютер, и
память на одной машине такой повтор пропустила бы.

## Несколько машин на одну папку

База открыта на нескольких компьютерах — файл увидят все. Захват идет **переименованием**:

```
заказы.json   →   заказы.json.занял-ПК17
```

Перед переименованием приемник открывает исходник с запретом второго захвата и держит дескриптор
до конца переименования и отметки времени. На Windows это чтение с `FileShare.Delete`: другой
приемник не сможет открыть исходник для чтения, а собственное переименование разрешено. На Unix
используется `FileShare.None`, который дает исключительный `flock` и не мешает переименованию.
Кто успел, тот и обрабатывает; остальные получают отказ файловой системы и идут дальше.

Одного `File.Move` для выбора победителя на Windows недостаточно: два вызова могут открыть один
исходник до первого переименования и затем оба переименовать его через свои дескрипторы. Путь
первого участника при этом исчезнет. Открытие перед `File.Move` исключает эту гонку, не добавляя
файлов блокировки и отдельного порядка их восстановления после сбоя.

Захват, брошенный дольше четырех часов назад (машину выключили посреди обмена), возвращается во
«Входящие». Окно намеренно большое: обмен на миллион строк идет долго, и отобрать файл у
работающего соседа хуже, чем подождать лишний час. Уборка сначала открывает тот же защитный
дескриптор, затем проверяет время: файл между переименованием и обновлением отметки она не заберет.

## Чего протокол не гарантирует

- **Мгновенного ответа.** Отправитель узнает результат только квитанцией, и только когда приемник
  до файла доберется.
- **Порядка между машинами.** Файлы одной машиной берутся по времени записи, но две машины могут
  разобрать два файла одновременно.
- **Ровно одной обработки при отключении питания.** Квитанция пишется сразу после укладки, но
  между ними есть окно шириной в один файл: упади программа именно там, повторная доставка в режиме
  `add` заведет записи второй раз. В режиме `update` это безвредно, и потому он предпочтительнее
  везде, где у записей есть свой ключ.
- **Проверки прав отправителя.** Кто может положить файл в папку, решают права на саму папку — тем
  же механизмом, что и доступ к базам.
