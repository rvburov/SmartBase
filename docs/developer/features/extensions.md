# Расширения

## Назначение

Раздел **«Расширения»** — это **список плагинов**, которые подключаются к приложению
и так же легко отключаются. Главная цель — **отделимость**: каждое расширение живет в
своей папке `Extensions/<Имя>/`, зависит только от интерфейса `IExtension` и ни от чего
больше. Добавить расширение = создать папку с классом и зарегистрировать его; удалить =
убрать папку и одну строку из реестра. Остальное приложение при этом не трогается.

У расширения по задумке **два режима работы**:

1. **Самостоятельный запуск** — кнопкой «Запустить» в навбаре раздела открывается
   **отдельное окно** с функционалом расширения. Окно оформлено в **основном стиле
   приложения** (общие темы/ресурсы), чтобы визуально не отличаться от штатных окон.
2. **Надстройка над блоками приложения** — расширение встраивается в конкретные места
   программы как опция и так же убирается. Пример на будущее: в таблице конструктора в
   **контекстном меню** появляется пункт «Расширения» с выпадающим списком — пользователь
   выбирает расширение, и оно выполняет свою функцию над таблицей (см. [[constructor/table]]).

> Состояние: реализован раздел (сайдбар + блок + контракт `IExtension` + реестр) и
> **режим 1** (запуск окна). Есть семь расширений — **«Переименование PDF»** (`PdfRename`),
> **«Сравнение составов изделий»** (`ProductCompare`), **«Расчет сборочных единиц»**
> (`AssemblyCalc`), **«Анализ PDF файлов»** (`PdfAnalyzer`), **«Документы в коллекцию»**
> (`DocsCollection`), **«Сводная трудоемкость»** (`TimeCollector`) и **«Регистрация КД»**
> (`DocRegistry`): по «Запустить» каждое открывает отдельное окно в стиле приложения.
> Режим 2 (точки встраивания) — в планах (см. ниже).

## Как работает

### Контракт `IExtension`

Оболочка знает о расширении **только** через интерфейс — это и обеспечивает отделимость:

| Член | Назначение |
|---|---|
| `Id` | стабильный ключ (строка сайдбара, поиск в реестре) |
| `Name` | отображаемое имя — в строке сайдбара и в навбаре блока |
| `MarkdownDescription` | тело блока, рендерится в Markdown |
| `CanRun` | управляет доступностью кнопки «Запустить» |
| `CreateWindow()` | окно расширения (в стиле приложения), которое оболочка показывает поверх главного окна; `null` — расширение окна не открывает |

### Реестр

[ExtensionRegistry](../../../Extensions/ExtensionRegistry.cs) — статический список,
зарегистрированный вручную (`All`). Сайдбар и блок работают только с ним и с
`IExtension`. В перспективе сюда подставляется автообнаружение папок `Extensions/*`
(рефлексия по сборке) — без правок оболочки.

### Раздел в UI

При выборе модуля «Расширения» в Activity bar показывается собственный сайдбар со
списком расширений (панели записи здесь нет). Выбор строки поднимает событие
`CategorySelected(Id)`, и [ExtensionsView](../../../Views/Extensions/ExtensionsView.axaml.cs)
`ShowExtension(id)` ставит в навбар имя, рендерит Markdown-описание и включает/выключает
кнопку «Запустить» по `CanRun`. Пустой/неизвестный `id` → первое расширение из реестра;
пустой реестр → подпись «Нет доступных расширений». Кнопка «Запустить» берет окно у
`CreateWindow()` и показывает его поверх главного окна (`Window.Show(owner)`).

### Стиль окон расширений

Окно расширения строится из контролов приложения, поэтому **автоматически наследует
основной стиль** (общие темы и ресурсы `Application.Styles`/`StaticResource`) — отдельное
оформление в расширении не объявляется, чтобы окна не отличались от штатных. Пример —
[PdfRenameWindow.axaml](../../../Extensions/PdfRename/PdfRenameWindow.axaml): те же кисти
(`BrushBg`, `BrushAccent`, …), классы кнопок (`accent`/`danger`) и `ConfirmDialog`, что и
в остальном приложении. Базовые ресурсы стиля описаны в [[../ui/theming]].

### Настройки расширения

Расширению бывает нужно запомнить строку между запусками — например, путь к файлу-шаблону.
Механизм устроен так, чтобы **отделимость не пострадала**: ядро хранит значение, но не знает
ни одного расширения по имени.

Расширение объявляет свои настройки списком
[ExtensionSetting](../../../Extensions/ExtensionSetting.cs) в `IExtension.Settings` (по
умолчанию список пуст — большинству расширений объявлять нечего):

```csharp
public const string ExtensionId = "product-compare";
public const string TemplateKey = "template";

public IReadOnlyList<ExtensionSetting> Settings =>
[
    new(TemplateKey, "Файл-шаблон", @"\\server\share\Шаблон….xlsm"),
];
```

Значения хранит оболочка — `AppSettings.LoadExtensionSetting(id, key)` / `Save…` — в `app.db`
под ключом `ext.<id расширения>.<имя настройки>`. Для ядра это просто строка: смысла ее оно не
знает, фиксированного списка ключей в [AppSettings.cs](../../../Utils/AppSettings.cs) нет.
Пустое значение стирает ключ (как у пути обновления).

Раздел **Настройки → Расширения** собирается целиком из реестра: `BuildExtensionsPanel`
проходит по `ExtensionRegistry.All`, берет у каждого расширения `Settings` и строит по одной
строке на расширение. В [SettingsView.axaml](../../../Views/Settings/SettingsView.axaml)
лежат только контейнеры — ни одного расширения по имени ни в разметке, ни в code-behind нет.
Панель перестраивается при каждом показе раздела: значение могло смениться мимо этого экрана.

Заполнить настройку можно и **кнопкой «Обзор» в окне самого расширения** — окно пишет в те же
ключи, поэтому выбранный файл запоминается и подставляется при следующем открытии.

### Открытие книг Excel

Книги открывает не каждое расширение само, а общий
[ExcelBook.cs](../../../Extensions/ExcelBook.cs) — им пользуются `ProductCompare` и
`AssemblyCalc`. Обычный путь — `new XLWorkbook(path)` один в один, без копий и накладных
расходов.

`TimeCollector` сюда больше не ходит: свод пишется потоково, шаблон читается как zip
(`TimeSheetWriter`), и битое определенное имя загрузку не роняет в принципе — из результата оно
просто выбрасывается той же проверкой. ClosedXML это расширение не использует вовсе.

Отдельно разбирается одна поломка, из-за которой ClosedXML не открывает книгу **целиком**:
непарсящееся определенное имя (`definedNames` в `xl/workbook.xml`). Такие имена заводятся сами —
скопировали лист между книгами, и осталось имя со ссылкой на внешнюю книгу вида `[2]Лист!$A$1`;
если в имени листа есть пробелы, а апострофов вокруг нет, `ClosedXML.Parser` обрывается. В Excel
книга при этом открывается нормально, и пользователю неоткуда узнать, что не так: имена с
`Visible = False` не видны даже в Диспетчере имен. Формулы ячеек и проверку данных ClosedXML при
загрузке не разбирает — они книгу не роняют, лечить нужно только имена.

Лечение идет на временной **копии**: из нее выбрасываются имена, которые не разбираются, и
открывается уже она. Оригинал (общий файл на сетевой шаре) не трогается, выброшенное уходит в
лог. Терять там нечего — без этого книга не открывается вообще; макросы не страдают, правится
только список имен. Проверка «разбирается ли ссылка» — `FormulaConverter.ToR1C1` из
`ClosedXML.Parser` (пакет закреплен явно в `SmartBase.csproj`): он падает ровно там же, где
загрузка книги.

Копия обязана дожить до конца работы с книгой — ClosedXML при `SaveAs` копирует ИСХОДНЫЙ файл и
без него падает `FileNotFoundException`. Поэтому `Open` отдает не голый `XLWorkbook`, а обертку
`ExcelBook`, которая владеет копией и убирает ее в `Dispose`.

Не удалось открыть и после ремонта — движки получают `ExcelOpenException` с готовым к показу
текстом (про Диспетчер имен, префикс `[2]` и скрытые имена) и оборачивают его в свое исключение,
добавив имя файла.

### Файлы данных расширения

Расширению бывает нужен собственный справочник — такой, которого у пользователя на диске нет и
который не влезает в код. Пример — классификатор ЕСКД у «Регистрации КД»: 78 тыс. строк.

Такие файлы кладутся **в папку расширения в сжатом виде** (`Extensions/<Имя>/<файл>.gz`) и
попадают в сборку встроенным ресурсом по правилу в
[SmartBase.csproj](../../../SmartBase.csproj):

```xml
<EmbeddedResource Include="Extensions\**\*.gz" />
```

Правило — **глоб, а не перечисление**: иначе заведение и удаление расширения перестали бы быть
операцией над одной папкой и потребовали бы правки csproj. Один раз добавленное правило больше
не трогается, сколько бы расширений со своими данными ни появилось.

Имя ресурса собирается из `RootNamespace` и пути файла (`SmartBase.Extensions.<Имя>.<файл>.gz`),
но искать его по полному имени не надо: правка правила молча оставила бы расширение без данных.
Потребитель ищет ресурс **по окончанию имени** и, не найдя, называет причину и место
(см. `EskdCatalog.OpenResource`).

Что держать в голове при подготовке такого файла:

- **сжатие обязательно** — встроенные ресурсы лежат в сборке как есть, без упаковки: у ЕСКД это
  596 КБ вместо 4,9 МБ;
- **порядок строк — часть устройства файла**, а не его оформление. У ЕСКД сортировка кода как
  строки дает обход дерева сверху вниз (38, 380, 3800, 38000, 380000, … 381), и на этом стоит
  все: и бинарный поиск по коду, и то, что предок всегда идет перед потомками;
- **дефекты исходника чинятся при загрузке**, а не в файле: файл остается честной выгрузкой, а
  правка живет на виду и под тестами (`EskdCatalog.Repair` — склейка перенесенного наименования
  и достройка пропущенного узла);
- **порядок и прочие инварианты файла проверяются тестом** набора расширения, а загрузчик падает
  с внятным текстом, если они нарушены: иначе поломка данных превратилась бы в молча неполный
  результат поиска.

Как готовился `eskd.tsv.gz` — из исходной выгрузки классификатора (`код⇥наименование`, все
уровни, CRLF, первой строкой заголовок таблицы):

```bash
tr -d '\r' < ЕСКД.bas \
  | awk -F'\t' '$1 ~ /^[0-9]+$/ && length($1) >= 2 && length($1) <= 6 && $2 != ""' \
  | LC_ALL=C sort -s -k1,1 \
  | gzip -9 -c > Extensions/DocRegistry/eskd.tsv.gz
```

`awk` отбрасывает заголовок и мусорные строки, оставляя все пять уровней классификатора: по
дереву ходят, значит промежуточные узлы нужны, хотя в обозначение ставится только шестизначный
код. `sort` дает тот самый порядок обхода дерева (`-s` сохраняет исходный порядок у задвоенных
кодов), `LC_ALL=C` — байтовое сравнение вместо локального: сортировать надо код КАК СТРОКУ, по
числам «380» встало бы после «38000» и дерево рассыпалось бы. Пересобрали файл — прогоните
`dotnet test Tests/Extensions/DocRegistry`: состав, порядок и результат починки там прибиты
тестами.

### Какие расширения показывать

Первая строка раздела **Настройки → Расширения** — «Отображение раздела расширений»: тот же
[CheckListDropdown](../../../Controls/Widgets/CheckListDropdown.axaml.cs), что у «Отображение
раздела …» в «Оформлении», и то же хранилище (`hiddenViews.<scope>`, хранятся СКРЫТЫЕ ключи).
Строка живет здесь, а не в «Оформлении», намеренно: там перечислены **виды** разделов, а тут —
**состав** самого раздела расширений.

Пункты дает [ViewCatalog](../../../Settings/ViewCatalog.cs) под scope `extensions` — и это
**единственный динамический раздел каталога**: список не перечислен в коде, а собирается из
`ExtensionRegistry.All` (ключ — `Id`, подпись — `Name`). Правило «позиция = глобальный номер
вида» к нему не относится: номеров у расширений нет, «вида по умолчанию» у раздела не бывает.

Снятая галочка убирает расширение отовсюду, кроме самой строки галочек (иначе вернуть его
было бы нечем):

| Где | Как отфильтровано |
|---|---|
| Сайдбар раздела «Расширения» | `MainWindow.SyncExtensionsSidebar` — пункты из `ViewCatalog.Visible`; пересобирается при заходе в раздел и только если состав менялся (`SetItems` перерисовывает строки и сбрасывает выбор) |
| Блок раздела | `ExtensionsView.ShowExtension` — скрытый Id не показывается, запасной выбор идет через `FirstVisible` |
| Список настроек ниже | `BuildExtensionsSettingsList` — `ViewCatalog.IsVisible` на каждое расширение; список перестраивается сразу по клику галочки, а сам выпадающий список — нет (его попап в этот момент открыт под курсором) |

**Уборка после удаления — та же, что у настроек.** Список пунктов динамический, поэтому Id
удаленного расширения мог бы остаться в `hiddenViews.extensions` навсегда: на старте рядом с
`RemoveOrphanExtensionSettings` вызывается `AppSettings.PruneHiddenViews(ScopeExtensions, …)`
со списком живых Id — осиротевшие ключи уходят, число убранных пишется в журнал. Без этого
вернувшееся расширение оказалось бы скрытым без видимой причины.

> Тесты каталога намеренно **не называют ни одного расширения и не рассчитывают на их число**
> (см. `ViewCatalogTests`): сборка без расширений — законное состояние, и набор ядра обязан
> оставаться зеленым.

**Уборка после удаления.** На старте (`App.OnFrameworkInitializationCompleted`, сразу после
`AttachStore`) вызывается `AppSettings.RemoveOrphanExtensionSettings` со списком Id из
реестра: строки `ext.<id>.…`, чьего расширения в сборке больше нет, удаляются, число убранных
пишется в журнал. То есть удалили папку и строку реестра, запустили программу — и в `app.db`
не осталось ничего лишнего, руками чистить нечего.

Живым расширение считается по полной приставке `ext.<id>.`, а не разбором ключа: Id с точкой
внутри уборку не сломает, а расширение с похожим началом имени не унесет чужие настройки
(`pdf-rename` и `pdf-rename-v2` — разные). Ключи вне `ext.` уборка не трогает.

> Обратная сторона: расширение, убранное из реестра **временно** (например, закомментировали
> строку, чтобы вернуть позже), теряет свои настройки при первом же запуске — после возврата
> значения придется ввести заново. Это осознанный размен в пользу «после удаления не остается
> ничего».

**Уникальность Id.** Там же на старте — `ExtensionRegistry.EnsureUniqueIds()`: при
совпадающих Id программа падает с явным сообщением. Иначе ошибка проходила бы молча и ломала
две вещи разом — `FindById` отдавал бы не то расширение, а тезки делили бы одни настройки
(ключ строится из Id). Уникальность заодно закреплена тестом.

> **Почему не отдельная база данных под расширения.** Отделимость ломает не общее хранилище, а
> знание ядра о конкретных расширениях: метод вида `LoadProductCompareTemplate` в `AppSettings`
> нарушал бы контракт и в отдельном файле БД ровно так же. Отдельный файл при этом стоит
> дорого — второй `DbContext`, свои миграции, бэкап, перенос, блокировки — ради нескольких
> строк. Поэтому значения лежат в `app.db` вместе с остальными настройками, а развязка
> достигнута обобщенным ключом.

Существование файла заранее не проверяется: это делает движок при запуске прогона и возвращает
«Файл-шаблон не найден» — сетевая папка может быть временно недоступна, и блокировать из-за
этого окно незачем.

### Расширение «Переименование PDF»

Пакетно переименовывает PDF-файлы в выбранной папке по правилу **«все до первого пробела
+ `.pdf`»** (например, `Отчет 2024 итог.pdf` → `Отчет.pdf`). Особенности реализации:

- Логика в [PdfRenamer.cs](../../../Extensions/PdfRename/PdfRenamer.cs) — без UI: `BuildPlan`
  (план без изменений) и `Process` (прогон по готовому плану с `IProgress`/`CancellationToken`).
  Учитывает внутрипакетные конфликты (несколько файлов → одно имя) и занятые имена на
  диске — такие файлы **пропускаются**.
- Окно [PdfRenameWindow](../../../Extensions/PdfRename/PdfRenameWindow.axaml.cs): выбор папки
  (`StorageProvider`), «Проверить» (dry-run, ничего не меняет), «Запустить» (с
  подтверждением через [ConfirmDialog](../../../Controls/Dialogs/ConfirmDialog.axaml.cs)) и
  «Остановить» (отмена). Файлы только переименовываются, не удаляются.
- **Масштаб (тысячи файлов).** План строится один раз и в фоне (`Task.Run`); прогон тоже в
  фоне. UI не обновляется на каждый файл: прогресс и журнал идут **с троттлингом** (~20/сек),

  **только конфликты/ошибки** (успехи — в счетчик/полосу), число строк ограничено. Поэтому
  окно остается отзывчивым на десятках тысяч файлов; узким местом остается лишь диск/сеть.

### Расширение «Анализ PDF файлов»

По папке с PDF формирует Excel-отчет (ведомость/опись КД, ПД, ТД): разбирает имена файлов
(номера КД/ПД/ТД по ГОСТ 2.201 / 19.101 / 19.103 + название), считает MD5, число и форматы листов
(по размерам страниц, допуск 30 мм), «листов формата А4», объем.

- [DocumentCodes.cs](../../../Extensions/PdfAnalyzer/DocumentCodes.cs) — справочники кодов
  ЕСКД/ЕСПД и разбор обозначений (регэкспы извлечения номеров, базовый номер, полное
  наименование). В шапке класса — шпаргалка по формированию децимального номера ТД/КД/ПД.
  Только публичные коды ГОСТ — не секрет. Суффиксы листов `-ЛУ`/`-УЛ`
  собираются из типа основного документа + названия листа (напр. `…СБ-ЛУ` → «Сборочный
  чертеж Лист утверждения») для **любого** кода; конкретные комбинации с особым именем
  (`Д42-УЛ` = «Данные программирования…», `ТУ-ЛУ`…) остаются приоритетными исключениями.
  Тип программного документа (ПД) определяется **кодом вида документа** (2-значное поле «ВВ»
  номера `КОДО.РРРРР-ИИ ВВ ДД`, ГОСТ 19.101 → `PdVidCodes`); номер без кода вида — сама
  программа (`Спецификация`). Носители `…НД`/`…НДЗ` берут тип как коды из `KdNameMapping`.
- [PdfAnalyzerEngine.cs](../../../Extensions/PdfAnalyzer/PdfAnalyzerEngine.cs) — обход папки
  (рекурсивно/локально), чтение PDF через **PdfPig** (число страниц + размеры), форматы
  листов, 3 режима сортировки, 6 типов выгрузки (КД и ПД разведены полностью: у каждого своя
  ведомость и опись; отбор строк — `ScopeRows`), запись отчета в .xlsx (лист «ОПИСЬ») через
  ClosedXML со стилем (Times New Roman, границы, ширины колонок); `IProgress`/`CancellationToken`.
- Окно [PdfAnalyzerWindow](../../../Extensions/PdfAnalyzer/PdfAnalyzerWindow.axaml.cs): папка/отчет
  (`StorageProvider`), тип выгрузки (`ComboBox`), опции (рекурсия / порядок из папки — взаимно
  исключающие; «наименование в несколько строк» — **вкл по умолчанию**), прогресс по файлам
  в фоне (`Task.Run`), по завершении — статистика + открыть папку.
- Чекбокс «Наименование документа в несколько строк (изделие / тип / лист)» (флаг `splitName`
  в `Run`): раскладывает наименование на части по строкам внутри ячейки через
  `GetDocumentFullNameMultiline` (иначе — одной строкой `GetDocumentFullName`, поведение
  1-в-1). Высота строки в .xlsx подгоняется под число строк ячейки. Влияет на выгрузки с
  наименованием (Ведомость/Опись КД, Ведомость/Опись ПД, Все; в ТД наименование = только
  изделие). Спец. комбинации (`ТУ-ЛУ`…) тоже разносятся: тип и лист разделяются по окончанию
  (`SplitSheetSuffix`).

> ⚠️ Зависимости: это расширение добавляет в общий `SmartBase.csproj` пакет **PdfPig** (чтение
> PDF) и использует **ClosedXML** (Excel). Т.е. расширение, которому нужна внешняя библиотека,
> добавляет NuGet-пакет в проект — в отличие от расширений, обходящихся контролами приложения.

Тесты: [Tests/Extensions/PdfAnalyzer/](../../../Tests/Extensions/PdfAnalyzer/) — разбор
обозначений ЕСКД/ЕСПД и сборка наименования (свыше сотни случаев) плюс сквозной прогон на PDF,
сгенерированных писателем PdfPig: форматы листов, счет листов А4, состав колонок по типу

### Расширение «Документы в коллекцию»

По выбранной папке создает **коллекцию конструктора**, где каждая запись — документ. Первое
расширение, которое не выгружает файл, а **пишет в базу** — образец того, как расширение
работает с данными приложения, оставаясь отделимым.

Схема создаваемой коллекции (порядок колонок задается `SaveColumnOrder`):

| Колонка | Чем является | Что записывается |
|---|---|---|
| Наименование | системная `Title` (переименована через `SetSystemFieldName`) | имя файла без расширения |
| Название папки | поле типа `text` | имя папки документа |
| Формат файла | поле типа `text` | расширение без точки, нижний регистр |
| Файл | поле типа `file` | абсолютный путь (см. [FileValue](../../../Core/Models/FileValue.cs)) |

- Логика в [DocsCollectionBuilder.cs](../../../Extensions/DocsCollection/DocsCollectionBuilder.cs)
  — без UI, три намеренно разнесенных шага: `Scan` (обход диска, `EnumerationOptions` со
  `IgnoreInaccessible` и пропуском скрытых/системных), `CreateShell` (коллекция + колонки на
  **общем** репозитории — там же срабатывает право `CreateCollection`), `FillRecords` (записи на
  **отдельном** подключении `new AppDbContext(repo.DbPath)` — общий контекст EF принадлежит
  UI-потоку, тот же прием, что у `AddRecordIsolated`/`DeleteCollectionIsolated`).
- Окно [DocsCollectionWindow](../../../Extensions/DocsCollection/DocsCollectionWindow.axaml.cs):
  папка (`StorageProvider`), чекбокс рекурсии, строка расширений-фильтра, выбор базы, прогресс с
  троттлингом (сообщение раз в 25 записей — поток постов в UI тормозит сильнее самой вставки),
  «Остановить». Отмена/ошибка → недособранная коллекция удаляется (`DeleteCollectionIsolated`).
- **Доступ к базам — без правок приложения**: расширение берет репозиторий через
  [RelationDbResolver](../../../Database/RelationDbResolver.cs) (`Databases()` / `RepoFor(dbId)`),
  а список коллекций в сайдбаре обновляет, найдя `SidebarTree` в визуальном дереве окна-владельца.
  Событие «коллекции изменились» живет внутри UI и расширению недоступно; поиск по дереву
  обернут в try/catch — не нашли, значит коллекция появится при следующем обновлении списка.
- ⚠️ Поле «Файл» создается **без** правила авто-привязки ([FileAutoRule](../../../Core/Models/FileAutoRule.cs)):
  правило умеет ровно одну папку (без подпапок) и один формат, чего не хватает при рекурсивном
  обходе и смешанных расширениях. Пути проставляются напрямую, поле остается редактируемым.
- ⚠️ Записи создаются публичным API (`AddRecord` + `SetFieldValue`), а не сырым пакетным
  INSERT, как импорт: это дает запись `Description` (ее `ImportStreamedCollection` не пишет),
  но стоит ~3 коммитов и трех строк журнала изменений на документ. На типовых папках
  (сотни-тысячи файлов) это секунды; для десятков тысяч — минуты, прогон отменяем.

Тесты: [Tests/Extensions/DocsCollection/](../../../Tests/Extensions/DocsCollection/) — обход
папки и фильтр форматов, каркас коллекции (поля, порядок колонок, уникализация имени, право
«Создавать коллекции») и наполнение записями на отдельном подключении.

### Расширение «Сводная трудоемкость»

Порт макроса `TimeCollector` из книги «_Таблица трудоемкости.xlsm» (пункт **«Обновить»** в
контекстном меню листа «Таблица»): обходит папку с расчетами `*.xlsm`, читает в каждом лист
«Расшифровка» и собирает сводную таблицу трудоемкости. В исходнике путь к папке жил в ячейке
`Настройки!B1`, а про непрочитанные файлы было известно только числом в итоговом `MsgBox` —
ради разбора этих файлов расширение и заводилось.

**Приемников у свода два**, выбор — списком «Куда выгрузить» в окне: лист «Таблица»
.xlsm-шаблона (порт макроса целиком) и **коллекция программы**. Общая часть — чтение папки и
сборка строк (`TimeCollectorEngine.Collect` → `CollectedTable`: строки в конечном порядке, план
раскраски, счетчики и замечания); все, что зависит от приемника (шаблон и скрытые колонки либо
поля коллекции), считается уже после. Блоки 2 и 3 окна принадлежат приемнику и переключаются
вместе с ним, поэтому нумерация подписей у обоих одинаковая.

- [CalcFileReader.cs](../../../Extensions/TimeCollector/CalcFileReader.cs) — чтение одного
  расчета через **ExcelDataReader** (потоково, книга в память не поднимается). Заменяет связку
  ADO/ACE OLEDB: колонки `F1…F11` запроса `SELECT … FROM [Расшифровка$]` — это колонки листа
  A…K, то есть индексы 0…10 ридера. Строка идет в свод, если заполнены И иерархический номер
  (B), И трудоемкость (G) — условие 1-в-1 из `GetData`. Обозначение чистится от пробелов;
  в скрытую колонку A кладется номер строки источника минус единица — ровно то, что читает
  `CalculationLink` при переходе по ссылке.
- [TimeCollectorEngine.cs](../../../Extensions/TimeCollector/TimeCollectorEngine.cs) — обход
  папки (рекурсивно/локально, `EnumerationOptions` со `IgnoreInaccessible`; берутся `*.xlsm`
  с именем **без «$»** — то же условие макроса, оно же отсекает служебные `~$`-файлы),
  **параллельное чтение** в `2 × ядра` потоков, потолок 16 (`Parallel.For`; результат каждого файла кладется в массив
  по его индексу, поэтому порядок сборки не зависит от потоков), разбор имени
  `Проект_ГГГГ.ММ.ДД_ФИО.xlsm`, сортировка и план раскраски. `IProgress`/`CancellationToken`.
- [TimeSheetWriter.cs](../../../Extensions/TimeCollector/TimeSheetWriter.cs) +
  [TimeSheetStyles.cs](../../../Extensions/TimeCollector/TimeSheetStyles.cs) — **потоковая**
  запись свода в копию шаблона: шапка с объединениями (`SetHeaderData`), данные с 4-й строки,
  границы, раскраска, скрытие пустых колонок, автофильтр и имя `ALL_DATA`. Результат
  собирается новым zip-архивом, куда части шаблона копируются побайтно, а лист свода пишется
  на лету — отсюда и скорость, и целость макросов (подробности и замеры —
  [[../architecture/performance/hot-paths]]).
- [TimeCollectionWriter.cs](../../../Extensions/TimeCollector/TimeCollectionWriter.cs) — запись
  свода коллекцией программы (см. ниже).
- Окно [TimeCollectorWindow](../../../Extensions/TimeCollector/TimeCollectorWindow.axaml.cs):
  выбор приемника, папка + рекурсия, дальше — либо шаблон и папка результата (`StorageProvider`,
  пути — объявленные расширением настройки `folder`/`template`/`output`), либо база и название
  коллекции; индикатор **по фазам** и журнал во всю оставшуюся высоту.

**Раскраска** (`PlanColors`) повторяет `SameProductsSameColor` + `SameNormColor`: цвет
чередуется на каждой смене обозначения (светло-желтый ↔ белый), строка без обозначения — белая;
у соседей с одинаковым обозначением и разной трудоемкостью совпали проект и дата — обе строки
красные, иначе красными становятся только их ячейки «Тр-ть». Красный только добавляется, поэтому
итог считается за один проход **до** записи, а заливка кладется в файл непрерывными кусками
одного цвета — на десятках тысяч строк вызов на каждую строку в ClosedXML стоит заметно дороже.
`OperationsColor` не переносился: его цикл `For col = 10 To 8` при восьми колонках не выполняется
ни разу (мертвый код исходника).

**Трудоемкость читается без шума двоичного представления** — 12 значащих цифр
(`CalcFileReader.WithoutBinaryNoise`). Ячейку расчета считает формула, и ее кэш оседает в файле
с двоичной погрешностью: вместо `6,1` там лежит `6,1000000000000005` — ДРУГОЕ число, у него другие
биты. .NET показывает это как есть: `ToString` у `double` дает кратчайшую запись, по которой число
восстанавливается точно, а для этого нужны все 17 цифр.

Без округления одна причина била в трех местах сразу:

| Где | Как выглядело |
|---|---|
| коллекция | `6,1000000000000005` вместо `6,1` (формат «Обычное число» отдает значение как есть; наш формат по умолчанию это прятал шаблоном на шесть знаков) |
| лист Excel | та же длинная запись в `<v>`; прятал формат колонки |
| **раскраска** | `PlanColors` сверяет трудоемкости ТОЧНО, и строки с одинаковым на вид значением объявлялись расходящимися и краснели — **в обоих приемниках**, потому что раскраска считается один раз до записи |

Формат колонки лечил только показ, сравнение он не лечил нигде — поэтому округление стоит
при ЧТЕНИИ, в одном месте на всех потребителей.

**Почему 12 значащих цифр, а не 15** (предел точности самого Excel). Трудоемкость считается
суммой: в реальной ячейке стоит что-нибудь вроде `=СУММ(G3:G11)+H12+H96+H97+…` на два десятка
слагаемых, и каждое из них — тоже сумма. Погрешность на сложении НАКАПЛИВАЕТСЯ: на двух десятках
слагаемых она добирается до 15-й значащей цифры, на сотнях — до 14-й, то есть за предел, который
прячет Excel. `0,850000000000001` он показывает как есть, и первая версия правки (15 цифр) такие
значения не чистила — это всплыло на настоящем своде.

Двенадцать — с запасом с обеих сторон. Сверху: трудоемкости хватает девяти-десяти значащих цифр
(`1234567,891` часа — уже фантастика), настоящих данных не теряется. Снизу: до 12-й цифры
накопленная погрешность добралась бы только на тысячах операций сложения. Единственная защита —
переполнение: у чисел под пределом `double` округление вверх дает бесконечность, и тогда значение
остается исходным.

**Журнал и проблемные файлы.** Во время прогона журнал молчит: счетчики, текущий файл и оценка
времени ([EtaEstimator](../../../Utils/EtaEstimator.cs), те же формулировки, что у импорта) идут
в индикатор, а замечания выводятся в конце — отсортированными по имени, секциями:

| Секция | Статусы | Как определяется |
|---|---|---|
| ⚠️ Открыты другим пользователем | `OpenedByOther` | рядом лежит `~$<имя>.xlsm` **и** книгу кто-то держит; имя владельца достается из маркера best-effort |
| ℹ️ Остались служебные файлы `~$` | `StaleLock` | маркер есть, но книга свободна; одна строка со счетчиком, имена не перечисляются |
| ❌ Не открылись | `Locked`, `NoAccess`, `Corrupted` | sharing violation (`HResult & 0xFFFF` = `0x20`/`0x21`, как в `ImportErrors.Map`), отказ прав, любая ошибка разбора |
| ⏭️ Пропущены | `NoSheet`, `BadName`, `NoRows` | нет листа «Расшифровка», имя не по образцу, нет подходящих строк |

**Приведение текста к одному алфавиту** ([Homoglyphs.cs](../../../Extensions/TimeCollector/Homoglyphs.cs)).
Галочка в окне, **включена по умолчанию**. Расчеты набивают в двух раскладках вперемешку, и
в русском слове оказывается латинская `C`, а в английском — кириллическая `О`. На глаз не видно,
для программы строки разные, а в своде это разъезжается по-крупному: `Обозначение КД` — ключ
`Sort` и `PlanColors`, причем сравнивается он **побайтно** (`StringComparison.Ordinal`), так что
одно обозначение, набранное двумя способами, дает две группы с разной заливкой.

Решение принимается **по слову**, а не по символу и не по значению. По символу нельзя: отдельная
`С` не несет никакого указания, чем ей быть. По значению — тоже: наименования и проекты сплошь
двуязычны, английское слово в русской фразе законно. Слово здесь — связный кусок букв и цифр;
точка, дефис, пробел его разрывают.

Внутри слова считаются буквы БЕЗ двойника — они и решают:

| Что в слове | Что делаем |
|---|---|
| однозначные буквы одного алфавита | язык известен, двойники переводятся в него |
| однозначные буквы обоих алфавитов | не трогаем, считаем в `Mixed` — либо законная смесь, либо порча, которую без человека не разобрать |
| однозначных букв нет вовсе (слово целиком из двойников) | решает большинство; поровну — не трогаем |

Пары берутся только **неотличимые на глаз** — 12 заглавных и 7 строчных. Регистры несимметричны,
и это не опечатка: `М`/`M` совпадают, а `м`/`m` — нет; то же с `К`/`k`, `Н`/`h`, `Т`/`t`, `В`/`b`.
Поэтому строчные `b d f g h k l m n q r s t v w z` — надежный признак английского слова.

**Цифры не трогаются никогда**, хотя `0`/`О` и `3`/`З` — те же гомоглифы: обозначения состоят из
букв и цифр вперемешку, и подмена нуля буквой уничтожила бы номер. Решать про цифры можно, только
зная формат обозначения, — это другая задача.

Правка идет в `Collect` **до** `Sort` и `PlanColors` (иначе смысла нет) и касается всех четырех
текстовых полей: `Наименование` и `Обозначение КД` из ячеек, `ФИО` и `Проект` из имени файла.
Итог — `TextFixes` в `CollectedTable`/`CollectResult`: счетчик исправленных значений, счетчик
нерешаемых слов и **поименный список замен в обозначениях**. Поименный потому, что обозначений
мало, они ключ группировки и цена неверной догадки в них выше, чем в наименовании; проверить
правку глазами должно быть можно. Не понравилась — прогон повторяется со снятой галочкой,
а прежний свод цел: результат всегда пишется в новый файл.

> Эта галочка, в отличие от снятой «Ссылка — формулой», настоящая настройка: она МЕНЯЕТ данные,
> и свод «ровно как в расчетах» — законное желание. Удалять ее как мертвую ветку нельзя.

**Всё, что расширение хочет сказать, оно говорит В СВОЕМ ЖУРНАЛЕ.** Ни одной записи в `logs.db`
(и, значит, в «Настройки → Диагностика») оно не делает — `Serilog` тут не подключен вовсе.
Причин две. Расширение обязано удаляться из программы без следов (см. [[extensions]] выше),
а записи в общей диагностике его переживут и станут мусором, который никто не свяжет с исчезнувшей
папкой. И практическая: разбирать прогон удобнее там же, где его запускали, — тому, кто видит
результат в журнале, лезть за второй половиной картины в настройки приложения незачем.

Поэтому в журнал уходит и то, что раньше было «для разработчика»: стек сбоя (`Fail`, см. ниже)
и заметки по готовому листу — `SheetNotes` в `CollectResult`. Заметок две, обе про то, что меняет
результат МОЛЧА (лист выглядит как надо, а ведет себя иначе): сколько строк остались со ссылкой
текстом вместо формулы и какие элементы обвязки шаблона не перенесены. В обычном прогоне обеих
нет, и журнал они не засоряют.

**Маркер `~$` подтверждается пробой.** Сам по себе он ничего не доказывает: остается лежать после
аварийного закрытия Excel и приезжает вместе с копией папки (файл скрытый, копируется молча) — на
скопированной папке таких набирались десятки, и настоящие замечания в них тонули. Поэтому найденный
маркер проверяется попыткой открыть книгу **монопольно** (`FileShare.None`, только для файлов
с маркером — на 3 тыс. расчетов это единицы проб): sharing violation → книга правда занята
(`OpenedByOther`), открылась → маркер осиротел (`StaleLock`). Любая другая ошибка пробы — не ответ
на вопрос «занят ли», и файл остается помеченным как занятый; настоящую причину назовет основное
чтение следом.

`StaleLock` **замечанием не считается** (`FileIssueRank.IsProblem`): строки такого файла полны
и свежи, поэтому он не идет ни в счетчик «с замечаниями» в индикаторе и статусе, ни в текст ошибки
«нечего собирать», а «✅ Все файлы прочитаны без замечаний» печатается и при одних только осиротевших
маркерах.

**Данные чистятся под XML.** Лист — это XML, а в XML 1.0 нет управляющих символов (кроме
табуляции и переводов строки), одиночных суррогатов и `FFFE`/`FFFF`. В расчетах они попадаются
(выгрузки CAD оставляют в наименованиях остатки форматирования), и `XmlWriter` на таком знаке
бросает `ArgumentException` — прогон падал на записи, потеряв все прочитанное за минуты до
конца. `XmlSafe` меняет такой символ на пробел; быстрый путь (`FirstBad`) проходит обычную
строку без единой аллокации, что на 600 тыс. строк важнее краткости. Пара суррогатов —
законный символ вне BMP — сохраняется, режется только половина пары.

**Бесконечность и NaN не идут в лист.** Формально это `double`, и приходят они из ячеек
с переполнением и ошибками формул, но `<v>Infinity</v>` оставляет XML синтаксически целым —
Excel такую книгу объявляет нечитаемой и при «восстановлении» выбрасывает лист ЦЕЛИКОМ
(«часть /xl/worksheets/sheetN.xml с ошибкой XML»). Отсеивает такие значения читатель
(`CalcFileReader.ReadNorm` → пометка `#ЧИСЛО!` вместо числа: строка свода уцелеет, а ошибку
видно), в `WriteNumber` осталась страховка — пустая ячейка со стилем.

**Шапка пишется ячейками во всех трех строках.** Рамка у Excel принадлежит ячейке, а не
диапазону: у объединенной пары `B1:B2` нижний край рисует именно `B2`. Строки 2 и 3 писались
вовсе без ячеек — шапка выходила с оборванными рамками, хотя макрос обводил весь `A1:H3`.
Теперь во всех трех строках стоят ячейки со стилем шапки, в строках 2 и 3 — пустые.

**Предел листа.** `EnsureFits` проверяет до записи, что свод влезает в 1 048 576 строк листа
вместе с тремя строками шапки: файл сверх предела записался бы молча, а Excel открыть его уже
не смог. В тексте отказа — подсказка про выгрузку в коллекцию, у которой предела нет.

**Сбой на записи называет строку и расчет.** Свод склеен из тысяч файлов, и ошибка записи почти
всегда про данные одной ячейки — `WriteDataRows` ловит ее и добавляет «строка N из M (расчет:
имя.xlsm)», иначе виновника в такой куче искать нечем.

**Колонки пишутся ровно восемь.** Диапазоны `cols` шаблона в результат не переносятся:
у Excel они обычно накрывают лист целиком (`min="1" max="16384"`) и запросто перекрывают друг
друга, а раньше каждый разрезался на отдельные колонки — на листе в 158 колонок это давало
тысячи лишних элементов и ДУБЛИКАТЫ диапазонов, из-за которых Excel считает лист поврежденным.
Ширины колонок свода берутся из накрывшего их диапазона (последний выигрывает, как у Excel),
справа от свода колонки пусты и дефолтная ширина им не мешает.

**Куски шаблона пишутся через контекст писателя** (`XElement.WriteTo`), а не сырой строкой:
`ReadOuterXml` тащит за собой префиксы (`x:sheetPr`) и по объявлению `xmlns` на каждом узле.
Формально это тот же неймспейс, но лист с чужими префиксами Excel читает неохотно; объявления
неймспейса листа снимаются при разборе.

**Порядок элементов листа.** Excel читает лист ПО СХЕМЕ (`CT_Worksheet`): элемент не на своем
месте — и книга объявляется нечитаемой, а лист выбрасывается целиком, хотя XML синтаксически
безупречен и наша самопроверка его пропускает. Раньше элементы шаблона писались в их исходном
порядке ПОСЛЕ наших `autoFilter` и `mergeCells`, и любой шаблонный элемент, которому положено
идти раньше (`sheetProtection`, `sortState`, `customSheetViews`), ломал лист. Теперь и наши,
и шаблонные куски складываются в один список и пишутся строго по `SheetOrder`. Список обязан
быть ПОЛНЫМ: `legacyDrawing` (им держатся примечания и кнопки на листе) в нем не значился,
получал ранг неизвестного элемента и уезжал за `tableParts` — лист становился нечитаемым.
Незнакомое имя теперь не переносится вовсе: у листа таких элементов не бывает, а поставить
его правильно все равно некуда. Что не поехало — уходит в журнал расширения: лист от потери
может выглядеть иначе, чем шаблон, и замечать это нужно.

**Объявления с корня листа.** `<worksheet>` шаблона несет не только неймспейс листа: Excel
помечает свои поздние добавки чужими неймспейсами (`xr:uid` на гиперссылках, фильтрах,
примечаниях; `x14ac:` на строках) и разрешает их не замечать списком `mc:Ignorable` — ровно
на корне. Раньше корень собирался заново из двух своих объявлений, и перенесенный из шаблона
элемент приезжал со своим `xmlns:xr="…"`, но без разрешения его игнорировать: Excel считает
такой лист поврежденным, хотя XML безупречен и самопроверка его пропускает. `ReadRoot`
снимает объявления шаблона с корня и переносит их вместе с `mc:Ignorable`.

**Колонка «Ссылка».** Макрос писал туда просто текст `>>>`, формула `HYPERLINK` — наше
дополнение (переход работает и без макросов). Адрес берется в апострофах — `'[путь]Расшифровка'!A15`,
апостроф внутри пути удваивается: без этого ссылка верна только для путей без пробелов, а расчеты
лежат в папках вида «Расшифровка 2025». Рядом с формулой пишется кэш результата (`<v>&gt;&gt;&gt;</v>`):
ячейка объявлена строковой, и без кэша Excel читает лист как неполный.

Записать адрес формулой удается не всегда — этим ведает `LinkTarget`, и `null` от нее означает
«пиши текстом». Мешают две вещи. **Скобки и кавычка** в пути (`BadLinkChars`): первые рвут адрес
книги `[путь]Лист`, вторая — саму строку формулы. **Длина свыше 255 знаков** (`ExcelMaxFormulaText`) —
это предел строковой константы в формуле, куда более жесткий, чем предел ячейки, а адрес
складывается из полного пути к расчету при MAX_PATH в 260. Формулу с константой длиннее Excel
при открытии книги выбрасывает («Удаленные записи: Формула из части /xl/worksheets/sheetN.xml»)
и не говорит, какая ячейка виновата.

В обоих случаях строка получает простой текст `>>>` — переход по ней делает макрос шаблона
(`WsSelectionChanged` → `CalculationLink`, он складывает путь из «Проекта», «Даты» и «ФИО»),
а число таких строк уходит в журнал расширения (`SheetNotes.PlainLinks`): колонка выглядит
одинаково, а работает по-разному.

Переключателя «писать формулой или текстом» в окне нет и быть не должно. Он существовал, пока
искали причину «нечитаемого» свода и формула ходила в подозреваемых; причина оказалась другой
(объявления с корня листа, см. выше). Выключенное состояние ничего не давало: `>>>` и номер
строки в скрытой колонке A пишутся ВСЕГДА, так что макрос шаблона работает при любом раскладе,
и снятая галочка лишь отнимала переход без макросов. А единственный настоящий риск — длинный
путь — разбирается построчно, что строго лучше общего выключателя на весь свод.

**Цепочка вычислений и служебные имена.** `xl/calcChain.xml` в результат НЕ копируется:
она перечисляет ячейки с формулами поименно, а свод меняет их набор целиком — не совпавшая
с листом цепочка и есть самая частая причина «нечитаемого содержимого» у книг, собранных
программой. Вместе с ней убираются `Override` в `[Content_Types].xml` и связь в rels книги:
заявленная, но отсутствующая часть ломает книгу ничуть не меньше. Excel строит цепочку заново
при первом пересчете. По той же причине из `definedNames` удаляется `_xlnm._FilterDatabase`
листа свода — в шаблоне оно указывает на диапазон прошлого свода, а фильтр мы ставим свой.

**Самопроверка результата.** После записи `Verify` прогоняет лист свода XML-парсером — тем же
способом, каким его читает Excel, — и сверяет число строк с ожидаемым. Без нее «нечитаемое
содержимое» всплывало у пользователя через полчаса после прогона и без единой подсказки, где
беда; теперь ошибка называет позицию в XML, номер строки свода и файл расчета, за которым она
стоит. Чтение 150-мегабайтного листа стоит секунды против минут самого прогона.

**Если свод не записался.** Писатель читает шаблон ВСЕ ВРЕМЯ ЗАПИСИ (части книги копируются
из него на лету), поэтому обрыв связи с папкой шаблона выглядит как сбой сохранения — прежний
текст «проверьте права на папку и что файл не открыт в Excel» в этом случае уводил не туда.
`SaveFailure` после сбоя смотрит, что из двух путей пропало, и называет виновника: пропал шаблон —
«стал недоступен во время записи» (сетевой диск на долгом прогоне), пропала папка результата —
она и названа, иначе общий текст плюс подсказка про антивирус (свод несет макросы шаблона).
Исходное исключение уходит в `TimeCollectException.InnerException`, а оттуда — в журнал окна:
`Fail` дописывает его под заголовком «Подробности сбоя (для разработчика)». Без стека от
дружелюбного текста мало толку, а места лучше журнала для него нет — см. ниже.

**Индикатор по фазам.** Выгрузка в Excel: чтение — 0…60 % (счетчик файлов + ETA), очистка листа
и запись строк — до 90 %, оформление — до 97 %; открытие шаблона и сохранение показываются бегущей
полосой (`SetIndeterminate`), чтобы 100 % не выглядели зависшими. Выгрузка в коллекцию: чтение —
0…70 %, запись записей — до 95 %, остаток — раскраска; создание каркаса идет бегущей полосой.
Смена фазы отображается сразу, движение внутри фазы — с троттлингом ~20 раз/сек.

**Выгрузка свода в коллекцию.**
[TimeCollectionWriter](../../../Extensions/TimeCollector/TimeCollectionWriter.cs) — второй приемник
свода. Шаги разнесены так же и по тем же причинам, что у [«Документов в
коллекцию»](#расширение-документы-в-коллекцию): `CreateShell` — коллекция и колонки на **общем**
репозитории (UI-поток, там же срабатывает проверка права `CreateCollection`), `FillRecords` —
записи, значения и раскраска на **отдельном** подключении в фоне (общий `AppDbContext`
принадлежит UI-потоку). Базы берутся через `RelationDbResolver.Databases()` — ту же точку, что и
межбазовые связи; сайдбар обновляется поиском `SidebarTree` в дереве окна-владельца.

Схема коллекции повторяет шапку Excel-свода, но типами свойств, а не текстом:

| Колонка | Тип | Значение |
|---|---|---|
| Наименование | системная колонка записи (`Title`, переименована) | столбец C расчета |
| Обозначение КД | `text` | столбец D без пробелов |
| Тр-ть | `number` | число инвариантной строкой с десятичной запятой; нечисловое значение пишется как есть. Поле заводится с готовым форматом показа: «Число с разрядами», знаков после запятой — «Авто» (`Decimals = -1`), десятичная запятая, разряды не разделяются. «Авто» — потому что трудоемкость приходит из расчетов с разной точностью, и фиксированная врала бы в обе стороны: дописывала бы `12` до `12,00`, будто точность измерена, и резала бы `12,456` |
| Дата | `date` | ISO-канон [DateValue](../../../Core/Models/DateValue.cs) («день целиком»); заводится с `autoCalendar: false` — в календаре колонка не показывается |
| ФИО, Проект | `text` | из имени файла расчета |
| Файл расчета | `file` | абсолютный путь; роль колонки «Ссылка» Excel-свода |

Служебной колонки с номером строки источника здесь нет: она нужна только макросу шаблона для
перехода по `>>>`. Порядок записей — порядок свода, `Position` с шагом 1000 (есть куда вставлять
строки руками). Имя занято — « (2)», « (3)»…, как у имени файла свода; по умолчанию —
«Трудоемкость (ГГГГ-ММ-ДД_ЧЧ-ММ)».

**Раскраска ложится на оформление таблицы**, а не на цвета Excel: заливка строки — в
`record_display` (`SetRowStyle`), пометка расхождения — в `cell_style` ячейки «Тр-ть»
(`SetCellStyle`). Цвета берутся из палитры приложения ([AppPalette](../../../Core/Models/AppPalette.cs)) —
«Желтый» `#FFCC00` и «Красный» `#FF3B30`: в таблице свод выглядит так же, как раскраска,
поставленная руками (приглушение фона — забота отрисовки). Белые строки не красятся вовсе:
«без заливки» и есть дефолт.

- Записи, значения и раскраска пишутся **сырым пакетным путем**, как у импорта:
  `BulkAddRecords` (записи и значения) и `BulkSetRowStyle`/`BulkSetCellStyle` (оформление).
  Пакет — одна транзакция, id записей приходят из самой вставки (`RETURNING Id`) и идут в
  раскраску, журнал изменений получает одну строку с числом записей.
  Публичное поштучное API (`AddRecord` + `SetFieldValue` + `SetRowStyle`), как в «Документах
  в коллекцию», здесь НЕ подходит: оно рассчитано на правку одной ячейки руками и на каждое
  значение делает проверку права, чтение типа поля, поиск прежнего значения, строку журнала и
  свой `SaveChanges` — на своде это ~7 коммитов и 7 строк журнала на КАЖДУЮ строку. Замер на
  600 тыс. строк: 18 строк/с (≈9 часов) против 9 100 строк/с (66 с) — см.
  [[../architecture/performance/hot-paths]].
- Разделитель числа приводится к канону поля прямо в расширении (`NormValue`), а не
  запросом на каждое значение, как это делал `SetFieldValue`: формат поля известен —
  `CreateShell` заводит «Тр-ть» с `NormFormat`, где разделитель десятичная запятая.
- Формат показа «Тр-ть» (`NormFormat` → ConfigJson поля) ставится сразу при создании каркаса:
  трудоемкость приходит из расчетов с разным числом знаков («12», «12,5», «12,456»), и без
  настройки столбец выглядел бы рваным, а пользователю пришлось бы открывать «Изменение
  свойства» после каждого прогона. На хранение формат не влияет (см.
  [NumberFormatValue](../../../Core/Models/NumberFormatValue.cs)), поэтому уже созданные
  коллекции он не меняет — только новые.
- Колонка «Дата» НЕ показывается в календаре: `AddField` включает флаг `IsCalStart` первому
  полю-дате коллекции сам (так ждет тот, кто заводит поле руками), а у свода дата — обычная
  колонка, и календарь заполнялся бы датами расчетов. Гасится параметром `autoCalendar: false`
  того же `AddField`, а не последующим `SetDateFieldVisible`: тот требует права `EditField`,
  которого у создателя коллекции может и не быть.
- Отмена и любая ошибка после создания каркаса удаляют коллекцию целиком (`TryDelete`) — окно
  зовет его из общего `catch`, полупустой коллекции не остается.

**Осознанные отличия от макроса** (проверять при сверке результатов):

- **Сортируются все строки.** В макросе `SetRange A4:H…` шел с `Header:=xlYes`, из-за чего первая
  строка данных считалась заголовком и оставалась приколотой к 4-й строке. Это дефект исходника.
- **Файл, открытый другим пользователем, читается.** Макрос пропускал его целиком
  (`IsFileAvailable` через `Open … Lock Read`); мы читаем данные с диска и помечаем файл в
  журнале — потерять строки хуже, чем показать состояние на момент последнего сохранения.
- **Имя не по образцу — пропуск, а не падение.** Макрос на таком имени падал на преобразовании
  даты и ронял весь прогон.
- **Лист «Настройки» не трогается**: путь к папке живет в настройках расширения. Значит, макрос
  шаблона откроет расчет по `>>>`, только если пользователь заполнил `Настройки!B1` сам — поэтому
  в колонку «Ссылка» кладется еще и формула `HYPERLINK` на файл и строку, работающая без макросов.
- ⚠️ Как у ProductCompare/AssemblyCalc: **макросы** .xlsm сохраняются средствами ClosedXML при
  `SaveAs` — проверить на реальном шаблоне. ClosedXML — DOM-модель, поэтому на десятках тысяч
  строк запись занимает заметное время и память; отсюда фазы прогресса и работающая отмена.

> ⚠️ ExcelDataReader лезет за кодировкой 1252 даже в OpenXml, а legacy-кодировок в .NET из коробки
> нет. `CalcFileReader` зовет `EncodingSetup.Ensure()` сам, не полагаясь на `Program.Main`: иначе
> вне приложения (тестовый хост, консольный харнесс) каждый файл считался бы поврежденным.

Тесты: [Tests/Extensions/TimeCollector/](../../../Tests/Extensions/TimeCollector/) —
`TimeCollectorEngineTests` — чистая
логика (разбор имени, отбор файлов, порядок, раскраска, скрытие колонок);
`TimeCollectorRunTests` —

### Расширение «Регистрация КД»

Выдает конструкторскому документу обозначение по ГОСТ 2.201-80 и заводит строку в журнале
регистрации. От остальных расширений отличается тем, что **пишет в ЧУЖУЮ готовую коллекцию**, а
не создает свою: журнал заводит человек в конструкторе, расширение только дописывает в него
строки. Отсюда две вещи, которых больше нигде нет, — проверка структуры выбранной коллекции и
встроенный справочник.

**Окно** ([DocRegistryWindow](../../../Extensions/DocRegistry/DocRegistryWindow.axaml)) —
ФИО, код организации, список кода ЕСКД, наименование, база и коллекция, четыре необязательных
примечания. После записи окно НЕ закрывается: документы регистрируют пачками, поэтому ФИО, код
организации, база и коллекция остаются, а код, наименование и примечания очищаются под следующий
документ.

Между запусками сохраняется все четыре значения — `ext.doc-registry.…`, объявлены настройками
(`IExtension.Settings`, экран — «Настройки → Расширения»). Заполняются они по-разному:

| Настройка | Кто заполняет |
|---|---|
| Коды организации | человек, руками |
| ФИО | человек; окно подставляет и переписывает после регистрации |
| База данных журнала | окно, при выборе |
| Коллекция журнала регистрации | окно, при выборе |

Последние две объявлены настройками не ради ввода руками, а ради видимости: их можно посмотреть,
очистить или задать заранее на новой машине. Записываются они ТОЛЬКО когда структура коллекции
сошлась (`RememberTarget` в `RefreshShape`) — возвращать в следующий раз выбор, на котором
работать все равно нельзя, незачем.

База восстанавливается по ИМЕНИ, а не по `DbId`: id живет в реестре и после переустановки или
перемонтирования баз может значить другое, а имя человек и видит в списке. Имя не нашлось — берется
первая база (без базы окно бесполезно). Коллекция тоже по имени, но не нашлась — не выбирается
ничего: наугад взятая первая тут же отвечала бы «Вы выбрали неправильную коллекцию» на пустом
месте.

**Список кода ЕСКД — дерево классификатора**, открытое на классах. Уровень показан ТОЧКАМИ,
дополняющими код до шести знаков (`38 ....`, `380 ...`, `380008`), — как в исходной таблице
классификатора. Точки заодно и признак: есть они — строка раскрывается, нет их (шесть цифр) —
строку можно зафиксировать. Отдельного значка раскрытия поэтому нет.

Щелчок и `Enter` делают со строкой одно и то же (`Choose`): шестизначную фиксируют, любую другую
раскрывают. `Esc` возвращает список к классам.

**Состояния «что раскрыто» окно не держит вообще** — всю картину задает одна строка в поле кода.
Раскрыть узел (`Descend`) — это записать его код в поле; список перестроится сам, как если бы код
набрали руками. Оттого и подъем наверх бесплатен: строки цепочки предков раскрываются тем же
щелчком. Выделение после перестройки встает не на первую строку, а на ПЕРВОГО РЕБЕНКА — иначе
`Enter` поднимал бы обратно вместо того, чтобы вести вглубь; так по дереву идут вниз одним
`Enter`.

Ввод слова переключает список в плоскую выдачу поиска по наименованию — там и промежуточные
уровни, так что словом удобно попадать в нужное место дерева: щелчок по найденной строке с
точками откроет ее ветку. `Enter` или щелчок по шестизначной строке фиксируют ее: код и
наименование уходят в поля, а сам список и выделение остаются на месте — список после выбора
намеренно НЕ перестраивается (`_suppressSearch`), иначе плоская выдача схлопнулась бы в ветку и
остальные находки пропали бы.

Рамка и список собраны один в один с окном «Отображение записей»
([RecordDisplayDialog](../../../Controls/Dialogs/RecordDisplayDialog.axaml)): `Padding="0"` и
`ClipToBounds` у рамки, нулевые отступы у `ListBoxItem`, отступы задает содержимое строки. Так
подсветка идет во всю ширину до линии рамки и обрезается по ее скруглению, а полоса прокрутки
встает вплотную к рамке, а не висит в отступе. Цвета — общие: `BrushAccentLight` на выбранной
строке, `BrushSecondaryBg` под курсором.

**Обозначение** ([Designation](../../../Extensions/DocRegistry/Designation.cs)) собирается по
маске `код организации` . `код ЕСКД` . `номер`, например `АБВГ.301121.001`. Номер — **первый
свободный в своей серии**, то есть в пределах пары «организация + код ЕСКД»: заняты 001 и 003 —
документ получит 002, а у другого кода ЕСКД счет снова начнется с 001. Разбор чужих обозначений
устроен так, чтобы не выдать номер дважды: исполнение `…001-01` и приписка `…001 (копия)`
считаются занятым номером 001, а хвост длиннее трех цифр номером не считается вовсе — иначе
`0011` занял бы номер 11 по ошибке разбора.

Номер подбирается **в момент записи**, а не в момент показа: то, что окно пишет в статусе
(«Будет присвоено: …»), — предпросмотр по списку, прочитанному при выборе коллекции. Если тот же
номер успел занять другой регистратор, документ получит следующий свободный.

**Справочник ЕСКД** ([EskdCatalog](../../../Extensions/DocRegistry/EskdCatalog.cs)) — 78 481
строка пяти уровней (43 класса, 290 подклассов, 1 722 группы, 10 240 подгрупп, 66 186 видов),
лежит рядом с расширением сжатым и попадает в сборку встроенным ресурсом
(см. [«Файлы данных расширения»](#файлы-данных-расширения)).

**Дерева в памяти нет — им служит сам файл.** Строки отсортированы по коду как по строке, а это
и есть обход дерева сверху вниз: предок всегда стоит перед потомками, поддерево лежит подряд.
Поэтому `Children` — не обход поддерева (у класса их десять тысяч), а десять бинарных поисков
«код узла плюс цифра», `Chain` — пять таких же, и ни то ни другое не зависит от размера
справочника. Рядом с `All` лежат два служебных массива той же длины и того же порядка: коды
строками для бинарного поиска и свертка наименований к единому виду для поиска по слову. Свертка
считается один раз при загрузке: сворачивать 78 тыс. названий на каждое нажатие клавиши стоило бы
дороже самого поиска.

`View` разбирает введенное и говорит, что показать. **Цифры** — ветка: цепочка предков, узел и
его дети, больше ничего. Введенного кода нет (в классификаторе есть пропуски — 3803 и 3806, к
примеру, не существуют) — открывается ближайшая живая ветка, а `Exact` говорит окну написать
предупреждение; введено меньше двух цифр — просеиваются классы. **Слово** — плоский обход по
готовым сверткам. Отобранное ссылается на ТЕ ЖЕ объекты, что и `All`. Распаковка идет заранее в
фоне при открытии окна, сам подбор — тоже в фоне, а ответ устаревшего запроса отбрасывается по
номеру (человек уже набрал дальше).

**Три дефекта исходных данных** разбираются при загрузке (`Repair`), а не правкой файла — файл
остается честной выгрузкой:

- два промежуточных кода задвоены (4814 и 48414), но это не две строки, а одна, разорванная
  переносом при выгрузке: хвост уехал в конец блока. Хвост приписывается к первой строке. Узел с
  детьми обязан быть один — иначе непонятно, к какому из двух одинаковых кодов дети относятся;
- 26 шестизначных кодов остались без пятизначного родителя (30458x, 30754x, 75045x). Родитель
  достраивается: код известен из кода потомка, наименования в справочнике нет — в списке на его
  месте прочерк. Иначе до этих кодов было бы не добраться ни щелчком, ни вводом;
- пять ШЕСТИЗНАЧНЫХ кодов задвоены с разными наименованиями (337641 — «Браслеты» и «Броши») —
  а вот это чинить нечего: детей у них нет, обе строки видны в списке, выбор за человеком.

**Проверка коллекции** ([RegistrySchema](../../../Extensions/DocRegistry/RegistrySchema.cs)) —
столбцов должно быть ровно восемь и в этом порядке:

| № | Столбец | Что попадает |
|---|---|---|
| 1 | Наименование | наименование ЕСКД; это СИСТЕМНАЯ колонка записи (Title), а не поле |
| 2 | Обозначение | собранное обозначение |
| 3 | Фамилия, имя, отчество | введенное ФИО |
| 4 | Дата регистрации | момент нажатия «Зарегистрировать» (не «весь день») |
| 5 | Тема | необязательное поле окна |
| 6 | Отметка учета | необязательное поле окна |
| 7 | Примечания (первичное применение) | необязательное поле окна |
| 8 | Примечание (краткая характеристика) | необязательное поле окна |

Не сошлось — статус говорит «Вы выбрали неправильную коллекцию» и называет, что именно не так
(«2-й столбец — „Шифр“, а должен быть „Обозначение“»), а кнопка остается выключенной. Сравнение
имен прощает регистр и крайние пробелы, но не прощает порядок: переставленные столбцы означают,
что значения лягут не туда. Порядок колонок
считается как в таблице (`column_meta` перекрывает позиции полей) — повторяет
`ConstructorRepository.GetExportColumns`, но БЕЗ его отсева полей типа «markdown»: экспорту они
не нужны, а проверке нужны, иначе вклинившаяся колонка осталась бы невидимой.

**Запись** ([DocRegistrar](../../../Extensions/DocRegistry/DocRegistrar.cs)) идет синхронно в
UI-потоке на общем репозитории — в отличие от «Документов в коллекцию» и «Сводной трудоемкости»,
где в базу уходят десятки тысяч записей и фон обязателен. Здесь одна запись и семь значений,
заводить отдельное подключение незачем, а на общем репозитории срабатывают проверки прав
(`CreateRecord`/`EditRecord`). Запись дописывается в конец (журнал ведется по порядку выдачи
номеров), пустые примечания строк значений не заводят, а ошибка после создания записи эту запись
убирает: полузаполненная строка хуже, чем никакой, — по ней выдали бы номер повторно.

Дата пишется в каноне ТОГО типа колонки, который в коллекции стоит: обычно это «дата» и канон
`DateValue` с временем, но если колонку завели текстом — пишется `дд.ММ.гггг ЧЧ:мм`, иначе в
журнале оказалась бы ISO-строка вида `2026-08-27T18:23`.

**Тесты** — [Tests/Extensions/DocRegistry/](../../../Tests/Extensions/DocRegistry/):
`DesignationTests` и `EskdCatalogTests` — чистая логика и справочник (в том числе порядок кодов,
на который опирается бинарный поиск, и прибитый состав файла); `RegistrySchemaTests` и
`DocRegistrarTests` — на файловой БД (`TempDatabase`, локальная копия обвязки, как у
`DocsCollection`): отказы по перепутанным, переименованным, лишним и недостающим столбцам,
заполнение всех восьми колонок, нумерация с дыркой, раздельный счет серий, исчерпанная серия,
дописывание в конец и отсутствие следов после отказа.

## Как добавить / удалить расширение

**Добавить:**

1. Создать папку `Extensions/<Имя>/` и класс, реализующий `IExtension`
   (образец — [PdfRename/](../../../Extensions/PdfRename/): контракт + логика без UI + окно).
   Если расширение окна не открывает — `CanRun = false`, `CreateWindow()` → `null`.
2. Зарегистрировать его в `ExtensionRegistry.All`.
3. Если расширению нужно что-то запоминать между запусками — объявить `Settings`
   (см. [«Настройки расширения»](#настройки-расширения)). Поля появятся в разделе
   «Настройки → Расширения» сами — как и галочка в «Отображение раздела расширений»
   (см. [«Какие расширения показывать»](#какие-расширения-показывать)).
4. Завести тесты: папка `Tests/Extensions/<Имя>/` — по проекту на расширение
   (образец — [Tests/Extensions/PdfRename/](../../../Tests/Extensions/PdfRename/), правила —
   [testing/extension-tests.md](../testing/extension-tests.md)). Скрипт прогона берет проекты
   глобом, поэтому править его не нужно.
5. Если расширению нужен свой файл данных — положить его в ту же папку сжатым
   (см. [«Файлы данных расширения»](#файлы-данных-расширения)). Правило в csproj уже есть и
   правки не требует.

**Удалить:** убрать папку расширения, папку его тестов `Tests/Extensions/<Имя>/` и строку
(плюс `using`) из `ExtensionRegistry.All`. Больше нигде ничего править не нужно: ни
`SmartBase.sln` (тестовых проектов расширений там нет), ни скрипт прогона, ни CI списка
расширений не содержат. Раздел, сайдбар, блок, экран настроек и галочки видимости продолжают
работать без изменений — все они строятся из реестра, а не из списков в разметке.

Единственная оговорка — общая обвязка тестов [`Tests/ExtensionsShared/`](../../../Tests/ExtensionsShared/):
если удаленный набор был ПОСЛЕДНИМ ее потребителем, за ним можно убрать и ее. Проверяется одной
командой — `grep -rl ExtensionsShared Tests/Extensions`; пусто, значит потребителей не осталось.

Из `app.db` следы уходят сами при первом запуске: строки `ext.<id>.…`
(`RemoveOrphanExtensionSettings`) и Id в «скрытых» (`PruneHiddenViews` для
`hiddenViews.extensions`) — оба вызова стоят рядом в `App.OnFrameworkInitializationCompleted`.
Вручную остается почистить документацию. Кода это не касается, но расширения называются по
имени не в двух файлах, а в нескольких — проще найти поиском, чем помнить список:

```bash
grep -rn '<Имя>\|<Название расширения>' README.md docs/
```

Обычно это абзац здесь, строка в [../../user/extensions.md](../../user/extensions.md) и дерево
папок в `README.md`; расширение, попавшее в примеры соседних документов (журналирование, горячие
пути, тестирование), назовется там же.

> Если расширение хранит что-то СВОЕ помимо этих двух мест (например, пишет данные в базу
> конструктора, как «Документы в коллекцию», «Сводная трудоемкость» и «Регистрация КД»),
> созданные им коллекции остаются — это данные пользователя, а не след расширения, и удалять их
> молча нельзя. У «Регистрации КД» это особенно важно: журнал регистрации она не создавала, а
> только дописывала в него строки.

**Требования к `Id`:** уникальный в пределах реестра и стабильный между версиями. Он служит
ключом строки сайдбара, приставкой группы настроек и ключом видимости, поэтому переименование
Id равносильно удалению расширения — прежние настройки и его галочка станут осиротевшими и
уберутся при старте.

## В планах

Режим 1 (запуск окна) реализован. Дальше:

- **Точки встраивания (надстройки)** — механизм, которым расширение объявляет, в какие
  блоки оно встраивается (например, «контекстное меню таблицы»), а блок спрашивает у
  реестра подходящие расширения и строит пункты меню. Это дает «подключил/убрал» без
  правок самого блока. Первая цель-пример — пункт «Расширения» в контекстном меню таблицы
  конструктора ([[constructor/table]]).
- **Автообнаружение** папок `Extensions/*` вместо ручной регистрации в реестре.
