# Расширения

## Назначение

Раздел **«Расширения»** — это **список плагинов**, которые подключаются к приложению
и так же легко отключаются. Главная цель — **отделимость**: каждое расширение живёт в
своей папке `Extensions/<Имя>/`, зависит только от интерфейса `IExtension` и ни от чего
больше. Добавить расширение = создать папку с классом и зарегистрировать его; удалить =
убрать папку и одну строку из реестра. Остальное приложение при этом не трогается.

У расширения по задумке **два режима работы**:

1. **Самостоятельный запуск** — кнопкой «Запустить» в навбаре раздела открывается
   **отдельное окно** с функционалом расширения. Окно оформлено в **основном стиле
   приложения** (общие темы/ресурсы), чтобы визуально не отличаться от штатных окон.
2. **Надстройка над блоками приложения** — расширение встраивается в конкретные места
   программы как опция и так же убирается. Пример на будущее: в таблице конструктора в
   **контекстном меню** появляется пункт «Расширения» с выпадающим списком — пользователь
   выбирает расширение, и оно выполняет свою функцию над таблицей (см. [[constructor/table]]).

> Состояние: реализован раздел (сайдбар + блок + контракт `IExtension` + реестр) и
> **режим 1** (запуск окна). Есть шесть расширений — **«Переименование PDF»** (`PdfRename`),
> **«Сравнение составов изделий»** (`ProductCompare`), **«Расчёт сборочных единиц»**
> (`AssemblyCalc`), **«Анализ PDF файлов»** (`PdfAnalyzer`), **«Документы в коллекцию»**
> (`DocsCollection`) и **«Сводная трудоёмкость»** (`TimeCollector`): по «Запустить» каждое
> открывает отдельное окно в стиле приложения. Режим 2 (точки встраивания) — в планах (см. ниже).

## Как работает

### Контракт `IExtension`

Оболочка знает о расширении **только** через интерфейс — это и обеспечивает отделимость:

| Член | Назначение |
|---|---|
| `Id` | стабильный ключ (строка сайдбара, поиск в реестре) |
| `Name` | отображаемое имя — в строке сайдбара и в навбаре блока |
| `MarkdownDescription` | тело блока, рендерится в Markdown |
| `CanRun` | управляет доступностью кнопки «Запустить» |
| `CreateWindow()` | окно расширения (в стиле приложения), которое оболочка показывает поверх главного окна; `null` — расширение окна не открывает |

### Реестр

[ExtensionRegistry](../../../Extensions/ExtensionRegistry.cs) — статический список,
зарегистрированный вручную (`All`). Сайдбар и блок работают только с ним и с
`IExtension`. В перспективе сюда подставляется автообнаружение папок `Extensions/*`
(рефлексия по сборке) — без правок оболочки.

### Раздел в UI

При выборе модуля «Расширения» в Activity bar показывается собственный сайдбар со
списком расширений (панели записи здесь нет). Выбор строки поднимает событие
`CategorySelected(Id)`, и [ExtensionsView](../../../Views/Extensions/ExtensionsView.axaml.cs)
`ShowExtension(id)` ставит в навбар имя, рендерит Markdown-описание и включает/выключает
кнопку «Запустить» по `CanRun`. Пустой/неизвестный `id` → первое расширение из реестра;
пустой реестр → подпись «Нет доступных расширений». Кнопка «Запустить» берёт окно у
`CreateWindow()` и показывает его поверх главного окна (`Window.Show(owner)`).

### Стиль окон расширений

Окно расширения строится из контролов приложения, поэтому **автоматически наследует
основной стиль** (общие темы и ресурсы `Application.Styles`/`StaticResource`) — отдельное
оформление в расширении не объявляется, чтобы окна не отличались от штатных. Пример —
[PdfRenameWindow.axaml](../../../Extensions/PdfRename/PdfRenameWindow.axaml): те же кисти
(`BrushBg`, `BrushAccent`, …), классы кнопок (`accent`/`danger`) и `ConfirmDialog`, что и
в остальном приложении. Базовые ресурсы стиля описаны в [[../ui/theming]].

### Настройки расширения

Расширению бывает нужно запомнить строку между запусками — например, путь к файлу-шаблону.
Механизм устроен так, чтобы **отделимость не пострадала**: ядро хранит значение, но не знает
ни одного расширения по имени.

Расширение объявляет свои настройки списком
[ExtensionSetting](../../../Extensions/ExtensionSetting.cs) в `IExtension.Settings` (по
умолчанию список пуст — большинству расширений объявлять нечего):

```csharp
public const string ExtensionId = "product-compare";
public const string TemplateKey = "template";

public IReadOnlyList<ExtensionSetting> Settings =>
[
    new(TemplateKey, "Файл-шаблон", @"\\server\share\Шаблон….xlsm"),
];
```

Значения хранит оболочка — `AppSettings.LoadExtensionSetting(id, key)` / `Save…` — в `app.db`
под ключом `ext.<id расширения>.<имя настройки>`. Для ядра это просто строка: смысла её оно не
знает, фиксированного списка ключей в [AppSettings.cs](../../../Utils/AppSettings.cs) нет.
Пустое значение стирает ключ (как у пути обновления).

Раздел **Настройки → Расширения** собирается целиком из реестра: `BuildExtensionsPanel`
проходит по `ExtensionRegistry.All`, берёт у каждого расширения `Settings` и строит по одной
строке на расширение. В [SettingsView.axaml](../../../Views/Settings/SettingsView.axaml)
лежит только пустой контейнер — ни одного расширения по имени ни в разметке, ни в code-behind
нет. Панель перестраивается при каждом показе раздела: значение могло смениться мимо этого
экрана.

Заполнить настройку можно и **кнопкой «Обзор» в окне самого расширения** — окно пишет в те же
ключи, поэтому выбранный файл запоминается и подставляется при следующем открытии.

**Уборка после удаления.** На старте (`App.OnFrameworkInitializationCompleted`, сразу после
`AttachStore`) вызывается `AppSettings.RemoveOrphanExtensionSettings` со списком Id из
реестра: строки `ext.<id>.…`, чьего расширения в сборке больше нет, удаляются, число убранных
пишется в журнал. То есть удалили папку и строку реестра, запустили программу — и в `app.db`
не осталось ничего лишнего, руками чистить нечего.

Живым расширение считается по полной приставке `ext.<id>.`, а не разбором ключа: Id с точкой
внутри уборку не сломает, а расширение с похожим началом имени не унесёт чужие настройки
(`pdf-rename` и `pdf-rename-v2` — разные). Ключи вне `ext.` уборка не трогает.

> Обратная сторона: расширение, убранное из реестра **временно** (например, закомментировали
> строку, чтобы вернуть позже), теряет свои настройки при первом же запуске — после возврата
> значения придётся ввести заново. Это осознанный размен в пользу «после удаления не остаётся
> ничего».

**Уникальность Id.** Там же на старте — `ExtensionRegistry.EnsureUniqueIds()`: при
совпадающих Id программа падает с явным сообщением. Иначе ошибка проходила бы молча и ломала
две вещи разом — `FindById` отдавал бы не то расширение, а тёзки делили бы одни настройки
(ключ строится из Id). Уникальность заодно закреплена тестом.

> **Почему не отдельная база данных под расширения.** Отделимость ломает не общее хранилище, а
> знание ядра о конкретных расширениях: метод вида `LoadProductCompareTemplate` в `AppSettings`
> нарушал бы контракт и в отдельном файле БД ровно так же. Отдельный файл при этом стоит
> дорого — второй `DbContext`, свои миграции, бэкап, перенос, блокировки — ради нескольких
> строк. Поэтому значения лежат в `app.db` вместе с остальными настройками, а развязка
> достигнута обобщённым ключом.

Существование файла заранее не проверяется: это делает движок при запуске прогона и возвращает
«Файл-шаблон не найден» — сетевая папка может быть временно недоступна, и блокировать из-за
этого окно незачем.

### Расширение «Переименование PDF»

Пакетно переименовывает PDF-файлы в выбранной папке по правилу **«всё до первого пробела
+ `.pdf`»** (например, `Отчёт 2024 итог.pdf` → `Отчёт.pdf`). Особенности реализации:

- Логика в [PdfRenamer.cs](../../../Extensions/PdfRename/PdfRenamer.cs) — без UI: `BuildPlan`
  (план без изменений) и `Process` (прогон по готовому плану с `IProgress`/`CancellationToken`).
  Учитывает внутрипакетные конфликты (несколько файлов → одно имя) и занятые имена на
  диске — такие файлы **пропускаются**.
- Окно [PdfRenameWindow](../../../Extensions/PdfRename/PdfRenameWindow.axaml.cs): выбор папки
  (`StorageProvider`), «Проверить» (dry-run, ничего не меняет), «Запустить» (с
  подтверждением через [ConfirmDialog](../../../Controls/Dialogs/ConfirmDialog.axaml.cs)) и
  «Остановить» (отмена). Файлы только переименовываются, не удаляются.
- **Масштаб (тысячи файлов).** План строится один раз и в фоне (`Task.Run`); прогон тоже в
  фоне. UI не обновляется на каждый файл: прогресс и журнал идут **с троттлингом** (~20/сек),
  журнал копится в `StringBuilder` и рендерится пачкой, на реальном прогоне в него пишутся
  **только конфликты/ошибки** (успехи — в счётчик/полосу), число строк ограничено. Поэтому
  окно остаётся отзывчивым на десятках тысяч файлов; узким местом остаётся лишь диск/сеть.

Тесты: [Tests/Extensions/PdfRename/](../../../Tests/Extensions/PdfRename/) — правило имени, все
исходы плана (переименуем / нечего менять / три вида конфликта) и применение плана к диску:
режим проверки, отмена, сорвавшееся переименование.

### Расширение «Сравнение составов изделий»

Сравнивает два Excel-состава изделия (старый/новый) и пишет результат в .xlsm-шаблон:
старые данные слева (столбцы 1–5), новые справа (7–11), начиная с 6-й строки; уникальное в
старом — красным, в новом — зелёным; стиль ГОСТ. Реализация на ClosedXML (тот же
стек, что и [[import-export/overview]]).

- Логика в [ProductCompareEngine.cs](../../../Extensions/ProductCompare/ProductCompareEngine.cs)
  — без UI: читает оба файла (ключ строки — иерархия в столбце 2; уникальность — обозначение
  в столбце 11), сортирует и пишет в шаблон через ClosedXML; `IProgress`/`CancellationToken`.
- Окно [ProductCompareWindow](../../../Extensions/ProductCompare/ProductCompareWindow.axaml.cs):
  выбор шаблона/старого/нового файлов и папки результата (`StorageProvider`), индикатор
  готовности, прогон в фоне (`Task.Run`), по завершении — предложение открыть папку через
  [ConfirmDialog](../../../Controls/Dialogs/ConfirmDialog.axaml.cs).
- ⚠️ Допущения порта: используется **первый лист** каждого файла (как «активный» в исходнике);
  **макросы** .xlsm сохраняются средствами ClosedXML при `SaveAs` — проверить на реальном
  шаблоне. Путь к шаблону — объявленная расширением настройка `template` (см.
  [«Настройки расширения»](#настройки-расширения)); доступность файла проверяется при запуске
  (если недоступен — «Файл-шаблон не найден»).

Тесты: [Tests/Extensions/ProductCompare/](../../../Tests/Extensions/ProductCompare/) — точки
отказа и сквозной прогон на собранных в тесте книгах: раскладка «старое слева / новое справа»,
числовой порядок иерархии, заливка уникальных обозначений, стиль ГОСТ, сохранность обвязки шаблона.

### Расширение «Расчёт сборочных единиц»

Переносит выбранные столбцы из исходного «Список КД и ТД» (лист «Исходные данные») в
.xlsm-шаблон (тот же лист), раскрашивает строки по уровню (0–10) и применяет стиль ГОСТ.
Реализация на ClosedXML.

- Логика в [AssemblyCalcEngine.cs](../../../Extensions/AssemblyCalc/AssemblyCalcEngine.cs)
  — без UI: лист берётся **по имени** («Исходные данные»); строки источника читаются с 6-й,
  пока заполнен столбец «Уровень»; уровень → целое + цвет; результат пишется в копию шаблона
  (`SaveAs`, макросы сохраняются). `IProgress`/`CancellationToken`.
- Окно [AssemblyCalcWindow](../../../Extensions/AssemblyCalc/AssemblyCalcWindow.axaml.cs): выбор
  исходного файла, шаблона и папки результата (`StorageProvider`), индикатор готовности,
  прогон в фоне (`Task.Run`), по завершении — предложение открыть папку через
  [ConfirmDialog](../../../Controls/Dialogs/ConfirmDialog.axaml.cs). Путь к шаблону берётся из
  объявленной расширением настройки `template` (см.
  [«Настройки расширения»](#настройки-расширения)); доступность проверяется при запуске.

Тесты: [Tests/Extensions/AssemblyCalc/](../../../Tests/Extensions/AssemblyCalc/) — вся карта
столбцов (включая 248 → 13 «ВЭ»), границы переноса, раскраска по уровню, область очистки
шаблона и перезапись результата в ту же минуту.

### Расширение «Анализ PDF файлов»

По папке с PDF формирует Excel-отчёт (ведомость/опись КД, ПД, ТД): разбирает имена файлов
(номера КД/ПД/ТД по ГОСТ 2.201 / 19.101 / 19.103 + название), считает MD5, число и форматы листов
(по размерам страниц, допуск 30 мм), «листов формата А4», объём.

- [DocumentCodes.cs](../../../Extensions/PdfAnalyzer/DocumentCodes.cs) — справочники кодов
  ЕСКД/ЕСПД и разбор обозначений (регэкспы извлечения номеров, базовый номер, полное
  наименование). В шапке класса — шпаргалка по формированию децимального номера ТД/КД/ПД.
  Только публичные коды ГОСТ — не секрет. Суффиксы листов `-ЛУ`/`-УЛ`
  собираются из типа основного документа + названия листа (напр. `…СБ-ЛУ` → «Сборочный
  чертеж Лист утверждения») для **любого** кода; конкретные комбинации с особым именем
  (`Д42-УЛ` = «Данные программирования…», `ТУ-ЛУ`…) остаются приоритетными исключениями.
  Тип программного документа (ПД) определяется **кодом вида документа** (2-значное поле «ВВ»
  номера `КОДО.РРРРР-ИИ ВВ ДД`, ГОСТ 19.101 → `PdVidCodes`); номер без кода вида — сама
  программа (`Спецификация`). Носители `…НД`/`…НДЗ` берут тип как коды из `KdNameMapping`.
- [PdfAnalyzerEngine.cs](../../../Extensions/PdfAnalyzer/PdfAnalyzerEngine.cs) — обход папки
  (рекурсивно/локально), чтение PDF через **PdfPig** (число страниц + размеры), форматы
  листов, 3 режима сортировки, 6 типов выгрузки (КД и ПД разведены полностью: у каждого своя
  ведомость и опись; отбор строк — `ScopeRows`), запись отчёта в .xlsx (лист «ОПИСЬ») через
  ClosedXML со стилем (Times New Roman, границы, ширины колонок); `IProgress`/`CancellationToken`.
- Окно [PdfAnalyzerWindow](../../../Extensions/PdfAnalyzer/PdfAnalyzerWindow.axaml.cs): папка/отчёт
  (`StorageProvider`), тип выгрузки (`ComboBox`), опции (рекурсия / порядок из папки — взаимно
  исключающие; «наименование в несколько строк» — **вкл по умолчанию**), прогресс по файлам
  в фоне (`Task.Run`), по завершении — статистика + открыть папку.
- Чекбокс «Наименование документа в несколько строк (изделие / тип / лист)» (флаг `splitName`
  в `Run`): раскладывает наименование на части по строкам внутри ячейки через
  `GetDocumentFullNameMultiline` (иначе — одной строкой `GetDocumentFullName`, поведение
  1-в-1). Высота строки в .xlsx подгоняется под число строк ячейки. Влияет на выгрузки с
  наименованием (Ведомость/Опись КД, Ведомость/Опись ПД, Все; в ТД наименование = только
  изделие). Спец. комбинации (`ТУ-ЛУ`…) тоже разносятся: тип и лист разделяются по окончанию
  (`SplitSheetSuffix`).

> ⚠️ Зависимости: это расширение добавляет в общий `SmartBase.csproj` пакет **PdfPig** (чтение
> PDF) и использует **ClosedXML** (Excel). Т.е. расширение, которому нужна внешняя библиотека,
> добавляет NuGet-пакет в проект — в отличие от расширений, обходящихся контролами приложения.

Тесты: [Tests/Extensions/PdfAnalyzer/](../../../Tests/Extensions/PdfAnalyzer/) — разбор
обозначений ЕСКД/ЕСПД и сборка наименования (свыше сотни случаев) плюс сквозной прогон на PDF,
сгенерированных писателем PdfPig: форматы листов, счёт листов А4, состав колонок по типу
выгрузки, отбор КД/ПД, битые файлы.

### Расширение «Документы в коллекцию»

По выбранной папке создаёт **коллекцию конструктора**, где каждая запись — документ. Первое
расширение, которое не выгружает файл, а **пишет в базу** — образец того, как расширение
работает с данными приложения, оставаясь отделимым.

Схема создаваемой коллекции (порядок колонок задаётся `SaveColumnOrder`):

| Колонка | Чем является | Что записывается |
|---|---|---|
| Наименование | системная `Title` (переименована через `SetSystemFieldName`) | имя файла без расширения |
| Название папки | поле типа `text` | имя папки документа |
| Формат файла | поле типа `text` | расширение без точки, нижний регистр |
| Файл | поле типа `file` | абсолютный путь (см. [FileValue](../../../Core/Models/FileValue.cs)) |

- Логика в [DocsCollectionBuilder.cs](../../../Extensions/DocsCollection/DocsCollectionBuilder.cs)
  — без UI, три намеренно разнесённых шага: `Scan` (обход диска, `EnumerationOptions` со
  `IgnoreInaccessible` и пропуском скрытых/системных), `CreateShell` (коллекция + колонки на
  **общем** репозитории — там же срабатывает право `CreateCollection`), `FillRecords` (записи на
  **отдельном** подключении `new AppDbContext(repo.DbPath)` — общий контекст EF принадлежит
  UI-потоку, тот же приём, что у `AddRecordIsolated`/`DeleteCollectionIsolated`).
- Окно [DocsCollectionWindow](../../../Extensions/DocsCollection/DocsCollectionWindow.axaml.cs):
  папка (`StorageProvider`), чекбокс рекурсии, строка расширений-фильтра, выбор базы, прогресс с
  троттлингом (сообщение раз в 25 записей — поток постов в UI тормозит сильнее самой вставки),
  «Остановить». Отмена/ошибка → недособранная коллекция удаляется (`DeleteCollectionIsolated`).
- **Доступ к базам — без правок приложения**: расширение берёт репозиторий через
  [RelationDbResolver](../../../Database/RelationDbResolver.cs) (`Databases()` / `RepoFor(dbId)`),
  а список коллекций в сайдбаре обновляет, найдя `SidebarTree` в визуальном дереве окна-владельца.
  Событие «коллекции изменились» живёт внутри UI и расширению недоступно; поиск по дереву
  обёрнут в try/catch — не нашли, значит коллекция появится при следующем обновлении списка.
- ⚠️ Поле «Файл» создаётся **без** правила авто-привязки ([FileAutoRule](../../../Core/Models/FileAutoRule.cs)):
  правило умеет ровно одну папку (без подпапок) и один формат, чего не хватает при рекурсивном
  обходе и смешанных расширениях. Пути проставляются напрямую, поле остаётся редактируемым.
- ⚠️ Записи создаются публичным API (`AddRecord` + `SetFieldValue`), а не сырым пакетным
  INSERT, как импорт: это даёт запись `Description` (её `ImportStreamedCollection` не пишет),
  но стоит ~3 коммитов и трёх строк журнала изменений на документ. На типовых папках
  (сотни-тысячи файлов) это секунды; для десятков тысяч — минуты, прогон отменяем.

Тесты: [Tests/Extensions/DocsCollection/](../../../Tests/Extensions/DocsCollection/) — обход
папки и фильтр форматов, каркас коллекции (поля, порядок колонок, уникализация имени, право
«Создавать коллекции») и наполнение записями на отдельном подключении.

### Расширение «Сводная трудоёмкость»

Порт макроса `TimeCollector` из книги «_Таблица трудоемкости.xlsm» (пункт **«Обновить»** в
контекстном меню листа «Таблица»): обходит папку с расчётами `*.xlsm`, читает в каждом лист
«Расшифровка» и собирает сводную таблицу трудоёмкости на лист «Таблица» .xlsm-шаблона.
В исходнике путь к папке жил в ячейке `Настройки!B1`, а про непрочитанные файлы было известно
только числом в итоговом `MsgBox` — ради разбора этих файлов расширение и заводилось.

- [CalcFileReader.cs](../../../Extensions/TimeCollector/CalcFileReader.cs) — чтение одного
  расчёта через **ExcelDataReader** (потоково, книга в память не поднимается). Заменяет связку
  ADO/ACE OLEDB: колонки `F1…F11` запроса `SELECT … FROM [Расшифровка$]` — это колонки листа
  A…K, то есть индексы 0…10 ридера. Строка идёт в свод, если заполнены И иерархический номер
  (B), И трудоёмкость (G) — условие 1-в-1 из `GetData`. Обозначение чистится от пробелов;
  в скрытую колонку A кладётся номер строки источника минус единица — ровно то, что читает
  `CalculationLink` при переходе по ссылке.
- [TimeCollectorEngine.cs](../../../Extensions/TimeCollector/TimeCollectorEngine.cs) — обход
  папки (рекурсивно/локально, `EnumerationOptions` со `IgnoreInaccessible`; берутся `*.xlsm`
  с именем **без «$»** — то же условие макроса, оно же отсекает служебные `~$`-файлы),
  **параллельное чтение в 4 потока** (`Parallel.For`; результат каждого файла кладётся в массив
  по его индексу, поэтому порядок сборки не зависит от потоков), разбор имени
  `Проект_ГГГГ.ММ.ДД_ФИО.xlsm`, сортировка и план раскраски. `IProgress`/`CancellationToken`.
- [TimeTableWriter.cs](../../../Extensions/TimeCollector/TimeTableWriter.cs) — запись в копию
  шаблона на **ClosedXML**: очистка листа, шапка с объединениями (`SetHeaderData`), данные с
  4-й строки, границы, высоты, раскраска, скрытие пустых колонок, автофильтр и имя `ALL_DATA`.
- Окно [TimeCollectorWindow](../../../Extensions/TimeCollector/TimeCollectorWindow.axaml.cs):
  папка + рекурсия, шаблон, папка результата (`StorageProvider`, все три пути — объявленные
  расширением настройки `folder`/`template`/`output`), индикатор **по фазам** и журнал во всю
  оставшуюся высоту.

**Раскраска** (`PlanColors`) повторяет `SameProductsSameColor` + `SameNormColor`: цвет
чередуется на каждой смене обозначения (светло-жёлтый ↔ белый), строка без обозначения — белая;
у соседей с одинаковым обозначением и разной трудоёмкостью совпали проект и дата — обе строки
красные, иначе красными становятся только их ячейки «Тр-ть». Красный только добавляется, поэтому
итог считается за один проход **до** записи, а заливка кладётся в файл непрерывными кусками
одного цвета — на десятках тысяч строк вызов на каждую строку в ClosedXML стоит заметно дороже.
`OperationsColor` не переносился: его цикл `For col = 10 To 8` при восьми колонках не выполняется
ни разу (мёртвый код исходника).

**Журнал и проблемные файлы.** Во время прогона журнал молчит: счётчики, текущий файл и оценка
времени ([EtaEstimator](../../../Utils/EtaEstimator.cs), те же формулировки, что у импорта) идут
в индикатор, а замечания выводятся в конце — отсортированными по имени, тремя секциями:

| Секция | Статусы | Как определяется |
|---|---|---|
| ⚠️ Открыты другим пользователем | `OpenedByOther` | рядом лежит `~$<имя>.xlsm`; имя владельца достаётся из него best-effort |
| ❌ Не открылись | `Locked`, `NoAccess`, `Corrupted` | sharing violation (`HResult & 0xFFFF` = `0x20`/`0x21`, как в `ImportErrors.Map`), отказ прав, любая ошибка разбора |
| ⏭️ Пропущены | `NoSheet`, `BadName`, `NoRows` | нет листа «Расшифровка», имя не по образцу, нет подходящих строк |

**Индикатор по фазам.** Чтение — 0…60 % (счётчик файлов + ETA), очистка листа и запись строк —
до 90 %, оформление — до 97 %; открытие шаблона и сохранение показываются бегущей полосой
(`SetIndeterminate`), чтобы 100 % не выглядели зависшими. Смена фазы отображается сразу,
движение внутри фазы — с троттлингом ~20 раз/сек.

**Осознанные отличия от макроса** (проверять при сверке результатов):

- **Сортируются все строки.** В макросе `SetRange A4:H…` шёл с `Header:=xlYes`, из-за чего первая
  строка данных считалась заголовком и оставалась приколотой к 4-й строке. Это дефект исходника.
- **Файл, открытый другим пользователем, читается.** Макрос пропускал его целиком
  (`IsFileAvailable` через `Open … Lock Read`); мы читаем данные с диска и помечаем файл в
  журнале — потерять строки хуже, чем показать состояние на момент последнего сохранения.
- **Имя не по образцу — пропуск, а не падение.** Макрос на таком имени падал на преобразовании
  даты и ронял весь прогон.
- **Лист «Настройки» не трогается**: путь к папке живёт в настройках расширения. Значит, макрос
  шаблона откроет расчёт по `>>>`, только если пользователь заполнил `Настройки!B1` сам — поэтому
  в колонку «Ссылка» кладётся ещё и формула `HYPERLINK` на файл и строку, работающая без макросов.
- ⚠️ Как у ProductCompare/AssemblyCalc: **макросы** .xlsm сохраняются средствами ClosedXML при
  `SaveAs` — проверить на реальном шаблоне. ClosedXML — DOM-модель, поэтому на десятках тысяч
  строк запись занимает заметное время и память; отсюда фазы прогресса и работающая отмена.

> ⚠️ ExcelDataReader лезет за кодировкой 1252 даже в OpenXml, а legacy-кодировок в .NET из коробки
> нет. `CalcFileReader` зовёт `EncodingSetup.Ensure()` сам, не полагаясь на `Program.Main`: иначе
> вне приложения (тестовый хост, консольный харнесс) каждый файл считался бы повреждённым.

Тесты: [Tests/Extensions/TimeCollector/](../../../Tests/Extensions/TimeCollector/) —
`TimeCollectorEngineTests` — чистая
логика (разбор имени, отбор файлов, порядок, раскраска, скрытие колонок);
`TimeCollectorRunTests` —
сквозной прогон на настоящих .xlsm: свод собирается и читается обратно, проверяются шапка,
порядок, раскраска, скрытая колонка, автофильтр, `ALL_DATA`, формулы `HYPERLINK` и разбор
битого файла, файла без листа, имени не по образцу и книги, открытой другим пользователем.

## Как добавить / удалить расширение

**Добавить:**

1. Создать папку `Extensions/<Имя>/` и класс, реализующий `IExtension`
   (образец — [PdfRename/](../../../Extensions/PdfRename/): контракт + логика без UI + окно).
   Если расширение окна не открывает — `CanRun = false`, `CreateWindow()` → `null`.
2. Зарегистрировать его в `ExtensionRegistry.All`.
3. Если расширению нужно что-то запоминать между запусками — объявить `Settings`
   (см. [«Настройки расширения»](#настройки-расширения)). Поля появятся в разделе
   «Настройки → Расширения» сами.
4. Завести тесты: папка `Tests/Extensions/<Имя>/` — по проекту на расширение
   (образец — [Tests/Extensions/PdfRename/](../../../Tests/Extensions/PdfRename/), правила —
   [testing/extension-tests.md](../testing/extension-tests.md)). Скрипт прогона берёт проекты
   глобом, поэтому править его не нужно.

**Удалить:** убрать папку расширения, папку его тестов `Tests/Extensions/<Имя>/` и строку
(плюс `using`) из `ExtensionRegistry.All`. Больше нигде ничего править не нужно: ни
`SmartBase.sln` (тестовых проектов расширений там нет), ни скрипт прогона, ни CI списка
расширений не содержат. Раздел, сайдбар, блок и экран настроек продолжают работать без
изменений, а настройки удалённого расширения уберутся из `app.db` при первом запуске
(см. [«Настройки расширения»](#настройки-расширения)). Вручную остаётся почистить
только документацию — абзац про это расширение здесь и в `docs/user/extensions.md`.

**Требования к `Id`:** уникальный в пределах реестра и стабильный между версиями. Он служит
и ключом строки сайдбара, и приставкой группы настроек, поэтому переименование Id равносильно
удалению расширения — прежние настройки станут осиротевшими и уберутся при старте.

## В планах

Режим 1 (запуск окна) реализован. Дальше:

- **Точки встраивания (надстройки)** — механизм, которым расширение объявляет, в какие
  блоки оно встраивается (например, «контекстное меню таблицы»), а блок спрашивает у
  реестра подходящие расширения и строит пункты меню. Это даёт «подключил/убрал» без
  правок самого блока. Первая цель-пример — пункт «Расширения» в контекстном меню таблицы
  конструктора ([[constructor/table]]).
- **Автообнаружение** папок `Extensions/*` вместо ручной регистрации в реестре.
