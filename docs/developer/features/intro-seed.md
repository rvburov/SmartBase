# Вводный чек-лист первого запуска

## Назначение

На **чистой установке** программа заводит коллекцию «Задачи» с задачами-инструкциями по
своим разделам: календарь, задачи, конструктор, расширения, настройки, профиль. Пустое
окно при первом знакомстве не объясняет, что здесь можно делать, — чек-лист показывает это
на живых данных, которые пользователь тут же правит и удаляет.

Каждая запись заводится как **задача со сроком**, поэтому одна и та же запись видна во всех
трёх разделах сразу: в календаре (событие), в задачах (карточка) и в конструкторе (строка
таблицы). Это и есть главная мысль чек-листа — разделы показывают одни и те же записи с
разных сторон.

## Когда чек-лист появляется

Ровно один раз — и решает **состояние установки**, а не содержимое базы:

| Условие | Где проверяется | Зачем |
|---|---|---|
| В реестре не было ни одной БД | `DatabaseRegistry.Open` — до `EnsureDefault` | после `EnsureDefault` «никогда не запускались» неотличимо от «всё удалили» |
| Файла основной БД нет на диске | там же | app.db мог быть удалён (или не пережить перенос) при живом `database.db` — это база с данными, а не чистый старт |
| Отметки `introSeedDone` в app.db нет | `IntroSeed.RunOnFreshInstall` | одноразовость: ставится ДО наполнения, поэтому прерванный сидинг не доделывается следующим запуском |
| Прав хватает | там же — `CreateCollection`/`CreateRecord`/`CreateField`/`EditRecord` | чек-лист правит схему коллекции, а не только записи |
| В базе нет ни одной коллекции | `IntroSeed.Seed` | вторая линия обороны: файл БД мог появиться в обход реестра |

Любая ошибка записи — предупреждение в диагностический журнал и молчаливый выход: вводные
задачи не условие работы программы и не имеют права сорвать старт.

**Удаление задач их не возвращает.** Пользователь, стерший чек-лист или всю коллекцию,
сделал это осознанно; отметка в app.db уже стоит, и следующий запуск ничего не создаёт.

## Что создаётся

Коллекция «Задачи» (цвет `#007AFF` — он же цвет её событий в календаре) и по задаче на
раздел. Каждая — через `AddTaskRecord`, то есть заполнена целиком:

| Что | Чем становится |
|---|---|
| Название | `Title` записи |
| Срок | поле-дата с `IsCalStart` → событие календаря, 1 час |
| Исполнитель | user-поле с `IsTaskExec` = отображаемое имя текущего пользователя |
| Назначил | user-поле с `IsTaskAssigner` = он же (человек ставит задачи себе) |
| Статус | `status`-поле = «Запланировано» |
| Описание | поле с `IsDescription`, markdown |

Сроки разведены по дням: первая задача — сегодня, дальше по одной в день. Время первой —
**ближайший целый час, но не раньше 10:00**: программу открывают и в середине дня, и
чек-лист не должен встречать пользователя карточкой «Просрочено». Поздний вечер —
единственное исключение, сдвигать уже некуда.

## История

Раньше сидинг жил в календаре (`CalendarControllerView.SeedIfEmpty`) и включался по условию
«в базе нет ни одной записи с датой». Это было не «первый запуск», а «календарь пуст»:

- пользователь, удаливший вводные задачи, получал их обратно следующим стартом;
- база, заведённая до появления чек-листа, могла получить его посреди своих данных;
- вторая и последующие подключённые базы не получали его никогда (проверялась `_dbs[0]`);
- запись шла без `TryWrite` и без проверки прав — на пустой базе у пользователя без прав
  `PermissionDeniedException` летел прямо из инициализации модуля.

Сейчас всё это закрыто переносом решения на уровень установки и старта.
