# ROADMAP — Универсальный конструктор данных

## Видение

Превратить приложение из «календаря с конструктором таблиц» в **универсальный конструктор информационных систем**, в котором пользователь сам собирает под себя:

- **CRM** — клиенты → сделки → контакты → задачи;
- **PLM** — изделия → узлы → детали, управление составом и статусами;
- **Базу знаний** в духе Notion / Obsidian — страницы-документы, ссылки между
  записями, обратные ссылки, граф связей;
- **Любую реляционную предметку** — связи «один-ко-многим» и «многие-ко-многим»
  между пользовательскими коллекциями, агрегаты и вычисляемые поля.

Принцип: **одни данные — много представлений** (таблица, календарь, задачи, страница,
в перспективе kanban/граф), все конструируется без программирования.

      равны `busy_timeout` (одно ожидание вместо двух); потеря проверяет соседей по серверу и

      ошибка UI-потока пишется в crash.log и не закрывает программу. Статус базы — живой

      показано (фильтры, сортировка, человеческие подписи из `ChangeLogLabels`/`LogLabels`);

- [x] Выбор целевой БД в окне записи календаря (когда смонтировано 2+ БД) — и при создании,

      (`CopyFieldValuesByName` — значения по имени поля, без одноименного поля значение отбрасывается;
      `CopyRelationLinksByName` — исходящие связи с пересчетом `TargetDbId`), входящие связи на нее
      обрываются — спрашивается подтверждение. В окне задачи комбобокс БД пока только при создании:
      перенос задачи между БД не поддерживается
- [x] **БД по умолчанию** = текущий `database.db`: всегда открыта, удалить нельзя, полная обратная совместимость
- [x] **Выбор целевой БД в диалогах** создания/изменения коллекций и групп (комбобокс «База данных» над «Расположением»; список «Расположение» перестраивается под выбранную БД)
- [x] **Перенос коллекции/группы между БД** при изменении: быстрый bulk-путь
      `MoveCollectionIsolated`/`MoveGroupIsolated` (`ATTACH` источника + `INSERT…SELECT` на отдельных
      подключениях; при объеме > 20 000 записей — фон с окном прогресса) — поля, записи, значения,
      проекция `calendar_index` **и UI-настройки** (аспекты `column_meta`: порядок, видимость,
      подпись, цвет и ручная ширина колонок; высоты строк, отображение записей) — + удаление
      из исходной, имя уникализируется.
      Копия идет **пакетами** (транзакция приемника на пакет, источник заморожен, маркер
      операции), удаление источника — отдельным подключением (межбазовая транзакция в WAL не
      атомарна) под своим маркером: сбой, пока исходник не тронут, откатывает копию; удаление уже
      началось — копия остается, остаток доудаляет монтирование источника. Связи: перенос коллекции и ветки-группы на обоих провайдерах копирует

## Этап 1б — Один тип «Связь» (решение 21.10.2026) · 3 работы открыто

Пользователь: «один тип свойства — только связь, и в нем все, что касается связи». Три пункта
списка типов («Связь», «Свойство связанной записи», «Итог по связанным записям») путали: показ
свойства цели уже был внутри связи, а вычисляемые столбцы жили отдельно и ломались при ее
удалении. Принцип — не повторять аналоги, а закрыть то, что у них не получилось: настоящие связи
между базами SQLite и PostgreSQL на любом компьютере, условие выбора, которое нельзя обойти,
проверка целостности у самого свойства. Сначала закрываются три дефекта из «Найдено разбором
типа «Связь»» в «Известных дефектах» — на них опирается все остальное.

- [x] **Данные из связанных записей — внутри связи** — сделано 21.10.2026: блок окна связи,
      `SaveRelationDataColumns`, итоги по датам; проверки `RelationDependentsTests`,
      `RelationComputedConfigTests`, стенд `--only relations`. План был: `lookup` и `rollup` уходят из списка
      типов; в окне связи блок строк «свойство цели + что показать» (значение, количество, сумма,
      среднее, минимум, максимум, самая ранняя и самая поздняя дата). Каждая строка — столбец

- [x] `multiselect` — несколько опций из списка; показ текстом через **настраиваемый разделитель**

      (в дропдауне фильтра значение сопоставляется целиком). См.
      [data-types/multiselect.md](developer/architecture/data-types/multiselect.md).
- [x] **Форматы `number`** — обычное/разряды/деньги/проценты (`NumberFormat`/`NumberFormatValue`):
      формат-обертка в `ConfigJson`. Вид/точность/разряды/валюта — только показ (таблица/страница
      записи/фильтр), смена обратима; **десятичный разделитель** (запятая/точка) канонизирует и
      хранение (нормализация на записи + миграция значений при смене настройки). Все — в диалоге
      свойства. Другие обертки над number/url (email/phone/rating/progress/duration) — по надобности.
- [x] `file` — **ссылка** на файл на диске (`FileEditor`): в `db_field_values` хранится
      абсолютный путь строкой или JSON-объект со списком путей, файлы не копируются. Показ — имена
      отдельными синими ссылками (клик — открыть
      через ОС) / «файл не найден» / «Выбрать файл…»; правка — ручной ввод пути + иконка-скрепка
      (системный выбор), неверный путь подсвечивается красным с плашкой.
      Копирование файлов/ручной выбор нескольких/превью — по надобности.
      **Авто-привязка по столбцу** (`FileAutoRule`): файл подбирается из папки по совпадению
      «значение_столбца-источника.формат» (источник — системное «Название» или текстовое поле
      типа `text`; регистр учитывается); есть вложенные папки и частичное совпадение с несколькими
      путями. Значение материализуется в `db_field_values`, ячейка read-only + «папка недоступна»,
      кнопка «Обновить привязку»; большой проход — фоном с прогрессом и отменой.
      См. [data-types/file.md](developer/architecture/data-types/file.md).
- [x] **«Файл»: явное включение и дисковый каталог (21.10.2026).**
      Тумблер **«Автоподстановка файлов»**: новое свойство выключено, старое корректное правило
      включено; выключение сохраняет пути и настройки. Только **«Сохранить»** применяет черновик.
      Каталог строится потоком в локальном пересобираемом SQLite-кеше, без списка всех путей
      в RAM: индекс точного имени, FTS5 `trigram` для кандидатов и обязательная `Ordinal`-проверка.
      Все обходы и запросы из UI — в фоне, с debounce/отменой/свежими контекстами; staging и
      атомарный commit повторно проверяют конфигурацию, снимок источников, прежние file-значения и права.
      Больше 10 000 путей на ячейку или 4 × 1024 × 1024 символов результата — `TooManyMatches`,
      предложение уточнить поиск и сохранение прежних значений без обрезания; недоступность,
      отмена и конфликт также не меняют значения. «Сохранить»/«Обновить привязку» обновляют кеш,
      постоянного watcher нет. Проверки путей — ограниченные, с объединением одинаковых запросов
      и фоновым I/O; inline не более 8 ссылок, все пути — в виртуализированном списке.
      Фильтр проверяет любой полный путь ячейки, варианты — отдельные пути; сортировка по
      показу имен со стабильной keyset-адресацией; старые групповые ключи фильтра сравниваются
      с исходным значением целиком. Проверен headless-стенд на 10 млн синтетических метаданных:
      настоящий SQLite-каталог построен за 63,779 с, пик RSS построения 137,55 МиБ; ввод и
      UI-таймер работают. Это не обход 10 млн физических файлов и не замер пользовательской сети.
      Полные показатели и границы измерения — [file.md](developer/architecture/data-types/file.md#проверка-масштаба-21102026).
- [x] **«Файл»: автоподстановка при создании записи (22.10.2026).**
      `AddRecord`, `AddRecordIsolated` и `AddCalendarRecord` запускают включенные правила с уже
      заполненным источником; пустой источник ждет правки. В UI задания уходят в фон после commit,
      rollback убирает очередь. Нужны прежние `ViewCollection` и `EditRecord`: право только на
      создание сохраняет запись и исходные поля, но автоподбор пропускается. Изолированные
      вставка, привязка, сценарий и `UseIsolated` передают `FileAutoPermissions`; фоновая запись
      повторно проверяет права. Синхронный подбор не читает чужой или нетекстовый источник.
      Переименование через `UpdateRecord` и календарь также обновляет привязку по названию.
      При календарном переносе подбор выполняется после копирования всех значений: старый
      путь не затирает результат, синхронный API и фон применяют одно правило цели.
      Покрытие — `FileAutoCreationTests` и `FileAutoPermissionTests`: создание, выключенное правило,
      commit/rollback, недоступная папка, сохранность значений и отзыв прав. Это описание покрытия,
      а не утверждение о прогоне в конкретной среде.
- [x] `created_at` / `updated_at` — системные read-only поля (+ `created_by` / `updated_by`; вычисляемые типы из аудит-метаданных записи).
- [x] `person` — реализован типом `user` (модуль «Профиль»): выпадающий список

## Масштабирование: цель 10+ млн записей

Анализ August 2026 по фактическому коду. После виртуализации данных, keyset-пагинации
и перевода горячих путей на raw SQL потолок **по записям** поднят до **~10 млн** на
коллекцию: скролл таблицы, календарь, импорт и экспорт этот объем держат (страница keyset —
0,3 мс на любой глубине, прыжок ползунком — ~200 мс; замеры в
[hot-paths.md](developer/architecture/performance/hot-paths.md)). Оговорка: **фильтр
и сортировка** считаются синхронно на UI-потоке — фильтр материализует весь список id
(`GetFilteredRecordIds`), сортировка вдобавок тянет в память всю колонку (`GetColumnValues`);
асинхронных вариантов и бенчмарка на 10 млн для них нет. Потолок **по полям** прежний —
комфортно **~30–100 колонок**: это чисто UI-ограничение (ячейки всех колонок на каждую
видимую строку), меры по БД его не лечат. Ниже — что именно ломается дальше и какими мерами
это лечится. Архитектура (EAV + SQLite) объем выдерживает — проблемы точечные и исправимые.

### Что ломается на 10 млн строк (уровень данных)

1. ✅ **Объем EAV-значений.** Значение = строка в `DbFieldValueEntity` (одна на
   ячейку; таблица WITHOUT ROWID с PK `(RecordId, FieldId)`). 10 млн записей × 1000 полей
   при 10% заполнении = ~1 млрд строк значений. SQLite технически способен,
   EF Core-материализация — нет, поэтому горячие пути уже уведены от нее (мера 5):
   страницы записей — raw SQL (`ReadRecordRows`), импорт — prepared ADO.NET
   (`ImportStreamedCollection`), дубль/перенос/удаление коллекции, поля и записей — bulk-SQL.
   На EF остаются точечная работа (одна запись, схема коллекции) и **значения страницы** —
   пакетный `GetFieldValuesBatch` (`AsNoTracking`, память O(страницы)); им же читает экспорт.
2. ✅ **Составной индекс `(CollectionId, Position)`** добавлен — страница больше не
   пересортировывает всю коллекцию.
3. ✅ **Keyset-пагинация** (`GetRecordsPageAfter`/`GetRecordsPageBefore` — в обе стороны,
   row-value сик `(Position, Id)`; OR-форма LINQ на индекс не ложилась и была O(глубины));
   произвольный прыжок — offset по покрывающему индексу `(CollectionId, Position)`
   (только `Id` в подзапросе, строки читаются лишь для страницы).
4. ✅ **Точечные операции без глобальной перенумерации**: `MoveRecord`/`PositionAfterRecord`/
   дубль/создание берут соседей индексными запросами; номера новых записей выдает
   `AllocatePositions` — при нехватке места раздвигаются не больше 1024 следующих записей
   (26.09.2026: прежний ребаланс всей коллекции на 10 млн записей шел две минуты и выводил
   номера за int). Полный реордер из окна «Отображение» — bulk-SQL.
5. **Строковые `Value`** — равенство-фильтр и сортировка работают (фильтр в SQL), но
   «число > N», «дата в диапазоне» по строкам некорректны и не индексируются типобезопасно
   (→ Этап 4).

### Что ломается на 1000 полей (уровень UI)

6. **Сетка без виртуализации колонок** — решено мерой 9 (25.09.2026). Прежняя
   таблица на `DataGrid` создавала для каждой видимой строки ячейки ВСЕХ
   колонок: 1000 полей × ~40 видимых строк = ~40 000 живых контролов; замер
   09.2026 — первая раскладка **6,4 с против 1,1 с** на 16 колонках, рабочий
   набор **1526 МБ против 213 МБ**, и скрытие колонок в «Отображении» цену
   не снимало (`PopulateCellContent` наполнял ячейку до `IsVisible = false`).
   Своя рисованная сетка рисует только видимое окно строк × колонок,
   контролов у ячеек нет: 1000 колонок открываются за 0,03–0,15 с, кадр
   прокрутки 2–4 мс, ячеек в кадре ~250 при любом числе колонок.

   Сделано раньше и осталось: контекстные меню шапки колонки и карточки
   свойства строятся на правом нажатии, а не заранее на каждую колонку; кеш
   страниц таблицы отмерян в ячейках и считается от окна видимых колонок.
7. **Снап ширин на каждый layout-проход** — ушел вместе с `DataGrid`: ширины
   колонок кладутся на физическую пиксельную сетку целыми квантами при
   построении раскладки (`ColumnLayout.Build`), обход колонок на каждый проход
   разметки не нужен.
8. **Страница записи**: список свойств — рисованная поверхность (26.09.2026, этап 7 плана
   drawn-grid.md, `PropertyList`/`PropertySurface`): карточки рисуются только в окне прокрутки,
   контролов у них нет, редакторы значений — прежние контролы — ставятся под указателем и при
   фокусе; состояние (выделение, ширина колонки названий, цели нижнего блока) в модели.
   Открытие записи на 1000 свойств — 0,32 с холодно и 26–34 мс тепло вместо 9,6 с, 109 объектов
   в дереве вместо 35 тысяч, шаг прокрутки на экран 7–9 мс. Виртуализация контролов
   (`ItemsControl`) была промежуточным шагом: показ карточки с контролом стоил 10–17 мс, экран —
   100–190 мс на каждый шаг прокрутки, поэтому выбран рисунок (решение 38 плана).

### Отрисовка и resize: что НЕ зависит от объема

Отрисовка виртуализирована по строкам: физически существуют только видимые
~30–50 строк, линии сетки рисуются только для них, `VirtualRowList` грузит
данные постранично. Поэтому:

- **линии сетки и resize колонок от числа записей не тормозят** — стоимость
  привязана к видимой области; 10 млн строк влияют только на математику
  скроллбара;
- тормоза при скролле больших коллекций приходят **из БД** (медленные
  страницы) — лечатся мерами 1–5, а не оптимизацией рендера;
- **1000 колонок — чисто UI-проблема**, меры по БД ее не решают; снята своей рисованной
  сеткой (мера 9, план — [drawn-grid.md](developer/architecture/performance/drawn-grid.md)):
  рисуется только окно видимых колонок, значения читаются только для него;
- resize **строк** реализован (`SetRowResizeMode` — ручная/авто высота, `SaveRowHeights`,
  хранение в `ui_row_heights`; раскладка `RowLayout` — арифметика по индексам, O(log n));
- resize **колонок** реализован (`SetColResizeMode` — стандартная/ручная ширина, зоны захвата
  у границ заголовков в самой сетке, `SaveColumnWidths`, хранение в `column_meta.Width`):
  рост колонки уводит соседей вправо с горизонтальной прокруткой, сужение раздает место
  колонкам справа (`ColumnResize`) — см.
  [features/constructor/table.md](developer/features/constructor/table.md).

> (`VirtualRowList` — страницы по 200 строк; до меры 9 ее подавала `DataGrid` обертка
> `VirtualCollectionView`, теперь список читает сама сетка); фоновая подгрузка строк
> (`LoadPageAsync`) и значений фильтра (`GetColumnCountsAsync`) с заглушками «Загрузка…»;
> фильтр/сортировка в SQL (`GetFilteredRecordIds` + список id, с этапа 1 меры 9 — в фоне и
> keyset'ом по индексу) вместо `LoadAllRows`; виртуализация окон «Отображение» записей/свойств
> и списка значений фильтра.
>
> Массовые операции над данными — **в фоне на отдельном подключении**: дубль/удаление/перенос
> коллекций и групп, дубль/удаление свойств и записей
> ([ConstructorRepository.cs](../Database/Repositories/ConstructorRepository.cs)). Общий
> однопоточный `Context` из фона не трогаем: каждая операция берет свежий `AppDbContext`
> и включает `ApplyBulkPerformancePragmas` (кеш ~512 МБ + mmap 2 ГБ — на десятках ГБ глобальные
> индексы `db_field_values`/`calendar_index` не влезают в стандартные 64 МБ, и вставка
> вырождается в случайный I/O). Работа идет пакетами по 10 000 записей: у удаления
> коллекции/группы **каждый пакет — своя транзакция** (одна гигантская держала бы весь объем
> в WAL), у дубля пакеты — только для гранулярности процентов. Окно прогресса: в сайдбаре
> порог ≤ 20 000 записей — мгновенно и без окна, больше — окно с % (`BulkProgressThreshold`);
> у свойств и записей окно отложенное — только если операция не уложилась в ~200 мс. См.
> [changelog.md](developer/architecture/performance/changelog.md).
>
> ¹ Точечные операции (`MoveRecord`, `PositionAfterRecord`, дубль/создание записи) больше не
> грузят и не перенумеровывают всю коллекцию: соседи берутся индексными запросами, при нехватке
> места раздвигаются не больше 1024 следующих записей (`AllocatePositions`), массовый дубль
> хвост не сдвигает; полный реордер из окна «Отображение» — bulk-SQL (`SaveRecordOrder`).
> ² На raw SQL/bulk: страницы таблицы (`ReadRecordRows` — row-value сик `(Position, Id) > (?, ?)`),
> `AllocatePositions`, `SaveRecordOrder`, копия значений в `DuplicateField` (`INSERT … SELECT`),
> `DuplicateCollection` (записи+значения bulk-SQL + фоновый поток), bulk-удаление/дубль записей
> и полей, импорт (`ImportStreamedCollection` — prepared ADO.NET) и экспорт
> (`ReadExportRowsIsolated` — keyset-страницы), перенос между БД
> (`MoveCollectionIsolated`/`MoveGroupIsolated`: SQLite↔SQLite — `ATTACH` + `INSERT … SELECT`,
> пары с PostgreSQL — generic-путь на двух подключениях). Фильтр/подсчет
> (`GetFilteredRecordIds`, `CountRecords`) — EF-запросы без материализации сущностей
> (в SQL уходят id и `COUNT`). Старые EF-методы `ExportCollection`/`ImportCollection`/
> `MoveCollection` остались **легаси** и из UI не вызываются (см.
> [cross-database-move.md](developer/features/import-export/cross-database-move.md)).

### Проверка на 10 млн записей × 1000 свойств (27.09.2026): решено и что требуется к решению

Стенды генератора: `~/TestData/wide10m.db` — 10 млн записей, 1000 свойств всех типов и
вариантов настроек, 31 ГБ; `wide1000full.db` — 100 тыс. записей, заполнены все 1000 свойств,
7,3 ГБ ([test-database.md](developer/testing/test-database.md)). Операции таблицы и боковой
панели меряет стенд `Tests/Sections --only tableops` и `--only sidebarops`: время до результата,
паузы UI-потока, память, размер журнала. Подробно — пятая часть этапа 8 в
[drawn-grid.md](developer/architecture/performance/drawn-grid.md) (решения 61–69), замеры —
[benchmarks.md](developer/testing/benchmarks.md).

**Решено:**

- [x] **Окно фильтра на колонке с тысячами значений** — первые 1000 значений и поиск по базе
      (выбор пользователя), снятое из «всех» значение — отбор «кроме». «Текст» на 10 млн разных
      значений: 105 с, пауза UI 25 с и 6 ГБ памяти → 0,17 с. Колонка до 1000 значений считается по
      индексу без обхода записей: «Список» 26,5 → 7,8 с.
- [x] **Окно «Отображение записей»** держит в памяти только id: названия — порциями для видимых
      строк, состояние — только отличия, поиск по базе, сохранение пишет только отличия. 31,7 с и
      1 ГБ → 4–5 с.
- [x] **Дубль, сдвиг и удаление записи** не пересчитывают 10 млн записей на UI-потоке: пауза
      0,9 с → 0.
- [x] **Журнал базы переносится в файл только в фоне** (`WalCheckpointer`), через 3 с после
      массовой правки: автоперенос SQLite шел внутри коммита случайной мелкой правки интерфейса
      (17 с на UI-потоке после дубля столбца). Столбец на 100 тыс. × 1000: дубль 66 → 8,3 с,
      очистка 27,6 → 8,8 с, вставка 29 → 9,1 с, удаление 23,5 → 6,3 с.
- [x] **Столбец больше 500 тыс. значений — порциями** с переносом журнала между ними. 10 млн
      значений: дубль 10,6 мин, удаление 11,7 мин; журнал до 1,1 ГБ вместо десятков гигабайт;
      самая длинная пауза UI 1,2 и 0,47 с (было 9 и 7 с). Прерванный дубль не оставляет пустой
      столбец.
- [x] **Локальная база не «теряется» под нагрузкой диска**: проба связи ждет минуту (сетевая —

      панели и подключалась заново.

### Боковая панель, перенос с PostgreSQL и резервная копия (19.10.2026): решено и что требуется к решению

Жалоба пользователя: удаление, дублирование и перенос в боковой панели «зависают» и идут
долго, резервная копия программой медленнее копии файла руками. Замеры — стенд
`Tests/Sections --only sidebarops` (с `--shared` — профиль общей базы), `Tests/Benchmarks`
`sidebar`, `backup`, `pgmove` ([benchmarks.md](developer/testing/benchmarks.md)); журнал —
[changelog.md](developer/architecture/performance/changelog.md).

**Решено:**

- [x] **Действия дерева баз — всегда в фоне** (19.10.2026): дубль, удаление и перенос в другую
      базу при любом объеме на отдельных подключениях, окно прогресса — если дольше 400 мс.
      Паузы UI с профилем общей базы: малые действия 150–190 мс → 0, большие — до 68 мс.
- [x] **Действия дерева заметок — в фоне** (19.10.2026): перенос, дубль и удаление в корзину;
      сбой посреди набора больше не оставляет дерево устаревшим.
- [x] **Дубль коллекции — транзакция на пакет** (19.10.2026): одной транзакцией дубль 2 млн
      записей раздувал `-wal` до 9,4 ГБ при базе 2,7 ГБ, а общую базу запирал до конца копии;
      сбой и выход из программы не оставляют недописанной копии (маркер, свип).
- [x] **Перенос SQLite ↔ PostgreSQL** (19.10.2026): в PG — поток `COPY`, в SQLite — prepared-команда
      вместо multi-row `INSERT` с квадратичной привязкой параметров. 300 тыс. записей: PG → SQLite
      3 мин 37 с → 1 мин 37 с, SQLite → PG 3 мин 24 с → 2 мин 17 с.
- [x] **Резервная копия SQLite** (19.10.2026): проверка частями параллельно (полная, как раньше:
      `quick_check` не ловит испорченный индекс), сетевая база — через последовательный снимок на

      целой при ротации. 1,36 ГБ локально: 23,5 → 20,5 с.
- [x] **Дубль и удаление коллекции на миллионы записей** (20.10.2026): записи дубля — своими пакетами
      в зарезервированный блок id, пакет по времени транзакции (8 с локально, 4 с у общей базы),
      проверка внешних ключей на время заливки снята; удаление берет записи пакета первыми по индексу

      больше 512 МБ. Стенд с данными вразнобой (`Tests/DbGenerator --shuffle`): дубль 300 тыс. — 87 →
      35,5 с; дубль 1 млн прежде падал «database or disk is full» (журнал 15,4 ГБ), теперь 4 мин 40 с
      и журнал до 1 ГБ; удаление 1 млн — 5 мин 46 с и 10,7 ГБ журнала → 4 мин 57 с и 0,9 ГБ.
- [x] **PostgreSQL: триггеры `calendar_index` на целый запрос** (20.10.2026, миграция
      `CalendarStatementTriggersPg`): сводки дней и длительностей правятся одним запросом по таблице
      переходов. 1 млн строк проекции: вставка 75 → 10 с, удаление 57 → 1,6 с, перенос дня у 200 тыс.
      — 33 → 2,4 с; на 400 случайных правках сводки совпали с построчными.
- [x] **Перенос между SQLite-базами (`ATTACH`) пакетами** (20.10.2026): своя транзакция приемника на
      пакет вместо одной на всю копию, источник заморожен отдельным подключением, маркер операции.
      Заодно исправлено: сбой удаления источника после того, как его начали удалять, удалял и копию —
      данные пропадали в обеих базах; теперь копия остается, остаток исходника доудаляет монтирование

- [x] **Маркеры недописанных копий с владельцем и временем** (20.10.2026): строка `pending.*` на
      операцию (компьютер, учетка, процесс, последняя отметка, снятие сравнением с прочитанным).
      Монтирование убирает только брошенное: процесс владельца на этом компьютере умер, чужой
      компьютер не отмечался 30 мин (копия одной транзакцией — 6 ч). Маркеры прежних сборок
      убираются, как раньше.

**Требуется к решению:**

- [ ] **Проверить у пользователя на сетевом диске**: резервную копию сетевой базы (снимок на свой
      диск против прежнего чтения вразброс — стенд сетевой диск не воспроизводит; сравнить со
      временем копии файла проводником) и действия боковой панели на общей базе.
- [ ] **Дубль и удаление 1 млн записей с данными вразнобой — все еще минуты** (4 мин 40 с и
      4 мин 57 с): время уходит на вставку и удаление в глобальных индексах
      `IX_db_field_values_FieldId_Value` и `calendar_index`, которые на таком объеме не помещаются в
      кеш. Обходить триггеры SQLite нельзя (решение 47); что можно попробовать — порядок вставки
      значений и проекции по ключу индекса, а не по рангу записи.
- [ ] **Ошибка фонового дубля и переноса в боковой панели видна только в журнале**: дерево баз
      ловит сбой фоновой работы и пишет его в журнал диагностики; сообщение пользователю показано
      только у известных ошибок базы (занята, недоступна) и у прерванной массовой копии (20.10.2026,
      `DbErrors.Handle`). Остальные сбои проходят молча.
- [ ] **Перенос с PostgreSQL-источника не замораживает источник**: копия читает снимок
      (`REPEATABLE READ`), а запись, которую коллега добавил в исходную коллекцию посреди копии,
      удалится вместе с источником. У SQLite-источника окно — только между концом копии и началом
      удаления. Удалять из источника только скопированные записи.
- [ ] **Откат транзакции после сбоя записи прячет настоящую ошибку**: SQLite сам откатывает
      транзакцию при «database or disk is full», и `ROLLBACK` из `Dispose` бросает «cannot rollback - no
      transaction is active» — пользователь и журнал видят ее вместо «диск переполнен». Обход сделан в
      переносе (`InAttachedTx`); нужен общий для транзакций EF.
- [ ] **Окно прогресса долгих операций модальное** — минутная операция закрывает программу. Решение
      пользователя 19.10.2026: окно прогресса оставить; вернуться, если станет мешать (фон без окна
      с индикатором).

### Файл не раздувается: сделано (сентябрь 2026) и что осталось

Общая база в сетевой папке доросла до 1,7 ГБ после нескольких сводов трудоемкости по 650 тыс.
строк: каждый прогон — новая коллекция (≈ 815 байт на запись, ≈ 0,5 ГБ на свод), удаленные
своды оставляли свой объем в свободных страницах (49 % файла), прежний порог автосжатия
«> 50 %» на этом не срабатывал, а сам автоматический `VACUUM` шел и на общей базе через сеть
под замком для всех. Что сделано — [storage-and-migrations.md → «Свободное место, сжатие,
WAL»](developer/architecture/database/storage-and-migrations.md#свободное-место-сжатие-wal):

- ✅ политика свободного места: локальная база ужимается при монтировании (свободно > 64 МБ и
  ≥ 25 % файла, либо > 512 МБ — `DatabaseManager.NeedsCompaction`), общая — никогда сама;
  с 27.09.2026 сама ужимается только база до 4 ГБ живых данных и при месте на диске на два
  объема живых данных, копия сжатия пишется на диск (`VACUUM` базы в 31 ГБ шел больше 10 минут с
  копией в памяти), большой базе — подсказка «стоит сжать» и «Сжать файл»;
  администратору — «Сжать файл» через очередь монтирования (состояние `Maintenance`, процент и
  оценка времени, BUSY → карточка «файл занят») и «Резервная копия…» (`VACUUM INTO` без
  отключения, проверка копии); строка «файл · свободно (%)» в «Управлении базой данных»;
- ✅ Windows не усекает файл после `VACUUM`, пока его держит отображенным в память любое
  другое подключение (в том числе простаивающее в пуле), а у опустевшей базы автоматический
  чекпоинт не запускается — перед `VACUUM` сбрасывается пул, после него явный
  `wal_checkpoint(TRUNCATE)`; тесты проверяют физический размер файла;
- ✅ WAL локальной базы ≤ 64 МБ (`journal_size_limit`); с 27.09.2026 журнал переносит в файл
  только фоновая задача (`WalCheckpointer`: после массовых правок через 3 с и по размеру
  журнала), автоперенос SQLite выключен, огромный столбец коммитится порциями;
  пустые ячейки не хранятся (импорт их пропускает, очистка ячейки удаляет строку);
- ✅ стенды: `dbsize` (состав файла по таблицам, индексам, коллекциям и полям; только чтение —
  годится для настоящей базы), `bloat` (сценарий свода по шагам), профиль `wide` генератора
  (2000 колонок, все типы свойств по одному, разреженное заполнение) —
  [benchmarks.md](developer/testing/benchmarks.md), [test-database.md](developer/testing/test-database.md);
  автотесты `StorageBloatTests`, `PragmaTests`.

- [x] **Первый сигнал прогресса SQLite без гонки (21.10.2026).** Миграция и сжатие
      сообщают начало этапа синхронно, до запуска таймера. Быстрый VACUUM больше не успевает
      закончиться без сообщения; проверка `StorageBloatTests` требует начальный сигнал
      на вызывающем потоке без ожиданий по времени.

Замеры: 1 млн × 2000 × 20 — 2,03 ГБ, 2 179 байт на запись, 115 на значение; таблица значений
и ее индекс `(FieldId, Value)` — 71 % файла поровну (индекс дублирует каждое значение), записи

Осталось (отложено; каждый пункт — отдельное решение по замеру):

- [ ] **`auto_vacuum=INCREMENTAL` для общей базы.** На локальном SSD накладных на вставку и

- [ ] **Стенд 10 млн × 2000 колонок.** 10 млн × 1000 свойств сгенерирован 27.09.2026

      Открытие самой таблицы на тысячах колонок решено мерой 9.
- [ ] **Схема хранения — по отчету `dbsize` с настоящего файла**

      большой таблицы и правка raw SQL репозитория — отдельный трек; аудит `db_records`
      (даты «o» 33 символа → 19, имена → id) — только если записи доминируют в отчете.

## Распространение: уведомления о сторонних компонентах в дистрибутиве

Лицензия проекта — **Apache-2.0** (`LICENSE` в корне), перечень стороннего кода —
`THIRD-PARTY-NOTICES.txt` (собран по фактическому runtime-графу: 100 поставляемых
пакетов, тестовые не входят). Оба файла лежат **только в репозитории**, и в этом
проблема: MIT, BSD и Apache требуют воспроизводить уведомления в **распространяемых
копиях**, а до человека, получившего `SmartBase.exe` на флешке или из сетевой папки,
репозиторий не доезжает. Сейчас `Scripts/{windows,macos,linux}-build.sh` кладут в
`dist/Version <версия>/<rid>/` только сам бинарник и установщик.

Отдельного мотива — `Fizzler 1.2.1` под **LGPL-3.0** — больше нет: пакет приезжал
транзитивно через `Markdown.Avalonia → .Svg → Avalonia.Svg → Svg.Model → Svg.Custom`, а
вместе с собственным рендером markdown вся эта ветка ушла из поставки. Заодно ушел
`Svg.Custom` под Ms-PL. Требования раздела 4 LGPLv3 о «заметном уведомлении с каждой копией»
к приложению больше не применяются; остаются обычные MIT/BSD/Apache — им хватает файла
уведомлений рядом с бинарником.

Два способа, не конфликтующие между собой:

- [ ] **Файл рядом с бинарником** — копирование `THIRD-PARTY-NOTICES.txt` в папку
      результата после `dotnet publish` (три строки, по одной на скрипт сборки; на macOS —
      внутрь бандла, `SmartBase.app/Contents/Resources/`). Дешево, но теряется, если
      отправить получателю ОДИН `SmartBase.exe` — он самодостаточный, соблазн велик.
- [ ] **Экран «Сторонние компоненты»** в разделе «Настройки → О программе» — текст вшит
      в приложение ресурсом. Уведомления физически не могут отстать от программы: куда
      уехал exe, туда и они. Для LGPL-требования о «заметном уведомлении» это аккуратнее
      txt-файла в архиве. Раздел `about` в [SettingsRegistry.cs](../Settings/SettingsRegistry.cs)
      уже есть, панель делается по образцу существующих.

Разумно сделать оба: экран — как основной способ, файл — для тех, кто смотрит дистрибутив,
не запуская программу. Отдельно при первом релизе: приложить `LICENSE` и
`THIRD-PARTY-NOTICES.txt` к самому релизу на GitHub.

## Распространение: подпись кода (SmartScreen / «Неизвестный издатель»)

При запуске `SmartBase.exe` у пользователей Windows появляется предупреждение
SmartScreen («Неизвестный издатель», иногда «Фильтр SmartScreen сейчас недоступен»).
Причина — **`.exe` не подписан** цифровой подписью. В коде приложения **не решается**;
это задача сборки/распространения.

**Важно:**

- **Публиковать программу где-либо не требуется.** Подпись и публикация — разные вещи:
  сертификат применяется к `.exe` локально (`signtool`), а раздавать файл можно как
  угодно (флешка, почта, сетевая папка, прямая ссылка). Microsoft Store — лишь одна из опций.
- **Сертификат от публичного CA — платный** (OV ~$80–300/год, EV ~$300–600/год).
  Бесплатного варианта, убирающего предупреждение для **посторонних** пользователей,
  нет. Самоподписанный сертификат бесплатен, но SmartScreen ему не доверяет.

**Что сделать:**

- [ ] Подписать итоговый `.exe` сертификатом **Authenticode (code signing)** от
      публичного CA (DigiCert / Sectigo / SSL.com / Certum). Самоподписанный
      сертификат SmartScreen **не** устраняет.
  - **EV-сертификат** — мгновенное доверие SmartScreen (предупреждение исчезает
    сразу), но нужен аппаратный/облачный токен (HSM), дороже.
  - **OV-сертификат** — дешевле; имя издателя появится, но SmartScreen еще
    накапливает репутацию (первое время предупреждение может оставаться).
- [ ] Подписывать после `dotnet publish` (single-file exe), с RFC-3161 таймстампом:
      `signtool sign /fd sha256 /tr <timestamp-url> /td sha256 /a SmartBase.exe`.
- [ ] Если появится инсталлятор (Inno Setup / WiX / MSIX) — подписывать и его.
- [ ] Встроить шаг подписи в пайплайн релиза.

**Бесплатно для организации (внутренний контур):** если все пользователи в одном
домене/AD, можно завести **внутренний** code-signing сертификат (своя PKI / AD CS)
и раздать его в «Доверенные издатели» через GPO. На этих машинах предупреждение
пропадет без покупки публичного сертификата. ⚠️ Работает **только** на машинах
организации — для внешних пользователей не годится.

**Если ничего не делать:** окно остается, но программа работает — пользователь может
нажать «Подробнее → Выполнить в любом случае».

**Прочие альтернативы:** публикация через Microsoft Store (MSIX) — SmartScreen не
показывается вообще (но это уже публикация).
