# ROADMAP — Универсальный конструктор данных

## Видение

Превратить приложение из «календаря с конструктором таблиц» в **универсальный конструктор информационных систем**, в котором пользователь сам собирает под себя:

- **CRM** — клиенты → сделки → контакты → задачи;
- **PLM** — изделия → узлы → детали, управление составом и статусами;
- **Базу знаний** в духе Notion / Obsidian — страницы-документы, ссылки между
  записями, обратные ссылки, граф связей;
- **Любую реляционную предметку** — связи «один-ко-многим» и «многие-ко-многим»
  между пользовательскими коллекциями, агрегаты и вычисляемые поля.

Принцип: **одни данные — много представлений** (таблица, календарь, страница,
в перспективе kanban/граф), всё конструируется без программирования.

## Масштабирование: цель 10+ млн записей

Анализ June 2026 по фактическому коду. Текущий комфортный потолок:
**~50–200 тыс. записей** на коллекцию и **~30–100 полей**. Ниже — что именно
ломается дальше и какими мерами это лечится. Архитектура (EAV + SQLite)
объём выдерживает — проблемы точечные и исправимые.

### Что ломается на 10 млн строк (уровень данных)

1. **Объём EAV-значений.** Значение = строка в `DbFieldValueEntity` (одна на
   ячейку). 10 млн записей × 1000 полей при 10% заполнении = ~1 млрд строк
   значений. SQLite технически способен, EF Core-материализация — нет:
   горячие пути переводить на raw SQL.
2. ✅ **Составной индекс `(CollectionId, Position)`** добавлен — страница больше не
   пересортировывает всю коллекцию.
3. ✅ **Keyset-пагинация** (`GetRecordsPageAfter`/`GetRecordsPageBefore` — в обе стороны,
   row-value сик `(Position, Id)`; OR-форма LINQ на индекс не ложилась и была O(глубины));
   произвольный прыжок — offset по покрывающему индексу `(CollectionId, Position)`
   (только `Id` в подзапросе, строки читаются лишь для страницы).
4. ✅ **Точечные операции без глобальной перенумерации**: `MoveRecord`/`PositionAfterRecord`/
   дубль/создание берут соседей индексными запросами; редкий ребаланс и полный реордер —
   bulk-SQL. Истинно дробных позиций (вовсе без ребаланса) пока нет.
5. **Строковые `Value`** — равенство-фильтр и сортировка работают (фильтр в SQL), но
   «число > N», «дата в диапазоне» по строкам некорректны и не индексируются типобезопасно
   (→ Этап 4).

### Что ломается на 1000 полей (уровень UI)

6. **DataGrid без виртуализации колонок** — для каждой видимой строки
   создаются ячейки ВСЕХ колонок: 1000 полей × ~40 видимых строк =
   ~40 000 живых контролов. Открытие — секунды, drag границы колонки —
   рывки (re-layout всех ячеек на каждый пиксель).
7. **Снап-логика ширин** (`TableView.OnGridLayoutUpdated`) обходит все
   колонки на каждый layout-проход.
8. **Страница записи строит все свойства без виртуализации**
   (`RecordPageView.BuildProperties`) — 1000 строк-редакторов.

### Отрисовка и resize: что НЕ зависит от объёма

Отрисовка виртуализирована по строкам: физически существуют только видимые
~30–50 строк, линии сетки рисуются только для них, `VirtualRowList` грузит
данные постранично. Поэтому:

- **линии сетки и resize колонок от числа записей не тормозят** — стоимость
  привязана к видимой области; 10 млн строк влияют только на математику
  скроллбара;
- тормоза при скролле больших коллекций приходят **из БД** (медленные
  страницы) — лечатся мерами 1–5, а не оптимизацией рендера;
- **1000 колонок — чисто UI-проблема**, меры по БД её не решают; решает
  только ограничение видимых колонок (мера 6 ниже);
- resize **строк** сейчас не реализован (`SetRowResizeMode` — заглушка);
  при реализации не хранить высоту на каждую запись (`UiRowHeightEntity`
  per-record не масштабируется) — только per-collection или для избранных.

### Вывод по модели данных

1000 полей в одной коллекции — почти всегда признак неправильной модели:
в реальных CRM/PLM это решается **связями** (Этап 1) — не 1000 колонок у
«Изделия», а коллекции «Параметры», «Детали», «Документы», связанные с ним.
Реалистичная и достижимая цель после мер выше: **миллионы записей × десятки
полей на коллекцию + связи** — покрывает практически любой CRM/PLM-сценарий.

## Распространение: подпись кода (SmartScreen / «Неизвестный издатель»)

При запуске `DataBase.exe` у пользователей Windows появляется предупреждение
SmartScreen («Неизвестный издатель», иногда «Фильтр SmartScreen сейчас недоступен»).
Причина — **`.exe` не подписан** цифровой подписью. В коде приложения **не решается**;
это задача сборки/распространения.

**Важно:**

- **Публиковать программу где-либо не требуется.** Подпись и публикация — разные вещи:
  сертификат применяется к `.exe` локально (`signtool`), а раздавать файл можно как
  угодно (флешка, почта, сетевая папка, прямая ссылка). Microsoft Store — лишь одна из опций.
- **Сертификат от публичного CA — платный** (OV ~$80–300/год, EV ~$300–600/год).
  Бесплатного варианта, убирающего предупреждение для **посторонних** пользователей,
  нет. Самоподписанный сертификат бесплатен, но SmartScreen ему не доверяет.

**Что сделать:**

- [ ] Подписать итоговый `.exe` сертификатом **Authenticode (code signing)** от
      публичного CA (DigiCert / Sectigo / SSL.com / Certum). Самоподписанный
      сертификат SmartScreen **не** устраняет.
  - **EV-сертификат** — мгновенное доверие SmartScreen (предупреждение исчезает
    сразу), но нужен аппаратный/облачный токен (HSM), дороже.
  - **OV-сертификат** — дешевле; имя издателя появится, но SmartScreen ещё
    накапливает репутацию (первое время предупреждение может оставаться).
- [ ] Подписывать после `dotnet publish` (single-file exe), с RFC-3161 таймстампом:
      `signtool sign /fd sha256 /tr <timestamp-url> /td sha256 /a DataBase.exe`.
- [ ] Если появится инсталлятор (Inno Setup / WiX / MSIX) — подписывать и его.
- [ ] Встроить шаг подписи в пайплайн релиза.

**Бесплатно для организации (внутренний контур):** если все пользователи в одном
домене/AD, можно завести **внутренний** code-signing сертификат (своя PKI / AD CS)
и раздать его в «Доверенные издатели» через GPO. На этих машинах предупреждение
пропадёт без покупки публичного сертификата. ⚠️ Работает **только** на машинах
организации — для внешних пользователей не годится.

**Если ничего не делать:** окно остаётся, но программа работает — пользователь может
нажать «Подробнее → Выполнить в любом случае».

**Прочие альтернативы:** публикация через Microsoft Store (MSIX) — SmartScreen не
показывается вообще (но это уже публикация).
