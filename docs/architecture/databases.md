# Хранилище, миграции, пути

## Назначение

Как и где физически лежат данные, как обновляется схема без потери данных и как
читаются/пишутся настройки.

## Два файла SQLite

| Файл | Контекст | Что внутри |
|---|---|---|
| `database.db` | [AppDbContext](../../Database/AppDbContext.cs) | пользовательские данные (коллекции, поля, записи, события календаря) |
| `app.db` | [SystemDbContext](../../Database/SystemDbContext.cs) | системное: реестр БД (`databases`) + настройки (`app_settings`) |

`app.db` — независимое хранилище: никогда не показывается в сайдбаре и не удаляется.

## Пути ([AppSettings](../../Utils/AppSettings.cs))

- **Release:** `%AppData%\Roaming\SmartBase\` (Windows); на Linux/macOS .NET
  `ApplicationData` указывает на `~/.config/SmartBase/`.
- **Debug:** папка `.localdata/` в корне проекта (находится по маркеру
  `SmartBase.csproj`) — изолированно «как venv», переживает `dotnet clean` и снос
  `artifacts/`.

`database.db` → `AppSettings.DbPath`, `app.db` → `AppSettings.SystemDbPath`.

## Миграции схемы (database.db)

Накатываются автоматически при открытии каждой БД в
[DatabaseManager](../../Database/DatabaseManager.cs) (`ApplySchemaMigrations`):

- **Новый файл** — `Migrate()` создаёт БД и применяет все миграции по порядку.
- **Старый файл из времён `EnsureCreated()`** (нет таблицы `__EFMigrationsHistory`,
  но есть `db_records`) — вручную создаётся таблица истории и `InitialCreate`
  помечается как уже применённая, после чего `Migrate()` накатывает только
  недостающие миграции. Так схема обновляется, **не пересоздавая** существующие данные.

Новые правки сущностей → `dotnet ef migrations add ...` → применятся при следующем
запуске. См. также [ROADMAP.md](../ROADMAP.md) и инструменты EF в гайде разработчика.

Перед `Migrate()` снимается протухший замок `__EFMigrationsLock`
(`ClearStaleMigrationsLock`): EF 9 держит строку-замок на время миграции, и убитый
посреди неё процесс оставляет замок навсегда — без очистки следующий запуск висел бы
вечно. Живого мигратора очистка не задевает: он держит файловый write-замок SQLite,
и чужой `DELETE` честно ждёт/падает по `busy_timeout`.

Когда есть ожидающие миграции, перед `Migrate()` разово поднимаются кеш и mmap
(`AppDbContext.ApplyMigrationPragmas`) — table-rebuild миграции на дефолтном кеше
SQLite ~2 МБ шли часами вместо минут; после наката файл ужимается
(`CompactWithProgress`: пересоздания оставляют свободные страницы ниже порога
планового самолечения).

**Тяжёлая SchemaCompact — возобновляемая** (партиал
[DatabaseManager.SchemaCompact.cs](../../Database/DatabaseManager.SchemaCompact.cs)):
EF выполняет миграцию одной транзакцией, и на больших базах (16 ГБ — десятки минут)
выключение программы откатывало всё — обновление могло не завершиться никогда.
Перекладка идёт порциями ~200 тыс. строк с коммитом каждой: выключение в любой
момент теряет максимум последнюю порцию, при следующем запуске процент СРАЗУ
продолжается с места остановки (точка возобновления — хвост новой таблицы по PK,
счётчики в `db_meta` `compact.*`). Конечное состояние задаёт файл миграции
(движок обязан ему следовать!), по завершении миграция помечается применённой в
`__EFMigrationsHistory` (паттерн моста InitialCreate). Финальное сжатие — по флагу
`db_meta compact.vacuum`: VACUUM неделим, но флаг переживает выключение — при
следующем запуске повторится только сжатие. Проверено kill-тестом на стенде
(1,6 ГБ / 12,7 млн значений, убийства на 20/50/80%: продолжение с точного места,
данные сходятся до строки; полный прогон ~50 с — паритет с одной транзакцией).
MainWindow при выходе во время обновления показывает подтверждение с напоминанием,
что прогресс сохранён. Все долгие этапы старта — разовая миграция, VACUUM,
бэкафилл календаря — репортятся через `stage`-колбэк `DatabaseManager.Open`
с живым процентом (гибрид VM-шагов SQLite и прироста журнала, см.
`SqliteStageProgress`) и оценкой времени во второй строке («Обновление «имя»» /
«Сжимаю файл «имя»» + «осталось ≈ N мин») — застывший индикатор неотличим
от зависания, поэтому этапов без движения быть не должно. Потребители колбэка:
сплэш (только дефолтная БД) и статусные строки заглушек в сайдбаре — остальные
базы мигрируют в фоновой очереди [MountQueue](../../Database/MountQueue.cs)
уже после показа окна (см. [multi-database](multi-database.md)), пользователь
ожидания на критическом пути не видит.

> **Правило:** любая миграция должна сохранять данные — никаких затёртых строк.
> Пересоздание таблицы допустимо только с полной перекладкой данных
> (`CREATE … → INSERT … SELECT → DROP → RENAME`, так SQLite меняет PK; пример —
> `SchemaCompact`: слияние трёх таблиц колонок в `column_meta` и перевод
> `db_field_values`/`calendar_index` на `WITHOUT ROWID`). Для app.db — только
> аддитивно (`CREATE TABLE IF NOT EXISTS` / `ALTER ADD`).

> **Правило дешёвых миграций.** Изменения схемы бывают двух классов, и по умолчанию
> разрешён только первый:
> - **дешёвые** — новая таблица, новая колонка (`ADD COLUMN`), новый индекс:
>   выполняются мгновенно или быстро на базе любого размера, пользователь ничего
>   не замечает;
> - **дорогие** — table-rebuild (перекладка всех строк существующей таблицы):
>   на больших базах это минуты ожидания у пользователя при первом запуске.
>
> Дорогая миграция — исключение, и она обязана: иметь письменное обоснование в
> шапке файла миграции; читать источник последовательно (`NOT INDEXED` + внешняя
> сортировка, не по индексу); полагаться на `ApplyMigrationPragmas` (кеш/mmap
> ставятся до `Migrate()`); репортить этап и живой процент на сплэш (рост WAL,
> `StartMigrationProgressReporter`); быть замеренной на большой базе до релиза
> (эталон: `SchemaCompact` — 12,7 млн значений / 1,6 ГБ ≈ 53 с вместе с VACUUM).

### app.db

Создаётся через `EnsureCreated()`; поскольку он не достраивает таблицы в уже
существующем файле, недостающая `app_settings` добавляется аддитивно при открытии
(`EnsureSettingsTable` в [DatabaseRegistry](../../Database/DatabaseRegistry.cs)).

## Режимы журнала: WAL локально, DELETE на сетевых путях

Локальные БД работают в `PRAGMA journal_mode=WAL` — параллельные чтения во время
записи и быстрые коммиты (рядом с файлом появляются `*.db-wal` / `*.db-shm`).

Файлы на **сетевых путях** ([NetworkPath](../../Database/NetworkPath.cs): UNC/сетевой
диск на Windows, `/Volumes/…` на macOS, cifs/nfs/sshfs по `/proc/mounts` на Linux;
сомнение трактуется как «сеть») открываются в `journal_mode=DELETE`. Важно: SQLite
**не** отказывается ставить WAL на SMB/NFS — он ставится, но когерентность разделяемой
памяти `-shm` между машинами молча ломается, и одновременная работа с разных
компьютеров портит файл. Поэтому `DatabaseManager.ApplyJournalMode` активно
конвертирует журнал по типу пути (созданный локально файл несёт WAL в заголовке —
первое открытие с шары переводит его в DELETE; если WAL держит старая версия
приложения — монтирование честно падает со статусом «недоступна»).

Профиль прагм тоже ветвится по типу пути внутри `AppDbContext.ApplyPerformancePragmas`
(все фоновые `new AppDbContext(path)` получают его автоматически): на сети —
`busy_timeout=15000`, `synchronous=FULL` (NORMAL в rollback-режиме рискует файлом при
сбое питания сервера), `mmap_size=0` (mmap поверх сетевой ФС не рекомендован SQLite).
Проверяется стендом `Tests/MultiUserHarness --check-pragmas`. Про совместную работу
нескольких пользователей — [multi-database](multi-database.md).

## Настройки приложения

`DatabaseRegistry` реализует `IAppSettingsStore` (Get/Set по ключу поверх
`app_settings`). [AppSettings](../../Utils/AppSettings.cs) даёт типизированный доступ:
масштаб интерфейса (`scale`), состояние и ширина правой панели записи
(`recordPanelOpen`, `recordPanelWidth`). Контекст app.db живёт всё время работы
приложения, поэтому настройки читаются/пишутся через него.

## Провайдеры

Сейчас только SQLite. `DatabaseManager` спроектирован как единая точка открытия БД,
чтобы ветку под PostgreSQL добавить здесь же, не переписывая вызывающий код.
