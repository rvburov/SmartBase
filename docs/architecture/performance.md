# Производительность

Сквозной обзор: где приложение чувствительно к объёму данных, какие приёмы держат
скорость и какие узкие места ещё открыты. Детали по конкретным фичам — в их
документах (подраздел «Производительность»); здесь — общая картина и принципы.

## Принципы

1. **Границы по содержимому, а не по форматированию.** Размер обрабатываемых данных
   считается по реально непустым ячейкам, а не по «следам» форматирования или
   набивке пустыми полями. Иначе объём раздувается на порядки (см. импорт).
2. **Виртуализация вместо «всё в память».** Большие таблицы грузятся постранично из
   БД; в памяти держится ограниченное окно строк, а не вся коллекция.
3. **Батч-операции вместо по-записных.** Массовая вставка идёт пачками в одной
   транзакции, с отключённым авто-отслеживанием изменений EF.
4. **Запросы по индексам и диапазонам.** Выборки фильтруются/сортируются по индексам
   и берут только нужный срез, а не «всё подряд» с последующей фильтрацией в памяти.
5. **Фоновая работа с БД — только на отдельном подключении.** Общий `AppDbContext`
   ([DatabaseManager](../../Database/DatabaseManager.cs)) один на смонтированную БД и его
   делят ВСЕ репозитории (конструктор, календарь, категории). Он не потокобезопасен:
   обращение к нему с фонового потока, пока им же пользуется UI (дерево/календарь), валит EF
   («A second operation was started on this context instance»). Поэтому любая тяжёлая операция
   с потока (импорт, копирование дубля, подгрузка страниц/значений) создаёт **свежий**
   `new AppDbContext(db.DbPath)`; WAL + `busy_timeout` дают параллельность без `SQLITE_BUSY`.
   Общий контекст трогаем строго из UI-потока.

### Таблица коллекции

**Avalonia DataGrid не умеет виртуализацию данных.** Если в `ItemsSource` положить
обычный список (даже ленивый `IList`), `DataGridCollectionView` в конструкторе
перебирает источник **целиком** → на 100k+ открытие занимает минуты. Обход:
[VirtualCollectionView](../../ViewModels/ConstructorDb/VirtualCollectionView.cs)
реализует `IDataGridCollectionView` + `IList` — такой источник DataGrid берёт **как есть,
без копирования** и запрашивает строки **по индексу только для видимых** (презентер строк
UI-виртуализирован).

Данные тянет [VirtualRowList](../../ViewModels/ConstructorDb/VirtualRowList.cs)
постранично (страница — 200 строк, в кеше до 50 страниц ≈10k с LRU):
- `Count` — из `CountRecords` без загрузки строк;
- последовательный скролл — **keyset** (`GetRecordsPageAfter`, `WHERE (Position, Id) >
  курсор`): O(take), не зависит от глубины;
- произвольный прыжок по скроллбару — offset (`GetRecordsPage`, `Skip/Take`), но по
  составному индексу `(CollectionId, Position)` это быстрый индексный скан;
- значения страницы — один пакетный запрос (`GetFieldValuesBatch`, `IN` по индексу
  `(RecordId, FieldId)`).

Подгрузка строк идёт в **фоновом потоке** (`LoadPageAsync` — отдельное read-only
подключение, WAL допускает параллельное чтение): строки сразу показывают «Загрузка…»
(`TableRowVm.IsLoading`), данные приходят и заполняют их на UI-потоке (`Fill`) → ноль
микроподвисаний при скролле. Параллелизм ограничен семафором; загрузки, устаревшие после
`Reset` (правка/перезагрузка), отбрасываются по счётчику поколений, а загрузки страниц,
вытесненных из кеша при быстром скролле, пропускаются (проверка `_pending`/`_pages` после
семафора) — чтобы страница, на которой пользователь остановился, грузилась без очереди из
устаревших. Флаг «Фоновая подгрузка строк» (Настройки → Общие, по умолчанию вкл) переключает
на синхронный путь.

> **Важно (Avalonia).** `Fill` уведомляет об изменении ячеек через `OnPropertyChanged("Item")`
> — именно имя индексатора. Привязка `Binding("[key]")` обновляется только по нему;
> WPF-стиль `"Item[key]"` Avalonia игнорирует (`ReflectionIndexerNode.ShouldUpdate`), и тогда
> «Загрузка…» не сменялась бы данными на месте, только при пересоздании ячейки скроллом.

### Фильтр и сортировка

При активном фильтре/сортировке таблица **не грузит все строки в память**. Фильтр уходит
в SQL (`GetFilteredRecordIds` — EAV-условия через `EXISTS`/`IN`, пустые значения учтены),
возвращает только id совпавших записей в порядке `Position`; сортировка применяется тем же
компаратором по значениям **одной** колонки (`GetColumnValues`). Показ виртуализируется по
списку id (`VirtualRowList` в режиме списка id + `GetRecordsByIdsOrdered`).

Выпадающий список значений в заголовке открывается **мгновенно**: значения считаются
SQL-агрегатом (`GetFieldValueCounts` / `GetTitleCounts` / `GetDescriptionCounts`, GROUP BY
по индексу `(FieldId, Value)`) на **фоновом потоке** (`GetColumnCountsAsync`), до прихода —
«Загрузка…». Значения идут в **порядке таблицы** (по `MIN(Position)`), «(Пусто)» — в конце;
список **виртуализирован** (`ListBox`), показываются все уникальные значения без лимита.

Старый материализованный путь (`LoadAllRows` — все строки в память) остаётся только как
fallback при **выключенной** виртуализации.

Подробнее: [[../features/constructor-db/tables]].

### Импорт таблиц

[ExcelImporter](../../Core/Importers/ExcelImporter.cs):
- Excel — заполненные ячейки читаются одним проходом `RangeUsed().CellsUsed()` в
  словарь (быстрее, чем `sheet.Cell(r,c)` в цикле, и без материализации пустых).
- Границы (`lastCol`/`lastRow`) берутся по **реальному непустому содержимому**, а не
  по адресу `RangeUsed` (Excel) и не по максимальной длине строки (CSV). Без этого
  хвост пустых столбцов превращал 526×10 в ~1 млн пустых значений полей.

`ImportExcelCollection` (в [ConstructorRepository](../../Database/Repositories/ConstructorRepository.cs)):
записи и значения пишутся **сырым ADO.NET** через подготовленные `INSERT` (prepared, переиспользуемые
параметры) в одной транзакции — НЕ через EF. EF на каждую из миллионов сущностей тратит построение
графа и чтение сгенерированного Id → импорт 425k×N колонок деградирует до минут (≈60× медленнее).
Сырой путь — секунды (бенч: 300k значений с двумя индексами ≈0.7 с). Id новых записей идут непрерывным
блоком (импорт — единственный писатель в транзакции), поэтому `RecordId` значения = `firstNew + индекс
строки` (`firstNew = last_insert_rowid − число_записей + 1`), как в bulk-копии дубля. Сама коллекция и
колонки (их мало) создаются через EF. Импорт идёт на **отдельном** контексте (`ImportExcelCollectionIsolated`,
см. принцип 5) на фоновом потоке.

Подробнее: [[../features/import-export]].

### Календарь

Календарь поддерживает **несколько дат на запись** (любое число полей-дат коллекции с
флагом `IsCalStart` показываются как отдельные события). Чтобы это масштабировалось, как
таблица, события материализуются в индексную таблицу-проекцию **`calendar_index`** (строка
на запись × видимое поле-дата: `RecordId, FieldId, CollectionId, StartIso, EndIso, AllDay`).

`GetCalendarRecordsByRange(start, end)` → `ReadCalendarEvents` читает из `calendar_index`
индексным range-query по `(CollectionId, StartIso)`: `StartIso < конец` И `EndIso >= начало`
(ISO-строки сравниваются лексикографически). Трогаются только события окна, а не все значения —
прежний путь (скан `db_field_values` с разбором в C#) был тяжёл на больших коллекциях.

Проекция поддерживается **инкрементально** (не пересобирается целиком на каждый чих):
upsert одной строки при правке значения (`SyncCalendarIndexValue` из
`SetFieldValue`/`SetCalendarDateValue`); пересбор поля при тумблере видимости/смене типа
(`RebuildCalendarIndexForField`); пересбор коллекции/записи при дубле и переносе между БД;
удаления — каскадом по FK (`ON DELETE CASCADE` + `PRAGMA foreign_keys=ON`). Однократный
потоковый бэкафилл (keyset + пакетный prepared `INSERT`, как импорт) в
`MigrateAndBackfillCalendarDates`, если проекция пуста.

> Колонки `db_records.StartDt/EndDt` остались от модели «одна дата на запись» и больше
> не читаются календарём.

## Индексы БД

Текущие индексы на «данных» (см. [AppDbContextModelSnapshot](../../Database/Migrations/AppDbContextModelSnapshot.cs)):

| Таблица | Индекс | Назначение |
|---|---|---|
| `db_records` | `(CollectionId, Position)` | записи коллекции в порядке отображения (страницы, keyset) |
| `db_field_values` | `(RecordId, FieldId)` UNIQUE, `(FieldId, Value)` | значения записи / фильтр и подсчёт по значению поля |
| `calendar_index` | `(RecordId, FieldId)` PK, `(CollectionId, StartIso)`, `(FieldId)` | проекция событий: range-query окна календаря / FK-каскады |
| `db_fields` | `(CollectionId, Name)` UNIQUE | поля коллекции, уникальность имени |
| `db_collections` | `(GroupId)` | коллекции группы |
| `db_groups` | `(ParentId)` | дерево групп |

Миграции применяются автоматически при монтировании БД (`db.Database.Migrate()` в
[DatabaseManager](../../Database/DatabaseManager.cs)); см. [[databases]]. Прагмы скорости
([DatabaseManager](../../Database/DatabaseManager.cs)): `journal_mode=WAL` (параллельные
чтения во время записи), `synchronous=NORMAL` (быстрее коммиты при WAL), `temp_store=MEMORY`,
`mmap_size=256MB`, `cache_size≈64MB`.

## Сделано (перф-итерация June 2026)

- ✅ Составной индекс `db_records(CollectionId, Position)` — убрал пересортировку коллекции
  на каждый запрос страницы.
- ✅ Keyset-пагинация (`GetRecordsPageAfter`) для последовательного скролла.
- ✅ Виртуализация данных DataGrid через `VirtualCollectionView : IDataGridCollectionView`
  (подтверждено: stock `DataGridCollectionView` материализует источник; кастомный — нет).
- ✅ Фоновая подгрузка строк (`LoadPageAsync`) и значений фильтра (`GetColumnCountsAsync`)
  с заглушками «Загрузка…».
- ✅ Фильтр/сортировка в SQL вместо `LoadAllRows`; индекс `db_field_values(FieldId, Value)`.
- ✅ Тяжёлые операции мимо EF-материализации на raw SQL: `RenumberPositions`,
  `SaveRecordOrder` (temp-таблица), копирование значений в `DuplicateField` (`INSERT … SELECT`);
  `MoveRecord`/`PositionAfterRecord` — соседи индексными запросами, без загрузки всей коллекции.
- ✅ Дубль коллекции — bulk-SQL + окно прогресса для больших, мгновенно для малых.
  `CopyCollectionData` (одна транзакция): **все записи одним `INSERT … SELECT … ORDER BY Position, Id`**
  (`firstNew = last_insert_rowid − recCount + 1`), затем значения **крупными пакетами (10 000 записей),
  ВСЕ поля за один `INSERT`** через временную карту полей `_dup_fmap` (old→new fid по `Position`);
  новый `RecordId = firstNew + processed + локальный ранг(ROW_NUMBER) − 1`. Пакеты — только для
  гранулярности процентов. Бенч (iCloud, 2M значений): **4.7–5.0 с против 16.8 с** у прежнего варианта
  «мелкие пакеты по 2000 × по одному полю с `ROW_NUMBER` на каждом» (≈3.4× быстрее, сравнимо с импортом).
  Дубль — **ПОЛНАЯ копия**: после записей/значений `CopyDuplicatedUi` (в той же транзакции) копирует и
  UI-настройки (ширины/порядок/видимость колонок, высоты/видимость строк, режим просмотра, подписи системных
  колонок) — id полей через `_dup_fmap`, id записей по рангу `(Position, Id)`; колонка-/коллекция-level
  копируется даже для пустой коллекции. Зеркало `CopyMovedUi` (перенос в другую БД). Раньше дубль в той же
  БД UI НЕ переносил (только cross-БД перенос).
  UI-поток (`Sidebar.DuplicateSelectionOrNode`):
  считает суммарное число записей по выделению; **≤ 20 000 — копирует синхронно мгновенно без окна**;
  **больше — окно прогресса с % (как импорт)**, копии идут ПО ОЧЕРЕДИ в фоне на отдельных подключениях
  (`DuplicateCollectionIsolated` → свежий `AppDbContext`, не трогает общий — см. принцип 5), проценты —
  общий прогресс по всем целям (`IProgress<int>` → `Dispatcher.UIThread.Post`). Работает и для
  мультивыбора, и для **групп** (дубль группы СО ВСЕЙ веткой: `DuplicateGroupCore`/`DuplicateGroupIsolated`
  — структуру групп и шеллы коллекций создаёт EF, данные каждой коллекции копирует тем же `CopyCollectionData`;
  верхняя группа получает «(копия)», вложенное — свои имена; индикатор показывает «Коллекций: X · Записей: Y»).
  По завершении — `ReloadAndNotify` + показ результата (коллекцию открыть, группу раскрыть; для одной цели).
  Прежний дубль группы создавал ПУСТУЮ копию (без вложений); ещё раньше дубль коллекции шёл по-записно через
  EF (2× `SaveChanges` на запись), зависание 5–10 с.
- ✅ Удаление коллекций И групп — по аналогии с дублем: не блокирует UI, с окном прогресса. `Sidebar.DeleteNodes`
  после подтверждения считает суммарное число записей (для группы — по ВСЕЙ ветке, `CountGroupSubtree`);
  **≤ 20 000 — синхронно мгновенно** (`DeleteCollection`/`DeleteGroup`, каскадный DELETE); **больше — окно
  прогресса с %** (`Title="Удаление"`; при группах строка «Коллекций: X · Записей: Y», иначе «Количество
  записей: N»), удаление ПО ОЧЕРЕДИ в фоне на отдельных подключениях (`DeleteCollectionIsolated`/
  `DeleteGroupIsolated` → свежий `AppDbContext`). Записи удаляются ПАКЕТАМИ по 10 000 (значения уходят каскадом
  по FK), затем строки коллекций (каскад — поля), затем строки групп ветки (`DeleteGroupData`: `ParentId` —
  SET NULL, не каскад, поэтому набор групп удаляем явно); пакеты — только ради процентов (по SQL та же работа,
  ≈5 с/2 млн значений). Каскад держится на `PRAGMA foreign_keys=ON` (в `ApplyPerformancePragmas` на каждом
  подключении — иначе записи/значения «осиротели» бы). Раньше группы удалялись синхронно на UI-потоке через EF
  (фриз на больших ветках, без индикатора).
- ✅ Перенос коллекции И группы (контекстное меню «Расположение», окно `LocationDialog` — БД + расположение,
  без названия; для коллекции расположение = её группа, для группы = родитель; мультивыбор, как дубль/удаление;
  ветки перемещаемых групп исключены из назначения — нельзя вложить в себя/потомка). **В той же БД — мгновенно**
  (коллекция: `UPDATE GroupId`; группа: `UPDATE ParentId` — ветка/записи на месте). **Перенос в другую БД** —
  `MoveCollectionIsolated`/`MoveGroupIsolated`: на подключении ЦЕЛЕВОЙ БД делаем `ATTACH src` и копируем bulk-ом
  `INSERT … SELECT` из присоединённого файла (записи одним INSERT в порядке `Position,Id`, значения крупными
  пакетами через temp-карту полей `_move_fmap`; id полей по `Position`, id записей по рангу `Position,Id` →
  `firstNew + ранг − 1`; ключи `column_order/display` — числовой → новый id поля, системные как есть; UI
  переносится). Группа: сначала структура групп (`CloneGroupTreeAttached`, имена через `INSERT…SELECT`), затем
  все коллекции ветки по очереди в одной транзакции с общим %. Затем удаление источника на ОТДЕЛЬНОМ подключении
  (каскад). **≤ 20 000 записей суммарно — синхронно мгновенно, больше — окно прогресса** (`Title="Перемещение"`;
  при группах «Коллекций: X · Записей: Y») + фон. **Индикатор покрывает ОБЕ фазы**: на цель 2× записей — копия
  это 0..Records (фаза «Перемещение…»), удаление исходника Records..2·Records (фаза «Удаление из исходной базы…»,
  через `BaseProgress`-сдвиг на `Move*Isolated`). Иначе бар замирал на 100% на всё время удаления (каскад
  записей/значений — минуты). Копия и удаление раздельны (в WAL межбазовая транзакция не
  атомарна) с компенсацией (при сбое удаления — откат копии). ≈5 с/2 млн значений (как дубль). Раньше — EF-снимок
  в память + по-записная вставка (минуты, без индикатора). Тот же быстрый путь использует и **смена БД из окна
  «Изменить»** (`EditCollection`/`EditGroup`): кросс-БД перенос и «Расположение» делят общий помощник
  `Sidebar.MoveNodesCrossDb` (порог/прогресс/фон); новое имя из диалога применяется на цели после переноса
  (быстрый путь копирует имя как есть). Раньше «Изменить» шло через статические `MoveCollection`/`MoveGroup`
  (EF-снимок в память, минуты, без индикатора). **Конфликт имён в целевой группе/уровне** обрабатывается
  по-разному в зависимости от наличия поля имени: **«Расположение»** (контекстное меню, без ввода имени) при
  совпадении даёт «(копия)»/«(копия) N» — как дубль (`UniqueCollectionName`/`UniqueGroupName` → `NextCopyName`;
  для bulk-переноса в другую БД — `UniquifyCollectionName`/`UniquifyGroupName` после копии; для группы
  уникализируется только корень ветки — вложенное легло в новую пустую ветку без конфликтов). **«Изменить»**
  и **«Создать»** (диалоги с полем имени) проверяют уникальность в выбранной БД/группе и при конфликте
  показывают баннер «Коллекция/Группа с таким названием уже существует», не сохраняя (в своей БД — исключая сам
  редактируемый узел; `CollectionDialog`/`GroupDialog`/`CreateItemDialog`). То же — у инлайн-переименования
  коллекции через заголовок над таблицей (`ConstructorControllerView.RenameCurrentCollection`): при конфликте
  имя в заголовке откатывается и у самого заголовка всплывает уведомление — переиспользуемый `Toast.Error(anchor,
  message)` (Flyout, привязанный к контролу, как tooltip; стиль `FlyoutPresenter.toast`; автоскрытие). `Toast` —
  общий помощник для всплывающих уведомлений у любого контрола (расширяется под Info/Success).
- ✅ Операции со свойствами (колонками) и записями (строками) В САМОЙ таблице — без фриза UI и без
  «белого» мелькания на больших коллекциях. [TableView](../../Views/ConstructorDb/TableView.axaml.cs) +
  [ConstructorControllerView](../../Views/ConstructorDb/ConstructorControllerView.axaml.cs).
  **Разделённая перезагрузка.** `Reload()` = колонки + строки, но операции зовут только нужную половину:
  `ReloadColumns()` (пересобрать колонки, кэш строк НЕ сбрасывать) для колоночных, `ReloadRows()` (пересоздать
  источник строк, колонки НЕ трогать) для строковых. Полная пересборка строк сбрасывала бы их в заглушки
  «Загрузка…» (мелькание), полная пересборка колонок (`Columns.Clear`) рушит дерево грида → белый экран 1–2 с
  на 456k строк × много колонок.
  **Точечные изменения набора колонок** (грид выровнен с `_colDefs` 1:1, без `Columns.Clear`): создание/«создать
  после»/дубль — вставка одной колонки (`AddColumnForField`); правка/переименование системной — замена одной на
  месте (`RebuildColumn`); сдвиг влево/вправо — `RemoveAt`+`Insert` одной колонки (`MoveColumn`, своп с соседом).
  У всех — безопасный фоллбек (`SameOrderExcept`) на полную пересборку, если набор/порядок разошёлся.
  **Тяжёлые операции с полем (удаление/дубль) — мимо EF, пакетами, в фоне.** `DeleteFieldData`/`DuplicateFieldData`:
  Id значений поля одним индексным запросом по `(FieldId, Value)` + сортировка по Id → пакеты `Id IN (…)` по 10 000
  (последовательные обновления индексов; прежний OFFSET давал O(n²) — удаление 425k значений ~4 мин → стало ~12 с).
  Удаление поля — каскад на `calendar_index` по FK + чистка `column_order`. Большой объём — на ОТДЕЛЬНОМ подключении
  (`DeleteFieldIsolated`/`DuplicateFieldIsolated`, см. принцип 5).
  **Мультиколоночные удаление и дубль** (`PropertiesDeleteRequested`/`PropertyDuplicateRequested` несут СПИСОК id):
  меню «Удалить»/«Дублировать» обрабатывают всё мультивыделение колонок (системные/обязательные отсекаются); каждая
  копия встаёт сразу за своим исходником одним `SaveColumnOrder`, после дубля — `ReloadColumns`+`ReloadRows` (у копий
  есть значения для уже отрисованных строк, иначе показывали бы пусто до перезапуска).
  **Прогресс без фриза и без блокировки UI до индикатора** (`RunBulkOp`): и подсчёт значений (`CountFieldValuesIsolated`
  — один `GROUP BY` на отдельном подключении), и сама работа идут в фоне (`Task.Run`, изолированные контексты), главный
  контекст из фона не трогаем. Окно прогресса показывается ОТЛОЖЕННО — только если работа не уложилась в ~200 мс
  (мелкие операции проходят без окна). Раньше `COUNT(*)` по каждому полю шёл СИНХРОННО на UI-потоке ДО показа окна → на
  >4 колонках по 456k значений фриз 5 с, и лишь потом индикатор. Фазы: «Подсчёт значений…» (бегущая полоса, пока «всего»
  неизвестно) → проценты → «Сохранение…» (`ProgressDialog.SetSaving`, бегущая полоса на время коммита большой
  транзакции, чтобы 100% не выглядели зависшими; фаза «N/M столбцов» при нескольких полях). Окно МОДАЛЬНОЕ — вторую
  операцию нельзя начать, пока текущая не закрылась (нет накопления параллельной нагрузки), а работа идёт строго по
  очереди на одном подключении. Лишний кросс-БД `CollectionsChanged` после колоночных операций убран (давал «зависон»
  после 100%) — зовётся только если удалили поле-источник календаря (`IsCalStart`).
  **Контекстное меню строки** резолвит `RecordId` лениво из `DataContext` в момент клика (`RowRecordId`): при
  async-подгрузке строка realized как заглушка с `RecordId=0` и заполняется реальным id уже без повторного
  `OnLoadingRow` — из-за захвата старого id дубль падал «Record 0 not found», а удаление было тихим no-op.
- ✅ Пакетное удаление и дубль ВЫБРАННЫХ записей (мультивыделение строк) — bulk-SQL мимо EF, в фоне, с
  индикатором (общий помощник `RunBulkOp`, что и у свойств). Прежний путь — `DeleteRecord`/`DuplicateRecord`
  в цикле с `SaveChanges` на КАЖДУЮ запись — на 1000+ строк давал сотни/тысячи транзакций и фриз UI.
  `DeleteRecordsData` — каскадный DELETE пакетами `Id IN (…)` (значения и `calendar_index` уходят по FK
  ON DELETE CASCADE; `record_display`/`ui_row_heights` FK-связи с записью НЕ имеют — чистим явно, иначе
  осиротевшие настройки прилипли бы к новой записи с тем же rowid — этого не делал и прежний `DeleteRecord`).
  `DuplicateRecordsData` — копии встают СРАЗУ ПОСЛЕ последней (самой нижней по Position, Id) выбранной записи
  (как дубль одной записи, а не в конец таблицы): освобождаем `count` слотов сдвигом ТОЛЬКО хвоста
  (`UPDATE … SET Position += (count+1)*1000 WHERE Position/Id > якоря`, без перенумерации всей коллекции), затем
  записи одним `INSERT…SELECT` в `anchorPos + ранг*1000` + значения пакетами по рангу (новый RecordId = `firstNew` + ранг − 1; `firstNew = last_insert_rowid − count + 1`),
  поля те же (одна коллекция) → FieldId не перемэппливаем; календарь — `FillCalendarIndex` по диапазону новых
  id. Обе — на ОТДЕЛЬНОМ подключении (`DeleteRecordsIsolated`/`DuplicateRecordsIsolated`). Одна запись из меню
  строки — прежний мгновенный путь (удаление сразу; дубль — копия СРАЗУ ПОСЛЕ исходной); много — bulk в фоне.
- ✅ Перенос ВЫБРАННЫХ записей в другую коллекцию/БД (контекстное меню «Расположение», окно
  [`RecordLocationDialog`](../../Controls/Dialogs/RecordLocationDialog.axaml.cs)) — тем же помощником `RunBulkOp`
  в фоне на ОТДЕЛЬНЫХ подключениях (`MoveRecordsToCollectionIsolated` → `MoveRecordsCore`). Перенос в другую
  схему требует сопоставления полей, но без поэлементных `SaveChanges`: план сопоставления (srcFieldId → целевое
  поле + приведение типов `ConvertValueForType`) считается ОДИН раз на пакет (все записи — из одной коллекции),
  значения каждой записи пишутся одним `AddRange`, копирование идёт в одной транзакции (один коммит, трекер EF
  чистим после каждой записи — память не растёт), `calendar_index` наполняется один раз по диапазону новых id
  (как `DuplicateRecordsData`), исходные удаляются bulk-ом (`DeleteRecordsData`). Недостающие в цели свойства при
  галочке «Перенести все свойства» создаются один раз до транзакции. (Календарь: смена коллекции/БД в окне
  события — всегда ОДНА запись, поэтому идёт простым путём `CopyFieldValuesByName` через `SetFieldValue`.)
- ✅ Правка записи в правой панели, сдвиг строк и создание — без полной перезагрузки таблицы.
  **Правка (панель «Страница записи»)**: имя/описание/значения свойств по сохранению шлют `RecordChanged`
  с id записи → [`RefreshRecordRow`](../../Views/ConstructorDb/ConstructorControllerView.axaml.cs) →
  `VirtualRowList.RefreshRecord`: перечитывает ОДНУ запись (`GetRecord`+`GetFieldValues`) и заполняет её
  строку на месте (`Fill`, если она в кеше) — без пересборки. Раньше каждая правка дёргала полный
  `Refresh()` (SelectCollection → пересборка колонок+строк) — на больших коллекциях с множеством колонок это
  «вешало» UI при параллельном редактировании. **Обратная сторона (таблица → панель)**: правка ячейки в
  `TableRowVm` поднимает `Edited` → `VirtualRowList.RecordEdited` → `TableView.RecordValueEdited` → MainWindow;
  если открыта та же запись, `RecordPageView.ReloadFromDb()` перечитывает её на месте (поле в фокусе панели не
  трогает) — синхронизация одной строки, а не полная перезагрузка панели.
  **Сдвиг строки вверх/вниз**: `VirtualRowList.RefreshLoadedPages` перечитывает только ЗАГРУЖЕННЫЕ страницы
  (offset по `(CollectionId, Position)`) и обновляет строки на месте (`Fill`) — порядок меняется, число нет,
  Reset не нужен → нет мелькания «Загрузка…» (раньше `ReloadRows` пересоздавал весь виртуальный список).
  Т.к. строки привязаны к ИНДЕКСАМ, а после пере-Fill запись переезжает в соседний VM, выделение
  переустанавливаем на VM, который теперь держит сдвинутую запись (`FindCachedByRecordId`) — голубая
  подсветка «следует» за записью, а не остаётся на прежней экранной позиции.
  **Создание/удаление/дубль (изменение ЧИСЛА строк)**: вместо пересоздания списка + нового `ItemsSource`
  (полный teardown грида + асинхронные заглушки «Загрузка…» = мелькание) — `ReloadRowsStructural` →
  `VirtualRowList.RefreshStructural`: пересчитывает число строк и СИНХРОННО перестраивает уже загруженные
  страницы реальными данными (+ страницу 0 под прокрутку в начало после Reset), сбрасывает устаревшие
  keyset-курсоры и шлёт мягкий `Reset` на ТОМ ЖЕ источнике. Кеш остаётся ТЁПЛЫМ → грид перерисовывается
  сразу из реальных строк, без заглушек «Загрузка…». При активном фильтре/сортировке — полный `ReloadRows`
  (надо пересобрать список id). Создание вдобавок НЕ зовёт кросс-БД `CollectionsChanged` (пустая новая
  запись не меняет ни список коллекций/групп, ни события календаря) — это убрало ~1 c задержки на мультибазе.
  Важно: вставку ОДНОЙ записи (создание `AddRecordIsolated`, дубль одной `DuplicateRecordIsolated`) делаем
  в ФОНЕ через `Task.Run` + `await`, как удаление/дубль НЕСКОЛЬКИХ. Синхронная вставка-плюс-`RefreshStructural`
  в одном кадре UI заставляла грид моргать именно на ВСТАВКЕ одной строки (удаление в том же синхронном
  кадре моргания не давало); фоновый путь + `await` отдаёт гриду чистый кадр. Размещение прежнее и быстрое:
  копия — по середине после исходной (без сдвига хвоста), создание — в конце/после строки.
  **Выделение (голубая подсветка) после структурных операций**: после `Reset` грид «восстанавливает»
  выделение по СТАРЫМ индексам — а они теперь указывают на другие записи (отсюда съехавшие/задвоенные
  подсветки). Поэтому контроллер переустанавливает выделение явно на РЕЗУЛЬТАТ операции: создание →
  `SelectRecords([новый id])`; дубль (одной/нескольких) → `SelectRecords(<id копий>)` (методы дубля
  возвращают id копий); удаление → `ClearRecordSelection()`. `TableView.SelectRecords` снимает прежнее
  выделение и добавляет VM нужных записей из тёплого кеша (`FindCachedByRecordId`).
  **Высота строк**: ручной ресайз меняет высоту одной строки вживую и сохраняет лишь маленький словарь
  изменённых строк (`ui_row_heights`; стандартные не хранятся; применяются `O(1)` в `OnLoadingRow`).
  Переключение режима «Стандартная ⇄ Ручная» применяет/сбрасывает высоту у уже отрисованных строк на месте
  (`ApplyRowHeightsToRealizedRows`) — без `ReloadRows` и мелькания; невидимые строки получат высоту при
  реализации.
- ✅ Окно «Отображение записей» грузит полный список (сотни тысяч строк) в ФОНЕ на отдельном подключении
  (`GetRecordTitlesOrderedIsolated` + `Task.Run`, индикатор «Загрузка записей…» через `FieldOpDialogDelayMs`) —
  открытие окна больше не подвешивает UI; сам список диалога виртуализирован (`ListBox`), сохранение
  порядка — bulk-SQL (`SaveRecordOrder`).
- ✅ Окна «Отображение» записей/свойств и список значений фильтра — виртуализированы (`ListBox`).
- ✅ Масштабируемый календарь на индексной проекции `calendar_index` (строка на запись × видимое
  поле-дата). Чтение — индексный range-query по `(CollectionId, StartIso)` вместо скана/разбора

  Заодно сняло прежнее узкое место «календарные запросы без индекса». Поддерживает несколько

## Известные узкие места / TODO

- **Строковые `Value` (EAV).** Фильтр по равенству и сортировка работают, но «число > N»,
  «дата в диапазоне» по строкам некорректны и не индексируются типобезопасно. Решение —
  типизированные колонки `ValueNumber/ValueDate` + индексы (Этап 4, см. [[../ROADMAP]]).
- **1000+ колонок — UI-проблема.** DataGrid создаёт ячейки всех колонок для каждой видимой
  строки; меры по БД её не решают. Решение — ограничение видимых колонок через сохранённые
  представления (Этап 3) + виртуализация списка свойств на странице записи.

## Как мерить

- `Stopwatch` вокруг методов репозитория (чтение страницы, импорт, выборка диапазона).
- Синтетика: генерировать 100k+ записей/строк и воспроизводить сценарий (так уже
  замеряли чтение Excel и взрыв числа столбцов CSV).
- На что смотреть: число SQL-запросов на действие, рост памяти, скрытые O(n²)
  (пагинация, трекер EF, перебор всех строк в UI).
