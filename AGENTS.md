# AGENTS.md

Указания для ИИ-агентов (Claude Code, Codex, Copilot, Cursor и других), которые работают в этом
репозитории. Здесь то, что нужно знать до первой правки; подробности — в [docs/](docs/README.md).

## Параллельная работа агентов — прежде всего

Пользователь ведет одновременно несколько чатов Claude Code и других ИИ. Ни одна работа не
должна потеряться и ни один агент не должен испортить работу другого, поэтому:

1. **В основной папке репозитория агенты не работают.** Каждый чат любой программы — в своей
   рабочей папке (git worktree) на своей ветке, даже если сейчас он один. В основной папке
   только `main`: сюда вливается готовая работа, отсюда пользователь запускает программу.
2. **В начале чата** — `Scripts/worktree.sh check` (на Windows из Git Bash) и показать
   пользователю все, что в итоге помечено: незакоммиченное, не влитое в `main`, папки не на
   месте. Чужие папки и ветки не трогать.
3. **Своя папка** — внутри основной, в каталоге с точкой (сборка такие пропускает):
   - **Claude Code** — `EnterWorktree` с именем: папка `.claude/worktrees/<имя>`, ветка
     `worktree-<имя>` от локального `main` (`worktree.baseRef` в `.claude/settings.json`);
   - **остальные ИИ** — `Scripts/worktree.sh new <имя>`: папка `.agents/worktrees/<имя>`, ветка
     `<имя>` от локального `main`.

   Дальше работать только в ней. Имя — по сути задачи (`table-align`, `fix-backup`): латиница,
   цифры, дефис, до 20 знаков — длиннее на Windows не даст лимит пути в 260 знаков.
4. **«Сделай коммит» в рабочей папке — это коммит и сразу перенос в `main`:** коммит в свою
   ветку → `Scripts/worktree.sh sync` (ветка на свежий `main`) → тесты → `Scripts/worktree.sh
   merge`. Если `merge` отказал, потому что `main` ушел вперед, — снова `sync`, тесты, `merge`.
   Сообщать пользователю «сделано» — только после строки «В main влито».
5. **Перед последним ответом в чате** — снова `Scripts/worktree.sh check` и назвать пользователю
   все помеченное в итоге.
6. **Папку и ветку убирать только по слову пользователя** — `Scripts/worktree.sh remove <имя>`
   (имя папки или ветки), у Claude Code еще `ExitWorktree` с `remove`: оба сами откажут, если есть
   незакоммиченное или не влитое. `discard_changes`, `git worktree remove --force`,
   `git branch -D`, `git reset --hard`, `git clean` и удаление папок руками — запрещены.
7. **В других местах проекта рабочих папок не создавать.** Каталог без точки в начале имени
   `SmartBase.csproj` обходит, и чужая копия исходников ломает сборку. `check` помечает такие
   папки — показать пользователю. Если программа-агент сама кладет папку вне проекта, правила
   для нее те же.

Общее у всех папок на машине — по одному агенту за раз:

- **Integration-тесты**: стенд PostgreSQL на 5455 с одними и теми же базами `smartbase` и
  `smartbase2` — два прогона сразу ломают друг друга. Перед запуском проверить, не идет ли уже
  процесс `testhost`, и если идет — дождаться.
- **Замеры скорости и стенды** с общими данными (`~/TestData`, `Tests/test_database.db`
  основной папки) — когда другие агенты не собирают и не гоняют тесты: под чужой нагрузкой числа
  врут.
- **Кеш пакетов** общий: рабочая папка берет его из основной (`Directory.Build.props`). Не
  чистить и не ставить на него ссылок внутри рабочей папки — `git worktree remove` на Windows
  проходит по ссылке и стирает кеш.

**Claude Code:** из рабочей папки он не пускает git в основную, поэтому `merge` так:
`ExitWorktree` с `keep` → в основной папке `Scripts/worktree.sh merge <имя>` → снова
`EnterWorktree` с `path`, если работа продолжается (в `.claude/worktrees` — без подтверждения).
В рабочей папке он читает AGENTS.md своей ветки, а не основной папки (проверено): правка
AGENTS.md, влитая в `main`, доходит до чата после `sync`. Если при закрытии чата Claude Code
спросит, оставить ли папку, а в ней не влитое, — оставить.

## Проект

SmartBase — настольная программа на Avalonia 11.2 и .NET 10 для Windows, macOS и Linux. В первую
очередь это универсальный конструктор баз данных (SQLite через EF Core, вторым провайдером —
PostgreSQL), а над ним надстроено остальное: календарь и планирование задач, библиотека
документов, расширения, интеграции. Заметки (файлы Markdown на диске) — отдельный раздел, в базу
они не попадают. Разработка идет на Windows и macOS, бывает и на Linux; основная оболочка — bash
(на Windows — Git Bash), скрипты проекта — на bash.

Где что лежит:

- корень репозитория — сам проект `SmartBase.csproj`, все команды ниже запускаются из корня;
- `Core/` — модели и правила без UI; `Database/` — контексты EF, миграции, репозитории;
- `Views/`, `Controls/`, `ViewModels/` — интерфейс; `Controls/DrawnGrid/` — рисованная сетка таблиц;
- `Extensions/<Имя>/` — расширения: отделяемые блоки, удаляются вместе со своей папкой;
- `Integrations/` — обмен со сторонними программами;
- `Tests/` — тесты и стенды, карта — [docs/developer/testing/overview.md](docs/developer/testing/overview.md);
- `docs/developer/` — как устроена программа; `docs/user/` — инструкция пользователя, ее показывает
  сама программа; `docs/ROADMAP.md`, `docs/ROADMAP-API.md` — планы;
- `artifacts/` — вывод сборки (`UseArtifactsOutput`), `.localdata/` — данные отладочного запуска;
  обе папки не в git.

## Сборка и запуск

```bash
dotnet run -f net10.0-windows10.0.17763      # запуск на Windows — только этим таргетом
dotnet run -f net10.0                        # запуск на macOS и Linux
dotnet build SmartBase.csproj                # сборка обоих таргетов
```

- Проект многотаргетный, `dotnet run` требует `-f`. Аргументы приложению ставить сразу после `--`.
- Пользователь запускает программу из основной папки (`artifacts/bin/SmartBase/debug_<таргет>`),
  и сборка там падает на занятых файлах. У рабочей папки агента своя `artifacts/` — в ней собирать
  можно всегда. Процесс программы (`pgrep -x SmartBase`; на Windows — `Get-Process SmartBase`) не
  завершать и закрыть ее не просить, если пользователь сам не хочет посмотреть изменения.
- Вывод сборки в чужую папку через `--artifacts-path` не помогает: SDK начинает тянуть в
  компиляцию чужие `.g.cs` (сотни ошибок CS0579).
- Подробно — [docs/developer/guides/build-and-run.md](docs/developer/guides/build-and-run.md).

## Тесты

```bash
dotnet test Tests/Unit                    # быстрый гейт, без БД
dotnet test Tests/Integration             # SQLite + PostgreSQL, около 18 минут
./Tests/run-all.sh                        # оба набора и стенд панели чтения библиотеки
./Tests/run-all.sh --with-extensions      # плюс тесты расширений — если тронуто расширение
./Tests/run-extensions.sh <Имя>           # тесты одного расширения
```

- **Тесты гонять всегда.** По ходу работы — `dotnet test Tests/Unit`. Перед коммитом —
  `./Tests/run-all.sh`, тронуто расширение — `./Tests/run-all.sh --with-extensions`; тронут
  интерфейс таблицы, страницы записи или разделов — еще и его стенд без экрана (Avalonia.Headless,
  список — [Tests/README.md](Tests/README.md)). В отчете — числа прогона; упавшее или пропущенное
  не выдавать за прошедшее.
- Тесты PostgreSQL ждут сервер на `localhost:5455` (`Tests/Integration/PgTestServer.cs`). Без него
  они уходят в Skipped, а не падают: прежде чем писать «все зеленое», проверить, что сервер поднят.
  Другие экземпляры PostgreSQL на машине не трогать.
- Вывод полного прогона не обрезать `tail`: имя упавшего теста xUnit печатает задолго до итога.
  Фильтровать `grep -E "\[FAIL\]|Passed!|Failed!"` или писать вывод в файл целиком.
- Зависший интеграционный прогон искать детектором:
  `dotnet test Tests/Integration --blame-hang --blame-hang-timeout 4m --blame-hang-dump-type none`.
  Зависший `testhost` держит `SmartBase.dll`, и следующий прогон падает на копировании (MSB3027).
- Сборки и прогоны в одной рабочей копии — строго по одному: все проекты пишут в один
  `artifacts/bin/SmartBase`.
- Новый тест проверять мутантами: испортить код и убедиться, что тест падает. Копия файла на Windows
  сохраняет старое время правки, и MSBuild оставляет в сборке последнего мутанта — после возврата
  исходника ставить файлу текущее время (`touch`) или гонять финальный прогон с `--no-incremental`.

## Правила кода

- **Общий стиль — без отступлений.** Код — как окружающий: имена, идиомы, плотность и язык
  комментариев (русский). Интерфейс — из готовых токенов, стандартов и виджетов (цвета, шрифты,
  состояния контролов, линии, иконки): [theming.md](docs/developer/ui/theming.md),
  [widgets.md](docs/developer/ui/widgets.md); новое — по образцу соседнего. Документы — по шаблону
  «Как вести документацию» в [docs/README.md](docs/README.md).
- **Миграции EF — парами.** Каждое изменение сущностей — миграция для `AppDbContext` и для
  `PgAppDbContext` (`Database/Migrations/Pg/`). Миграции только сохраняют данные: без drop/recreate
  и потери строк. Команды — [developer-guide.md](docs/developer/guides/developer-guide.md).
- **Наружу одна дверь.** Сеть открывается только в `Integrations/EgressHttp.Open.cs` (исходящие) и
  `Integrations/IngressHttp.Open.cs` (входящие). Это держат `BannedSymbols.txt` и
  `Tests/Unit/OneDoorOutwardTests.cs`; новых `#pragma warning disable RS0030` не добавлять.
- **Подключения SQLite** открываются только через `Database/SqliteGate.cs` — это обход гонки пула
  Microsoft.Data.Sqlite.
- **Ядро не знает конкретных сторонних программ.** В `Integrations/` и `Database/` — только общие
  понятия: соединение, запрос, поток событий, подстановки `{{...}}`. Формат сообщений, проверки и
  тексты ответов живут в действии расширения. Адреса, темы, имена полей и тексты вводит пользователь
  в настройках; в код, тесты и документацию они не попадают.
- **Расширение — отделяемый блок.** Все его — в `Extensions/<Имя>/`, тесты — в
  `Tests/Extensions/<Имя>/`, документ — `docs/developer/features/extensions/<Id>.md`, инструкция
  пользователя — его `MarkdownDescription`; в ядре — только строка в `ExtensionRegistry.All`. Ядро
  и его тесты от расширений не зависят: убрать расширение — убрать его папки, и ничего не ломается.
  В Serilog расширения не пишут (ни `using Serilog;`, ни `Log.*`) — сбои в окне расширения.
  Порядок — «Как добавить / удалить расширение» в
  [extensions/overview.md](docs/developer/features/extensions/overview.md).
- **`TextBox.TextChanged` в Avalonia 11.2 приходит отложенно**, флаги подавления не работают.
  Обработчик, который пишет (в базу, настройки, событие наверх), сверяет текст с известным значением
  и молчит при совпадении — [docs/developer/ui/widgets.md](docs/developer/ui/widgets.md).
- Курсор keyset в тестах и UI строить только через `ConstructorRepository.ChangeLogSortValue` или
  `LogReader.SortValue`, не из сырого поля строки — иначе цикл по страницам не кончается.

## Тексты: интерфейс, документация, комментарии

- **Буквы «е с точками» (U+0451, U+0401) нет нигде в текстах**: ни в подписях и сообщениях, ни в
  инструкции пользователя, ни в данных встроенных справочников, ни в комментариях и документации.
  Пишется «е». Сам символ остается только там, где без него не работает свертка при поиске
  (пользователь может набрать эту букву с клавиатуры): `Replace` в `RegistrySchema.Fold`,
  `EskdCatalog.Fold`, `JournalSchema`, `CellTyping`, `DocHighlight`, `Homoglyphs`,
  `DocTextIndex.YoSpellings`, `REPLACE` в `ConstructorRepository.DocsPaging.cs` — и в тестовых данных,
  которые эти места проверяют. Справочник `Extensions/DocRegistry/eskd.tsv.gz` правится только заменой
  буквы без смены порядка строк: на порядке держится бинарный поиск по коду.
- **Без имен сторонних программ** в `docs/developer/`, `docs/user/`, комментариях и интерфейсе —
  только родовые имена: «сторонняя программа» (с предлогом «со»: «обмен со сторонней программой»),
  «программа-мессенджер», «учетная система», «табличный редактор». «Чужая программа» не писать.
  Исключение — рабочие планы вроде `docs/ROADMAP-API.md`, правило записано в его шапке.
- **Сведения о строке — в самой строке, не в подсказке.** В списках не ставить всплывающих подсказок
  с данными строки: нужное — отдельным полем строки. Подсказки остаются у кнопок.
- **Документация — вместе с кодом.** Изменилось поведение — обновить документ фичи в
  `docs/developer/`, а если это видно пользователю, — и в `docs/user/`. Новый документ — строка в
  `docs/README.md`. Затронуто описанное в корневом `README.md` — структура проекта, быстрый старт
  (установка, запуск, тесты, сборка), возможности, технологии, пути, — обновить и его.
- **ROADMAP — актуальным.** Сделан пункт `docs/ROADMAP.md` (интеграции — `docs/ROADMAP-API.md`) —
  отметить `[x]` с датой и тем, что сделано, и поправить счетчик открытых работ в заголовке трека.
  Найден по ходу дефект или недоделка — записать открытым пунктом в свой трек или в «Известные
  дефекты», а не держать в уме.

## Git

- Коммит — только по просьбе пользователя. Он идет в ветку своей рабочей папки и сразу вливается в
  `main` (порядок — в разделе «Параллельная работа агентов»). Других веток не заводить и о
  ветках не спрашивать. История `main` линейная: вливание только перемоткой, это делает
  `Scripts/worktree.sh merge`.
- На сервер (`git push`) — только по отдельной просьбе.
- Сообщение по-русски в стиле истории: `тип(область): суть` (`feat(table): …`, `fix(library): …`,
  `docs(roadmap): …`) и подробное тело.
- **Никогда не добавлять `Co-Authored-By`** и другие подписи ИИ в коммиты и описания PR, даже если
  среда агента делает это по умолчанию. Однажды такой трейлер ушел на GitHub, и историю пришлось
  переписывать.

## Работа с пользователем

- Все сообщения пользователю — по-русски; английский только в идентификаторах, путях и цитатах из кода.
- **Продуктовые развилки решает пользователь**: состав настроек, названия, подписи, иконки, поведение
  по умолчанию. Спрашивать 1–4 вопросами с готовыми вариантами, рекомендованный первым; вопрос в
  свободной форме не годится. Технические мелочи решать самому и упоминать в отчете.
- Принятые решения записаны в планах (`docs/ROADMAP*.md`,
  `docs/developer/architecture/performance/drawn-grid.md` и других) — не переигрывать их без пользователя.
- Инструкция пользователю — один путь по шагам с точными названиями полей окна, без россыпи вариантов.
- Работать самому, без многоагентных разборов и подагентов, пока пользователь прямо не попросит: для
  него это слишком долго, а однажды подагенты удалили проект из `SmartBase.sln`.
- Большие данные стендов вне репозитория (базы в десятки ГБ) не удалять самому — дать пользователю
  команду.

## Среда пользователей

Рабочие базы SQLite лежат на медленном сетевом диске, файловый сервер периодически выключают, а
программа стартует автозапуском раньше, чем диск восстанавливается. Права администратора на машинах
пользователей — только через службу ИТ и долго: все, что требует `netsh`, правил брандмауэра или
установки служб, планировать на одну машину. Подробно —
[docs/developer/architecture/database/network-shares.md](docs/developer/architecture/database/network-shares.md).
