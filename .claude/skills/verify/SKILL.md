# Проверка приложения DataBase вживую

## Сборка и запуск

```powershell
dotnet build DataBase.csproj -v q --nologo        # ~1 мин
Start-Process "artifacts\bin\DataBase\debug\DataBase.exe"
# старт ~8 секунд до окна
```

Debug-данные лежат в `.localdata\` в корне репозитория (app.db — настройки/реестр,
database.db + подключённые БД — данные). Настройки — таблица `app_settings(Key,Value)`
в app.db: `calendarView` (0–6, стартовый вид календаря), `startupModule`
(`calendar`/`constructor`/`extensions`).

## Ограничения машины

- НЕТ `sqlite3`, `python`, `py` — в БД напрямую не залезть; менять настройки
  только через UI приложения (или собрать мини-утилиту на dotnet).
- PowerShell 5.1 (.NET Framework) НЕ грузит .NET 9-сборки приложения (Add-Type падает).

## Визуальная проверка — ТОЛЬКО через пользователя

Скриншоты приложения делает САМ пользователь и присылает в чат — НЕ снимать
экран и НЕ гонять мышь автоматикой (перехватывает его мышь/фокус и ловит его
промежуточные состояния как ложные «баги»). После сборки/перезапуска — попросить
пользователя проверить и ждать его скриншот/отчёт.

Технически автоматика возможна (user32: `SetForegroundWindow`, `GetWindowRect`,
`SetCursorPos`, `mouse_event`; скриншот `Graphics.CopyFromScreen`), но применять
только по явной просьбе; drag через `mouse_event` ненадёжен (артефакт
синтетического ввода), `SetForegroundWindow` может не сработать (окно за IDE).

## Что стоит прогонять после изменений календаря

Переключение всех видов ComboBox'ом, навигация ←/→/«Сегодня», клик по событию
(диалог), drag/resize, поиск, галки коллекций в сайдбаре, пустой месяц.
